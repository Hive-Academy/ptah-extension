Best practices for building custom Kubernetes Operators in Go

Sarah Chen verified Core Team
Posted 2 hours ago • Edited

I've been reviewing a lot of community PRs lately involving custom controllers and operators. While the functionality is often great, I'm noticing a recurring pattern of issues related to state reconciliation and client usage.

Here are a few key practices we should standardise on:

  • Always use Informers: Never poll the API server directly in your reconcile loop. Use `cache.SharedIndexInformer` to keep a local, watch-updated cache.
  • Idempotent Reconciliation: Your reconcile loop must be idempotent. It should arrive at the desired state regardless of how many times it is triggered for the same object.
  • Update Status Subresource Separately: Avoid updating the spec and status in the same API call to prevent conflicts.

Here is a basic example of a clean setup using controller-runtime:

import (
    "context"
    "k8s.io/apimachinery/pkg/runtime"
    ctrl "sigs.k8s.io/controller-runtime"
    "sigs.k8s.io/controller-runtime/pkg/client"
    "sigs.k8s.io/controller-runtime/pkg/log"
    
    myappv1 "github.com/example/operator/api/v1"
)

type MyReconciler struct {
    client.Client
    Scheme *runtime.Scheme
}

func (r *MyReconciler) Reconcile(ctx context.Context, req ctrl.Request) (ctrl.Result, error) {
    logger := log.FromContext(ctx)
    // Fetch the MyResource instance
    var resource myappv1.MyResource
    if err := r.Get(ctx, req.NamespacedName, &resource); err != nil {
        return ctrl.Result{}, client.IgnoreNotFound(err)
    }

    logger.Info("Reconciling MyResource", "name", resource.Name)
    // ... business logic ...
    return ctrl.Result{}, nil
}

What patterns have you all found most robust for handling transient API errors during reconciliation?

For transient API errors, implementing exponential backoff in the requeue logic is crucial. If an API call fails (like updating status), don't just return an error which triggers immediate requeue.

Instead, return ctrl.Result{RequeueAfter: time.Second * 5} (or a variable backoff) along with the error. Controller-runtime handles this gracefully, preventing hot loops against the API server.

@Jason Davies Absolutely. We almost exclusively use `envtest` for our controllers now. It stands up a real control plane (API server and etcd), so you are testing against actual Kubernetes behaviour, not a mocked client's interpretation of it. It catches so many subtle state bugs.

Just to add to Sarah's excellent points: when working with `envtest`, make sure you are properly handling the teardown phase. Leaking API servers in your test suite can cause massive slowdowns in CI.

We've added a new helper library in the ptah-core pack that wraps envtest setup/teardown in a Ginkgo suite to make this foolproof.
