Best practices for building custom Kubernetes Operators in Go

PACKS
Sarah Chen Core Team
2 hours ago

When building operators using controller-runtime, I frequently see developers struggling with state reconciliation loops. The most common anti-pattern is treating the Reconcile() function as an event handler rather than a level-based state synchronizer.

After reviewing several internal packs last week, I've compiled a few critical pitfalls to avoid when setting up your managers and controllers:

  • Ignoring cache sync states before attempting to read resources.
  • Failing to implement proper backoff via ctrl.Result{RequeueAfter: ...} on transient errors.
  • Leaking goroutines in custom source watchers.
  • Misusing finalizers, leading to deadlocked namespace deletion.
main.go 
func (r *MyReconciler) Reconcile(ctx context.Context, req ctrl.Request) (ctrl.Result, error) {
    // Fetch the custom resource
    var cr myv1.CustomResource
    if err := r.Get(ctx, req.NamespacedName, &cr); err != nil {
        if errors.IsNotFound(err) {
            return ctrl.Result{}, nil
        }
        return ctrl.Result{}, err
    }

    // ALWAYS rely on state, not events
    if !cr.ObjectMeta.DeletionTimestamp.IsZero() {
        return r.handleDeletion(ctx, &cr)
    }

    return r.syncState(ctx, &cr)
}

Another edge case to watch for is handling status subresource updates. If you update the status but return an error to force a requeue, the status update might get lost if it conflicts with another controller. Always return ctrl.Result{Requeue: true}, nil after a successful status update to ensure a clean cycle.
