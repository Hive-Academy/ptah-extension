# PtahCode browser replay spike

Run `node task-tracking/landing-live-demo/spike/capture.mjs` after the webview build exists. The script starts an in-process static server, opens Chromium at 1440×900, captures boot, stream, and completion frames, and writes `evidence/run.json`. `node task-tracking/landing-live-demo/spike/serve.mjs [port]` serves the page for manual inspection (default port 4873). The page accepts `?autoplay=0` for manual controls through `window.__ptahReplay`; an embedding parent can post `{source:'ptah-replay-control',cmd:'play'|'pause'|'speed'|'restart',value}`. The bridge rejects nonstatic fetch/XHR and all WebSocket/EventSource attempts; Playwright also aborts external resource requests.

## Implementation and contracts

- `replay-bridge.js` installs the same `window.vscode` methods and `window.ptahConfig` shape as Electron preload (`apps/ptah-electron/src/preload.ts:24-53`), before the Angular script. The frontend reads those globals in `libs/frontend/core/src/lib/services/vscode.service.ts:124-145`.
- The bridge responds to `rpc:call` using `payload.method` and `payload.correlationId`, then dispatches a `rpc:response` with a top-level `correlationId`, `success`, and `data`. These are the frontend wire shapes in `libs/frontend/core/src/lib/services/claude-rpc.service.ts:215-224,250-267`. An unanswered method gets `{success:true,data:null}` and a logged miss.
- The scenario uses `chat:chunk` payloads with `tabId`, `sessionId`, and a flat `event`, as consumed by `libs/frontend/chat/src/lib/services/chat-message-handler.service.ts:526-561`. Event fields and types come from `libs/shared/src/lib/types/execution/stream.ts:60-166` and `libs/shared/src/lib/types/execution/stream-background.ts:303-340`. Turn completion uses `session:turnEnded`, parsed at `libs/frontend/chat/src/lib/services/chat-message-handler.service.ts:450-467`; its payload contract is `libs/shared/src/lib/types/sdk-hook.types.ts:115-123`.
- The scenario's `license:getStatus` answer uses the free `community` tier defined in `libs/shared/src/lib/types/rpc/rpc-misc.types.ts:276-310`. `session:list`, `session:load`, and `chat:resume` answers follow `libs/shared/src/lib/types/rpc/rpc-session.types.ts:119-134,256-278` and `libs/shared/src/lib/types/rpc/rpc-chat.types.ts:345-360`.
- The production Angular index has `<base href="/">` at `apps/ptah-extension-webview/src/index.html:6`, so `serve.mjs` serves the build at `/`. It removes CSP meta and injects the bridge into the document head before the inline theme script. VS Code injects a delayed `webview-ready` signal (`apps/ptah-extension-vscode/src/services/webview-html-generator.ts:497-506`), while Electron has no ready message (`apps/ptah-electron/src/preload.ts:18-51`). For deterministic playback, the bridge synthesizes that signal after the app root renders. The `ptahConfig` workspace `/workspace/acme-app` and `electron-main` panel match the Electron preload field pattern (`apps/ptah-electron/src/preload.ts:35-51`).
- The Electron shell switches workspace after `TabManagerService` creates an initial session tab. That first switch reads a separate workspace tab key and otherwise drops the requested tab (`libs/frontend/chat-state/src/lib/tab-manager.service.ts:724-760,847-865`; `libs/frontend/chat-state/src/lib/tab-workspace-partition.service.ts:194-232,559-589`). The bridge seeds a sanitized fake tab and its optimistic user prompt under that key before Angular starts. This follows the `ExecutionChatMessage` shape (`libs/shared/src/lib/types/execution/agent.ts:85-120`) and the normal live user echo behavior (`libs/frontend/chat-streaming/src/lib/streaming-handler.service.ts:505-520`). The streamed user `message_start` is still present in the timeline, but the live renderer expects an optimistic prompt bubble first.
- Reused the harness's early bridge installation and `MessageEvent` injection pattern from `libs/frontend/webview-e2e-harness/src/lib/postmessage-bridge.ts:47-92`, its CSP neutralization rationale and checked-in font copies from `libs/frontend/webview-e2e-harness/src/lib/csp-stub.ts:7-40,50-75`. The actual Angular boot precedent is `libs/frontend/webview-e2e-harness/src/lib/scenarios/boot/boot-progress.e2e.spec.ts:20-114`. The harness chat specs that mount a minimal receiver are not used as evidence of real chat rendering.

## Measured result

Chromium rendered the real SPA shell, the user prompt, streamed assistant chunks, a `Read` tool call/result, final text, and the completed turn. `evidence/boot.png`, `evidence/mid-stream.png`, and `evidence/complete.png` show those stages. The mid-stream screenshot visibly shows `Read main.ts`; the final screenshot shows the turn summary. I compared them with the actual PtahCode webview layout: session list at left, transcript in the middle, and session inspector at right. There was no separate design mock supplied.

From the successful capture (individual timings vary with Chromium startup):

| JS + CSS scope | Raw bytes | Gzip bytes | Brotli bytes |
| --- | ---: | ---: | ---: |
| Entire build, excluding maps | 23,329,859 | 5,544,909 | 5,498,139 |
| Files requested on initial page load | 4,072,288 | 1,047,432 | 1,037,977 |

The capture requested 52 URLs. It recorded zero unanswered RPC methods, zero unknown outbound messages, zero console errors, and zero external requests. `evidence/run.json` retains each request URL, method, resource type, status, and response content length, plus individual JS/CSS sizes. First contentful paint was 1,068 ms, shell-ready signal was 18,721 ms, and playback completed 26,518 ms after navigation started in that run. These are headless local measurements, not a production performance estimate.

Every distinct RPC method called during boot/playback was answered by the scenario: `config:models-list`, `config:pricing-get`, `config:effort-get`, `workspace:getInfo`, `config:autopilot-get`, `ptahCli:list`, `session:cli-sessions`, `session:status`, `auth:getAuthStatus`, `license:getStatus`, `displayWindow:status`, `update:get-state`, `boot:getReadiness`, `attention:getSnapshot`, `session:load`, `artifacts:list`, `chat:agent-sessions`, `git:turnChangeSets`, `workspace:switch`, `auth:getScope`, `chat:resume`, `session:list`, `provider:getPlanLimits`, `chat:setStreamViewport`, `git:info`, `git:branches`, `git:stashList`, and `git:lastCommit`. The only outbound types were `rpc:call` and the synthesized `webview-ready`. Host-to-webview types were `rpc:response`, `chat:chunk`, and `session:turnEnded`.

## Known limits

The first boot had invalid `update:get-state` and analytics answer shapes, which caused Angular errors; both now have real envelopes. Missing boot RPC answers were added after inspecting `window.__ptahReplay.misses`. The empty transcript was caused by the workspace tab switch described above. The app's chat redirect checks `AuthStateService.hasAnyAuth()` (`libs/frontend/chat/src/lib/components/templates/app-shell.component.ts:275-305`); its installed Claude CLI branch accepts our synthetic auth answer (`libs/frontend/core/src/lib/services/auth-state.service.ts:449-468`). The free `community` license answer populates membership state but does not gate chat (`libs/frontend/chat/src/lib/services/chat-store/chat-lifecycle.service.ts:80-90`). The server rewrites gstatic font URLs in CSS to the harness's checked-in font copies, and the bridge's `theme-v2` state selects the app's dark `ptah-glass` theme (`apps/ptah-extension-webview/src/index.html:2,38-85`).

Remaining limits: this is one hand-made chat scenario, with fake workspace and git data. The right inspector shows plan usage as unavailable because the fake free-tier provider has no live quota. The bridge does not implement any real host write, authentication, repository action, or other workspace flow. The full build still weighs about 23.3 MB raw JS/CSS even though the initial requested subset is about 4.1 MB raw.

Ptah skill discovery was available, but returned no local matching skill for this spike. The coordinator owns repository lint, test, typecheck, and build verification; none was run here.
