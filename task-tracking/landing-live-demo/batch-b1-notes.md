# B1 — PtahCode replay runtime

## Files and design

- `libs/web/landing/src/lib/live-demo/runtime/replay-bridge.entry.ts`: installs storage isolation, the network guard, Electron-shaped host globals, RPC answers, readiness detection, the playback engine, and parent controls before Angular runs. It exposes `window.__ptahReplay` with state, misses, calls, outbound messages, and controls.
- `types.ts`, `scenario-loader.ts`, `time-shift.ts`: local structural scenario contract, validated query and scenario URL, and immutable recursive timestamp shifting. No Angular or shared runtime imports.
- `memory-storage.ts`, `network-guard.ts`, `install-host-globals.ts`: separate in-memory `Storage` objects, same-origin-under-base checks for fetch/XHR/WebSocket/EventSource/sendBeacon, and Electron preload-compatible globals without `initialSessionId` or app-key seeding.
- `rpc-responder.ts`, `ready-detector.ts`, `playback-engine.ts`, `control-channel.ts`: parameter-subset RPC cases before errors before method defaults, top-level `rpc:response` envelope, `ptah-root` + 300 ms quiet or 8 s cap, scheduled replay with pause/speed/restart, and strict parent origin/source checks with state throttling.
- `disable-dynamic-function.ts`: proxies `window.Function` before Angular starts so Zod v4's JIT feature probe receives an `EvalError` without causing a CSP `securitypolicyviolation`. The proxy preserves `Function.prototype` and `instanceof Function`, which Angular DI needs.
- `boot-quiet.ts`: wait another 300 ms without RPC call or response activity after the `switchView` boot message opens the session; a 5 s cap records a miss and allows playback to start.
- `replay-runtime.spec.ts`: jsdom checks for storage, query, timestamp shift, RPC precedence/envelope/miss, readiness, playback, control channel, and blocked network.

## Exact session-open path

1. Electron preload supplies `ptahConfig` with `workspaceRoot`, `workspaceName`, `panelId: 'electron-main'`, and `initialView`, but a normal Electron preload does not supply `initialSessionId` (`apps/ptah-electron/src/preload.ts:35-51`). The runtime uses that shape. `TabManagerService` reads storage and creates **no default tab** without `initialSessionId` (`libs/frontend/chat-state/src/lib/tab-manager.service.ts:724-760`). The first workspace switch replaces the active partition's tabs (`tab-manager.service.ts:847-865`; `tab-workspace-partition.service.ts:194-232,559-589`).
2. The scenario must answer `workspace:getInfo` with `{ folders: ['/workspace/acme-app'], activeFolder: '/workspace/acme-app' }`, then `workspace:switch` with `{ success: true }`. `ElectronLayoutService` requests and coordinates this in order (`libs/frontend/core/src/lib/services/electron-layout.service.ts:847-908`). `session:list` then supplies the synthetic session row (`libs/frontend/chat/src/lib/services/chat-store/session-loader.service.ts:209-225,522-560`). This populates Previous sessions, but does not open a tab.
3. The scenario's `bootMessages` sends `switchView` with `view: 'chat'`, a valid `sessionId`, and an optional `sessionName`. `AppStateManager.handleMessage` switches views and calls `requestOpenSession`; `SessionOpenBridgeService` uses the existing canvas session path. This opens the first tab through the host message and scenario RPC answers, without storage seeding or `initialSessionId`.
4. That path requests `session:load`, creates a tab with `TabManagerService.openSessionTab`, then requests `chat:resume` (`libs/frontend/chat/src/lib/services/chat-store/session-loader.service.ts:925-1012`). Scenario RPC answers include `session:load` with `messages` and `agentSessions`, `chat:resume` with `events`, `historyPage` and `cliSessions`, plus `session:cli-sessions` and `session:status`. The runtime waits for an RPC quiet period before playback. Timeline messages carry the same `sessionId` and omit `tabId`; the app resolves the tab by `sessionId`.
5. After a tab exists, send timeline messages in order: `chat:chunk` user `message_start`/`text_delta`; `turn_state` with `phase: 'generating'` and revision 2; assistant `message_start`; text and tool chunks; assistant `message_complete`; terminal `turn_state` with `phase: 'idle'` and revision 3; `session:turnEnded`. `turn_state` drives the tab status (`libs/frontend/chat-streaming/src/lib/turn-state-applier.service.ts:16-86`). `message_complete` precedes idle per the scenario contract. The second quiet period gives the resumed session time to settle before these messages play.

## Proposed contract addition

`ReplayScenarioData.bootMessages?: ReplayMessage[]` is the session-open contract. The runtime injects these once after readiness, then waits for a fresh RPC quiet period before playback. Timeline events use `sessionId` only and omit `tabId`.

## Follow-up — autonomous session open

- `ViewChangedPayload` in `libs/shared/src/lib/types/messages/payload-map.ts` now permits optional `sessionId` and `sessionName`. `AppStateManager.handleMessage` in `libs/frontend/core/src/lib/services/app-state.service.ts:361-369` switches views normally, then publishes `requestOpenSession({ sessionId, name })` for chat with a non-empty string ID. `SessionOpenBridgeService` consumes that request through the existing canvas session path. Specs cover an ID and name, empty/non-string IDs, and another view.
- **Tab ID decision:** the scenario must **omit `tabId`** on timeline events. `ChatMessageHandler.handleChatChunk` accepts absent `tabId` and passes `sessionId` through (`libs/frontend/chat/src/lib/services/chat-message-handler.service.ts:534-561,565-587`). `StreamingHandlerService` finds an active tab by the event's `sessionId` (`libs/frontend/chat-streaming/src/lib/streaming-handler.service.ts:312-335`); `session:turnEnded` resolves by `sessionId` (`libs/frontend/chat/src/lib/services/chat-store/turn-end-handler.service.ts:96-123`). The runtime uses session IDs to route timelines. No storage seeding is used.
- Recorded timestamps are shifted once when the scenario loads. Pause, resume, and speed changes do not shift them again; scenario authors should keep numeric IDs in the recorded-time window as strings.
- `disableDynamicFunction()` runs before Angular starts (`libs/web/landing/src/lib/live-demo/runtime/replay-bridge.entry.ts:14-15`). Its Proxy preserves `Function.prototype` and `instanceof` while making construction and calls throw `EvalError` before Chromium reports a CSP `eval` violation. A runtime spec covers both forms and prototype behavior.
- `bootMessages` are injected once after readiness; the runtime waits for a fresh 300 ms quiet period after boot RPC calls and responses before autoplay. The B2 scenario form is exactly:

  ```json
  "bootMessages": [{ "type": "switchView", "payload": { "view": "chat", "sessionId": "11111111-1111-4111-8111-111111111111", "sessionName": "Explore the project" } }]
  ```

  Each `chat:chunk` timeline payload is `{ "sessionId": "11111111-1111-4111-8111-111111111111", "event": { ... } }` with **no `tabId` field**. The `session:turnEnded` payload uses that same `sessionId` and also has no `tabId`. The recorded timeline order remains generating `turn_state`, assistant `message_start`, text/tool events, `message_complete`, idle `turn_state`, then `session:turnEnded`.
- Scoped verification: `npm run verify -- -p web-landing,@ptah-extension/core` passed all 6 lint/test/typecheck tasks (3 cached) after correcting a `Window.Function` typing error. The first run had 5/6 passing and only that type error. Ptah scoped diagnostics timed out twice; the scoped verifier supplied the definitive typecheck result.
