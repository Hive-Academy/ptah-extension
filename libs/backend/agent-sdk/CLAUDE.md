# @ptah-extension/agent-sdk

[Back to Main](../../../CLAUDE.md)

## Purpose

Wraps the official `@anthropic-ai/claude-agent-sdk` (plus `@openai/codex-sdk`) into Ptah's `IAIProvider`-style adapter. Owns session lifecycle, message transformation, permission handling, provider registry, and SDK-managed JSONL session persistence.

## Boundaries

**Belongs here**:

- SDK adapter (`SdkAgentAdapter`) — interactive chat path
- Internal one-shot queries (`InternalQueryService`) — used by skill-synthesis, memory-curator agents
- SDK message transformation, permission handling, session metadata, history reading
- Provider registry (Anthropic-compatible providers), CLI detector, system prompt assembly
- Compaction hook fanout (`CompactionCallbackRegistry`) and subagent dispatcher

**Does NOT belong**:

- Platform-specific code (must go through `platform-core` ports)
- RPC handlers (those live in `rpc-handlers`)
- Persistence beyond what SDK writes to `~/.claude/projects/`
- Propagating skills/commands/agents into `.claude/` or any rival CLI's harness
  dir — that fan-out is `@ptah-extension/harness-sync` (TASK_2026_278; replaces
  the deleted `SkillJunctionService`). `agent-sdk` must never import
  `harness-sync` — see `src/lib/harness/harness-preflight.port.ts`

## Public API

`SdkAgentAdapter`, `InternalQueryService`, `SdkMessageTransformer`, `SessionMetadataStore`, `SessionImporterService`, `SessionHistoryReaderService`, `JsonlReaderService`, `SdkPermissionHandler`, `ProviderModelsService`, `ClaudeCliDetector`, `SubagentMessageDispatcher`, `CompactionCallbackRegistry`, `CompactionHookHandler`, `SessionIdResolvedCallbackRegistry`. Errors: `SdkError`, `SessionNotActiveError`, `ModelNotAvailableError`. Registration: `registerSdkServices`, `SDK_TOKENS`. Constants: `ANTHROPIC_PROVIDERS` (provider entries carry `defaultTiers` for bare tier resolution).

## Guidelines

- **Harness plugins live in TWO roots and only ONE of them may be mirrored.** `~/.ptah/plugins` is user-global; `{ws}/.ptah/plugins` is workspace-scoped and committable beside `.ptah/specs`. Both reach `resolveCurrentPluginPaths` (the reconciler's overlay); only `discoverHarnessPluginPaths` — the user-global one — reaches each host's `buildMirrorSources`. That asymmetry is what makes the scope real, and it is the same rule `discoverSkillsShPluginPaths` documents: the user-layer mirror clones create-if-absent into `~/.ptah/user/skills`, and the user layer is the desired state's BASE, so a mirrored workspace skill would outlive its workspace and propagate into every other project forever. **Never add `discoverWorkspaceHarnessPluginPaths()` to `buildMirrorSources`.** A slug present in both roots resolves workspace-wins with a warn, and `ptah.harness.createSkill` refuses the second write rather than creating the clash.
- **Session identity**: the SDK's UUID from the system 'init' message is the canonical sessionId everywhere. Never mint a Ptah-side sessionId.
- **Message persistence**: rely on SDK JSONL files at `~/.claude/projects/{sessionId}.jsonl`. `SessionMetadataStore` only tracks UI metadata.
- **Interactive vs headless**: chat path = `SdkAgentAdapter`; everything else (skill synthesis, memory curator) = `InternalQueryService`.
- **One message per turn**: `SessionStreamPump` yields a user message only when `SessionRecord.turnInFlight` is false, and claims it before every yield. Ptah owns the follow-up queue on purpose — a prompt handed to the SDK mid-turn is classified as a _queued command_: the SDK enqueues it, removes it, writes it as a `queued_command` transcript attachment, and never materialises it as a user turn. It is silently lost, and the model is never told. Measured before the fix: 180 removed queue items, 0 delivered, 58 of them human prompts (TASK_2026_294). The release is `StreamTransformConfig.onTurnEnd`, fired first inside the `result` branch — NOT `onResultStats`, which `validateStats` can skip.
- **Hook session identity**: a hook callback MUST resolve its session id through `resolveHookSessionId` / `resolveHookCwd` (`src/lib/helpers/hook-session-resolver.ts`) — payload first, closure second, `''` from either source treated as absent — and MUST NOT publish the result until it has rejected `null`. `SdkQueryOptionsBuilder.createHooks` captures whatever `SessionQueryExecutor` handed it as `sessionId` — the `?? ''` coercion this rule was first written against is gone, and both signatures now model absence (`createHooks(cwd: string, sessionId?: string, …)` → `CompactionHookHandler.createHooks(sessionId: string \| undefined, …)`). For a NEW session the captured id is the **tabId**, not the SDK UUID, which arrives later in the system `init` message: the closure holds a real but non-canonical id for the whole query, and since a tabId is itself a UUID v4 no handler can tell the two apart by inspection (TASK_2026_296). That is why the payload comes first. PreCompact skipped the resolve entirely and fanned the unresolved id to the memory curator, whose transcript reader rejected it as path traversal and curated a placeholder instead of the conversation (TASK_2026_293). Seven more handlers resolved but never rejected, and `SubagentStart` gated registration on the closure while the real parent id sat on the payload — which silently unregistered every subagent of an internal one-shot query, killing steering, stop, background listing and resumption for it (TASK_2026_295). The resolver returns `null`, never `''`, so "no id" cannot be published by accident.
- **MCP caller identity**: `SdkQueryOptionsBuilder.buildMcpServers` MUST emit the Ptah MCP URL as `http://localhost:{port}/session/{routingId}`, never the bare origin. That segment is the only channel telling an MCP tool call which session made it — `extractCallerSessionId` (vscode-lm-tools `http-server.handler.ts:145`) parses it onto `request._callerSessionId` and `ptah_agent_spawn` uses it as `parentSessionId`. Drop it and the consumer falls back to `getActiveSessionIds()[0]`, so with two sessions open session B's spawn is attributed to session A (TASK_2026_295). That consumer fallback is deliberate — stdio, CLI and internal one-shot callers genuinely have no caller id — so the producer must never emit an anonymous URL on the interactive path; a missing routing id throws `SdkError`. The id is `sessionConfig.tabId ?? sessionId`, matching `SessionQueryExecutor`'s `registerKey` so the consumer's `resolveSessionId` can `find()` it. A tabId is correct here: for a new session it is the only id that exists, since the SDK UUID arrives later in the system `init` message. Internal one-shot queries use `SdkQueryRunner.buildOneShotMcpServers`, which has no segment by construction.
- **`query()` spawns the CLI SYNCHRONOUSLY, so every launch goes through `OffThreadProcessSpawner`.** `child_process.spawn` is not async: libuv's `uv_spawn` runs `CreateProcessW` on the calling thread and Windows scans the target image while creating the process, so the cost tracks the executable's SIZE — `cmd.exe` 9 ms, `node.exe` ~700 ms, `claude.exe` (253 MB) 1850-1975 ms. The SDK does that spawn inside `query()`'s synchronous prologue (`ProcessTransport` constructor → `initialize()` → `spawnLocalProcess()`), so each launch froze the Electron main process for ~1.6 s and every one produced an `[event-loop] lag` line matching its own duration to within ~10 ms — ten times during boot alone (TASK_2026_341). No spawn flag changes it; a different THREAD is the only lever. `SdkQueryRunner` therefore sets `Options.spawnClaudeCodeProcess` on BOTH paths (`buildOneShotOptions` and `invokeWithLoadedQuery`) — it is the one funnel every launch passes through, which is why the seam is there and not in `SdkQueryOptionsBuilder`. A caller-supplied `spawnClaudeCodeProcess` is never replaced: a host running the CLI in a VM or container has already answered that question. Two consequences to remember when touching this: supplying a custom spawner makes the SDK skip its own stderr wiring, so `options.stderr` is handed down as `onStderr` explicitly; and `SdkQueryRunner` warns `query() blocked the event loop` above 100 ms, which is the only signal that would catch a regression back onto the main thread. `PTAH_SDK_INLINE_SPAWN=1` restores the blocking inline spawn without a rebuild. Callers that invoke `queryFn` directly instead of through the runner do NOT get the seam for free and must pass the spawner themselves. `SdkModelService.fetchModelsViaSdk` now does (TASK_2026_353) — it was the one that showed up on the boot path, as 1803 ms and 1992 ms of `[event-loop] lag` behind a `config:models-list` that reported 7095 ms while `session:list` and `chat:resume` reported 3.5 s and 9.3 s for work they had not started. `cli-agent-runtime`'s `ptah-cli-registry.ts` remains. **No absolute millisecond budget is a CI gate here.** `off-thread-process-spawner.spec.ts` asserts the MECHANISM (`transport === 'worker'`) and a RELATIVE bound — best-of-three worker returns against best-of-three inline returns, measured on the same box in the same seconds — because a fixed wall-clock budget measures the HOST, and several agents testing in one working tree is this repo's normal operating mode. The literal 50 ms / 100 ms figures live in `off-thread-process-spawner.perf.spec.ts`, which is `describe.skip` unless `PTAH_PERF_SPECS=1`; run it on a quiet machine after touching the spawner, the worker source or the runner's launch seam.
- **`OffThreadProcessSpawner` has TWO seams, and only one of them is the SDK's (TASK_2026_367 Batch B9).** `spawn(options, hooks)` is `Options.spawnClaudeCodeProcess` and its contract is the SDK's `SpawnedProcess`: no stderr stream, no pid, `exit` only. `spawnProcess(request)` implements `IProcessSpawner` from `platform-core` and is what `cli-agent-runtime`'s `spawnCli` calls, so the rival-CLI launches (300-900 ms of `CreateProcessW` each, `tmp/logs/log.log`) leave the calling thread too. It needs four things the SDK seam does not, and all four are ADDITIVE on the worker protocol so the SDK path behaves exactly as before: `detached`, `windowsHide` (false when `needsConsole` is set, because ConPTY's `AttachConsole()` fails without a console), `windowsVerbatimArguments`, and `stderrMode: 'stream' | 'callback' | 'ignore'` — `'stream'` posts raw `stderr-chunk` bytes and a `stderr-end` so the host can expose a real `Readable`, while `'callback'` keeps decoding in the worker for the SDK's one classifier hook. The handle also exposes `pid` and `whenSpawned: Promise<number | null>`, taken off the `spawned` message that already carried the pid; **every tree-kill site must await `whenSpawned`**, because off-thread the pid does not exist when the handle is returned. `close` is emitted only once the child settled AND stdout drained, which is the event a stdout consumer must wait on. **Windows `.cmd` resolution runs on the HOST**: `cross-spawn`'s `_parse` is a pure function, so `spawnProcess` calls it here and sends the already-resolved `cmd.exe` command line to the worker. Never add a `require('cross-spawn/...')` to `off-thread-process-spawner-source.ts` — that body is `eval`'d into a Worker and has no reliable module resolution in a bundled Electron app. `off-thread-process-spawner.spec.ts` pins all of it against real children, including a real `.cmd` wrapper whose stdout must equal inline `cross-spawn`'s.
- **Three read caches, each with an EXACT validity token — never a bare TTL (TASK_2026_353).** `SdkModelService` keys its catalog on an auth fingerprint (active auth method + **provider id** + base URL + hashed credential + tier `ANTHROPIC_DEFAULT_*_MODEL` values) read from the process-global `AuthEnv` the auth strategies mutate in place, so a provider switch misses by construction rather than by someone remembering to clear anything. The provider id is in the key even though it never reaches the spawn env, because `applyTierMapping` resolves tiers through `ModelResolver`, which falls back to the ACTIVE provider's registry `defaultTiers` — two providers can present identical AuthEnvs and still map `opus` to different ids. **A workspace/provider switch must call `invalidateForAuthChange()`, never `clearCache()`**: the per-identity catalogs are already isolated, so wiping them is not protection, it is a guaranteed extra multi-second SDK-bridge spawn every time the user switches BACK (A → B → A paid three spawns for two providers). `invalidateForAuthChange` drops only the genuinely auth-scoped `/v1/models` response, which is a single unkeyed field behind a 5-minute TTL. `clearCache()` remains for full re-initialisation (config change, dispose, `clearModelCache()`) and bumps a `cacheGeneration` that every write-back re-checks, so a fetch already in flight cannot write a pre-change catalog back; `invalidateForAuthChange` deliberately does NOT bump it, because an in-flight fetch is keyed to the identity that started it and its result stays correct however the active auth moves. `JsonlReaderService.findSessionsDirectory` memoises per workspace against the `~/.claude/projects` `mtimeMs` — a directory's mtime moves when a child is added or removed and at no other time, which is exactly what that answer depends on, and is why the NEGATIVE answer is cached too. `JsonlReaderService.readJsonlMessages` memoises the parse on `(path, size, mtimeMs)`, needing no extra syscall because the size guard already stats; `readJsonlTail` is deliberately excluded (its result also depends on `maxBytes`, and its callers read a moving window of a file being appended to). Each cached parse is handed out as a fresh array so an array-level mutation by one caller cannot reach the next. Both `JsonlReaderService` maps are BOUNDED as well as tokened — a token invalidates an entry but never removes one, and this is a long-lived Electron process: the sessions-dir memo is a 32-entry LRU, the transcript memo an LRU over 8 entries / 24 MB with a 60 s TTL, and `TRANSCRIPT_CACHE_MAX_FILE_BYTES` is DERIVED as `MAX_BYTES / 2` so that "anything cacheable fits alone" holds by construction — the eviction loop depends on it to stop without ever considering the entry it just wrote. If you add a fourth cache, bring a token AND a bound: a TTL alone lets a stale answer be served for its whole window, and an unbounded map is a leak whatever its token.
- **`InternalQueryService` has TWO concurrency ceilings, and the per-lane one is what makes the global one safe to raise.** `DEFAULT_MAX_CONCURRENT` is 2 and `DEFAULT_MAX_CONCURRENT_PER_LANE` is 1 (`ptah.internalQuery.maxConcurrent` / `.maxConcurrentPerLane`). It was a single host-wide slot, and the reason it was — TASK_2026_323 B6, that `query()` spawns the CLI synchronously on the thread owning every `BrowserWindow` — **no longer exists**: TASK_2026_341 moved the spawn onto a worker thread and measured eleven launches at 1-7 ms against a 1576-1732 ms baseline. What the single slot cost is on the record: the memory curator and skill-synthesis are unrelated pipelines with unrelated budgets, and one boot serialised them into each other nine times (`tmp/logs/log.log:938,955,1011,1070,1104,1365,1380,1408,1424`, every line reading `limit:1, inFlight:1`), turning two independent backlogs into one queue that took 122 s and 156 s to drain (TASK_2026_352). Raising the global limit ALONE would not have fixed it — skill-synthesis would simply have taken both slots — which is why the per-lane ceiling is the load-bearing half and why adding lanes is not a way to buy concurrency (a new lane still counts against the global ceiling). `InternalQueryConfig.lane` is a caller-supplied string, trimmed and lower-cased so a near-miss cannot silently mint a second lane with its own ceiling; the two background pipelines name themselves `'memory-curator'` (the curator adapter) and `'skill-synthesis'` (`LaneRunnerService`, ONE lane for all four `SkillLane`s — they are routes for one pipeline, not independent consumers), and everything else shares `'default'`. `InternalQueryConcurrencyGate` is ONE object with ONE queue and ONE admission predicate (`active < limit && activeInLane < perLaneLimit`) rather than two nested semaphores, so there is no lock ordering to get wrong; and `drain()` SCANS the queue for the first admissible waiter instead of waking the head, because a lane-blocked head would otherwise block an unrelated lane behind it — reintroducing the exact coupling the lanes remove. Order stays FIFO within a lane. `execute` does not forward `lane` to `runOneShot`: it is accounting, not an SDK option.
- **`ClaudeCliDetector` coalesces both its detection AND its `--version` spawns, and the reason is the same 253 MB executable that TASK_2026_341 moved off-thread.** Every probe here is a `CreateProcessW` on the calling thread, ~1850-1975 ms for `claude.exe` on the reference machine. Two things made one boot pay that many times over. First, `cachedInstallation` is only written when the whole strategy chain finishes, so the four boot-time consumers of this DI **singleton** — `CliStrategy`, `SdkAgentAdapter`, `SdkModuleLoader` and `AuthRpcHandlers.probeClaudeCli`, all starting within the same second — each ran the entire chain before any of them populated the cache. Second, `performHealthCheck` re-ran `--version` on the binary `findExecutable` had just verified through `verifyInstallation`, which parses that exact output — a second spawn to re-answer a question answered milliseconds earlier. `findExecutable` is now single-flight (`detectionInFlight`, released by identity) and every `--version` call goes through `probeVersion`, which shares the settled result for `VERSION_PROBE_TTL_MS` (30 s) and shares the running spawn with any concurrent caller. **Only SUCCESSES are cached** — a failed probe is not evidence the CLI is absent, and retrying costs one spawn. The window is deliberately short: this is not a health cache, callers that want one keep their own (`AuthRpcHandlers` memoises the verdict for five minutes). `clearCache()` must drop the version results too, or a caller asking for a fresh detection is answered from the evidence it asked to discard. Measured before (smoke 2026-08-29, `tmp/logs/log-after.log:727`): `auth:getAuthStatus` 22736 ms, with `[event-loop] lag` lines of 1000/1053/2357/2081/2183 ms beside it.
- **Turn state is derived HERE and travels IN the chunk stream (TASK_2026_360).** `SessionTurnStateRegistry` (`helpers/session-turn-state.registry.ts`) is the backend's single source of truth for "is this session busy": `generating | awaiting-background | sleeping | idle | failed`, revision-stamped per session. **The revision is monotonic per SESSION ID, not per SDK query, and that is load-bearing (TASK_2026_371 D1).** `ChatStreamBroadcaster` deletes the record on every clean loop exit, while the webview compares revisions per SESSION and allows a restarted counter only when the session id CHANGED — so a `chat:continue` that auto-resumes under the same id emitted `generating@1` and terminal `idle@2` against a stored baseline of 300-odd, both were dropped before any side effect, and the tab kept its spinner and Stop button forever while the backend sat idle (measured on session 50653b50; the control case in the same log is an abort, where `clear` is skipped and the next turn updated the UI normally). `clear(sessionId)` therefore deletes the RECORD and keeps a `revisionFloor`; `ensure` seeds a fresh record from it, `rekey` carries both aliases' floors into the surviving baseline, and the map is bounded by `REVISION_FLOOR_MAP_LIMIT` (256, LRU-evicted — a cache needs a bound as well as a retention rule). The fix belongs here rather than in `TabManagerService.acceptsTurnState`: loosening that guard re-opens the replay window review F1 (TASK_2026_360) closed, and would leave the same trap for `chat:resume --activate` and the rewind path, which also restart a query under an existing session id. The bound has one residue the backend cannot cover — an eviction INSIDE a live process restarts the counter for a session whose tab is still open and still holds a high `lastTurnStateRevision`, which is D1 again — so `acceptsTurnState` carries one narrow heal for it: a TERMINAL phase on a tab BOUND to exactly that session is accepted at or below its last revision. That is not the loosening above; `generating` at or below `last` is still rejected, so the replay window stays closed. The `Stop` / `StopFailure` / `SubagentStop` hooks only SNAPSHOT into it (`recordStop`, `recordFailure`, `applySnapshot`) — they must never flip the phase, because the SDK dispatches a hook from its transport read loop BEFORE the consumer has pulled the final `assistant` message of the same turn, so a phase flipped from a hook overtakes the chunks it describes. The phase flips at two stream positions only: the root assistant `message_start` (`markGenerating`, once per turn) and the `result` message (`ResultMessageTransformer` → `settleTurn`), each emitted as a `turn_state` `FlatStreamEvent` so it is ordered with the deltas by construction. `ChatStreamBroadcaster` closes the remaining exits (`forceIdle` on stream error, abort and a loop that ends mid-turn). Do not add a `MESSAGE_TYPES` push for status — the three-channel race (`session:turnEnded` direct, chunks batched, `session:stats` direct) is exactly the defect this replaced. `rekey` is wired to `SessionIdResolvedCallbackRegistry` and never overwrites an entry under the real id.
- **The no-activity watchdog is HELD while no turn is in flight and for the lifetime of every registered subagent (TASK_2026_363).** `NoActivityWatchdog` (TASK_2026_190) reads 180 s of silence on the PARENT stream as a hung provider, and two healthy states are silent there by construction: idle between turns, and a subagent composing one long message — the SDK forwards subagent activity only as COMPLETE messages (`forwardSubagentText`), so a subagent's partial deltas never reach the parent. Measured 2026-08-31: idle kills landed exactly 180.0 s after `result` (session 314c9c90, result 00:37:02Z → kill 00:40:02Z, again 00:51:13Z → 00:54:13Z), and an architect writing a 30 KB plan died 180 s after its last transcript record with no `Write` ever requested; per-day kills went from 0 to 12-38 the day v0.1.68 shipped the watchdog. Two owners now hold it. The TURN STATE owns one hold: `SessionQueryExecutor` takes it at registration for a non-slash prompt, `SessionRegistry.markTurnStarted` releases it and `markTurnEnded` re-takes it, both guarded on the `turnInFlight` transition — `markTurnEnded` is called from the `result` branch, the interrupt path and the adapter, and a double call must not stack holds (invariant: the count owned by the turn state is 1 while no turn is in flight, 0 while one is). A slash-command string prompt never goes through the pump, so it takes no idle hold and the watchdog arms on `start()` as before. `SubagentHookHandler` owns one hold per `agent_id`: taken on `SubagentStart` independent of the registry outcome, released on `SubagentStop`, keyed in a closure-local set so a `SubagentStop` for an unknown `agent_id` NEVER releases — it would drop the session's idle hold. The abort itself stays: it can now fire only when the root turn is in flight, no subagent is registered and the parent stream is silent for the whole window, which is the case TASK_2026_190 was built for.
- **`preTokens` has TWO sources, and the resume baseline is a SECOND slot on `LiveUsageTracker` rather than a seeded snapshot (TASK_2026_374).** `CompactionHookHandler` samples `usageTracker.getCumulativeTokens` lazily through `ensurePreTokens()`, and that sample must stay a single synchronous map read: the hook runs on the SDK's transport path, may not do file I/O and may not throw. For a session RESUMED from JSONL nothing has streamed in this process, so the live map was empty and every manual `/compact` published `preTokens: 0` — the frontend then computed its pre/post delta from a zero baseline. `LiveUsageTracker.seedResumedSession` fills that gap, written by `SessionHistoryReaderService.readSessionHistory`, which `chat:resume` already calls and which has already parsed exactly these fields, so the seed costs no extra read. **Do not route it through `recordSessionUsage`.** That method keeps a per-field MAX, so anything written there outranks every real frame that arrives afterwards and can never be corrected downwards — the historical number would beat live evidence for the rest of the session, which is the one guarantee this class exists to make. The baseline therefore lives in its own map, is consulted ONLY when the live map has never been written for that session (a live snapshot wins even if it sums to 0 — once we have observed a frame, that observation IS the answer), and is dropped by `clearSessionTokenSnapshot` along with the snapshot, because a pre-compaction figure answering a post-compaction read is the same re-poisoning that method already prevents, arriving through the other slot. **The seed must be ONE request's frame** — `input + output + cache_read + cache_creation` of the last message after the last `compact_boundary` — not a cross-turn sum. `aggregateUsageStats` and `SessionMetadataStore.totalTokens` both hold sums, and with prompt caching a long session's summed `cache_read` runs into the millions; publishing that as `preTokens` would be a confidently wrong answer where 0 was merely an empty one. A scan that reaches a boundary before finding usage seeds nothing, on purpose. The map is the fourth read cache in this lib and obeys the rule the bullet above states: bounded (64 entries, least-recently-seeded evicted, because `session:stats-batch` reads a whole session list in one call) AND given a retention rule rather than a TTL. `ICompactionCallbackRegistry` is deliberately untouched — see its own doc comment.
- **`SessionMcpStatusCallbackRegistry` is a DI fan-out, the same shape as `SessionIdResolvedCallbackRegistry`, not a `StreamTransformConfig` field (TASK_2026_375).** `StreamTransformer` publishes `{ kind: 'servers', … }` from the SDK `init` message's `mcp_servers`; `SdkQueryOptionsBuilder`'s stderr handler publishes `{ kind: 'notice', … }` via `classifyCliNotice` when the CLI reports `claude.ai connectors are disabled`. Neither producer's config reaches `ChatSessionService`, the consumer B4 names, so a registry was the only seam that did not widen `IAgentAdapter`. It rides the DIRECT message channel deliberately — the guidance elsewhere in this file that forbids a `MESSAGE_TYPES` push for turn state does not apply here, because MCP status arrives exactly once per session at `init` and is never revised, so there is no ordering relationship with the chunk stream for a race to break. Do not read this as a precedent for pushing other status.
- **Compaction**: subscribers must register via `CompactionCallbackRegistry`, not by patching the adapter.
- **Session-id resolution is fanned out, not owned**: `SdkAgentAdapter` fires `SessionIdResolvedCallbackRegistry.notifyAll` from BOTH resolve sites (resume and new-session) **alongside** `SdkAdapterCallbackRegistry.emitSessionIdResolved`, never instead of it. The single-slot `setSessionIdResolvedCallback` is part of the shared `IAgentAdapter` port (`agent-adapter.types.ts:253`) and is already consumed by `cli-agent-runtime` (`wiring/sdk-callbacks.ts`), so promoting it into a fan-out would be a breaking port change for no gain (TASK_2026_296). The registry exists because a residual hook path — one whose payload genuinely lacks `session_id` and falls back to the tabId-bearing closure documented above — arms consumer state under the **tabId**, while `SessionEnd` always canonicalises to `realSessionId ?? tabId` and arrives under the UUID. `MemoryTriggerService` and `SkillTriggerService` subscribe and migrate their keyed state (`rekeySession`). A subscriber's handler MUST be synchronous, MUST refuse to overwrite an entry already held under the destination id, and MUST re-arm any timer with its REMAINING delay — a `setTimeout` closure captures the id it was armed with. Nothing anywhere may detect a tabId by SHAPE: a tabId is itself a UUID v4.
- Always `catch (error: unknown)` and narrow.
- Boundary inputs validated via zod schemas.
