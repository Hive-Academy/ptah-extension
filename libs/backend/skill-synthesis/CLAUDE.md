# @ptah-extension/skill-synthesis

[Back to Main](../../../CLAUDE.md)

## Purpose

Track 2 of TASK_2026_HERMES. Records each successful AI session; when a stable trajectory repeats 3 times the workflow is promoted to a permanent `SKILL.md` under `~/.ptah/skills/<slug>/`. Cosine-similarity dedup against the active set keeps the library focused; over the residency budget (`maxActiveSkills`, default 200) the weakest skills are demoted to `dormant` residency (kept on disk + in the DB, skipped at the junction layer) rather than rejected. Authored skills (`clone_status='authored'`) are first-class: never re-synthesized and never demoted to dormant.

## Boundaries

**Belongs here**:

- Candidate store, invocation tracker, trajectory extractor
- Promotion service + judge LLM caller
- Skill MD generator + migration utility
- Dedup (cosine clustering) + curator

**Does NOT belong**:

- DB connection (via `persistence-sqlite`)
- LLM execution (via `agent-sdk`'s `InternalQueryService` / `JsonlReaderService`)
- RPC surface (`SkillsSynthesisRpcHandlers` in `rpc-handlers`)

Pass 1 gets a tail+head window; the reply may request turn ranges or searches that the reader serves back, re-bounded by `maxInputChars`, until a pass returns a verdict with nothing outstanding. It heartbeats through `ctx.touch()` BETWEEN passes and writes NOTHING once that returns `false`. A `toolUse: 'none'` lane collapses to one pass, but **the collapse decides how many passes, not whether the verdict is complete** — `degradedReason` is written only when the collapse left requests unserved, so a clean single-pass verdict stays usable. Gating it on the capability flag instead would make `hasUsableVerdict` discard everything the cheap lanes produce, which are exactly the lanes the lane routing exists to move background work onto. Each is a WEEKLY-tier queue stage; see the registration and mapping rules below.
- `src/lib/queue/` — the durable synthesis queue (migration `0032`): `SkillQueueStore` (enqueue / CAS claim / heartbeat / `mergePayload` / reap), `SkillBudgetStore` (token ledger keyed per UTC day **and stage**, migration `0035`; `spentToday()` still returns the day total across every stage, which is what the drain's budget gate reads — stage `''` holds spend no queue stage owned, so the per-stage rows always sum to it), `SkillDrainService` (the gated, round-robin drain), `SkillStageHandlersService` (see below), `ForegroundActivityTracker` (ms since the last chat turn), and the row/stage/status types
- `src/lib/queue/stage-handlers.service.ts` — the stage-DISPATCH layer, extracted from `skill-synthesis.service.ts` by TASK_2026_256 (which had grown from 906 lines to 1929 holding it). It owns `registerStageHandlers(workers)`, the six `run*Stage` methods with their outcome mappings, the chain producers (`enqueueArchaeology`, `enqueueCandidateGates`, `enqueueGate`) and the claim heartbeat. It injects the drain and all four optional LLM collaborators (`archaeologist`, `judgePanel`, `replayValidator`, `triggerEval`), so the conditional-registration rule lives beside the handlers it guards. Extraction was behaviour-preserving: every mapping below is unchanged.

## Guidelines

- **Trajectory extraction requires ≥ `MIN_ROLE_TURNS_FLOOR` (2) turns, NOT `MIN_TURNS_FOR_TRAJECTORY` (5).** `extract`'s `minTurns` parameter is honoured — it used to be `void`-ed, so the floor silently decided for everyone — and its default is the floor, clamped up (`Math.max(MIN_ROLE_TURNS_FLOOR, ...)`). The extractor answers "is there a readable session here"; the decision to SPEND is `passesPrefilter`, which is where `eligibilityMinTurns` is applied. Two callers pass a value explicitly: the synthesis paths pass the floor, and `skill-enhancer.service.ts:733` passes `TRAJECTORY_MIN_TURNS` (5), so **the enhancer genuinely requires 5 role turns where it used to get 2**. That narrowing is deliberate and pinned by a test; do not "simplify" the default back without reading it.
- `SkillSynthesizerService.buildSystemPrompt()` encodes skill-creator best practices (verb-first kebab name that never echoes the request; trigger-oriented `description` carrying ALL "when to use" info; concise imperative body with no frontmatter / no "When to use" section). Keep it aligned with `ptah-core/skills/skill-creator`.
- `SkillJudgeService` scores five criteria (novelty, actionability, scope, generalization, triggerClarity) and returns their average. It runs at the promotion gate AND the suggestion-pass gate. It **reports a status; it never decides pass/fail and never fabricates a score.** It returns `{status, score, criteria, reason}` where only `'scored'` carries a number, and comparing that number against `minJudgeScore` is the CALLER's job — promotion, the curator's suggestion pass and the enhancer each apply it with their own policy for the two non-`scored` statuses. The three paths that used to fail OPEN with `{passed: true, score: 10}` — no JSON in the reply, values that are not scores, and a thrown call — now return `'unscored'` with the three distinct `JUDGE_REASONS` members `judge-no-json-in-response`, `judge-invalid-score-values` and `judge-call-threw`; a lane failure passes the lane's own reason straight through. `score: 10` appears nowhere in the service, pinned by a source scan in its spec.
- **`unscored` is neither a pass nor a block.** Promotion persists the verdict and returns `reason: 'judge-unscored'` with the candidate left at `status='candidate'` — NOT rejected — so the next drain re-judges it. `'disabled'` (gate off, or no LLM in this host) does not block anything. Only a `'scored'` verdict below `minJudgeScore` rejects. The curator's suggestion pass files no suggestion at all on a non-`scored` verdict, because `skill_suggestions.judge_score` is a NUMBER and the old fail-open wrote a 10 nobody had awarded.
- **The judge PANEL's two panellists are asked DIFFERENT questions, and that is the whole reason it costs two calls** (`gates/judge-panel.service.ts` + `gates/judge-lens.ts`). B3.4 shipped a panel that called `judge()` twice with byte-identical arguments — against a temperature-0 endpoint the second verdict is guaranteed to reproduce the first, so the escalation branch could never fire and the second call bought nothing. Panellist A is unchanged (the artifact on its own terms). Panellist B judges the same artifact IN CONTEXT and is shown material A never saw: the candidate's nearest DESCRIPTION neighbours among the active skills, and the gate results already MEASURED on its row (`trigger_score`/`trigger_precision`/`trigger_recall`, `replay_confidence`). Four rules, each of them a contract: (1) **the scorecard shape never varies** — same five criteria, same 1–10 scale, because the escalation compares PER CRITERION and a reshaped rubric on one side turns every delta into noise; vary the question, never the answer format. (2) **The lens rides `systemPromptAppend`, evidence included.** `maxInputChars` clips `prompt`, and a clipped lens silently degrades B back into A — the failure mode that would make the fix look applied while doing nothing. The evidence is variable material on the unclippable half by exception, because it is bounded by construction (≤ `JUDGE_LENS_MAX_NEIGHBOURS`, each description clamped) and because it is the only thing that makes the second call a second call. Pinned by a spec that drives the REAL `LaneRunnerService` at `maxInputChars: 40`. (3) **Neighbours are description-space, freshly embedded — never `searchActiveByEmbedding`**, which is the transcript/dedup space `TriggerEvalService`'s header separates out and which returns nothing at all without sqlite-vec. `novelty` and `triggerClarity` are questions about descriptions. (4) **A degenerate lens buys no second judge.** No neighbours AND nothing measured means B would ask A's question with A's inputs, so the call is skipped and the reason is recorded as `judge-panel-lens-degenerate` rather than leaving a silent single judge. The lens is built from a FRESH `findById`, not from the caller's row: the gates write the measurements, so a caller that loaded its row first would hand the panel an all-`null` copy and degenerate on evidence that exists. The escalation is shown the same evidence, or it is adjudicating a gap it cannot explain and splitting the difference is its only move.
- **Every stage runs on a lane; no stage owns a timeout.** `JUDGE_TIMEOUT_MS`, `SYNTHESIS_TIMEOUT_MS` and `CURATOR_TIMEOUT_MS` are deleted — `SkillJudgeService`, `SkillSynthesizerService`, `SkillCuratorService` and `CandidateNamerService` all call `LaneRunnerService.run`, which owns the `AbortController`, `timeoutMs`, `maxInputChars` and the structured-output ladder. Each service's FIXED instructions (the judge rubric, the synthesizer's authoring rules, the naming rubric) travel as `systemPromptAppend`, which the lane does NOT clip; only the variable material rides `prompt`. Putting a rubric in the clippable half is a defect: `maxInputChars` would silently eat the "reply with ONLY JSON" instruction off the end and every call on that lane would come back unparseable. The curator's overlap pass deliberately sends NO `outputSchema` — its answer is a JSON array and the runner resolves objects only.
- `CandidateNamerService` (`src/lib/naming/`) is a cheap `{name, description}`-only pass on the `judge` lane that fills `display_name`. `name` stays the SLUG — internal id, `SKILL.md` folder name, UNIQUE index — and is never a title. The title is clamped to `CANDIDATE_DISPLAY_NAME_MAX_CHARS` (60) on a word boundary, and the slug-echo check runs BEFORE that clamp: a slug built from 140 characters of prose is longer than the ceiling, so clamping first turns an exact echo into a 60-char prefix that compares unequal and gets persisted as a title. An unavailable lane, an unparseable answer, or an echoed slug all leave `display_name` NULL and write nothing — NULL is a complete value (the UI falls back to the slug), whereas a placeholder would leave nothing to retry.
- `SkillSuggestionStore.updatePending(id, {name?, description?, body?})` edits a still-pending suggestion (immutable once accepted/dismissed); backs `skillSynthesis:updateSuggestion`. `skillSynthesis:getSuggestion` returns the full row incl. body.
- Invocation telemetry (`SkillTriggerService.onPostToolUse` → `SkillInvocationRecorder`, slug-keyed `skill_invocation_events`) records `Skill` tool use (`source:'tool-use'`), slash/skill expansion (`'prompt-expansion'`), AND **subagent runs** via the `Task` tool keyed on `subagent_type` (`'subagent'`). This usage signal is what makes agent/skill clones auto-enhance-eligible (`getInvocationStats(slug).total ≥ MIN_INVOCATIONS_TO_ENHANCE`). Without the `Task` branch, agent clones never accrue usage.
- `SkillEnhancerService.generateCandidate` injects kind-specific authoring best practices (skill-creator for skills, role/trigger guidance for agents, single-purpose for commands). `MIN_INVOCATIONS_TO_ENHANCE` + `ENHANCE_COOLDOWN_MS` are exported for the Library eligibility UI (surfaced on `CloneSummary.enhanceMinInvocations` / `enhanceCooldownUntil`).
- Judge calls go through `INTERNAL_QUERY_SERVICE_TOKEN` (injected) — do not invoke SDK directly.
- **The `unscored` verdict and where `judge_status` is enforced.** `judge_score: null` IS the `unscored` verdict — it is not a low score and never `0`. It replaces the three fail-OPEN `{passed: true, score: 10}` paths, so a candidate whose judge call failed reads back as "we do not know", carries the reason, and stays retry-eligible; promotion treats `unscored` as neither pass nor block. Migration `0033` deliberately ships `judge_status` with **NO `CHECK` constraint** (SQLite cannot widen a CHECK via `ALTER TABLE`, and phases 3/4 add scoring paths), so **the `JudgeStatus` TypeScript union in `types.ts` is the ONLY enforcement there is.** `SkillCandidateStore` is therefore the enforcing gate on both edges: `recordJudgeVerdict` throws on a non-member status, on `scored` with a non-finite score, and on any non-`scored` status carrying a number; `toCandidateRow` maps `null`/`''` to `null` ("never judged") and downgrades any unrecognised stored string to `'unscored'` with a warn. Do not add a second validation layer above the store, and do not catch and downgrade. The nine judge columns are written as ONE fixed UPDATE, never a dynamic fragment — a partial write leaves the previous pass's per-criterion scores beside a new headline score. The `0033` columns live directly on `SkillCandidateRow` (`JudgedCandidateRow` is a deprecated alias); `unjudgedVerdictFields()` supplies the never-judged block.
- Queue semantics (`src/lib/queue/`): **enqueue is idempotent, claiming is the at-most-once primitive.** `enqueue` is a plain INSERT whose `UNIQUE(session_id, stage)` violation becomes a guarded re-open gated on `turn_count` — never `INSERT OR IGNORE`, never UPSERT. `tryClaim` returning `null` means another worker won; that is success, not an error, and it must never throw. A stage that runs long MUST call `touchClaim(id)` between passes or `reapStale` will reclaim it mid-flight.
- Drain semantics (`SkillDrainService`): **`drain()` never throws** — every gate and every failure resolves to a `DrainSummary`. Gate order is a contract, not an implementation detail: `skillSynthesis.enabled` → daily token budget → battery → foreground backoff → abort, then reap → round-robin → CAS claim → stage dispatch. `enabled` is first because the Electron tray's "Pause background learning" writes that key, so paused must mean "reads nothing, spends nothing". Selection NEVER orders globally by `enqueued_at`: it walks eligible workspaces least-recently-drained first and bumps the cursor of every workspace it visited, including one that yielded nothing for the current tier. **Throughput is per tier (`DRAIN_TIER_LIMITS`), and it is the throughput half of `DRAIN_TIER_STAGES`.** The frequent tier takes `drain.maxItemsPerRun` (4) in ONE round; the nightly tier takes `drain.nightlyMaxItemsPerRun` (40) and the weekly tier `drain.weeklyMaxItemsPerRun` (400), both dealt out over repeated round-robin rounds. The reason is cadence, not taste: the frequent tier fires 96×/day so its fairness is delivered ACROSS ticks, while the nightly and weekly tiers fire once per period and must be fair INSIDE the one tick each gets. A shared cap is what starved `archaeology` — measured at ≤ 4 rows/day of supply against ~30/day of demand, an 835-row standing backlog, while `maxTokensPerDay` sat ~96 % unspent. **`weekly` had the identical defect and it was live, not theoretical.** B0.10 left it on the shared key because its own stages had no producers; phase 3 then chained `judge-panel` and `trigger-eval` off every successful `prefilter` beside `enqueueArchaeology`, so the weekly tier carries ~2 rows per eligible session at one seventh the cadence. Re-measured on the same corpus harness (828 sessions / 31 days): ~163 eligible sessions a week ⇒ ~325 rows/week of demand against a supply of 4. `replay` is weekly-only too but still has NO producer on purpose (TASK_2026_245), so it adds nothing to that demand — the arithmetic is two stages, not three. All three item caps are on the RPC wire and each has its own control in the settings panel, the frequent-tier field being labelled as such (TASK_2026_242). **`perWorkspaceBatch` stays 1 for every tier and must not be raised to buy throughput**: under rounds it is a fairness quantum (a lone workspace still reaches the whole cap because the rounds repeat), whereas a big batch re-creates R4 — every workspace visited on one tick carries the identical `last_drained_at`, so the order among them falls back to `workspace_root ASC` and the alphabetically first busy project eats the tick. The eligibility scan per workspace is `max(20, tier cap)`; scanning the bare 20 with a cap of 40 would silently halve the tick, and with the weekly 400 would cut it by twenty. The cap is a THROUGHPUT throttle and never a cost control — the daily token budget is the only cost ceiling and is unchanged. The token budget is a HARD stop checked twice — once per tick and once per item — and above 80 % of it the eligible window is ordered cheap-stages-first. **`TOKEN_SPENDING_STAGES`'s complement is exactly THREE stages — `prefilter`, `embedding`, `clustering` — and `trigger-eval` is NOT a fourth (TASK_2026_253).** The comment on that set used to call the complement "pure local computation (regex prefilter, the local embedder, cosine math)", and this bullet repeated it; the claim is true of those three and false of `trigger-eval`, whose SCORING path is local but whose probe set is generated per evaluation by `TriggerEvalService.generatePrompts` calling `laneRunner.run`. One LLM call per row is not zero. While the stage sat outside the set the drain kept dispatching those rows past `maxTokensPerDay` — so the daily ceiling was not a ceiling for roughly half of all weekly rows, `trigger-eval` and `judge-panel` being the only weekly stages with producers — and `STAGE_COST_RANK` ranked it BELOW `judge`, so above 80 % of budget the drain actively preferred a spending stage it believed was free. The spend was never invisible: `LaneRunnerService` records it into `SkillBudgetStore` either way, so it was counted AFTER the fact and never gated BEFORE it, which is why nothing surfaced. `trigger-eval` now ranks between `judge` (one call) and `judge-panel` (two calls plus escalation), and an over-budget host stops running the stage entirely — that behaviour change is the fix, not a side effect. The alternative — caching probes per skill so the stage becomes genuinely local — was considered and DEFERRED; do not implement it as a "simplification" of this bullet. `staleClaimTtlMs` must stay `>= 3 × max(lane.timeoutMs)` — `assertStaleClaimTtl` READS THE CONFIGURED LANES (`maxLaneTimeoutMs(readSkillLanes(ws))`) through the drain's own `IWorkspaceProvider`, warns and continues. It is a lane read and not a constant because no stage has owned a timeout since phase 1: the guard shipped comparing against a hard-coded `30_000` left over from the deleted `SYNTHESIS_TIMEOUT_MS`, so it reported "safe" for every TTL from 90 s up while the archaeologist lane could legitimately run for its 120 s default — the whole 90 s–360 s band silently reaped live runs, which is the one thing R5 exists to prevent. `MAX_STAGE_TIMEOUT_MS` survives as the LANE-LESS figure and is now DERIVED (`maxLaneTimeoutMs(SKILL_LANE_DEFAULTS)`, today 120 s), so it cannot rot when a lane default moves; it is what an install configuring no timeout gets, which is what `readSkillLanes` returns for it, so the two agree by construction. Stage handlers register via `registerStageHandler(stage, handler)`; an item whose stage has no handler in this host is marked `skipped`, never re-claimed forever. **`SkillSynthesisService.start()` is the registration seam** — it calls `SkillStageHandlersService.registerStageHandlers(this)` (which wires `prefilter` → `analyzeSession`, `archaeology` → `SessionArchaeologistService.analyze` and `embedding` → `backfillEmbeddings`) ABOVE both of its early returns, because registration spends nothing and a host that booted while `skillSynthesis.enabled` was false must still drain once the tray re-enables it. **That ordering IS pinned**, by `skill-synthesis.stage-handlers.spec.ts`'s "registers handlers even when the master switch is off at start": it drains with `enabled: false` and asserts the row comes back skipped by the HANDLER's reason (`no candidate from this session`), not by `no handler for stage prefilter`. Moving the call below the guard fails that test — verified by mutation during TASK_2026_256. `archaeology` is nightly-tier and token-spending; its row is chained from the END of a successful `prefilter`, with `dependsOn` deliberately left NULL — `ELIGIBLE_SQL` requires an ancestor to be `done`, so pointing it at the prefilter row would strand the dependent forever the first time that row ended `skipped`, and the ordering is already guaranteed by construction because the row does not exist until prefilter succeeded. The `prefilter` handler passes `force: true` deliberately: `enqueueAnalyze` already recorded the turn count in the same-process `analyzedSessions` map, so without it the drain's own callback would be deduped out and the queue would drain into a void. A long stage heartbeats through `ctx.touch()`; a `false` return aborts the derived signal. `skill-synthesis` still NEVER imports `cron-scheduler` — `onBattery` is a `drain()` parameter that `thoth-runtime` supplies from `IPowerMonitor`.
- **Queue payload: two owners, one shallow merge (`SkillQueueStore.mergePayload`).** `INSERT_SQL` used to be the ONLY writer of `payload`, and `REOPEN_SQL` still does not touch it — so a stage that learned something WHILE it ran had nowhere to put it, and `replay-validator.service.ts`'s documented "the drain writes this to `payload.verdictFallback`" was describing a writer that did not exist. `mergePayload(id, patch)` is that writer: shallow-merge, patch wins per key, **never a blind overwrite and never an append**. The column has two owners and the merge is what keeps them off each other — PRODUCER INPUTS (`candidateId`, `clusterSessionIds`, named in `SKILL_QUEUE_PAYLOAD_KEYS`) written at enqueue, and STAGE OUTPUTS (`verdictFallback`) written mid-run. It runs inside `inImmediateTransaction` because it is a read-modify-write and two hosts draining the shared `~/.ptah/state/ptah.sqlite` is a real configuration; a deferred read with a late write would drop the other host's key instead of merging it. An unparseable stored payload degrades through the store's existing `parsePayload` (warn + `{}`) rather than a second parse path — pinned by a spec, because a bare `JSON.parse` here throws into a stage handler and from there into `drain()`, which must never throw. **`REOPEN_SQL` deliberately does NOT clear `payload`**: it looks like it should (a re-opened row re-runs from scratch, so a carried-over `verdictFallback` is stale) but the statement does not re-write the column either, so clearing it would hand the handler a row with no candidate to grade — trading a stale field for a dead row. `json_remove(payload,'$.verdictFallback')` was considered and rejected as hard-coding one gate's output key into the store. The rule is OWNERSHIP instead: each writer refreshes its own keys — the `replay` handler writes `verdictFallback` on EVERY path it can return through, and a producer re-points a re-opened row at the candidate the current pass produced. **That re-point happens INSIDE `enqueue`'s own transaction, not in a follow-up call.** `enqueue` writes the caller's `payload` on the INSERT path and shallow-MERGES it on the re-open path, both under the one `BEGIN IMMEDIATE`, so `enqueueGate` is a single store call. It was two — `enqueue` then `mergePayload` — and between those two commits the row sat `queued` carrying the PREVIOUS pass's `candidateId`; `CLAIM_SQL` gates on `status` alone, so a second host on the shared DB could claim it in that window, grade a SUPERSEDED candidate and `markDone` the row, silently, with no error and a plausible verdict. **Merging is not clearing, in either direction**: the merge writes only the keys the producer named this pass and leaves every other key (including a stage output the store knows nothing about) untouched, whereas clearing destroys keys nobody named and hands the handler a dead row. Do not simplify the merge into a clear, and do not read it as licence to clear. Pinned by `skill-queue.store.reopen-payload.spec.ts` — two `SkillQueueStore` instances over ONE file DB, with the other host's `tryClaim` fired at store A's commit boundary. `candidate_id` (the COLUMN) is not a duplicate of the payload key: the column is written by the DRAIN on completion and records what a row PRODUCED, while the key records what the row was dispatched to grade and must exist before the stage runs.
- **The three phase-3 gate stages are registered CONDITIONALLY and are weekly-tier.** `judge-panel`, `replay` and `trigger-eval` are wired in `SkillStageHandlersService.registerStageHandlers()` only when their service resolved, following the archaeologist's rule — all three are injected `{isOptional:true}` because each needs an LLM lane and a CLI/e2e host has none, and registering a handler that could only ever answer "I am not here" spends a claim and an attempt to say what "no handler for stage X" says for free. All three sit in `WEEKLY_ONLY_STAGES`, so a frequent or nightly tick never claims one; `skill-drain.gates.spec.ts` proves that through the real drain (claimed + dispatched on `weekly`, zero claims on `frequent`/`nightly`) rather than by re-reading `DRAIN_TIER_STAGES`, which would only prove the table equals itself. Outcome mapping, per gate: a **lane failure is handed over VERBATIM** as `{outcome:'lane-failed', failure}` — only the drain reads `maxAttempts`, so a handler that flattened it would choose the retry ceiling and the backoff where neither is visible; **gate disabled / no lane in this host → `skipped`** (it ran, there is nothing to do, and a host with no LLM must not carry a backoff for a stage it can never run); **ran but produced no measurement → `unscored`**, re-eligible under `not_before`; **measured and persisted → `done`** with the gate's stable reason token and the candidate id. The split is BY REASON where the reasons differ in kind: `replay-no-holdout` is `skipped`, not `unscored`, because every session in the cluster fed the draft and no amount of waiting grows a hold-out — an `unscored` row would return every week forever to re-derive the same `null` — while `replay-no-holdout-evidence` / `-empty-plan` / `-unscored-comparison` are bad samples and stay re-eligible.
- **Two gates have no lane-failure channel out of them, and the handlers cannot invent one.** `JudgePanelService` and `TriggerEvalService` both collapse a `SkillLaneFailure` into a reason STRING (`JudgeDecision.reason`; a `TRIGGER_EVAL_SKIP_REASONS` token), so neither handler can answer `lane-failed` and a timed-out lane lands as `unscored` with the default 30-minute backoff instead of the lane's own `retryAfterMs`. Fabricating a `SkillLaneFailure` to fill the gap would mean inventing a `kind` and a `retryAfterMs` nobody measured, and the drain would then pick a retry ceiling from a guess. Widening `JudgePanelResult` is still the real fix on that side. **The trigger-eval half is DONE (TASK_2026_253) — do not re-file it.** `TRIGGER_EVAL_SKIP_REASONS.noPrompts` used to be a COLLAPSE of three unlike facts into one token, and `generatePrompts` returning `TriggerPromptSet | null` was what destroyed the distinction. It is now three tokens off a discriminated return: `noLane` (`trigger-eval-no-prompt-lane`, PERMANENT — a host with no LLM does not grow one on a retry, exactly like `noEmbedder`), `laneFailed` (`trigger-eval-prompt-lane-failed`, from both the `failed` status and the thrown-call catch) and `unusableReply` (`trigger-eval-unusable-prompt-reply`), the latter two RETRYABLE. **Consumers classify through `RETRYABLE_TRIGGER_EVAL_SKIP_REASONS`, never with a per-call-site `if`** — it is exported beside the tokens so every consumer answers "can a retry get past this" the same way, and `runTriggerEvalStage` reads it to map permanent → `skipped` and retryable → `unscored`. With one token there was no correct mapping, only a choice of which half to be wrong about (it chose `unscored` for all three, because that failure mode is bounded at one skipped `listEligible` match a week and zero tokens while `skipped` would permanently drop a measurable candidate over a transient outage). Note the reason token is written to `skill_synthesis_queue.reason` and rows carrying the retired string still exist; nothing reads that column back for a comparison, so they are display-only history.
- **`replay` has a handler and NO producer, on purpose.** Nothing enqueues a `replay` row. `ReplayValidatorService` needs a graded `SkillCandidateRow` drafted from a CLUSTER, and the cluster path (`SkillCuratorService.runSuggestionPass`, which runs inline on a timer) produces SUGGESTIONS, not candidate rows — registering a cluster draft as a candidate to feed the gate would send it back through clustering, dedup and AUTO-PROMOTION, bypassing the user's suggestion-accept step. That is a product change with its own batch. The handler ships anyway so the stage is live the moment a producer lands. `judge-panel` and `trigger-eval` DO get producers, chained from the successful end of the `prefilter` handler beside `enqueueArchaeology` for the same R3 reason: both grade a candidate, and there is no candidate until the cheap regex prefilter said there was something worth spending on. `JudgePanelService.evaluate` calls `judge.judge()` for panellist A itself, so it is a superset of the single-judge step and needs no `judge` row first; `UNIQUE(session_id, stage)` plus the `turn_count <` re-open guard bounds it to one panel per session that only re-runs when the session GROWS — it is not a weekly re-judge of the library. Both rows take the prefilter row's `workspaceRoot`, never `''` (which is reserved for genuinely cross-project work like clustering and the embedding backfill); `trigger-eval` reading the cross-project active library is a property of the measurement, not a statement about who owns the row. `dependsOn` stays NULL for both, exactly as `archaeology`'s does.
- **Lane semantics (`src/lib/lanes/`).** Every background LLM call runs on a **lane** — a declared-capability record (`provider`, `model`, `defaultTier`, `structuredOutput`, `toolUse`, `timeoutMs`, `maxInputChars`, `maxPasses`) read from `skillSynthesis.<lane>.*`. Four lanes: `archaeologist`, `synthesis`, `judge`, `replay`. Three rules that are contracts, not preferences:
  1. **No provider is privileged.** Lanes differ ONLY by capability fields. If any code path names a provider id, it is wrong — pinned mechanically by `lane-resolver.providers.spec.ts`, which is parameterized over `ANTHROPIC_PROVIDERS` and whose body contains zero provider-id literals. That scan reads compiled function bodies (`Function.prototype.toString`), and it covers the WHOLE model-resolution chain: `LaneResolverService.{resolve,readConfig,readConfigs}` **plus the two free functions `resolveLaneModel` and `resolveJudgeModel`**. The free functions were outside it until TASK_2026_250 follow-up A, so this bullet's word "mechanically" was an overclaim for exactly the code most likely to break the rule — proven by mutating a provider id into `resolveJudgeModel`, which the old scan passed and the current one fails. Docblocks are deliberately NOT scanned (`toString` returns the body only), which is what lets them name the three entries below. R6 (a small-context or non-tool-use model looping to timeout) is mitigated by `toolUse: 'none'` collapsing the pass loop — a capability guard, never a judgement about a vendor.
  2. **A lane MUST NOT mutate global `AuthEnv` or `process.env`.** `LaneResolverService` obtains an `OneShotAuthOverride` **snapshot** through the shared `IProviderAuthResolver` (token `Symbol.for('SdkProviderAuthResolver')`, injected `{isOptional:true}`) with `scope: 'lane'`, and passes it as `input.auth`. Never route a lane through `ProviderModelsService.setModelTier` / `applyPersistedTiers` — the latter writes `this.authEnv[k]` **and** `process.env[k]` unconditionally with no scope guard and would repoint the user's live chat session mid-conversation (R1). `'lane'` is inert with respect to globals by construction, because `setModelTier` guards its writes with `scope === 'mainAgent'`.
  3. **`LaneAuthOverride.env` is `Readonly<Record<string, string | undefined>>`, and the `| undefined` is load-bearing (R2).** The resolver blanks the chat provider's keys by ASSIGNING `undefined`, never `delete`-ing, because the consumer rebuilds the subprocess env as `{ ...process.env, ...override }`. Anything that drops undefined-valued keys — a JSON round-trip, `structuredClone`, a Zod parse, a truthiness filter — silently re-leaks foreground credentials into background work. Never serialize or normalize a lane env.
- **Lane resolution is three lines and has no provider branching** (`resolveLaneModel`): a pinned `model` wins; otherwise with NO provider configured it returns `resolveJudgeModel(settings.judgeModel, ws)`; otherwise it returns the **bare tier alias**. Every lane defaults to `provider: ''` / `model: ''` = "inherit". **Lines 2 and 3 return different KINDS of value and that is not a contradiction — it follows from the auth env each runs under.** Line 3's lane gets an override env whose chat `ANTHROPIC_DEFAULT_*_MODEL` keys are BLANKED by design (R2), so a pinned dated Claude id has no tier mapping left to travel through and would reach a non-Anthropic endpoint verbatim and 404; only a bare alias resolves there, via the lane env's own `ANTHROPIC_DEFAULT_<TIER>_MODEL` — which `ProviderAuthResolver.buildTierValues` rebuilds from the RESOLVED provider's persisted lane tier, then its registry `defaultTiers`, then its LIVE catalogue (TASK_2026_262). Line 2's call rides the user's AMBIENT chat auth env, where those same tier keys are populated by `ProviderModelsService.applyPersistedTiers` on the identical three-link chain, and `ModelResolver.resolve` substitutes the tier override for any `claude-*` id (`auth-providers/src/lib/auth/model-resolver.ts:38-48`) — so a non-Anthropic user gets their own haiku-tier model, not the literal. **That substitution has a boundary; see the next bullet before relying on it.** The two chains are separate code on purpose — `buildLaneEnv` blanks every `ALL_TIER_ENV_KEYS` entry out of the ambient env so background work cannot inherit the chat provider's mapping, which means a fix applied only to the chat path arrives at a lane just to be deleted. They share the derivation (`auth-providers/src/lib/model-tier-derivation.ts`) and differ only in where they write.
- **"Inherit" keeps a PINNED default, on purpose, and it is a CHOICE — do not re-file it** (TASK_2026_250, Decision 1). `resolveJudgeModel('inherit', ws)` reads the ACTIVE PROVIDER'S selected model — `provider.<authKey>.selectedModel`, with `authKey` computed from `authMethod` + `anthropicProviderId` by `resolveAuthProviderKey`, exactly as `ModelSettings` computes it — and where the user pinned no model anywhere it returns `JUDGE_DEFAULT_MODEL_ID`. That is a **deliberate divergence** from the memory curator's bare `'haiku'` tier (`CURATOR_DEFAULT_MODEL_TIER`, TASK_2026_159): "no preference expressed anywhere" is answered by shipping a model known to be good at the judge/synthesis rubric, rather than by a tier whose meaning is set by a provider the user never chose for this work — and per the line-2 mechanism above the pinned id is remapped, not sent raw, off-Anthropic. **The remapping is CONDITIONAL and the condition is not always met — do not quote the previous sentence without this one.** `ModelResolver` substitutes only where the provider has a tier mapping at all. `defaultTiers` is OPTIONAL on `AnthropicProvider`, and **3 of the 11 `ANTHROPIC_PROVIDERS` entries still omit it — `openrouter`, `lm-studio`, `requesty`** (that figure is unchanged and correct; no registry entry was edited). Each omission is DELIBERATE and documented (a 200-model dynamic catalogue; a local server holding whatever model the user loaded; a tier map Requesty's own docs contradict, `requesty-provider-entry.ts:19-23`), so "just add `defaultTiers` to those three" was never the fix — it would ship unverified ids as defaults. That set is pinned, derived from the registry, in `auth-providers/src/lib/auth/model-resolver.spec.ts`. **What changed in TASK_2026_262 is the FALLBACK BELOW `defaultTiers`, not the registry**: a tier no user pick and no registry map supplies is now derived from the catalogue the provider itself returned (`auth-providers/src/lib/model-tier-derivation.ts`), which is exactly what `requesty-provider-entry.ts:19-23` said tiers should come from. So the condition is no longer "which provider" — it is "has that provider's catalogue been fetched yet". Inside the window before the first fetch lands, or where the fetch failed, `claude-haiku-4-5-20251001` still goes to the endpoint verbatim. `openrouter` is `DEFAULT_PROVIDER_ID` **and** the registered `anthropicProviderId` default, so that was the likeliest config, not a corner. Direct Anthropic (`apiKey`) and `claude-cli` (`nativeAuth`) are unaffected — the pinned id is correct there. **Decision 1 is NOT what held the gap open and reversing it would not have closed it** (TASK_2026_250 follow-up A): a dated id and a bare alias enter the SAME tier env var (`model-resolver.ts:43` and `:57`), so whatever populates it closes both together and whatever leaves it empty leaves both verbatim — pinned by the spec above rather than asserted. Nor was this path where the gap showed first: the foreground chat substitutes `'default'` for an empty `selectedModel` (`chat-session.service.ts:418`) and sent a bare `'opus'` in the same situation, which is where TASK_2026_262 closed it. `ModelResolver` still emits a one-time `logger.warn` on that path, deliberately un-narrowed, because it is now the only signal for the timing window that remains. The other half of the old caveat — "`applyPersistedTiers` may not have run" — is **settled and ruled out**: every third-party activation branch calls `switchActiveProvider`, hence `applyPersistedTiers` (`api-key.strategy.ts:456,591,635`, `oauth-proxy.strategy.ts:146,247`, `local-proxy.strategy.ts:101`, `local-native.strategy.ts:153,222`); only the direct-Anthropic branch skips it, correctly. `JUDGE_DEFAULT_MODEL_ID` and `lane-resolver.service.spec.ts:116` stay as they are.
- **`resolveJudgeModel` has TWO callers and only one is a lane.** `resolveLaneModel` is the lane one; `SkillEnhancerService.generateCandidate` (`skill-enhancer.service.ts:690`) calls it directly and passes the result to `internalQuery.execute` with **no `auth`**, so it is not a lane but does run under the same ambient env, which is why the reasoning above covers it. It is also an affected consumer of TASK_2026_250 in its own right: skill/agent/command **enhancement** read `llm.vscode.model` before that change and reads `provider.<authKey>.selectedModel` after it, so any install where those two keys diverge sees enhancement calls change model. Pinned by `skill-enhancer.service.spec.ts` ("the model handed to InternalQuery"). It read `llm.vscode.model` until TASK_2026_250: that is the VS Code Language Model `vendor/family` selector whose only consumer (`VsCodeLmAdapter`) was deleted in `096930b51`, so it was a model id from one provider family handed to another family's endpoint — `ModelResolver.resolve` matches neither the `claude-` prefix nor a tier alias for `vendor/family` and returns it unchanged. **Never pass a `defaultValue` when reading these keys**: `PtahFileSettingsManager.get` prefers the caller's default over the registered `FILE_BASED_SETTINGS_DEFAULTS` entry, so a `''` argument shadows the host's own default and makes this path disagree with the chat path about which provider is active.
- **Unresolvable lane auth STALLS; it never falls back** (Q2). `ProviderAuthError` on a configured provider yields `{ok:false, kind:'auth-unresolvable'}` with a 30-min backoff and a user-facing reason; the queue row returns to `queued`. **The `maxAttempts` ceiling applies to `timeout` ONLY — an unresolvable-auth row stalls indefinitely and is never marked `failed`, however many attempts it burns.** That asymmetry is a product decision, not an oversight: a timeout is a transport fault nobody may ever clear, whereas unresolvable auth is a **user-fixable configuration** fault, and `markFailed` is terminal — a row re-opens only via `enqueue` once the session grows, so a _finished_ session's work would be unrecoverable even after the user corrected the provider. `not_before` gating makes an indefinite stall nearly free. Pinned by a spec that dispatches an auth failure at an attempt count far above the ceiling, so re-widening breaks a test rather than quietly discarding work. This is a deliberate divergence from the memory curator, which DOES fall back to the active provider (`sdk-internal-query.curator-llm.ts:84-91`) — falling back here would put background work straight onto the foreground quota, the exact defect phase 1 exists to remove. Any NON-auth error is rethrown rather than buried in a queue `reason`; the drain's own catch is where a real defect belongs.
- **`skill-synthesis` keeps ZERO direct SDK imports.** `IInternalQuery`, `LaneAuthOverride` and `ILaneAuthResolver` are LOCAL structural mirrors, not imports, because `agent-sdk` depends back on this side of the graph. Widening `IInternalQuery` is safe only while the concrete `InternalQueryService` still accepts the wider shape — it forwards field-by-field to `SdkQueryRunner.runOneShot`, which already declares `auth` and `outputFormat`.
- **`lane` must stay in `PROVIDER_SCOPED_TIER_PATTERN`** (`platform-core/src/file-settings-keys.ts`). A scope missing from that alternation fails in the WRITE direction only: reads fall through to `defaultTiers` and look correct, so nothing surfaces until a lane tier is persisted and silently discarded. Pinned by a round-trip spec in `file-settings-manager.spec.ts`.

The dormant set is fed to the junction layer's `disabledSkillIds` channel at the Electron activation seam (`apps/ptah-electron/src/activation/plugin-activation.ts`) — `agent-sdk`'s `SkillJunctionService` MUST NOT import `skill-synthesis` (hexagonal isolation).
- **One path to `analyzeSession`.** Every trigger — session end, idle, subagent-stop, edit-then-test, turn-complete and the boot scan — calls `SkillSynthesisService.enqueueAnalyze`, which writes ONE `prefilter` row and spends nothing. The only background caller of `analyzeSession` is the `prefilter` stage handler; the only other caller anywhere is the explicit user-initiated `skillSynthesis:analyzeNow` RPC. `enqueueAnalyze` is a shared entry point rather than six local `queue.enqueue` calls because the row's `turn_count` must be the freshly observed trajectory turn count — `REOPEN_SQL` is gated on `turn_count < ?`, so enqueuing `0` compiles, passes any call-counting test, and wedges every finished row permanently.
- **`listByStatus` has ONE scoped caller and that is the whole design** (TASK_2026_322). `skill_candidates` was the last table in the subsystem with no workspace column — `skill_synthesis_queue` has had `workspace_root` since `0032`, `skill_session_verdicts` since `0034` — so the Skills tab's list was an unfiltered read of a database every workspace on the machine shares, and a brand-new project's review queue was every other project's backlog. Migration `0040` adds the column, `SkillSynthesisService` writes the root it already hashes into `contextId` (that hash is a GENERALITY count via `countDistinctContexts` and cannot be reversed to a path, which is why the path is stored as well), and `listByStatus(status, workspaceRoot?)` gains the optional scoped form — mirroring `getWinRates` exactly, including the rule that **a scoped read INCLUDES `NULL`**. The column is three-valued: a real path is "captured there", `''` is "deliberately cross-project" (reserved, never written by the capture path), `NULL` is "origin unknown". Never coalesce `NULL` to `''` — that turns "we do not know" into a claim, which is the same defect `judge_score`'s nullability exists to prevent. **Only `SkillsSynthesisRpcHandlers` passes a root.** Clustering, dedup, the residency budget, the promotion sweep and the phase-3 gates read across projects DELIBERATELY: a promoted skill is written to `~/.ptah/skills/` and propagated into every workspace, so scoping any of those six would change what the subsystem does rather than what it shows. Widening the scoped form into the default re-scopes all six silently. The wire default is nevertheless the NARROW one (`scope?: 'workspace' | 'all'`, defaulting to `'workspace'`), because the list backs a review queue; a host with no workspace open resolves to `undefined` and sees everything, since scoping to `''` would match only rows marked cross-project and leave the list permanently empty. `0040`'s backfill resolves what `skill_synthesis_queue.candidate_id` can trace and leaves the rest `NULL` — those rows show in every workspace, which is why the UI keeps an "all projects" toggle.
- **The SKILL.md content migration is marker-gated, ONE ROW PER ROOT** (migration `0041`, TASK_2026_331 B4). `migrateSkillMdFiles` injects `when_to_use:` frontmatter and is a ONE-TIME transform, but `SkillSynthesisService.start()` ran it unconditionally, TWICE per launch — once for the active root and once for the candidates root. Measured 2026-08-28 against a real `~/.ptah/skills` of 2420 `SKILL.md` files (9.2 MB): **388 ms** of synchronous main-thread I/O per launch (walk 188.6 ms + read 199.2 ms), all of it to re-confirm files it would never change. The plan's "~2 s" figure exists nowhere in this repo — do not quote it. `SkillMdMigrationStateStore` now answers "has this root already been migrated?" from `skill_md_migration_state` BEFORE the first `readdirSync`. Four rules. (1) **The gate's only inputs are `SKILL_MD_MIGRATION_VERSION` and a 24 h age ceiling.** Change what a migrated file looks like ⇒ bump the constant ⇒ every stored marker is invalidated. **Directory mtime is deliberately NOT an input**: a directory's mtime does not change when a file inside a SUBdirectory is edited, and every `SKILL.md` lives at `<root>/<slug>/SKILL.md`, so an mtime comparison would skip real work with full confidence. (2) **The marker may only ever cause a walk, never wrongly prevent one.** No store, a store that throws, an absent row, a future-stamped row — all resolve to "walk". `SkillMdMigrationStateStore` swallows its own failures and the caller catches anyway, because `connection.db` throws `PERSISTENCE_UNAVAILABLE` when the DB is not open and a port cannot force its implementors to degrade. (3) **The marker is written only after a walk that completed with `errors` empty** — a pass that failed on even one file has files still carrying the old shape, and marking the root done abandons them for a day and again on every launch while the failure persists. (4) **One row per root, keyed by path, NOT one row for the table.** The two roots are walked back to back, so a shared row written by the first would claim the second was migrated even when it failed; and `candidatesRoot` defaults to a subdirectory of `activeRoot` but `skillSynthesis.candidatesDir` (like `ptah.skillsRoot`) can repoint it, so a path key means a moved root simply has no marker and gets walked — the safe direction. Pinned by `skill-md-migration.marker.spec.ts`, which asserts CALL COUNTS (zero `readdirSync`/`readFileSync` against a 2000-file stub tree), never timings, and whose header records the seven mutations that kill its twelve cases.
