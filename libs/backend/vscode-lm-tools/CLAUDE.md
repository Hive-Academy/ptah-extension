# @ptah-extension/vscode-lm-tools

[Back to Main](../../../CLAUDE.md)

## Purpose

Hosts the **Code Execution MCP server** and Ptah API surface (`PtahAPI`) exposed to AI agents — IDE capabilities, browser automation, web search providers, permission prompts, and the platform system prompt.

## Boundaries

**Belongs here**:

- `CodeExecutionMCP` server + `PtahAPIBuilder`
- IDE/browser capability ports (`IIDECapabilities`, `IBrowserCapabilities`)
- Permission prompt service
- Web search provider implementations (Tavily, Serper, Exa)
- Chrome-launcher browser capability + screen recorder
- Platform system prompt assembly

**Does NOT belong**:

- Direct `vscode` imports in the platform-agnostic surface (VS Code impl is gated behind the `/vscode` subpath)
- Persistence, memory, RPC handlers

## Public API

Code execution: `PtahAPIBuilder` (+ `IDE_CAPABILITIES_TOKEN`, `BROWSER_CAPABILITIES_TOKEN`), `CodeExecutionMCP`. Types: `PtahAPI`, `BrowserRecordStartResult`, `BrowserRecordStopResult`, `ToolResultCallback`.
Capabilities: `IIDECapabilities`, `IBrowserCapabilities`, `BrowserSessionOptions`, `ChromeLauncherBrowserCapabilities`.
System prompt: `PTAH_SYSTEM_PROMPT`, `PTAH_SYSTEM_PROMPT_TOKENS`, `buildPlatformSystemPrompt`.
Web search: `TavilySearchProvider`, `SerperSearchProvider`, `ExaSearchProvider`, `WebSearchProviderType`, `IWebSearchProvider`, `WebSearchFailureReason`, `WebSearchProviderOutcome`, `WebSearchAttributedResultItem`.
Other: `PermissionPromptService`, `ScreenRecorderService`, `registerVsCodeLmToolsServices`.
Note: `VscodeIDECapabilities` lives at the `'@ptah-extension/vscode-lm-tools/vscode'` subpath (excluded from Electron bundling).

## Guidelines

- The platform-agnostic surface MUST NOT import `vscode`. VS Code-specific `VscodeIDECapabilities` is at the `/vscode` subpath only — bundlers (Electron) drop that subpath at build time.
- Capabilities are injected via `IDE_CAPABILITIES_TOKEN` / `BROWSER_CAPABILITIES_TOKEN` — host apps register their own implementations. Use a DI token ONLY when the implementation genuinely differs per host (VS Code LSP, Electron CDP). Host-agnostic collaborators (MCP registries, `McpInstallService`) are wired directly in `PtahAPIBuilder` — there is exactly one construction site and all three hosts share it via `registerVsCodeLmToolsServices`.
- `ptah.harness.*` collaborators are declared as narrow structural interfaces in `harness-namespace.builder.ts` (`HarnessMcpRegistrySource`, `HarnessSkillsDirectory`, `HarnessMcpInstaller`) so the builder stays unit-testable; each is optional and degrades to a clear error.
- **`createSkill` takes a real `scope`, and the two scopes share one plugin id.** `user` (default) writes `~/.ptah/plugins`; `workspace` writes `{ws}/.ptah/plugins` via the shared `workspacePluginsDir` — never a hand-rolled join, since the plugin loader scans the same path. A name already taken in the other scope is REFUSED: the loader resolves a clash workspace-wins, so the second write would silently stop the first from loading.
- **A harness search reports THREE states, never two.** `searchSkills` and `searchMcpRegistry` return `{ …, status: 'ok' | 'degraded', sources: HarnessSourceReport[] }`, and the dispatcher turns `degraded` into an MCP tool error. Never map a caught upstream failure to an empty result set: `{ skills: [], count: 0 }` is indistinguishable from "the marketplace has nothing", and an agent that read one as the other told the user no Three.js skills existed and authored replacements for four that already did. `unavailable` (no client wired on this host) is deliberately distinct from `failed` (the source threw) and does not degrade the call. All six harness methods are exposed BOTH on `ptah.harness.*` and as `ptah_harness_*` MCP tools — a method reachable from only one of the two surfaces is a bug, and `proposeConfig` was exactly that.
- **`CodeExecutionMCP` registers Ptah's own server for every DETECTED CLI, not just Claude (TASK: user-launched CLIs saw no Ptah tools).** Ptah's server used to have exactly one persistent registration — `{ws}/.mcp.json` — and every rival CLI received it IN-PROCESS at spawn time: Codex via SDK `config.mcp_servers`, Copilot via `--additional-mcp-config`, Cursor via `agentOptions.mcpServers`, opencode via `OPENCODE_CONFIG_CONTENT`, Antigravity via an ephemeral key removed after `done`. That covers every CLI Ptah spawns and no CLI the USER launches, which is why a `codex` in a terminal listed `node_repl` and nothing else while Ptah ran beside it. `ptah-mcp-slots.ts` is the one definition of the slot set; the scope per target was MEASURED, not assumed:

  | Target      | File                               | Scope     | Gated on detection |
  | ----------- | ---------------------------------- | --------- | ------------------ |
  | claude      | `{ws}/.mcp.json`                   | workspace | no                 |
  | cursor      | `{ws}/.cursor/mcp.json`            | workspace | yes                |
  | codex       | `{ws}/.codex/config.toml`          | workspace | yes, if TRUSTED    |
  | codex       | `~/.codex/config.toml`             | home      | yes, if UNTRUSTED  |
  | antigravity | `~/.gemini/config/mcp_config.json` | home      | yes                |
  | antigravity | `{ws}/.agents/mcp_config.json`     | workspace | yes                |

  Workspace scope is preferred wherever it exists. **Antigravity is two products with different answers, so it gets both files.** The Antigravity EDITOR documents `{ws}/.agents/mcp_config.json`; the `agy` CLI does not read it, on three independent measurements — `agy mcp list` reported `No MCP servers configured` with that file on disk and listed a server the moment the same entry went into the global file; the CLI's bundled docs define a Global and a Plugin scope only; and the `agy` binary carries literals for `.agents/skills`, `.agents/rules`, `.agents/hooks.json`, `.agents/plugins`, `.agents/workflows` and `.agents/agents`, and none for `.agents/mcp_config.json`. Workspace-only would therefore break the CLI silently, which is the surface Ptah detects and spawns. `AntigravityCliAdapter` writes only the HOME file, so the workspace one has a single writer. **Codex DOES have a project scope and its own CLI surfaces hide it** — `codex --help` and `codex doctor` name only `~/.codex/config.toml` and `codex mcp add` has no scope flag, which is exactly what an earlier version of this doc wrongly concluded from. Codex's documentation says otherwise, and the probe agrees: with `{ws}/.codex/config.toml` present, `codex doctor` in that workspace went from `MCP servers 1` to `2` and `codex mcp list` printed the project server alongside the home one. The two MERGE, so the project file disturbs nothing set globally. Workspace scope is also the only scope that can be RIGHT here — Ptah's server is one port per Ptah process, and two windows on two folders cannot share one home entry. **A project-scoped Codex config is honoured only for a TRUSTED project, so the scope is CHOSEN per root rather than fixed.** A fresh `git init` temp repo with no `[projects.'<path>'] trust_level = "trusted"` entry reported `MCP servers 1` — the file was ignored, silently. `codexProjectTrusted` (harness-sync) reads that record, and an untrusted root gets the HOME config, which Codex reads unconditionally. That is self-healing in the right direction: the untrusted root works on the first `codex` run, that run raises the trust prompt, and the next pass moves the entry to the workspace file and drops the home one. Ptah never writes a trust entry — trust grants Codex the right to run commands in a directory, and answering that for the user would be Ptah settling a security question asked of them. The one cost: two _untrusted_ roots open at once share the single home entry, so the last write wins. **Copilot is deliberately absent** — `copilot mcp --help` loads workspace `.mcp.json` / `.github/mcp.json`, verified with `copilot mcp list` printing `Workspace servers: ptah (http)` with no Copilot-specific file on disk, so writing `~/.copilot/mcp-config.json` would declare the same server twice in every project. **VS Code is absent** because its MCP servers are user-managed in the editor and Ptah already serves that host in-process. Everything but `claude` is gated on the CLI detector: writing `~/.codex/config.toml` on a machine with no Codex CREATES that file. `claude` is ungated because `.mcp.json` is read by three tools and has always been written unconditionally.

- **`claude` is the one slot NOT written through a facet, and that asymmetry is deliberate.** `createMcpFacet('claude')` has `includeType: false` and emits `{ url }`; this key has been `{ type, url }` in every `.mcp.json` Ptah has written. Routing it through the facet would rewrite that entry in every existing user's repository to say the same thing differently, for no capability — Ptah's server already reached Claude. Every OTHER slot goes through its facet, which owns the path, the dialect (`url` vs `serverUrl`, a fenced TOML table for Codex), the atomic write and the per-config-file lock. It is still one writer per file.
- **A Codex server entry is SUFFICIENT. Do not add a `features` flag beside it — one was written, measured and deleted.** The belief that `features.tool_search_always_defer_mcp_tools = false` is required came from `CodexCliAdapter`, which sends it in-process. A file-based half was built for the user-launched path and then tested end to end against a live Ptah MCP server on codex-cli 0.150.1, with `codex exec`:

  | Config                                           | Eager tool list | Tool callable                                                      |
  | ------------------------------------------------ | --------------- | ------------------------------------------------------------------ |
  | server entry only                                | NONE            | —                                                                  |
  | server entry + flag in `{ws}/.codex/config.toml` | NONE            | —                                                                  |
  | server entry + flag in `~/.codex/config.toml`    | NONE            | —                                                                  |
  | server entry only, asked to search               | —               | **yes** — `mcp: ptah/ptah_workspace_analyze started → (completed)` |

  So the flag changes nothing in either scope, and the registration alone gives a user's own Codex session working access. What Codex does is **defer** MCP tools out of the eager list until the model runs a tool search — a behaviour the flag no longer disables (`codex features list` reports it with stage `removed`), and one Ptah cannot override from a config file. If eager listing ever matters, the lever is the AGENTS.md Ptah already propagates, not a config key.

- **`CodeExecutionMCP` owns one `.mcp.json` entry per OPEN workspace folder, not one for the active root.** It used to track a single `registeredMcpJsonPath` resolved through `getWorkspaceRoot()`, and on Electron `setActiveFolder()` fires `onDidChangeWorkspaceFolders` — which `workspace:switch` calls on every tab switch. So switching between two folders that were BOTH already open unregistered from one and registered in the other: a write into a file inside the user's version-controlled repository, six times in one session, for a change nothing could observe (TASK_2026_354). Ownership is now the folder SET (`registrations: Map<path, port>`, reconciled against `getWorkspaceFolders()`), so a switch is a no-op, an added folder gets an entry, and only a folder that LEFT the workspace loses one. `registerInMcpJson` is additionally read-COMPARE-write: an entry already equal to the desired one is left byte-for-byte alone and logs nothing. Per-path records also make a failed removal safe to leave outstanding — it can no longer be overwritten by a write elsewhere — so the TASK_2026_332 rule that coupled the two mutations is gone, and refusing to register the folder the user is working in because an unrelated CLOSED folder's file was contended would have been a false `mcpServerRunning: false`.
- **Every `.mcp.json` ownership mutation goes through `CodeExecutionMCP`'s operation queue, and `withMcpConfigLock` is not a substitute for it.** The lock is `harness-sync`'s and is keyed per FILE; the races here span DIFFERENT files. A user switching workspace A → B → C produces two reconciles that both read the registration record as {A} and then write B and C independently, stranding a live `ptah` entry in B for a folder that is no longer open; a `stop()` right after a switch unregisters A while an outstanding event writes B back with a port that is about to die. So `mcpOpQueue` serializes the OPERATION (a job reads `registrations` only after the previous job finished updating it) and `repointGeneration` makes the newest request win (a superseded re-point is dropped before it touches disk). `stop()` bumps the generation and sets `stopped`, which is what cancels an in-flight or late-arriving re-point. Both halves are needed and both are pinned by `http-mcp-server.service.spec.ts` section 6 — with a DELIBERATELY DEFERRED lock, because the straight-through lock stub completes each mutation inside one microtask and neither race is reachable without it. The real-lock, real-`fs` half lives in `http-mcp-server.service.concurrency.spec.ts` (TASK_2026_332).
- **`startHttpServer` attempts every candidate port against ONE `http.Server`, so `tryListen` must remove its `'listening'` listener on failure too.** A one-time listener is only consumed when it FIRES; a candidate refused with `EADDRINUSE` leaves its listener attached and the next candidate's single `'listening'` event reaches both, logging the started line and writing `ptah.mcp.port` once per ATTEMPTED port (TASK_2026_354). The fallback also emits exactly one warning, after the outcome is known, naming the likely holder (another Ptah instance for `EADDRINUSE`, an OS-reserved range for `EACCES`) and the port actually chosen.
- **`ensureRegisteredForSubagents()` returns an outcome, and every caller must AND it into the `mcpServerRunning` it passes to the session.** It resolves with `{ registered, reason }` (`McpSubagentRegistration`), never rejects, and `registered: false` is a normal answer — the config file was contended (`lock-timeout`) or the write failed (`write-failed`). It used to resolve with `undefined` whatever happened, because both mutation helpers swallowed every failure into a warn, so a caller that awaited it and then reported `mcpServerRunning: true` was making a **false assurance**: the subagent spawns believing it has Ptah tools and finds no `ptah` key in `.mcp.json`. That is worse than the lost update the lock prevents, not better. Rejecting was considered and rejected as the shape — three of the six callers have no local catch and would abort a whole chat session over a two-second contention, whereas `mcpServerRunning: false` is a degraded mode the SDK path already supports. `lock-timeout` is deliberately distinct from `write-failed` (via `isFileLockTimeoutError`, its one production consumer): the first is transient by construction and retryable, the second is likely to repeat. A failed REMOVAL is also never followed by a write into a different file — that would leave a live entry in two repositories and destroy the record of the stale one (TASK_2026_332).
- Web search providers all implement `IWebSearchProvider`. Selection is a LIST (`ptah.webSearch.providers`), and `WebSearchService` queries every selected provider **in parallel with `Promise.allSettled`** (TASK_2026_372). The failure policy has three parts, and all three are load-bearing:
  - **Isolation** — one provider failing never fails the call while another returned results. A missing API key is that provider's own `missing-api-key` failure, not a throw. The ONLY throw is total failure, and its message names every provider and its reason.
  - **Attribution** — `outcomes` carries one `WebSearchProviderOutcome` per SELECTED provider, ok and failed alike, each failure with a machine-readable `reason` (`missing-api-key` | `timeout` | `provider-error`) and a message. Never let an empty result set and a failed provider look the same — that is the same defect the harness-search three-state rule exists to prevent. Merged results are de-duplicated by normalized URL (`new URL` lower-cases the scheme and host, the fragment is dropped, and trailing slashes are stripped from the PATH only) and each item is tagged with the `sources` that returned it. The strip is path-scoped on purpose: `https://example.com/a?b=1/` and `https://example.com/a?b=1` are different pages, and a path is case-sensitive so it is never case-folded.
  - **Re-assessment** — `ptah_web_search` takes an optional `providers` argument that overrides the configured set for one call, and `formatWebSearch` ALWAYS renders a `Provider status` section, success included. That section is the only way the agent learns a provider failed and can retry with the ones that worked, so it must not be made conditional on failure. Every outcome line carries the result count AND the duration, failures included — a failure's duration is what separates a slow timeout from an instant refusal.
  - **The `providers` argument is validated with Zod at the dispatcher, and an invalid value is an MCP tool ERROR — never a silent fallback.** `WebSearchArgsSchema` (`mcp-core/protocol-dispatcher.ts`) is `strict()`, so the singular `provider` is reported rather than dropped. Before it existed, a bare string such as `providers: 'serper'` passed the length test in `resolveProviders`, was iterated character by character, emptied, and fell back to `['tavily']` — the retry ran the provider that had just failed and `outcomes` named Tavily as though the agent had asked for it. A discarded override is invisible to the agent; an error is not.
  - **The merge is round-robin across the successful providers, NOT provider-by-provider concatenation.** This is a deliberate amendment to the TASK_2026_372 contract, which said "concatenate in selection order". Concatenation let the `maxResults` trim discard every row of a provider that `Provider status` still reported `ok`: with `['tavily','serper']`, `maxResults` 5 and five distinct URLs each, the merged list held ten and the cut kept only the five Tavily rows, while the status section still said `serper — ok (5 results)` and no result line named Serper. Interleaving makes the trim sample every provider, which is the reason the feature exists — to actually USE every selected provider. The de-duplication rule is unchanged (first occurrence wins its title and snippet, each later duplicate appends its provider to `sources`) and selection order is the tie-break inside one round.
  - `webSearch.providers` falls back to the legacy single `webSearch.provider` string, then to `['tavily']`. That is the one read migration — existing installs carry the legacy key on disk. Do not add a second.
- Permission prompts route through `IUserInteraction` (platform-core) via the prompt service.
- `catch (error: unknown)`.
