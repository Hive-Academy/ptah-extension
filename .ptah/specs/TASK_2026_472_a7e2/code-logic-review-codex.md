# Verdict

APPROVE WITH FINDINGS — the persistent-stream change is behaviourally sound on the normal path and preserves watchdog/turn invariants, but resumed input failure is still reported as a started query and the required real-background-subagent proof is absent.

## Findings

1. **A resumed slash command can be accepted even when its only delivery channel has already failed.**
   - Evidence: `libs/backend/agent-sdk/src/lib/helpers/session-lifecycle/session-query-executor.service.ts:328-354` starts a resumed query on an idle iterable, attaches the actual command stream through `streamInput()`, then catches that promise's rejection by logging only and still returns the query at `:359-370`.
   - Concrete failure scenario: `executeSlashCommandQuery(session, "/context", ...)` successfully constructs the SDK query, but `sdkQuery.streamInput(userMessageStream)` rejects because the transport cannot write while the output side remains open. The command is never delivered, yet `executeSlashCommand` returns a stream and the RPC path reports startup success; the user waits on an idle query until another failure or the 180-second watchdog abort instead of receiving the input error immediately.
   - Severity: should-fix.

2. **Acceptance item 5 has not been verified by either supplied evidence artifact.**
   - Evidence: `.ptah/specs/TASK_2026_472_a7e2/task.md:82-84` requires a real background subagent to survive the slash parent result, while `.ptah/specs/TASK_2026_472_a7e2/experiment-slash-over-streaminput.md:126-131` explicitly says that downstream checkpoint behaviour was not tested; the new spec substitutes an ordinary second user message at `libs/backend/agent-sdk/src/lib/helpers/session-lifecycle/session-query-executor.slash-persistence.spec.ts:288-298`.
   - Concrete failure scenario: streamed input remains open and accepts the spec's second ordinary message, but Claude Code independently checkpoints on the zero-turn slash result and aborts a live background agent. All new assertions pass while the user still sees the original background-agent denial, so the task cannot yet claim its fifth acceptance item.
   - Severity: should-fix.

3. **The spec's zero-turn command assertion is synthetic rather than evidence that the streamed message was parsed as a command.**
   - Evidence: the fake assigns `num_turns: 0` solely from `text.startsWith('/')` at `libs/backend/agent-sdk/src/lib/helpers/session-lifecycle/session-query-executor.slash-persistence.spec.ts:91-96`, and the assertion at `:285-286` checks that value generated by the same rule. The non-tautological regression signal is the later second result at `:295-298`, which would not occur through the old raw-string branch.
   - Concrete failure scenario: a future SDK change stops recognizing streamed `/context` messages and treats them as model prompts, but the fake still labels every slash-prefixed string zero-turn; this spec stays green despite command semantics regressing. The real-SDK experiment currently covers that boundary for 0.3.150, so this is a test limitation rather than a defect in the submitted production path.
   - Severity: note.

## Questions answered

1. **Watchdog accounting.** Registration creates `turnInFlight: false` with no hold (`session-registry.service.ts:147-160`); a non-empty slash prompt deliberately takes no initial idle hold (`session-query-executor.service.ts:239-255`). The first pump yield calls `markTurnStarted`, whose release cannot underflow because `NoActivityWatchdog.release()` returns at zero (`session-stream-pump.service.ts:75-85`; `no-activity-watchdog.ts:50-60`); the first result re-takes exactly one hold on the true-to-false transition, the second yield releases it, and the second result re-takes it (`session-registry.service.ts:347-380`). Thus the turn-owned count traces `0 → 0 → 1 → 0 → 1`; it neither goes negative nor stacks above one, though independent permission/subagent owners may legitimately add their own reference-counted holds.

2. **Turn settlement.** `StreamTransformer` invokes `onTurnEnd` first in every result branch (`stream-transformer.ts:435-445`), and the adapter callback reaches `SessionRegistry.markTurnEnded` (`sdk-agent-adapter.ts:1271-1279`). That clears `turnInFlight` and wakes the parked pump (`session-registry.service.ts:373-385`), while the pump claims the next turn before yielding and refuses another yield until settlement (`session-stream-pump.service.ts:75-105`), so the slash path neither bypasses the one-message gate nor deadlocks after a normal result.

3. **The attachment path.** The executor now sends every non-empty initial prompt through `createUserMessage`, forwarding both files and images unchanged (`session-query-executor.service.ts:126-153`), and it never selects a raw-string path (`:324-345`). A slash-looking prompt with attachments therefore remains on the same iterable `SDKUserMessage` path it used when the old attachment bypass excluded it from slash classification; no attachment-specific branch was lost.

4. **Resumed versus initial.** `executeSlashCommandQuery` captures the real session id, awaits teardown of the old record, then registers a fresh record with the command as its initial prompt (`session-lifecycle-manager.ts:539-556`); registration creates a new queue (`session-registry.service.ts:141-167`) and the executor pushes the command into that new queue (`session-query-executor.service.ts:146-153`). On resume, `query()` receives the idle iterable and the queued command is delivered through `streamInput(userMessageStream)` (`session-query-executor.service.ts:328-357`); on an initial session, the user-message iterable itself is the query prompt. The old record's queue does not survive—and should not—but the command survives correctly because it is queued only after the replacement record exists.

5. **Abort and teardown.** Explicit session teardown interrupts, aborts, and removes the record even when an earlier cleanup step throws (`session-control.service.ts:203-278`); abort also ends both the idle prompt and user-message iterators (`session-stream-pump.service.ts:67-93,147-170`) and stops the watchdog through its abort listener (`session-query-executor.service.ts:227-230`). A persistent idle slash session intentionally remains registered and held for later turns; when its sole output consumer exits, the broadcaster performs token-guarded teardown (`chat-stream-broadcaster.service.ts:371-432`), while genuine unheld in-turn silence can still trigger the watchdog (`no-activity-watchdog.ts:215-236`). The exception is finding 1: a rejected resumed `streamInput()` is swallowed, delaying visible failure/cleanup.

6. **Does the new spec prove the fix?** Yes for the Ptah mechanism: under its two modeled SDK transport rules, the old raw-string branch closes after result one, so the asserted second result fails without the production change, while both resumed and initial iterable paths produce two results on the same fake query (`session-query-executor.slash-persistence.spec.ts:273-330`); it contains no elapsed-time assertion. The fake faithfully models string-derived single-turn closure (`:81-119`), but its zero-turn command classification is by construction (`:91-96`) and it does not model a real background agent, so real command parsing rests on the supplied SDK experiment and acceptance item 5 remains open.
