## Five logic questions

### 1. How does this fail silently?

- **The attribution notice silently disappears in production with no build warning.** `brand-marks.generated.ts:1-104` carries the SHA, MIT notice, trademark note and the per-icon licence table (including `angular: CC-BY-4.0` at `:46` and `sonarqube: LGPL-3.0` at `:95`) as a plain `/**...*/` JSDoc-style block comment. `apps/ptah-extension-webview/project.json:71-77` sets `optimization.scripts: true` for the production configuration with no `legalComments` override, and `extractLicenses` is unset in that configuration (only set `false` at `:87`, inside the `development` block). I verified experimentally with the workspace's own esbuild binary (`node_modules/.bin/esbuild`, v0.28.2 — same major as Angular's `@angular/build:application`) that a `/**` comment with no `/*!` prefix and no `@license`/`@preserve` token is dropped entirely under `--minify`, in every `--legal-comments` mode (`eof`, `none`, and the implicit default) — nothing is written, not even to a linked/EOF notices block. The identical input re-run with a `/*!`-prefixed comment IS preserved and moved to EOF. This is a hard esbuild classification rule, not an Angular-builder configuration choice, so no combination of `extractLicenses`/`legalComments` on `project.json:71-93` can rescue the _current_ comment text — it is never classified as a legal comment in the first place. Nothing in the build fails or warns; the bundle is produced successfully with the notice simply gone. See Blocking-1.

### 2. What user action produces unexpected behaviour?

- None yet from Batch 4 in isolation — the generated table is not wired into any renderer (`native/index.ts` has no `brand-mark` export; confirmed live), so nothing changes for a live user until Batch 7b lands. Once wired, a user who opens the CLI-target picker expecting a real VS Code logo (R1: "real AI-vendor marks for CLI targets") will instead see a generic monogram tile for `visual-studio-code`, because the live run rejected every variant (`blend mode; filter; gradient; gradient or pattern fill; mask other than one opaque white rectangle`) with no mono fallback available. This is documented and correctly handled by the code (falls back gracefully to `MONOGRAM_SLUGS`), but it is a partial shortfall against the R1 promise the user should be told about explicitly rather than discovering in the UI. See Moderate-1.

### 3. What input data produces a wrong answer?

- I did not find a concrete case in the actual data (spot-checked `surface`, `onDark` and `mono` assignments in the live run report against every explicit expectation in `implementation-plan.md` Task 4.2 validation notes — `github`/`vercel`/`openai` have `onDark`; `sentry`/`davinci-resolve` are `surface: 'light'`; `anthropic`/`claude` have `mono` — all matched). The residual risk class is theoretical: `colour.mjs:26-46` parses `rgb()`/`rgba()` with percentage or fractional alpha, and `:47-67` parses CSS `color(srgb|display-p3 ...)`; a malformed-but-matching value could silently compute a wrong hex and thus a wrong WCAG contrast ratio (`colour.mjs:101-104`), which could misclassify `surface` (e.g. an actually-illegible-on-dark mark gets `surface: 'any'` and renders on `bg-base-200` instead of a white tile). No such case exists in the 68 vendored slugs today, so this is a residual-risk note, not a finding against the delivered code.

### 4. What happens when a dependency fails?

- **Index fetch, licence-text fetch, or any per-icon SVG fetch fails (network/HTTP error) on every mirror**: `fetchPinned` (`vendor-brand-icons.mjs:312-339`) collects failures per mirror and throws `VendorError` after exhausting `source.mirrors`. `main()` never reaches `writeFileSync` (`:694-697`) before every fetch resolves, so nothing is written — traced through the full call graph, confirmed correct.
- **A mirror returns HTTP 200 with non-SVG content (e.g. an error page)**: `extractArtwork` (`extract-artwork.mjs:417-433`) checks `/<svg[\s>]/.test(svgText)` first and returns a clean rejection rather than throwing, which the caller treats as a normal rejection (falls back to mono/monogram) — correct, no crash.
- **theSVG's index schema drifts** (`indexBySlug`, `vendor-brand-icons.mjs:200-217`): entries missing `slug` or with a non-object `variants` are silently skipped from the index (`continue`), which could silently drop a manifest icon out of the index. This does not fail silently overall, though: `planIcon` (`:268-272`) then throws `VendorError` for any manifest icon not found in the (possibly shrunk) index, so a schema drift still aborts the run loudly rather than producing a wrong table. Correct fail-safe design.
- **Output exceeds the 300 KB budget** (`:672-678`): checked after formatting, before any write; throws and writes nothing. Actual output is 66,423 bytes, well inside budget.

### 5. What is missing that the requirements never mentioned?

- A shipped, build-independent notices artifact. The plan (`implementation-plan.md` D6, C12) specifies the header as the vehicle for the SHA/date/MIT/trademark note but never asks "does this survive minification into the artifact users receive?" — that question was left implicit, and the answer today is no (Blocking-1).
- Nothing enforces that the rejection/report output (`printReport`, `vendor-brand-icons.mjs:597-631`) actually gets pasted into a PR description, as `batches.md` Batch 4's rationale expects ("Rejection report goes in the batch report"). This is a process gap for the team-leader to close at commit time, not a code defect.

- Symptom: none visible to anyone — the build succeeds, the extension works, and there is no artifact (console output, warning, CI failure) indicating the notice is gone. ### `visual-studio-code` CLI-target mark falls back to a monogram

- Trigger: theSVG's `visual-studio-code/default.svg` at the pinned commit uses a blend mode, a filter, a gradient, and a non-rectangular mask — all hit hard rejection rules — and has no `mono` variant to fall back to.

- Current handling: correct and safe (graceful monogram fallback, no crash, reason printed), but not surfaced anywhere the user/architect would see it without reading console output.
- Recommendation: see Moderate-1.

### Manifest-vs-index schema drift aborts the whole run

- Symptom: the script exits non-zero with a clear per-slug error; nothing is written.
- Evidence: `vendor-brand-icons.mjs:268-272`, `:200-217`.
- Current handling: correct — fails loudly, never produces a silently-wrong table.
- Recommendation: none; this is the desired behaviour and needs no change.

## Blocking issues

### Blocking-1: Licence/attribution notice does not survive into the production bundle

- File: `libs/frontend/ui/src/lib/native/brand-mark/brand-marks.generated.ts:1-104` (the notice); `apps/ptah-extension-webview/project.json:71-77` (the build configuration that drops it); generator at `scripts/vendor-brand-icons.mjs:515-548` (`headerLines`, which authors the comment in the form that gets stripped).
- Scenario: any `npx nx build ptah-extension-webview` (or the `production` configuration used for the shipped VSIX) minifies the JS. esbuild only preserves comments it classifies as "legal" — those starting with `/*!`, or containing `@license`/`@preserve`. `headerLines` emits a comment starting with `/* eslint-disable ... */` followed by `/**`, neither of which esbuild recognises, so the whole block (SHA, source URL, MIT notice, trademark/nominative-use note, and the per-icon licence table including `angular: CC-BY-4.0` and `sonarqube: LGPL-3.0`) is deleted during minification with no warning and no fallback location (not even a linked EOF/notices file, because it was never classified as legal in the first place).
- Impact: CC-BY-4.0 requires attribution as a licence condition; LGPL-3.0 requires notice preservation. Shipping the vendored Angular and SonarQube marks (and, by the same mechanism, every other icon whose licence requires a notice) with zero attribution in the artifact users actually receive is a licence-compliance failure, not merely a documentation gap — the repository has no other notices mechanism (confirmed: no `THIRD_PARTY*`/`NOTICE*` file anywhere in the tree, no license-extraction script). This blocks release of any build that includes these marks.
- Fix (recommend option 2, a shipped notices file, over options 1 and 3 — see rationale below):
  1. **Monogram-only for the CC-BY/LGPL icons** (drop `angular` and `sonarqube` real artwork, force them through `MONOGRAM_SLUGS`). Rejected as the primary fix: it silently narrows R1/D6's icon set for reasons unrelated to visual/technical rejection, and would need to be repeated for every future icon whose licence carries an attribution term — a policy problem solved by removing assets, not by fixing the pipeline.
  2. **RECOMMENDED — a small, build-independent `THIRD_PARTY_NOTICES.md` (or `.txt`) shipped inside the VSIX**, generated by `vendor-brand-icons.mjs` alongside the TS table (same source-of-truth, same determinism guarantees) and explicitly _not_ excluded by `apps/ptah-extension-vscode/.vscodeignore` (the ignore file already special-cases `**/LICENSE.md` for scanner reasons at `:57-62`; a differently-named notices file avoids that rule while still shipping). This is immune to minification/bundling entirely, requires no `/*!` marker gymnastics, and is the standard mechanism this kind of attribution obligation is met with elsewhere (e.g. `3rdpartylicenses.txt` conventions). It also naturally scales to every future licensed icon without depending on build-tool comment-preservation semantics staying stable across Angular/esbuild upgrades.
  3. Preserve a `/*!`-tagged legal comment and turn `extractLicenses` on for the `production` configuration. Viable but strictly weaker than option 2: it depends on Angular's esbuild wrapper continuing to map `extractLicenses` the same way across version bumps, produces a separate `3rdpartylicenses.txt` whose packaging into the VSIX still has to be independently verified (nothing today copies `dist/**/3rdpartylicenses.txt` into the vsce package root the way `pre-package` copies `README.md`, `apps/ptah-extension-vscode/project.json:101-113`), and ties compliance to a minifier implementation detail future contributors are unlikely to know about when they next touch `headerLines`.
  - Whichever option: add a spec/CI check that fails if a manifest icon's declared licence requires attribution (anything other than `CC0-1.0`/`MIT`) and the notice mechanism does not list it, so this cannot regress silently the way it did here.

3. `planIcon()` per manifest entry resolves which files to fetch (`monogram`/`unindexed`/theSVG-indexed), validates required variants exist, and determines the light/dark `art` split — OK, throws for any inconsistency (declared monogram but indexed, requested mono but unavailable, etc.).
4. `probeA4()` runs the A4 assumption check against `github/dark` before any output is produced — OK, aborts the whole run on failure per the plan's "STOP and report" rule for assumption checks (though this run passed).
5. `vendorIcon()` per icon: fetch → `extractArtwork` (svgo normalise + custom rejection-plugin) → visibility/contrast gates → optional `dark`/`mono` variants, each independently gated — OK, a rejected variant degrades gracefully (art→mono→monogram; dark→omitted; mono→omitted) and is recorded in `rejections`, never silently dropped from the report.
6. `renderModule()` builds the TS source as a pure string transform over the already-computed `outcomes` — OK, no I/O, fully deterministic given the same `outcomes`.
7. Budget check on the formatted, prettier-run output — OK, before any write.
8. `--check` mode diffs in memory against the committed file and exits non-zero on drift; normal mode writes to a `.tmp` file and `renameSync`s it into place — OK, atomic, no partial-write window. **Gap**: step 6's output, once it reaches the committed TS file, carries a licence notice that step 9 (the downstream Angular/esbuild production build, outside this script's control) silently discards — this is the one place in the whole pipeline where "committed correctly" does not imply "reaches the user correctly." See Blocking-1.

## Verdict

- Recommendation: REVISE
- Confidence: HIGH
- Top risk: shipping vendored CC-BY-4.0/LGPL-3.0 icon artwork with zero attribution in the production VSIX is a licence-compliance failure that a code review, not a legal review, is the last checkpoint to catch before release.
- What a robust implementation would add: (1) a build-independent notices file generated alongside the TS table and shipped in the VSIX (Blocking-1, recommended option 2); (2) a spec/CI check tying "licence requires attribution" to "notice mechanism lists it," so this class of gap cannot regress silently; (3) the `visual-studio-code` monogram fallback named explicitly in the batch/PR report so the user can decide whether to accept it or commission hand-authored artwork, the same way `opencode` was handled.
