## Findings

1. **Blocking — The only Stop control is not available for a backend generator run on this base.** Design-spec §2.1 line 52, §2.3.2 lines 115–120, §2.4.1 lines 187–189 and decision 6 make the shared chat Stop the only path to `wizard:cancel` and the new prompt cancellation. In current code, `libs/frontend/chat/src/lib/components/molecules/chat-input/chat-input.component.ts:484–501` renders Stop only when `isActiveTabStreaming()` is true, and `:1715–1724` calls `chatStore.abortWithConfirmation()`, not either generator RPC. The generator work can continue after its chat stream finishes, or can be active before/without one. The design has no accessible Stop in that state. It needs a specific integration contract for availability, tab/run identity, event routing, and late completion suppression for both workflows. This is a chat change; 649's D1 avoided chat add-ons for *builder* pages, but that does not supply cancellation for 650.
2. **Serious — The completion-wide error list has no destination.** Design-spec §2.3.4 gives item failure messages and §2.3.5 gives aggregate count chips, but neither gives the existing separate completion `errors` list a place. `libs/frontend/setup-wizard/src/lib/components/completion.component.ts:208–222` renders `completionData.errors` independent of item rows; errors can describe overall/finalization failures that do not map to an agent item. Parity row 35 requires completion data and actions to reflect the final payload. Add a safe completion error section/state, including what happens if the run fails without an item ID; do not silently discard the payload. The design also says “four existing commands” in §2.3.6, while the existing Quick Start has five examples, including checkpoint resume (`completion.component.ts:333–376`). Preserve that example or explicitly identify its replacement.
3. **Serious — `chrome="bare"` and the builder sidebar are described as existing reuse on this branch.** Design-spec §3 line 276 calls `ptah-session-embed` with `chrome="bare"` an existing component, but `libs/frontend/chat/src/lib/components/templates/session-embed.component.ts:33–64` has no `chrome` input. The actual embed exists and hosts `ChatView`; bare chrome needs PR #736 or new work. No harness-builder sidebar file is present on this base; the 649 design's builder-local adapter/sidebar are still in PR #736, as `context.md` states. §§2.1, 3 and 10 should distinguish what exists in the 648 base from what must arrive after #736 and make merge/integration a design dependency. The 649 layout is a visual reference, not an importable component here.
4. **Moderate — The combined-flow handoff is specified in two incompatible ways.** Design-spec §2.3.1 line 95 says Next steps offers a separate start and never implies guidance; §2.3.2 line 123 says `done-flow` shows “Project guidance starts in its own tab next” **and** Skip guidance; §2.4.1 line 185 says Skip appears before guidance starts. AC9 and accepted D5 require automatic continuation for the combined flow with a meaningful Skip. Specify the exact order: when the agent result commits, when the guidance tab opens, whether its backend run has begun, and the last point at which Skip prevents it. Otherwise the prototype can show a Skip button after the work has started.
5. **Moderate — The designed model picker duplicates a live chat control without an ownership rule.** Design-spec §2.3.3 line 131 and decision 8 say sidebar and composer write “the same tab model state”; after a run the sidebar becomes read-only. `libs/frontend/chat/src/lib/components/molecules/chat-input/chat-input.component.ts:414–513` still exposes the shared composer controls. AC19 requires an effective selection before submit and persistence on resume. Define whether the composer remains editable during a locked run, whether its changes are deferred to a future run, and which value a resumed checkpoint uses. The UI must never show one model in the read-only sidebar while a different model is used for retry/resume.
6. **Moderate — One prototype state claims no files were written before the backend can know that.** Design-spec §2.3.2 line 113 says a rejected start shows “Nothing was started and no files were written,” but §2.3.7 line 164 permits generation with an unavailable preview, and start/finalization failures have different boundaries. Reserve the absolute no-write statement for authorization/lock rejection before execution; give post-start failures and `trace-failed` their own verified outcome wording. This matters to AC7/14 and the safe-write boundary in parity row 26.
7. **Minor — The Hub reference uses an invented card surface rather than the actual home component as proof of unchanged styling.** `prototype/assets/hub.js:14–18` explicitly calls itself an excerpt, while the real `libs/frontend/harness-builder/src/lib/components/setup-hub.component.ts:322–390` uses its existing card grid and Workspace Analysis card. §2.6's instruction to clone that recipe is acceptable, but the architect should treat `hub.html` as a content/wiring illustration, not a pixel-accurate Hub redesign or a new grid rule.

## User-reserved items

- No design decision among §7's 19 is an explicit request to remove a capability. Decisions 1–2, 4–14 and 16–19 are reversible presentation/interaction choices within approved scope. Decision 3 removes the old seven-step navigation; the proposed landing and two-step analysis indicator must still preserve its analysis navigation and the existing results access. Decision 15 drops decorative Quick Start emoji, which is cosmetic, but the missing fifth command in Finding 2 is user-visible instructional content and should be restored under the keep-and-fix constraint.
- §8's “None” under Proposed Removals is premature until the completion errors and fifth Quick Start command are restored. Any intentional omission of them is a user-reserved removal under `context.md`'s keep-and-fix rule.
- The Hub's visual design and the analysis result page markup are fixed inputs. §2.6 respects the Hub constraint. §2.2/decision 3 alter the wizard shell and the results page's *handlers* (`analysis-results.component.ts:337–355` currently enter the old selection/generation steps); they need not restyle the result page.

## Lane-introduced constraints

- Design decisions 1, 2, 7–12, 14–18 set new choices that the user did not specifically require: landing order and page form; Run-first sidebar; duplicate provider/model controls and locking; hiding catalog scores and leaving all unselected; “Checked when the run starts”; preview dialog treatment; ephemeral “Not now” for resume; renamed Hide action; closed Quick Start with emoji removed; prompt text in Settings; tint/ink details; and authored state copy. They are generally reasonable and reversible, subject to Findings 2 and 5.
- Decision 6 makes chat Stop the **only** Stop, which is a new constraint beyond AC18 and is not currently feasible (Finding 1). Decision 13 limits Skip to the combined flow, an interpretation of D5 and parity row 33 that needs the timing contract in Finding 4. Decisions 3 and 4 define wizard-shell and chat-tab ownership beyond the requirements, and decision 19 adds rejection copy while following D5's safe-text rule.
- The 336 px/720 px/scrolling sidebar and no new Hub styling come from approved 649 constraints. The exact freshness strings, seven-day freshness rule, safe text, workspace binding, independent versus combined continuation, and project-guidance Stop come from approved Gate 1/D5; they are not new designer constraints.
