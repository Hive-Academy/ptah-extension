## Summary

Split agent generation and project-guidance generation into two workspace-bound normal chat tabs, tagged `setup-agent-generation` and `setup-project-prompt`. Each generator checks the same latest completed analysis through `AnalysisFreshnessService` at submit time, uses only a verified matching run, and otherwise gathers current workspace context. The analysis pages and artifacts remain available. The analysis-result **Continue** path is the sole combined flow: finalized agent generation offers a visible five-second Skip/Start now handoff to a separate guidance tab. Independent starts never chain. Generation success comes from committed agent checkpoint outcomes or committed guidance trace/state, never the end of a chat stream.

This plan changes generation contracts and the internal wizard surfaces. It does not run the four analysis phases as chat sessions, change the analysis manifest schema (TASK 651), implement builder flagged-session navigation (680), or take 649 review follow-ups (682). Hub home retains its existing layout and styles. No user-visible capability is proposed for removal.

## Integration architecture

1. `GenerationWorkflowLauncherService` finds/creates a same-workspace workflow tab, tags it (`chat-types.ts:873-887`), and navigates the `setup-wizard` child route in `ptah.main`. Panel requests cross through the typed `SETUP_GENERATION_OPEN` host-to-main push and its `MESSAGE_HANDLERS` consumer. Analysis remains in its existing route; Electron/CLI keep their legacy landing/commands.
2. Page reads tab/workspace, run lookup and committed state without writing. A tab-bound submit snapshots its model; the host resolves the workspace effective provider route and supported model before accepted, then checks host/tab workspace equality before analysis I/O. Tabless callers keep their current awaited semantics.
3. Host evaluates `AnalysisFreshnessService.getStatus` at submit. Latest fresh matching directory → verified analysis source and run identity; any missing/stale/not-latest/read failure → workspace discovery reason; foreign path → reject. The `analysisData` gate uses the same decision. Static recommendations can be requested independently through explicit catalog mode.
4. Backend reserves the workflow-specific lock, creates a bound run ID, persists agent checkpoint or records in-memory guidance run, returns accepted start, and emits bound events. Shared chat renders only safe live text; workflow store renders progress/result from bound envelopes. A stream closing is not a success signal.
5. Agent supervisor validates/writes and finalizes checkpoint, then emits terminal result and propagation/consent; guidance supervisor waits for trace and state commit before terminal success. Reopening reads those durable records. Guidance run cancellation status is page-session state only; after reload committed prompt status is authoritative.
6. Stop from sidebar or chat C1 queues during `starting`, then cancels exact bound run. A lost answer invokes same-tab/workspace run lookup. Late completion from a cancelled/terminal run is ignored; an already-finalized run shows the verified final record. Logs may carry internal diagnostics, but user-facing text is mapped to safe fixed copy.
