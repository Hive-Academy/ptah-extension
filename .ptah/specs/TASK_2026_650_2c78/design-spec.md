## 1. Goals

1. Replace the forced scan, selection, generation, enhancement, completion sequence with a **landing** that offers three independent workflows (Generate agents, Generate project guidance, Workspace analysis).
2. Give each generation workflow one page with the same pattern as the approved 649 builder page: the shared chat (`chrome="bare"`) in the main region and a workflow **sidebar** beside it (docked from 720 px host width, a sheet below). The sidebar scrolls (649 D11).
3. Show, in one status component, **where the context came from**: a verified analysis, or the current workspace, with the exact freshness reason from the task-description table, and show it the same way on both pages.
4. Keep every parity capability (section 4): recommendations and catalog, provider and model, selection, community packs, preview and confirmation, per-item progress and retry, cancellation, resume (including old checkpoints), completion data, detected stack and summary, enablement, regeneration, skip, and Stop for project guidance.
5. Make every end state honest: no success shown for a run that did not finalize; cancelled, interrupted and failed runs report only what was verified as written or saved; "nothing was started and no files were written" is used only for a start rejected before anything ran (2.9.4); and there is always a working Stop while a run is active (2.9.1).
6. No new visual language and no new theme token: the pages use the 649 recipe and the existing `anubis` and `anubis-light` tokens only.

### 2.9 Contracts the design depends on (rounds 1 and 2)

#### 2.9.1 Stop generation (both generators; review item 1; AC8, AC14, AC18, parity row 22)

Verified in code on this branch:

- The shared composer renders its Stop only while the tab is busy streaming: `@if (isActiveTabStreaming())` at `libs/frontend/chat/src/lib/components/molecules/chat-input/chat-input.component.ts:487`, the predicate at `:638-649` (built on `isTabBusyGenerating`, `libs/frontend/chat/src/lib/services/chat-store/message-dispatch.service.ts:83-100`). Its `handleStop()` (`:1718-1725`) calls `chatStore.abortWithConfirmation()`, which resolves `tabManager.activeTab()` (`libs/frontend/chat/src/lib/services/chat-store/conversation.service.ts:468-478`) and sends `chat:abort` for that chat session. It never calls `wizard:cancel` (`libs/frontend/setup-wizard/src/lib/services/wizard-rpc.service.ts:143-150`, payload `{ saveProgress }`, no tab or run identity) nor the new project-guidance cancellation (AC18).
- A generator run can be active while no chat stream is: before the first stream exists (`starting`), between items, and while finalizing after the last chunk. In those moments the chat Stop is absent exactly when the user needs one. So the chat Stop alone cannot be the cancel control (the first draft's decision 6).

Design: the **page owns the Stop**, and the chat Stop is wired to the same action.

| Aspect | Contract |
| ------ | -------- |
| Control | **Stop generation**: `btn btn-outline btn-sm`, square icon in `state-err` ink, `aria-label="Stop generation"`, in the Run section below the state card; and, under 720 px, a 32 px square icon button beside the peek bar (2.7). Same label and icon on both pages. The shared composer's own button keeps its name "Stop generating" and its streaming-only visibility. No confirmation dialog on either (Stop is a pause: written files and the last saved guidance are kept; a resume exists) |
| Availability | From the moment Generate, Resume, Regenerate or the combined-flow start is submitted until the run reaches a terminal state: `starting` (on both pages: the guidance page has its own pending-start state, 2.4.1), `running`, `running-quiet`, `running-fail`, `retrying`, `regenerating` (guidance); also while `cancelling` (shown as "Stopping...", `aria-disabled`, `aria-busy`) and `stop-unconfirmed` (disabled "Checking..."). It does not depend on the chat streaming. Absent in setup, rejected, blocked, `stop-unknown` (a retry is offered only for a run verified as active) and every terminal state |
| Tab and run identity | The page holds `{ tabId, workflow, workspace, runId }`. `tabId` and `workflow` come from the tab; `workspace` is the authorized tab workspace (AC13); `runId` is the id returned by the start response and also stored with the checkpoint. A click sends `cancelRun({ tabId, workflow, runId })` to the host: agents map to `wizard:cancel` (today `{ saveProgress }` only; it must carry the run binding, the architect adds it), guidance maps to the new cancellation of AC18. The host cancels only the run bound to that tab and workspace; a mismatched tab, workspace or run answers `not-running` and cancels nothing (AC15: never another workspace's run) |
| Before the run id exists | While `starting` (agents and guidance alike) the click is queued: the card shows "Stopping generation" and, as soon as the start response yields a `runId`, the page sends the cancel for it. If the start is rejected or blocked instead, the queued stop is discarded and the rejected or blocked card shows with "Your stop request was dropped: nothing was running." If the start response never arrives, the no-answer rules below apply. The user never needs to wait for a run id to press Stop |
| Event routing | Progress, item, completion and cancellation events carry `runId` (and the tab or workspace binding). The page drops events for another run, tab or workspace, and every event for a run that is already terminal. Per-tab state means a stop in one workflow tab cannot change the other generator's tab |
| Outcomes | After a click the card is `cancelling` until the host answers: **`cancelled`** (agents: written items kept per the checkpoint, Resume offered; guidance: not marked complete, last committed state named only when verified, 2.9.4); **already finalized**: the page shows the final result (`done`, `partial`, `complete`) plus "It finished before the stop took effect. The result below is final." (states `stop-late`); **no confirmed stop**. The page never says whether the request "reached" the run, which it cannot know; it re-reads the run state (checkpoint, run record and active-run lookup) before it claims anything (the verified-fact rule of 2.9.4). Three cases. **Refused** (the host answered with an explicit refusal) and the re-read says the run is still active: state `stop-failed`, `role="alert"` "Could not stop the run" / "The run is still active. Try stopping again.", Stop enabled again; if the re-read shows an ended run the page shows that terminal state instead. **No answer** (timeout, lost response, closed connection): state `stop-unconfirmed`, `role="status"` "Stop could not be confirmed" / "We could not confirm whether the run stopped. Checking its state...", Stop disabled as "Checking...", then resolved by the re-read (still active: `stop-failed`; ended: the recorded terminal state, e.g. `cancelled`, `stop-late`, `interrupted`). **Re-read failed too**: state `stop-unknown`, `role="alert"` "Run state could not be confirmed" / "We could not confirm whether the run is still active or has ended." plus what to check (the agents folder, or project guidance in Settings) and the button "Check again"; no Stop is offered, because a retry is offered only for a run verified as active; the peek bar reads "Unconfirmed"; **`not-running`**: the run ended by itself meanwhile or was not this tab's, so the page re-reads the checkpoint or result and shows whatever terminal state is recorded |
| Late completion | From `cancelling` on, a completion event, a stream end or a trace write for that run cannot show success. The only terminal states are the outcomes above. Guidance never marks an unfinished trace or state successful (AC18, AC11). After the terminal state, later events for that run id are ignored |
| Chat Stop (change C1, section 3) | On tabs whose workflow is `setup-agent-generation` or `setup-project-prompt`, the composer Stop calls the same `cancelRun` for the tab it belongs to (the tab id comes from the embed, not from `tabManager.activeTab()`, `conversation.service.ts:474`), so a user who presses it gets what they expect and the two controls cannot disagree. Both produce the same `cancelling` state and the host treats the second request as idempotent. Fallback if the architect rejects C1: the composer Stop only ends the chat reply, and the Run card must then say "The chat Stop does not stop the run." |

Reconciliation with decision 6 (the old "one Stop"): the intent of 649 D3, that two Stop buttons on one page are duplicates, holds where both exist for the same stream. Here the two controls differ in availability (the composer's only while streaming, the page's for the whole run) and by C1 they run the same action. The cost is one more button in the sidebar. The alternative, the chat Stop only, leaves no Stop while the chat is idle (finding 1), which AC18 and D5 do not allow ("a chat-tab Stop that does not stop the backend run would mislead").

#### 2.9.2 Combined-flow handoff (agents, then project guidance; review item 4; AC9, parity rows 27, 28, 33)

The combined flow is a run started from the analysis hand-off ("Yes, Continue"); the page carries an origin flag. An independent start never continues by itself (AC9): its result ends at Next steps with the separate "Generate project guidance" button, and nothing is pending, so there is nothing to skip.

| Step | What happens | UI |
| ---- | ------------ | -- |
| 1. Commit | The host finalizes the agent run: checkpoint complete and completion payload recorded. The page shows `done` (or `partial` when items failed) **only** from that record (AC14). No guidance tab exists yet and no guidance backend run exists | the result states of 2.3.2 |
| 2. Countdown | Immediately after the commit the Run section adds the continuation card "Project guidance starts next" / "Setup continues with project guidance in its own tab. It starts in 5 s and uses Anthropic, Claude Opus 4.1, the model of the Project Prompt tab. The agent run used Anthropic, Claude Sonnet 4.5." (with "Failed items stay available to retry here." after a `partial`). Buttons: **Skip guidance** and **Start now**, both outline (the sidebar's one primary is not used: nothing here is the single required action). **Which model, and why** (review item 1): the card names the model the guidance run will actually submit, the **Project Prompt tab's own tab model** (2.9.3), not the agent run's. An existing guidance tab keeps whatever the user selected there; if no tab exists yet, the value is the default tab model for a new tab and the sentence reads "...and uses <model>, the default model for a new Project Prompt tab." The sentence "The agent run used <model>." appears only when the two models differ, so the card never implies they match. The value is read live: if the tab model changes during the countdown the card updates, and the start submits exactly the value the card shows when the countdown ends or Start now is pressed. The tab model is never overwritten from the agent run. The countdown is held in page state, not in the component, so it keeps running when the user looks at another tab | seconds are text only, not announced each tick; one polite `role="status"` line says once "Project guidance will start in 5 seconds. Skip guidance cancels it." The user can switch it off with Skip (WCAG 2.2.1) |
| 3. The card becomes "Project guidance skipped" / "No guidance run was started. You can generate guidance any time from Next steps." and Next steps shows the normal separate-start card. Closing the agents tab during the countdown counts as Skip | `fs=skipped` in the prototype |
| 4. The tab enters `starting` (2.4.1) from this moment, with Stop generation available while the run id is pending. The backend guidance run begins **at this point and not earlier**, and the tab is created at this point and not earlier. After an automatic start the guidance tab opens in the background (focus stays where it is, the tab dot shows the run); after Start now it is focused | the card becomes "Project guidance started" / "It is running in its own Project Prompt tab with <provider, model>. | 5. After the start point | There is no Skip anywhere. The only way to end it is **Stop generation** in the guidance tab (2.9.1). A guidance run started this way is an ordinary `setup-project-prompt` workflow: reopen, Stop and Regenerate behave as in 2.4 | |
| Start rejected or blocked at step 4 (no provider, workspace rejection, lock held by another workspace) | Nothing ran, so Skip is meaningful again: the guidance tab opens in `setup`, `rejected` or `blocked` with the card "Part of setup. Skip finishes setup without project guidance." and a ghost "Skip guidance" | 2.4.1 |
| Guidance fails after start | Retry plus the same "Skip guidance" card finishes setup without guidance (parity row 33). Skipping never blocks agent completion | 2.4.1 |
| Agents `run-failed` (no completion payload with items) | Nothing continues by itself. A start that cannot be cancelled would make Skip meaningless, so the page delays the start by a visible 5 seconds. Five seconds is a reversible designer choice (decision 20).

#### 2.9.3 Model state (review item 5; AC19, parity row 5)

One value per tab, the **tab model** (the per-tab provider and model that the composer's model selector already writes, `chat-input.component.ts:414-513`). The sidebar picker is a second view of it before a submit; a run takes a snapshot.

| Moment | Rule |
| ------ | ---- |
| Before a submit (Generate, Regenerate, Resume) | The sidebar Provider and Model selects and the composer's selector show the same value; changing either updates the other at once. The effective value is printed beside the submit control ("Model: Anthropic, Claude Sonnet 4.5"), in the Provider and model section ("This run will use ..."), and in the preview dialog |
| At submit | The effective provider and model are snapshotted into the run and its checkpoint (AC19). The snapshot, not the tab model, is what the run and its retries use |
| While a run is active | The sidebar shows the snapshot read-only: "Running with this model. Retries use it. It cannot change while the run is active." The composer selector stays usable but now only governs chat replies. When its value differs from the snapshot, the sidebar adds "Chat replies currently use Claude Opus 4.1. This does not change the run." so two different models are never shown without a label. Changing the composer model never changes the run |
| Item retry | Always the snapshot. The retry row names it: "3 attempts left. Uses Claude Sonnet 4.5." and the button's `aria-label` carries it (2.3.4) |
| Resume (resume offer, cancelled, interrupted, old checkpoint) | Defaults to the checkpoint's snapshot: "Resume uses Anthropic, Claude Sonnet 4.5, saved with the run." The picker is editable here: changing it is the explicit change AC19 allows, and the line then names the new model. The checkpoint is updated only when Resume is submitted |
| After a finished run (partial, done, run-failed) | Read-only snapshot with "Used for this run and saved with it. Retries use it. Choose Change selection to start a new run with another model." A new run snapshots the then-current tab model |
| Guidance after a result | The picker is editable again: "The next run will use <model>. The saved guidance was made with <model>." The Regenerate button reads `aria-label="Regenerate with <model>"` |
| Combined-flow start (agents, then guidance) | The guidance run takes the **Project Prompt tab's own tab model**: an existing tab's current selection, or the new-tab default when the tab is created at the start point. It never takes the agent run's snapshot and never writes to the tab model. The continuation card prints that effective value before the start ("...uses <model>, the model of the Project Prompt tab"), adds "The agent run used <model>." only when the two differ, and re-reads the value until the start; the started card repeats it ("...with <model>"). After the start the guidance tab shows its snapshot read-only like any run |

Invariant: no element names a model for a run other than the run's snapshot or, before a submit, the explicit "will use" (the combined-flow countdown is such a "will use": it names the guidance tab's value and labels the agent run's separately). The composer selector can differ only during or after a run, and the sidebar then says so.

#### 2.9.4 Outcome wording (review item 6; AC7, AC14, parity row 26)

The absolute sentence "Nothing was started and no files were written" (guidance: "...and nothing was saved") is used **only** for a start rejected before anything ran: a foreign analysis directory, a tab and host workspace mismatch (AC13), and the card's lock case in its own words ("Another workspace is generating ..."). It is always preceded by "The start was rejected before anything ran." Everything after the start (including a run that starts with a preview that was unavailable, 2.3.7) is an ordinary run and uses facts verified by the host:

| Situation | Wording | Verified source |
| --------- | ------- | --------------- |
| Agents: item failures after the start | "N written, M already current, K failed. Files written earlier are kept. Retry failed items below." | checkpoint and per-item outcomes |
| Agents: `run-failed` | "The run stopped with errors before any item finished. N written, K failed. Files already written, if any, are kept. See the errors below." | checkpoint counts |
| Agents: counts cannot be verified | "The run stopped with a problem and the files it wrote could not be confirmed. Check the agents folder in your workspace before you try again. See the errors below." (never "no files were written"; no counts, no item statuses and no "Written files are kept" are printed; the Generation section says "Counts could not be confirmed.") | no checkpoint |
| Agents: cancelled, interrupted | "N items were written and kept. Resume to finish the rest." | checkpoint |
| Guidance: `failed` | "The model did not return usable guidance. Try again." plus "The last saved guidance stays in place until a new one is saved." only when the host reports the committed state unchanged | committed state |
| Guidance: `trace-failed` | "The guidance was generated, but its record could not be written. This run was not marked complete." plus the verified sentence above | trace and state write |
| Guidance: `ended`, `cancelled` | "This run was not marked complete." / "This run was cancelled and not marked complete. The last saved guidance is unchanged." (or "No guidance has been saved yet.") | committed state |
| Guidance: committed state unknown | "We could not confirm whether earlier guidance is intact. Open it in Settings to check, then retry." | none |

Rule: a sentence that says something was kept, unchanged or not written is printed only when the host reports that fact. The same rule governs Stop: "did not reach the run" is never printed, because a failed request does not show where it failed; the page says only what a re-read of the run state verified (still active) or says it could not confirm. The sentence "Written files are kept." in the completion error block is omitted when no written file is verified (2.3.5). This is the safe-write boundary of parity row 26: the UI never claims more than the validated-write results show.

## 6. Accessibility

- **Landmarks and names**: each page one `h1`; the sidebar `aside` is named "Agent generation" or "Project guidance"; each section is `section` with `aria-labelledby` its `h3`; landing rows are `section`s with `aria-labelledby`; the dialog has `aria-labelledby` and `aria-describedby`.
- **Focus order**: header (sidebar toggle), chat (transcript, composer), sidebar sections top to bottom: Run first. Under 720 px: header, peek bar, the sheet when open, then chat. In the landing: Back or Close, the three rows (CTA, then the model disclosure in the analysis row), the saved-analysis rows (Use This, Hide).
- **Keyboard**: everything is reachable and operable with Tab, Enter and Space; Escape closes the preview dialog (= Cancel) and the narrow sheet; the dialog traps focus and returns it to the control that opened it (Generate button; if gone, the peek bar); no keyboard trap in the sheet. Checkbox rows toggle with Space; the switch toggles with Space and Enter. Arrow-key navigation is not needed (no composite widgets).
- **Disabled with a reason** uses `aria-disabled="true"` plus a visible reason tied with `aria-describedby` (Generate with nothing selected, blocked starts, the waiting retry), never the `disabled` attribute, so the reason stays reachable.
- **Live regions**: `role="status"` for the Run state cards while running or cancelling, the source card, "Retrying in 2 s", the Hide announcement, "Loading community packs...", install spinners (`sr-only` text) and the switch description (`aria-live="polite"`); `role="alert"` for rejections, failures, "Targets changed", "Preview unavailable", pack load errors and "Previous analyses did not load". One announcement per event: a warning card is part of its result, not a second alert. Progress bars are `role="progressbar"` with `aria-valuenow` and a name; the percentage is also text, so no live announcement of every tick is made.
- **Names**: icon-only buttons have `aria-label`s (Back to Setup Hub, Close setup wizard, Hide this analysis from the list, Stop generating and Send message from the shared chat). Retry buttons name the item and the attempts: "Retry Team Leader (3 attempts remaining)". Checkboxes are named "Select <agent>". The relevance chip has an `aria-label`. The switch is named by its visible label and described by its state line.
- **State exposure**: sidebar toggle and peek bar `aria-expanded` and `aria-controls`; community pack headers `aria-expanded`; the Use project guidance switch `aria-checked`; "Why recommended" and the Quick start and model disclosures are native `details`.
- **Contrast and targets**: section 2.8. Field edges, checkbox edges and the switch use `base-content/50`. Every control is at least 24 x 24 px (prototype audit, 0 failures); primary and outline buttons 32 px; peek bar and pack headers 44 px.
- **Motion**: the sheet slide, chevron rotation, spinners and skeleton shimmer collapse through the existing reduced-motion block in `styles.css`. Nothing is conveyed by motion alone.
- **Stop generation** (round 1): a real `button` named "Stop generation" (Run section) and an icon-only button with the same `aria-label` beside the peek bar; 32 px targets; reachable by Tab in order Run card, Stop, then the rest of the sidebar (and, under 720 px, directly after the peek button, without opening the sheet). While stopping it is `aria-disabled="true"` with `aria-busy="true"` and the visible word "Stopping..." (not removed, so focus is not lost). Focus stays on it through `cancelling`; when it is replaced by a terminal card, focus moves to the card heading (`tabindex="-1"`). The composer's "Stop generating" is a separate, shared control and is unchanged. `stop-failed` is one `role="alert"` ("Could not stop the run" / "The run is still active. Try stopping again."), after which the Stop button is enabled again. `stop-unconfirmed` is a polite `role="status"` (the page is checking, nothing has failed yet) and the disabled Stop keeps its place with the visible word "Checking..."; `stop-unknown` is a `role="alert"`; the Stop button is removed there, so focus moves to the "Check again" button. The guidance `starting` card is a polite `role="status"` and the Stop button is the first control after it.
- **Countdown** (2.9.2): the five seconds are a time limit the user can switch off with Skip guidance (WCAG 2.2.1); the seconds are `aria-hidden` text with an `sr-only` "5 seconds", and a single polite status states the countdown once instead of every tick; Skip and Start now are real buttons in the card, reachable immediately after the Run card; with `prefers-reduced-motion` nothing animates (the number is text).
- **Completion error block** (2.3.5): one `role="alert"` for the block (the warning card above it stays `role="status"`, one announcement per event); entries are plain text; the "Show N more" disclosure is a native `details`.
- **Language**: error text is plain and says what was verified ("Files written earlier are kept" only when written files are verified; "Nothing was started and no files were written" only for a start rejected before anything ran, 2.9.4).
