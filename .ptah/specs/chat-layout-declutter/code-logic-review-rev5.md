## Findings (all minor)

1. **[minor] The Pane actions menu has no arrow-key roving.** `canvas-focus-header.component.ts:40-70` renders `role="menu"` with `role="menuitem"` buttons but only an Escape handler (`:25`); the card menu implements roving (`canvas-rail-card.component.ts:699-723`), this menu does not. Failure scenario: a keyboard user opens a split pane's `⋯`, presses ArrowDown — nothing moves; Tab instead leaves the group for the next pane's controls, which contradicts the ARIA menu pattern both menus declare. Suggested fix: reuse the card's roving keydown logic (shared helper) for the three items.
2. **[minor] The comment "its listbox keeps its own arrow keys" is false — picker arrows are dead.** `canvas-rail-card.component.ts:700` claims the hand-off picker's listbox handles its own arrow keys, but `handoff-binding-picker.component.ts:91-103` renders `role="option"` buttons with no keydown handler anywhere in the component. Failure scenario: the picker is open, the user presses ArrowDown/ArrowUp to choose a binding — focus does not move at all; options are reachable only by Tab. (The safety property the check asks for still holds: the arrows move nothing, verified against the card skip, the rail's `IGNORED_TARGET` and the absence of `menuitem` roles in the picker.) Suggested fix: add roving to the picker's option buttons, or correct the comment and drop the skip rationale.
3. **[minor] The "only if focus was lost" guard is manufactured on every close.** Every close-menu action first calls `closeMenu()`, which unconditionally focuses the `⋮` trigger inside the card being removed (`canvas-rail-card.component.ts:568-571, 686-690`), so by the time `focusNeighbourCard` checks `focusLost` (`canvas-board-focus.ts:77-87`), focus is always in the removed card. Failure scenario: a mouse user with keyboard focus in the chat composer clicks a card's `⋮` → Close session; focus is pulled out of the composer and lands on the neighbour card, although focus was never lost before the interaction — the pointer flow deviates from the stated "only if focus was lost" contract (keyboard flows need exactly this behaviour). Suggested fix: track whether the menu was opened/used by pointer and skip the trigger focus in that case, or accept the always-repair behaviour and note it in the spec.
4. **[minor] Closing the last session leaves focus on `<body>`.** With a single card, `neighbour` is `null` (`canvas-rail-board.component.ts:1050`), and `focusNeighbourCard(board, null)` finds no card, so `focusRailSelectButton(undefined)` is a no-op with no fallback (`canvas-board-focus.ts:14-19, 85`). Failure scenario: the user closes the only session; focus falls to the document body, the next Tab restarts from the top of the page instead of the New session button or the sidebar expand control. Suggested fix: when no neighbour exists, fall back to the empty board's New session button or the expand control (the `survivingSessionControl` fallback already names one).
5. **[minor] A failed Stop gives no user-visible feedback.** `canvas-rail-card.component.ts:559-567` catches the rejection and logs it; no announcement is emitted, although the card owns an `announce()` channel it uses for rename/organize failures (`:507-514, 654, 677`). Failure scenario: the abort RPC fails; the menu closes, the session keeps running, and the only trace is a console log — the user cannot tell the stop was attempted and failed. (Inherited from the removed focus-area/dock stop paths, but the commit moved the code into a component that has the feedback mechanism.) Suggested fix: `this.announce('Could not stop this session.')` in the catch.

## Decisions

- **Line budget counting.** The 700/1241 ceilings match the repo's `max-lines` lint rule (skip blank and comment lines), so I scored by that rule: card 698, board 1111 — both pass. Raw `wc -l` counts (731/1186) would fail the card budget; I did not report that as a defect because the repo's own enforcement counts differently.
- **Close-session focus target in a split board.** When a Close session from a card menu also collapses a split, focus goes to the rail neighbour, not the split survivor. The stated contract names the neighbour for Close session and the survivor only for Close pane/Close split, so I scored this as conformant, not as a defect.
- **Inherited stop-confirmation race not scored.** `abortWithConfirmation` re-resolves the active tab when the confirmation resolves; if the dialog permits tab switching while open, the confirmed abort could hit a different session. The commit moved this code unchanged from the removed focus-area/dock paths, so it is out of this commit's scope.
- **`resolvedTab` lookup scope not scored.** `send-to-messaging` resolves its tab via `tabManager.tabs()` (active workspace) while the card uses `findTabByIdAcrossWorkspaces`. Visible rail cards belong to the active workspace and inert boards cannot be focused, so the mismatch is unreachable in practice; the component degrades to an aria-disabled item with a reason if it ever occurs.
