## New defects

1. **Blocking — A stale-owner takeover can move a newly acquired live lock.** `libs/backend/worker-runtime/src/lib/file-lock.ts:147-165`. Process A reads dead owner D and passes `abandoned`; before A renames, B removes D and acquires the same lock. A then renames B's live lock to `grave`. The nonce check sees a mismatch and attempts to rename it back, but the public lock path was vacant between those operations. Process C can acquire it and start writing while B still writes; the restore can then fail with `ENOTEMPTY`, stranding B's lock in `grave`. The nonce check protects deletion after the fact but does not make takeover atomic. **Fix:** serialize takeover contenders through an atomic claim protocol, or replace this directory/rename algorithm with a process-safe lock primitive; a post-rename identity check alone cannot preserve exclusion. Add a deterministic three-process interleaving test.

2. **Serious — Shutdown releases a driver lock for a start whose session ID never arrives.** `libs/backend/worker-runtime/src/lib/session-driver.ts:313-319,395-400`; `libs/backend/worker-host/src/lib/commands/remote-sessions.ts:518-539`. After `chat:start` succeeds but `session:id-resolved` times out, the driver keeps a tab-only orphan with no `sessionId`. `drain()` reports its tab as unresolved and cannot abort it. `releaseLocks()` enumerates the engine's lock by session ID, but `driver.running(sessionId)` only finds turns and admissions with a known ID (`session-driver.ts:163-167`), so it releases that lock even though the engine turn may still run. A new driver can take the session during shutdown. A terminal event containing only the tab also cannot retire the orphan because `session-driver.ts:194-206,537-548` searches only *admitting* tabs and known-ID orphans. **Fix:** carry the engine's lock session ID into the orphan admission, or associate held lock IDs with unresolved starts; keep those locks until confirmed termination. Retire tab-only orphans on a matching terminal event and release exactly once.

## Five logic questions

1. **Silent success:** `file-lock.ts:157-165` can return to the retry loop after moving a live replacement lock; another contender may then acquire a path that looks free while a writer is active. The ordinary operation result need not reveal this (`file-lock.ts:80-93`).
2. **Unexpected user action:** Starting a remote session and stopping the worker before its ID arrives can free the still-running turn's lock (`session-driver.ts:313-319`; `remote-sessions.ts:530-539`).
3. **Wrong input rather than error:** A replacement lock installed after the stale-owner read is valid input, yet `file-lock.ts:147-165` treats its directory as the abandoned lock until the post-rename comparison.
4. **Dependency failure/timeout:** A missing `session:id-resolved` times out at `session-driver.ts:495-509`; the orphan remains unabortable at `:395-400`, and shutdown's lock decision at `remote-sessions.ts:534-539` is then wrong.
5. **Unspecified requirement:** The implementation does not define how to prove exclusive ownership across an owner-file read and a directory rename (`file-lock.ts:147-165`), or how to map an ID-less orphan to the engine lock it holds (`session-driver.ts:313-319`; `remote-sessions.ts:534-539`).
