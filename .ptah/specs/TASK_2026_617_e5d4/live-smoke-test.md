## Defects and observations

1. **Not a Grok defect, but it blocks the documented smoke path:** `ptah agent-cli detect|models` hard-fails with `sdk_init_failed` when no Anthropic key/provider is configured (`apps/ptah-cli/src/cli/commands/agent-cli.ts`, `engine(globals, { mode: 'full' }, ...)` at ~lines 440 and 455). `mcp-serve` uses `requireSdk:false` and works. Suggested fix, if desired: have the read-only `detect`/`models` subcommands boot with `requireSdk: false`, like `mcp-serve`. Out of scope for task 617.
2. **Headless host never provides an MCP port to lanes** (step 4 citation). Any lane's Ptah MCP tools are unavailable under `mcp-serve`/`interact`. Handoff item "Ptah MCP tool call from inside the lane" must be verified in the VS Code or Electron host.
3. **Minor, unverified impact:** the mcp-serve stderr repeatedly shows `Got response to unknown request skills-reload` during Grok lanes. Grok appears to answer a `skills-reload` request that the host did not track. Cosmetic as far as observed (lanes completed), but worth a look in the Grok adapter/client request-id bookkeeping (`grok-cli.adapter.ts` / ACP client). I did not locate the line.
4. **Step 5 evidence gap:** the literal `queue-next-turn` mode string was not captured (see row 5). Behaviour matches.
5. Grok, when asked for `ptah_agent_report`, tried `ptah_agent_report` unqualified and got `'ptah_agent_report' is not a valid MCP tool name. Tool names must be qualified as server__tool`. That is Grok's own convention. If Ptah's per-session MCP is attached, prompts and role preambles should name the tool as `ptah__ptah_agent_report` (or whatever qualified form Grok exposes) for Grok lanes.

## Verdict

Steps 3, 5 (caveat), 6, 7, 8 pass live. Steps 1 and 2 passed only in part: grok detection is confirmed via `agent_list`, but `agent-cli detect` and `models` are blocked by the SDK-key requirement. Step 4 is blocked by the headless host (no MCP port).
