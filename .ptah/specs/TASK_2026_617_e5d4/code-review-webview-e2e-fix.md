## Defects

1. **Serious — nowrap converts variable badge content into horizontal matrix scrolling.**
   - **Location:** `libs/frontend/chat/src/lib/settings/ptah-ai/cli-orchestration-matrix.component.ts:352,959-960`
   - **Why it matters:** At 400 px, the current screenshot proves only the short fixture strings fit. `Cloud sign-in`/`No key needed` plus a tier summary, and any future longer badge copy, cannot wrap or shrink. The nearest narrow inline treatment explicitly uses `min-w-0` and truncation (`:328-345`); this sub-line has neither. The visual evidence also shows that the table is already wider than the 400 px viewport.
   - **Fix:** Keep wrapping at the smallest container width, or gate `nowrap` behind a measured minimum container width. If a one-line presentation is required, give the sub-line a bounded/truncating accessible representation (with the full value available to assistive tech) and add a 400 px regression that uses the longest supported labels.

2. **Serious — compact matrix controls do not provide 24 by 24 px targets, and focus clearance is unverified after density reduction.**
   - **Location:** `libs/frontend/chat/src/lib/settings/ptah-ai/cli-orchestration-matrix.component.ts:547,931-933,955-957`
   - **Why it matters:** The active checkbox is 18 px and the permission details trigger is 20 px. With only 2 px block padding, neither has a demonstrated 24 px interactive/spacing area and the 2 px offset focus outline has less room than before. This fails the requested WCAG 2.5.8 check and risks clipped focus at the matrix boundary.
   - **Fix:** Provide a 24 px hit area for every direct row control while retaining the smaller visual glyph if needed, then add a keyboard-focus compact visual/assertion at the first and last matrix rows and re-measure the 660 px fold.

3. **Minor — comments describe a test reference set that no longer exists.**
   - **Location:** `libs/frontend/webview-e2e-harness/src/lib/scenarios/settings/settings-visual.e2e.spec.ts:307-308,327`
   - **Why it matters:** Future maintainers will read 5+2 as the fold contract even though the test strictly enforces 6+2, making a later failure look like a fixture drift rather than a layout regression.
   - **Fix:** Update both comments to “6 installed CLIs / instances, 2 uninstalled” (and “6 installed rows, 2 uninstalled”).

## Style review questions

1. **What breaks when requirements change in six months?** Longer key/tier labels or another instance can force horizontal scrolling because the new no-wrap rule has no width boundary; a future reader may also restore the wrong 5+2 baseline from stale comments.
2. **What would a new team member misread here?** The comments say the compact layout prevents sideways scrolling and document a 5+2 reference set, while the 400 px evidence already needs a horizontally scrollable table and the asserted fixture is 6+2.
3. **What does this cost to maintain that a simpler shape would not?** Each future label change needs manual width reasoning. Keeping wrap below a measured threshold avoids hidden coupling between badge copy and the table's geometry.
4. **Where is this inconsistent with the same problem elsewhere?** The adjacent narrow provider/status line uses `min-w-0` plus truncation (`cli-orchestration-matrix.component.ts:328-345`) to constrain flexible content; the new badge sub-line relies on unbounded no-wrap instead.
5. **What would be better, and why?** Use the existing responsive pattern: preserve wrapping at very narrow widths and enable one-line compaction only where the container has sufficient measured width. It continues to meet the fold objective without turning ordinary content changes into horizontal overflow or reducing accessibility clearance.
