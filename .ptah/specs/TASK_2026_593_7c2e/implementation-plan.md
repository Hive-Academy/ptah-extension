## Architecture decision

Put the root `NotificationService` and pure attention contracts in `libs/frontend/core`. This core service owns keyed current requests, capped Recent notices, presentation visibility, deduplication, burst identity, and `upsert/resolve/dismissPresentation/clearAll` signals. It imports shared types and Angular only. `chat` owns a root `ChatAttentionSourceService` that projects `PermissionHandlerService`, `AgentMonitorStore`, terminal failure pulses, voice failures, and ActionBanner warnings/errors into core; C3 separately adds the back-office failure projection. `notification-center` becomes rendering plus focus/action routing and imports core only. Feature adapters publish local git notices. The shell instantiates the source once and mounts one snackbar host and bell.

Reject putting the service in `notification-center`: its current ledger imports `chat-streaming`, `chat-state`, and `chat-ui` (`notification-ledger.service.ts:9-21`), so other features importing it would perpetuate a feature-to-feature cycle. Reject renderer-origin host notifications: VS Code's view can be absent when a request arrives (`sdk-permission-handler.ts:253-270`). Reject reusing `IUserInteraction`: Electron's implementation opens a dialog (`electron-user-interaction.ts:144-168`).

## Integration architecture

1. Backend permission/question/lane event enters the common `IHostAttentionIngress` at the active host's transport before renderer delivery, even with no registered view. Host coordinator keys it by workspace/kind/request ID; checks settings and window/view visibility, then calls port once per lifecycle. It also publishes a sanitized attention change for renderer reconciliation. Host resolution is driven by authoritative response/withdrawal/cleanup paths, including an answer from another view, never UI dismissal. If a platform notification cannot be issued, in-app state remains authoritative.
2. Angular source adapter reads authoritative chat/lane signals and maps them to core `NotificationService` once per unique identity. New item may trigger one sound/live announcement; current focused owner suppresses its snackbar. Core signals drive bell and snackbar host. On answer, the shared in-flight guard rechecks pending state, invokes existing responder, and waits for source state to remove the item. Host and renderer both resolve by key/generation, including when answer happens elsewhere.
3. Bell/Open uses `NOTIFICATION_FOCUS_ROUTER`; native click/reveal carries only target IDs and lets renderer route when ready. Multiple workspaces never use the currently selected workspace as a substitute for origin. If the owner disappears, show a disabled action while preserving the count until authoritative withdrawal.
4. `Clear all` clears dismissible Recent history and transient failure/warning presentations only, never live-request snackbars or Needs you rows. It is enabled only while Recent or transient failure/warning presentation exists. A later duplicate event does not re-show an individually dismissed snackbar; a genuinely new lifecycle generation may. Recent notices remain in memory for session lifetime; settings alone persist across restart. No cross-device sync.

- **VS Code visibility:** sidebar and panel can coexist. Adapter checks all registered Ptah views, not only `ptah.main`; a hidden renderer cannot be the notice source. Stale host action only reveals and reports status.
- **Privacy:** host text is constructed from a whitelist. Tests assert the authoritative session title appears (truncated when long; generic fallback when absent) while canaries in question/body, description, tool input, raw error and paths stay out. Never log rejected payload contents.
- **OS variance:** Electron notification may be denied or suppressed; in-app state is authoritative and remains usable. One-time log avoids noisy loops.
