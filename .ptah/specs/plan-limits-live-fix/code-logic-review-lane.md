# Code logic review — plan limits live fix

**Verdict: REVISE.** Score: **5/10**. The live path and scoped specs reported in `antigravity-ollama-report.md` and `ui-report.md` establish that one account works; the defects below affect account changes and probable failures. This is a sounder result than a 3–4 because the happy paths are connected and verified, but it does not reach 7–8 while quota can be attributed to the wrong owner. Native `ptah_*` tools, including `ptah_get_diagnostics` and `ptah_agent_report`, were not available in this lane; inspection used native reads and per-file diffs. No source files were edited and no new check was run.

## Numbered defects

1. **Blocking — quota can be credited to the wrong Antigravity account.** `libs/backend/auth-providers/src/lib/quota/readers/antigravity-oauth-plan-usage.reader.ts:97-104,127-141,190-245` caches one access token for the whole process, keyed only by fetch function. `libs/backend/auth-providers/src/lib/quota/provider-owner.resolver.ts:376-388` independently derives the owner from an observed language-server account or `google_accounts.json`. When the active account changes while the cached token is valid, the reader skips the keyring and can return account A's windows as an `available` reading for account B. `libs/backend/auth-providers/src/lib/quota/plan-usage.service.ts:369-373` records those windows against B in the ledger. **Fix:** bind token and quota cache to a verified account identity; on owner change, invalidate the access token and require a fresh keyring read. If the token's account cannot be proved to match the requested owner, return an unavailable reading instead of recording the windows.

2. **Major — cold reads miss the caller deadline, and cancellation does not stop the keyring process.** `libs/backend/auth-providers/src/lib/quota/readers/antigravity-oauth-plan-usage.reader.ts:132-146` awaits `readKeyring()` before attaching the caller's abort signal or starting its ten-second timeout. `libs/backend/auth-providers/src/lib/quota/readers/antigravity-keyring.ts:68-75,165-174` gives PowerShell up to 15 seconds and accepts no signal. The lane's Antigravity deadline is 12 seconds (`libs/shared/src/lib/utils/plan-limits/evidence-precedence.ts:13-36`), so a slow cold read is reported as a timeout while its child continues. Repeated cancelled reads can spawn more PowerShell children; the module's token cache also permits parallel callers to refresh at once (`antigravity-oauth-plan-usage.reader.ts:127-187`). **Fix:** pass the caller signal through `readAntigravityKeyringToken` to `execFile`, start one shared, cancellable token acquisition/refresh flight before the keyring read, and align the caller deadline with the bounded cold path or return a distinct pending state.

3. **Major — a failed project lookup is misreported as no quota source.** `libs/backend/auth-providers/src/lib/quota/readers/antigravity-oauth-plan-usage.reader.ts:265-299` turns any `loadCodeAssist` failure, malformed body, or 401 into `undefined`; lines `190-214` then send an empty project body. The reader's own flow documents that this can yield 403, which lines `217-251` convert to `no-usage-source`. A temporary project service outage therefore looks like a successful determination that the account has no limits. **Fix:** distinguish a validated response with no project from a failed project read; propagate failure as `service-unavailable`. Treat a 403 as no source only when the required project was obtained and the provider explicitly says quota is unavailable.

4. **Major — a rejected keyring credential is hidden by the local fallback.** `libs/backend/auth-providers/src/lib/quota/readers/antigravity-oauth-plan-usage.reader.ts:163-175` correctly returns `unsupported-auth` for `invalid_grant`, but `libs/backend/auth-providers/src/lib/quota/readers/antigravity-plan-usage.reader.ts:77-87,157-166` only accepts `available` from OAuth, then substitutes `service-unavailable` when no language server is open. A user with a revoked keyring login sees “Open Antigravity to read local quota” (`libs/frontend/dashboard/src/lib/components/provider-account-card/provider-account-card.component.ts:655-657`) instead of an authentication problem. **Fix:** preserve the OAuth `unsupported-auth` result when the local probe cannot provide an available reading; define separate UI text for a rejected Antigravity login.

5. **Major — an unreadable Ollama response is reported as an absent source.** `libs/backend/auth-providers/src/lib/quota/readers/ollama-cloud-plan-usage.reader.ts:79-87,118-131` maps a 200 response with malformed JSON, missing `totals.request_count`, or a too-large body to `no-usage-source`. The endpoint is present and authenticated; this is a service or schema failure, so the dashboard's “No usage source” is a success-looking, wrong diagnosis. **Fix:** return `service-unavailable` on malformed/oversized 200 bodies, retaining `no-usage-source` for a known absence of the endpoint. Add a spec for malformed 200 separately from 404.

6. **Minor — Ollama request counts claim local CLI provenance.** `libs/backend/auth-providers/src/lib/quota/readers/ollama-cloud-plan-usage.reader.ts:133-143` marks data fetched from `https://ollama.com/api/usage` as `source: 'local-cli'`, because `libs/shared/src/lib/types/plan-limit.types.ts:132-150` permits only that source for `PlanLocalUsage`. Consumers that use provenance will treat remote account usage as local accounting. **Fix:** extend the local-usage source type to include a provider API value, then set Ollama's source accordingly.

## Five logic questions

1. **Silent failure:** a project lookup failure becomes `no-usage-source` (defect 3); an unreadable Ollama 200 becomes the same (defect 5).
2. **Unexpected user action:** switching Antigravity accounts while the access token remains cached can show the previous account's quota under the new account (defect 1).
3. **Wrong answer from input data:** malformed authenticated Ollama usage data is classified as absence of a source (defect 5); remote counts are marked `local-cli` (defect 6).
4. **Dependency failure or timeout:** `loadCodeAssist` failure is masked (defect 3); slow keyring reads survive caller cancellation and miss the 12-second lane deadline (defect 2).
5. **Missing requirement:** the owner and OAuth token must refer to the same account across account switches (defect 1); authentication failures must survive fallback to the local probe (defect 4).

## Scope and evidence

Reviewed the listed new keyring file and the changed reader, owner, shared type, and dashboard paths; per-file diffs and surrounding ledger, plan-usage, and lane-deadline code were inspected. The Windows keyring command is a fixed PowerShell script with a fixed service name (`antigravity-keyring.ts:108-119,148-174`): no user input is interpolated into a shell command, `windowsHide: true` is set, and token output is neither put in process arguments nor logged. The dashboard moves the card above analytics (`dashboard-grid.component.html:48-54`), uses standalone OnPush components (`provider-account-row.component.ts:43-47`, `provider-account-card.component.ts:198-202`), and leaves unknown window percentages as `null` for a hatched track (`provider-account-card.component.ts:694-695,731-738`; `provider-account-row.component.ts:321-348`). Those paths support the requested happy-path presentation, subject to the backend findings. The cited reports state scoped Jest, typecheck, and live Windows probes passed; this review did not independently rerun them. macOS/Linux keyring behavior and the rendered Electron layout remain unverified here.
