## Findings

### 1. Moderate — the abort-failure contract the new service tests is unenforceable; a real failed abort still disposes the workflow and the replacement proceeds silently

- **Evidence:** `harness-workflow-request.service.ts:29-37` catches a rejection from `abortAndDispose()` and aborts the replacement ("Could not stop the workflow already running, so the new one was not started"). But the real dependency never rejects on an abort failure: `harness-workflow.service.ts:432-452` — `abort()` wraps the RPC in try/catch and funnels every failure into `failTurn()` (log + `_error`), and `abortAndDispose()` (`:497-502`) disposes unconditionally after the swallowed failure. `dispose()` (`:464-490`) releases the claim, closes the surface and drops identity even though the backend agent may still be running. `harness-workflow-request.service.spec.ts:100-111` ("preserves abort failure and leaves the active workflow untouched") passes only because the mock can reject.
- **Failure scenario:** cross-mode replacement (Setup Hub discard-confirm → `confirmDiscardAndStart` → RPC success → `requestAndNavigate`) while `chat:abort` fails on the backend. `abortAndDispose` swallows the failure and disposes anyway; `requestAndNavigate` sees a resolved promise, resets state, registers the new request and navigates. The user sees a clean start; the old agent keeps running backend-side, streaming into a closed surface with nothing listening — exactly the orphan the old `replaceActiveWorkflow` doc comment (`harness-workflow-message.handler.ts`, deleted lines) promised to prevent. No error surfaces anywhere.
- **Suggested fix:** make `abortAndDispose` (or a new `abortAndDisposeStrict`) throw on a failed `chat:abort` *before* disposing, and let `requestAndNavigate` keep its current catch; or at minimum have `abortAndDispose` surface the abort failure so the replacement path can refuse. Add one test against the real `HarnessWorkflowService` semantics.
- **Note:** the swallow-and-dispose semantics predate this diff (the old `replaceActiveWorkflow` called the same method with the same assumption); what Batch 6/7 added is a service and spec that codify a contract the real collaborator does not have.

### 2. Moderate — after a reload only the head session's proposal file is restored; proposals from earlier sessions of the same conversation are lost

- **Evidence:** the feature is built for multi-session conversations — `harness-workflow.service.ts:183-189` (`sessionIds` computed), the handler hydrates *every* session oldest-first (`harness-workflow-message.handler.ts:113-123`), and the spec pins an appended second session (`harness-workflow.service.spec.ts:187-201`, handler spec "keeps state and hydrates only the appended head session"). But the persisted reload record stores only the head: `harness-workflow.service.ts:224-229` (`sessionId: this.sessionId()`), and `rehydrate()` (`:554-597`) seeds the fresh conversation with only `record.sessionId` via `onSurfaceCreated(surfaceId, sessionId)`. After a reload `sessionIds()` is therefore `[head]` and the store is per-session (`implementation-plan.md:46`, file per `sha256(sessionId)`; backend `harness-rpc.handlers.ts:921`).
- **Failure scenario:** configure-harness run; session A's agent proposes persona/agents (persisted in A's proposal file); a second session id accumulates on the conversation (any stream event carrying a new id appends it — `stream-router.service.ts:339-345`); session B proposes more; the user reloads. `rehydrate` binds only B; hydration applies only B's file; every field the user approved during A is gone from the builder state, silently. (Single-session workflows restore fully — verified.)
- **Suggested fix:** persist the full session list in the workflow record (versioned key, same convention as `HARNESS_WORKFLOW_STORAGE_KEY`) so `rehydrate` can rebind the whole conversation, or expose a conversation-merged proposal read.

### 3. Moderate — a proposal event for a session the stream router has not appended yet is silently dropped, not buffered

- **Evidence:** `harness-workflow-message.handler.ts:141-155` — `handleConfigProposed` returns when `!sessionIds.some(id => id === data.sessionId)`; only events for *known* sessions are buffered (`:153`). Sessions enter the conversation only via `routeStreamEventForSurface` (`stream-router.service.ts:339-345`) or `onSurfaceCreated` with an explicit id.
- **Failure scenario:** the `HARNESS_CONFIG_PROPOSED` broadcast for a new session id reaches the webview before any stream event carrying that id has been routed (possible with reordering across the stream and broadcast bridges, or a session id that first appears in a proposal rather than a stream event). The update is persisted in the proposal store but never applied live, with no log — the builder silently misses fields until a reload/surface change re-hydrates.
- **Suggested fix:** while a surface is bound, buffer (or trigger a one-shot `getProposal` for) events whose session id is unknown instead of dropping them, and log the drop.
- **Honest uncertainty:** in the normal path the `tool_use` event precedes the tool result/broadcast on the same bridge, so the append should win the race; I could not prove cross-bridge ordering from the source.

### 4. Minor — the buffered replay loop runs outside any try/catch on an un-awaited promise

- **Evidence:** `harness-workflow-message.handler.ts:134-138` — `for (const event of buffered) this.applyProposal(event);` is not wrapped, and `hydrate` is called as `void this.hydrate(...)` (`:109`). `hydrationPending` is already `false` at that point, so a throw rejects an unhandled promise and drops the remaining buffered events.
- **Failure scenario:** an `applyProposal` throw (pathological `configUpdates` shape or a state-service failure) during replay → unhandled rejection, the rest of the live updates lost with no log. Likelihood is low — `mergeHarnessConfigUpdates` degrades gracefully on malformed-but-truthy input — which is why this is Minor.
- **Suggested fix:** wrap each `applyProposal(event)` in try/catch with a `logger.error`, matching the per-session error handling in the fetch loop.

### 5. Minor — same-mode resume silently discards a fresh New Project intake (judgment requested by the focus)

- **Evidence:** `harness-workflow-request.service.ts:26-28` — same mode → navigate only; the new seed/intake is not requested. Setup Hub gates the intake behind `hasActiveNewProject()` (`setup-hub.component.ts:656-692`, `:1307-1314`) and the discard-confirm behind `hasConflictingWorkflow()` = active **and other mode** (`:1235-1238`), so from Setup Hub the same-mode branch is reachable only when a new-project workflow activates while the intake modal is already open (e.g. a legacy `HARNESS_OPEN_WORKFLOW` broadcast during the seconds the modal is open). On that path `setup-hub.component.ts:1449-1460` closes the modal on `landed`, over the discarded intake, with no message. The backend has already run side effects for the new intake (plugin enable/reconcile, seed composition, wizard-panel disposal — `harness-rpc.service.ts:286-299` doc), and the returned `seedPrompt` is thrown away.
- **Judgment:** yes, the user's typed answers are lost with zero feedback — but this is preserved pre-existing behavior, not a regression: the deleted relay branch (`harness-workflow-message.handler.ts`, removed `if (this.workflow.mode() === data.mode)` block) navigated only, and `implementation-plan.md:60` explicitly requires "preserving same-mode resume". Reported because the focus asks for the judgment, not as a batch defect.

### 6. Minor — "Start over" now wipes the builder state; a user-visible behavior change the batch never stated (flagged per the keep-and-fix rule)

- **Evidence:** `harness-workflow-message.handler.ts:92-100` — any surface change with an observed previous surface calls `state.reset()`. "Start over" → `abortAndDispose` → `dispose()` sets `_surfaceId` null (`harness-workflow.service.ts:477-481`), so the effect fires the reset. `HarnessBuilderStateService.reset()` (`:634-638`) wipes config, streaming/execution tree and `hasInitialized` (forcing a `harness:initialize` re-run on the next mount). Before Batch 7, only a **cross-mode** replacement reset (`replaceActiveWorkflow`); "Start over" left the accumulated config and execution tree rendered.
- **Impact:** after "Start over" the config summary reads "No configuration yet" and the old run's visible tree is gone. Defensible ("clear the config the discarded run produced" was the cross-mode rationale, and the transcript dies with `dispose()` anyway), but the user can no longer view the discarded run's config summary — a removed user-visible capability that neither `batches.md` 6-8 nor the batch-7 decision records ("when an already observed session changes or disappears") states for the dispose path.
- **Suggested action:** team-leader confirms intent; if intended, record it; if not, scope the reset to surface changes where a new surface is bound (`surfaceId !== null` transitions), not to unbind.

### 7. Minor — a hung `harness:get-proposal` delays every live proposal by up to the RPC timeout per queued session

- **Evidence:** the RPC default timeout is 30s (`claude-rpc.service.ts:135`); while `hydrationPending` is true all live events buffer (`harness-workflow-message.handler.ts:153`). The failure is bounded and self-healing — the timeout resolves the call as an error, `hydrate` logs it (`:124-132`) and the buffered events replay afterwards — but with several queued sessions the builder preview can lag minutes with no user-visible signal.
- **Suggested fix (optional):** a shorter per-call timeout for `getProposal`, or surface a "restoring saved proposal…" state while hydration is pending.

## The five logic questions

1. **Silent failure:** finding 1 — a failed backend abort is swallowed inside `abortAndDispose`, so the replacement completes "successfully" while the old agent may still run; finding 3 drops unknown-session events without a log; the legacy `cancelled` outcome is silent by design.
2. **Unexpected user action:** submitting a second New Project intake while one is active (finding 5) resumes the old run and discards the typed answers; "Start over" now also wipes the builder view (finding 6); clicking Cancel mid-navigation still lets the started workflow land (benign, verified).
3. **Wrong answer instead of an error:** a proposal broadcast whose session id is not yet appended (finding 3) is dropped, leaving the builder permanently behind the store until reload; malformed-but-truthy `configUpdates` degrade to a no-op inside the merge rather than corrupting state (verified against `merge-harness-config-updates.ts`).
4. **Dependency failure/timeout/wrong shape:** `getProposal` rejection → logged, hydration continues, buffered events replay (spec-pinned); timeout → bounded delay (finding 7); a proposal whose `sessionId` mismatches the request is skipped (`harness-workflow-message.handler.ts:120`); `navigateToSurface` is value-based with a defensive catch; `requestAndNavigate` rejections surface in the intake modal (Setup Hub) or via `workflow.setError` (legacy).
5. **Missing from requirements:** the multi-session reload restore (finding 2) — the hydration feature assumes conversations can hold several sessions but the persisted record survives only the head; also nothing logs a filtered-out foreign-session proposal (observability gap behind finding 3).

## Decisions

- **D1 (findings 5/6 graded as preserved/adjacent, not regressions):** the deleted relay's same-mode branch also navigated only, and `implementation-plan.md:60` requires preserving same-mode resume; the dispose-path reset is new surface for an existing `dispose()` flow. Both are reported for confirmation rather than silently accepted. Reversible: re-grade once the team-leader confirms intent.
- **D2 (finding 1 graded against the real collaborator, not the spec's mock):** `abort()`/`abortAndDispose()` source at `harness-workflow.service.ts:432-452,497-502` is the contract that runs in production. Reversible: change the grade if `abortAndDispose` is later hardened.
- **D3 (finding 2's precondition taken from the feature's own design):** `sessionIds` + hydrate-every-session + the appended-head spec case establish that multi-session conversations are in-scope, so the head-only persisted record is a real gap rather than an impossible case. Reversible if a product decision caps conversations at one session.
