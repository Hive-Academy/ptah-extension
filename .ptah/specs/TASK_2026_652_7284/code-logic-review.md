## Findings

1. **Serious. A successful save reports as failed when the lock file is gone at release** (`STORE:161-163,85-87`). Scenario: a save outlasts 5 s (slow disk) and another process recovers the lock. The holder's `unlink` throws ENOENT. The proposal is on disk but the RPC fails. **Fix:** make the release `unlink(...).catch(e => { if (!isErrno(e,'ENOENT')) log })`, and release only if the owner token matches.
2. **Serious. Two processes can hold the lock after stale recovery** (`STORE:166-171`). Interleaving: both see a stale lock, A unlinks and re-creates it, B unlinks A's new lock and re-creates its own. The result is a lost update. **Fix:** see check 3.
3. **Moderate. One corrupt or unremovable file halts pruning** (`STORE:213-221`). **Fix:** in the inner catch, log and `continue` for every error. Also prune records that fail validation once their mtime exceeds retention.
4. **Moderate. `save` does not validate `sessionId`** (`STORE:56-83`, `rpc-harness.schemas.ts` `HarnessProposalSchema` trims `sessionId`). With `' a '`, the proposal is written with the trimmed id `'a'`, but the filename hash uses the untrimmed id and the read compares `'a' !== ' a '`, so `get` returns null and warns. The save reports success and the proposal is unreadable, a silent loss. The empty string and ids over 256 characters are rejected only at `HarnessProposalSchema.parse`, after the lock is taken. **Fix:** parse `sessionId` with the same schema before locking, and use the trimmed id for both hashing and comparison.
5. **Moderate. Crash-left lock blocks writes for up to 5 s** (`STORE:19-20,176`). Wait is 1 s, stale is 5 s. **Fix:** make `LOCK_WAIT_MS > LOCK_STALE_MS` (for example 6 s), or reduce the stale window.
6. **Moderate. `get` and `save` prune on every call** (`STORE:67,102`). Each call lists the directory and reads and parses every record, so cost grows with retained sessions. `save` also prunes before acquiring the lock. **Fix:** throttle with a time-based gate (for example once per hour).
7. **Moderate. Merge lets an explicit `undefined` or `null` overwrite base fields** (`merge-harness-config-updates.ts:14,48,61`). Scenario: `persona: {label: undefined}` clears the saved label. After stringify the field is dropped, so data is lost. **Fix:** skip undefined entries, or validate the update with `HarnessConfigUpdatesSchema` before merging (the schema is strict and normalizes).
8. **Moderate. Apply-time deletion and `save` have no producer or consumer in Phase 1** (`harness-rpc.handlers.ts`, no `HARNESS_PROPOSAL_STORE.save` or delete call). Proposals persist for 30 days and are never cleaned on apply. Record this so Phase 2 wires both. If the requirements put it in Phase 1, it is a missing requirement.
9. **Minor. `start-new-project` returns `seedPrompt` and `intake` that are consumed only if Phase 2 reads the result** (`harness-rpc.handlers.ts:~882-889`). The webview has no other way to open the workflow because the broadcast is gone.
10. **Minor. Aliased arrays in merge output** (`merge-harness-config-updates.ts:22-23,43-44,52`). Callers mutating the merged result mutate the base or update. **Fix:** copy the arrays.

## Five logic questions

1. Silent failure: Finding 4 (an unreadable record after a "successful" save), Finding 1 (pruning silently stops), the `focusChat` and wizard-dispose failures logged and swallowed, and the release failure in Finding 1 in the opposite direction (a false failure).
2. Unexpected user action: Finding 4, and a double save during a slow disk (stale lock recovery).
3. Wrong answer from data: Finding 7 and Finding 4.
4. Dependency failure: a read EACCES or EPERM rethrows to the RPC (fine); a crash-left lock gives a 1 s timeout (Finding 5); a disk-full write unlinks the temp file (good).
5. Missing: apply-time deletion (Finding 8), a multi-process test, and a corrupt-record prune test.
