## Five logic questions (fix round)

1. **Silent failure:** none introduced. Archive failure (ARC:84-91), fingerprint failure (ARC:66-69) and freshness I/O failure (AFS:81-87) all warn; `hashFileOrNull`'s null is a documented mismatch, never a success (AFP:87-98).
2. **Unexpected user action:** resume after a transient fingerprint read failure — New finding 1: the resumed run discards completed phases and can never be fresh.
3. **Wrong answer instead of error:** a project whose slug genuinely contains `-v3-archive-` becomes invisible to latest/resumable/freshness while still listed (ASS:52-54 `includes` match) — already recorded as Minor in the Batch 19 verification note; not re-raised, not worse than Minor (no data loss; the run re-runs).
4. **Dependency failure:** a provider delete that removes files then fails keeps the verified archive (L1, ASS:398-431); a v3-specific copy failure (e.g. an unsupported entry, ASS:452-453) no longer blocks a fresh analysis (L2). A workspace-wide I/O failure still blocks everything equally, as before.
5. **Missing from requirements:** the resume interaction of the degraded fingerprint (New finding 1) and the unpinned outer-catch pause (New finding 2).

## New findings

1. **[Moderate] Degraded fingerprint on resume discards completed phases and permanently stales the run** — `ARC:61-75` + `ARC:123`. The L5 fix covers every `open`, including resume. On resume, `manifest.workspaceFingerprint = fingerprint` (ARC:123) now writes the random degraded digest into the resumed manifest. Concrete scenario: a paused v4 run has phases 1-2 completed and verified; at resume time a root metadata file (e.g. `package.json` under a transient Windows lock) fails to read; `open` warns, overwrites the fingerprint with the random digest, and every `isCompleted` comparison then mismatches on `workspaceSha256` (ARC:200-207), resetting all completed phases to `pending` (ARC:211-222). The run restarts every phase (minutes of SDK work the pre-fix code would have preserved: a fingerprint failure then aborted `open` with an error and left the paused run intact), and the finished run's random digest can never match the workspace, so it reports `workspace-changed` forever — the user must run one more full analysis. No wrong data results (outputs are recomputed against the current workspace, freshness never reports fresh), the degradation is warned, and the trigger is rare, so this is a named-follow-up item, not another fix round: on resume with a degraded fingerprint, keep the persisted digest (phase inputs were hashed against it; a genuinely changed workspace is still caught later by freshness at AFS:179-181) or state the restart in the warning.
2. **[Minor] The outer-catch best-effort pause has no spec** — `MPA:443-452`. No test makes a checkpoint write fail mid-run (grep for `Could not pause` / writeManifest rejections in MPASpec: no matches), so the L3 second half — pause attempted, failure logged, run left resumable — is unpinned. A single case driving a `markRunning` persist rejection would cover it.

No new race, stale-state, unhandled-error, data-loss, stub or placeholder defect found in the fix diff: the archive guard is set before the destructive call (ASS:399-400); the fingerprint module is a byte-identical move of the old logic (digests stay compatible across the fix boundary, so pre-fix v4 runs keep their freshness verdicts); `sha256Hex`/`hashFileOrNull` preserve the exact old hash behaviour at all four call sites (ARC:196-199, MPA:258-266, MPA:644-646, AFS:201); Batch 22 is comments and array order only; the barrel removals (Tasks 20.3/21.3) are grep-checked in the batch reports and all consumer typechecks passed.
