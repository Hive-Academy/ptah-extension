# TASK_2026_331 — worker-boundary audit

## Scope and interpretation

Read-only audit of all **31 TypeScript files** in the requested directories: file-indexing has 5 production files + 4 specs, hash has 1 production file + 1 spec, reconciler has 1 production file + 19 specs, and `libs/backend/harness-sync/src/lib/user-layer/` is not present. Test files were structurally scanned too; their Jest callbacks/helpers are represented as test-only rows because they are not shipping worker entry points.

`pure? = yes` means the body is CPU-only or filesystem-only and has no dependency on a main-process DI object, logger, event emitter, watcher, or main-owned cache. A `yes` filesystem row is still called out as async or sync FS. Private pure helpers are `yes` for computation but are not directly callable as worker entry points until exported/extracted. `pure? = no` means the current method uses injected collaborators or main-process state; it may still contain worker-worthy work internally.

Payload estimates use a synthetic 15,000-entry JSON measurement with roughly 60-character relative paths: absolute-path array **1.43 MiB**, relative-path array **0.84 MiB**, `IndexedFile[]` **3.66 MiB**, minimal `IgnoreTestResult[]` **1.82 MiB**, minimal `PatternMatchResult[]` **1.56 MiB**, and one `ManagedEntries` object **3.55 MiB**. Rich matched-pattern arrays, longer real paths, structured-clone bookkeeping, and object duplication increase those baselines. A boolean-only result is just **14.65 KiB** as a `Uint8Array`, or **1.83 KiB** as a bitset. Harness-sync normally scales with harness artifacts rather than all workspace files; its ordinary payloads are therefore usually KBs, not MBs.

Tooling note: `ptah.code.searchSymbols` and `ptah.code.getSymbol` were not exposed in this session. I used `ptah.ast.analyze` first for every shipping file and all test files, then fell back to line-numbered reads/`rg` for bodies and cross-file type/DI evidence. DI evidence: workspace-intelligence registers the matcher, ignore resolver, filesystem service, classifier, token counter, indexer, and live file index as singletons at `libs/backend/workspace-intelligence/src/di/register.ts:81-120`; harness-sync constructs one reconciler and registers it as a value at `libs/backend/harness-sync/src/lib/di/register.ts:123-182`.

## Recommended cut points

### 1. Move glob/ignore CPU as one batch, not one file per message

Existing exact callable with no DI bootstrap:

```ts
new PatternMatcherService().matchFiles(
  paths: string[],
  patterns: string[],
  options?: PatternMatchOptions,
): PatternMatchResult[]
```

Worker request/response:

```ts
interface MatchFilesRequest {
  kind: 'match-files';
  requestId: string;
  paths: string[];
  patterns: string[];
  options?: PatternMatchOptions;
}

interface MatchFilesResponse {
  kind: 'match-files-result';
  requestId: string;
  results: PatternMatchResult[];
  cacheStats: { patternCacheSize: number; resultCacheSize: number };
}
```

For 15k files the measured JSON baselines are 0.84 MiB for relative paths or 1.43 MiB for absolute paths in, and 1.56 MiB for minimal `PatternMatchResult[]` out; populated `matchedPatterns` increases the response. If the caller only needs kept paths, call the existing exact signature `matchFilesSimple(paths, patterns, options): string[]` and return `paths: string[]` (up to the same 0.84/1.43 MiB baseline). If ordering is already known on the main side, a boolean `Uint8Array` is only 14.65 KiB, or a bitset 1.83 KiB. Keep a long-lived matcher instance in the worker so compiled/result caches remain warm. Do not try to transfer `MatcherFunction` or the LRU maps.

For ignore semantics, the better worker entry is a batch extraction rather than current `IgnorePatternResolverService.testFiles`, because the class constructor requires two DI singletons and `isIgnored` is synchronously CPU-bound:

```ts
function matchIgnoreBatch(input: { filePaths: string[]; ignoreFiles: ParsedIgnoreFile[]; workspaceRoot?: string }): IgnoreTestResult[];
```

The exact return is the current `IgnoreTestResult[]` shape:

```ts
interface IgnoreTestResult {
  filePath: string;
  ignored: boolean;
  matchedPattern?: IgnorePattern;
  matchedFile?: string;
}
```

Send `ignoreFiles` once with the batch, not 15k times. The minimal 15k `IgnoreTestResult[]` JSON baseline is 1.82 MiB and grows when matched pattern objects are present. If diagnostics are not consumed, return `{ includedPaths: string[] }`, or a boolean `Uint8Array`/bitset when the main side retains path ordering.

### 2. Move the one-shot workspace scan; keep live index ownership and watchers in main

The computational/FS cut is the work currently behind:

```ts
WorkspaceIndexerService.indexWorkspace(
  options: WorkspaceIndexOptions = {},
  onProgress?: (progress: IndexingProgress) => void,
): Promise<FileIndex>
```

It is **not callable as-is without bootstrap** because its constructor needs seven injected collaborators. A worker entry should construct worker-local Node-FS, classifier, token counter, ignore resolver, matcher, and a collecting logger, then expose only serializable data:

```ts
interface BuildWorkspaceIndexRequest {
  kind: 'build-workspace-index';
  requestId: string;
  generation: number;
  options: WorkspaceIndexOptions & { workspaceFolder: string };
}

interface BuildWorkspaceIndexResponse {
  kind: 'build-workspace-index-result';
  requestId: string;
  generation: number;
  index: FileIndex;
  parsedIgnoreFiles: ParsedIgnoreFile[];
  warnings: Array<{
    kind: 'skipped-stat' | 'ignore-file-read' | 'content-read';
    path?: string;
    skipped?: number;
    discovered?: number;
  }>;
}
```

The exact `FileIndex` main needs is:

```ts
interface FileIndex {
  files: Array<{
    path: string;
    relativePath: string;
    type: FileType;
    size: number;
    language?: string;
    estimatedTokens: number;
  }>;
  ignoredPatterns: string[];
  totalFiles: number;
  totalSize: number;
}
```

Return 256–1,024-file chunks or one final result (3.66 MiB `IndexedFile[]` JSON baseline plus small index metadata). Avoid 15,000 one-file generator messages. Progress must be a message carrying the existing exact `IndexingProgress` shape `{ currentFile, filesIndexed, totalFiles, percentComplete }`; throttle it (for example every 100–250 files) because a callback cannot cross IPC.

`WorkspaceFileIndexService` itself should remain main-side. It must retain the watcher, `generation`, `startPromise`, root identity, and mutable maps. Main should accept a worker snapshot only when `response.generation === this.generation`, rebuild its maps using the pure `detectFileType`/entry helpers, publish `parsedIgnoreFiles` for watcher rechecks, then arm the watcher. This preserves the current cross-root contamination guard. Do not ship the full 15k live snapshot (roughly 4–7 MiB) to a worker for every `search(query, limit)` merely to return ~10–30 KB. If interactive search becomes a measured blocker, keep a long-lived worker-owned snapshot and send incremental watcher deltas `{generation, op: 'upsert'|'delete', entry/path}` plus tiny query messages.

### 3. Harness-sync: move hashing only

Existing exact worker-safe calls:

```ts
hashFile(filePath: string): Promise<string | null>
hashDir(dir: string, options?: ContentHashOptions): Promise<string | null>
hashContent(content: string): string
```

Recommended batch protocol:

```ts
interface HashDirectoriesRequest {
  kind: 'hash-directories';
  requestId: string;
  jobs: Array<{ id: string; path: string }>;
}

interface HashDirectoriesResponse {
  kind: 'hash-directories-result';
  requestId: string;
  results: Array<{
    id: string;
    path: string;
    hash: string | null;
  }>;
}
```

Only paths cross in and 64-character hashes/null cross out, normally a few KB. Cancellation should be a separate `{ kind: 'cancel', requestId }` message that aborts a worker-local `AbortController`; do not attempt to pass the main `AbortSignal` or `hashOf` callback across the boundary. Keep `listContentFiles` and `digestFileMap` internal to the worker so the potentially multi-MB path map and file buffers never cross IPC.

Do **not** move `HarnessReconcilerService.reconcile`, `verify`, `remove`, `runReconcile`, or `reconcileTarget` wholesale. Main must continue owning the process-local serialization queue, cross-process lock acquisition/release, manifests/gates/target instances, commit point, logger, `lastHealth`, and health emitter. The exact response main already needs from reconciliation is `HarnessHealth`:

```ts
interface HarnessHealth {
  workspaceRoot: string;
  generatedAt: string;
  mode: 'full' | 'preflight';
  reason: string;
  sources: 'ok' | 'sources-missing' | 'pending-download';
  targets: HarnessTargetHealth[];
  collisions: HarnessCollision[];
}
```

Let builders/targets call the hash worker and keep orchestration local. `hasDrift` is technically extractable pure sync-FS work, but at normal harness sizes its manifest payload and lock-context complexity outweigh the gain; profile it only after hashing has been moved.

## Headline verdict

The clean, low-risk worker boundaries are **`PatternMatcherService.matchFiles[Simple]` for large batches**, a **worker-local one-shot workspace-index build that returns `FileIndex`/chunks while main retains watchers and generation state**, and **`hashDir`/`hashFile` for harness hashing**. The live file-index service and the harness reconciler are main-process state machines, not worker jobs; moving them as-is would split singleton caches, watchers, event delivery, serialization queues, manifest ownership, and logging across processes.
