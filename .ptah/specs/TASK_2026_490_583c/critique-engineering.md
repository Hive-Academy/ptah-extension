## Verdict

Plan is not sound as an implementation plan yet. Product direction is feasible, but Revision 3 commits to a dual-connection broker before proving Ptah can enumerate or exclusively own every MCP connection. The biggest flaw is connection ownership: duplicated stdio servers create correctness and security failures, while the proposed evidence (`sdk-query-options-builder.ts:916`) only covers Ptah's own HTTP server plus explicit overrides, not every server the SDK can load.

## 1. Broker design

The claimed seam is overstated. `SdkQueryOptionsBuilder` passes an `mcpServers` map at `libs/backend/agent-sdk/src/lib/helpers/sdk-query-options-builder.ts:916-921`, but its normal builder returns only the local `ptah` HTTP endpoint at `libs/backend/agent-sdk/src/lib/helpers/sdk-query-options-builder.ts:1459-1489`. The same query separately enables filesystem setting sources at `libs/backend/agent-sdk/src/lib/helpers/sdk-query-options-builder.ts:938-946`. Therefore Ptah does not necessarily possess a canonical, complete server inventory. The SDK explicitly says `setMcpServers()` does not affect servers loaded from settings files (`node_modules/@anthropic-ai/claude-agent-sdk/sdk.d.ts:2295-2310`). A broker cannot be the only owner until this split is resolved.

Running a stdio server twice is not a mere performance tax:

- Stateful servers now have two memories, subscription sets, caches, working directories and transaction views. A tool result produced through the SDK connection may not match the resource read through the broker connection.
- Singleton servers may contend for a PID file, SQLite lock, Unix socket, named pipe or fixed localhost port. The second process may fail or, worse, attach to partially shared state.
- OAuth/device-code flows may register or refresh twice, race on a shared token file, invalidate a rotated refresh token, or prompt twice. `needs-auth` is visible through the SDK status type, but status exposes no host-useful `_meta` (`node_modules/@anthropic-ai/claude-agent-sdk/sdk.d.ts:1033-1077`).
- Initialization, polling, subscriptions and background indexing happen twice. That doubles rate-limit pressure and can double billable external API work even when tool calls themselves are not duplicated.
- Shutdown, cancellation and reconnect are no longer atomic. One connection can be healthy while the other is stale, so UI metadata and model-visible tools diverge.
- The agent path uses Ptah's existing `canUseTool` callback (`libs/backend/agent-sdk/src/lib/helpers/sdk-query-options-builder.ts:922-924`); the app path would bypass it unless the broker reimplements the policy. That creates two authorization systems.

| Option                                                              | Upstream stdio processes per server | Ptah sees tool `_meta`                                                           | Ptah sees resources               | Permission-flow impact                                                                                                      | Effort  | Principal risk                                                                            |
| ------------------------------------------------------------------- | ----------------------------------: | -------------------------------------------------------------------------------- | --------------------------------- | --------------------------------------------------------------------------------------------------------------------------- | ------- | ----------------------------------------------------------------------------------------- |
| SDK owns connection; status only                                    |                                   1 | No; status returns name, description and annotations only (`sdk.d.ts:1036-1075`) | No host API                       | Existing agent permission flow remains intact                                                                               | Low     | Cannot implement MCP Apps host                                                            |
| Revision 3: SDK connection plus broker connection                   |                                   2 | Yes, on broker copy                                                              | Yes, on broker copy               | Agent calls use `canUseTool`; app calls use a second policy path                                                            | Medium  | Split state/auth, locks, duplicated cost and metadata/result skew                         |
| Ptah owns connection; one in-process SDK server per upstream server |                                   1 | Yes                                                                              | Yes, directly through Ptah client | Agent calls still cross `canUseTool`, then proxy handler; app calls must enter the same policy service with `caller: 'app'` | High    | Anthropic-specific adapter; dynamic tool-list/auth/reconnect semantics must be reproduced |
| Ptah owns connection; SDKs connect to a loopback MCP proxy          |   1, plus no extra upstream process | Yes                                                                              | Yes                               | Vendor SDK permissions remain in front of proxy calls; broker separately authorizes app calls                               | Highest | Local endpoint hardening, namespace fidelity and broader protocol forwarding              |

The in-process option is real, not speculative: `createSdkMcpServer()` creates an in-process server (`node_modules/@anthropic-ai/claude-agent-sdk/sdk.d.ts:457-475`), `McpServerConfig` accepts a live `type: 'sdk'` instance (`sdk.d.ts:1013-1029`), and `SdkMcpToolDefinition` preserves `_meta` (`sdk.d.ts:3202-3214`). It only exposes tools, not resources; that is acceptable because the Ptah-owned client should retain `resources/list` and `resources/read` for the host. It must create one SDK server using the original upstream server name so `mcp__<server>__<tool>` identities and permission rules do not silently change.

**Recommendation:** reject the dual-connection design. Build a transport-neutral, single-owner broker, then use one in-process SDK server per upstream server for the first Anthropic vertical slice. Keep the SDK adapter outside broker core so a loopback proxy can serve Codex/Cursor/other providers later. Gate this recommendation on proving that filesystem-loaded MCP servers can be disabled or replaced without losing project instructions, plugins and skills. If the SDK cannot do that, stop and pursue the loopback proxy or an upstream SDK capability; do not fall back to two stdio processes.

Required broker semantics are currently absent from the plan: canonical server inventory and identity; ownership of OAuth/token lifecycle; tool-list change notifications; resource cache invalidation; cancellation/progress forwarding; reconnect/backoff; per-session routing; namespace collision handling; redaction; and teardown. `setMcpServers()` supports process and SDK servers, but it only manages dynamically added servers (`sdk.d.ts:2295-2310`), so it is not proof of exclusive ownership.

## 2. Security

Current Electron defaults are necessary but insufficient. The main window has `contextIsolation: true`, `nodeIntegration: false`, `sandbox: true` and `webSecurity: true` (`apps/ptah-electron/src/windows/main-window.ts:122-128`), and navigation/new-window guards exist (`apps/ptah-electron/src/windows/main-window.ts:70-82`). However, the shell loads a privileged preload exposing generic RPC, state, clipboard and diagnostics bridges (`apps/ptah-electron/src/preload.ts:23-33`, `:48-63`), while the app shell has no CSP meta in its document head (`apps/ptah-extension-webview/src/index.html:1-8`). Third-party HTML must never execute in that origin or receive that preload.

A concrete defect must be fixed before any iframe spike: the session permission handlers approve requests based only on the top-level `webContents` id (`apps/ptah-electron/src/windows/main-window.ts:135-143`). Electron permission checks provide requesting/embedding origin and frame details; a subframe can share the top-level `webContents`, so the current predicate is not an app-origin policy. Electron recommends explicit permission handlers, CSP, navigation limits, IPC sender validation and no Electron API exposure to untrusted content ([Electron security checklist](https://www.electronjs.org/docs/latest/tutorial/security)). Default policy for MCP Apps must be deny; camera, microphone, geolocation, clipboard, notifications, downloads, filesystem and screen capture require a separately reviewed allow path.

| Container                                                                         | Isolation obtained                                                                                      | What a malicious app can still do                                                                                             | Assessment                                                                                                                                                                                                                                                  |
| --------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `iframe srcdoc` without `allow-same-origin`                                       | Opaque origin and no parent DOM access                                                                  | Phish inside its rectangle, flood `postMessage`, consume renderer CPU/memory, use CSP-allowed network, attack Chromium        | Safer browser primitive, but conflicts with the MCP Apps sandbox-proxy requirement recorded at `.ptah/specs/TASK_2026_490_583c/research-mcp-apps.md:96-100`                                                                                                 |
| `iframe srcdoc` with `allow-scripts allow-same-origin`                            | Little useful origin isolation because `srcdoc` becomes parent-origin                                   | Potential parent DOM/preload access if sandbox is weakened or removed, plus shared-renderer denial of service                 | Reject. MDN states `srcdoc` with `allow-same-origin` is same-origin with parent ([MDN `srcdoc`](https://developer.mozilla.org/en-US/docs/Web/API/HTMLIFrameElement/srcdoc))                                                                                 |
| `iframe` from `blob:`                                                             | Sandbox flags still apply; no separate Electron `webContents`                                           | Origin behavior depends on creator/sandbox combination; shared renderer, session and permission handler remain                | Do not claim secure until tested. Blob is not a substitute for an intentionally distinct origin                                                                                                                                                             |
| `iframe` from a Ptah custom protocol with unique app origin                       | Separate scheme/host origin while keeping DOM positioning and `postMessage`                             | Shared-renderer CPU/memory crash, phishing, message floods, CSP-allowed exfiltration, Chromium escape                         | Best MVP candidate if scheme has no `bypassCSP`, service workers, broad fetch or file mapping. Electron documents custom-scheme privileges and path-containment requirements ([Electron protocol API](https://www.electronjs.org/docs/latest/api/protocol)) |
| `WebContentsView` with ephemeral per-app partition and no preload                 | Separate `webContents`, session/cookies/cache, permission and navigation policies; main-process control | Can exhaust its own process/session, phish, use allowed network, exploit Chromium; can still attack a weak main-process relay | Stronger containment. More work: it is not a DOM element, so resize/z-order/focus and MCP `postMessage` bridging need IPC ([Electron web embeds](https://www.electronjs.org/docs/latest/tutorial/web-embeds))                                               |
| Separate sandboxed `BrowserWindow` with ephemeral partition and no opener/preload | Separate window, `webContents` and session; clearest privilege boundary                                 | Window spoofing/phishing, resource abuse, allowed-network exfiltration, Chromium escape                                       | Strongest practical isolation but wrong embedded UX and high lifecycle complexity; reserve for high-risk/full-screen apps                                                                                                                                   |

Minimum controls before rendering any third-party app:

1. Add a restrictive CSP to the trusted shell and an independently generated CSP to every app response. Default `default-src 'none'`; derive only the declared MCP Apps domains; never enable `unsafe-eval`, wildcard origins, `bypassCSP`, service workers or arbitrary `file:` access. The MCP Apps host duties require a restrictive default and declared-domain enforcement (`.ptah/specs/TASK_2026_490_583c/research-mcp-apps.md:92-118`).
2. Use a different origin per server/app/version. For iframe MVP, serve cached resource bytes through a narrow custom protocol handler with normalized exact paths, immutable content hashes and no filesystem pass-through. Use `sandbox="allow-scripts allow-same-origin"` only because the document is genuinely cross-origin; do not add forms, popups, modals, downloads, top navigation, pointer lock or presentation by default.
3. Replace permission checks with `(requestingOrigin, embeddingOrigin, isMainFrame, permission)` policy. Deny every app-origin request unless app manifest, host policy and current user grant all agree. Never reuse the main-frame allow decision.
4. Validate every View message with Zod: exact method allowlist, `event.source`, expected origin, unguessable view token, app/server binding, request id, payload byte limit and rate limit. Reject cross-server tool calls. Log decisions and redact secrets.
5. Route app-initiated calls through one authorization service. Required inputs: app identity, server identity, tool, validated arguments, workspace, session, user gesture/foreground state and declared `visibility`. `visibility: ['app']` is eligibility, not consent. Read-only, local, low-risk tools may have remembered grants; destructive, external-write, credential and open-world tools require explicit confirmation. Scheduled/background calls need a separate non-interactive grant and budget.
6. Enforce resource budgets: HTML/message bytes, DOM/view count, network domains, concurrent calls, call timeout, resize frequency, CPU/memory watchdog and crash recovery. Tear down with cancellation and clear ephemeral storage.
7. Never expose `window.vscode`, `ptahClipboard`, `ptahDiag`, arbitrary Electron IPC, Ptah RPC, filesystem paths/handles, environment variables, auth tokens, workspace contents, shell/openExternal, or host DOM to app code. A dedicated bridge may relay only MCP Apps protocol messages after validation; it must not import the existing preload API.

The app studio is a second threat boundary, not a UI feature. Agent-authored server code and HTML require an isolated build/run directory, dependency allow/provenance policy, lockfile, package/file count limits, secret redaction, explicit install/run consent, static checks and a preview that has exactly the same sandbox as production. The plan currently sequences it without any of these controls.

## 3. Hexagonal fit

“Electron-only page” must mean an Electron-only composition and navigation entry, not `if (electron)` branches inside shared backend code. The renderer already selects distinct Electron and VS Code shells (`apps/ptah-extension-webview/src/app/app.html:53-58`), while shared view state currently has one common `ViewType` union (`libs/frontend/core/src/lib/services/app-state.service.ts:20-33`). Mount the page from the Electron shell and keep it unreachable in the VS Code shell; do not add a globally callable view that fails after navigation.

Proposed ownership:

| Location                              | Name/tags                                           | Responsibility                                                                                                                                              |
| ------------------------------------- | --------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `libs/shared/mcp-apps-contracts`      | `scope:shared`, `type:util`                         | Zod wire schemas and types for app descriptors, view messages, action calls, stored manifests and text fallback. No Electron/Angular imports                |
| `libs/backend/mcp-apps-broker`        | `scope:shared`, `type:feature`                      | Sole upstream MCP client ownership, inventory, metadata/resources, connection lifecycle, app-call routing and audit events. No renderer or Electron imports |

| `libs/backend/action-registry`        | `scope:shared`, `type:core`                         | Transport-neutral action definition/registration contract. Domain actions stay with their owning feature                                                    |
| `libs/frontend/mcp-apps-page`         | `scope:webview`, `type:feature`, `platform:angular` | Electron-gated page state, selection and orchestration; signals, standalone OnPush components                                                               |
| `libs/frontend/declarative-dashboard` | `scope:webview`, `type:ui`, `platform:angular`      | Fixed catalog renderer only; no broker, filesystem or Electron dependency                                                                                   |

Add `IMcpAppSandbox` at `libs/backend/platform-core/src/interfaces/mcp-app-sandbox.interface.ts` and `MCP_APP_SANDBOX` in `platform-core/src/di/tokens.ts`. Existing tokens use `Symbol.for(...)` and document platform adapters (`libs/backend/platform-core/src/di/tokens.ts:1-13`, `:71-89`). The port should expose capability and lifecycle only: `supported`, create/resize/send/dispose a view keyed by an opaque id. It must not expose DOM types or Electron classes.

- `platform-electron`: `electron-mcp-app-sandbox.ts` implements the real custom-protocol iframe support or `WebContentsView` lifecycle, permission/session policy and crash reporting.
- `platform-vscode`: `vscode-mcp-app-sandbox.ts` implements `supported: false` and returns the mandatory text fallback. It must not weaken the VS Code shell CSP.
- `platform-cli`: `cli-mcp-app-sandbox.ts` implements `supported: false` and emits only ordinary tool content. No iframe or browser dependency.

The Anthropic re-exposure adapter belongs beside `agent-sdk`, not in broker core, because `createSdkMcpServer` is vendor-specific. Other provider adapters may use the loopback proxy later.

Boundary traps:

- A `scope:webview` page cannot import `platform-electron` or the backend broker; webview projects may depend only on `scope:shared`/`scope:webview` (`eslint.config.mjs:243-246`). Use shared RPC/message contracts.
- A `scope:shared` broker cannot import `scope:electron`; shared projects may depend only on shared projects (`eslint.config.mjs:234-238`). Resolve the sandbox port at the composition root.
- `platform-electron` can consume shared/extension/electron scopes (`eslint.config.mjs:298-304`), but the inverse is forbidden.
- Register the Electron adapter and broker in the appropriate ordered DI phases and update expected-resolvable/expected-absent manifests. Do not register app RPC handlers under `apps/**`; handler classes belong in `rpc-handlers` and must retain the `*RpcHandlers` suffix.

The existing tag precedents are `platform-core` as `scope:shared,type:util` (`libs/backend/platform-core/project.json:1-6`), `platform-electron` as `scope:electron,type:feature` (`libs/backend/platform-electron/project.json:1-6`) and Angular feature libs as `scope:webview,type:feature,platform:angular` (`libs/frontend/thoth-shell/project.json:1-7`).

## 4. Shared actions

“One definition” is realistic only if it means one domain executor plus one canonical Zod schema. It cannot mean one undifferentiated permission path. RPC registration is compile-time and runtime duplicated: methods must enter `RpcMethodRegistry` (`libs/shared/src/lib/types/rpc.types.ts:640-654`) and its runtime key map (`libs/shared/src/lib/types/rpc.types.ts:3375-3394`), while a new namespace must also enter `ALLOWED_METHOD_PREFIXES` (`libs/backend/vscode-core/src/messaging/rpc-handler.ts:38-90`). MCP tools currently hand-author JSON Schema, for example `ptah_harness_propose_config` (`libs/backend/vscode-lm-tools/src/lib/code-execution/mcp-core/tool-description.builder.ts:1519-1552`). Zod 4 already exports `toJSONSchema` (`node_modules/zod/v4/classic/external.d.ts:9`), so new actions should generate MCP schema rather than add another handwritten copy.

Minimal type shape:

```ts
type ActionCaller = { kind: 'ui'; sessionId: string; userGesture: boolean } | { kind: 'agent'; sessionId: string; toolUseId: string } | { kind: 'app'; sessionId: string; appId: string; serverId: string } | { kind: 'schedule'; grantId: string; jobId: string };

interface ActionPolicy<I> {
  authorize(caller: ActionCaller, input: I): Promise<{ decision: 'allow' } | { decision: 'prompt'; reason: string } | { decision: 'deny'; reason: string }>;
}

interface SharedAction<I, O> {
  readonly id: string;
  readonly rpcMethod: RpcMethodName;
  readonly mcp: {
    readonly name: string;
    readonly description: string;
    readonly annotations?: ToolAnnotations;
    readonly meta?: Readonly<Record<string, unknown>>;
  };
  readonly input: z.ZodType<I>;
  readonly output: z.ZodType<O>;
  readonly policy: ActionPolicy<I>;
  execute(input: I, caller: ActionCaller, signal: AbortSignal): Promise<O>;
}
```

Adapters register the same executor with RPC and MCP and derive JSON Schema from `input`; they do not bypass their transport boundary. UI arguments remain untrusted RPC input. Agent calls must still traverse `SdkPermissionHandler`, which resolves a per-session permission level on every call (`libs/backend/agent-sdk/src/lib/sdk-permission-handler.ts:367-377`, `:497-511`) and can persist “Always Allow” tool rules (`:851-880`). App and schedule callers are neither trusted UI nor agents: they require app identity, declared visibility, installation grant and background-use grant. One action definition may centralize policy, but its policy must branch explicitly on caller kind, user gesture and execution context.

Do not expose every existing RPC method automatically as an MCP tool. Many RPCs reveal host state, accept paths or perform UI/navigation operations and were never designed as agent capabilities. Exposure must be explicit per action; default is no RPC and no MCP registration.

## 5. Declarative dashboard

“Agent emits JSON spec from a fixed catalog” omits the data contract and lifecycle. A safe first version needs:

- An envelope with `schemaVersion`, `catalogVersion`, `specId`, `revision`, `generatedAt`, component tree and data references. Persist the original version; migrations must be explicit and forward-only. Unknown versions/components fail closed with a text fallback.
- Strict Zod validation at agent/MCP/RPC/file boundaries. Validate component count, tree depth, unique ids, string lengths, URL schemes, row/column counts, numeric ranges and total UTF-8 bytes. Existing reusable byte-budget utilities are in `libs/backend/platform-core/src/utils/json-budget.ts:4-46` and `:187-217`.
- Atomic snapshots for v1. Do not render a half-parsed streaming JSON object. If incremental updates are later required, use validated operations carrying `baseRevision` and monotonic `sequence`; buffer until a complete transaction validates, then swap the signal once. Reject gaps, replay and out-of-order patches.
- Separate layout from data. Large datasets should be paged or referenced by opaque result id, never embedded without a cap in the spec or sent wholesale through `postMessage`.
- Sanitized text through the existing markdown chokepoint when markdown is allowed. The catalog must not introduce another markdown parser or bind model strings to `innerHTML`.

Pinned refresh is under-specified. Current cron rows store a prompt, schedule, timezone and workspace root (`libs/backend/cron-scheduler/src/lib/types.ts:37-52`, `:67-78`). The runner either dispatches `handler:NAME` directly or sends an ordinary prompt to the SDK/model (`libs/backend/cron-scheduler/src/lib/job-runner.ts:13-18`). Therefore the plan must choose:

1. **Deterministic refresh (default):** persist an action/tool id, schema version, validated input, credential references, output budget and installation grant; a named scheduler handler invokes it without a model, validates output and updates the pinned snapshot.
2. **Agent refresh (opt-in):** persist a prompt/model/provider/max-turn/token/USD budget and permission policy; show estimated and actual cost; cap retries/concurrency; never silently switch providers. This is automation with recurring cost and nondeterministic side effects, not “refresh.”

The database needs new columns/tables because the current job schema cannot represent an action invocation or budget. The scheduler already has a global concurrency cap (`libs/backend/cron-scheduler/src/lib/types.ts:110-118`) and records skipped/failed outcomes (`libs/backend/cron-scheduler/src/lib/job-runner.ts:123-158`); reuse those mechanics, but add per-app backoff, staleness and disable-after-repeated-auth-failure semantics.

“Delivered through messaging-gateway” is also not available as described. Its adapter contract sends/edits text only (`libs/backend/messaging-gateway/src/lib/adapters/adapter.interface.ts:75-120`), and outbound delivery paginates a text body (`libs/backend/messaging-gateway/src/lib/outbound-delivery.service.ts:53-68`). Define one of: text summary with deep link, server-side PNG/PDF render plus new attachment capability, or provider-native blocks. Do not claim dashboard delivery until at least one representation, size limit, accessibility fallback and failure policy exists.

Scheduled costs include model tokens, upstream tool/API billing, renderer/export work, gateway messages and retries. Budgets must be per run/day/app/workspace, observable before pinning, and enforced below both the cron global concurrency cap and provider rate limits.

## 6. Sequencing

Revision 3's sequence (`.ptah/specs/TASK_2026_490_583c/research-report.md:249-258`) is mis-sequenced. It blocks risk discovery on two unrelated major upgrades, places shared actions after a broker that needs authorization, and schedules persistence/refresh before defining storage, identity, budgets or delivery format.

1. **Contracts and threat model.** Define app/server/version identity, trust zones, caller kinds, storage schema, uninstall semantics, text fallback and permission matrix. **Go/no-go:** reviewed data-flow diagram; no path from app origin to existing preload/RPC/filesystem; all external boundaries have schemas and byte limits.
2. **Connection-ownership spike on current dependencies.** Build a fake stateful stdio server and prove a single upstream PID while model and host both list/call/read it. Test auth-needed, cancellation, reconnect, `tools/list_changed`, resource change and conflicting settings-file server. **Go/no-go:** one process, stable `mcp__server__tool` names, metadata/result consistency, existing permission prompts preserved. Failure means redesign or upstream SDK work, not dual process.
3. **Containment spike independent of Angular migration.** Compare custom-protocol iframe and ephemeral-partition `WebContentsView` using malicious fixtures. Fix shell CSP and origin-aware permission handlers first. **Go/no-go:** app cannot see preload globals/host DOM/local files/cookies; undeclared network/navigation/popups/permissions fail; message flood and renderer crash have bounded recovery; security review signs off.
4. **Electron vertical slice with one first-party read-only app.** Add broker/store/contracts/port/adapters/page, one `ui://` resource and mandatory text fallback. No third-party apps, pinning or studio. **Go/no-go:** cold start unchanged when page unopened; install/open/reload/uninstall works; CLI and VS Code still execute the tool as text; Playwright-Electron and contract tests pass.
5. **Third-party conformance slice.** Run official `ext-apps` examples, resource CSP variants and app-initiated read-only calls. **Go/no-go:** documented conformance matrix, per-app grants, audit log, teardown and offline behavior pass.
6. **Shared-action foundation.** Introduce canonical Zod action definitions and generated MCP schemas; convert one low-risk action only. **Go/no-go:** RPC, agent, app and schedule caller tests prove distinct policy outcomes and no existing RPC is auto-exposed.
7. **Declarative dashboard without pinning.** Ship versioned fixed catalog, atomic specs, quotas, accessibility and large-data references. **Go/no-go:** invalid/oversized/old/partial specs fail to text; keyboard/screen-reader and render-budget tests pass.
8. **Pinned deterministic refresh, then delivery.** Add action-invocation jobs, grants, budgets, staleness/backoff and text/deep-link gateway output. Agent refresh and image attachments are separate opt-ins. **Go/no-go:** no-model refresh is repeatable; cost/rate caps and revocation work; delivery failure cannot corrupt the last good snapshot.
9. **App studio and gallery.** Only after sandbox, signing/provenance, package format, isolated build, preview parity, version/update/uninstall and moderation exist. **Go/no-go:** generated malicious fixtures cannot escape; generated app is reproducible from manifest/lockfile; uninstall removes schedules/grants/cache.
10. **Coding-chat chart mount.** Reuse the proven declarative renderer, not arbitrary third-party HTML. **Go/no-go:** no regression in chat streaming, virtualization, focus, markdown security or VS Code CSP.

Do not make Angular 22 plus MCP SDK 2 a prerequisite. Current workspace pins Angular 21.2.6, Claude Agent SDK 0.3.150 and MCP SDK `^1.29.0` (`package.json:91`, `:99`, `:108`). The existing research identifies an MCP Apps version compatible with MCP SDK 1.x; use that for the risk spikes, then migrate MCP SDK when a required conformance feature demands it. Angular major migration has no causal dependency on broker ownership or Electron containment. If later upgrades are required, split them into independent tasks with build, typecheck, unit, Electron render and package tests; never hide incompatibility behind `overrides` alone.

## 7. Missing pieces

- **Install/package format:** immutable app id, server id, publisher/provenance, manifest version, protocol/catalog versions, entry resource hash, tool bindings, permissions, dependency lock and signature/trust status.
- **Storage:** normalized SQLite tables in `~/.ptah/ptah.db`, not loose executable files. This repository already centralizes that database and numbered migrations (`libs/backend/persistence-sqlite/src/index.ts:1-4`, `libs/backend/persistence-sqlite/src/lib/migration-runner.ts:2-12`). Store manifests/grants/schedules/results separately from content-addressed cached HTML/assets; never store secrets in app records.
- **Update/rollback/uninstall:** atomic version activation, last-known-good rollback, incompatible-schema state, cache GC and uninstall that revokes grants/tokens, cancels calls, removes schedules, clears per-app storage/partition and keeps auditable tombstones.
- **Isolation:** unique origin and storage partition per server/app identity; quotas and no app-to-app messaging. Define whether two versions share storage and how migrations occur.
- **Multi-workspace behavior:** app installations, selections, grants, pinned views and refresh results need explicit global-versus-workspace scope. Current view state is workspace-partitioned (`libs/frontend/core/src/lib/services/app-state.service.ts:244-262`); app state must not leak between workspaces.
- **Lifecycle:** reconnect/auth expiration, server/tool/resource change notifications, resource hash change while open, app crash, host restart, cancellation, suspend/resume and teardown acknowledgement.
- **Offline behavior:** last-known-good snapshot with timestamp and stale banner; no silent agent/tool rerun; explicit retry; queued delivery policy; deterministic behavior when auth or server is unavailable.
- **Observability:** structured logs/metrics keyed by app/server/version/view/call/job, with arguments/results redacted; permission decisions, CSP violations, crashes, resource sizes, tool latency, token/USD cost and gateway outcome. Users need an activity/history surface and “why blocked” errors.
- **Testing:** unit-test Zod schemas, budgets, permission matrix, CSP builder, action adapters, store migrations and refresh state machine. Integration-test a fake MCP server for one-process ownership, auth, resources, cancellation and notifications. Use Playwright-Electron for malicious iframe/View fixtures, permission denial, navigation/popups, preload invisibility, focus, crash recovery, install/update/uninstall and offline restart. The repository already has a Playwright Electron target (`apps/ptah-electron-e2e/project.json:1-21`) and axe dependencies (`package.json:204`, `:249`).
- **Performance budgets:** define and measure unopened-page startup cost, broker connection count/time, max live views, resource/message/data bytes, memory/CPU per view, resize/message rate, dashboard render time and scheduled concurrency. Lazy load UI and do not connect every installed server at Electron startup without evidence.
- **Accessibility:** iframe/View title and landmark, keyboard entry/exit, focus restoration, zoom/high contrast/reduced motion, chart table/text alternative, error announcements and no color-only encoding. Cross-frame focus must have Electron E2E coverage.
- **VS Code/CLI contract:** hide Electron-only navigation in VS Code, do not register a broken view, do not negotiate UI support in headless hosts, and always surface meaningful text content. The renderer already has separate Electron/VS Code shells (`apps/ptah-extension-webview/src/app/app.html:53-58`); use that seam. Add explicit contract tests proving the same MCP tool remains usable without UI.
- **Authoring safety:** isolated build/run, dependency allow/provenance checks, package/file/output limits, no inherited environment secrets, no host workspace write by default, deterministic preview, explicit publish/install consent and moderation/abuse handling for gallery content.
- **Recovery/support:** export diagnostics without app payload secrets, safe mode disabling all apps, per-app disable/quarantine, CSP violation viewer and a way to recover when an app crashes the page repeatedly.

## 8. Top 5 changes

1. **Replace the second connection with a single-owner broker and make exclusive ownership Gate 0.** Reason: two stdio processes can disagree on state/auth and defeat one permission/audit story. Cost of not doing it: nondeterministic tools, duplicate billing/rate limits, lock/port failures and incidents that cannot be reconstructed from one log.
2. **Finish the Electron containment and permission model before loading any third-party HTML.** Reason: current preload is powerful and current permission handler is not origin-aware. Cost of not doing it: app HTML can become a path to arbitrary RPC/clipboard/diagnostic access or silently granted browser permissions; one sandbox mistake becomes local-machine compromise.
3. **Define identities, versioned storage, caller-aware shared actions and uninstall/revocation before pinning or studio.** Reason: authorization and durable automation depend on stable app/server/action/version identity. Cost of not doing it: orphan schedules, stale grants, un-migratable specs, app-to-app data leaks and irreversible compatibility debt.
4. **Remove Angular 22/MCP SDK 2 from the critical path; use current versions for risk spikes and migrate independently when evidence requires it.** Reason: neither major upgrade proves broker ownership or sandbox security. Cost of not doing it: weeks of migration churn before the project learns whether the core architecture is viable, with failures impossible to attribute cleanly.
5. **Make deterministic action refresh and a concrete gateway representation prerequisites for “pinned apps.”** Reason: current cron defaults to a model prompt and gateway is text-only. Cost of not doing it: recurring unbounded model/API spend, nondeterministic side effects, dashboards that cannot actually be delivered and marketing claims ahead of executable contracts.
