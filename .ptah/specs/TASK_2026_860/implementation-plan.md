## Architecture decision

- Chosen approach: make overflow and rail grouping pure calculations, keep UI-only state in the current Angular components or a small inspector-actions child, and add a targeted variant to the existing frontend abort service. Do not alter RPC methods, backend handlers, stored tile order, or host ports.
- Rationale: these are presentation and frontend target-selection changes. The existing services already own rename, organization, confirmation, and abort. Pure calculations permit the parity tests to inspect both plans and rendered order.
- Rejected alternatives: kind-grouped dock rendering (breaks cross-kind running-first order); a second inspector rename/organize service (duplicates business logic); selecting the inspector tab before Stop (races with later active-tab changes); storing grouped rail order (changes user order); a per-card observer or timer (unbounded cost).
- Effect on existing code: replace local spin keyframes and old overflow ranking; keep existing menu, session-card actions, transcript/composer sizing, session identity, and RPC contract. The inspector action child supplies only UI state and delegates operations.

## Integration architecture

- Data flow: roster → pure overflow plan → rendered dock/menu; stored ordered tiles + current `CompactRailState` map → pure group plan → rail/keyboard/jumps; inspector `tabId` + current running state → action child → existing session services → existing RPC methods.
- State/persistence: dock width/focus/menu and rail Finished/focus preference are component-lifetime signals; stored tile order remains in `CanvasStore`. No new backend or persisted shape.
- External boundaries: existing `ClaudeRpcService` validates RPC contracts; the action child reads a tab/session pair before async work. No new URL, filesystem, secret, or protocol boundary.
- Failure/rollback: revert the component/helper/pulse files and targeted abort changes together for this task; no data migration. A failed RPC leaves rename/organize feedback visible; Stop fallback is captured-target only. If rendering width is unknown, conservative dock/menu and inspector action-menu layouts retain reachability.
- Observability: use the existing `LoggingService` for touched async failure paths and live-region announcements already used by rail/card; do not add console logging.

## Architecture-level quality requirements

- Functional: at most five rendered dock chips on every path; all omitted agents exactly once in menu; running-first rendered order with the selected non-running exception; rail group and per-status counts match displayed cards; Stop never affects a later active tab.
- Performance: no observer or timer per agent/session; one dock and one inspector-header width observer with destroy cleanup. Infinite pulse animations affect only `transform` and `opacity`.
- Security/accessibility: no raw error or secret rendering, no `any` or unchecked cast, stable labeled controls, 2px focus-visible outline and offset, light-theme `--ptah-gold-strong` override, decorative dots/rings `aria-hidden`, static 8px dot under reduced motion.
- Maintainability: imports across projects use public `@ptah-extension/*` aliases; helpers remain same-project relative imports; no new lib, backend protocol, dependency cycle, or large multipurpose component. Split new inspector UI into child rather than extending the inspector body or board logic.
- Testability: test both pure plans and rendered output; use one regression for the Stop tab-switch bug and component tests for keyboard and focus behavior.
