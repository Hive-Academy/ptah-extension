# Provider card `nested-interactive` diagnosis

## Question and options

Decision served: how should the provider connection card keep whole-card navigation and its inline repair action without nesting interactive controls? Options are (A) make this provider card's navigation a separate native button inside a noninteractive card frame, (B) change the shared `NativeCardComponent` contract for all callers, or (C) leave the current nested controls. **Recommend A for the separate fix assignment.** This is a reversible, provider-scoped markup change; the coordinator owns implementation and design review.

## Proposed minimal fix scope and regression coverage

1. In `provider-connection-card.component.ts` only, use `ptah-native-card` as a noninteractive frame (`clickable` false/omitted; move its `ariaLabel` to the navigation control). Add a full-surface, native `<button type="button">` inside the frame as the details trigger, with `cardAriaLabel()` as its accessible name and `(click)` emitting `detailsRequested`. Keep the repair button and optional scope-row button as **siblings** of that trigger, never descendants of it. Preserve the current tone, spine, status tooltip, data attributes, card dimensions, hover affordance, and a visible high-contrast keyboard focus indicator on the new trigger. Layer the repair and scope controls above the trigger so pointer input reaches each control while clicking the remaining card surface opens details. Native button behavior supplies Enter and Space without a custom key handler.
2. Update `providers-settings.component.ts:1165-1172` to restore focus to the new details trigger by a stable selector; the existing `[role="button"]` lookup targets the old generic-card root and is not a reliable native-button selector. Avoid changes to `NativeCardComponent` and its other callers.
3. In `provider-connection-card.component.spec.ts`, replace assertions tied to the old root `role`, `tabindex`, and zero/one total-button counts with assertions that the navigation trigger and inline action are separate buttons under a noninteractive frame. Keep tests for card-area click, Enter/Space navigation, action-only output, accessible names, key-unreadable Retry, and scope-badge activation. Add a focused check that the repair action does not emit `detailsRequested` and that the new trigger remains focusable. Cover the focus-return selector in the settings component test. The coordinator's later Electron axe capture should confirm `nested-interactive` is gone and the action remains pointer reachable; no visual review was repeated in this diagnosis.

## Decisions

- **Recommended A over B/C.** A changes only the provider component and its focus/test callers. B would alter a shared UI contract and its `NativeCardComponent` tests (`libs/frontend/ui/src/lib/native/card/native-card.component.spec.ts:101-165`) for a violation localized to this provider card. C leaves the serious axe finding. **Reversible:** yes; the markup and selector change can be reverted without persisted-data migration.
- **Preserve both actions.** The details trigger remains keyboard operable and named; the inline action and scope control remain independent focusable controls. This follows the current card contract (`provider-connection-card.component.spec.ts:1-16,66-96`) and the approved onboarding reuse at `context.md:34-59`. **Reversible:** yes.

## Limitations

- Read-only diagnosis: no code, test, build, browser, axe rerun, or visual-review execution. The provided axe JSON lacks a descendant selector, so the specific captured Retry child is an inference from the fixture and state mapping; the root/descendant nesting itself is verified in source.
- CSS hit testing and focus-ring appearance for the proposed overlay need verification when the fix is implemented. The settings focus-return selector and button-count specs need coordinated updates; otherwise the accessibility fix would regress behavior or tests.
