## New blocking defects

1. **First-run remains unreachable on normal Electron startup (§1.2; residual blocker 1).** S:35–40 says first match wins and preserves the existing host-deep-link branch ahead of onboarding. `apps/ptah-electron/src/preload.ts:47` supplies `chat` by default. With no restored route, `libs/frontend/core/src/lib/routing/boot-navigation.ts:58` treats that non-null value as different from `restored?.seed`, returning immediately. Adding first-run after restored-route selection therefore never handles a normal fresh Electron install. `apps/ptah-extension-webview/src/app/initial-navigation.ts:95` consumes exactly this plan.

   **Required fix:** explicitly distinguish the Electron default chat seed from an explicit deep link before the host branch. Preserve DevTools overrides and genuine explicit nondefault links; a fresh Electron default-chat boot with no saved route and never-shown flag must select onboarding. Include the cases absent host value, default `chat`, explicit other surface, saved route and superseding navigation in the precedence contract. Also retain the user's Angular guard requirement as meaningful first-run eligibility/readiness enforcement on that boot-selected entry; the current guard only distinguishing implicit hosts does not itself implement first-run eligibility. No second initial-navigation owner is needed.

2. **The migration promises translation at the wrong boundary and an undefined host deep path (§1.3; residual blocker 6).** S:54 removes old IDs from `initialView`/`SWITCH_VIEW` validation, while S:62 promises to translate old host wire values in the shared route parser. Those messages do not traverse that parser: `libs/frontend/core/src/lib/services/app-state.service.ts:362` reads only `payload.view`, validates it at :364 and otherwise rejects it. `libs/shared/src/lib/types/webview-surface.types.ts:95` defines the host allow-list independently of saved route parsing. S:55–56 additionally promises `onboarding` “with path analyze”, but the Electron producer at `apps/ptah-electron/src/services/electron-setup-wizard.service.ts:78` sends only a view and the VS Code producer at `libs/backend/agent-generation/src/lib/services/wizard/webview-lifecycle.service.ts:153` supplies only `initialView`. Initial navigation's surface branch (`initial-navigation.ts:104`) likewise accepts a surface, not that child path.

   **Required fix:** define legacy normalization before both host validation boundaries and saved-route parsing, without retaining the retired UI surfaces; or explicitly choose a supported recovery behavior instead of promising wire compatibility. Choose a supported launcher destination: opening Onboarding Home is sufficient, or specify an existing typed event/frontend handoff that reaches Analyze. Do not silently add a new backend path payload under the no-backend-change constraint. Include base `/setup-wizard` and `/harness-builder` as well as child URLs in the translation table. Explicitly migrate the generation tab validator (`libs/frontend/core/src/lib/routing/surface-routes.ts:44`) from path segments to the new query binding while retaining workflow/workspace validation.

3. **Reload reads cannot recover the promised completed analysis and guidance sections (§3.6, §4; residual blockers 2 and 4).** S:163 loads completed contents only if the resumable lookup supplies a completed manifest. `libs/backend/rpc-handlers/src/lib/handlers/setup-rpc.handlers.ts:431` delegates to `findLatestResumableRun`; `libs/backend/agent-generation/src/lib/services/analysis-storage.service.ts:503` excludes completed analyses unless an unfinished generation checkpoint accompanies them. A completed analysis with no generation yet normally returns no resumable manifest. The load RPC also requires a filename (`setup-rpc.handlers.ts:856`). Separately, S:161 says `enhancedPrompts:getStatus` supplies saved sections, but R:473 returns enabled/generated/freshness/stack metadata only. `summary.sections` belongs to the final run response at R:528, not getStatus or `SetupGenerationRunState` (R:98).

   **Required fix:** specify completed analysis discovery independently: load the validated `?analysis` filename when present, or resolve saved analysis identity from status/list-analyses and then call load-analysis. Keep unfinished discovery separate and never substitute an unrelated latest unfinished run for the selected completed result. For guidance, retain the final summary locally with workspace/run identity when actually received, or omit section metadata after reload and show the supported saved-content/status controls. Explicitly handle a lost final response: no fabricated section names/counts and no claim that getStatus reconstructs them. For completed generation cards, use terminal `result.agentOutcomes`/`counts` (R:65), not a promise that resumable discovery returns completed checkpoints.

4. **Proposal-only rendering incorrectly includes fields outside HarnessConfig (§3.3–3.4, §4; residual blocker 4).** S:119 says the panel is built “only” from `proposeConfig` revisions yet requires `plugins.enabledBundled`, `missingExternal`, Toolchain and Document. `HarnessConfig` at H:25 has persona, agents, skills, prompt, MCP and CLAUDE.md; plugin/toolchain fields instead belong to `HarnessStartNewProjectResult` at H:518. The standalone generated document comes from `harness:generate-document` at H:372. The proposal revision type is `Partial<HarnessConfig>` (`libs/shared/src/lib/types/rpc/rpc-harness-proposal.types.ts:6`). S:134 then promises identical sections in team-builder, which does not run the new-project intake RPC.

   **Required fix:** extend the field-source table to distinguish proposal configuration, intake plugin/toolchain facts and helper document output. Define retention/hiding for those auxiliary facts after reload and in team-builder; do not fabricate absent intake results. Keep revision diffs restricted to configuration snapshots plus explicitly tracked frontend overrides. Label helper-generated Document separately from CLAUDE.md, preserving its review/copy capability. This is a frontend presentation/source correction, not a request for new endpoints.

## Non-blocking suggestions

1. Make the controller's local record include durable send acknowledgement/attempt state, applied-revision identity and any retained apply receipt. S:142 currently lists only tab/session/mode/workspace/intake/lastRevision, while S:169–173 promises sending and applied-result reload states. Reconcile with authoritative session state before showing busy or offering Retry send; an intake hash alone is not proof that a lost send was never accepted. Existing record/override machinery can be extended in the frontend.
2. Keep the review prototype's labels mode-aware: `prototype/index.html:356` says New project, but :358 links its completed Intake step to team-builder. Demonstrating the common review once is sufficient; fix the breadcrumb/link mismatch during implementation.
3. Treat `get-resumable-run` as one latest eligible analysis/generation pair (R:337), not an enumeration of all historical runs. Stacked Home banners may combine that pair with known bound tabs and local harness records; do not promise discovery of every disk checkpoint.
4. When rendering proposal revisions, fold partial updates in durable revision order and merge existing explicit user overrides. Use stable revision IDs internally even if the display uses ordinal numbers; do not compare two partial payloads as complete snapshots.

## Decisions

- **(a) Accept shownAt**, with the exact successful-render trigger already specified. It does not waive durable workflow recovery or the boot-precedence fix.
- **(b) Accept section references** in the revision log; line-number mappings are unnecessary. This review uses file:line evidence for reproducibility.
- **(c) Accept dropping the installed-file diff.** Proposal revision comparison meets the orchestrator constraint and requires no new backend baseline.
- User decisions 2 and 3 are represented; decision 4 has a substantially complete parity/removal map. User decision 1 remains blocked on default Electron boot. The three retired surfaces can be deleted once the explicit migration contract is corrected. VS Code keeps manual entry; TUI must retain shared-type compatibility.
- Evidence: inspected revised spec, old eight-blocker review, inventory/contract and targeted shared/frontend/backend/host source. Used Ptah browser navigation and screenshots on the in-workspace prototype. The desktop Home and 360px iframe proposal were visually inspected against the three-card, collapsed-log/dock and non-colour-label requirements. The screenshot session remained desktop-sized despite a requested 1280px viewport; no independent 1280px or 640px screenshot claim is made. Browser evaluation attempts failed, so focus trapping/Escape restoration were source-inspected, not interaction-verified. No axe, build, tests or verify were run, as requested.
- Tool/skill availability: Ptah workspace/browser tools were available. No native skill discovery/loader was exposed; read the repository UI/UX and Angular SKILL.md files directly. Used native targeted line reads and rg for source evidence. Only this deliverable was written; no Git mutation or application change.
