## Verdict

**REVISE** — The proposal-centric direction is viable, but startup routing, hidden-session recovery, unsupported screen data and capability omissions prevent a correct implementation plan from being derived from this spec.

References below are worktree-relative `file:line`. `S` = `.ptah/specs/TASK_2026_ONBOARDING/design-spec.md`; `I` = sibling `parity-inventory.md`; `B` = sibling `backend-contract.md`; `W` = `libs/frontend/setup-wizard/src/lib`; `H` = `libs/frontend/harness-builder/src/lib`. Line references identify evidence, not proposed implementation locations.

## Blocking defects

1. **The first-install guard is attached to a navigation that normal startup bypasses.** Spec §1, S:28–32 and Decision 8 specify a guard only on the empty-root redirect. `apps/ptah-extension-webview/src/app/initial-navigation.ts:61` navigates directly to a surface; :95 resolves the host/restored boot plan and :105 executes it. `apps/ptah-extension-webview/src/app/app.ts:90` sets connected then invokes that navigation. The empty redirect at `app.routes.ts:231` is not the normal first-install entry. `libs/frontend/core/src/lib/services/app-state.service.ts:710` supplies a readiness predicate, not a deferred guard retry. Returning through the root while unready and then allowing chat would also consume the only opportunity to redirect. This violates user decision 1.

   **Required fix:** specify the boot integration and precedence: explicit host/developer deep link and valid restored route take precedence; the default first-install Electron boot must deliberately enter the guarded route and await readiness, without blocking initialization required to establish that readiness. Specify cancellation when a newer navigation wins, host eligibility, browser-safe flag access, and first-run state updates for each completion/re-entry action. State whether VS Code shares onboarding or retains a supported fallback; TUI has no Angular guard. Preserve the single initial-navigation owner. Menu plus Settings re-entry is sound, but `setCurrentView` remains readiness-gated.

2. **Generation and guidance lose their required tab/workspace binding; generic lifecycle labels do not define recovery.** Spec §1 has only `?run` for generation and no binding for guidance (S:18–19); §5 says existing stores bind to `?run` (S:186). `libs/shared/src/lib/types/rpc/rpc-setup.types.ts:14` requires `tabId`, `workflow`, `workspacePath`; :20 adds `runId`. `libs/frontend/core/src/lib/routing/surface-routes.ts:44` currently extracts and validates workflow/tab from four path segments. I:21, :54 and :75 document tab validation, separate guidance ownership and authoritative refresh. A run ID alone does not replace that identity, particularly before acceptance or on guidance-only entry.

   **Required fix:** define durable route/session identity for *both* generation workflows (e.g. validated `?tab` plus optional `?run`), creation/reuse before start, tab restoration before binding, workspace mismatch/missing-tab handling, model ownership, handoff to the guidance tab and URL/query preservation on every step transition. Include per-workflow reload tables for starting, running, cancelling, cancelled, failed, timed-out, resumable and completed. Map `SetupGenerationRunLifecycle` at `rpc-setup.types.ts:32` explicitly; do not equate all cancellation/failure with a resumable checkpoint. Analysis recovery must load the saved manifest/contents after freshness discovery: `AnalysisStatus` at :149 is only freshness metadata, while `WizardGetResumableRunResponse` at :337 is unfinished analysis/generation discovery, not a replacement terminal result. Explain what the UI does while the original analysis RPC has been lost but the backend is still running.

3. **The two proposal flows retain a hidden chat dependency without specifying how it executes or survives reload.** Spec §§3.3–3.5 and §5 merely promise stores/rebind/drafts and a `?tab` recovery screen. `H/services/harness-workflow-request.service.ts:430` queues the first intake message, :435 waits for the tab to become visible, then sends. Reusing that service unchanged with no visible embed can time out. I:154 explicitly identifies this seam. `libs/shared/src/lib/types/rpc/rpc-harness-proposal.types.ts:15` persists proposals against a real SDK `sessionId` and workspace, not a UI tab ID. The `?tab` is listed only on `/workspace`, not preserved through `/review`. I:153 distinguishes proposal hydration from conversation recovery. Existing conflicting-mode behavior at `harness-workflow-request.service.ts:269` captures a pending intent and navigates to the active owner; the new dialog “Replace it?” does not specify stop, draft retention or successful cancellation before replacement.

   **Required fix:** define a headless frontend session controller that activates the bound session and sends/retries independently of transcript visibility, while preserving the hidden preamble and user-visible intake. Define tab→SDK-session restoration, workspace pinning, query retention, draft/revision merge, missing session versus unavailable proposal, and idle/busy/cancelling/failed/done behavior for **each** mode. Cover closing/reopening the webview, not only navigation within the app. Specify same-mode reuse and cross-mode consent/stop/save/discard outcomes, including uncertain stop and failure. No backend changes are necessary merely to keep existing session execution working; that does require explicit frontend work beyond restyling.

4. **Several screens promise data that the no-backend-change contract does not provide.** Spec §§3.2–3.4:

   - **Analysis Step 1:** S:62–66 repeatedly specifies nine phases and per-row running durations. `B:35` and `libs/backend/agent-generation/src/lib/types/multi-phase.types.ts:20` identify four current phase IDs. `libs/shared/src/lib/types/wizard/phase.ts:51` supplies optional phase counts/statuses, but no per-phase running duration. Failed/skipped phases are also omitted from the specified row states. Use returned IDs/counts/statuses; reserve authoritative durations for manifest results, or label a frontend timer as session-local and unknown after reload. Phase progress rather than fabricated percentage is otherwise correct.
   - **New-project and team-builder proposal dock:** S:99 claims a structured “Agent is asking” state and detected quick-reply options. `B:181–186` exposes chat plus config revisions, not a question/options payload. Define use of an existing structured interaction source if one can be cited; otherwise show the latest assistant message in the answer dock with a generic composer, without claiming reliable question/option detection or requiring the main raw log to be opened. No speculative natural-language parser should become a hidden backend contract.
   - **Both Review & apply screens and team-builder initial proposal:** S:104 and :109 promise created/changed file diffs, a proposal initialized from installed config and “Adds 2, changes 1” against installed state. `libs/shared/src/lib/types/rpc/rpc-harness.types.ts:239` returns context, available agents/skills, presets and pinned workspace, not the installed full harness/file baseline. `rpc-harness-proposal.types.ts:4` provides proposal revisions; `rpc-harness.types.ts:328` returns paths only after apply (also B:139). Revision-to-revision comparison is possible; installed-file comparison is not established by these contracts. Remove those claims or cite an actual existing baseline/preview endpoint and exact derivation. Under the orchestrator decision, do not introduce backend changes.
   - **Generation terminal card:** S:79 promises per-agent propagated-section counts. `rpc-setup.types.ts:75–95` exposes agent outcomes and aggregate tailored/rejected counts, but propagation is consent/status/targets, not a per-agent propagated-section count. Show only the supported fields. Running per-item progress must distinguish observed events/checkpoints from terminal outcomes and leave unavailable fields unknown after reload.

   **Required fix:** add a field-to-source/derivation table with unavailable-data behavior for these screens. Guidance Step 4 correctly avoids percentage and section progress while running and uses final `summary.sections[]`; retain that distinction. Recommendation reasons should derive from `matchedCriteria`/optional description rather than an assumed extra reason field (`B:51`).

5. **The parity map has a row for each capability category, but drops details inside those rows.** Spec §5 versus I:38–76 is not lossless, violating user decision 4 unless the omissions are explicitly proposed for removal:

   - Independent agent generation is lost behind an analysis prerequisite (S:17, :150). I:39 and :48 support a workspace-catalog launch without analysis. §7 item 5 lists removal of standalone entry points, but does not disclose removal of the *ability* to generate without analysis; guidance-only is specially preserved while agent-only is not. Retain a secondary agent-only path using workspace-catalog, or explicitly propose the capability loss and its impact.
   - I:44 includes text and thinking statistics; S:63 lists only elapsed/tool/error statistics and retires the dashboard. Specify their new location, normally the details log, or list the removal.
   - I:66 includes created skills and document content; I:68 includes `harness:generate-document`. S:177 and :179 abbreviate these away and S:98 omits generate-document from the actual helper menu. Preserve document generation/review/copy and created-skill distinction explicitly.
   - I:49 and :58 require conflict/open-owner and chat-busy behavior for guidance as well as agent generation; S:160 locates the conflict only in Step 2. Direct guidance entry must expose the same owner recovery.
   - I:76 preserves inert transcript behavior during overlays. S:187 replaces it with a disclosure and Escape handling; the mobile expanded dock still needs defined modal/nonmodal semantics, background focus behavior and focus return.

   **Required fix:** amend the map to retain every sub-capability (including refresh actions, preset name/description/errors, apply warnings and existing proposal overrides), or explicitly list each intended loss under Proposed Removals. Preserve separate workflow identity even where UI surfaces are consolidated. Reusing a component can cover a capability, but the destination/control must be named rather than contradicted by the new screen description.

6. **Surface consolidation lacks the host and route migration contract.** Spec §1 (S:11) names the shared contract, but §§4–5 do not identify all producers that will send invalid old values. Removing old IDs from `libs/shared/src/lib/types/webview-surface.types.ts:44`/`:67` changes both `initialView` and `SWITCH_VIEW` validation; `surface-routes.ts:21` is only a re-export, not a second registry.

   Concrete affected references:
   - `apps/ptah-electron/src/services/electron-setup-wizard.service.ts:79` sends `view: 'setup-wizard'`.
   - `libs/backend/agent-generation/src/lib/services/wizard/webview-lifecycle.service.ts:153` creates the VS Code wizard panel with `initialView: 'setup-wizard'`.
   - `apps/ptah-extension-vscode/src/services/webview-html-generator.ts:113` documents the shared allow-list validation seam; its `webview-html-generator.initial-view.spec.ts:98` still explicitly expects the old builder/hub values.
   - `apps/ptah-extension-webview/src/app/app.routes.ts:100`, :107, :128, :141 and :154 register the old routes and surface providers.
   - `libs/frontend/chat-ui/src/lib/services/generation-workflow-launcher.service.ts:78`, `H/services/harness-workflow-request.service.ts:355`, `W/services/setup-wizard-focus-router.service.ts:27`, and the corresponding harness focus router generate old child URLs. `libs/frontend/chat/src/lib/components/templates/electron-shell.component.ts:617` opens the old hub; I:10 covers the shared configuration actions.

   **Required fix:** enumerate host producer, shared contract, route parser/validator, startup persistence, launcher/focus-router and menu migrations. Choose explicit treatment of old persisted URLs and old host wire values: translate them without retaining old UI surfaces, or document an intentional recovery path. Surface IDs may change while backend event names and workflow discriminator values remain stable; do not mechanically rename `setup-wizard:*` events. Specify the VS Code launch destination and non-Electron gating. No direct TUI old-surface producer was found in the scoped host search; compilation compatibility is a requirement, not verified here. Consolidation is architecturally sound once these seams are included.

7. **Completeness gating and “Review anyway” contradict one another and existing behavior.** Spec §3.3 S:101 permits override to reach Review, but :104 still gates Apply on incomplete state; Decision 7 does not resolve this. `H/components/sidebar/builder-apply-section.component.ts:275` guards initialization, preview, busy/applying and workspace, not `isConfigComplete`; :232 uses completeness for styling. Thus completeness gating is a new policy, not simply preserved parity, and the proposed override can strand a valid manually edited/preset proposal.

   **Required fix:** separate review navigation from write eligibility. Preserve valid manual/helper/preset apply while retaining initialized/nonempty/pinned-workspace/not-busy checks, or explicitly propose the restriction. State exactly what override changes; never mutate the agent's completeness fact to represent user consent. Document handling of stale preview and post-apply edits. Mark this whole policy lane-proposed.

8. **The prototype does not demonstrate the specified narrow/accessibility behavior or the distinct third workflow.** Spec §§3.3, 3.4, 6 and Decision 11. In `prototype/index.html:146`, the dock becomes a static block above the proposal; the ≤720px rules at :150 never make it a collapsed bottom bar. The 640px light proposal screenshot confirms the fully expanded composer above the proposal, contrary to S:99. Changed items at `index.html:298`, :301 and :304 have gold styling but no “New”/“Changed” text; the screenshot confirms colour-only differentiation, contrary to S:98 and §6. The script at :336 exposes only home/analyze/project views, not a distinct AI-team-builder path. `prototype/narrow.html:3` is a fixed 640px iframe, not evidence for ~400px or embedded-sidebar widths.

   **Required fix:** make the prototype and spec agree on dock expansion, focus/Escape/return behavior and non-colour status labels. Provide the team-builder start/review distinction and representative loading, empty, error/cancel/recovery and done states before this design gate passes. Inspect a genuinely narrow viewport as well as 640px. Do not treat a source-only accessibility checklist or single-surface contrast measurements as verified route-level accessibility.

## Non-blocking suggestions

1. Clarify specimen versus literal copy: “9 selected”, “6 of 9” and “Attempt 2 of 3” must be examples derived from actual selections/checkpoints/retry policy. Hide optional facts when unavailable. Avoid promising exact live phase durations after reload.
2. Use a small polite status announcement rather than making the entire frequently changing proposal/card grid live. Keep completed-step links named and visibly focusable; explicitly label progressbar minimum/maximum as well as current value.
3. Correct Decision 11: the discovered `ptah_browser_navigate` supports viewport dimensions when creating a session. A 640px iframe is useful supplementary evidence, but is not a tool limitation requiring that width.
4. Resolve “keep the stable selector renamed” (S:31): either preserve the existing automation selector or explicitly migrate its consumers. Include the guidance-only secondary action in the Home layout, where §3.1 currently omits it.
5. Keep the review's findings about unsupported facts distinct from presentation preferences. The larger Analyze tile, restrained colours and proposal-centric workspace are reasonable design choices; they do not require backend additions.

## Decisions

- **User-decision assessment:** decision 1 is blocked by startup integration; decision 2 is satisfied by the route concept but not fully demonstrated by the prototype; decision 3 is satisfied in the intended layout, conditional on the answer dock/headless execution fix; decision 4 is blocked by the parity gaps. Keep the orchestrator decision: proposal-centric New project and AI team builder with existing seed conversations and `proposeConfig`, without backend changes.
- **Parity coverage audit:** every capability category at I:38–76 has a nominal §5 row. Status/presets; provider/model selection; saved analysis; analysis start/results; recommendations/previews; generation results/retries; community packs; guidance content/toggle/download; intake; revisions/helpers/presets/apply; statistics; leave dialogs; rebind and overlay behavior are all represented. That is category coverage, not complete feature preservation: defects 2, 3, 5 and 7 identify the omitted or contradictory sub-capabilities. Entry points I:9–28 additionally require defect 6's migration. No omission is approved merely because a row label resembles the inventory.
- **Proposed Removals audit:** §7 item 1 (legacy enhancement) is safe only after Step 4 and handoff preserve summary/retry/skip/continue; it is reachable legacy UI, not proven dead (I:166). Item 2 (manual-adjust placeholder) is safe: it only opens a coming-soon modal (I:170). Item 3 (`setup-wizard:launch` facade) is a scoped unused candidate, not a proved global removal: I:168 explicitly limits the claim; remove only after checking public/exported callers, and do not conflate it with active host wizard launch services. Item 4 (duplicate analysis/scan/welcome screens) is safe consolidation if their controls survive. Item 5 (standalone generation entries) needs the agent-only decision in defect 5; guidance-only must remain discoverable. Item 6 (visible chat pane) is authorized, but execution/tab ownership must survive. Item 7 (search/create-skill facades) proposes no current deletion; keeping them unsurfaced is safe, deletion still requires caller/export review. No other removal is approved.
- **Visual evidence:** navigated to the in-workspace `file://` prototype and inspected screenshots of wide dark Home, 640px dark Home and 640px light New-project proposal. Against the spec, Home has three distinct visual cards, emphasized Analyze and stacked narrow layout; the proposal keeps configuration primary and the log collapsed. The light narrow screenshot exposes the dock and colour-only change-marker discrepancies. Screenshots were returned in memory; no screenshot files were written. Analysis-generation was source-reviewed; an attempted selector click did not establish a rendered analysis view. No screenshot evidence is claimed for that view, team builder, real ~400px viewport, recovery states or all keyboard interactions.
- **Methods and limits:** read-only source/contract review; no builds, tests, verify, git mutations or application edits. Only this deliverable was written. Ptah workspace analysis, AST analysis and browser tools were available; native `rg` and line-range reads were used for free-text evidence. No native CLI skill loader/discovery tool was exposed: directly read `.claude/skills/ui-ux-designer/SKILL.md` and `.claude/skills/angular-frontend-patterns/SKILL.md` and applied their review guidance. No backend execution, runtime reload recovery, compile compatibility, automated axe or independent contrast measurement was performed. These limits are not evidence that those checks pass.
