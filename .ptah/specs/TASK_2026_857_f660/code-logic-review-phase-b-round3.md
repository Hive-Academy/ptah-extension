## New findings

1. **Serious — a valid decision-model change can inject a stale `Routing:` reminder.** `host-routing.coordinator.ts:175-179,519-542`; `next-turn-reminder.queue.ts:51-57,87-91`; `user-prompt-submit-hook-handler.ts:100-129,179-193`; `host-routing-setting.ts:26-32,47-59`. The fix deliberately resets routing work when the selected decision model changes (`host-routing.coordinator.ts:533-536`), but the queue gate tests only whether routing is enabled. Suppose an old-model reminder is queued and the user selects another valid model. Before the delayed setting event, a hook can drain and inject the old reminder because `isEnabled()` remains true. Even if the event resets the coordinator while `handoffPointer` is awaited, `discardOwned` cannot revoke the already drained local reminder, and the final gate still returns true. The next turn can therefore receive routing guidance from a model whose result the coordinator has invalidated. The added model-change test covers an unsettled pre-flight (`host-routing.coordinator.spec.ts:915-927`), not a queued or drained reminder. This stale-reminder possibility was latent before this commit; the new reset policy makes it an explicit inconsistency rather than creating the entire race. **Smallest future fix:** bind each routing reminder to a configuration generation and check that generation both when draining and immediately before injection; revoke drained entries when the generation changes.

No other new Critical or Serious defect was established from the fix. Dropping a gated entry in `takeEntry` is deliberate single-use behavior (`next-turn-reminder.queue.ts:51-57`), and a throwing gate is caught by the hook with only an error class logged (`user-prompt-submit-hook-handler.ts:100-111,179-193`).

## Exact PR disclosure

> Phase B host routing has three known limits after fix round 2. First, an off → on setting pair that occurs entirely between coordinator reads can let an old assessment or pre-flight result queue a `Routing:` reminder before the delayed settings event resets it; a hook in that interval can inject the reminder. Second, settings writes that emit no provider event can leave the live-value tracker's event count out of sync, so a later event may be consumed without the required reset. Third, changing from one valid decision model to another can inject a queued or already drained reminder produced by the old model: the hook's owner gate checks only whether routing remains enabled. These races can send stale routing guidance to a chat turn. The existing settings UI serializes writes, which narrows the first case, but programmatic or overlapping writes and hook timing remain exposed. A platform write-time configuration generation carried through assessment, pre-flight, queue drain, and final hook injection is needed to close them. The off-at-hook check and owner-filtered discard from this round are otherwise effective. `future-enhancements.md:20-28` already combines the first two limits as Open defects item 3. Its item 4 (`:29-31`) is the unused `switchChanged` field, **not** the event-less-write defect; the new valid-model reminder race needs separate disclosure.
