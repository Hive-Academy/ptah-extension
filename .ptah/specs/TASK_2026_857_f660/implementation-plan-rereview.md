## New findings

### 1. Serious — Req 1 still counts a run with a stale deliverable as delivered and misses an exit-zero API limit

**Evidence:** Decision row 10 explicitly adds both live cases (`decisions.md:13`). Component 10 adds recorder diagnostics and the existing terminal-path fixture (`implementation-plan.md:483-516`); its test expects a nonempty declared deliverable to be `delivered` (`:505-509`). `checkLaneDeliverable` computes `writtenAfterSpawn` (`libs/backend/cli-agent-runtime/src/lib/cli-agents/lane-completion-notifier.service.ts:112-131`), and the session-child verdict checks it (`:173-186`), but the lane verdict ignores it (`:667-678`). `enqueueLaneCompletionOutcome` copies that verdict and classifies only from `status`, `failureKind` and `authMatched` (`libs/backend/cli-agent-runtime/src/lib/cli-agents/lane-completion-outcome.ts:28-49`); `classifyLaneFailureClass` returns null for `delivered` and recognizes usage limits only when `failureKind === 'quota'` (`libs/backend/cli-agent-runtime/src/lib/cli-agents/limits/lane-failure-class.ts:14-25`). An exit-zero API 429 with an old nonempty file therefore still becomes `delivered` with no failure class.

**Exact change requested:** Put the fix in **Component 10 / B10**. Make the lane verdict require `writtenAfterSpawn !== false`, as the session-child verdict does. Define a bounded, non-persisted way to detect an API 429/rate-limit result even when the CLI exits zero, set a failure verdict and `failureClass: 'usage-limit'` without logging output text, and name any additional source file in B10 (for example the failure classifier or process-output adapter). Add integration cases for a pre-existing nonempty deliverable, an exit-zero 429 response with that file, and a fresh successful deliverable. Verify both the signal and persisted row.

### 2. Serious — An older scope-check answer can replace a newer turn's routing state

**Evidence:** Each admission increments `generation` (`implementation-plan.md:749-751`), but the state-machine rules mutate revision and cache without comparing the answering turn's generation (`:752-771`). The generation/revision guard is specified only when **pre-flight** settles (`:775-782`). Two turns can be admitted while their independent `assess` calls are pending. If turn 2 answers first and initializes or revises the scope, turn 1 can then answer `new-task` or `material_change=yes`, increment the revision again and start pre-flight from stale text. This can replace the newer reminder and cache entry. The deferred test covers pre-flight resolution order, not scope-check resolution order (`:825-839`).

**Exact change requested:** In **Component 16 / B18**, associate each assessment with its admission generation and discard an older answer before it changes revision, continuity, pending scope, nudge or pre-flight state. Preserve the latest turn's conversation window. Add a deferred two-turn test that resolves scope assessments in reverse order, including a stale `new-task` answer after a newer settled answer, and assert that only the newer scope reaches pre-flight, cache and reminder.

### 3. Moderate — Disabling routing during an in-flight pre-flight still queues a reminder

**Evidence:** The setting is checked at admission and cache `get` (`implementation-plan.md:737-739,633-645`), while pre-flight completion checks only `state.revision !== v` before `cache.put` and `queue.put` (`:775-781`). The toggle is read live on the next admission or cache lookup (`:985-986`). If the user turns routing off after the request starts and before it resolves, no admission is needed for the pending result to queue a routing reminder. The disabled-setting test checks zero calls at admission, not this transition (`:815-824`).

**Exact change requested:** In **Component 16 / B18**, check effective enablement when pre-flight settles, discard its result when disabled, clear the reusable result and pending reminder for that tab, and add a deferred pre-flight test that toggles the setting off before resolution. Specify that a later re-enable requires fresh scope validation before reuse.

### New finding — Moderate: disable reset leaves pre-disable operations eligible after re-enable

**Evidence:** Disable reset clears `inFlight` and attempt marks but retains the revision (`implementation-plan.md:878-889`). `applyAssessment` rejects only a changed admission generation or a setting that is _currently_ off (`:901-913`); the pre-flight settle checks only current enablement and revision (`:951-958`). If a pre-flight starts, an off-state admission resets the tab, and the setting is re-enabled before that old promise settles, the old result can queue a reminder and cache entry for the retained revision. A new same-revision pre-flight can also start after re-enable, and the old continuation can clear its `inFlight`. A pending assessment has the analogous gap because the off-state admission returns before incrementing `generation` (`:875-877,901-913`). The deferred test settles while still off (`:1025-1034`), so it cannot catch either case.

**Exact change requested:** In **Component 16 / B18**, increment a per-tab cancellation epoch during Disable reset, capture it when starting each assessment and pre-flight, and discard a result whose epoch changed before any state, cache or queue mutation. Guard `inFlight` cleanup by promise identity. Add deferred tests for off → on before an old assessment settles and before an old pre-flight settles, including a new same-revision pre-flight; assert no old reminder or cache entry, and that only the new request remains active. This makes re-enable's fresh-scope requirement observable.
