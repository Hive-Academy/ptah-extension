## Findings

1. **Moderate — wrong learning counts; fix now.** `libs/backend/lane-outcomes/src/lib/write/report-effect.ts:43-68` reduces every reviewer run to its agent ID when forming the report ID; `store/sqlite-lane-outcome.store.ts:133-148` treats that ID as already applied. **Scenario:** reviewer agent `r` reviews implementer run `i:2026-10-31T10:00:00.000Z` and writes `REVISE`; after a code revision, the same continuation-capable reviewer agent makes a new review turn and writes `APPROVED` for that run. Both reports become `review:i:2026-10-31T10:00:00.000Z|r`; the second is `duplicate`, leaving `finalReview` unset. Two separate `REVISE` turns similarly count as one. Req 7 calls for dedupe by reviewed and reviewer **run** IDs (`.ptah/specs/TASK_2026_857_f660/task-description.md:105-109`). **Smallest sound fix:** give each review turn a stable host-minted event ID shared by capture and the MCP report path; retain it on replay but issue a new one for a new turn. The current test covers two endings with identical text (`lane-outcome-recorder.service.spec.ts:786-801`).

2. **Moderate — missing review evidence and wrong learning counts; fix now.** `libs/backend/lane-outcomes/src/lib/lane-outcome-recorder.service.ts:369-380` keeps an unknown bare ID unchanged; `store/sqlite-lane-outcome.store.ts:196-201` joins held reports only when `report.run_id = input.runId`. **Scenario:** `Reviewed-Run: implementer-agent` arrives before a lane implementer writes its outcome row. The review is held under `implementer-agent`; the eventual lane row uses `implementer-agent:<completedAt>`, so the verdict never joins, then expires. The tool's agent-target fallback to `subagent:<id>` has the same mismatch for an unseen lane (`libs/backend/vscode-lm-tools/src/lib/code-execution/mcp-core/tools/outcome-report.tool.ts:110-128`). The approved plan requires an early review lane to land its verdict (`.ptah/specs/TASK_2026_857_f660/implementation-plan.md:1376-1379`). **Smallest fix:** resolve from an authoritative pending lane record when available; otherwise hold a typed agent-target alias and resolve it on insertion, with ambiguity handling. Add a fixture that inserts a lane row after a bare-ID review.

3. **Serious — raw provider error text reaches logs; fix now.** `libs/backend/cli-agent-runtime/src/lib/ptah-cli/helpers/ptah-cli-stream-loop.service.ts:689-701` logs `rawMessage` before calling `sanitizeErrorMessage` for display. **Scenario:** an SDK query rejects with an error message containing a prompt fragment, CLI output, or provider response body. The full fragment is written to the application log even though the emitted segment is sanitized. **Smallest fix:** log a fixed message with a bounded error class/code only; keep text sanitization confined to the visible error segment. Inspect the analogous notifier error-detail log (`lane-completion-notifier.service.ts:416-421`) for the same exposure.

4. **Serious — anonymous tool review bypasses self-review and dedupe; fix now.** `libs/backend/lane-outcomes/src/lib/lane-outcome.schema.ts:25-32` makes `reviewerRunId` optional; `libs/backend/vscode-lm-tools/src/lib/code-execution/mcp-core/tools/outcome-report.tool.ts:141-146,205-208` skips `isSelfReview` when both that argument and `getCallerAgentId()` are absent, then uses `randomUUID()` for the report ID. The MCP context explicitly permits a URL without an agent segment (`libs/backend/vscode-lm-tools/src/lib/code-execution/mcp-core/mcp-request-context.ts:88-94`). **Scenario:** an agent calls `ptah_outcome_report` twice through a session or workspace MCP URL with `kind: review`, `target.runId` equal to its own run, `verdict: revise`, and no `reviewerRunId`. Both submissions are accepted and each has a new report ID; the same self-review increments `reviseRounds` twice. **Smallest fix:** require an attributable reviewer identity for every review, reject review calls without one, and derive the receipt from a stable reviewer turn identity shared with host capture.

### Five logic questions

1. **Silent failure:** an early bare-ID review is accepted as `held` but never joins its lane row (Finding 2).
2. **Unexpected user action:** continuing a reviewer after a revision and producing a distinct approval leaves the prior review state unchanged (Finding 1).
3. **Wrong input result:** an unseen lane agent ID in `Reviewed-Run` is treated as a concrete run ID (Finding 2).
4. **Dependency failure:** a raw SDK rejection reaches the log before sanitization (Finding 3); unreadable review files are skipped with a code (`review-deliverable.reader.ts:72-84`).
5. **Unstated case:** one reviewer agent can conduct more than one legitimate review turn against one implementer run; the receipt key has no turn identity (Finding 1).

- **Review-event identity:** Report agent-level receipts as a defect rather than a permanent contract. Options are per-agent dedupe or a stable per-turn event key. Req 7 names reviewer run IDs, and the collision loses later verdicts (`task-description.md:105-109`; `report-effect.ts:58-68`). Reversible: yes.
- **Early bare-ID targets:** Report the unmatched hold as a defect. Options are require a concrete run ID before the target lands or support a typed alias hold. F3 deliberately accepts bare IDs and the plan requires early joins (`lane-outcome-recorder.service.ts:369-380`; `implementation-plan.md:1376-1379`). Reversible: yes.
- **Missing reviewer identity:** Reject unattributed tool reviews. Options are allow anonymous reports with random IDs or require a caller or declared reviewer identity. Optional `reviewerRunId` plus an agentless MCP URL bypasses the self-review guard and stable dedupe (`lane-outcome.schema.ts:30`; `outcome-report.tool.ts:141-146,205-208`). Reversible: yes.
