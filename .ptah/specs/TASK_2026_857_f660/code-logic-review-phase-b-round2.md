## Findings

1. **Serious — a delayed setting event lets stale work mutate state and can cancel a newer request.** `host-routing-setting.ts:47-59`; `host-routing.coordinator.ts:187-215,265-281,396-439,512-517`; `file-settings-manager.ts:135-151`; `electron-workspace-provider.ts:217-225`. In Electron, `set(false)` changes the in-memory value synchronously, then awaits disk persistence before the provider emits a change event. A rapid `set(true)` likewise makes the value read as on before either event. If an old assessment or pre-flight settles in this interval, `isEnabled()` reads on and its unchanged epoch permits a decision call, cache write or queued reminder. Conversely, a new turn admitted after the on value is visible but before the pending off event can have its assessment canceled by that late event. This fails the binding rule to discard old results before _any_ state/cache/queue mutation while retaining the new request. **Smallest fix:** publish a monotonic configuration generation at the in-memory mutation point (including both off and on writes), and capture/check it on each assessment and pre-flight; or make the effective setting change and cancellation event atomic before new work can observe the value. Test with deferred persistence/events and an old result plus a new same-revision request.

2. **Serious — disabling during a hook can still inject a routing reminder.** `user-prompt-submit-hook-handler.ts:97-123,168-196`; `host-routing.coordinator.ts:512-517`; `electron-workspace-provider.ts:217-225`. A queued `Routing:` entry can be taken while the hook runs, then the user turns routing off while `handoffPointer` is pending. `discardOwned` sees no queued entry, and the hook returns its local `reminder` after the await. A second path exists before the delayed Electron change event: the setting already reads off, but the queue is still populated and the hook takes it. Both paths send routing context after off despite the fix. **Smallest fix:** make the hook's final routing-context decision consult the live enabled state immediately before returning, with owner-aware queue data so unrelated context remains; also make invalidation occur when the setting becomes effective. Test a deferred pointer and a deferred settings write.

3. **Moderate — a setting reset removes another producer's reminder at the same session key.** `host-routing.coordinator.ts:497-525`; `next-turn-reminder.queue.ts:51-62`. `onSettingChanged` calls `disableReset` for each tab before `discardOwned`; `disableReset` calls `discardQueued`, whose unscoped `discard(key)` deletes whichever entry currently occupies that session key. If another producer put a reminder after routing's latest entry, switching routing off deletes that producer's entry, even though `discardOwned('host-routing')` would have preserved it. The new queue test uses a separate key for the other producer and misses this case. **Smallest fix:** add an owner-filtered keyed discard for revision changes and resets, or use only `discardOwned` for a global reset; test an unrelated entry on the same resolved session key.

No new prompt, scope or assistant text logging was found in the reviewed fix (`host-routing.coordinator.ts:576-586`). The subscription is released on disposal (`:250-254`). Decision row 28's disputed F3 and deferred F4/F5 were not reopened.

## Five logic questions

1. **Silent failure:** a stale result can write cache/queue state while the setting already reads on after an off/on pair but before its events arrive (`host-routing.coordinator.ts:278-325,404-439`; finding 1). Its later reset makes the earlier mutation easy to miss.
2. **Unexpected user action:** quickly toggling routing off and back on during a pending settings write can discard a newly admitted request; toggling off during a pending hook pointer can still inject a routing reminder (`electron-workspace-provider.ts:217-225`; `user-prompt-submit-hook-handler.ts:97-123`; findings 1–2).
3. **Wrong input rather than error:** another producer's valid reminder on the same session key is deleted by the unscoped reset (`host-routing.coordinator.ts:523-525`; finding 3).
4. **Dependency failure or timeout:** if the optional pointer stalls until its timeout, the already drained reminder remains local across that wait and can be injected after routing is disabled (`user-prompt-submit-hook-handler.ts:97-123,168-196`; finding 2). A settings persist delay likewise postpones the cancellation event (finding 1).
5. **Unspecified requirement:** preserving other producers' context at the _same_ session key needs owner-aware keyed removal; the current owner tag covers only global removal (`next-turn-reminder.queue.ts:51-62`; finding 3).
