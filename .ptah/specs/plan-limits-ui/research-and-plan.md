# Plan limits: research, root causes, and implementation plan

Scope: read-only source review on 2026-10-11. Screenshot symptoms were not reproduced locally. File:line references below refer to this worktree; t3code links refer to its `main` branch as inspected on this date.

## Root causes

1. **Duplicate Claude card: owner-key-only dedup and unresolved identity.** `plan-limit-owner-discovery.service.ts:182-236` collects selected provider, sessions, CLI lanes, owner keys, and ledger evidence and deduplicates solely by `owner.key` (`:189-195`). `provider-owner.resolver.ts:443-456` creates a verified account key from `accountInfo().email + organization`, but a missing email creates an `unknown` key from route material; `:529-531` applies this to native sessions. A second Claude route/run with unresolved account can therefore become a separate card even if its window values are the same. The screenshot alone cannot prove that both keys are the same human account. Do not merge by equal percentages. First trace the two keys' origin/session handle; then canonicalize them only if both resolve to the same verified account (or the exact same credential/home provenance), migrating ledger evidence to that key. Keep genuinely distinct Claude accounts separate.
2. **“Owner unknown” is a deliberate fallback, with provider-specific causes.** `provider-owner.resolver.ts:413-419` uses `unknown` when a stored provider key is absent or a placeholder; `:443-456` does so when Claude `accountInfo` has no email; `:463-479` does so for Codex until its app-server read supplies an owner key. `:243-245` in `codex-account-usage.service.ts` requires a nonempty ChatGPT email even after login. `provider-owner.resolver.ts:511-525` also leaves an unrouted Ollama daemon session unknown. These are distinct situations; the UI currently collapses them to the same suffix. A privacy-safe account handle (verified email hash/account ID; credential fingerprint; CLI home when no better identity exists) and a reason-specific neutral label are needed. Never equate a CLI-store path with a verified account unless the provider confirms it.
3. **Codex quota is discarded with optional activity.** `codex-account-usage.service.ts:204-275` initializes the packaged Codex app-server, checks `codexHome`, reads `account/read`, `account/rateLimits/read`, then unconditionally parses `account/usage/read` (`:249-271`). Any failure or schema mismatch in *any* of those steps reaches `:184-200` and becomes `service-unavailable`, with `ownerKey` unset. Thus installed/logged-in Codex is insufficient; a rate-limit response may already have succeeded. The strict schemas in `codex-account.schemas.ts:47-98,117-135` and the home equality check at `:220-221` are additional possible failure points. The screenshot does not distinguish them; add safe stage diagnostics and test each. Ptah also ignores `rateLimitsByLimitId.codex` although its schema accepts it (`codex-account.schemas.ts:92-98`), so a non-Codex default bucket can be shown even after success. T3's rate-limit read is independent of activity.
4. **OpenCode card has no plan-window source and may have no local stats.** `plan-usage.service.ts:147-155` maps OpenCode variants to `opencode-local-usage.reader.ts`; that reader calls `opencode stats --json --cost` and returns `windows: []` even on success (`:55-76`). A command/schema/timeout error returns `service-unavailable` with no local usage (`:61-85,131-132`). `provider-account-card.component.ts:580-592` then has no rows or local block. The CLI-store discovery path (`plan-limit-owner-discovery.service.ts:328-340`) proves only installation, not Go subscription. The existing service header comment saying OpenCode has no reader (`plan-usage.service.ts:8-12`) is stale.
5. **Dashboard card layout creates narrow labels and whitespace.** `provider-account-card.component.ts:149-150` allows 15rem cards; `:169-207` places an unconstrained heading beside an unshrinking status badge and refresh button; `:240-319` uses 8rem auto-fit window cells with centered 3.5rem donuts and source chips per window. At the screenshot width this forces title breaks, truncates subtitle, and spends vertical area on decoration. The repeated “Provider API” chip is from each row's sources at `:310-319`.
6. **Session tile face overloads a two-column stats grid.** `plan-limit-tile.component.ts:34-37,74-115` places a 2.75rem donut beside a stacked label, truncated owner caption, value, and reset string, then adds chips at `:143-160`. The chevron is absolutely positioned at `:162-167`. `plan-limit-tiles.ts:101-106` builds the caption from generic owner label plus key suffix; `:250-255` adds a full reset line. The expanded detail (`plan-window-detail.component.ts:29-95`) is a sequence of compact text rows, not a structured label/value grid. This explains overlap and poor scan order.

## Proposed design

### Dashboard cards

- Render one card per **verified** quota owner. Show provider mark, readable account title, and short source/plan line. Put refresh and state in a separate action row or a fixed right column; allow account name to wrap normally. Unknown identities remain separate only when provenance differs, and get a clear reason (for example “Account identity unavailable”).
- Use `grid-template-columns: minmax(0, 1fr) auto` for header text/actions, `min-width: 0` on text, and a responsive card container `repeat(auto-fit, minmax(min(100%, 21rem), 1fr))`. At narrow widths move actions to their own row. Avoid `h-full` for empty cards.
- Each window is a compact row: `grid-template-columns: minmax(5.5rem, auto) minmax(0, 1fr) 4.5rem`; first column label, middle horizontal meter plus reset, final fixed `tabular-nums` percent. Long reset wraps in the middle. Show source once in card metadata when all windows share it; retain field-level provenance in details/accessible title when sources differ. Explicit empty states: “No plan limits for API key”, “Local usage only”, “Sign in to OpenCode Go”, or a specific read failure.

### Session stats tiles

- Keep 5-hour and weekly rows visible whenever the session owner has those windows, regardless of disclosure state. Make each face a compact `grid-template-columns: 4.75rem minmax(0, 1fr) 4rem 1rem` (window label, meter/reset summary, fixed-width percentage, chevron). The percentage uses `tabular-nums` and stays on one line. Remove the donut from the face. At very narrow widths let the middle summary wrap; fixed columns keep the label and number stable.
- Expanded panel spans the stats grid (`col-span-full`) and uses `grid-template-columns: minmax(6rem, auto) minmax(0, 1fr) 4.5rem` for detail rows. Owner and reset values occupy the flexible middle column and wrap; numeric utilization is right aligned in the fixed column. Put status, absolute/relative reset, observed time, source, and per-lane breakdown in separate labeled rows/sections. Reuse `PlanWindowDetailComponent` for the meter with a `showSummary` mode; do not duplicate the percent and source in both face and panel.
- Keep one disclosure button per tile with `aria-expanded`/`aria-controls`, visible focus styling, and an explicit unavailable value (`—`, never 0%). On a known limit, the collapsed row must communicate percent and upcoming reset without a click.

## Implementation plan

1. **Backend identity and discovery.** In `provider-owner.resolver.ts`, add provider-specific reason/provenance for unknown identities and a safe path to promote an unknown route to a verified account after `accountInfo`/Codex read. In `plan-limit-owner-discovery.service.ts`, reconcile selected-provider, session, lane, and ledger entries by verified identity and preserve source priority plus a usable session handle; never dedup on matching usage numbers. Update `plan-limit-ledger.service.ts` / `plan-limit-ledger.rules.ts` only if migration of active evidence to a verified owner is required; define stale-key expiry rather than leaving a phantom card. Tests: `provider-owner.resolver.spec.ts`, `plan-limit-owner-discovery.service.spec.ts`, `owner-lifecycle.integration.spec.ts`, including two real Claude accounts, missing `accountInfo`, and later identity resolution.
2. **Backend Codex reader.** In `codex-account-usage.service.ts`, make `account/read` and `account/rateLimits/read` sufficient for quota success, parse `account/usage/read` independently and optionally, and retain the owner key if quota/activity fails after account identity is established. Use `rateLimitsByLimitId.codex ?? rateLimits` and accept partial/missing activity. Add bounded stage diagnostics (no body or email) for initialize, home, account, rate-limits, and activity. Evaluate using the active installed CLI or packaged app-server consistently with the resolved `CODEX_HOME`; do not equate CLI detection with app-server compatibility. Update `codex-account.schemas.ts`, `codex-plan-usage.reader.ts`, and specs for quota success with activity failure, missing email, alternate bucket, home mismatch, older method, and auth changes. Add `account/rateLimits/updated` ingestion if Ptah's app-server lifecycle exposes notifications; preserve prior windows on partial updates.
3. **Other providers.** Add an OpenCode Go subscription reader alongside local stats in `plan-usage.service.ts`, keyed to verified `opencode-go` credential; use 403/no Go login as clean no-plan state. In `opencode-local-usage.reader.ts`, keep local totals optional and never let failure blank an otherwise clear plan status. For `grok-session-usage.reader.ts`, add a separate account billing reader only for confirmed grok.com login; keep local usage distinct. For `antigravity-plan-usage.reader.ts`, either add a matching OAuth profile read modeled on t3code or improve the local-server status/retry; check account binding before mixing windows. For `ollama-cloud-plan-usage.reader.ts`, distinguish API-key/no published plan windows from network errors. Update `plan-credential.source.ts`, `plan-owner-read.ts`, relevant provider specs, and status copy as needed. Do not fabricate limits.
4. **Frontend view models and cards.** In `provider-account-card.component.ts`, restructure header/actions and compact window rows; centralize shared source metadata and explicit empty states. In `analytics-card.component.html` check the available width around `<ptah-provider-account-card>`. Update `provider-account-card.component.spec.ts` and the focused plan-limits visual fixture for duplicate/unknown/empty states and narrow widths.
5. **Frontend session tiles.** In `plan-limit-tiles.ts` and `stats-limit-view-model.types.ts`, expose separate owner, short reset, percent, status, source, and detail fields rather than composing long face strings. In `stats-limit-view-model.ts`, ensure 5-hour/weekly tiles are emitted whenever known for the session owner, including while closed; preserve unknown and stale semantics. In `plan-limit-tile.component.ts`, use the fixed/flexible CSS grid above and leave long strings to the expanded panel. In `plan-window-detail.component.ts`, show structured labeled rows. In `lane-tiles.ts` / `lane-usage-tile.component.ts`, expose per-lane owner relation and breakdown within the expanded detail with consistent layout; adjust `stats-tile.styles.ts` for shared spacing. Update focused component/view-model specs and narrow viewport accessibility assertions. No builds or tests were run in this research phase.

## Decisions

- Treat limits as account data and local token/cost statistics as a separate data type. A successful quota read must survive an activity-read failure.
- Use verified account identity or the exact credential provenance for deduplication. Matching percentages and reset times alone are insufficient evidence.
- Keep an explicit `unknown`, `no plan limits`, `local usage only`, and `temporarily unavailable` distinction. Never display an unknown value as zero.
- Prefer SDK/app-server/provider-supported quota sources already used by the active login; gate unofficial endpoints by matching credential and account identity, timeout, and graceful failure.
- Preserve source provenance in expanded details while removing redundant repeated chips from compact faces.
