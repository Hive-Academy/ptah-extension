## 3. The mechanism decision — why `@defer` cannot do the main job

`context.md` says "prefer `@defer` where it fits because it does not touch DI at all." That preference is honoured where it _can_ apply, but it does **not** apply to the seven inversion tokens, and the reason is structural:

`@defer` defers the **static template dependencies of the deferred block**. The seven token surfaces are rendered through `*ngComponentOutlet` with a component reference obtained from DI (`app-shell.component.html:23, 50, 63, 83, 96, 109, 658`). The component class is not a static dependency of that template — **the static edge lives in `app.config.ts:116-125`, in a different file, in a different library.** Wrapping `<ng-container *ngComponentOutlet="tasksComponent" />` in `@defer` moves exactly **0 bytes**.

Verified: repo-wide grep over `libs/frontend/**/*.html` and `apps/ptah-extension-webview/**/*.html` finds **zero existing `@defer` blocks**. Two code comments record `@defer` being deliberately _removed_ (`execution-node.component.ts:71,171`) and one records `import()` being chosen over it (`lazy-diff-view.component.ts:11`).

So the mechanism split is:

| Situation                                                                     | Mechanism                                    | Why                                                   |
| ----------------------------------------------------------------------------- | -------------------------------------------- | ----------------------------------------------------- |
| Component reaches the graph via `app.config.ts` DI token                      | **Lazy inversion-token factory**             | `@defer` cannot see the edge                          |
| Component is in `AppShellComponent.imports` and used once, inside one `@case` | **`@defer` (preferred)**                     | Angular can see and cut the edge; zero DI change      |
| Barrel edge created by a _service_ import in `app.config.ts`                  | **Narrow `/services` secondary entry point** | Proven pattern — this is exactly what Unit 1 exploits |

That third row is the load-bearing insight and the reason Unit 1 is so cheap.

## 5. Explicitly rejected: deferring the two shells

`apps/ptah-extension-webview/src/app/app.ts:19-33` statically imports **both** `AppShellComponent` and `ElectronShellComponent`, and `app.html:18-22` picks between them with a runtime `@if (isElectron())`. The same artifact ships to both VS Code and Electron, so one shell is always dead weight.

Converting those two `@if` branches to `@defer` would split most of the application out of `main.js` and would be, on paper, the largest single win available.

**Do not do it in this task.** Reasons:

1. `ElectronShellComponent` itself imports `AppShellComponent` (`electron-shell.component.ts:60-69`), so the two branches share nearly all their mass. esbuild would hoist the shared code into a common chunk that **both** defer blocks import — that common chunk is fetched on the critical path to chat in _both_ hosts. That is a direct hit on the acceptance criterion "chat must not regress in time-to-interactive," for a benefit that is only the non-shared delta.
2. Units 1–4 are projected to clear the target without it.
3. It is the one change in this space that can plausibly make chat slower, and chat is the launch surface.

Record it as a follow-up if a future budget squeeze demands it, and require a measured TTI comparison before accepting it.

Even though their behaviour is unchanged, the failure mode is silent, so after Unit 1 a human must open a diff view in Electron and confirm **green/red add-remove highlighting** is present, not just that text renders.

### xterm: fixed by Unit 1, not by a bundler change

`@xterm/xterm` (281.5 kB) + `@xterm/addon-webgl` (99.0 kB) are value-imported at `libs/frontend/editor/src/lib/terminal/terminal.component.ts:12-14`. `TerminalComponent` is re-exported from the wide barrel `libs/frontend/editor/src/index.ts:47`, and `app.config.ts:47` statically imports that barrel — so xterm is statically reachable from the app entry.

The three existing `await import('@ptah-extension/editor')` sites (`electron-shell.component.ts:306`, `file-path-link.component.ts:91`, `lazy-diff-view.component.ts:166`) are therefore **defeated** — they currently emit ~1 kB re-export facades over an already-eager chunk. That is the entire "under 8 kB of lazy chunks" finding: it is not that nothing was deferred, it is that everything that _was_ deferred got hoisted back by one static import.

**The fix is the import-path change in Unit 1.** It is not a bundler-level change and not a per-component dynamic import.

**Do NOT** chase the non-ESM warnings. `Module '@xterm/*' is not ESM` will still be emitted after Unit 1 — it is emitted for CJS interop regardless of chunk placement. Do not add `allowedCommonJsDependencies`, do not swap to an ESM fork, do not restructure `terminal.component.ts`. Once the module lives in a lazy chunk the tree-shaking limitation costs nothing on the initial bundle.

## 7. `zod` — 304 kB, deliberately out of scope

`zod` is the second-largest npm item in the initial bundle. It is not a mistake and not trivially removable:

- No frontend file imports `zod` directly. It arrives via `@ptah-extension/shared`, whose barrel (`libs/shared/src/index.ts`) re-exports 11 modules containing top-level `z.object(...)` schema construction.
- The frontend **uses these schemas at runtime on the launch path**: `libs/frontend/chat/src/lib/services/chat-message-handler.service.ts` calls `.safeParse()` at lines 263, 287, 311, 333, 454, 528 — and `ChatMessageHandler` is registered in `MESSAGE_HANDLERS` at `app.config.ts:105`, so it is constructed at bootstrap.
- `libs/shared` has exactly one entry point (plus `/testing`) — `tsconfig.base.json:140-141`.

Removing it means either splitting `libs/shared` into type-only and schema entry points (touching ~149 frontend import sites) or replacing the six chat schemas with hand-written guards. Both are real tasks with real correctness risk on the streaming path. **Do not attempt either here.** Record as the largest remaining structural item once this task lands.

## 8. The DI change, spelled out

### 8.1 Token type change

`libs/frontend/core/src/lib/tokens/lazy-view-components.token.ts` — add the loader type and change all seven token generics:

```ts
// NEW
export type LazyViewLoader = () => Promise<Type<unknown>>;

// CHANGED — all seven, e.g.:
export const TASKS_VIEW_COMPONENT = new InjectionToken<LazyViewLoader>('TASKS_VIEW_COMPONENT');
```

The seven: `WIZARD_VIEW_COMPONENT`, `ORCHESTRA_CANVAS_COMPONENT`, `HARNESS_BUILDER_COMPONENT`, `SETUP_HUB_COMPONENT`, `MARKETPLACE_COMPONENT`, `TRIBUNAL_COMPONENT`, `TASKS_VIEW_COMPONENT`. Export `LazyViewLoader` from `libs/frontend/core/src/index.ts` alongside the tokens (`index.ts:15-21`).

### 8.2 Provider change

`app.config.ts` — delete the seven static component imports (lines 39, 48, 54-58, 59) and replace each `useValue` with a loader:

```ts
{
  provide: TASKS_VIEW_COMPONENT,
  useValue: () =>
    import('@ptah-extension/tasks-ui').then((m) => m.TasksViewComponent),
},
```

**Critical**: `useValue` with an arrow function — **not** `useFactory`. `useFactory` would run the arrow at injection time and start the import eagerly for every token at bootstrap, which is the exact opposite of the goal.

### 8.3 The consumer problem, and the resolution

`AppShellComponent` is the **only** consumer of all seven tokens (`app-shell.component.ts:156-203`), and every one is in a **template position that cannot await a Promise** — `*ngComponentOutlet` requires a materialised `Type<unknown>`. So every consumer needs an async wrapper. Add a small service in `@ptah-extension/core`:

```ts
// libs/frontend/core/src/lib/services/lazy-view.service.ts
@Injectable({ providedIn: 'root' })
export class LazyViewService {
  /**
   * Returns a signal that stays null until `trigger()` first returns true,
   * then resolves to the loaded component. Loading starts on the first true
   * reading of the trigger and never repeats.
   */
  resolveWhen(token: InjectionToken<LazyViewLoader>, trigger: () => boolean): Signal<Type<unknown> | null>;
}
```

Implementation shape: `inject(token, { optional: true })`, a `WritableSignal<Type<unknown> | null>(null)`, and an internal `effect()` that watches `trigger()` and fires the loader exactly once. It must be **trigger-gated, not read-gated** — a bare `computed()` that imports on first read would fire all seven at first change-detection pass and undo the split.

Consumer change in `app-shell.component.ts`, seven fields:

```ts
// BEFORE
readonly tasksComponent = inject(TASKS_VIEW_COMPONENT, { optional: true }) ?? null;

// AFTER
private readonly lazyViews = inject(LazyViewService);
readonly tasksComponent = this.lazyViews.resolveWhen(
  TASKS_VIEW_COMPONENT,
  () => this.currentView() === 'tasks',
);
```

Trigger per token: `currentView() === 'setup-wizard' | 'harness-builder' | 'setup-hub' | 'marketplace' | 'tribunal' | 'tasks'`, and for canvas `layoutMode() === 'grid'`.

**`lazyViews` must be declared before the seven fields** — Angular initialises class fields top-to-bottom and `inject()` in a field initialiser requires the injection context, which is fine, but ordering matters for the `this.lazyViews` reference.

### 8.4 Template change — smaller than it looks

`app-shell.component.html` already wraps every outlet in `@if (component) { … } @else { spinner }` (lines 22-28, 49-55, 62-68, 82-88, 95-101, 108-114, 657-659). **That `@else` spinner is already the correct loading state for an in-flight dynamic import** — no new UI is needed. Each site becomes:

```html
@if (tasksComponent(); as cmp) {
<ng-container *ngComponentOutlet="cmp" />
} @else {
<div class="flex items-center justify-center h-full">
  <span class="loading loading-spinner loading-md"></span>
</div>
}
```

The canvas site at line 657 has **no `@else`** — add the same spinner there, and note that canvas sits under `[class.hidden]="layoutMode() !== 'grid'"` (line 656), i.e. it is hidden-not-destroyed. Gate its loader on `layoutMode() === 'grid'`, not on visibility.

### 8.5 The trap that makes the token work worthless

Flipping a token to a lazy factory does **nothing** if `app.config.ts` still statically imports a _service_ from the same wide barrel. Six of the seven are entangled this way:

| Lib                  | Service still statically imported                       | `app.config.ts` line |
| -------------------- | ------------------------------------------------------- | -------------------- |
| tasks-ui             | `TasksStore`                                            | 59                   |
| setup-wizard         | `SetupWizardStateService`, `provideWizardInternalState` | 38-42                |
| harness-builder      | `HarnessWorkflowMessageHandler`                         | 52-56                |
| dashboard            | `ThothStatusService`                                    | 51                   |
| messaging-gateway-ui | `GatewayStateService`                                   | 49                   |
| skill-synthesis-ui   | `SkillSynthesisLiveService`                             | 50                   |
| memory-curator-ui    | `VecEmbedderRecoveryService`                            | 60                   |

These services are `MESSAGE_HANDLERS` entries and **must stay eager** — they have to be registered at bootstrap to receive push messages. The components must not. The fix is the pattern Unit 1 already proves: give each lib a narrow secondary entry point.

Per lib: add `libs/frontend/<lib>/src/services.ts` exporting only the services, add the `@ptah-extension/<lib>/services` path to `tsconfig.base.json`, and repoint the `app.config.ts` import. Template to copy verbatim: `libs/frontend/editor/src/services.ts` + `tsconfig.base.json:81-83`.

`canvas`, `marketplace` and `tribunal-panel` have **no** service imported in `app.config.ts` — those three are pure token changes with no barrel work. That is why they go first.

**Uncertainty, stated honestly**: Angular emits `/*@__PURE__*/` on `ɵcmp`/`ɵfac`, so esbuild _may_ already tree-shake the unused components out of the wide barrels without the narrow entry points. It demonstrably did **not** for `@ptah-extension/editor`. Assume it will not, but have each batch **measure**: if the narrow barrel for a given lib produces no delta, drop that half of the unit rather than carrying dead scaffolding.
