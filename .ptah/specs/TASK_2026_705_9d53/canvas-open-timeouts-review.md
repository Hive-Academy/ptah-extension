# Canvas open timeouts — independent code logic review

Verdict: REVISE  
Score: 6/10  
Review family: codex (implementer: Claude)

Scope: working-tree diff against HEAD excluding `.gitignore`; the task report, changed bridge and queue paths, canvas drain, branch flow, three other `requestCanvasTab` callers, and relevant specs. No tests or builds were run as requested. `ptah_get_diagnostics` could not finish its scoped TypeScript check within 45 seconds; it reported three files unchecked. The implementer reports 143 core and 100 chat tests passing, which is useful but does not exercise the cases below.

## Numbered findings

1. **Serious — a drained tab request can hang forever after an adoption or focus exception.** `libs/frontend/canvas/src/lib/orchestra-canvas.component.ts:459-470` removes the whole queue before calling `adoptTab` and `focusTile`, with no per-request `try/finally`. If either call throws, `req.resolve` is skipped. At `libs/frontend/core/src/lib/services/app-state.service.ts:1346-1355`, the timer finds that request absent and therefore also refuses to settle it. The bridge remains suspended at `libs/frontend/chat/src/lib/services/chat-store/task-prompt-bridge.service.ts:97`, leaving its caller unresolved and `processing` true at line 75. Later task launches are ignored at line 74. **Fix:** settle every drained request in a protected per-request boundary, including when adoption or focus throws; decide the result from whether the tile actually exists, and continue processing the remaining requests. Add an exception-path test covering one failed request followed by another.

2. **Serious — a late branch failure can overwrite a newer action's banner and appear in another tile.** After the 10-second timeout, `_actionInFlight` is cleared at `libs/frontend/chat/src/lib/components/templates/chat-view.component.ts:1508-1511`, so the user can start another action. The old request's handler later calls `showBranchNotOpenedError` at lines 1490-1497 without checking whether that branch is still the current action. The helper calls `showActionError` with its default `tabId = null` at lines 1515-1518 and 341-342. `libs/frontend/chat/src/lib/services/action-banner.service.ts:7-16,107-116` confirms that a null banner is global and each new banner replaces the previous one. Thus a late failure for branch A can replace the success or error for newer action B across mounted chat views. **Fix:** capture the originating tab and action generation; scope the failure to that tab and suppress or otherwise contextualize it when a newer action has taken over. Test timeout, newer action, then late false/rejection, including a second mounted tile.

3. **Moderate — the specs do not establish the new branch failure contract across rejections or overlapping actions.** `libs/frontend/chat/src/lib/components/templates/chat-view.component.spec.ts:1411-1472` covers late `false` and `true` only. It never rejects the original promise or starts a newer action before the late outcome, so it cannot detect finding 2 or validate the claimed late-rejection handling. **Fix:** add those behavioral cases; assert the displayed banner and that the second action remains the current one. The trailing `.catch` at `chat-view.component.ts:1490-1497` does prevent a throwing late handler from becoming an unhandled rejection, but it can silently discard a banner-service error.

## Five logic questions

1. **Silent failure:** the late handler's `.catch(() => undefined)` at `chat-view.component.ts:1490-1497` discards a thrown notification failure; the earlier still-opening notice can remain the only visible result. The drain exception in finding 1 leaves no caller result at all.
2. **Unexpected user action:** start branch A, wait ten seconds, start or finish action B, then let A fail. The global banner for A replaces B's notice (`chat-view.component.ts:1485-1497`; `action-banner.service.ts:107-116`).
3. **Wrong answer from input data:** with two mounted chat tiles, a failure from a branch in tile A uses a null tab ID and displays in tile B (`chat-view.component.ts:341-346,1515-1518`; `action-banner.service.ts:7-12`).
4. **Dependency failure:** `adoptTab` or `focusTile` throwing after queue removal strands the bounded request (`orchestra-canvas.component.ts:459-470`; `app-state.service.ts:1346-1355`). A late `requestCanvasSession` rejection is handled by the branch rejection callback at `chat-view.component.ts:1490-1497`, but its message is subject to finding 2.
5. **Missing requirement:** the timeout contract does not define how to report a drained request whose canvas adoption throws, nor how an old branch result should interact with a newer action (`orchestra-canvas.component.ts:459-475`; `chat-view.component.ts:1490-1511`). Both need explicit behavior and tests.

## Verified paths and limits

- **Normal drain race:** `app-state.service.ts:1345-1358` enqueues one request object and its timer removes only that object if still queued. `takeCanvasTabRequests` empties the queue at lines 1366-1371; the canvas resolves each request in the same synchronous loop at `orchestra-canvas.component.ts:459-475`. JavaScript timer callbacks cannot interleave with that loop. Once `req.resolve` runs, `settle` clears the timer at `app-state.service.ts:1331-1336`. The tile-plus-timeout-failure race is closed on this normal path; finding 1 covers an exception before resolve.
- **Bridge flow:** `task-prompt-bridge.service.ts:73-141` creates a tab, requests a bounded tile, then links and prefills only after `true`. A same-workspace `false` closes the tab and reports failure; a changed-workspace `false` keeps the tab. `finally` resolves once along ordinary return and caught-error paths, compares the current request, clears only its own signal, resets `processing`, and invokes a deferred replacement. A throwing `request.resolve` at line 133 would interrupt that cleanup; the normal producer supplies a Promise resolver, so this is a residual contract assumption rather than a separate finding. The single-slot signal also retains only the most recent replacement while processing.
- **Other tab callers:** workflow launcher at `libs/frontend/chat/src/lib/services/workflow-tab-launcher.service.ts:45-49`, agent adoption at `libs/frontend/chat/src/lib/services/agent-session-adoption.service.ts:363`, and harness builder at `libs/frontend/harness-builder/src/lib/components/harness-builder-view.component.ts:436-440` omit the new options argument. They retain the prior unbounded queue behavior; `app-state.service.spec.ts:1880-1895` explicitly checks it.
- **Branch guard:** the `finally` at `chat-view.component.ts:1508-1511` clears `_actionInFlight` after ordinary success, false, timeout, or pre-timeout rejection. The trailing catch at lines 1490-1497 handles a throw from its late notification callback. A pre-timeout rejection still propagates from the `Promise.race` at lines 1476-1484 without an error banner; that behavior predates this diff.
- **Test strength:** `app-state.service.spec.ts:1827-1895` exercises exact-object timeout removal, a drained result, and unchanged unbounded requests. `task-prompt-bridge.service.spec.ts:248-287` checks no link/prefill and failure on timeout, but its fake reproduces the queue contract rather than testing the canvas effect. `chat-view.component.spec.ts:1379-1472` checks the guard, late false and late true; finding 3 identifies its remaining gap.

The score reflects two real failure modes, one of which defeats the new bounded-wait guarantee, while the normal timer/drain ordering and unchanged caller behavior are supported by the cited code. A 7–8 would require exception-safe settlement and action-aware late banners; a 5 or lower would imply the ordinary requested paths were also broken, which the evidence does not show.
