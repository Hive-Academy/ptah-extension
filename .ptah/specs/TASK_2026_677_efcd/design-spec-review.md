# Design spec review — TASK_2026_677_efcd

**Verdict: REVISE. Score: 5/10.** The wide dark layout closely follows the two reference images, and the token choices are mostly grounded in the Anubis themes. The score is above 3–4 because the main state machine, responsive layout, and core inspector sections are specified and illustrated. It is below 7–8 because replacing the current view would drop or leave undefined several live capabilities, and a key permission action has no complete route.

## Findings

1. **Blocking — replacement parity and removals are unresolved.** `design-spec.md:155-156`, `:218-222`, and `:486-491` describe a user bubble only and a two-button assistant action row, then assert parity for the details aside. The current message bubble has user branch and rewind actions (`libs/frontend/chat/src/lib/components/organisms/message-bubble.component.html:311-345`), file/image attachments (`:273-309`), collapsed tool/file counts (`:63-71`), per-message token/cost/duration badges (`:136-183`), and a compaction continuation disclosure (`:238-265`). The full chat view has a stats summary with limits and budget (`libs/frontend/chat/src/lib/components/templates/chat-view.component.html:35-49`), background tray (`:53-64`), compaction markers (`:66-77`), permission badge (`:165-169`), and question cards (`:171-183`). A one-to-one replacement cannot silently remove these. **Required change:** add a surface-by-surface parity table with the new location and interaction for each capability; list every genuine removal in the user-decision section and obtain user approval before implementation.

2. **Serious — permission and question actions do not have an end-to-end destination.** `design-spec.md:268-274` promises `Review` and `Answer` buttons that open an existing permission surface, while `:455` acknowledges that Electron single chat has no such CLI permission surface. The prototype only renders a permission button (`prototype/index.html:236-241`); `prototype/assets/app.js:126-136,155-178` binds agent selection but no permission or question action. The current chat view uses separate unmatched-permission and question cards (`chat-view.component.html:165-183`), not a generic lane row. A waiting request can therefore look actionable and leave the user blocked. **Required change:** specify routing for each request type and host, request identity/queue behavior when several requests exist, success/error/closed states, and an explicit fallback until Electron wiring exists. Provide a question-row prototype state.

3. **Serious — the inspector data contract overstates what is available and can show a success-looking but wrong summary.** `design-spec.md:446-457` says `N needs you` is waiting lanes plus pending questions, while a lane waiting on a question can be counted twice; it does not define unique request identity or whether multiple requests from one lane count once or separately. The real `MonitoredAgent` has `permissionQueue` (`libs/frontend/chat-streaming/src/lib/agent-monitor.store.ts:394-442`), and the current chat has separate question requests (`chat-view.component.html:171-183`). `summarizeTodos` currently exposes counts and active text in the details aside (`libs/frontend/canvas/src/lib/canvas-detail/canvas-session-details.component.ts:125-142`); the per-item parser is still proposed in `design-spec.md:452`. The illustrated `4 active · 1 finished`, full todo list, and ahead/behind counts can be mistaken for already available data. **Required change:** define a single session-scoped aggregation contract, de-duplicate needs-you requests, state loading/unknown/partial behavior per section, and make the backend/parser dependencies explicit acceptance gates. Keep ahead/behind hidden until the new source exists.

4. **Serious — overlay keyboard behavior is specified but absent from the interactive prototype.** `design-spec.md:394-395` requires focus to enter the inspector, background content to become inert, and focus to return to the toggle. `prototype/assets/app.js:90-98` only changes visibility and ARIA attributes; `:170-177` returns focus on Escape alone. Clicking the close button or scrim does not restore focus, and opening the sheet does not move focus or make the thread inert. On a 400 px viewport the sheet covers the entire main view (`prototype/screenshots/dark-narrow-400-inspector-sheet.png`), so keyboard users can remain behind it. **Required change:** implement and demonstrate focus entry, trapping/inertness, return on all close paths, and a keyboard-order check in the prototype or mark the prototype as incomplete for Gate 1.7.

5. **Moderate — the permission target misses the stated 24 px minimum.** `design-spec.md:268-272` gives the `Review` button `h-[22px]`; `:403` claims all targets meet at least 24 px. The narrow inspector screenshot shows the small Review control beside a wrapped command. **Required change:** make Review and Answer at least 24 by 24 px, preserving command wrapping; explicitly size `+N more` and Retry targets too.

6. **Moderate — “one-to-one” fidelity is close but has concrete deviations.** Compared at equal 1594 px screenshot width, `reference/02-session-shell-with-inspector.png` places the main column content near x=273 and the user bubble near x=415; `prototype/screenshots/dark-collapsed-wide.png` places them near x=267 and x=409. The reference's Codex and Gemini chips use generic `>_` marks, while the prototype gives Codex a branded icon (`prototype/index.html:113,230-233`); this is a reasonable product adaptation but not literal one-to-one. The prototype adds a prominent `Review` control that the reference permission row lacks, and its composer sits lower relative to the 48 px header. **Required change:** reconcile the six-pixel alignment and composer spacing, and label the provider-mark and Review additions as intentional departures from the image.

7. **Moderate — contrast audit is partly unverified and one rule is too broad.** The theme values in `apps/ptah-extension-webview/src/styles.css:130-143` match the proposed surfaces. Spot checks in `design-spec.md:413-430` report muted ink on surface-1 at 5.71/5.46, running ink on surface-1 at 4.75/5.49, idle ink on surface-2 at 6.82/4.73, and light gold context fill on surface-0 at 4.10 (UI pass); these are plausible against the actual theme values. But the audit script uses the plain light gold token for its focus-ring row (`prototype/assets/contrast-check.mjs:89`), whereas the real light focus ring uses gold-strong (`styles.css:695-708`), so the claimed 6.28 focus result is not reproduced by that row. `design-spec.md:435-438` also limits the check to Anubis themes while the app supports other theme-picker themes. **Required change:** audit the actual focus token and define fallback ink rules or measured checks for supported third-party themes before claiming universal contrast.

8. **Minor — icon availability is not fully independently verifiable in this worktree.** `design-spec.md:79-107` lists Lucide exports and `ptah-provider-mark` identifiers. The provider slugs for claude, codex, antigravity, opencode, grok, copilot, and cursor exist in `libs/frontend/ui/src/lib/native/brand-mark/brand-slugs.ts:74-94`; Gemini does not, matching the declared Terminal fallback. The requested `node_modules/lucide-angular` directory is absent in this worktree, so six direct export checks could not be performed. **Required change:** mark Lucide export verification as pending dependency availability; check `PanelLeft`, `PanelRight`, `GitBranch`, `ShieldAlert`, `LoaderCircle`, and `TriangleAlert` in the implementation environment.

## Five logic questions

1. **Silent failure:** the inspector can display an apparently complete needs-you count and todo list even though request de-duplication and per-item todo data are undefined (findings 2–3).
2. **Unexpected user action:** activating Review in the prototype does nothing; closing the narrow sheet with its button or scrim can lose the intended keyboard focus path (findings 2, 4).
3. **Wrong answer from valid input:** one question that also marks its lane waiting can be counted twice by the stated formula (`design-spec.md:457`); multiple permission requests in one lane have no count rule (finding 3).
4. **Dependency failure or odd shape:** Git has loading/error/Retry (`design-spec.md:297-298`), but todo parsing and lane activity have no corresponding malformed/unknown presentation (`:452-453`); the permission destination is absent in Electron (`:455`).
5. **Missing requirement:** preserving the current message, stats, compaction, permission, and question capabilities while changing the compact view is not established (finding 1).

## Lane-introduced constraints

- **`[lane-proposed] --ptah-link`** (`design-spec.md:110-114`): sound for gold text in light mode; keep it scoped to links and verify with the actual rendered surface.
- **`[lane-proposed] surface-border-strong Tailwind colour** (`:115-116`): optional convenience only; sound, since the existing CSS variable is already present.
- **`[lane-proposed] R1 status words off surface-3; R2 no tinted status fills** (`:420-421`, `:481-484`): sound for the two measured themes, but should be stated as a contrast-driven recipe for the tested tokens rather than a permanent prohibition on any future tuned status fill.
- **`[lane-proposed] stagger caps of eight turn items and six inspector rows** (`:345-358`, `:477-484`): sound for long sessions; ensure items beyond the cap are immediately readable and fast switching cancels stale animations.
- The spec's non-interactive workspace/branch hints and needs-you chip (`:309-314`, `:325-326`, decisions D6/D8) are designer choices beyond the user's explicit request. They are reversible and sensible if the existing workspace/branch controls remain accessible elsewhere.
