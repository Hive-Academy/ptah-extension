1. **Moderate — Antigravity account identity is unwired: the plan's primary owner for Antigravity is implemented only as its fallback.**

   Failure scenario: two Google accounts sharing one machine (one `~/.gemini` root) get one merged owner key — account A's exhaustion evidence suppresses account B's spawn alternatives (and B's S3 `'plan'` success, `agent-process-manager.service.ts:94-98`, clears A's exhaustion), i.e. cross-account misattribution inside one CLI store, the class of leak Decision 3 exists to prevent. On a single-account machine (the overwhelmingly common case) nothing is wrong: every consumer — discovery, lookup, manager spawn/exit/S3 — consistently keys the same `cli-store` owner, and `cli-store` is the plan's own sanctioned fallback.
   Fix: named later task, not a Phase 4 fix-round blocker (see Ruling 1). It must not stay silently unwired: extend the reader's `StatusSchema` with the account field once the provisional LS payload is confirmed, then add the one `recordQuotaOwner` call site. Tracked in the Batch 13 record (deviation 1); carry it into a named follow-up batch.

2. **Moderate — `ledgerOnly` discards the status `planOwnerRead` already resolved, mislabelling the one in-scope owner that is `unsupported-auth`.**
   `libs/backend/cli-agent-runtime/src/lib/cli-agents/limits/plan-limit-owner-discovery.service.ts:299-311` calls `planOwnerRead(owner)` only as a scope filter and then hard-codes `{ status: 'service-unavailable' }`. 3. **Moderate — `discoverTargets` has no deadline; one hung source hangs the whole call.**

## The five logic questions

1. **Silent failure.** By design (documented and spec-verified): ledger write failures never alter exit handling; signal callbacks never break the stream; a source throw drops only that source. Genuinely silent: the Antigravity upgrade that can never happen (finding 1) and the ledger-only `unsupported-auth` mislabel (finding 2) — both produce success-looking results that are subtly wrong in their edge cases.
2. **Unexpected user action.** Selecting the `anthropic` provider card while the Claude subscription is the active auth resolves to the subscription route (`routeInput`'s `activeIds` includes both, `plan-limit-owner-discovery.service.ts:332-335`) — consistent with the plan's route table (the `anthropic`-direct target is keyed on `authMethod:'apiKey'`, which cannot be active while `claudeCli` is), and there is no API-key usage to inspect (Req 2.2), so nothing is lost; noted as confirmed rather than a defect. A dashboard refresh while a source hangs is finding 3.
3. **Wrong answer rather than error.** Guarded: non-canonical `ownerKeys` are dropped, dated Codex retries leave the reset unknown, per-CLI wordings stop tool output quoting another vendor's message, a ptah-cli 429 with an unknown provider is not Ollama quota. Residual: an unrecognized window adjective in a Claude message degrades to owner-level evidence (the honest fallback), and the wording regexes remain provisional for OpenCode/Ollama/Antigravity per the fixtures.
4. **Dependency failure/timeout/wrong shape.** Reader timeout → per-lane `{lookup:'timeout'}` with readers released; reader throw → `failed` for that lane only; `accountInfo()` failure or a 3 s owner-read timeout → owner stays unknown, lane still releases; malformed LS payload → the reader rejects it and returns unavailable; a hung discovery source is the one unhandled case (finding 3).
5. **Missing versus requirements.** The Antigravity account field (named by the plan, blocked on a provisional payload — ruling 1); a dedicated ledger-only status (deferred with a binding Batch 18 carry-forward — ruling 2); a discovery deadline (never specified; finding 3); `agent-namespace.builder.ts` ptah-cli rows still lack `providerId` — outside this diff, already a binding Batch 14 carry-forward.
