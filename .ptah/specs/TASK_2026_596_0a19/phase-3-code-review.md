## Findings

### 1. Moderate — an unattributed proxy's cooldown is never cleared by that proxy's own successes

- **Where:** `libs/backend/auth-providers/src/lib/quota/plan-limit-ledger.service.ts:434-443` (`onProxySuccess` returns early when `observation.ownerKey === null`), against `:419-432` (`onProxyRateLimit` files null-owner 429s under `unknownOwnerKey(providerId, 'proxy:'+sourceId)`) and `plan-limit-ledger.rules.ts:235-237` (`cooldownEnd = max(until, rawUntil)`).
- **Scenario:** a Codex translation proxy 429s before the first account read (or right after an auth-file change), so `currentOwnerKey()` is null. The 429 lands under the per-proxy unknown owner with `rawUntil` taken unclamped from `retry-after` — a seven-day header pins a seven-day cooldown (spec `plan-limit-ledger.service.spec.ts:629-641` proves the seven-day `rawUntil` is kept). The proxy's account is then read successfully and it serves 2xx from then on, but every 2xx observation still carries `ownerKey: null` and is dropped at `:435`, so the cooldown survives to its full deadline while the provider demonstrably works. For an *attributed* owner the same 2xx clears the cooldown (spec `:558-581`).
- **Conflict of guidance:** the Batch 8 carry-forward says proxy events with `ownerKey: null` "must not be dropped or merged across proxies" (`batches.md:683-687`); plan Component 5 says `onSuccess` is "S4 success, on the carried owner key only" (`implementation-plan.md:666`) and the spec pins "a 2xx with a null owner clears nothing" (`plan-limit-ledger.service.spec.ts:583-598`). The two documents disagree; the implementation follows the weaker one, and the failure mode is a misleading up-to-7-day "provider-imposed wait" on an owner that `knownOwners()` still lists (`plan-limit-ledger.service.ts:303-313`, the cooldown keeps the owner state alive in `prune`).
- **Suggested fix:** in `onProxySuccess`, route null-owner observations through the same `proxyOwner(observation)` the rate-limit path already uses (`:582-593`), so the 2xx clears exactly the unknown owner that proxy's 429 created. Update the F66/F68 spec case accordingly.

### 2. Moderate — Codex `rateLimitReachedType` is plumbed through but never becomes window evidence

- **Where:** `libs/backend/auth-providers/src/lib/providers/codex/codex-account-usage.service.ts:191-198` puts `rateLimitReachedType` on `CodexAccountUsageResult.quota`; `libs/backend/auth-providers/src/lib/quota/readers/codex-plan-usage.reader.ts:57-77` (`mapCodexAccountUsage`) drops it — no code path turns it into a `PlanLimitWindow.exhaustion`, and no path sets exhaustion from a provider-api reading at all (`plan-limit-ledger.rules.ts:104-130` only *carries* or *clears* exhaustion; the only producers are stream-event/error-derived evidence via `windowFromClaudeEvidence`, `plan-limit-ledger.rules.ts:266-294`, and carried exhaustion).
- **Scenario:** Codex reports `rateLimitReachedType: 'rate_limit_reached'` with a window at 100%. The account read succeeds, the dashboard shows the window at 100% used, but no `exhaustion` is attached — the "Limit reached" state the engine keys off never appears from this source, and unknown-reset exhaustion is never armed from it either.
- **Plan reference:** Component 7 says "Pass `rateLimitReachedType` through when present, **as window evidence**" (`implementation-plan.md:766`). The passthrough half is implemented; the evidence half is not. Batch 9's own record logs this as out of scope (`batches.md:853-855`), so this is recorded requirements drift, not an unnoticed slip — but the phase review is where it should be decided.
- **Suggested fix:** in the Codex reader, when `rateLimitReachedType` is present (or `usedPercent >= 100`), attach an `exhaustion {observedAt, source:'provider-api'}` to the matching window; the ledger's precedence (`supersedes`) already refuses to let it displace newer live evidence, and `readingClears` already refuses to let a later below-limit read clear an exhaustion it did not observe after.

### 3. Moderate — the ledger's `sessions` map never evicts; discovery grows with every session the host has ever run

- **Where:** `libs/backend/auth-providers/src/lib/quota/plan-limit-ledger.service.ts:154` (`sessions` map), `:456-468` (`sessionState` creates an entry for every session that emits one signal; no removal path exists anywhere in the file), `:303-313` (`knownOwners()` folds every session's owner in), `:316-325` (`sessionOwners()` serialises all of them).
- **Scenario:** every Claude chat session that emits a single `turn-start` gets a `SessionState` that lives for the host's lifetime — nothing consumes a session-end signal and nothing ages entries out. After weeks of a VS Code host, `knownOwners()` (Component 10b's discovery source) returns owners of long-dead sessions, and the snapshot's `sessionOwners` record grows monotonically. This is exactly the "cost that grows with the session" class: slow, unbounded, and invisible until discovery lists stale owners.
- **Note:** the *owners* map is correctly bounded — `prune` (`:471-498`) drops owners with nothing left and F74 (100 active owners) is covered; the spec even pins "owners with no remaining entries are dropped". Only the session index leaks.
- **Suggested fix:** age out session entries whose owner has no live ledger evidence and which have seen no signal within a bounded window (e.g. `FRESHNESS_MS` or 24 h), or consume a session-end notification if the registry can grow one. Keep the "current owner" contract for live sessions untouched.

### 4. Minor — the default proxy hook treats a placeholder header value as a real credential (carry-forward premise is false on the header path)

- **Where:** `libs/backend/auth-providers/src/lib/quota/provider-owner.resolver.ts:131-150` — `credentialFromHeaders` / `credentialOwnerKey` never consult `isPlaceholderCredential` (`:243-245` is used only by `realCredential`, `:253-257`, i.e. the stored-key path, and by `plan-credential.source.ts:114`). The default hook `translation-proxy-base.ts:274-290` feeds whatever the headers carry straight into `credentialOwnerKey`.
- **Scenario:** if a proxy ever forwards one of the `*_PROXY_TOKEN_PLACEHOLDER` values upstream, the owner becomes a stable fake `<providerId>#credential:<fp(placeholder)>` — shared by every instance of that provider (F68's merge failure) and wrongly relatable (`ownerRelation` would answer `same`/`different` on a value that identifies nobody, where Decision 3 requires `unknown`). The Batch 7 carry-forward asserted "Placeholder tokens already resolve to unknown there" (`batches.md:594-596`); that is true for the stored-key path but false for the header path this hook uses.
- **Verified non-triggering today:** every production `getHeaders()` was checked — opencode (`opencode-proxy.factory.ts:32`), codex (`codex-auth.service.ts:254`), copilot (`copilot-auth.service.ts:612`), openrouter (`openrouter-auth.service.ts:77`), sakana (`sakana-auth.service.ts:64`) and custom (`custom-openai-translation-proxy.ts:161`) all send real credentials; LM Studio sends `Content-Type` only (`local-model-translation-proxy.ts:85`), which correctly yields `null` → unattributed. So this is latent, not live.
- **Suggested fix:** return `null` from the default hook when `isPlaceholderCredential(credential)` is true, so a placeholder forwards to the unattributed (per-instance unknown) owner, and add one spec case for it.

### 5. Minor — observations without a `sourceId` all merge into one `'proxy:unidentified'` owner per provider

- **Where:** `libs/backend/auth-providers/src/lib/quota/plan-limit-ledger.service.ts:587-592` — `proxyOwner` keys an unknown owner by `proxy:${observation.sourceId ?? 'unidentified'}`; `provider-quota.store.ts:56,74` makes `sourceId` optional on the context/observation.
- **Scenario:** the only production writer always sets it (`translation-proxy-base.ts:211`, `randomUUID()` per instance), so nothing merges today. But the type invites a future writer (any new proxy or test harness) that omits it, and then every such proxy's unattributed 429s of one provider silently merge into a single fake owner — the exact failure F68 forbids, with no error to observe.
- **Suggested fix:** make `sourceId` required on `ProviderQuotaContext`/`ProviderQuotaObservation` (the only writer always supplies it), or key the fallback by a fresh random id per observation so a missing id can never merge.

### 6. Minor — `PlanUsageService`'s `cache` and `failingSince` maps are never evicted

- **Where:** `libs/backend/auth-providers/src/lib/quota/plan-usage.service.ts:127-129`. `flights` is correctly released on settle/cancel (`:194-197`), but `cache` and `failingSince` entries live for the host lifetime once an owner key has been queried once.
- **Scenario:** bounded by the set of distinct owner keys ever passed to `getOwnerSnapshot` (discovery-driven, so smaller than finding 3's session set, and each entry is one small reading), so this is a slow leak of the same family, not a hot path. A stale `failingSince` entry also survives forever for an owner that never becomes transient again, though it is overwritten on the next non-transient read.
- **Suggested fix:** drop `cache`/`failingSince` entries older than the TTL on access (the same lazy-eviction style the quota store uses in `cooldownFor`, `provider-quota.store.ts:253-265`).

## The five logic questions

1. **Silent failure:** finding 1 — a dropped null-owner success looks like "nothing to record" while the user-facing cooldown contradicts live 2xx traffic; finding 2 — a limit-reached flag arrives and is discarded one layer before it becomes evidence. Storage write failures are correctly logged-and-continued with memory authoritative (`plan-limit-ledger.service.ts:522-542`), and a corrupt persisted owner is dropped without losing the rest (`plan-limit-ledger.persistence.ts:111-138`; `parseQuotaOwnerRef` returns `undefined` rather than throwing — verified in `quota-owner-ref.schema.ts`).
2. **Unexpected user action:** an account switch A→B mid-session is handled everywhere it was specified (generation guard drops in-flight reads, `codex-account-usage.service.ts:105-111,137-145`; the ledger moves the session and keeps A's evidence, spec `:686-701`). The uncovered actions are session churn (finding 3) and "open the dashboard while an unattributed proxy is cooling down" (finding 1).
3. **Wrong answer instead of an error:** a placeholder credential forwarded upstream would produce a confident, wrong owner (finding 4); a missing `sourceId` would merge owners (finding 5); a Codex `rate_limit_reached` read yields a window that looks fine at 100% with no exhaustion (finding 2).
4. **Dependency failure:** proxy hook and listener failures never reach the response (`quotaOwnerKeyFor` catch → null, `noteUpstreamQuota` try/catch, store `notify` isolates listeners, ledger `notify` isolates listeners); secret-store failure → `service-unavailable`/unknown owner without logging material; App Server failure → `stale` only while the cache predates the change, else a bare status; abort paths reject only the aborting caller and cancel the shared read only when all cancellable callers left.
5. **Missing from requirements:** session-lifetime eviction (finding 3), success handling for unattributed proxies (finding 1, two plan passages disagree), and the `rateLimitReachedType` → exhaustion mapping (finding 2).

- **Codex re-pin (R3)** — pin bumped to `0.155.1` with a purely additive generated diff (verified in the batch record and in `codex-account.generated.ts`: `RateLimitReachedType` union, `edu_plus`/`edu_pro`, `normalModelSlug`, `ordinaryUsageAllowed`, `accountId`, `threadUsage?`); the schema projection deliberately widens `rateLimitReachedType` to `z.string()` so a future CLI value passes through as evidence instead of failing the read; `currentOwnerKey()` is null before the first read, after `clearCache`, on unsupported-auth/service-unavailable and for an email-less account; the generation guard drops in-flight reads across an auth change while still answering their callers (spec `:386`); the owner key never lands on `CodexAccountUsageResult` (RPC-safe) — it is exposed only through the backend-only `ICodexOwnerKeySource`.
