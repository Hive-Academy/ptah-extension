### 1. Moderate — Empty roster with the lookup wired appends an orphan, row-less `### Plan limits` table the design does not specify

- **Where:** `mcp-response-formatter.ts:1794-1827` (`formatAgentList` appends `formatPlanLimitsSection(limits)` whenever `limits !== undefined`, including the `agents.length === 0` branch), `agent-limit.formatter.ts:226-232` (`table(headers, [])` emits a header + separator row with no data rows), `lane-limit-lookup.service.ts:125` (`lookup([])` returns `[]`, not `undefined`).
- **Failure scenario:** a host with the CLI agent runtime registered (so `getLaneLimits` is wired, `ptah-api-builder.service.ts:750`) but zero detected CLIs and zero Ptah CLI agents — a fresh install. `ptah_agent_list` then produces `lookup([])` → `limits = []` (non-`undefined`), so the output is the pre-change "No agents found…" text, the roles line, **an empty two-line `### Plan limits` table (`| Agent | Window | … |` with no rows), then** the alternatives section. Design §5.1 empty-roster output enumerates exactly: "the existing 'No agents found…' text, the roles line, then the full alternatives section" — no Plan limits table. All the specified content is present; the orphan table is unspecified output on the first-run experience. No spec covers `formatAgentList([], roles, [])` with limits present (the F52 and empty-roster specs use `limits === undefined`).
- **Fix:** skip the Plan limits section when `limits.length === 0` (keep the alternatives sentence and four groups, which §5.1 does specify), or make the namespace `limits` (`agent-namespace.builder.ts:424-427`) return `undefined` for empty rows so the whole output stays byte-identical to the pre-change empty-roster text. Add the empty-roster-with-limits spec either way.

### 2. Moderate — `ptah_agent_list` calls `agent.limits` outside any guard; the "tool never fails because of the lookup" invariant is unenforced on the list path

- **Where:** `protocol-dispatcher.ts:1318` and `agent-tool.dispatcher.ts:714` (`const limits = await ptahAPI.agent.limits?.(agents);` with no try/catch), versus the guarded spawn path `protocol-dispatcher.ts:214-218` / `agent-tool.dispatcher.ts:240-244` (`lookupAgentLimits` returns `undefined` on any failure).
- **Can it throw today?** No — I traced it: the namespace `limits` (`agent-namespace.builder.ts:424-443`) catch-wraps `getLaneLimits`, and its fallback body is total (`Date.now()`, `rows.map`, and `classifyLaneState(undefined, {lookupFailure})`, whose undefined branch is a constant-shape return with no dereference, `lane-state.ts:314-324`). `rows` is always the array returned by `agent.list()`. So the answer to the batches.md question (`:1595-1597`) is: the fallback cannot throw for any array input.
- **Failure scenario:** the invariant "The tool never fails because of the lookup (Req 5.4, 5.7, plan Component 11 failure behaviour)" is enforced by a guard on spawn but by nothing on list. Any future edit that makes the fallback body throw (e.g. reading a property of `row` that can be absent, or a second lookup variant that bypasses the namespace catch) turns a limit-lookup failure into a full `ptah_agent_list` failure ("Tool ptah_agent_list failed: …") — exactly the regression class Req 5.4/5.7 exist to prevent, and asymmetric with the spawn path, which would keep working.
- **Fix:** route both list call sites through the same `lookupAgentLimits` helper (try → `undefined`), whose `limits === undefined` fallback output already exists and is byte-identical.

### 3. Minor — The P5 3 s bound covers only the lookup, not the roster fetch the spawn path adds

- **Where:** `protocol-dispatcher.ts:214-218` and `agent-tool.dispatcher.ts:240-244` — `lookupAgentLimits` awaits `ptahAPI.agent.list()` before `agent.limits?.(rows)`, and only the latter is bounded by the 3 s `LIMIT_LOOKUP_DEADLINE_MS`.
- **Failure scenario:** on a cold process (detection cache empty, `cli-detection.service.ts:33,85-103`), a spawn response waits for first-call CLI detection plus the ≤3 s lookup, so the effective enrichment delay can exceed the P5 "lookup deadline" intent, though the tool still never fails. Cost judgment (focus 9): **acceptable** — the lookup needs roster rows to resolve lane keys, `detectAll` caches and dedups concurrent calls, `registry.listAgents()` is a config read, and `ptah_agent_list` pays the same cost anyway. Record the bound honestly: enrichment ≈ detection (first call only) + ≤3 s.
- **Fix (optional):** mention the roster fetch in the P5 documentation, or pass the caller's signal into `agent.list()` for the spawn path only.

### 4. Minor — Sustained ledger-change streams make the broadcaster run discarded assembles

- **Where:** `plan-limits-broadcaster.ts:84-99` — `push()` increments `generation`, awaits a full assemble (discovery plus per-owner reads, up to ~6 s worst case), then drops the result if a newer push started.
- **Failure scenario:** a change stream faster than one per ~500 ms for longer than one assemble keeps superseding every push: pushes start every ~500 ms, each runs discovery + reads, and each is discarded on completion, so no broadcast happens until the stream settles (then the newest snapshot is sent — correct data, delayed, with up to ~a dozen overlapping assembles). Bounded in practice: discovery sources each race a 3 s deadline, `PlanUsageService` single-flights reads behind a 30 s cache, and detection is cached — but the discarded work is pure duplicate cost under a burst.
- **Fix (optional):** skip a new push while one is still assembling (re-arm the 500 ms timer instead of starting a second push), so at most one assemble runs at a time.

### 5. Minor — `provider:getAccountUsage` answers `provider-unsupported` when the selected-provider discovery source is dropped

- **Where:** `plan-limits-snapshot.service.ts:124-130` — `ownerSnapshotForProvider` returns `undefined` both when the route names no owner and when the selected-provider source threw or timed out (`plan-limit-owner-discovery.service.ts:433-462` drops it silently).
- **Failure scenario:** a transient 3 s discovery stall on the selected-provider source makes the dashboard card read "provider-unsupported" (a permanent-sounding status) instead of a retryable one. Already recorded and accepted as not-required (batches.md `:1646`, deviation 3); listed because the two states are indistinguishable to the view. No Codex impact (its discovery branch is synchronous).
- **Fix (optional):** have the dropped-source case surface as `service-unavailable` (retryable) rather than `provider-unsupported`.
