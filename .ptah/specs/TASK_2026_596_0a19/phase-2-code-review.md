## Findings

1. **Moderate — a non-object entry in a persisted `cliSessions` array throws inside the restore seam.**
   `libs/backend/agent-sdk/src/lib/session-metadata-store.ts:309-318` (`restoreQuotaOwner`) runs `'quotaOwner' in stored` on every entry of `metadata.cliSessions` (`:883-892`). The `in` operator throws `TypeError` on `null`, `undefined` and primitives, so one corrupted or hand-edited entry (a `null`, a number, a bare key string) makes `getCliSessionsForRestore` reject — the whole restore/resume path for that session (`session-rpc.handlers.ts:1008-1009`, `chat-session.service.ts:1022-1023`, per batches.md D5) fails for every run, not just the bad entry. This is exactly the untrusted-blob threat model G3 itself names (`quota-owner-ref.schema.ts:5-10` treats the persisted owner as untrusted because "a hand-edited or corrupted blob may carry anything") — the owner value is defended, the enclosing list entry is not. G3's "never throws" goal holds for the owner value but not for the container. Suggested fix: guard the entry before the `in` checks — `if (typeof ref !== 'object' || ref === null) return ref;` — restoring the pre-change pass-through behaviour for such entries. Note: the write path always stores objects, and the store's read path may already validate entries (I could not verify that within this review's tool budget); if it does, this is unreachable and drops to Minor.

2. **Minor — the fire-and-forget prefetch's "never rejects" invariant is documented, not structural.**
   `libs/backend/agent-sdk/src/lib/helpers/plan-limits/session-quota-probe.service.ts:221` does `void this.readAccount(sessionId)`. `readAccount` (`:147-172`) resolves through `callBounded`, which catches everything (`:275-285`) — but the `.then` callback at `:155-169` itself calls `this.logger.debug(...)` (`:160-166`); a `Logger` implementation that throws on a debug call turns that into a rejected promise with nobody attached, i.e. an unhandled rejection in the extension host, while the comment at `:220` promises the opposite. Failure scenario: a host logger that throws during debug formatting → unhandled-rejection log noise; no functional impact on the stream or the cache. Suggested fix: append `.catch(() => undefined)` (or route the presence-flag log through a try/catch) so the invariant cannot be broken by a dependency.

3. **Minor — `ACCOUNT_INVALIDATING_ERRORS` omits auth-shaped errors the SDK union does carry.**
   `libs/backend/agent-sdk/src/lib/helpers/plan-limits/session-quota-probe.service.ts:108-113` drops the cached account for `authentication_failed`, `oauth_org_not_allowed`, `account_on_hold`. The installed SDK's `SDKAssistantMessageError` union (verified in `@anthropic-ai/claude-agent-sdk` `sdk.d.ts`) also contains `cloud_credential_error` and `verification_required`, both of which plausibly accompany a credential/account change. Scenario: the CLI re-authenticates after a `cloud_credential_error`; the probe keeps serving the pre-error cached `AccountInfo` for the remainder of that turn, so any owner resolution in the turn attributes evidence to the old account. The staleness is bounded — the next `turn-start` drops and re-reads (`:216-223`) — and the plan (batches.md Task 5.1 validation notes) named exactly the three implemented errors, so this is a plan gap, not a deviation. Suggested fix: add `cloud_credential_error` (or record the omission for the Batch 8 ledger, which inherits the same list semantics).

4. **Minor — registry doc sends the next consumer to build re-keying that the design does not need.**
   `libs/backend/agent-sdk/src/lib/helpers/plan-limits/session-plan-limit-callback-registry.ts:61-64` documents that `sessionId` "is the tabId; consumers re-key on `SessionIdResolvedCallbackRegistry`". The only consumer does not re-key: the probe keys its cache by the `Query` object and resolves either id form through `SessionLifecycleManager.find` (`session-registry.service.ts:346-348`; batch-5 report decision (a)). A Batch 8 ledger author following this comment will build a re-key subscription against a problem the registry's consumers already solve. Suggested fix: reword the doc to state that both the tabId and the real session id resolve to the same record through `find`, and that keying by the record (or `Query`) needs no re-keying.

## The five logic questions

1. **How does this fail silently?** The probe's failure modes are specified nulls, not silent successes: timeout/rejection/missing method → `null` (`session-quota-probe.service.ts:251-289`), failed reads are deleted from the cache only while still current (`:156-158`), and callers fall back to Req 2.1 data per plan `:621`. The mapper's failure path logs at debug with no payload and the stream continues (`stream-transformer.ts:570-580`; spec `stream-transformer.plan-limits.spec.ts:350-363`). The one silent-failure-adjacent gap is Finding 2 (an unobserved rejection).
2. **What user action produces unexpected behaviour?** An account switch mid-session: `turn-start` drops the cache and re-reads once per turn (`:216-223`), two consecutive turns yield two reads (F77, `session-quota-probe.service.spec.ts:170-182`), the tabId-then-real-id path hits the same entry, and a replaced `Query` is a new `WeakMap` key (`:126-129`, `:150-171`; spec `:212-224`). A failed turn then a retry does not pin the old owner: the failed read is not cached.
3. **What input data makes this produce a wrong answer rather than an error?** Unknown/absent `rateLimitType` → owner evidence or no evidence, never a wrong window (`claude-rate-limit.mapper.ts:92-111`, `:139-168`; spec `:151-175`); an unparseable reset is left absent (`:177-185` spec); `utilization` in any scale is never read (G1 verified below); a malformed `rate_limit_event` payload throws inside a caught branch (spec `:350-363`). Finding 1 is the one wrong-shape input that is not contained.
4. **What happens when a dependency fails, times out, or returns a wrong shape?** `callBounded` bounds every call at 3 s, clears the timer in `finally` (`:286-288`) and returns `null` on any of it; `Promise.race` attaches handlers to both candidates, so a late rejection of the SDK call after a timeout win is swallowed, not unhandled (timeout spec `:288-308`). A subscriber that throws is contained per-subscriber by `CallbackRegistryBase` (`callback-registry.base.ts:22-45`), so the probe's sync handler cannot break the stream. A `SessionRecord` without `capacityRoute`/`accountingAuthEnv` degeneracy is handled (`sessionRoute` returns `unknown` for a missing route; `accountingAuthEnv` is non-optional on `SessionRecord`, `session-registry.service.ts:114`).
5. **What is missing that the requirements never mentioned?** Findings 3 and 4; also `opensClaudeTurn` treats a between-turns `system/compact_boundary` as turn-opening (`claude-rate-limit.mapper.ts:265-274`) — the cost is one extra bounded `accountInfo()` read (R6-compatible), not a wrong value; and `cloud_credential_error` timing (Finding 3) is unmentioned.
