## New blocking findings

1. **BLOCKING — native Claude account changes still have no production invalidation signal.** Decision 10 and F55 rely on `authFileChanged` to invalidate the Claude probe and re-read account B (`implementation-plan.md:421-427, 1404-1409`). The event contract is explicitly provider-specific (`libs/backend/agent-sdk/src/lib/helpers/sdk-adapter-events.service.ts:25-29`), and the only production emitter is the Codex auth watcher, which emits `providerId: 'openai-codex'` (`libs/backend/auth-providers/src/lib/providers/codex/codex-auth.service.ts:184-198`). `configChanged` is emitted for application configuration changes, not external Claude account changes (`libs/backend/agent-sdk/src/lib/helpers/config-watcher.ts:108-129`). A fake F55 event would therefore pass without proving A→B in production. Required correction: define a source-backed native-Claude account-change observation/invalidation path, name its owner and lifecycle, and exercise that real path in F55/F77. Provider-scoped events must not be treated as generic Claude invalidations. Also change the stale “at most one `accountInfo()` per session” claim (`implementation-plan.md:598`) to the actual per-query/per-cache-generation bound.

2. **BLOCKING — a restored owner key cannot be reconstructed when the ledger has no evidence for it.** Revision 3 persists only the opaque string `CliSessionReference.quotaOwnerKey` (`implementation-plan.md:430-440, 472-474`) and asks discovery to turn arbitrary `ownerKeys` into ledger-only snapshots (`implementation-plan.md:975-976, 1149-1152`). Yet the ledger persists only known-reset evidence, drops owners with no entries, and does not persist owner references merely because a run used them (`implementation-plan.md:360-362, 623-642`). The current persistence boundary writes only the reference fields supplied at `libs/backend/cli-agent-runtime/src/lib/wiring/agent-events.ts:398-413`; after restart there is no account object from which to rebuild `QuotaOwnerRef {providerId, identityKind, label}`. F55 can therefore lose run A's identity whenever A had no persisted limit evidence, defeating the binding restored-run case (`implementation-plan.md:1404-1409`). Required correction: add one canonical, validated `ownerRefFromKey`/rehydration contract in `ProviderOwnerResolver` (with safe handling for malformed legacy state and a non-secret generic label), or persist the minimal full owner reference instead of only its key. Add a restart fixture where run A has no ledger evidence and still compares as “Different owner” from session B.

## Non-blocking notes for implementation

- `resolveEffectiveAuthRoute` requires both an `EffectiveRouteConfig` and a provider snapshot (`libs/backend/auth-providers/src/lib/auth/effective-route.ts:36-58`); `ActiveProviderResolver.resolveActiveAuth()` supplies only auth method/provider identity (`libs/backend/auth-providers/src/lib/auth/active-provider-resolver.ts:25-41`). Component 10b should explicitly assemble the provider snapshot and preserve the F81-F83 route cases.
- Persisting on spawn and exit is supported by the current event wiring (`libs/backend/cli-agent-runtime/src/lib/wiring/agent-events.ts:171-213`). If an owner upgrades from unknown to known while a run is active, implementation should either persist that upgrade immediately or document why terminal persistence is the accepted durability boundary.
