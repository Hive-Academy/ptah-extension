# property-hub agent-driven UI and its relevance to Ptah Apps

## Summary

- **property-hub uses Angular and a custom agent/UI protocol.** Its NestJS agent service runs `deepagents`/LangGraph; native fetch streams custom SSE events to Angular. The code calls its surface envelopes “A2UI”, but the inspected implementation does not use the A2UI SDK/protocol, CopilotKit, AG-UI, or frontend `useStream` (evidence in §1–2).
- **Its generative UI is a larger version of the catalog idea.** Tools emit `{ type, surfaceId?, data }`; Angular resolves a compiled component catalog, including a recursive `Ui` primitive tree with inputs and buttons. Business tools also emit surfaces automatically (§2).
- **“Shared state” is several explicit mechanisms, not a generally synchronized agent/UI object:** surface replacement events, persisted conversation events, local form state submitted as a new user turn, route context, server-data reload notifications, and LangGraph approval interrupts (§3–4).
- **Ptah’s smaller path is a product-scope and runtime-contract choice, not an Angular limitation.** TASK_2026_494 already shares a validated spec and selected item across host/webview. It deliberately waits for the next user turn instead of allowing emitted buttons/forms to start turns or command the application (§6).
- **Transfer the patterns selectively.** Angular catalog rendering, isolated form state, action dispatch boundaries and conflict-aware refresh are reusable with adaptation. LangGraph checkpoint/resume semantics are not drop-in for Claude SDK/vendor CLI sessions. Keep Ptah’s stricter validation and existing markdown sanitizer; property-hub is not a stronger validation reference (§5–6).

Evidence convention: unless prefixed **Ptah**, every `apps/...`, `libs/...`, `docker/...`, `package.json` or `package-lock.json` citation below is relative to **`D:\projects\property-hub`**. Line ranges identify the inspected excerpts. Ptah plan citations refer to `.ptah/specs/TASK_2026_494_ca38/implementation-plan.md` in the requested worktree. This is a source inspection, not a running-system or penetration test; declared package ranges are distinguished from lockfile resolutions.

## 2. Exact agent-to-UI rendering mechanism

The implemented flow is:

```text
deepagents tool invocation
  -> config.configurable.a2uiEmitter(envelope)
  -> AgentService per-run queue
  -> custom SSE { type: 'a2ui', seq, payload, agent? }
  -> Angular AgentChatStore surface event/upsert
  -> ProEstateCatalog[type]
  -> NgComponentOutlet with { data: surfaceData }
  -> compiled domain component OR recursive UiNodeComponent
```

1. **Explicit generative UI tool:** `buildEmitUiTool()` registers `emit_ui`. It accepts an object or JSON string, normalizes it, invokes `a2uiEmitter`, and returns `{ emitted: true, surface: envelope }`. Evidence: `libs/api/ai-agent/src/lib/tools/core.tools.ts:206–238,260–264`. Its description names domain components and a generic `Ui` root (`:247–255`). This is a LangChain structured tool, not the Ptah MCP tool.
2. **Automatic business-tool surfaces:** `list_properties` searches server data and emits `PropertyGrid` with a stable `properties-surface` ID (`libs/api/ai-agent/src/lib/tools/properties.tools.ts:120–151`). Dashboard analytics emits `KpiRow` with `dashboard-kpi` (`libs/api/ai-agent/src/lib/tools/analytics.tools.ts:25–51`). Consequently, not every rendered component needs a separate model call to `emit_ui`.
3. **Custom event bridge:** `AgentService` injects emitter callbacks (`libs/api/ai-agent/src/lib/agent.service.ts:1659–1668`), consumes LangGraph `streamEvents({ messages }, { version: 'v2', ... })` (`:1687–1697`), and flushes UI payloads into custom SSE events (`:1123–1158`). The HTTP writer serializes `event: ${event.type}` plus JSON `data:` (`libs/api/ai-agent/src/lib/agent.controller.ts:116`). This is server-side projection of graph events, not direct graph-state subscription.
4. **Catalog rendering:** `ProEstateCatalog.components` contains 13 entries, including `PropertyGrid`, `LeadTable`, `KpiRow`, `InsightsChart`, kanbans, and `Ui` (`libs/admin/feature-ai-agent/src/lib/catalog/pro-estate-catalog.ts:31–45`). The bubble resolves a type and supplies only its `data` input to `NgComponentOutlet`; otherwise it displays the type label (`libs/admin/feature-ai-agent/src/lib/message-bubble/message-bubble.component.ts:114–123,151–152`). The model supplies data; it does not supply Angular classes/templates or executable components.
5. **Primitive composition:** `UiSurfaceComponent` extracts `data.root` and delegates to `UiNodeComponent` (`libs/shared/client/agent-chat-ui/src/lib/primitives/ui-surface.component.ts:20–43`). The recursive switch renders layout/content/input nodes: Stack, Grid, Card, Section, Divider, Text, Heading, Stat, Field, Badge, Image, Button, Table, Input, Select, RadioGroup and Checkbox (`libs/shared/contracts/agent/src/lib/ui-node.types.ts:48–68`; recursion at `libs/shared/client/agent-chat-ui/src/lib/primitives/ui-node.component.ts:54–65`). This is substantially broader than Ptah’s five data-display kinds. `InsightsChart` is a small CSS bar chart, not a full chart engine (`libs/admin/feature-ai-agent/src/lib/catalog/insights-chart/insights-chart.component.ts:9–35`).

**Tool-call → component mapping nuance:** there is also an optional `AGENT_TOOL_RENDERERS` injection token (`libs/shared/client/agent-chat-ui/src/lib/tool-renderers.tokens.ts:21–23`). `ToolOutputComponent` looks up the raw tool name and otherwise falls back to JSON, sanitized markdown, or interpolated text (`src/lib/molecules/tool-output.component.ts:54–64,78–94`). The source search found no actual app provider for that token. Treat this as an extension seam, not proof of a populated CopilotKit-style tool renderer registry. The active rich-surface path is the emitted surface-type catalog above.

## 3. Shared state and both communication directions

### Agent → frontend: projected events and surface replacements

`AgentChatStore` is an NgRx signal store (`libs/admin/feature-ai-agent/src/lib/stores/agent-chat.store.ts:5,331–371`). Its `a2ui` handler accepts `type`/`component`, normalizes kebab-case names, and derives `surfaceData`. An explicit repeated `surfaceId` replaces that surface **within the current turn’s event list**, preserving its original position; otherwise a per-emission ID creates another surface (`:735–790`). This is a complete surface-data replacement, not JSON Patch, a field delta, or general two-way data binding. It also is not necessarily a cross-turn persistent dashboard object.

LangGraph’s actual thread state remains server-side in `PostgresSaver`, initialized in schema `agent` (`libs/api/ai-agent/src/lib/checkpointer/pg-checkpointer.service.ts:125–134`). The service passes a thread ID and message input to the graph; on continuation it adds only the new user message and relies on checkpoints for history (`libs/api/ai-agent/src/lib/agent.service.ts:1659–1694`). The frontend receives text/tool/surface/metrics/HITL events, not a serialized copy of all graph channels (`libs/admin/feature-ai-agent/src/lib/services/agent-api.service.ts:171–198`). `__interrupt__` is a specific channel the server extracts (§4).

Conversation display persistence is separate: Prisma stores assistant content plus ordered `events`, legacy tool traces and surfaces (`libs/api/ai-agent/src/lib/conversation-store.service.ts:200–223`) and reconstructs transcript rows (`:305–324`). A detached run manager buffers and replays the current run, then tails live events (`libs/api/ai-agent/src/lib/agent-run-manager.service.ts:92–103,138–163`). Angular reconnects through `GET /agent/threads/:id/stream` (`libs/admin/feature-ai-agent/src/lib/services/agent-api.service.ts:265–270`). This is event replay plus transcript loading, not a shared-state SDK. Runs are process-local; a redeploy falls back to persisted partial turns (`libs/api/ai-agent/src/lib/agent-run-manager.service.ts:4–14`).

### Frontend → agent: local state becomes explicit requests

- **Ordinary chat/context:** Angular sends `threadId`, `message`, optional `appContext` and attachments to `POST /agent/chat` (`libs/admin/feature-ai-agent/src/lib/services/agent-api.service.ts:214–227`). `AgentContextService` derives route/entity/language and a selected Studio page (`src/lib/services/agent-context.service.ts:29–68`); dispatch reads that context (`src/lib/stores/agent-chat.store.ts:952–956`). The server builds context into its system prompt (`libs/api/ai-agent/src/lib/agent.service.ts:2234–2257`). **Caveat:** the prompt is inserted only for a new thread (`:1671–1684`), so do not claim that every route change automatically updates model-visible context in an existing thread.
- **Inputs are local until submit:** each rendered `UiSurfaceComponent` provides its own `SurfaceFormStore` (`libs/shared/client/agent-chat-ui/src/lib/primitives/ui-surface.component.ts:16–18`). It holds Angular form controls and local validity signals (`surface-form.store.ts:47–78`); `snapshot()` reads values only when requested (`:151–175`). There is no per-keystroke transport here.
- **Button/tool/form actions start ordinary follow-up turns:** `UiAction` supports `navigate`, `tool`, `submit` (`libs/shared/contracts/agent/src/lib/ui-node.types.ts:14–36`). Submit merges field values over static arguments (`libs/shared/client/agent-chat-ui/src/lib/primitives/ui-node.component.ts:387–398`). The app provider routes navigation to Angular Router and forwards other actions to the store (`libs/admin/feature-ai-agent/src/lib/services/ui-actions.providers.ts:51–69`). The store checks streaming/pending-approval/read-only state and dispatches a new turn (`src/lib/stores/agent-chat.store.ts:1014–1036`). The message is literally `Submitted <tool>: <JSON>` (`libs/shared/client/agent-chat-ui/src/lib/primitives/ui-action.format.ts:29–45`). **This requests a tool through the model; it does not directly execute a backend tool or resume a graph interrupt.** Tenant/SaaS providers wire the same formatter to their own chat stores (`libs/tenant/feature-sales-agent/src/lib/provide-tenant-sales-agent.ts:40–56`; SaaS equivalent `:52–68`).

### Agent → application commands and shared business data

`navigate_to` emits `client_action: navigate` through a second callback (`libs/api/ai-agent/src/lib/tools/core.tools.ts:275–289`). Angular dispatches registered names (`libs/admin/feature-ai-agent/src/lib/stores/agent-chat.store.ts:808–810`; `src/lib/services/client-tool-registry.service.ts:20–55`); the baseline handler invokes `Router.navigateByUrl` (`client-tools.providers.ts:22–25`). The registry returns `void`/`Promise<void>` and the store does not send its result back. This is a one-way command notification, not a frontend tool-result round trip. The server’s `{ navigated: true }` means the event was emitted, not that navigation completed successfully.

There is also genuine **shared persistent business data**: `update_page` writes through the page service and emits `refresh_page_preview` (`libs/api/ai-agent/src/lib/tools/pages.tools.ts:361–376`, envelope at `:70–75`). The page-builder listener checks the target page, reloads metadata, and reloads sections only when no local edits/save/open form exist; otherwise it offers a user-triggered reload (`libs/admin/shared-page-builder/src/lib/page-builder-wrapper/page-builder-wrapper.component.ts:491–524`). This is server-authoritative data plus invalidation/refetch and explicit conflict handling. It is not automatic graph-state/UI-state merging.

## 4. Human-in-the-loop approvals, interrupts and questions

1. **Backend gates named tools.** `HITL_TOOL_CONFIG` marks sending messages, publishing/scheduling, deletes, assignments and other mutations (`libs/api/ai-agent/src/lib/agent.constants.ts:16–69`). `createDeepAgent` receives this through `interruptOn` alongside the checkpointer (`libs/api/ai-agent/src/lib/agent.service.ts:694–695,942–945`). Tools absent from the map are not automatically gated (`agent.constants.ts:14`).
2. **Graph interrupt becomes UI event.** The service extracts `__interrupt__` from graph stream chunks or final outputs, normalizes `actionRequests` and `reviewConfigs`, and emits one `hitl` event per run (`libs/api/ai-agent/src/lib/agent.service.ts:386–428,1176–1185`). Angular records `pendingHitl` (`libs/admin/feature-ai-agent/src/lib/stores/agent-chat.store.ts:812–815`).
3. **The card asks for a decision.** It shows tool names/arguments, approve/reject buttons and a custom text response (`libs/admin/feature-ai-agent/src/lib/hitl-card/hitl-card.component.ts:24–68`). It emits the same selected decision for each interrupt in the batch; custom guidance is a rejection with a message (`:104–118`). Backend DTOs also accept `edit` with an edited action (`libs/api/ai-agent/src/lib/dto/resume.dto.ts:15–54`), but the inspected card does not expose an argument-editing UI. Protocol capability and shipped UI differ.
4. **Resume is a separate operation.** Angular calls `POST /agent/threads/:id/resume` (`libs/admin/feature-ai-agent/src/lib/services/agent-api.service.ts:260–261`); the service supplies `new Command({ resume: { decisions } })` with the same org/user/thread identity (`libs/api/ai-agent/src/lib/agent.service.ts:2013–2039`). This continues a suspended graph operation, unlike a form submission or normal chat message.

**Questions:** ordinary questions can be answered in chat, and generated Input/Select/RadioGroup/Checkbox forms can collect structured answers through the submit path (§3). No dedicated `ask_user`/`ask_question` tool or standalone question-interrupt implementation was found in the inspected staff/tenant/SaaS tool sources. The concrete interrupt path found is approval review; do not equate every interactive form with a suspended agent waiting on `Command.resume`.

## 6. What transfers to Ptah and why the smaller scope is reasonable

**Portable as is — the design principles, not the complete feature code:** a fixed compiled component catalog; data instead of executable UI; separate local form/view state; a single markdown sanitizer; and treating user action arguments as untrusted input. These do not depend on HTTP or LangGraph. property-hub demonstrates them in `pro-estate-catalog.ts:31–45`, `surface-form.store.ts:47–78,158–175`, `ui-action.format.ts:6–10,29–45`, and `provide-agent-markdown.ts:24–57` under the full paths cited above. Its sanitizer even documents that it was adapted from Ptah (`libs/shared/client/agent-chat-ui/src/lib/markdown/provide-agent-markdown.ts:22`). No entire property-hub Angular/backend library is a drop-in Ptah dependency.

**Portable with adaptation:**

- **Angular catalog/presentation:** use Ptah package boundaries, Native UI primitives and daisyUI tokens, keeping transport out of the renderer. Angular is not an obstacle. property-hub has Angular 21/Tailwind 4/daisyUI 5, whereas Ptah’s supplied constraints differ; adapt imports/styles/contracts rather than copying components wholesale. Preserve Ptah’s five-kind schema and bounds initially. Source pattern: `libs/shared/client/agent-chat-ui/src/lib/primitives/ui-node.component.ts:54–164`. Ptah plan `:557–598` already specifies the corresponding controlled renderer.
- **Form/button follow-ups, if later required:** introduce a versioned, bounded action schema and host-owned capability mapping, bind actions to session/spec/revision/component, and send validated user intent through the existing chat continuation path. Use a separate explicit submit action to start a turn. property-hub’s immediate `dispatchUserTurn` (`libs/admin/feature-ai-agent/src/lib/stores/agent-chat.store.ts:1014–1036`) demonstrates the behavior, but copying its arbitrary `Submitted <tool>` text loses Ptah’s stronger host-owned selection semantics. This would be a scope change, not merely another catalog component.
- **Application commands/invalidation:** the named client-action registry and dirty-editor protection can be adapted to IPC pushes with host/renderer allowlists and correlation IDs. Source: `libs/api/ai-agent/src/lib/tools/pages.tools.ts:70–75,361–376`; `libs/admin/shared-page-builder/src/lib/page-builder-wrapper/page-builder-wrapper.component.ts:491–524`. Add acknowledgements/idempotency if command completion matters: the current property-hub channel has no result acknowledgement and buffered events replay on reconnect (`agent-run-manager.service.ts:142–144`).
- **UI replay/persistence:** surface IDs and ordered event projections are reusable ideas, but storage/lifetime and replay semantics must fit Ptah’s existing session router. property-hub uses Prisma plus process-local run buffers (§3); Ptah currently plans root service slices and a 16-session in-memory host store, without restart persistence (plan `:691–694`).
- **Approval presentation:** reuse the idea of rendering a pending operation and collecting a typed decision, but route it to Ptah’s existing provider permission/question mechanisms. The plan already reuses `PermissionRequestCardComponent` and `QuestionCardComponent` (plan `:69`). Dashboard selection is not an approval channel.

**Not portable because the runtime contract differs:** `PostgresSaver`, `__interrupt__` extraction and `Command({ resume })` require a LangGraph execution/checkpoint model (`libs/api/ai-agent/src/lib/agent.service.ts:386–428,2013–2039`). Claude Agent SDK/vendor CLIs do not become LangGraph graphs by adopting an event schema. Each provider’s actual pause/resume/tool-result capability would need an adapter. Likewise, the fetch/Bearer SSE implementation (`libs/admin/feature-ai-agent/src/lib/services/agent-api.service.ts:504–549`) is not Ptah’s IPC transport. Introducing CopilotKit/AG-UI would be a separate integration decision; property-hub supplies no working example of that adoption.

**Why TASK_2026_494 is smaller:** its promised interaction is “show this dashboard, let me inspect it, then discuss the selected data.” D3 claims one Apps session and re-validates incoming spec pushes; D4 stores the delivered spec on the host, checks selection identity/revision/indexes, and injects host-resolved selection context into the next surface-mode turn. A selection RPC never calls the model, and filters/sort/paging remain local (Ptah plan `:143–208,674–699`). This is already a narrow shared-state contract. It avoids the additional questions property-hub’s broader feature must answer: when a button starts a turn, which commands are permitted, what happens during an approval, whether local edits survive replacements, and how replayed commands behave. The smaller path is justified for that interaction. If the requirement becomes agent-built forms/workflows or live editing of application data, selection-only will be insufficient and should be extended deliberately.

**Correction to the older Ptah decision table:** TASK_2026_490’s `research-report.md:18,31` cites Angular 22 as a CopilotKit blocker while describing Ptah as Angular 21. The inspected worktree’s `package.json:93` now declares **Angular 22.1.7** (`:101` declares Claude Agent SDK **0.3.278**). That version mismatch is stale. The old report’s sanitizer/custom-transport/licensing assertions (`:32–35`) are historical research, not independently reverified current facts here. They should not be presented as fresh external-product evidence. The source-backed reasons for the smaller Apps scope remain transport/runtime fit, its explicit interaction contract, and Ptah’s security boundaries.
