# Code logic review: `0ce422101`

**Verdict: REVISE.** The commit fixes the earlier active-only lookup for settled workspace state, and the queue refactor preserves its intended paths. The running cap still has a persistent stale-count case for hidden sessions.

## Findings

### Moderate — a finished hidden turn can leave the cap disabled indefinitely

`libs/frontend/canvas/src/lib/canvas.store.ts:152-184` reads hidden tabs with `getWorkspaceTabs(path)`, but that map is not a signal. `libs/frontend/chat-state/src/lib/tab-workspace-partition.service.ts:372-400` changes a hidden tab's `status` in place without touching a signal. When nine canvas sessions are running across two workspaces, one plain turn in the hidden workspace can finish while the user stays in the current workspace. The computed retains nine, so `canStartRunningSession` remains false and the New Session button remains disabled. It releases the slot only after a dependency of this computed changes: active `tabs()`, canvas `_workspaceTiles` or `_activeWorkspacePath`, or `agentMonitor.agents()` / `subagents()` (`canvas.store.ts:157-180`). A plain hidden turn need not change any of those. With no later such change, the button stays disabled indefinitely. This is the limitation recorded in `decisions.md:24`; a reactive partition revision or status signal is needed to close it.

### Minor — switch order permits a transient undercount

`libs/frontend/chat/src/lib/services/workspace-coordinator.service.ts:177-183` switches TabManager first. `libs/frontend/chat-state/src/lib/tab-manager.service.ts:773-785` then publishes the new tabs; the canvas path changes later through an Angular effect (`libs/frontend/canvas/src/lib/orchestra-canvas.component.ts:479-484`). During that interval, `canvas.store.ts:157-167` sees the old canvas path as active but reads the new workspace's live tabs for its tiles. It also queries the new path through `getWorkspaceTabs`, which correctly returns the live list via `tab-workspace-partition.service.ts:239-243`. Thus old workspace tiles can be missed if the cap is read before the effect flushes. The canvas path signal change triggers a recount, so this is a transient window rather than a stable wrong count. Selecting tabs by TabManager's authoritative active path would remove the mismatch.

## Requested checks

- **Keys and active copy:** Canvas keys are workspace paths, with `''` only as an implicit pre-workspace sentinel (`canvas.store.ts:62-67,99-108,432-462`). Partition keys are the same supplied paths (`tab-workspace-partition.service.ts:193-226`); it has no `''` partition for the initial null state. The implicit canvas entry is active before the first real path and therefore reads `tabs()` (`canvas.store.ts:157-164`). On the first real switch, its tiles migrate to that path (`canvas.store.ts:440-461`). For normal paths, the active branch reads live `tabs()` and hidden paths read the partition. The temporary disagreement during a switch is described above. `getWorkspaceTabs` itself has an active-workspace fast path, so a newly active path requested as “hidden” still returns live tabs (`tab-manager.service.ts:810-815`, `tab-workspace-partition.service.ts:239-243`).
- **Stale active map:** The partition saves the old active list on a switch (`tab-workspace-partition.service.ts:198-205`), while ordinary active tab updates use TabManager's `_tabs` signal (`tab-manager.service.ts:1332-1375`). The map can lag while active. The new code avoids that copy when CanvasStore and TabManager agree on the active path (`canvas.store.ts:157-164`).
- **Duplicates and closed tabs:** `byId` keeps one entry per tab ID (`canvas.store.ts:159-170`), and `countRunningSessions` further deduplicates by `claudeSessionId ?? tab.id` (`canvas-running-cap.ts:22-32`). A duplicate tab ID across workspaces is therefore counted once even if it represents two independent tabs; normally new tabs receive generated IDs (`tab-manager.service.ts:865-867,3024-3026`). A tile for a closed tab with no matching tab is ignored by the lookup (`canvas.store.ts:165-167`). Active closes are pruned by `orchestra-canvas.component.ts:491-505`; background closes are pruned by its close listener at lines 507-517. A stale tile alone cannot inflate the count.
- **Queue release:** A skipped lane post now calls `releaseAnswer`, exactly matching the prior removal (`canvas-needs-you-queue.component.ts:161-168,185-191`). The missing session request branch now releases the key (`:169-177`), fixing its previous stuck buttons. A thrown error still releases the key and rethrows (`:179-181`). The normal posted/request-found paths still wait for the item to disappear, when `clearAnsweredItems` removes the key (`:143-150`).
