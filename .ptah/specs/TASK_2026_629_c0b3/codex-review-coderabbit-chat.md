# PR #730 CodeRabbit chat fixes: code logic review

Review family: codex reviewing Claude

Score: **5/10**. Verdict: **REVISE**. One Blocking and one Serious finding. The tab-switch, marker-retention, turn-key, display, normalization, popover, and timeout fixes follow their intended paths, but the send path still has user-visible data loss and duplicate dispatch. These separate the result from a sound 7–8; the bounded, working fixes separate it from a foundational 3–4.

## Findings

1. **Blocking — a rejected send deletes the submitted draft.** `libs/frontend/chat/src/lib/components/molecules/chat-input/chat-input.component.ts:1497-1512` awaits `sendOrQueueMessage` but ignores its `SendOutcome`, then clears the stored draft; `:1513-1526` clears the visible draft. `libs/frontend/chat/src/lib/services/chat-store/message-dispatch.service.ts:155-160` returns `{ success: false }` synchronously for an unavailable slash command, and `:202-206` propagates an unsuccessful sender outcome. For either path the composer shows a successful-looking reset even though nothing was sent; on a tab switch the sending tab's saved draft is lost. Require `outcome.success` before either clear and cover both rejection paths in the composer spec. The current tab-switch spec only mocks a successful, `undefined` outcome (`chat-input.component.spec.ts:339-353`).

2. **Serious — two Send actions can dispatch the same draft.** `libs/frontend/chat/src/lib/components/molecules/chat-input/chat-input.component.ts:1471-1497` has no pending-send guard, and the draft remains visible and `canSend()` remains true until the await settles (`:1504-1526`). The button and Enter handler both call `handleSend` (`:404`, `:1463`). A double click, or Enter followed by a click while the first send is pending, calls `sendOrQueueMessage` twice with the same content. The new reference comparison determines what to clear after completion but cannot prevent the second dispatch. Add a per-composer or per-tab in-flight guard that still permits a distinct queued follow-up during streaming, and test two overlapping calls.

## Focus checks

- **Tab switch and queue:** `chat-input.component.ts:1483-1489` captures the sending tab and draft before the await; `:1507-1526` limits clearing by tab and draft identity. `ComposerDraftStore` stores the same array references (`composer-draft.store.ts:27-39`), so the new comparison protects B's restored draft and an edited A draft. The dispatcher resolves its target before its own await and returns success for queueing (`message-dispatch.service.ts:162-202`). Findings 1–2 limit the send-path verdict.
- **TodoWrite:** `chat-types.ts:312-356` records the current top-level write and retains parsed streamed input; `:473-485` captures it before accumulator deletion. `compact-session-metrics.ts:110-127` reads the marker before finalized messages and uses the retained input when the live source is absent. `chat-streaming/src/lib/accumulator-core.service.ts:574-575` copies the marker through compaction. This preserves BM-design §2a rule 1: a marker with unavailable input yields `unknown`, never an older finalized list. Whole `libs/frontend` search found the writer, this reader, the compaction copy, and tests; the scoped chat-streaming typecheck passed.
- **Turn identity:** `display-dock.state.ts:119-137` selects the same map key for the summary and turn identity. The dock passes it through `display-dock.component.ts:97,139-141` and `display-panel.component.ts:226,264` to the required input in `turn-summary.component.ts:384`. Disclosure signals depend on that key (`turn-summary.component.ts:417-433`), so another file-less turn resets them and adding a test run to the same turn preserves them. The panel's default empty key applies to other panel hosts, not the dock.
- **Other fixes:** `compact-rail-card.component.ts:159-162` draws an inset host ring when the transparent select button has keyboard focus; `:384,461-463` rounds the context percentage. `workspace-root.ts:2-5` folds drive-root case after trimming its slash. `native-popover.component.ts:260-266` logs the caught positioning rejection in dev mode before returning the failed outcome. `git-history.reader.real-git.spec.ts:109-112` sets 30 seconds for the real-git suite.

## Five failure questions

1. **Silent success:** an explicit unsuccessful `SendOutcome` is discarded and the draft is cleared (finding 1).
2. **User action:** double-click Send or press Enter and click while the first send is pending (finding 2).
3. **Wrong answer from data:** the previous draft clear could erase another tab's text; the new captured tab and identity comparison prevent that path (`chat-input.component.ts:1483-1526`). A current TodoWrite marker prevents an older finalized list from reappearing (`compact-session-metrics.ts:110-127`).
4. **Dependency failure or timeout:** a rejected positioning promise produces a logged dev-mode cause and a failed outcome (`native-popover.component.ts:260-266`). A sender rejection represented as `{ success: false }` remains destructive (finding 1); a thrown sender error is logged and leaves the draft (`chat-input.component.ts:1530-1532`).
5. **Unspecified case:** overlapping send attempts need an ownership rule for the pending draft and for a genuinely new follow-up (finding 2).
