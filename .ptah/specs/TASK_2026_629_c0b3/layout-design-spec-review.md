# Rail layout design review

**Part A verdict: REVISE — 5/10.** The fixed-card and stable-order model follows decisions 43–44, but the prototype has keyboard and narrow-width defects, and the spec leaves six inventory capabilities and several implementation seams unresolved. This is a design review; no app implementation or runtime verification is claimed.

## Findings

1. **Serious — parity table stops six rows early.** `layout-design-spec.md:162-203` claims rows 1–38 and `:219-220` claims full parity, while `parity-inventory-layout.md:57-62` has rows **39–44**. Add explicit destinations and contracts: 39 BL node/injector release (Grid engine release; Rail component/injector release), 40 one `buildTree` per published snapshot (focused live view), 41 render metrics (board host in both modes), 42 dock ticker/header/empty state (shared dock plus Rail zero state), 43 card keyboard/click/text-selection semantics (Rail card), 44 workspace prune/cross-workspace close (both modes). Row 43 is also wrongly implemented in the prototype (finding 2); row 39 must not be translated into a promise about Gridstack nodes in Rail.

2. **Serious — rail lane rows cannot be reached by keyboard.** `layout-design-spec.md:132-135` promises Tab to lane buttons; prototype `02-focus-rail.html:305-307` renders each lane action as `<li class="lr" data-act="lane">` without button, `tabindex`, or key handler; `:483-488` handles only the card select button. `patchCard` sets tabindex on `button` elements only (`:338`). A keyboard user cannot open a lane from a card. Use a real button within each list item and keep the roving focus order specified in section 5.

3. **Serious — card text selection regresses F6.** Prototype `.rc-select` covers the whole card (`02-focus-rail.html:74`), `.rc-body` has `pointer-events:none` (`:76`), and click without an action focuses the card (`:473-475`). Unlike the current tile's text-selection guard (`canvas-tile.component.ts:692-727`, parity row 43), selecting a title or permission command is unavailable or activates selection. Preserve selectable text and ignore an active text selection before focusing.

4. **Serious — state chips exceed the fixed 72 px header.** `layout-design-spec.md:31-32,78-82` requires up to five jump chips; prototype `.rail-head` is fixed to 72 px with two 28 px rows and `.chips` has no bounded overflow (`02-focus-rail.html:48,52-55,354-360`). In `rail-dark-9.png` and `rail-light-9.png` the chip labels wrap across rows and overlap the cards; `rail-dark-12-perm.png` adds an Idle chip and worsens it. Provide a single-line scroll/overflow strategy or a compact count menu without increasing rail-header height on state changes.

5. **Moderate — the fixed metric slots hide a required value at 920 px.** The design promises git `+a -d` and no horizontal scroll (`layout-design-spec.md:43-50`), but `.rc-foot` uses `1.3fr .8fr .8fr 1fr` with clipped spans (`02-focus-rail.html:100-101`). `rail-dark-920.png` displays `+176 −…`, so deletions are unavailable without a hover title; the 920 px focus-header “Compact view” also wraps to two lines (`rail-dark-920.png`, `.focus-h` at `02-focus-rail.html:119`). Reserve enough width for both signs and values or provide an accessible expansion; keep header controls one line or specify a narrow-width fallback.

6. **Serious — persistence and mode switching need a new contract, not only a field name.** `layout-design-spec.md:184,205-215,235` promises workspace-specific `boardMode`, `railCollapsed`, scroll restoration and untouched Grid geometry. Current persistence accepts only versions 1/2 and writes `version:2` tile records (`canvas-layout-persistence.service.ts:29-51,179-209,265-283`), while the store keeps only per-workspace tile/focus state (`canvas.store.ts:116-151,261`). Define a v3 read/write/migration policy, default Rail for old records, preservation of Grid tile intent, forward-version read-only behavior, and no write before hydration. Without that, a switch/reload can silently revert the mode or lose Grid positions.

7. **Serious — one live view and selected lane cannot be assumed from today's detail service.** The spec says one mounted focus view, per-session lane choice and hidden workspace pause (`layout-design-spec.md:90-102,121,182-183,211-215`). Today each retained workspace keeps a mounted grid (`orchestra-canvas.component.ts:232-251`); the grid mounts tiles via `@for` (`canvas-workspace-grid.component.ts:111-138`) and the detail service has one `_laneKey`, reset on close, rather than a per-tab map (`canvas-detail.service.ts:9-41`). Rail needs a mode-aware mount boundary, exactly one active `ChatViewComponent`/lane panel, `SURFACE_ACTIVE`/`SESSION_FOCUSED` gating for retained workspaces, lane selection keyed by tab, and injector cleanup on swaps. Draft persistence is feasible because `ComposerDraftStore` is root-scoped, keyed by tab id and cleared on tab close (`composer-draft.store.ts:19-51`), but it does not itself prove the new mount/unmount sequence saves the current input before switching. Verify this seam with real component state.

8. **Moderate — the no-shift claim needs a precise boundary.** Stable oldest-first append, repaint in fixed 176 px slots, permission replacement, cap-state text and explicit close behavior satisfy decisions 43–44 in the model (`layout-design-spec.md:64-82`, `02-focus-rail.html:64-76,341-349`). `layout-design-spec.md:74` expressly permits geometry changes on window/canvas resize and details toggle; `:14-27` changes rail/details widths at breakpoints and auto-collapses the rail when the details strip opens. This is acceptable as responsive/user geometry, but state it as “card order and height stay fixed; slot widths change at breakpoints/panel toggles,” and verify the focused card/scroll anchor after a side panel opens. The prototype's zero “slot moves” counter (`layout-design-spec.md:85-86`) resets its baseline on a rail toggle (`02-focus-rail.html:498-500`), so it is not evidence of no geometry movement across that action.

9. **Moderate — a stale callout can remain actionable.** Prototype `patchCard` skips replacing `.rc-body` while an inner control has focus or is being pressed (`02-focus-rail.html:333-338`), while `renderRail` still updates chips and meter (`:341-360`). If a permission resolves from the queue while the user has focused its Allow button, the card can continue to offer Allow/Deny after the request is gone. Reconcile the card on external resolution while restoring focus to a surviving control and prevent duplicate actions. The real queue needs the same state-driven update path.

10. **Moderate — theme measurements are prototype-specific.** `layout-design-spec.md:143-160` reports acceptable prototype text/UI ratios and explicitly defers Electron measurement. Prototype dark surfaces `shared.css:3-11` (`#141417/#1a1a1e/#222227`) differ from real `anubis` `base-100/200/300` (`#131317/#1a1a20/#242430`, `tailwind.config.js:97-105`); prototype light surfaces (`02-focus-rail.html:12-18`) are hex approximations, while real `anubis-light` uses OKLCH values (`tailwind.config.js:165-170`). `styles.css:368` is only a light-theme override, not the source of all base tokens. The stated 4.8–5.0 ratios therefore do **not** establish AA for actual DaisyUI surfaces; remeasure on the real computed tokens, including callouts, status labels and focus ring, in both themes.

## Feasibility and failure-mode answers

- **Data path:** the smart card already derives branch, elapsed, context, todos and git from tab/monitor/stream stores (`compact-session-card.component.ts:142-160,232-268,304-350`), and supplies the presentational activity component (`:91-99`). Reuse those sources for Rail; do not copy prototype sample values (`02-focus-rail.html:299-314`). Lane tabs and output components already exist (`canvas-lane-tabs.component.ts:78-154`, `canvas-lane-view.component.ts:194-195`), but need a Rail host. Running cap is 9 across canvas tabs/workspaces (`canvas.store.ts:176-215`, `canvas-running-cap.ts:6`); hard tile bound is 20, separate from running cap (`task-description.md:41`, spec `:46-49,112-114`).
- **Silent success:** `patchCard` can leave a resolved permission visible (finding 9); a mode stored only in memory would look switched until reload (finding 6).
- **Unexpected user action:** keyboard Tab cannot open a card lane (finding 2); text selection activates/fails (finding 3).
- **Wrong answer from input:** five nonempty status groups overflow the rail header (finding 4); three-digit git counts lose deletions at 920 px (finding 5).
- **Dependency failure/timeout/wrong shape:** Rail must retain existing permission and git unknown/error states, cap guard, and per-tile cleanup rather than treating missing data as success (`compact-session-metrics.ts:11-29,47-65`; `canvas-tile.component.ts:662-665`). The spec does not describe how a failed layout write is surfaced or how a lane disappears while selected (finding 6/7).
- **Missing from requirements:** parity rows 39–44, per-session lane state, and exact switch/hydration lifecycle (findings 1,6,7).

## Open questions: settled by evidence

- **Q1:** stable oldest-first only. Decisions 43–44 demand stable slots, and `layout-design-spec.md:78-83,227,233` already chooses append without regrouping. A sort-by-state toggle would intentionally move slots and is a later option.
- **Q3:** Esc returns keyboard focus to the selected rail card after the queue closes; it must not change session selection or geometry. This follows the existing detail-key behavior and the spec's keyboard path (`layout-design-spec.md:132-141,189`).
- **Q6:** remeasurement on real `anubis`/`anubis-light` tokens is required before implementation acceptance, because the prototype ratios are not real-token ratios (finding 10). No separate product preference is needed.

## Open questions: for the user

- **Q2:** whether a second dense 96 px card mode at 12+ sessions is desired. The fixed 176 px card scrolls predictably (`layout-design-spec.md:46-49,111-113`); no evidence requires another density now. Recommend ship one density and measure use.
- **Q4:** placement of Send to messaging in the focus header. The capability must remain (parity row 34, `layout-design-spec.md:199`); an overflow item is the spec's recommended placement, but the current prototype focus header has no such control (`02-focus-rail.html:388-394`).
- **Q5:** whether to add a direct close control on non-focused cards. The current selected-session close in the focus header covers parity row 33 (`layout-design-spec.md:198,246-247`); direct close is a product preference. Recommend defer.

## Part B — cb00c04fb todo title

**Verdict: APPROVED with a semantic caveat.** The changed branch is `kind:'none'`, the result when no usable `TodoWrite` event was found (`compact-session-metrics.ts:126-133`), so “Todos not reported by this session” is the honest label for the observed Claude sessions; `kind:'unknown'` means compaction or unparseable input (`:84-86,128`) and remains “Todos unknown” (`:47-52`). Both card tooltip and canvas details use the exported `todoTitle` (`compact-session-activity.component.ts:801-806,853`; `canvas-session-details.component.ts:67,135`). Caveat: an explicit empty `TodoWrite` also maps to `none` (`compact-session-metrics.ts:84-86`), so that tooltip says “not reported” even when an empty list was reported. If explicit empty-list semantics matter, separate that state; this does not undo the user decision for sessions without `TodoWrite`.

**Review limits:** read-only review of the supplied docs, prototype, screenshots, relevant component/service paths and commit diff. No tests, builds, installs or app run were performed, as requested. Existing final-run checks in `decisions.md:50` cover the prior Grid/card implementation, not Rail.
