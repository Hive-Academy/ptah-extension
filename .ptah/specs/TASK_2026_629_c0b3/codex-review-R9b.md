# R9b code logic review

Review family: codex (implementer: Claude)  
Score: 6/10  
Verdict: REVISE

The named-session happy path is wired from the Rail footer and zero-tile board through `newSessionRequested` to the host popover (`canvas-rail-board.component.ts:69,99,370-377`; `orchestra-canvas.component.ts:138-224,237-243,563-595`). A live-cap change during that flow still leaves stale open state. That observed path separates this from a 7-8 review; the working typed/default-name and cap/null-add branches, with writer-reported 14/14, 30/30 and 26/26 named specs, separate it from a 3-4 review.

## Findings

1. **Serious — Popover silently reopens after the board temporarily reaches its tile bound.** `libs/frontend/canvas/src/lib/orchestra-canvas.component.ts:138,306,563-570,579-595`; `libs/frontend/ui/src/lib/native/popover/native-popover.component.ts:172-180,236-241`. Open the naming popover, type a name, then let a queued/adopted session occupy the final tile before Create. The `@if (canAddTile())` destroys the popover, but neither the host's `sessionPopoverOpen` nor its typed name is cleared; the native component's destroy handler does not emit `closed`. When a tile is later closed, the popover mounts again with `isOpen=true` and stale text, without a fresh New session action. **Fix:** close and clear host popover state when `canAddTile` becomes false, or keep the popover mounted and show a guarded refusal. Add a spec that changes `canAddTile` true → false → true while the popover is open.

2. **Moderate — The empty-board control claims to be disabled but still activates.** `libs/frontend/canvas/src/lib/canvas-rail/canvas-rail-board.component.ts:92-109,211-213,370-372`. At the running cap, the button exposes `aria-disabled="true"` but its click always emits a creation request; the host then announces a refusal in the dock (`orchestra-canvas.component.ts:563-567`). This does not add a tile, but a keyboard or pointer user can activate a control presented as unavailable, and the live response is away from the focused control. **Fix:** either truly suppress activation while disabled and keep its local reason, or leave it semantically enabled and announce the refused action in the board's existing live region at `canvas-rail-board.component.ts:166`. The current test at `canvas-rail-board.component.spec.ts:530-550` codifies the mismatch.

## Decisions

- **Protected display dock is an outstanding cross-batch release dependency, not introduced by R9b.** The Rail focus area mounts the transcript (`canvas-rail-board.component.ts:112-119`; `canvas-lane-view.component.ts:118`), and that transcript still sets `HIDE_AGENT_SIDEBAR: true` (`canvas-detail-transcript.component.ts:46-57`). ChatView creates its dock only when that token is false (`chat-view.component.ts:237-250`). This violates decision 77 for the current Rail experience. The plan explicitly assigns removal of this provider to R9f (`implementation-plan-rail-r9.md:100`); do not treat R9b's Grid-host removal as completing protected-dock restoration. Before release, verify the R9f fix and a fenced display update in the live Rail host.
- **Host-owned cap check is acceptable.** Board `newSession()` only emits (`canvas-rail-board.component.ts:364-372`); `createBlockReason()` checks running and tile caps before opening and again before adding (`orchestra-canvas.component.ts:563-567,579-607`). The footer also has a local presentation guard (`canvas-rail.component.ts:234-247`), but the host is the final gate.
- **The duplicated tile-bound message is maintenance risk, not a current logic defect.** Both strings match now (`orchestra-canvas.component.ts:38-39`; `canvas-rail.component.ts:23`). Sharing the constant in R9c would prevent drift.
- **Grid host removal and Rail layout dependency match this batch.** The host imports only `CanvasRailBoardComponent` and no Grid host controls (`orchestra-canvas.component.ts:27-36,70-77,237-243`); the Rail board still injects `CanvasLayoutService` and derives its width band (`canvas-rail-board.component.ts:20,176,210`). The deleted Grid detail spec's named-popover concern is covered at `orchestra-canvas.rail.spec.ts:315-418`. Parity rows 45, 46, 62 and 67 are represented by the Rail-only host and its empty-board route.
- **Writer's checks are evidence for the existing branches, with a limit.** `lane-R9b-report.md` records named spec passes (14/14, 30/30, 26/26), full canvas 421/421, canvas typecheck and lint. The tests do not change tile capacity while the popover is open (`orchestra-canvas.rail.spec.ts:315-418`); `sessionCreated` is a stub spy there (`orchestra-canvas.rail.spec.ts:120,347,362`), while the board spec spies on `anchor` (`canvas-rail-board.component.spec.ts:128,140-151`), so real post-add scroll remains unexercised. Scoped `ptah_get_diagnostics` returned unavailable after its 45-second compiler timeout; no independent suite was run.

## Five logic questions

1. **Silent failure:** capacity changing under an open popover removes it without clearing open state, then silently restores it later (`orchestra-canvas.component.ts:138,306,563-570`).
2. **Unexpected user action:** activating the empty-board button at the running cap triggers an event despite `aria-disabled` (`canvas-rail-board.component.ts:92-109,370-372`).
3. **Wrong answer from input data:** a whitespace-only name correctly falls back to `defaultSessionName()`; the real mismatch is stale typed input after a capacity transition (`orchestra-canvas.component.ts:584,569-570`). No separate wrong-data path was evidenced.
4. **Dependency failure/shape:** a null `addTile` is announced and does not focus a tile (`orchestra-canvas.component.ts:581-594`); an exception from `addTile` is not caught here, so the popover remains open and Angular handles the error (`orchestra-canvas.component.ts:579-586`). This is lower confidence because the current store only returns null at the cap (`canvas.store.ts:335-343`).
5. **Requirement gap:** the Cases list omits a cap transition while the naming popover is already open, and the protected dock still awaits R9f (`orchestra-canvas.component.ts:138,306`; `implementation-plan-rail-r9.md:100`).
