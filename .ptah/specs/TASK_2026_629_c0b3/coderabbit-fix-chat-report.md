## Decisions

- **4277283869: keep the todo data with the marker, not the message fallback.** The design (`BM-design.md` §2a rule 1) says "Never fall through to the finalized messages" when a marker exists. The existing specs pin that rule: "returns unknown for an evicted start…" and "does not resurrect an older finalized list after a live turn is compacted". So I took CodeRabbit's other option and kept the latest input with the marker. A write whose input never parsed still reports `unknown`, never a stale list. The input is captured on the write's `tool_result`. That event goes through `setStreamingEventCapped` after every `tool_delta` has been added to the accumulator (`accumulator-core.service.ts:408-416, 434`). So compaction keeps the input without any change to `chat-streaming`, which is outside my scope: its `fresh.latestTodoWrite = state.latestTodoWrite` copies the input as well.
- **4277283882:** the ring is inset (`-4px`). The parent `compact-session-card` host is `overflow-hidden` (`chat/.../compact-session-card.component.ts:112`), so an outer outline would be clipped. At `-4px` the ring sits just inside the 2 px focused frame (1 px border plus 1 px inset shadow), in the state ink, so it reads apart from the frame. The test inspects the inline CSS source, because jest-preset-angular strips component styles (existing pattern at spec `:59`).
- **4277283908:** the turn identity is the existing summaries-map key: the user message that opened the turn (`transcript-turn-summaries.ts:29-30, 182`). I did not add a field to `DisplayDockSummary`. That would have broken six spec literals outside scope. Instead, the key selection moved into `summaryKeyFor` with unchanged behaviour. `DisplayPanelComponent.summaryTurnKey` defaults to `''` so that existing panel hosts and specs that pass only `summary` keep working; the dock always passes the real key. The `display-dock.component.spec.ts` stub panel gained the `summaryTurnKey` input that the dock now binds.
- **4277283912:** the stored draft is compared as well, not only the visible composer. If the user switches away and back and edits during the send, the store holds the new edit, and an unconditional clear would lose it.
- **Regression proof:** each new test fails against the old code, by construction. Eviction or compaction gave `unknown`; there was no host `:has` rule; the card showed `37.41666%`; the run-derived key reset or merged turns; the composer was cleared unconditionally; the drive-root regex missed `C:`. I did not run the tests against reverted code: the brief forbids git state changes, and the lock allows one heavy check at a time.
- **Not run:** I did not run the `chat-streaming` specs that read `latestTodoWrite` (`latest-todo-write-marker.spec.ts`, `accumulator-core.service.spec.ts:909-916`). That project is not in scope. They use `toEqual({ toolCallId, timestamp })`, which ignores the new `input: undefined` property.
