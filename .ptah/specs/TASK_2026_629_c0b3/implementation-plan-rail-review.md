# Rail implementation plan — cross-side logic review

Scope: `implementation-plan-rail.md`, decisions 43–54, approved design including Dense mode, parity rows 1–44, and the cited pre-Rail code. No Rail implementation exists yet. No build or tests were run. `ptah_get_diagnostics` returned unchecked because its TypeScript check was still running.

## Findings

1. **Serious — Rail cards lose the question action.** The new Rail card declares `allow`, `deny`, `openRequest`, and `showOutput`, but no `answer` output or question-specific control (`implementation-plan-rail.md:458-465,473-485`). The existing card routes `answer` to the full session (`libs/frontend/chat/src/lib/components/molecules/compact-session/compact-session-card.component.ts:100-105`), and its view renders a question Answer control (`libs/frontend/chat-ui/src/lib/molecules/compact-session/compact-session-activity.component.ts:778-787`). A question can be the chosen callout (`compact-session-card.component.ts:180-187`), so switching the default board to Rail removes the card's direct answer route; parity row 28's queue test does not exercise it (`implementation-plan-rail.md:919`). Specify the Rail question control, bind it to the shown question id, select the orchestrator lane, and test replacement and keyboard use.

2. **Serious — the proposed error id is not an error-event identity.** D10 composes an id from `lastTurnStateRevision` and reason and assumes every new failure advances that revision (`implementation-plan-rail.md:381-386,950`). The current `StopFailure` path stamps `lastTerminalReason` without changing the revision (`libs/frontend/chat-state/src/lib/tab-manager.service.ts:2219-2226`); revision is changed by a separate backend `turn_state` handler (`:1498-1500`). Two equal-reason failures on that path can therefore share an id, so the keyed callout and shown-id guard cannot distinguish them. This leaves R2-1 unresolved for a real failure path. Use an identity advanced for every terminal failure, including StopFailure, and test two equal-text failures through that path. The absence of Retry itself is consistent with `task-description.md:82,140` and current `canRetry:false` (`compact-session-card.component.ts:215-221`).

3. **Moderate — lane summary equality can suppress a real row update.** The specified comparator checks row id, status, name and `endedAt`, but omits `startedAt` and `kind` (`implementation-plan-rail.md:372-375`). Both are fields in `CompactLaneRow` (`libs/frontend/chat-ui/src/lib/molecules/compact-session/compact-lane.types.ts:11-20`); the existing lane view derives elapsed time from `startedAt` (`compact-session-lanes.component.ts:171-174`). If an agent acquires or corrects its start time while the listed fields stay equal, the computed summary retains the old row and shows a wrong duration. Compare all rendered row fields, and test a same-status start-time update as well as the unrelated-session event.

4. **Moderate — dense lane access is underspecified and untested.** The dense card is said to show a `+N` button, but the plan never states that `N` is `lanes.total` and that the button appears when `total` is 1–3 (`implementation-plan-rail.md:465-475`). The existing summary exposes both `total` and `moreCount` (`libs/frontend/chat-ui/src/lib/molecules/compact-session/compact-lane.types.ts:23-29`); using the comfortable card's `moreCount` would produce `+0` or no button and leave those sessions without a card route to their lanes. The dense design explicitly requires `N = number of lanes` (`layout-design-spec.md:286`). Add a dense test with one lane and with four lanes; check the button's label and lane-tab destination. The current card spec list tests only the comfortable three-row presentation (`implementation-plan-rail.md:502-509`).

5. **Moderate — density geometry acceptance is incomplete.** The approved addendum requires a single 176/96 height pair read by the card, list, shift guard, and scroll anchor, plus a geometry-baseline reset on a density toggle (`layout-design-spec.md:354-356`). The plan gives the card fixed heights and asks the board to anchor after a toggle, but never defines that shared pair or a shift-baseline reset (`implementation-plan-rail.md:465-470,664-665,692-706`). Existing render metrics only provide counters (`libs/frontend/canvas/src/lib/canvas-render-metrics.service.ts:19-31`), so the proposed unit seams cannot prove the required baseline behavior. Specify the baseline ownership and test the toggle followed by a stream/state change in each density; keep the Electron geometry probe (`implementation-plan-rail.md:1072-1076`).

## Five failure questions

1. **Silent success:** an equal-reason StopFailure can reuse the displayed error id, making the shown-id guard appear valid for a later failure (finding 2).
2. **Unexpected user action:** Answer on a Rail question has no specified control or route; dense `+N` can disappear for a session with only a few lanes (findings 1, 4).
3. **Wrong answer from valid data:** a late `startedAt` update can leave a stale elapsed duration (finding 3).
4. **Dependency failure or malformed data:** the v3 plan retains read-only treatment for newer and non-integer versions, gates writes until hydration, surfaces storage write failures, and uses field fallbacks (`implementation-plan-rail.md:138-181,206-210,755-758`; current gate `canvas-layout-persistence.service.ts:213-236`). No further concrete failure was established in this path. The proposed `ResizeObserver` fallback and disconnect cover the absent-observer case (`implementation-plan-rail.md:282-299`).
5. **Missing from requirements coverage:** the density shift baseline and the few-lane dense route need explicit acceptance tests (findings 4–5).

## Coverage and decision check

The plan maps every inventory row 1–44 to a destination and names a test in the parity table (`implementation-plan-rail.md:890-935`), but row 28's tests do not cover the Rail question action and rows 25–27 do not cover the dense one-to-three-lane case (findings 1, 4). The v3 migration, read-only newer versions, hydration gate, and unchanged Grid tile intent are specified with targeted tests (`:138-181,201-228`). The keyed live view, transcript injector release, draft swap seam, per-tab lane map, ended-row sort, one queue Escape consumer, and tab-strip ResizeObserver have destinations and tests (`:231-360,365-375,608-641,765-779,979-981`). The proposed batches are ordered and file-disjoint, stay near eight files each, and carry project-scoped strict commands (`:989-1058`).

D4 changes hidden Rail hosts from paused cards to empty hosts, but those cards are inaccessible while hidden and remount from retained state on reveal (`implementation-plan-rail.md:643-652,944`); no lost user capability was established. D10's omitted Retry follows the original explicit exclusion and existing model (`task-description.md:82,140`; `compact-session-card.component.ts:215-221`), while its id source needs revision (finding 2). D11 keeps existing running-cap wording and guard (`implementation-plan-rail.md:525-530,951`); this changes explanatory copy, not the cap. D14 gives a candidate dark error color and leaves real-token contrast to the required Electron check (`:795-815,1085-1093`); no contrast result is claimed.

**Verdict: REVISE — 6/10.** The plan has sound migration, live-view, and batch seams, which keeps it above the significant-problems band. Two likely interaction failures and three test/contract gaps keep it below the sound band. The risk is limited to the specified cases until the Rail code and Electron checks exist.
