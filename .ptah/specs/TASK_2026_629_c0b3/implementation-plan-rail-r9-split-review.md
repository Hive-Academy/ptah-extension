## Findings

1. **Serious. The pane state model contradicts itself.** Line 22 says "Primary follows the existing focused tile". It then says Open beside "makes secondary active, and calls `CanvasStore.focusTile`". `focusedId` is `store.focusedTabIdFor(path)` (`canvas-rail-board.component.ts:163-168`), and `focusTile` sets that value (`canvas.store.ts:499-503`). So after Open beside, primary would also show the secondary tab, which gives two hosts for one tab. Other callers also move focus outside the board: `close` focuses the neighbour (`:337`), plus `jumpTo`, `newSession`, Rail arrows, `CanvasDetailService.open` and main-panel tab switches. Any of them can land on the inactive pane's tab. **Fix:** say that the active pane's tab is always `focusedTabIdFor(path)`. The board stores only `otherTabId` and which side is active. Add one reconcile rule: if the focused id equals the other pane's tab, swap the active side and do not copy the tab. Add board spec cases for close-neighbour, `jumpTo`, and a main-panel switch that lands on the other pane's tab.

2. **Serious. One tab can have two transcript trees.** Each ChatView has its own `TranscriptRetentionService` (`chat-view.component.ts:230-232`). Pane A can keep tab X frozen while pane B shows X live, so X has two `ptah-chat-transcript` subtrees. The coordinator is said to reconcile "by tab id", but the plan never says what happens to that duplicate. **Fix:** the coordinator owns each tab id at most once across both panes. When a tab becomes live in one pane, the other pane disposes its frozen copy. The tree cache is cleared only when the last owner releases it. Add named cases to `rail-transcript-retention-coordinator.service.spec.ts` and `chat-view.keepalive.spec.ts`: "tab retained in A then shown in B gives exactly one subtree", and "count <= 4 counts distinct tab trees". `s-heap` should also report transcript subtrees per tab id.

3. **Serious. No batch owns the path that tells each pane whether it is focused.** Today the transcript binds both `SESSION_VISIBLE` and `SESSION_FOCUSED` to the same `SURFACE_ACTIVE` (`canvas-detail-transcript.component.ts:45-50`). The transcript is mounted by `CanvasLaneViewComponent` (`canvas-lane-view.component.ts:27,38`), which has no pane or focused input. R9x changes the transcript but owns only the lane-view spec, not `canvas-lane-view.component.ts`. R9w's focus-area specs (F5, dock in both panes) run before R9x adds the split. **Fix:** name the mechanism. Either the focus area provides a pane-scoped focused signal through an element-injector token, with its token file owned, or `canvas-lane-view.component.ts` gains an input and is added to a batch. Then move the transcript and lane-view change before or into R9w, or move R9w's dock/F5 assertions to R9x.

4. **Serious. Delta 3 conflicts with the batch table.** Line 63 says the approved R9f/R9h files "are changed only when their batches implement this addendum after Gate 2". That reads as R9f/R9h absorbing the deltas. The batch table instead builds R9f/R9h as approved and reworks them in R9u/R9w/R9x after R9l. Decision 80 held R9f/R9h for this gate, so a team-leader can read it either way. **Fix:** state one rule. Recommended: R9f/R9h run unchanged as approved once this gate passes, and R9u-R9x alone carry deltas 1-2. Remove the conflicting sentence. Say plainly that this accepts rework of R9h's per-instance cap in R9u, as a visible change to decision 80's hold.

5. **Moderate. The dock at 1600 is unresolved.** Each 644 px pane is above `AGENT_PANEL_OVERLAY_BREAKPOINT` 600 (`chat-view.component.ts:181,422-426`). So the 400 px default dock sits side by side and leaves about 244 px for the transcript and composer. S2's rejection note (488 px with a 300 px dock) does not apply to the chosen layout. "Raise the threshold if it clips" leaves the rule to the implementer. **Fix:** set a measurable rule now, for example minimum transcript width >= 360 px with the dock open. If it fails, either the threshold rises (about 1720 px) or split panes force the dock to overlay. Add it to Electron re-check 1.

6. **Moderate. Screen reader and keyboard pane rules are incomplete.** Both panes would carry the same `aria-label="Focused session"` (`canvas-focus-area.component.ts:31`). Only "clicking" activates a pane. **Fix:** label panes "Left session: {title}" and "Right session: {title}", and mark the active one (for example "active" in the label). Activate a pane on `focusin` as well as click, so Tab into the inactive composer retargets send, stop and permissions. Add both to the R9w spec cases.

7. **Minor. The geometry reset skips the height check.** A `null` baseline makes the next sample return 0 shifts without checking heights (`canvas-rail-geometry.ts:30-32`). **Fix:** after an explicit move, set the baseline to `{key, order: expectedIds}` so that same sample still checks the 176/96/56 heights.

8. **Minor. The write-failure signal is on the persistence service, not the store.** `writeFailed` lives on `CanvasLayoutPersistenceService` (`:157-158`), not `CanvasStore`. Correct the reference so the board injects the right service.

9. **Minor. "Live ChatViews" has no selector.** `data-canvas-live-views` counts `ptah-canvas-lane-view` (`canvas-rail-board.component.ts:232-236`), and the main-panel ChatView stays mounted in canvas mode. **Fix:** name the selector `s-heap`/`s-switch` use (ChatView inside the board host) so 1 or 2 excludes the main panel.

Item 10 acceptance still holds in single mode: one live view, cap 4, 180 ms fade, warm switches with no task over 50 ms, CLS 0. Decision 77 is honoured, with a per-pane dock and re-check of `ptah-ui display [id]` in both panes. No approved decision is reversed silently, apart from finding 4.
