## New defect

**Serious — late positioning can leave auto-update observers attached to stale panels.** `native-popover.component.ts:241-264` only races the promise; it neither cancels `floatingUI.position()` nor retains ownership of its eventual result. If timeout wins, the panel becomes visible (`:219-230`). If the user closes it before `computePosition` later resolves, `closePopover()` calls `cleanup()` while no observer exists (`:270-276`), and the already-completed open continuation will never run again. The service then applies coordinates to the detached element and installs `autoUpdate` (`floating-ui.service.ts:143-150`). There is no subsequent cleanup for that observer. Close/reopen also fails: a stale position can finish after the new one and overwrite the service's single `cleanupFn` (`floating-ui.service.ts:87,123,143-150`); the generation branch intentionally skips cleanup while `isOpen()` is true (`native-popover.component.ts:215-217`), so the new observer can become unreachable and survive close/destroy. Repeated delayed opens can accumulate scroll/resize observers and updates against detached panels. The close-before-resolve spec at `native-popover.component.spec.ts:334-362` proves only the case where resolution occurs before the 1000 ms timeout and the popover stays closed; no spec covers late resolution after timeout or close/reopen. Fix ownership/cancellation in the service or explicitly release each position request's observer, then cover both orderings.

## Five logic questions

1. **Silent failure:** rejection and timeout now show a menu and log in development (`native-popover.component.ts:219-230`), but a late observer leak gives no signal after close (`floating-ui.service.ts:143-150,172-177`); impact is session-growing work.
2. **User action:** open, close, and reopen quickly while the first position remains pending (`native-popover.component.ts:188-218`); the old result can replace the live cleanup handle (`floating-ui.service.ts:143-150`), leaving listeners after the final close.
3. **Wrong answer from input data:** no new data-dependent wrong answer was found in the changed card; its guarded `opened` handler checks the current `menuOpen()` (`canvas-rail-card.component.ts:337-340`). The remaining edge-position limit can hide part of a wide menu at the viewport boundary (`orchestra-canvas.component.ts:139-159,183-186`; `native-popover.component.ts:219-227`).
4. **Dependency failure/timeout/wrong shape:** rejection and no resolution recover after at most 1000 ms (`native-popover.component.ts:237-265`); a late success after timeout can register an observer after cleanup (`floating-ui.service.ts:143-150`). The UI spec covers reject and timeout but not that late success (`native-popover.component.spec.ts:280-362`).
5. **Missing requirement:** ownership of an asynchronous position request across close, reopen, timeout, and destroy was unspecified. The component generation check controls focus/output but does not control the service's listener lifecycle (`native-popover.component.ts:215-217`; `floating-ui.service.ts:123-150`).

**Required before approval:** resolve the late-position observer lifecycle and add focused tests for timeout-then-close-then-resolve and close/reopen with resolutions in both orders. Keep the pixel fit and collapsed-scrollbar questions for the already assigned visual/manual check.
