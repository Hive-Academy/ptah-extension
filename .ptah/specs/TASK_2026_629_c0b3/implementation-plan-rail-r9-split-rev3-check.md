## Open items

### S1 (Serious): stale failure case contradicts decision 85

- Plan line 44: "Width drops below threshold during a stream or dock interaction: keep the active tab as the one visible pane; streams continue in session state, the hidden host releases, and the live region announces once. Narrow Details remains reachable."
- This is the pre-Revision-3 "split unavailable below 1440" behaviour. Revision 3 changed lines 28, 30, 54 and 86 but not this list. It directly contradicts plan 28 ("Resizing across the boundary changes layout only: both live pane hosts ... remain mounted"), 30 ("keep the split") and decision 85.
- Impact: an implementer or test author working from the failure cases will build collapse-on-resize, which silently ends the user's split and releases a live stream host on a likely user action (resizing the window). Failure cases are a spec source for the R9w and R9x named cases.
- Fix (one line, in the plan): replace line 44 with a case that matches decision 85, for example "Width crosses 1440 (or drops below 920) during a stream or dock interaction: both panes stay mounted; only the layout changes (side by side to stacked); dock side/overlay is re-evaluated per pane; no host releases; nothing is announced except the layout name if the board chooses to." Also add the entry to the Revision 3 table with its plan line.

### Batch-level notes (Moderate; settle inside the batch contracts)

- **B1 (Moderate, R9w), Details in split at sm and on mode change.** Plan 24 and 86 name the overlay, Open and Close controls, Escape, focus return and "closes on collapse". They do not say:
  - what `detailsOpen` does when split turns on. In sm single focus, `detailsOpen` forces `effectiveCollapsed` and shows the 288 px aside (`canvas-rail-board.component.ts:213-218,121-148`).
  - that in split `effectiveCollapsed` must ignore the Details overlay (otherwise the Rail collapses while a pane-bounded overlay is open).
  - whether the sm "i" strip, 44 px wide, stays a column in split. If it does, the 648 px pane at 920 is really 604 px.
  Add: on entering split, close the single-focus Details aside; in split the Rail ignores `detailsOpen`; the opener is a pane-header or overlay control that takes no layout width. Add a spec case "920 split: Details open does not collapse the Rail".
- **B2 (Moderate, R9w and R9u), 400 px floor derivation and test reality.** Carry the derivation into the R9w contract (wrapper 400 = header 48 + lane tabs 36 + about 316 for ChatView with composer 2 lines to 10 rem), state that the 400 applies to the pane wrapper including its header, and reword plan 28's "check in R9w's named stacked spec at the shortest supported Electron viewport". jsdom cannot measure it. The spec should assert the `min-h-[400px]` and `overflow-y-auto` bindings, and Electron re-check item 2 (plan 94) should name the shortest supported window, 800 x 600 (`main-window.ts:119-120`), where the column must scroll and the lower composer must be reachable by keyboard. Add 976 px (side dock) and 648 px (overlay) rows to R9u's keepalive case beside 804 and 644; they are the real stacked widths at 1280 and 920, and R9w's board specs cannot measure them. Add boundary cases at container widths 1439 (stacked) and 1440 (side by side).
- **B3 (Moderate, R9x), stacked Tab order mechanism.** CSS `order` does not change tab order. Top-before-bottom after a swap needs a keydown handler that intercepts Tab and Shift+Tab at the last or first tabbable of a pane and also on entry from the Rail. State: the host of the handler, how "last tabbable" is found (a query that skips hidden elements and an open dock or Details overlay), that open overlays and menus are excluded, and that the handler runs only in stacked mode with `visualOrder` swapped. jsdom does not move focus on Tab, so the spec must assert the handler's `focus()` target from synthetic keydown events. Add the named case "side-by-side swap keeps DOM Tab order" (plan 87 states the rule but names only two cases). Note also the asymmetry the plan accepts: side-by-side Tab order does not follow the visual order after swap (plan 26, 142). That is a conscious trade-off and should be recorded as one, not left implicit.
- **B4 (Moderate, R9w and Electron re-check), narrow floor.** Plan 30's horizontal scroll below 360 px needs the pane wrappers to carry the 360 px minimum width and the column `overflow-x-auto`. Cite `minWidth: 800` in the plan and add an Electron step at the smallest window with the left sidebar open, because the canvas container there can be well under 800 (Rail 272 + 360 = 632 is the real floor).
- **B5 (Minor, R9u and R9w), named assertions.** Name a transcript spec case for "token value is 360 when `splitDisplayed`, null in single focus" and one asserting `HIDE_AGENT_SIDEBAR` is not provided by the canvas detail transcript (today `canvas-detail-transcript.component.ts:56` provides `true`; R9f and R9w must remove it). N6(a) is in the contracts but has no named case.
- **B6 (Minor, R9v and R9w), `splitDisabledReason` cases.** The width reason is gone (decision 85). Enumerate what still produces a reason, for example only one tile on the board, target equals the active tab, stale or cross-workspace id (plan 22, 43), so the Rail and card specs have concrete strings to assert.
- **B7 (Minor, R9w and R9x), field and owner clarity.** Plan 28 says panes stack "inside the focus area", but plan 24 and 86 have the board render two `CanvasFocusAreaComponent` panes. Name the board as the owner of the pane container, the `order` binding and the `splitStacked` computed (from `layout.containerWidth() < 1440`). State that R9w creates `visualOrder` with its default and labels and R9x only adds the swap. R9w is the heaviest contract by far (pane state machine, close and ghost reconcile, Details overlay, stacked layout, tokens, lane ids, reorder consumers); the team-leader should watch its size at decomposition, since the 8-file cap cannot split it without breaking file disjointness.

The measurement selector `ptah-canvas-rail-board ptah-chat-view` (plan 38, 96) is layout independent. Crossing 1440 adds no mount (plan 94, 96 resize step).
