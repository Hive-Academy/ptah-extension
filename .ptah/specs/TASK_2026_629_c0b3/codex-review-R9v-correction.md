## Answers

1. **Ordering:** Timeout then close then late fulfillment: popover timeout resolves the race at `native-popover.component.ts:241-263`; close calls service cleanup at `:270-276`; the late result fails `isCurrent` at `floating-ui.service.ts:151-156` and installs nothing (`native-popover.component.spec.ts:362-386`). Close/reopen in either resolution order: each `position()` starts by invalidating the earlier token (`floating-ui.service.ts:125-131`), and only the current result can assign the handle (`:156-162`); both orders are asserted at `floating-ui.service.spec.ts:262-299`. Destroy while pending: `isDestroyed` is set and cleanup runs (`floating-ui.service.ts:102-106`), then the late result fails the guard (`:165-166`; spec `:224-234`). An in-flight update cannot apply stale coordinates after cleanup because its continuation checks the token (`:158-161`; spec `:302-316`).
2. **Handle ownership:** Only a current request can reach the synchronous `applyPosition` and `autoUpdate` assignment (`floating-ui.service.ts:156-162`). JavaScript runs that segment without an await, so cleanup cannot interleave between the guard and handle assignment. Each later `position()` or explicit close invalidates the token and releases the one handle (`:130-131,188-194`). The two reversal specs verify that an older request cannot replace the newer handle and that cleanup calls the newer handle once (`floating-ui.service.spec.ts:262-299`). No normal ordering loses a live handle or invokes a stale one.
3. **Rejection:** A rejected first `computePosition` still rejects `position()` because the guard follows the await (`floating-ui.service.ts:151-156`). The popover's race catches it as `'failed'`, shows the panel, focuses it, and emits `opened` for a current generation (`native-popover.component.ts:212-229,248-264`; spec `:281-309`). If a stale request rejects, `Promise.race` has already attached a rejection handler; the popover's generation check stops the old continuation from changing its UI (`native-popover.component.ts:212-217,248-263`). The popover therefore has no unhandled rejection on this path. Other direct users can still propagate or ignore an initial rejection, for example the tab-bar's `void position()` at `libs/frontend/chat/src/lib/components/organisms/tab-bar.component.ts:352-359`; that behavior predates this correction and is outside its bounded scope.
4. **Removed popover cleanup:** Closing calls `cleanup()` and increments the open generation (`native-popover.component.ts:270-276`); destroy does the same (`:300-306`); a new open starts a new service request (`:202-217,237-259`, `floating-ui.service.ts:125-131`). Thus the old continuation's removed conditional cleanup is unnecessary. Keeping it on a reopened popover could instead release the newer request. The generation check still blocks stale focus and `opened` (`native-popover.component.ts:212-229`).
5. **Users/API:** Public methods, parameters, and return types remain `position(...): Promise<void>` and `cleanup(): void` (`floating-ui.service.ts:125-129,188-194`). A content search under `libs/frontend` found five direct production component consumers, despite the correction report's claim of nine; all five provide their own instance (`native-dropdown.component.ts:63`, `native-autocomplete.component.ts:83`, `native-popover.component.ts:76`, `unified-suggestions-dropdown.component.ts:55`, `tab-bar.component.ts:73`). Spot checks found no caller relying on simultaneous observers: dropdown uses one panel and cleans up on close (`native-dropdown.component.ts:181-215`), autocomplete cleans up on close (`native-autocomplete.component.ts:320-360`), and tab-bar cleans up its badge tip (`tab-bar.component.ts:352-368`). Repeated `position()` already released the previous handle before this patch, as the existing contract test shows (`floating-ui.service.spec.ts:173-185`). An existing limitation remains: dropdown emits `opened` after an awaited request returns even if cancellation made it a no-op (`native-dropdown.component.ts:203-215`); the pre-correction service also returned normally after destroy (`git show HEAD` service lines 143-150), so this correction does not introduce a new return-status contract.
6. **Spec sensitivity:** The cancellation and supersession cases at `floating-ui.service.spec.ts:249-299`, the in-flight tick case at `:302-316`, and the popover's close-before-resolution and timeout-then-close cases at `native-popover.component.spec.ts:335-386` would fail if the token guard were removed, because they assert no stale `autoUpdate` or stale coordinates. The new normal-path case (`floating-ui.service.spec.ts:238-247`) would still pass; it is a baseline. The new destroy case (`:224-234`) would also pass if only the token comparison were removed while `isDestroyed` remained, because that independent guard still blocks it. Thus the answer to “each new case” is no, but the cases aimed at the reported leak are not vacuous. The specs use mocked `computePosition` and `autoUpdate` (`floating-ui.service.spec.ts:6-12`, `native-popover.component.spec.ts:10-16`), so actual browser observer disposal remains outside their evidence.

## Five logic questions

1. **Silent success:** A stale `position()` resolves normally with no coordinates (`floating-ui.service.ts:151-156`); in the popover the generation check prevents that from signaling an old open (`native-popover.component.ts:212-229`). Dropdown's earlier `opened` issue is described in Answer 5.
2. **User action:** Open, close, and reopen while the first position is pending; only the latest request can register an observer (`floating-ui.service.ts:125-131,156-162`; reversal specs `:262-299`).
3. **Wrong-answer data:** There is no data-dependent coordinate rewrite in this correction: current `x,y` are applied unchanged, while stale results are ignored (`floating-ui.service.ts:151-179`). Malformed coordinate shapes remain a pre-existing external-contract assumption.
4. **Dependency failure:** Initial rejection propagates to the popover fallback; timeout shows that fallback; late success after close cannot register observers (`native-popover.component.ts:218-264`; `floating-ui.service.ts:151-166`). A rejected auto-update callback remains a pre-existing library-boundary risk (`floating-ui.service.ts:158-162`).
5. **Missing requirement:** The original contract omitted ownership of a pending position across close, reopen, and destroy; the request token and component generation now cover those transitions (`floating-ui.service.ts:89-106,125-166`; `native-popover.component.ts:182-217,270-306`).
