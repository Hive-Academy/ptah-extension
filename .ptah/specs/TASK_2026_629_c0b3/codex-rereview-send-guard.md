# Scoped re-review: chat composer send guard

Review family: codex reviewing Claude. Score: **6/10**. Verdict: **REVISE**.

## Prior findings

1. **Blocking draft loss — partially closed; outcome handling remains open.** `libs/frontend/chat/src/lib/components/molecules/chat-input/chat-input.component.ts:1514-1524` now retains the visible and stored draft on `{ success: false }`, including failures before an optimistic user bubble exists. That fixes the original loss at this boundary. But unconditional retention conflicts with the ordinary failed-send behavior described below, so the overall send failure flow still needs revision.
2. **Serious duplicate dispatch while pending — closed.** `chat-input.component.ts:1490-1506` records the sending tab and submitted text and attachment-list identities before calling the store; an unchanged second Send on the same tab returns before dispatch. `:1550-1553` removes the exact entry in `finally`, so success, unsuccessful outcome, and thrown error release it. The guard is scoped to the submitted draft, allowing edited follow-ups and another tab to send while a prior call awaits. `chat-input.component.spec.ts:388-444` covers an overlapping unchanged send, a subsequent send, and an edited follow-up. The ordinary RPC call has a default 30-second timeout (`libs/frontend/core/src/lib/services/claude-rpc.service.ts:129-167`); the sender's service-readiness wait is bounded at five seconds (`libs/frontend/chat/src/lib/services/message-sender.service.ts:375-388,599-611`). An indefinitely unresolved dependency promise would keep its guard entry until the promise settles, but that is outside those normal bounded paths and a different draft remains sendable.

## New finding

1. **Serious — retry duplicates an optimistic user message after a failed send.** `chat-input.component.ts:1522-1524` keeps the draft for every unsuccessful outcome. For a new conversation, the sender writes the user's bubble *before* `chat:start` (`libs/frontend/chat/src/lib/services/message-sender.service.ts:425-445`) and leaves it in place on an unsuccessful RPC result (`:466-488`). For an existing conversation it likewise writes the bubble before `chat:continue` (`:676-697`) and explicitly keeps that bubble on failure unless the caller is a queue flush (`:718-736,763-781`). The dispatcher adds a delivery-failure notice, but does not restore text to the composer or remove the optimistic bubble (`libs/frontend/chat/src/lib/services/chat-store/message-dispatch.service.ts:202-206,332-344`). If the user retries the preserved draft, another user bubble is appended while the first failed bubble remains. The blocked slash-command path also writes a user bubble before returning failure (`message-dispatch.service.ts:155-160,371-400`). Resolve ownership of failed prompt content across the composer and transcript: keep retryable text without leaving duplicate visible user prompts, and cover a real sender failure followed by retry in a scoped test. The current spec mocks `sendOrQueueMessage` and cannot observe transcript duplication (`chat-input.component.spec.ts:446-474`).

## Historical intent and verification

The test changed at `chat-input.component.spec.ts:1288-1299` previously asserted clear-on-failure. `git blame` traces its original assertion to `7566a9596b` (Oct 4, 2026); that commit's added test explicitly said a budget refusal keeps the draft and **any other outcome clears it**, and its implementation made that distinction. After the budget flow was removed, commit `5a42273c0` retained the general clear-on-failure test. Thus clearing on an ordinary failed send was an intended rule, supported by the sender's retained optimistic bubble. It was incomplete for failures before any bubble is written, such as validation and service-readiness failures (`message-sender.service.ts:321-330,375-388`); blanket clearing could lose the only editable copy there. The current blanket keep fixes that loss but creates the duplicate-transcript case above. The product needs an explicit rule for both phases of failure.
