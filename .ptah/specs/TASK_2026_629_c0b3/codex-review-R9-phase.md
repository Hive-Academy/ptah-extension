## Findings

1. **Serious — selecting the other visible session from its Rail card collapses the logical distinction between panes.** `libs/frontend/canvas/src/lib/canvas-rail/canvas-rail-card.component.ts:273-276` calls `CanvasStore.focusTile(id)` before emitting `focusRequested`; the store writes the focused id synchronously at `libs/frontend/canvas/src/lib/canvas.store.ts:424-428`. The Rail forwards the event at `libs/frontend/canvas/src/lib/canvas-rail/canvas-rail.component.ts:192`, and the board handles it at `libs/frontend/canvas/src/lib/canvas-rail/canvas-rail-board.component.ts:88,639-648`. With A active and B in the other pane, clicking B's card makes store focus B before `board.focus(B)`. Because B still equals `otherTabId`, `focus()` calls `activatePane()`, which now reads B as both `id` and `current` (`canvas-rail-board.component.ts:507-516`), sets `otherTabId` to B and fails the distinct-pane assertion (`:473-476`) in development. In production, `paneTab()` suppresses the duplicate inactive pane (`:486-497`), leaving a split state with only one visible host, rather than activating B's existing host. **Fix:** make the board the sole writer for Rail selection: remove the card's direct `focusTile` call, keep the event, and add an integration spec that clicks a real Rail card for the inactive pane and checks distinct pane ids, two mounted lane views and the selected card. Touch `canvas-rail-card.component.ts`, its spec, and `canvas-rail-board.component.spec.ts` (or the Rail host integration spec).

## Five logic questions

1. **Silent failure:** In production the distinct-pane assertion is disabled (`canvas-rail-board.component.ts:473-476`); `paneTab()` then returns `null` for the duplicated inactive pane (`:486-497`) while `splitDisplayed()` remains true (`:239-242`). The UI can look like a one-pane split without reporting why.
2. **Unexpected user action:** Click or keyboard-activate the Rail card for the session already visible in the other pane; it reaches the bad event ordering in finding 1 (`canvas-rail-card.component.ts:273-315`; `canvas-rail-board.component.ts:639-648`).
3. **Wrong-answer data:** With active A and other B, `focusTile(B)` changes the store before `activatePane()` reads `current`, so B is recorded as both focused and other (`canvas.store.ts:424-428`; `canvas-rail-board.component.ts:507-516`).
4. **Dependency failure or malformed shape:** Initial popover positioning is bounded and falls back on failure (`native-popover.component.ts:202-229,237-264`); a late request is generation-checked (`:212-217`). The review found no new failure path from the R9b/R9v interaction beyond the already recorded clipping and warning cases in `handoff-10.md:113-132`.
5. **Unspecified requirement:** The direct board tests do not define ownership of the focus write when a real Rail card selects an already mounted pane (`canvas-rail-board.component.spec.ts:742-780`). The split invariant requires one owner for that write across the card-to-board boundary.
