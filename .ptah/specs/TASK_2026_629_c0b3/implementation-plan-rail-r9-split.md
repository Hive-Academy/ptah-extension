## Data flow and contracts

The board owns one transient pane state `{ activeSide: 'left' | 'right', otherTabId: string | null, visualOrder: ['left','right'] | ['right','left'] }` per visible workspace. [lane-proposed] Collapse to single focus resets visualOrder to ['left','right']; a new split begins in that order. The active pane's tab is always `CanvasStore.focusedTabIdFor(path)`; `otherTabId` belongs only to the inactive pane. The two ids must differ. On **Open beside**, leave the current tab in its pane, put the target in the other pane, set that side active with the previous focused id as `otherTabId`, then call `CanvasStore.focusTile(target)` as one board transition (do not run the external-focus reconcile against that internal transition). Opening the active tab is refused with a polite announcement; opening the inactive tab activates that pane without duplication. A normal card click, Rail arrow, `jumpTo`, `newSession`, or `CanvasDetailService.open` changes the active pane's tab through the existing focus path. [lane-proposed] The board keeps `lastFocusedId` from the last settled store focus, updated synchronously inside each internal transition; an external-focus effect reads this field before reconciliation (the old value cannot be sampled from the already changed signal). If the new focused id equals `otherTabId`, exchange `activeSide` and `otherTabId` with `lastFocusedId`, so the ids stay in their panes; otherwise replace only the active pane's tab. A main-panel tab switch uses the same rule. [lane-proposed] A confirmed `close(id)` captures whether `id` was the store-focused id and the surviving pane before `removeTile`; on success it performs the pane-state transition inside `close`, updating lastFocusedId before the external-focus effect reconciles so that effect sees the settled transition. If the closed id was inactive, remove only that pane, leave store focus and the active tab untouched, and do not call `focusTile(neighbour)`. If the closed id was active, retain the surviving pane's tab, call `focusTile(survivorId)` only if the store did not already select it, and collapse to single focus; only without a survivor may the ordered neighbour become active. [lane-proposed] Reconcile pane ids against the current workspace tiles() after any removal, including removeTileOnly/removeTileFromAnyWorkspace outside close(): drop a missing pane, never render the same tab in both panes, keep the surviving valid tab focused, and announce the collapse once. Update lastFocusedId synchronously inside each internal transition before the external-focus effect can run; no temporary boolean suppression. Never derive this choice from `focusedId()`'s `tiles[0]` fallback while store focus is transiently null. Cancellation leaves both panes intact. Normal card selection, send, stop, permissions, Rail selection, Details and lane selection target the active pane; the inactive pane streams contextually and keeps its own draft. Activation by click or `focusin` calls `focusTile` for that pane's tab, without remounting either pane.

Each pane owns a distinct `CanvasFocusAreaComponent` and stable `CanvasLaneViewComponent`; both use the existing per-tab `CanvasDetailService.laneKeyFor` and `selectLaneFor`. [user-requested, decision 83] Details overlays the active pane only while split is on; in single focus it remains the existing column. [lane-proposed, N2] The board owns an Open details control and Close details control in split at every width band. The absolutely positioned overlay is bounded by the active pane, does not push either pane, follows the active tab when focus changes, closes and returns focus to its opener on Escape or Close, and closes on collapse; the single-focus column then resumes its existing band behavior. [lane-proposed] Pane region labels use visual placement: `Left session: {title}` / `Right session: {title}` side by side, and `Top session: {title}` / `Bottom session: {title}` when stacked, with `, active` appended only to the active one; `focusin` as well as click activates the pane before composer actions route.

## Item 10 interaction and budget

R9f's stable host and R9h's Rail opt-in must remain. The new hard limit is **one live ChatView in single focus; exactly two while split is on**. A frozen retained transcript is a `ptah-chat-transcript` subtree, never another live ChatView. The four retained transcripts form **one cap per visible Rail board**, shared across both panes, with both visible tabs pinned during split and at most two additional frozen tab trees. A board-scoped chat-side retention coordinator owns each tab id at most once across both panes and reconciles the two component-scoped retention services by tab id and LRU; it never evicts either visible tab. Before tab X becomes live in pane B, pane A disposes its frozen X subtree, then B acquires X; no intermediate state mounts two X subtrees. [lane-proposed] Swap panes only changes wrapper order, so tab X stays in its original owner and requires no release/acquire sequence; test that both live ChatViews retain DOM identity, tab-keyed drafts and dock state after a swap. The count is distinct tab trees, not summed service entries. Retained ids stay in insertion order so `@for` does not move DOM. Close, workspace removal, split collapse and board destroy release owners; clear a tab's execution-tree cache only after its last surface owner releases it. A transfer between panes is not a last-owner release. There must be zero detached `ptah-canvas-lane-view`, `ptah-canvas-detail-transcript`, `ptah-chat-transcript` and `chat-msg-slot` nodes after settling and GC.

## Failure cases

- [lane-proposed] A tab closes or leaves the board while secondary: remove its pane after confirmed close, retain the store-focused active tab and do not focus an ordered neighbour; cancellation keeps both hosts and drafts. When the active tab closes, choose the surviving pane even when it is `tiles[0]` and the store's focused id becomes null transiently; do the transition in `close()` and focus the survivor only when needed. If a workspace is removed, release both hosts and the shared registry.
- A second Open beside names primary, secondary, a stale id or a tab in another workspace: activate an existing pane or reject the stale/cross-workspace id with an announcement. Never create a third host.
- Width crosses 1440 px (or drops below 920 px) during a stream or dock interaction: both panes stay mounted; only the layout changes (side by side <-> stacked); the dock side/overlay choice is re-evaluated per pane (decision 82); no host releases; the live region announces only the new layout name once. Narrow Details remains reachable as the active-pane overlay (decision 83).
- Dock lazy load failure uses ChatView's existing failed-load fallback in the affected pane only. A failed display update must not corrupt the other pane's dock state. Each pane's pin/width follows its own tab key under R9h.
- A stale Move target, first/last boundary, or storage write failure does not mutate selection. The board observes `CanvasLayoutPersistenceService.writeFailed` for save failure and announces it; `CanvasStore` does not own that signal. The existing debounce may defer persistence, so reload acceptance waits for its flush.
- Reorder while both panes stream changes only card order. Geometry sampling must treat the intentional permutation as its new baseline but still detect card height changes and any unexpected CLS.
