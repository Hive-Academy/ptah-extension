# BM design review — TASK_2026_629_c0b3

**Verdict: REVISE. Score: 5/10.** The existing `git:info` contract supports the proposed source, but the live todo selector can attribute a subagent's list to the parent session, and the refresh plan has an undefined streaming signal and unbounded cross-root concurrency. These are material behavior gaps; a 6 would require the entry paths and refresh ownership to be specified. The design is above the 3–4 band because the RPC, worktree authorization, line-count source, and batch dependency direction are evidenced in code.

## Findings

1. **Serious — live TodoWrite can select a subagent's list.** Design §2a, lines 37–40 scans every live `tool_start` named `TodoWrite`, but only excludes nested agents in the finalized tree. Live events carry `parentToolUseId` (`libs/shared/src/lib/types/execution/stream.ts:83-86,145-150`), so a subagent TodoWrite after the parent TodoWrite becomes the displayed session list. **Change:** exclude live events with a parent tool use ID, and test interleaved parent and subagent tool calls in BM1.

2. **Serious — live retention can expose an older list as current.** Design §2a, line 40 returns unknown only when the newest *found* input fails the guard. The live event map evicts oldest events at its cap, including `tool_start` (`libs/frontend/chat-types/src/lib/chat-types.ts:246-283`). If the latest TodoWrite's start disappears, the scan can fall back to a finalized older TodoWrite. The same uncertainty applies if the latest relevant finalized message has been removed, whereas input folding itself is correctly detectable (`libs/frontend/chat-streaming/src/lib/execution-tree-retention.ts:355-365`). **Change:** specify a retained latest TodoWrite marker or an explicit unknown state when event/message history is incomplete; add a cap-eviction test. Without such evidence, do not claim the latest list is known.

3. **Moderate — the todo guard does not validate todo entries.** Design §2a, lines 40–41 treats `isTodoWriteToolInput` as complete validation, but it only checks that `todos` is an array (`libs/shared/src/lib/type-guards/guards/exec.ts:239-247`). A parsed partial or malformed array can produce a plausible but wrong done/total count or an invalid active label. **Change:** validate each item's status, content, and activeForm before counting; return unknown for incomplete entries. Add malformed and partially streamed array cases to BM1.

4. **Serious — the live refresh trigger has no specified source of truth.** Design §2b, lines 47–58 gives `track` only `(root, sessionId)` yet starts an interval while a tracked tab streams. Streaming is on `TabState.streamingState` (`libs/frontend/chat-types/src/lib/chat-types.ts:538-543,606`), and the existing card detects it from its tab (`libs/frontend/chat/src/lib/components/molecules/compact-session/compact-session-card.component.ts:212-214,387-394`). Session ID alone does not supply the changing streaming state or identify an unassigned draft session. **Change:** specify how the store observes tracked tab IDs and streaming transitions, including ID assignment, shared roots, and release. Test interval start/stop after state changes, not merely fake-timer ticks.

5. **Serious — the proposed polling and concurrency policy exceeds the requested refresh policy.** Design §2b, lines 53–58 and §5 R1 add a 30-second live polling interval, while the requested source was refreshed at turn end and `git:status-update` (`.ptah/specs/TASK_2026_629_c0b3/BM-design.md:1-4` states the intended sources; the task request specifies the triggers). Each read performs status, two numstat diffs, and up to 200 untracked file reads (`libs/backend/vscode-core/src/services/git-info.service.ts:999-1037,257-267`). The backend single-flight key is per workspace path (`libs/backend/vscode-core/src/services/git-info.service.ts:950-952`), so first display of nine distinct worktree tiles can launch nine expensive reads together; a 1-second per-root debounce does not bound that burst. **Change:** remove the periodic loop unless live updates are an explicit requirement; if retained, justify it and add a global concurrency limit or queue and tests with nine distinct roots. Account for the 1 MiB per-untracked-file cap as well as the 200-file cap.

6. **Moderate — a failed refresh displays old counts as current.** Design §2b, line 52 preserves the previous value on `statusUnavailable` or an RPC failure. The RPC type explicitly says an empty file list under `statusUnavailable` is not a clean tree (`libs/shared/src/lib/types/rpc/rpc-git.types.ts:122-147`). Keeping old counts without a stale indicator silently presents a prior worktree state as today's uncommitted changes. **Change:** carry freshness/error state to the card and detail row, or show unknown after a bounded stale window. Test failure after a successful read and recovery after the next push/read.

7. **Moderate — absent card metrics violate the documented placeholder rule.** Design §2c, line 64 says null todo/git metrics are omitted, while the task requires a no-data zone to keep its place and show a placeholder (`.ptah/specs/TASK_2026_629_c0b3/task-description.md:135`). The current metrics zone is persistent (`libs/frontend/chat-ui/src/lib/molecules/compact-session/compact-session-activity.component.ts:787-802`). **Change:** render fixed todo and git slots with an em dash or equivalent unknown state; test null/unknown board layout in BM1. The detail row's dash already follows this rule (`libs/frontend/canvas/src/lib/canvas-detail/canvas-session-details.component.ts:52-65`).

## Evidence audit and batch assessment

- **S4/S5:** `StreamingState` holds events and input accumulators (`libs/frontend/chat-types/src/lib/chat-types.ts:64-78`); `toolInputOf` resolves the accumulator after parsing (`libs/frontend/chat-ui/src/lib/molecules/compact-session/compact-session-summary-cache.ts:113-125`). Input capping is entry-wise (`libs/frontend/chat-streaming/src/lib/execution-tree-retention.ts:355-365`). The S5 citation to lines 321–329 describes *output* capping, so replace it with the input-capping lines.
- **S6/S7/S8:** `GitInfoResult.files` and nullable per-file line counts are present (`libs/shared/src/lib/types/rpc/rpc-git.types.ts:18-46,133-147`). `getGitInfo` attaches staged/worktree numstat and capped untracked counts (`libs/backend/vscode-core/src/services/git-info.service.ts:999-1037`). `git:info` calls `resolveReadRoot`, which accepts a registered worktree of an open workspace repository (`libs/backend/rpc-handlers/src/lib/handlers/git-rpc.handlers.ts:203-220,318-347`). **No new RPC is required for those roots.** An unregistered or removed worktree returns the non-git default, so the design's limit is real.
- **S10/S12/S13/S14:** The existing status handler matches a pushed workspace root (`libs/frontend/chat/src/lib/services/change-set/change-set.store.ts:520-532`); child worktrees need a read. Child root and session ID live in `TabState` (`libs/frontend/chat-types/src/lib/chat-types.ts:519-533,538-563`), and the card already looks up a tab's workspace partition (`libs/frontend/chat/src/lib/components/molecules/compact-session/compact-session-card.component.ts:228-233`). The card's metrics zone and detail placeholders are as cited (`libs/frontend/chat-ui/src/lib/molecules/compact-session/compact-session-activity.component.ts:787-802`; `libs/frontend/canvas/src/lib/canvas-detail/canvas-session-details.component.ts:52-65`).
- **Boundaries/batches:** BM1 `chat-ui` types and selector, BM2 `chat` store/card plus app registration, and BM3 `canvas` detail are file-disjoint and ordered by exports (design §4, lines 78–100). `canvas` already imports `chat` (`libs/frontend/canvas/src/lib/canvas-detail/canvas-session-details.component.ts:9`); `chat-ui` should remain a data-only presentational dependency. Estimates of 25/35/15 calls are under 40, but BM2 needs the streaming-state, nine-root burst, and stale-failure tests above. Its one-line app provider change still needs a focused registration/DI assertion: handlers are explicitly registered in `apps/ptah-extension-webview/src/app/app.config.ts:219`.

## Five logic questions

1. **Silent failure:** retaining counts on RPC failure without marking them stale looks successful (finding 6; `rpc-git.types.ts:122-147`).
2. **Unexpected user action:** opening nine worktree cards at once can queue nine expensive reads (finding 5; `git-info.service.ts:950-952,999-1037`).
3. **Wrong answer from input:** a subagent TodoWrite or malformed todo entry can produce the wrong parent count (findings 1 and 3; `stream.ts:83-86`; `exec.ts:239-247`).
4. **Dependency failure:** a timeout preserves prior counts indefinitely under the proposed policy (finding 6; design §2b line 52).
5. **Requirement gap:** unknown metric slots need placeholders, and the live refresh signal needs ownership (findings 4 and 7; `task-description.md:135`).
