REVISE

## Numbered findings

1. **High — Component 5 / F8: deferred correction can navigate back to chat after a rapid page switch.** `followUrl` correctly abandons chat state when the URL is not a chat URL (`libs/frontend/chat/src/lib/services/chat-tab-route-sync.service.ts:130-140`), but the proposed `afterTransition` callback only re-reads the active tab and tests whether the URL names it (`implementation-plan.md:303-309`). If a queued `/chat/<id>` correction flushes after the user has navigated to Settings, `replaceChatUrl` unconditionally calls `navigateToSurface(CHAT_SURFACE, ...)` (`chat-tab-route-sync.service.ts:273-281`). **Required change:** guard the callback with the current chat surface/URL and a navigation generation; discard superseded corrections. Test chat → settings and chat → another page within 80 ms, including a queued correction. Do not hold or overwrite the user's newer navigation.

2. **High — Component 6: the proposed entrance snapshot is not tied to the first settled active transcript render.** A retained transcript returns `_frozenView` while `workActive()` is false (`chat-transcript.component.ts:323-327, 558-570`); `vm()` is recomputed only after activation. The plan has an effect driven solely by the rising `entering()` edge and reads `vm().slots` untracked (`implementation-plan.md:341-353`). Depending on effect ordering, this can capture the hidden snapshot, zero slots, or slots before replay; later mounted messages then get no entrance. The existing behavior explicitly waits for `afterNextRender` (`chat-view.component.ts:1203-1213`). **Required change:** define a deterministic activation/render boundary for taking the six IDs, preserve the rule that later stream/replay/resync IDs never animate, and test retained A→B, nonretained load, and rapid A→B→A with real `active`/`vm` updates. A synchronous signal test alone is insufficient.

3. **High — Quality requirements / B0: the 50 ms acceptance target is weakened without user approval.** The task context carries “no long task > 50 ms per switch” (`context.md:9-13`), while the plan passes M1 when there is no long task *attributable to motion code* and only reports overall render long tasks (`implementation-plan.md:514-525, 564-572`). **Required change:** retain the overall per-switch threshold as the acceptance criterion, or explicitly obtain the user's decision to move render-cost failures to TASK_2026_629 before calling this task complete. M0 may diagnose ownership; it should not silently redefine success.

4. **Medium — Component 1 / Current state map: the skip rule has an unproven route identity contract.** The plan uses `root.firstChild?.routeConfig?.path` (`implementation-plan.md:199-207`) to decide whether a navigation changes a top-level surface. The installed Router does pass root snapshots (`node_modules/@angular/router/fesm2022/_router-chunk.mjs:3971-3977`), but this tree also has component-less chat routes and child routes (`apps/ptah-extension-webview/src/app/app.routes.ts:78-95, 141-160`). The test list covers `/chat` child and Thoth child but not redirects, empty-path children, or a failed/cancelled rapid navigation. **Required change:** derive the surface from the actual first primary URL segment or prove the snapshot traversal for every top-level route shape; add a redirect and rapid-cancel case. Also qualify “skipping happens before capture”: the installed router calls `document.startViewTransition` before invoking `onViewTransitionCreated` (`_router-chunk.mjs:3685-3713`), so `skipTransition()` is called after creation.

5. **Medium — Components 3–5 / B0: interaction and focus during the 200 ms overlay are not acceptance-tested.** `::view-transition` is an overlay over page content ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/View_Transition_API/Using)); CSS `pointer-events:none` is explicitly an assumption (`implementation-plan.md:149-150, 263-269`). The plan has no B0/M1 assertion for click-through, keyboard focus, or the focused element after a routed element is destroyed. A page click 80 ms after another click (`implementation-plan.md:492`) could miss the intended target without being reported. **Required change:** record target click receipt, `document.activeElement`, and focus restoration for pointer and keyboard routes during and after transitions in both hosts; specify skip/cancel behavior for a new navigation while one is active. Accessibility risk is also documented by [MDN](https://developer.mozilla.org/en-US/docs/Web/API/View_Transition_API).

6. **Medium — Current state / Codebase evidence: several observations are stated more strongly than source proves.** F1 says every visible item gets the 360 ms maximum (`implementation-plan.md:48-55`), but the source only proves DOM-order indexing capped at 8 (`chat-view.component.ts:1223-1231`) and a 2000 px render margin (`transcript-render-window.ts:3-10`); the exact visible delay depends on mounted item count and scroll position. “Six visible messages are always mounted” (`implementation-plan.md:100`) should say six *trailing* messages are always mounted (`transcript-render-window.ts:20-25`), which need not all be visible. `display:none`/rAF first-frame scroll and empty-state flash are correctly labelled assumptions (`implementation-plan.md:70-78`). **Required change:** qualify F1 and the tail claim, and keep F6/F7 conditional on measured frames rather than asserting visual outcomes from source alone.

7. **Medium — Batches B0–B3: file ownership is disjoint, but B1 and B2 are oversized for a single lane.** B1 owns a router feature, transition tracker, cross-host CSS, Electron template, URL reconciliation, and four test seams across core/chat/webview (`implementation-plan.md:668-691`). B2 changes seven production files plus two new specs and must resolve render timing, replay, and optional F6/F7 work (`implementation-plan.md:693-713`). These are likely to exceed roughly 40 tool calls each. **Required change:** split B1 at the router/CSS versus URL-reconciliation boundary, and B2 at ChatView edge versus transcript/render integration or give one executor sequential checkpoints; keep file ownership exclusive. B0 and B3 are reasonably bounded. B0's “typecheck passes” does not prove its recorder actually captures an M0/M1 window; a recorded fixture run remains required, with execution authorization as the repository rule requires (`CLAUDE.md:8-16`).

8. **Low — Component 7 / API testability: the split-pane assertion cannot be proved in jsdom as written.** The source creates pane sections under `@if (paneTab(side); as id)` (`canvas-rail-board.component.ts:157-196`), so `[animate.enter]` is a suitable creation-time hook. Installed Angular disables it when `document.documentElement.getAnimations` is unavailable (`node_modules/@angular/core/fesm2022/_debug_node-chunk.mjs:4071-4076, 14023-14038`). **Required change:** keep a template binding assertion and require M1 frame evidence for the entrance and reduced-motion behavior; do not treat a jsdom class assertion as animation proof. The plan mostly acknowledges this at `implementation-plan.md:431-435`; make it explicit in B3 acceptance.

## Verified claims

- Router configuration has `withDisabledInitialNavigation` and no `withViewTransitions` (`apps/ptah-extension-webview/src/app/app.config.ts:174-183`).
- Installed `@angular/router` 22.1.7 exposes `skipInitialTransition`, `onViewTransitionCreated`, and route snapshots (`node_modules/@angular/router/types/router.d.ts:121-150`); the runtime invokes the callback in an injection context after calling `startViewTransition` (`node_modules/@angular/router/fesm2022/_router-chunk.mjs:3685-3713`). Its unsupported/initial case falls back to a timeout (`:3673-3680`), and `withViewTransitions` sets `skipNextTransition` (`node_modules/@angular/router/fesm2022/_router_module-chunk.mjs:1829-1841`).
- `animate.enter` is a creation-time queue; `''` produces no classes and unsupported/jsdom environments return early (`node_modules/@angular/core/fesm2022/_debug_node-chunk.mjs:4200-4207, 14023-14078`). `animate.leave` pertains to removal, so it cannot animate a retained transcript merely becoming visible. Runtime behavior and TypeScript API are consistent here.
- Existing stagger indexes `.st-t` in mounted DOM order, writes `--i`, forces `offsetWidth`, and clears a timer (`libs/frontend/chat/src/lib/components/templates/chat-view.component.ts:1203-1248`); its CSS caps at 8 × 45 ms and uses backwards fill (`chat-view.component.css:227-230`).
- Header and composer currently carry the fade marker (`chat-view.component.html:35, 269`; `chat-view.component.css:222-225`).
- Transcript hosts are hidden via `[class.hidden]` and their `vm()` is frozen while inactive (`chat-transcript.component.ts:275-277, 558-570`). The render window always mounts six trailing messages (`transcript-render-window.ts:20-25`).
- Scroll restoration occurs in rAF on activation (`chat-transcript.component.ts:1117-1133, 1300-1315`); the plan correctly treats a painted wrong-scroll frame as unverified.
- Canvas lane focus writes `fade=true`, then clears it in rAF, with a 180 ms opacity/transform rule (`libs/frontend/canvas/src/lib/canvas-detail/canvas-lane-view.component.ts:52-66, 286-292`).
- Chat URL correction occurs on bare `/chat` (`libs/frontend/chat/src/lib/services/chat-tab-route-sync.service.ts:175-178`) and tab switches (`:206-212`), using a replace navigation (`:273-281`).
- The replay service opens a live-event fence before the resume reply, chunks replay with macrotask yields, and exposes a replaying-tab signal (`libs/frontend/chat/src/lib/services/chat-store/session-history-replayer.service.ts:204-218, 295-330`). Older-history prepends intentionally publish no replay motion state (`:427-445`). Therefore the tab-id edge is a useful guard, but new-tab replay timing must be tested.
- Global reduced-motion CSS shortens durations but not delays or `::view-transition-*` (`apps/ptah-extension-webview/src/styles.css:747-756`); explicit rules and the router skip are appropriate.
- Electron 44 ships Chromium 152 ([Electron release](https://www.electronjs.org/blog/electron-44-0)); VS Code 1.101 shipped Electron 35 / Chromium 134 ([VS Code release](https://code.visualstudio.com/updates/v1_101)). Both Chromium versions support document view transitions, but the exact 1.100+ webview environment still needs the planned runtime feature check. The router fallback handles absence.

## Lane-introduced constraints

- **Lane-proposed, not required by `context.md`:** split-pane `animate.enter`, inspector stagger retiming, moving component easing tokens to global `:root`, a root-scoped transition tracker, and the VS Code layout-toggle question (`implementation-plan.md:166-185, 231-278, 410-435, 741-744`). These may be justified by the implementation, but they should be marked as supporting choices rather than user requirements.
- **Lane-proposed approval flow:** the plan asks for separate consent to run M0/M1 (`implementation-plan.md:745-749`). Repository `CLAUDE.md:8-16` reserves build/e2e execution; preserve that gate, while preparing the recorder and tests without running them.
- **Scope choice needing user resolution:** treating render-caused >50 ms switches as a follow-up (`implementation-plan.md:737-740`) changes the prior acceptance target; see finding 3.
