# Research Report - TASK_2026_597_ab22

## Question

- Decision this supports: which exact mechanisms the architect should wire to cut token and quota burn for spawned Codex / OpenCode / Ollama Cloud lanes and the Claude-side compaction items (561 Track A, 562 Waves 2 and 4).
- Question: which verified config keys, flags and SDK behaviours cut lane token cost, and what do the 406 Phase 0 experiments (E2-E5) answer from installed source?
- Bounds: no live `codex` / `opencode` / Claude sessions were run (lanes disabled, quota). Used only `--help`, `codex features list`, `codex mcp list`, `codex debug prompt-input` (renders the prompt locally, makes no model call), installed package source, and existing logs. No auth data read. Not investigated: Antigravity/Gemini/Copilot lanes, 561 Track B.

## Answer

The largest, cheapest win is a set of `--config` overrides on the existing SDK `config` option: with `agents.enabled=false`, `features.plugins=false`, `features.apps=false` and `skills.include_instructions=false`, the locally rendered Codex prefix drops from 31,874 to 6,416 chars (measured). Do NOT isolate `CODEX_HOME`: `auth.json` is ChatGPT-mode with a `refresh_token`, so a copy risks token-rotation conflicts with the user's login. Model choice matters as much: the 12% weekly burn was `gpt-6-astra` (frontier, priced about 2.5x-5x Sol per unverified third-party sources). Several premises in the task are stale: the `tool_search_always_defer_mcp_tools=false` line is a dead no-op on the installed binary, and the installed Claude SDK is 0.3.278 (runtime 2.1.278), not 0.3.150 / 2.1.150.

## Disagreements

- Astra cost versus Sol: one article says Astra is 5x Sol ($2/$10 vs about $10/$50); a search result says 2.5x ($4 to $10 input). Both third party; OpenAI help article was not retrievable. Decide with the used_percent experiment, not the prices.
- Where tool-discovery cost lives: `context.md` D3 says every MCP tool loads on turn one because the flag is `false`. Logs and `features list` show the flag is `removed/true` and lanes find MCP tools via code-mode `ALL_TOOLS`. The log is authoritative for 0.155.1 with GPT-6 models; the older 0.150.1 comment in `codex-cli.adapter.ts:620-631` is stale. Tool-list token size is not visible in rollouts.
- Role-block size: context.md quotes 34,608 chars; the sampled 74-turn lane's role developer message is 12,173 chars. The 34,608 figure is probably a different role (not checked); the architect should not assume one number.
- Docs vs binary on `features.tool_search_always_defer_mcp_tools`: docs say "now rejected"; 0.155.1 and 0.160.0 accept it silently. Either way the line must go.
- 406 says runtime is 2.1.150 and `autoCompactWindow` has "no evidence it is honored"; the installed runtime is 2.1.278 and consumes it. The 406 gate was written for a version no longer installed.

Setting a lower explicit value is accepted by the CLI but its effect on `exec_command` was not measured (see Unknowns).
- `agent-spawn-environment.service.ts:165` (`resolveModel`): ship `gpt-6-sol` as the default when `codexModel` is empty; keep an override. `models_cache.json` is the discovery source (`slug`, `visibility: list`).
- `models_cache`: GPT-6 `context_window 272000` (95% effective) means a `model_auto_compact_token_limit` of roughly 120k-150k leaves headroom; the 74-turn lane grew to 183,759 tokens per request.
- D6 usage accounting: `token_count` events and SDK `turn.completed` expose `cached_input_tokens` as a subset of `input_tokens` (log: input 27,264 cached of 38,086). The adapter should carry a cached field.
- Q5 fix, `Failed to parse item`: the SDK splits stdout on U+2028/U+2029/U+0085 as well as newlines, and Codex (serde_json, raw U+2028 in strings is the standard behaviour but not confirmed here) emits them unescaped inside `command_execution` output. Defensive options: (1) direct spawn with a `\n`-only splitter (Option C; also lets Ptah log-and-skip unparseable lines); (2) a `codexPathOverride` shim that escapes U+2028/2029 on stdout (fragile on Windows: `.cmd`/`EFTYPE` problem already documented at `codex-cli.adapter.ts:222`); (3) patch the SDK with `patch-package` replacing the readline loop. Recommend (1). Whichever, add a unit test with a fixture line containing U+2028 inside an `aggregated_output` string.
- `ollama-cloud-metadata.service.ts:382,404,426`: replace the fabricated `DEFAULT_CLOUD_CONTEXT = 128_000` with a nullable/unknown window; read the true window from Ollama itself (`ollama ps` CONTEXT column locally; for direct cloud there is no verified endpoint here), otherwise report "unknown" and fall back to the model's `getContextUsage()` result. Doc fact: cloud models run at maximum context by default, so 128k is not a cap Ollama applies.
- Ollama Cloud and caching (D5): the Anthropic-compat layer has no `cache_control` and returns only `input_tokens`/`output_tokens`, so the Claude SDK cannot show cache reads and Ptah cannot assume the prefix is discounted. Billing there is plan-based, not per token (not verified). Ptah's cost for Ollama Cloud is therefore context size per request, which makes A1 (autoCompactWindow) and keeping the proxy MCP set small matter more on that path.
- `opencode-cli.adapter.ts:524-541, 606`: add to the `OPENCODE_CONFIG_CONTENT` JSON, per documented keys: `compaction: {auto:true, prune:true, reserved:<n>}` and optionally `snapshot:false`. Per-MCP tool filtering: documented `tools` map and `mcp.<name>` entries; whether `tools` accepts globs like `ptah_*` is unverified.
