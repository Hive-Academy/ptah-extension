## Findings

1. **[Blocking] Successor session ID is not known when `ptah_session_handoff` returns (`tabId` vs SDK `realSessionId` gap) — missing from Current behavior, Acceptance Criteria, and Risks**
   - **Section**: `## Current behavior` (lines 24–50, 61–69), `## Acceptance criteria` (Criteria 6, 7, 8, 10, 11), `## Risks` (lines 284–292), `## Decisions` (Decision 5, lines 382–390).
   - **Evidence**:
     - `SessionHandoffService.guardAndStart` and `start` (`libs/backend/cli-agent-runtime/src/lib/session-children/session-handoff.service.ts:209, 267-290, 309-312`) mint a placeholder UUID `tabId = SessionId.create()` for the successor and call `host.startHandoffSession`.
     - When `ChatSessionService.startHandoffSession` (`libs/backend/rpc-handlers/src/lib/chat/session/chat-session.service.ts:1408-1424`) returns `{ success: true }`, the successor's SDK query has only just launched; its canonical SDK session UUID (`realSessionId`) does not exist until the Claude CLI emits its `system: 'init'` message on the stream (`libs/backend/agent-sdk/src/lib/sdk-agent-adapter.ts:1103-1112, 1645-1721`), which fires `SDK_TOKENS.SDK_SESSION_ID_RESOLVED_CALLBACK_REGISTRY`.
     - Every durable store (`SessionMetadataStore` at `libs/backend/agent-sdk/src/lib/session-metadata-store.ts:433-437`, `SessionOrganizationStore` at `libs/backend/session-organization/src/lib/session-organization.store.ts:108-109`, and `ISessionOrganizationRecorder` at `libs/backend/platform-core/src/interfaces/session-organization-recorder.interface.ts:8-10`) keys rows strictly by the SDK `realSessionId`, never by `tabId`.
     - Compare `SessionSpawnerService.onSessionIdResolved` (`libs/backend/cli-agent-runtime/src/lib/session-children/session-spawner.service.ts:229, 863-909`), which listens to `SessionIdResolvedCallbackRegistry` to bind `tabId → realSessionId` before writing durable lineage.
   - **Why it blocks**: If the durable handoff link is written at `handoff()` completion using the successor's `tabId`, that ID will never match the successor's `sessionId` (`realSessionId`) in `SessionMetadataStore` or `session:list`, breaking Criteria 6, 7, 8, 10, and 11 both live and after restart. The specification must require binding/rekeying the successor's provisional `tabId` to its resolved `realSessionId` (and define behavior while the successor's `realSessionId` is still pending or if the successor fails before `init`).

2. **[Serious] Turn-end stop trigger conflates `session:turnEnded` (Stop hook) with `markTurnEnded` / stream `result` boundary, risking truncation of the caller's final assistant message and stats**
   - **Section**: `## Acceptance criteria` (Criterion 2, lines 201–205), `## Risks` (Risk 1, line 286), `## Decisions` (Decision 1, lines 340–347).
   - **Evidence**:
     - `StopHookHandler` (`libs/backend/agent-sdk/src/lib/helpers/stop-hook-handler.ts:87-113`) emits `sdkAdapterEvents.emitTurnEnded` (which `SessionLifecycleNotifier` at `libs/backend/rpc-handlers/src/lib/handlers/session-lifecycle-notifier.ts:116-141` broadcasts as `session:turnEnded`) inside the SDK `Stop` hook.
     - As documented in `SessionTurnStateRegistry` (`libs/backend/agent-sdk/src/lib/helpers/session-turn-state.registry.ts:41-48`), the SDK dispatches the `Stop` hook from its transport read loop **before** the stream consumer has pulled the final `assistant` message and `result` message of the same turn.
     - Conversely, `releaseTurnOnResult` / `onTurnTerminal` (`libs/backend/agent-sdk/src/lib/sdk-agent-adapter.ts:1133, 2307-2310`) and `ChatStreamBroadcaster` flushing (`libs/backend/rpc-handlers/src/lib/chat/streaming/chat-stream-broadcaster.service.ts:286-303`) occur on the in-stream `result` / `message_complete` boundary.
   - **Why it matters**: Treating `session:turnEnded` and `markTurnEnded` as interchangeable invites stopping the caller inside `SdkAdapterEvents.onTurnEnded`. Calling `endSession` there aborts `rec.abortController` (`libs/backend/agent-sdk/src/lib/helpers/session-lifecycle/session-control.service.ts:299, 316`) before the caller's final assistant message, `SESSION_STATS`, and terminal `turn_state` chunk are drained and flushed to the webview, causing `ChatStreamBroadcaster` (`chat-stream-broadcaster.service.ts:346-350`) to record `aborted_streaming`. In addition, Criterion 2 only names normal turn end (`session:turnEnded / markTurnEnded`); it must also specify that if the caller's turn ends via failure/error after `ptah_session_handoff` already succeeded, the caller's SDK session is still stopped once that turn terminates.

3. **[Serious] Late-completing `start()` after the 30s deadline can still record handoff state inside `SessionHandoffService.start`**
   - **Section**: `## Current behavior` (lines 56–60), `## Acceptance criteria` (Criterion 5, lines 215–218), `## Risks` (Risk 3, line 288).
   - **Evidence**:
     - In `libs/backend/cli-agent-runtime/src/lib/session-children/session-handoff.service.ts:213-236`, `withDeadline(attempt, SESSION_HANDOFF_START_TIMEOUT_MS)` races `this.start(...)` against a 30s timer. When `result === TIMED_OUT`, `guardAndStart` reverts adoption and returns `ok: false` to the caller, while `this.start(...)` remains in flight until `host.startHandoffSession` settles.
     - Inside `this.start(...)` at `session-handoff.service.ts:309-312`, `this.remember(record.tabId, { sdkSessionId: record.realSessionId, tabId })` executes unconditionally whenever `outcome.started` is `true`, even after the 30s timeout has already refused the handoff.
   - **Why it matters**: Risk 3 only states that the *stop* must not be armed on timeout, missing that `this.start()` currently mutates handoff state (`this.remember`) before `withDeadline` checks whether the deadline expired. Criterion 5 and Risk 3 must explicitly require that a timed-out handoff whose `start()` resolves late does **not** persist the handoff chain, mark the caller `Handed off`, or arm the caller stop.

4. **[Serious] Unresolved ambiguities in session-tree nesting across `groupBy` modes, canvas rail state buckets, multi-hop chains (`A → B → C`), and VS Code webview (`organizationAvailable = false`)**
   - **Section**: `## Current behavior` (lines 119–129), `## Out of scope` (line 190), `## Acceptance criteria` (Criteria 6, 7, 11, lines 219–227, 239–241).
   - **Evidence**:
     - **Previous-sessions `groupBy` modes & server contiguity**: `PreviousSessionsModalComponent` (`libs/frontend/chat/src/lib/components/organisms/previous-sessions/previous-sessions-modal.component.ts:216-222`) defaults `groupBy` to `'none'` (and forces `'none'` when `organizationAvailable()` is `false`, which `libs/frontend/chat/src/lib/services/session-list/session-list-view.store.ts:30-34` documents as the VS Code host state). Both `groupSessionRows` (`libs/frontend/chat/src/lib/components/organisms/previous-sessions/session-row-groups.ts:44-62`) and `applySessionListQuery` (`libs/backend/rpc-handlers/src/lib/handlers/session-list-query.ts:73-91, 147-153`) only keep parent/child rows contiguous and indented when `groupBy === 'parent'`. Criterion 6 does not state whether handoff nesting applies in the default `groupBy: 'none'` view (and `groupBy: 'parent'`), what happens in `groupBy: 'status' | 'task'`, or whether durable storage must work when SQLite `SessionOrganizationStore` is absent (`libs/backend/platform-core/src/interfaces/session-organization-recorder.interface.ts:12-15`).
     - **Canvas rail state buckets vs card nesting**: `groupRailTiles` (`libs/frontend/canvas/src/lib/canvas-rail/canvas-rail-grouping.util.ts:58-74`) buckets cards by live state into `Running`, `Background work`, `Waiting / Needs input / Error / Idle`, and `Finished` (collapsible in `libs/frontend/canvas/src/lib/canvas-rail/canvas-rail.component.ts:248-263`). While the successor is `Running`, the stopped predecessor's state is `done` (`Finished`). For the predecessor card to *"sit directly under the new session's card"* (Criterion 6) without *"Rebuilding ... the canvas rail groups"* (Out of scope, line 190), Criterion 6 must specify that an open handed-off predecessor card is attached directly beneath its open successor card inside the successor's rail group (without counting toward `running` / `background` chip or cap counts) and returns to its own state group when the successor card is not open in the rail.
     - **Multi-hop chains (`A → B → C`) in the session tree**: Criterion 6 specifies *"indented one level directly under the new session"*, while Criterion 11 specifies multi-hop chains `A → B → C → D`. When `A` hands off to `B` and `B` hands off to `C`, does `A` nest under `B` (depth 2, up to `MAX_SESSION_ROW_DEPTH = 3` in `session-row-groups.ts:29`) or flatten at depth 1 under `C` (or under `B` at depth 1)?

5. **[Moderate] Webview `AgentMonitorStore` re-parenting and `SessionLivenessRegistry` `awaiting-background` clearing are underspecified**

   - **Evidence**:

     - In `SessionTurnStateRegistry.settleTurn` (`libs/backend/agent-sdk/src/lib/helpers/session-turn-state.registry.ts:352-368`), if the `Stop` hook snapshot reported background tasks, the turn settles to `'awaiting-background'`, which `SessionLivenessRegistry` (`libs/frontend/chat-state/src/lib/session-liveness.registry.ts:9-12`) treats as live and `SessionLivePhaseIndicatorComponent` (`libs/frontend/chat/src/lib/components/atoms/session-organization-chips/session-live-phase-indicator.component.ts:47-74`) renders as the moon icon (`Waiting on background work`). ## Lane-introduced constraints

1. **Stopping the caller must not stop or mark interrupted any adopted CLI lane or child session (Criterion 4, Risk 2)** — *Justified*: required to preserve `TASK_2026_655` work adoption when `SessionLifecycleManager.endSession` tears down the caller.
2. **Failed, refused, or timed-out handoffs must not stop the caller and must revert provisional adoption (Criterion 5, Risk 3, Decision 2)** — *Justified*: directly implied by `context.md` Decision 1 ("Old session after a successful handoff") and protects the caller from losing active work on a failed handoff.
3. **Top-level fallback when the successor is not in the loaded `session:list` page (Criterion 7)** — *Justified*: matches existing `nestByParent` behavior (`libs/frontend/chat/src/lib/components/organisms/previous-sessions/session-row-groups.ts:94-97`) so paginated predecessors never disappear from the list.
4. **Hiding `Linked sessions` when a session has no handoff links, and keeping the compact 14px inspector rail unchanged (Criterion 9, Decision 6)** — *Justified*: the 14px rail (`libs/frontend/chat/src/lib/components/organisms/session-inspector/session-inspector.component.html:1-72`) only fits compact metric buttons, and sessions outside a handoff chain should not render an empty section.
5. **Restart durability for both session-tree nesting/`Handed off` and the `Linked sessions` chain (Criteria 6 & 10, Decision 5)** — *Justified*: required for "Keep its history" and the session tree/inspector to remain coherent across app restarts.
6. **Updating `sessionHandoffReply` tool text and `plugins/ptah-core/skills/session-handoff/SKILL.md` so they no longer instruct the user to close the old session (Criterion 12, Decision 7)** — *Justified*: existing text (`libs/backend/vscode-lm-tools/src/lib/code-execution/mcp-core/session-tool-handlers.ts:333-346` and `SKILL.md:61-64`) contradicts the user's decision.
7. **Not adding `handed_off` to `SESSION_WORKFLOW_STATUSES` and not registering the predecessor in `SessionChildRegistry` (Out of scope lines 186–189, Decisions 3 & 4)** — *Justified*: `SESSION_WORKFLOW_STATUSES` drives `groupBy: 'status'` ordering, and `SessionChildRegistry` membership would cause `ptah_session_stop` and `ptah_session_handoff` guards to mistreat a handed-off predecessor as a supervised child.
8. **Single-level indentation phrase ("indented one level directly under the new session") in Criterion 6** — *Needs clarification (see Finding 4)*: justified for a 2-session handoff, but ambiguous for multi-hop chains (`A → B → C` in Criterion 11).
