## Architecture decision

- Chosen approach: one handoff service owns the kept-success gate. It arms a one-shot caller stop, remembers the refusal map, and holds successor-tab → caller SDK id until `SessionIdResolvedCallbackRegistry` fires. A small chain document in workspace state storage records directed SDK-id edges. The stream broadcaster notifies the service only after it has flushed the turn. The webview learns a kept lane reparent from one new monitor message, and marks the ended caller idle. The expanded inspector reads `session:handoffChain` and renders `ptah-inspector-linked-sessions`.
- Rationale: the tool result returns before the turn ends (`session-tool-handlers.ts:450-456`), and `endSession` aborts the caller's controller (`session-control.service.ts:299`). Stopping from inside `handoff()` or from `session:turnEnded` drops the flush. The successor SDK id does not exist at `handoff()` return (`chat-session.service.ts` returns success before init, as cited in the task description). Organization SQLite is absent on VS Code, and `SessionMetadata` is what `session:list` projects, so the chain cannot be a field on that row.
- Rejected alternatives:
  - Stop inside `handoff()` or on the Stop hook. Loses the tool result or the terminal chunks.
  - Let `start()` keep calling `remember` after a timeout. The task forbids a late start from arming a stop or writing a chain (`session-handoff.service.ts:309-312`).
  - Store the link on `SessionMetadata` or `parentSessionId`. Collides with `session:list` and with supervised children, which `ptah_session_handoff` refuses (`session-handoff.service.ts:167-174`).
  - Re-broadcast `agent-monitor:spawned` for the new parent. `onAgentSpawned` treats that as a reopen (`agent-monitor.store.ts:1431-1468`) and the spawn listener also persists a CLI session (`agent-events.ts:174-188`).
  - Put the chain inside `ptah-inspector-session-stats`. The design spec forbids growing that file, and the section must show when the metrics snapshot is missing.
- Assumptions:
  - `registry.find` checks `byTabId` first, then `bySessionId` (`session-registry.service.ts:415-416`). `onCallerTurnFlushed` always calls `endSession(SessionId.fromTrusted(tabId))` with the armed caller tab id. Passing the resolved SDK id also finds the record, and this plan does not do that: the tab id is the registration key (`session-registry.service.ts:322`). `endRecord` does not build `chat:sessionEnded`. The stream broadcaster does, and only after the record is already gone (`chat-stream-broadcaster.service.ts:467-472`), with `{ tabId, sessionId: turnSessionId }`. `turnSessionId` becomes the SDK id once an event carries it (`chat-stream-broadcaster.service.ts:204-210`). The flush hook runs inside that stream, after the terminal publish and before that `finally`, so the payload keeps the caller tab id and the resolved session id.
  - Aborting the caller query from `endSession` after `chat:complete` surfaces in the broadcaster `catch` as it does for a user abort. The stop does not rely on that catch to clear `awaiting-background`. It calls `forceIdle` itself.
  - `ptah_get_dependencies` was still `building`. Tag evidence above is the cycle check. If a later graph shows rpc-handlers not already importing cli-agent-runtime, the new import is still allowed by `eslint.config.mjs:369-376`.
- Effect on existing code: `remember` moves from `start()` to the kept branch of `guardAndStart`. The file header that says the caller is not stopped is rewritten. The 64-cap refusal map stays. No list, rail, organization, or metadata-row change. `AutoHandoffSourceCloserService` is left as it is.

## Integration architecture

- Data flow:
  1. `ptah_session_handoff` runs `SessionHandoffService.handoff`. Adoption is still provisional before `start()` resolves.
  2. Timeout, refusal, or host `started: false`: revert adoption, return the refusal, do not `remember`, do not arm, do not pending-bind. A `start()` that resolves later finds the attempt already closed and does not `remember`.
  3. Kept success: `remember` the refusal entry, settle adoption as kept, emit `agent:reparented` for the lane ids, set pending successor tab → caller SDK id, arm the stop, return the tool result. The model finishes the turn. The result message hits `markTurnEnded` / `settleTurn`. The broadcaster flushes and publishes `chat:complete` or the error terminal. Then `onCallerTurnFlushed` matches the caller, `forceIdle`s both ids, and `endSession(SessionId.fromTrusted(callerTabId))`. The broadcaster's later `chat:sessionEnded` carries that tab id and `turnSessionId`. `handleSessionEnded` marks both idle.
  4. Later, `system: init` notifies the registry. If that tab is pending, `append(callerRealId, successorRealId, workspaceRoot)` runs. The chain store fires `onLinkWritten`. `wireAgentEventListeners` broadcasts `sessionHandoff:linked`. The open inspector reloads `session:handoffChain`.
  5. `resolveParentSessionId` on that same notify moves lane parents from the successor tab id to the successor SDK id. The running cap and AGENTS follow `parentSessionId`.
- State or persistence: refusal map stays in process, cap 64, caller tab key. Pending bind stays in process until the successor id resolves or the successor is gone. The chain document `ptah.handoffChain` lives in the workspace storage for the handoff's `resolvePaths` root (`session-handoff.service.ts:442`), same port session metadata uses, separate key. On a workspace-scoped host that root's `getStorageForWorkspace` is the only store written. It survives restart. It is not a `SessionMetadata` field and not an organization row.
- External boundaries: tool result text is model-facing, not a new IPC schema. The RPC params and the stored document are Zod-parsed in the backend handler and the chain store. The reparent message, the linked message, and the RPC result are narrowed from `unknown` in the webview, with no `zod` import. Session ids on the RPC are `UUID_REGEX`. The open action reuses `SessionRowActionsService`. No `openExternal`. No new secret.
- Failure and rollback:
  - Stop fails: log a real `Error`, leave the session as the abort left it, do not report a second success. The tool text has already been returned.
  - Chain write fails, including storage not ready and a workspace root with no scoped store: log a real `Error`, serve the edge from that workspace's memory document, retry the document write on the next read or append for that path. The stop is independent. Do not write another workspace's document.
  - Successor never receives a real id: no edge, section absent, caller still stopped if the tool succeeded and the turn flushed.
  - Session name missing: row title `Session ` + 8 hex-or-id characters, link kept.
  - CLI without a webview: `broadcastMessage` failures are caught. The RPC returns `[]` or the chain. The process does not throw. No tree and no inspector are added.
  - Malformed RPC, message, or document: drop or RPC-reject. No cast. Section absent.
- Observability: stop and chain failures go through `Logger.error` (`logger.ts:156-174`) with a real `Error`. Existing handoff traces stay on `IOutputChannel` (`session-handoff.service.ts:540-547`). A flush that never arrives has no log. That is the no-extra-deadline rule.

## Decisions

1. Stop is armed on the tool-visible success and fired from the broadcaster after the terminal flush.
   Options: stop in `handoff()`; stop on `session:turnEnded`; stop from `onCallerTurnFlushed` after `chat:complete` or the error flush.
   Evidence: criteria 1 and 2. `endSession` aborts `rec.abortController` (`session-control.service.ts:299`). The Stop hook runs first (`session-lifecycle-notifier.ts:116-141`). `finally` force-idles only `generating` (`chat-stream-broadcaster.service.ts:387-389`), so `forceIdle` is explicit.
   Reversible: yes, until a release depends on the timing.

2. `remember` moves out of `start()` onto the kept branch. Late `start()` writes nothing.
   Options: a flag checked inside `start()`; delete the call from `start()` and invoke it only after `guardAndStart` sees `result.ok`.
   Evidence: `start()` calls `remember` before it returns (`309-312`), which is why a timeout winner can still persist. The race disappears if `start()` does not write.
   Reversible: yes.

3. The chain is a workspace-state document `ptah.handoffChain`, edges of SDK ids, written on registry notify into the handoff workspace's storage. Not a metadata field, not organization, not the 64-cap map. Reads and writes wait for async readiness and never call synchronous `get` / `update` on a not-ready Electron worker store.
   Options: column on `SessionMetadata`; SQLite organization; one document on the active workspace with synchronous `get`; this document, scoped and async.
   Evidence: criteria 8 and 13. `SessionMetadata` (`session-metadata-store.ts:421-508`) is what list rows are built from. Detail keys use `ptah.session:` (`587`). `IStateStorage` (`state-storage.interface.ts:12-29`) is registered for the CLI (`container.ts:517`) and is the VS Code memento port. Electron `get` and `update` throw until `whenReady` (`electron-state-storage.ts:116-120`, `139-140`, `201-203`). `SessionMetadataStore.readStorage` branches on `isAsyncStateStorage` (`session-metadata-store.ts:1006-1009`). `getStorageForWorkspace` returning `undefined` must not be replaced with the active store (`workspace-scoped-state-storage.interface.ts:32-38`). The caller's root is `resolvePaths` (`session-handoff.service.ts:442`). Cap 256, drop oldest, because an unbounded document is a write amplification with no product need. The live refusal map still dies on restart, so who may hand off is unchanged.
   Reversible: yes, with a one-time read of the old key if the key is renamed before release. Nothing is stored yet.

4. Lane reparent is a new `agent-monitor:reparented` message on kept settle only.
   Options: reuse `agent-monitor:spawned`; push on provisional adopt and again on revert; this message.
   Evidence: `onAgentSpawned` reopens a card (`agent-monitor.store.ts:1449-1458`). Provisional adopt is reverted on failure (`session-handoff.service.ts:237-239`), and the webview has not been told, so a revert needs no UI message. Existing `resolveParentSessionId` (`chat-message-handler.service.ts:908-909`) covers the tab → SDK hop once the parent is the successor tab id.
   Reversible: yes.

5. Linked sessions is a presentational molecule in chat-ui, mounted only by the live `SessionInspectorComponent` in `libs/frontend/chat`, and loaded by a chat client through `ClaudeRpcService`. Open reuses `SessionRowActionsService.openSession`. The current row does not call it. The chain is not a field on `SessionInspectorModel`.
   Options: RPC inside the chat-ui component; mount a second inspector under chat-ui; put the chain on `SessionInspectorStore`; this split.
   Evidence: `design-spec.md` component map names `libs/frontend/chat/.../session-inspector.component.html` after lines 163–183. Canvas imports that class from `@ptah-extension/chat/inspector` (`canvas-inspector-dock.component.ts:9`, `inspector.ts:1-4`). This worktree has no session-inspector file under chat-ui (`chat-ui/src/index.ts:265` exports the stats molecule only). `openSession` (`session-row-actions.service.ts:50-56`) is how a previous-sessions row opens. Design spec line 81: the current control does not open a second session. `SessionInspectorModel` (`session-inspector.types.ts:67-76`) is the agent aggregate.
   Reversible: yes. Moving the section inside the stats component would violate the design spec.

6. Tool and skill success copy say the old session was stopped and its history was kept. They do not say Handed off, and they are not rewritten if a later `endSession` fails.
   Options: say "will be stopped"; say "was stopped" and log a failed stop without a second confirmation.
   Evidence: criterion 10 versus the NFR that a failed stop must not report the caller as stopped. The tool result is required to return before the stop (criterion 1), so it cannot observe `endSession`. The log is the failure report (`Logger.error`).
   Reversible: yes.

7. `session:handoffChain` is served on every host (`requires: []`), returns `{ sessions: [] }` when there is no chain or no store, and does not extend `session:list`.
   Options: Electron-only capability; empty list on every host.
   Evidence: criterion 11. `sessionOrganization` already uses `requires: []` and an optional store (`manifest.ts:357-366`). `session:` is allowlisted (`rpc-handler.ts:48`).
   Reversible: yes.

8. `endSession` receives the caller tab id.
   Options: pass `realSessionId` when it is set; pass the tab id.
   Evidence: `find` checks `byTabId` first (`session-registry.service.ts:415-416`). Registration stores the record under the tab id (`322`). The webview end message is not built in `endRecord`. The broadcaster sends `{ tabId, sessionId: turnSessionId }` after the record is gone (`chat-stream-broadcaster.service.ts:467-472`), and `turnSessionId` is the SDK id once the stream has seen it (`204-210`). The flush hook runs in that function, so both ids are on the payload when the stop uses the tab id. `handleSessionEnded` marks idle for both strings (`chat-message-handler.service.ts:750-758` is where that mark is added).
   Reversible: yes.

9. `onLinkWritten` lives on `ISessionHandoffChain`. `wireAgentEventListeners` is the only subscriber.
   Options: subscribe from `SessionHandoffService`; subscribe in `register-rpc-surface.ts` beside the call; subscribe inside `wireAgentEventListeners`.
   Evidence: `wireAgentMonitorListeners` is `agent-events.ts:165`. The function already holds `WebviewManagerLike` (`40-42`) and is invoked from `register-rpc-surface.ts:254`. Resolving `SessionHandoffService` pulls `SDK_SESSION_LIFECYCLE_MANAGER` (`session-handoff.service.ts:111-112`). `rpc-handlers` already imports cli-agent-runtime, so the RPC batch cannot be parallel with the runtime batch that exports the new token.
   Reversible: yes.

10. Webview wire parsers stay hand-written. Zod stays on the RPC schema and the stored document.
    Options: Zod in `AgentMonitorMessageHandler`, `ChatMessageHandler`, and `HandoffChainClient`; the existing `unknown` parsers.
    Evidence: TASK_2026_187 Unit 10 removed Zod from the initial handlers (`chat-message-handler.service.ts:110-113`, `786-788`). `parseSessionHandoffOpenedPayload` is the pattern (`agent-session-adoption.service.ts:49-51`, `97-119`). Neither the chat handler nor `agent-monitor-message-handler.service.ts` imports `zod`.
    Reversible: yes. A later lazy chunk could take Zod. These handlers are on the initial path.
