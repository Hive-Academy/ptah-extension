## Findings

1. **[Moderate, not a Batch B defect] Write/read mismatch until Batch A lands** — `libs/backend/rpc-handlers/src/lib/handlers/agent-rpc.handlers.ts:307-314` (this worktree, based on `main`, does not include `fix/cursor-key-secrets`) still writes `agent:setConfig{cursorApiKey}` to `workspace.setConfiguration('ptah', 'provider.cursor.apiKey', …)` and `isCursorApiKeyConfigured()` (`agent-rpc.handlers.ts:1026-1037`) still reads that same setting. Batch B's `CursorCliAdapter` (`cursor-cli.adapter.ts:192-206`) no longer reads the settings file at all (the `readFileSync`/`homedir`/`join` imports are gone). If Batch B ships to `main` without Batch A (`fix/cursor-key-secrets`), a user calling `agent:setConfig{cursorApiKey}` gets a success response and `cliDetection.invalidateCache()` fires (`agent-rpc.handlers.ts:313`), but the subsequent `detect()` re-read finds nothing (`resolveCursorApiKey()` checks `CURSOR_API_KEY` then the secrets resolver, and the write never touched the secret store) — Cursor silently stays "not installed." This is answer to logic question 1 (silent failure) but is a merge-order/integration hazard between the two batches, not a bug inside the reviewed diff. Fix: land Batch A and Batch B together (or gate Batch B's merge on Batch A), and do not report Batch B alone as done to a user needing the Cursor key to work end to end.
2. **[Minor, pre-existing, unchanged by this diff] Generic SDK error text is logged/emitted with `detail`** — `cursor-cli.adapter.ts:373-385` (`runTurn`'s catch) logs `this.logger?.error('[CursorCliAdapter] SDK run failed', { detail: errorMessage })` and emits `summarizeCliSdkError(error, 'Cursor')` to both `output` and `segment` (visible to the UI/transcript). `errorMessage` is `error.message` from whatever `@cursor/sdk`'s `Agent.create`/`send`/`stream()` throws; if the SDK's own auth-failure message embeds the key (e.g. an "invalid key: sk-…" style message), it would flow into the logger and the user-visible segment. This code path and its shape are unchanged by this diff — only where `apiKey` comes from changed, not this catch block — so it is not a regression introduced by Batch B, and the batch's own new resolver-failure path (`resolveCursorApiKey`'s catch, `cursor-cli.adapter.ts:200-204`) correctly logs fixed text only. Recorded for completeness against the "never log the value" requirement in `task.md`; no fix required in this batch.
3. **[none — verified, no defect]** Every other check in the CHECK list (resolver await coverage, other `provider.cursor.apiKey` readers inside `cli-agent-runtime`, cache-invalidation semantics, DI registration order, manual-construction sweep, and the test run) held up under direct inspection — see sections below.
