# Research Report - TASK_2026_367 (harness-sync / mcp-directory / memory-curator)

## Question

- Decision this supports: how to fix C3 (harness-sync), C6 (mcp-directory OAuth
  swallow) and C4 (memory-curator prompt cap) for TASK_2026_367's implementation
  plan.
- Question: for each of the four sub-questions (Q1a preflight budget, Q1b
  blocked set, Q1c/Q2 PulseMCP 410, Q3 OAuth failure surfacing, Q4 curator cap),
  what does the code do today, what is the root cause, and what should the fix
  be.
- Bounds: no code was changed. C1/C2/C7 (spawn runtime, event-loop lag,
  SubagentRegistry race) are covered by the sibling `research-report.md` and are
  out of scope here.

## Answer

**Q1a** — the 1500 ms preflight budget is a real, wired cancellation
(`AbortController` threaded into the async, yielding hash walk), not a
background leak; it was a background leak before TASK_2026_323/B8 but that is
fixed. It times out 8/8 times in this log because the workspace's `~/.ptah/user`
walk (3 plugins: `ptah-core`, `ptah-nx-saas`, `ptah-angular`) runs concurrently
with a 12-agent tribunal spawn burst that measured up to 2923 ms of
`[event-loop] lag` on the same Electron main thread — the timer and the hash
walk's cooperative yields both depend on an event loop that is saturated by
CLI-spawn adapter resolution at the same moment. Recommend: keep the budget as
a safety net, but skip the preflight call entirely when the last **full** pass
for this workspace is fresh (the reconciler already tracks this via
`minIntervalMs`/`lastPassAt` for the _preflight_ throttle, but a tribunal burst
of concurrent spawns each pays the throttle window independently — see Local
consequences).

**Q1b** — `blocked: 12` (`missing ∩ foreign`) is the documented, closed
mechanism in `harness-sync/CLAUDE.md`: 12 desired `.claude/skills/<slug>` paths
are occupied by directories Ptah cannot prove it wrote (no manifest entry, no
legacy `.ptah-managed.json`, no `source: ptah` signature). This is not a new
defect — TASK_2026_306 already built the consent-gated repair
(`HarnessBlockedRepairService` + quarantine convention) for exactly this shape,
and the reconcile log already de-duplicates the WARN per unchanged set
(`"Blocked set unchanged since the last full pass"`, seen at
`tmp/logs/log.log:1317`). The only thing not yet shipped is the **consent
dialog UI** (Batch 9) that lets a user select paths to repair — nothing here
needs a design change, it needs that already-planned UI, or, if out of scope
for this task, no further action (the log line is doing its job).

**Q1c/Q2** — PulseMCP's free, no-key `v0beta` API
(`https://api.pulsemcp.com/v0beta/servers`) is what this codebase's
`PulseMcpRegistrySource` calls with `requiresApiKey = false`. It now returns
`410 Gone`. PulseMCP's current documented API is `v0.1`
(`https://api.pulsemcp.com/v0.1/servers`), and it is a **private, API-key-gated
B2B "sub-registry" offering** ("Contact us to discuss how we can tailor our MCP
server registry") — not a drop-in free replacement. Recommend removing the
source rather than pointing at the new URL, because the new URL cannot be
satisfied without a paid API key this codebase has no provisioning path for
(`requiresApiKey = false` would become a lie).

**Q3** — the RPC result already carries `success:false` + a sanitized `error`
string, and the frontend (`oauth-surface.component.ts:467-481`) already renders
it via `connectError`. Nothing is silently swallowed on the wire or in the UI.
The confusion in the log is `RpcHandler`'s generic "succeeded" debug line,
which means "the handler resolved without throwing" (transport-level), logged
right after the handler's own `ERROR` line for the same call — a legitimate
but confusing juxtaposition, not a data-loss bug. The real defect is UX: the
thrown message ("No OAuth authorization-server metadata found … may not
support OAuth discovery") never tells the user Firecrawl needs an API key
instead, and the Connect button has no pre-flight discovery check before the
user submits. Recommend a typed failure reason
(`McpDirectoryConnectOAuthResult.reason?: 'no-oauth-discovery' | ...`) mapped
to a UI hint, discovery run on blur/before-submit rather than only inside
`connect()`.

**Q4** — the 32 KB head+tail cap (`clampTranscript`,
`CURATOR_TRANSCRIPT_MAX_CHARS`) is deliberate and well-documented (closes
TASK_2026_352's 170 655-char prompt fault), but it drops 91% of a 366,540-char
transcript in one observed run. The curator model is unpinned by default
(`CURATOR_DEFAULT_MODEL_TIER = 'haiku'`) and nothing in the internal-query path
reads the resolved model's context window — `ProviderModelsService` only
carries `contextLength` for OpenRouter-style catalog entries, unconsulted by
the curator. `skill-synthesis`'s `TranscriptWindowReader`
(`libs/backend/skill-synthesis/src/lib/archaeology/transcript-window.reader.ts`)
is an existing, pure, turn-indexed, multi-pass retrieval engine built for
exactly this problem (bounded windows, head/tail/range/search, omission
markers) and is the natural reuse target for a chunked map/reduce curation
pass. Recommend option (1), chunked curation reusing/adapting
`TranscriptWindowReader`, over a static cap raise or context-window-scaled cap
— see Options table for cost/tradeoffs of all three.

## Options

### Q1a — preflight budget

| Option                                                                                                                                                                                                                                                           | Fit here                                                                                                                                                                                                                                                                                                                       | Cost to adopt                                                                                                                                                                                                                                                                                 | Known failure mode                                                                                                                                                                                                                        |
| ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Skip preflight for a spawn burst when a **recent full pass exists and the desired state has not changed since** (extend `HarnessPreflightService.throttled` to consider "any pass — preflight or full — within N ms", not just the last _preflight's own_ stamp) | Fits: the reconciler already logs "Blocked set unchanged since the last full pass" — the machinery for "nothing changed" already exists at the reconcile-report level; extending the throttle window to cover concurrent per-agent preflight calls closes the actual gap (12 agents in one burst each pay their own preflight) | Small — extend `lastPassAt` semantics or share a single in-flight preflight promise per workspace root across concurrent callers (coalesce, like `InternalQueryConcurrencyGate` does for lanes)                                                                                               | A coalesced preflight could mask a genuinely stale one if two callers race before the first's Promise settles; needs the same "stamped BEFORE the pass" discipline already used for the throttle                                          |
| Raise the default budget (e.g. 3000 ms)                                                                                                                                                                                                                          | Cheap, but treats the symptom (measured event-loop lag up to 2923 ms in this same session) not the cause; a busier tribunal burst (more agents) will blow through any fixed budget again                                                                                                                                       | Trivial (one constant)                                                                                                                                                                                                                                                                        | Purely cosmetic — the underlying event-loop contention from concurrent CLI spawns (documented root cause of C7) is untouched, and a bigger budget makes users wait longer for the "session continues" line with no better odds of success |
| Make the hash walk cheaper (e.g. skip content hashing for skills already verified this process-lifetime)                                                                                                                                                         | Addresses CPU cost of the walk itself                                                                                                                                                                                                                                                                                          | Larger — needs a new in-memory cache keyed by source path + mtime, and a correctness argument that mtime is a safe proxy (harness-sync's own `.gitignore`/`preflight` docs already argue AGAINST mtime as an input for the SKILL.md migration marker, for a similar but not identical reason) | Risk of the exact investigation-cost mistake flagged in `harness-sync/CLAUDE.md` (SKILL.md migration bullet): mtime does not reliably reflect subdirectory content changes                                                                |

**Recommendation**: coalesce/throttle concurrent preflight calls per workspace root during a spawn burst (12 agents in ~seconds is the observed trigger), rather than raising the budget or re-engineering the hash walk. This is the smallest change that matches the documented intent ("Throttled per workspace… this is what makes the background drain affordable") — the throttle exists, it just isn't shared across the 12 near-simultaneous `AgentProcessManager.doSpawn` callers in this session.

| **(1) Chunked curation** — split the transcript into `TranscriptWindowReader`-style windows, run `extract` per window, then a `resolve`/merge pass over the union of drafts | Fits best: `SessionArchaeologistService`'s multi-pass "model requests ranges, TypeScript serves them" pattern already exists in this codebase and solves the identical problem (bounded per-pass input, deterministic windowing, omission markers); the curator's `extract`→`resolve` shape already has a merge step (`related` memories, `mergeTargetId`) that chunk-level drafts could feed into unchanged | Largest of the three: multiplies curator LLM calls per PreCompact firing (N windows × 1 extract call, vs. today's 1), touches `doCurate`'s control flow, and needs a policy for how many windows to run (all of them? cap at K, tail-weighted like today's clamp?)                                       | More provider spend per compaction — directly in tension with the curator's own design goal ("curation is small, cheap"); needs a budget guard (e.g. max windows per pass) or it re-introduces a cost blowup on the largest sessions, which are exactly the ones this fix targets                                                                                                                                                                                                                                  |
| **(2) Cap scaled to the resolved model's context window, with a hard ceiling**                                                                                              | Not currently wireable without new plumbing: nothing in `InternalQueryService`/`SdkQueryRunner`/`ModelResolver` exposes a context-window figure for the model the curator will actually dial (`ProviderModelsService.contextLength` exists only for OpenRouter-style catalog fetches, and the curator never calls that service)                                                                              | Medium-large: needs `resolveCuratorModel()` (or a new step) to look up the resolved model's context window from wherever `ProviderModelsService`'s catalog lives, thread it through `ICuratorLLM`/`InternalQueryConfig`, and pick a cap = `min(contextWindow * safetyFactor, hardCeiling)`               | The "riding the haiku tier of the resolved provider" default (a TIER ALIAS, not a concrete model id — deliberately, per TASK_2026_159) means the context window isn't even known until the tier resolves to a concrete model at spawn time, which may be AFTER the cap decision needs to be made; and 3 of 11 `ANTHROPIC_PROVIDERS` entries ship no `defaultTiers` at all (per `skill-synthesis/CLAUDE.md`), so a context-window lookup can silently degrade to the same hard ceiling as today for those providers |
| **(3) Smarter selection — keep user turns + final assistant turns, drop tool_result bodies**                                                                                | Cheapest to build; `TranscriptWindowReader`'s own turn renderer already truncates `tool_result` content to 600 chars and `Bash` commands to 80 chars as a MODEL of how to de-noise a turn cheaply, so the pattern for "compress before clamp" already exists in this codebase, just not wired into the curator's `transcript` input                                                                          | Small-medium: needs a pre-clamp transform on the raw transcript (not just a character-boundary cut) that recognizes and compresses tool_result/tool_use blocks the way `TranscriptWindowReader.textOf`/`toolResultMarker` already do, then feeds the compressed text into the EXISTING `clampTranscript` | Single-pass only — a session whose signal is genuinely spread across 300K characters of USER/ASSISTANT prose (not tool noise) still gets clamped to 32 KB; this option reduces waste but does not remove the ceiling, so a 91%-dropped session with little tool noise sees little improvement                                                                                                                                                                                                                      |

**Recommendation**: option (1), chunked curation, reusing (not necessarily inheriting) `TranscriptWindowReader`'s pattern — pure, deterministic, turn-indexed windowing with an explicit omission marker — because it is the only option that actually stops throwing away 91% of a transcript's _content_, not just its noise. Pair it with a variant of option (3) (compress tool_result/tool_use blocks in each window's rendering) to keep per-window/per-call token cost down, since chunking alone multiplies LLM calls. Option (2) is blocked today on missing plumbing (no context-window lookup reaches the curator, and the tier-alias-by-default resolution makes the model unknown until spawn time) and should not be pursued without that plumbing landing first as its own piece of work.
