## Plan conformance and assertion coverage

### B8 — C7a off-thread SDK query seam

- [x] The planned structural port exists and uses the SDK's published `SpawnOptions` and `SpawnedProcess` types (`sdk-process-spawner.port.ts:1-17`).
- [x] The port's current method shape is compatible with `OffThreadProcessSpawner.spawn(options, hooks = {}) → PtahSpawnedProcess` (`off-thread-process-spawner.ts:69-89,443-466`).
- [~] The plan's claimed compiler check is not at the DI injection site. The current real class is checked indirectly by the pre-existing `SdkQueryRunner` assignment, but the symbol binding and local duplicate interface remain disconnected (F2).
- [x] `PtahCliRegistry` injects the existing `SDK_TOKENS.SDK_PROCESS_SPAWNER`; no new token or barrel export was added (`ptah-cli-registry.ts:122-123`).
- [x] The options object actually handed to `queryFn` carries `spawnClaudeCodeProcess`; the new harness captures the real registry-built `options` object rather than constructing a tautological options mock (`ptah-cli-registry-off-thread-spawn.spec.ts:71-83,137-159,172-209`).
- [x] Calling that function passes the exact `SpawnOptions` object through and returns the fake spawner's result (`ptah-cli-registry-off-thread-spawn.spec.ts:182-209`).
- [x] The hook is the same lexical `handleChildStderr` callback assigned to `options.stderr` (`ptah-cli-registry.ts:688-696,742-746`). Once `spawnClaudeCodeProcess` is present, the pinned SDK skips `spawnLocalProcess`, so its own stderr piping and `options.stderr` invocation are dead; the explicit `onStderr` hook is the active path (`node_modules/@anthropic-ai/claude-agent-sdk/sdk.mjs:60`).
- [~] The tests prove equivalent classifier behavior through the hook, but do not assert `capturedHooks.onStderr === capturedOptions.stderr`. The implementation does use the same reference.
- [x] Benign stderr reaches DEBUG and never WARN/ERROR; error stderr reaches WARN and never ERROR (`ptah-cli-registry-off-thread-spawn.spec.ts:211-282`). This maps the plan-pinned classifier callback assertion.
- [x] `cwd`, `env: buildSafeEnv(authEnv)`, and `pathToClaudeCodeExecutable` remain on the SDK `Options` object (`ptah-cli-registry.ts:698-750`). The SDK converts those into the callback's command/args/cwd/env, and the registry delegates that object unchanged. Both worker and inline spawner paths use the supplied command, args, cwd, env, and signal (`off-thread-process-spawner.ts:208-218,501-520`).
- [x] `PTAH_SDK_INLINE_SPAWN=1` and a synchronous worker-construction failure call `spawnInline(options, hooks)`, whose stderr listener invokes the supplied hook (`off-thread-process-spawner.ts:447-465,501-520`). A later asynchronous worker failure emits an error rather than falling back; that is existing documented behavior, not a B8 deviation.
- [x] Token registration precedes CLI-runtime registration in CLI engine (`cli-engine/src/lib/container.ts:638-690`), VS Code (`apps/ptah-extension-vscode/src/di/phase-2-libraries.ts:146-194`), and Electron (`apps/ptah-electron/src/di/phase-2-libraries.ts:179-258`). Tsyringe resolution is lazy, and no earlier registry resolution was found.
- [ ] No container smoke constructs `PtahCliRegistry`; the two app smoke manifests cover only four shared RPC handlers, and the CLI shutdown tests use token fakes (F2).
- [ ] The eight updated direct-constructor call sites do not use a signature-checking spawner fake; seven erase the type with `as unknown as never`, and one passes `null as never` (F2).
- [~] Eight necessary compatibility spec edits fall outside the plan's three-file list and are not reported as a deviation (F3).
- [~] The current full-suite total is correct, but B8 itself adds five tests, not seven (F4).
- [x] No unplanned production behavior, new token, public-barrel change, or host composition-root edit was found.

Test robustness: the new suite genuinely exercises the registry's options object and invokes the installed callback, so its central delegation and stderr assertions are not tautological. Its spawner is typed only against the local duplicate port, it does not assert callback identity, and the other eight constructor harnesses intentionally erase the new dependency's type. The full current suite passes despite those gaps.

### B10 — C5c synthesized start

- [x] `transform()` passes the full `sdkMessage` into `onContentBlockStart` (`stream-event.transformer.ts:61-71`).
- [x] With no active message, `tool_use` emits `[message_start, tool_start]`, stores the message ID and real tool-call ID, and no longer drops the block (`stream-event.synthesized-start.spec.ts:131-169`).
- [x] Text emits `[message_start]`; thinking emits `[message_start, thinking_start]` (`stream-event.synthesized-start.spec.ts:171-232`).
- [x] The handled condition logs DEBUG with context/block type and does not WARN (`stream-event.synthesized-start.spec.ts:234-260`).
- [x] The synthesized `message: {}` takes `sdkMessage.uuid`; if that is absent/falsy it takes `stream-msg-${Date.now()}` (`stream-event.transformer.ts:117-144`). The specs cover the UUID branch, not the timestamp fallback.
- [x] In the real state implementation, `setMessageId` immediately persists a truthy generated ID (`sdk-message-transformer.ts:314-315,358-363`), so the post-synthesis `if (!currentMessageId) return prelude` guard does not fire. If a nonconforming state failed to retain the mutation, it would silently drop the block after emitting the prelude; no production implementation does that.
- [~] Root synthesis changes the turn phase once in the real `SessionTurnStateRegistry`: the first `markGenerating` commits, while a following real start calls it again but receives `null` because `generatingEmitted` is set (`session-turn-state.registry.ts:119-138`). The new B10 test uses a mock and covers only the isolated synthesis call, so it does not itself pin the “exactly once across synthesized + real starts” sequence.
- [x] A synthesized start followed directly by `message_stop` would complete and clear the synthesized ID through the existing state path (`stream-event.transformer.ts:231-259`). The new spec does not exercise this simpler lifecycle.
- [ ] The plan-pinned synthesized → real start → stop test is insufficient. It proves one `tool_start`, one `message_complete`, and cleared current state, but it emits two `message_start`s and does not prove that every start is completed (`stream-event.synthesized-start.spec.ts:262-329`).
- [ ] Tool correlation does not survive a following real start: its standard cleanup deletes the mapping established by the early block, so the next delta falls back to `tool-block-${index}` and switches to the real message ID (F1).
- [~] The subagent spec proves initial context isolation and `parentToolUseId` attribution (`stream-event.synthesized-start.spec.ts:461-493`), but it does not cover the real-start/delta/stop sequence. Subagents therefore inherit F1.
- [x] Normal `message_start` → block ordering emits no synthesized prelude for tool, text, or thinking blocks (`stream-event.synthesized-start.spec.ts:332-420`).
- [x] `assistant-message.transformer.ts` was not touched, and the B10 production/spec file set exactly matches the plan.

Test robustness: the state fake maintains real maps and implements clear operations, so it is capable of exposing F1; the lifecycle test simply stops one event too early. Counting one completion is not equivalent to proving balanced envelopes, and counting one tool start is not equivalent to proving later deltas retain that tool's ID.
