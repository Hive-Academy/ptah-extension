## 1. Diagnosis verification (review question 1) — SOUND, both legs

**Stop and change are synchronous siblings.** `onEndMoving` (`node_modules/gridstack/dist/gridstack.js:2603-2641`) calls `this.triggerEvent(event, target)` at `:2635` (dispatches `dragstop`/`resizestop`) and then `this._triggerChangeEvent()` at `:2640` in the same synchronous call stack. `triggerEvent` (`:2811-2818`) invokes the handler directly; `_triggerChangeEvent` (`:1683-1695`) dispatches `change` at `:1691` synchronously and then calls `engine.saveInitial()` at `:1693`. Nothing awaits and nothing schedules between `:2635` and `:1691`. The webview runs `provideZoneChangeDetection({ eventCoalescing: true })` (`apps/ptah-extension-webview/src/app/app.config.ts:141`), so change detection (and every effect/`afterRenderEffect`) runs on the next animation frame, never inside the mouseup handler; the `queueMicrotask` in `onGestureStop` (`canvas-workspace-grid.component.ts:522-524`) drains only after the whole handler stack returns. A render pass cannot fall between stop and change — the context.md hypothesis is correctly refuted.

**A geometry pass mid-gesture is real and re-baselines the engine.** `load()` ends in `this.batchUpdate(false)` (`gridstack.js:1927`) → `_triggerChangeEvent` (`:736` → `:1683`) → `engine.saveInitial()` (`:1693`). `saveInitial` (`gridstack-engine.js:675-682`) rewrites every node's `_orig` and deletes `_dirty`; `getDirtyNodes(verify)` (`gridstack-engine.js:633-638`) reports a node changed only when `n._dirty && !Utils.samePos(n, n._orig)`. So a `grid.load(pre-drag)` landing between `dragstart` and the last mousemove leaves the dropped node clean at drop → **no `change` at all** → the stop-microtask cancels the gesture → reconcile re-applies pre-drag geometry → exactly the observed `['0','0','0']` on a healthy canvas. The mid-gesture window is genuinely reachable: every mousemove is a zone task with coalesced CD, and the drag can grow the container via `_extraDragRow` (`gridstack.js:2742-2755`) → ResizeObserver → rAF → container signals → effect pass while `_gesture !== null`.

The fix design ("never re-apply authoritative geometry while a gesture is in flight", `canvas-workspace-grid.component.ts:752-755`) removes the load from exactly that window. Correct target, correctly implemented.

## 2. Gesture guard state machine (review question 2) — no stuck states found

`_geometryDeferred` is set in exactly two places (`:748` forced-while-inactive; `:753` non-forced-while-gesturing) and released in three: the full write (`:834`), the empty-positioned early return (`:768`), and the explicit retry in `cancelGesture` (`:717-721`). It is a plain field, so effects never re-run on it — I traced every set/release pairing:

- **Mid-gesture deferral, gesture commits:** `onGridChange` clears the gesture at `:545`, then `reconcileGesture` (`:725-733`) force-applies → `:834` clears the flag. This is the ordering both new regressions pin (spec `:701`, `:736`).
- **Mid-gesture deferral, gesture rejected/cancelled:** `cancelGesture` (`:711-723`) runs the same forced reconcile, then — if the reconcile was skipped (stale workspace, `:728`) — the explicit non-forced apply at `:720` releases it, correctly projecting the *new* workspace. The comment at `:718-719` documents exactly this path.
- **Forced-inactive deferral (behaviour change vs main):** main applied forced writes to hidden grids; this code defers them (`:747-750`). Release on reactivation is guaranteed because the geometry effect tracks `active()` (`:395`): the effect re-runs on the flip, reads the layout *fresh* (not the deferred-at-the-time state), and applies. Locked-at-reactivation is covered by the new `|| this._geometryDeferred` condition in the locked branch (`:399-407`), which force-applies with frozen measurements and clears at `:834`. The pending responsive reflow itself stays frozen under lock and lands on unlock (`:410`), consistent with the documented lock contract. The modified "cancels a gesture when the grid hides before its change event" test (spec `:798-827`) asserts exactly this deferred-then-released behaviour.
- **Workspace switch mid-gesture:** `visible()` flips → `active()` flips → the invalidation effect (`:448-469`) cancels, reconcile defers (inactive), the explicit retry leaves the flag set, and the release lands on the switch back. Self-healing.
- **`!grid` early return (`:774`) does not clear the flag** — benign: the geometry effect tracks `gridComp()` (read at `:773` inside the effect), so it re-runs and retries when the grid attaches; a grid that never attaches has nothing to write.
- **Re-entrancy:** `applyAuthoritativeGeometry` called from inside an effect (directly, or via `cancelGesture` from the invalidation effect `:467`, or via the new deferred release at `:720`) wraps every `grid.load()` in `_applyingLayout` (`:805`/`:846`), so the synchronously re-entered `onGridChange` returns at `:537` before it can recurse or touch a half-written state. Signal writes inside effects (metrics `version`, `canvas-render-metrics.service.ts:53`) are permitted on Angular 22 (`@angular/core` 22.1.7). No cycle found: nothing the apply writes re-triggers the invalidation effect's tracked inputs.

One inherited behaviour, not a regression: while locked, the geometry effect can force-apply into a still-in-flight gesture (`:406` forced bypasses the `:752` guard) before the invalidation effect cancels that gesture in the same flush. Main does the same via reconcile-on-lock; the write is authoritative and the gesture is doomed in the same tick, so I am noting it, not counting it.

## Five logic questions

1. **How does this fail silently?** In the *product* code, no new swallowed-error path was found: the `_applyingLayout` swallow is deliberate and documented, and every deferred-write state has a traced release. The silent failure lives in the *test* code: `metric()` (`canvas.spec.ts:259-260`) converts a missing attribute to a constant `-1`, so the new "gesture rejected" assertion passes vacuously (`-1 === -1`) even when the gesture was in fact rejected, and the change-callbacks poll asserts `-1 > -1` forever, reporting "change swallowed" on a perfectly healthy build. A reviewer reading a green "rejected unchanged" line learns nothing; a red suite misattributes the cause.
2. **What user action produces unexpected behaviour?** A drag that starts in the same animation frame as surface/workspace (re)activation and then commits successfully leaves a skipped remeasure unretried (Moderate finding 2). 3. **What input data produces a wrong answer rather than an error?** 0×0 ResizeObserver entries (hiding) no longer revoke a good pending measurement (validated first, `:91-98`); inactive entries are ignored; non-finite node geometry in `readCompleteNodes` (`:677-709`) rejects the gesture rather than committing garbage — all unchanged-or-improved.

A fired-after-cancel rAF is generation-invalidated. A destroyed/missing grid early-returns (`:774`). 5. **What is missing that the requirements never mentioned?** The component-side half of the e2e contract: `context.md` asserts the component "already exposes `data-canvas-rejected-gestures` … and `data-canvas-change-callbacks` on its host" — it does not, and never did (not even in `acb791814`; host block `canvas-workspace-grid.component.ts:96-101`). ### 1. BLOCKING — the e2e asserts metrics the component never renders; the primary test cannot pass on a healthy build

**Evidence:** `apps/ptah-electron-e2e/src/specs/canvas/canvas.spec.ts:291-297` reads `data-canvas-gesture-commits`, `data-canvas-rejected-gestures`, `data-canvas-change-callbacks`; `:321-334` asserts on them; `:259-260` defines `metric = Number((await grid.getAttribute(name)) ?? '-1')`. The host bindings at `libs/frontend/canvas/src/lib/canvas-workspace-grid.component.ts:96-101` render only `data-canvas-measured-width`, `-layout-computations`, `-apply-checks`, `-apply-passes`, `-grid-updates`, `-gesture-commits`. A repo-wide search finds no binding for `data-canvas-rejected-gestures` or `data-canvas-change-callbacks` anywhere — including the reverted `acb791814` version of the component. The counters exist in the metrics service (`canvas-render-metrics.service.ts:9-11`) and are maintained (`onGridChange` increments `changeCallbacks` first thing at `:536`, `rejectedGestures` at `:556/:563/:584/:638/:650`) — only the DOM projection is missing.

**Concrete failure scenario:** on the next Linux CI run, a correctly fixed app executes the two-leg drag; `change` fires and the commit lands; the suite then reaches `:321-325`, polls `metric('data-canvas-change-callbacks')` = `-1` against `changeCallbacksBefore` = `-1`, `-1 > -1` is false forever, `expect.poll` times out and the test fails with the message "change swallowed: Gridstack emitted no change" — the exact opposite of what happened. The "gesture rejected" assertion at `:326-329` would pass vacuously even for a genuinely rejected gesture, so the rejected-vs-swallowed discrimination this task's verification strategy depends on (context.md, implementation-plan.md §1) is defeated. The e2e was never executed (it cannot boot on Windows), which is why a compile-clean, lint-clean, unit-green change still contains a runtime-impossible assertion. **Fix:** add the two host bindings (`'[attr.data-canvas-rejected-gestures]': "metric('rejectedGestures')"` and `'[attr.data-canvas-change-callbacks]': "metric('changeCallbacks')"`), then re-check the assertion block (which is otherwise well designed). This is a "partially wired behaviour" defect: the test half is wired, the component half is not.

### 2. MODERATE — a remeasure skipped mid-gesture is not retried when the gesture commits

**Evidence:** `remeasureIfNeeded` (`:861-872`) skips while `_gesture !== null` without setting `_wasVisible`; the retry sites are the remeasure effect (`:417-425`, re-runs only when `active()`/`gridComp()` change) and `cancelGesture` (`:722`). The successful-commit path clears the gesture at `:545` and calls only `reconcileGesture` (`:591`, `:604`, `:640`) — nothing retries the remeasure, and the remeasure effect has no tracked input left to re-run on.

**Concrete failure scenario:** the surface (or workspace `visible`) flips active and a mousedown-dragstart is processed before the reactivation CD flush latches the gesture — the remeasure effect then skips, `_wasVisible` stays `false` — the drag completes and commits; the pending remeasure is now orphaned until the *next* activity cycle, leaving Gridstack's internal column measurement stale in the interim. The trigger window is one animation frame (a signal flip and a user drag interleaving in the same frame — improbable for a human, reachable by scripted/automated input), and the authoritative projection is unaffected (it reads the container signals, not Gridstack's cached measurement). Narrow edge, real gap in a mechanism this change itself added (the mid-gesture skip plus retry), hence Moderate: mirror the `cancelGesture` retry (a `remeasureIfNeeded` call after the commit's reconcile, or clearing the gesture via a shared path that retries).

### 3. MINOR — the deferred release and remeasure retry run on the teardown path

**Evidence:** `ngOnDestroy` (`:911-913`) calls `cancelGesture(false)`, but the deferred release (`:717-721`) and the remeasure retry (`:722`) are not gated on `reconcile`. A component destroyed mid-gesture with `_geometryDeferred` pending and the surface active can run one final `applyAuthoritativeGeometry()` (a `grid.load()` into a grid whose `<gridstack>` child is being torn down) and `grid.onResize()` during destroy. Main never wrote from the destroy path. Uncertain blast radius (Angular destroys child views around the parent hook, so `gridComp()` may already resolve to nothing and the `:774` early return protects it), but the work is pointless at best. Gate both on `reconcile` or on a destruction flag.

`canvas-workspace-grid.component.ts` is at 728 counted lines against the 700 budget (`eslint.config.mjs:514-517`, warn). Zero errors, targets pass. Style debt incurred by this change; the repo's established over-budget patterns apply.
