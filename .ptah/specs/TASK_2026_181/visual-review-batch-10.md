## 1. The focus ring, recomputed across all four mandated bases

`task-card.component.ts:65`: `focus-visible:outline focus-visible:outline-2 focus-visible:outline-offset-2 focus-visible:outline-[oklch(var(--s))]` — a literal duplicate of the global rule at `apps/ptah-extension-webview/src/styles.css:439-448` (`outline: 2px solid oklch(var(--s)); outline-offset: 2px;`), reproduced here because the global rule's selector (`button, input, select, textarea, a`) does not match this card's `role="button"` `<div>` (`:70`). That reasoning is sound and matches the class of gap Batch 7 finding #8 flagged for the facet-menu `<summary>` triggers.

The card's background is `bg-base-100` (`:65`) in every state — `selected()` only toggles `border-base-content` / `ring-1 ring-primary` (`:66-69`), never the fill — so the outline's contrast against its background is the same computation whether the card is resting, hovered (`hover:border-primary/40`, also `:65`), or selected. I computed `--s` (secondary) against `base-100` for all four mandated bases, using the literal theme values (`tailwind.config.js:56` anubis, `:112` anubis-light, `node_modules/daisyui/src/theming/themes.js` `dark`/`light`), converting OKLCH→sRGB by the standard Björn Ottosson formulas and applying WCAG 1.4.11's non-text 3:1 gate (a focus indicator is a UI component, not text):

| Theme           | secondary                                       | base-100  | Contrast   | Gate (3:1)                  |
| --------------- | ----------------------------------------------- | --------- | ---------- | --------------------------- |
| anubis          | `#d4af37`                                       | `#131317` | **8.81:1** | passes comfortably          |
| anubis-light    | `oklch(58% 0.132 75)` → `rgb(167,108,0)`        | `#faf7f5` | **4.11:1** | passes comfortably          |
| daisyUI `dark`  | `oklch(74.8% 0.26 342.55)` → `rgb(255,82,217)`  | `#1d232a` | **5.63:1** | passes comfortably          |
| daisyUI `light` | `oklch(69.71% 0.329 342.55)` → `rgb(255,0,211)` | `#ffffff` | **3.39:1** | **passes, but by only 13%** |

Three of four bases pass with real margin. The fourth — daisyUI's own stock `light` theme, one of the four mandated bases — clears the gate by 0.39, a thin margin for a value I derived with a naive per-channel clamp rather than a browser's actual CSS Color 4 gamut-mapping algorithm. `C: 0.329` is a very high chroma for that hue (near the edge of the sRGB gamut for magenta), so this is exactly the kind of OKLCH-authored value where a browser's real gamut-mapping could legitimately land a few hundredths either side of my number — I'm flagging the confidence level rather than asserting the ring fails, because it doesn't, on my numbers. **Non-blocking**, but worth knowing this is a thin pass, not a comfortable one, and — this matters for scope — it is not new to this batch: it is inherited unchanged from the app-wide `styles.css:445` rule that `task-filter-bar`/`task-view-menu` already use. Nobody had actually run the numbers against `base-100` for this specific colour pair before; now it's on record that the margin on daisyUI `light` is thin everywhere this rule is used, not just here.

**Selected + focused, concretely traced.** A card can be both `selected()` (open in the detail panel) and the board's one roving tab stop at once. In that state the card shows, from inside out: a 1px `border-base-content` sitting at the card edge, a `ring-1 ring-primary` box-shadow at the same offset (0, since no `ring-offset-*` is set) so it visually merges with the border into one coloured edge, then a 2px gap (`outline-offset-2`), then the 2px secondary-coloured focus outline. That's two concentric, differently-hued rings — primary at the edge, secondary two pixels out — which is legible as "this card is both selected and where keyboard focus is" on every theme where primary and secondary are visually distinct hues (all four: blue-vs-gold on anubis, teal-vs-gold on anubis-light, blue-vs-pink on `dark`, blue-vs-magenta on `light`). I did not find a theme in the mandated four where the two rings could be confused with each other. **No blocking issue here.**

**One mechanism worth naming, not blocking**: the roving-focus arrow-key path moves DOM focus programmatically (`task-board.component.ts:262-271`, `card.focus()`), not via a user click or Tab. `:focus-visible` heuristics in modern Chromium (which both VS Code's webview and Electron's `BrowserWindow` embed) do keep the ring visible for script-triggered focus that originates inside a `keydown` handler, which is exactly this case — so the ring is expected to render on every arrow-key move, not just the initial Tab-in. I could not confirm this live, but it is standard, well-documented Chromium behaviour, not a speculative one.

## 2. The palette at realistic width

The dialog is `fixed inset-0` covering the _viewport_, not the board column — `w-full max-w-xl mx-3` (`task-command-palette.component.ts:94-95`), so its width tracks the whole webview panel, not the 256px column. At a 576px+ viewport it has full room; the brief's framing ("a VS Code sidebar that can be narrower [than 256px]") is the case worth tracing, since `mx-3` leaves only `viewportWidth − 24px` for the dialog itself, and each result row loses a further `24px` (`px-3` on the button, `task-command-palette.component.ts:144`) plus two `gap-2` (16px) before any content renders.

**Long task titles: truncation itself is very likely fine, on the CSS spec's own terms.** `entry.label` (`:160`, `class="text-sm truncate"`) is a flex child with no `flex-*` utility, sitting between an empty `flex-1` spacer (`:161`) and a reason/group-label span. Tailwind's `truncate` sets `overflow: hidden`, and per the CSS Flexbox spec, a flex item's _automatic_ minimum size is 0 (not its content size) specifically when its own `overflow` is anything other than `visible` — so this span does not need an explicit `min-w-0` the way Batch 9 found the view-menu's plain `<input>`s did (inputs don't get that same automatic override). I'm stating this with the confidence the spec text supports, while noting I could not watch it render.

**Where the row actually gets contested is a priority problem, not an overflow one — and it is the same class of bug Batch 9 flagged and left as a non-blocking follow-up one file over.** The disabled-reason span (`:163-167`, `class="text-[11px] text-right max-w-[16rem]"`) carries neither `truncate` nor `whitespace-nowrap`, so it wraps rather than overflows — legible, arguably _more_ honest than truncating a sentence FR-C6.6 requires to be readable. But neither it nor `entry.label` carries `shrink-0`, so under real space pressure (a narrow host, a long disabled-reason sentence like `NO_SELECTION_REASON` at `palette-entries.ts:136-137`, 74 characters) CSS's default proportional-shrink distribution gives both spans a comparable percentage of the squeeze. The reason text can absorb it by wrapping to more lines (its rendered width just shrinks toward its longest unbreakable word, ~70-90px); the label has no such fallback — it can only lose horizontal space until only a sliver of the _command name itself_ is visible, while the multi-line reason next to it stays fully legible. That is the exact inversion Batch 9's finding-2 follow-up named for `chip.value`/`chip.note` ("the note is the annotation, the value is the fact it's annotating... backwards"): here, the reason is the annotation and the label is the fact. I could not confirm the precise pixel split without a live browser — same honesty bound Batch 9 applied to its own version of this finding — but the mechanism is real and it is the second time this exact priority-inversion pattern has shipped in this task.

- **File**: `libs/frontend/tasks-ui/src/lib/components/palette/task-command-palette.component.ts:160,163-167`
- **Fix**: `shrink-0` on the label span (or on the whole `entry.label`/spacer/reason group's non-reason members) so the command's own name is the last thing to concede space, mirroring the fix already named for the chip case.

**Group-label text is a non-issue.** The `@else` branch (`:168-172`, `text-[11px] whitespace-nowrap`, no `max-w`) renders short static strings from `TASK_PALETTE_GROUP_LABELS` (`palette-entries.ts:95-101`) — "Jump to a task" is the longest at 15 characters. Even an unshrinkable, un-wrapping span that short cannot force a real palette width to overflow.

## 3. Disabled-with-reason entries: legible, and distinguishable by more than colour — until the same colour makes the sentence itself hard to read

FR-C6.6's structural requirement is met: the reason renders as an actual sentence (`task-command-palette.component.ts:163-167`), not a tooltip-only or colour-only signal, and `aria-disabled` (`:148`) plus a distinct `data-testid` (`:149-153`) give it a second, non-visual channel too. The one visual differentiator at rest is `[class.opacity-60]="entry.disabledReason !== null"` (`:156`), bound at the `<button>` level — so it dims the _entire_ row (background and all descendant text) by blending it 40% toward the dialog's own `bg-base-200`.

**I ran the actual blend, not an assumption, and it fails 4.5:1 (normal text — `text-[11px]` is unambiguously small) on three of the four mandated bases.** `opacity-60` is a different mechanism from the `text-base-content/NN` utility Batch 9's audit banned (that ban is scoped to text-colour opacity, and `TASK_2026_183` owns the remaining sweep of that specific class) — but the visual and mathematical result of alpha-blending a foreground toward its backdrop is identical whichever CSS property produces it, so I computed it the same way Batch 7/9 computed every other opacity case:

| Theme           | disabled-row text × 0.6 vs its own 0.6-blended background | Contrast   | Gate (4.5:1, normal text) |
| --------------- | --------------------------------------------------------- | ---------- | ------------------------- |
| anubis          | `#e8e6e1` × 0.6 on `bg-base-200` `#1a1a20`                | **5.75:1** | passes                    |
| anubis-light    | dark-purple base-content × 0.6 on cream `base-200`        | **4.28:1** | **fails**                 |
| daisyUI `dark`  | `#A6ADBB` × 0.6 on `#191e24`                              | **3.55:1** | **fails**                 |
| daisyUI `light` | `#1f2937` × 0.6 on `#F2F2F2`                              | **3.90:1** | **fails**                 |

This is precisely the same shape of defect the codebase already litigated twice — `badge-primary` in Batch 7, `alert-error`/`alert-info` in Batch 9, both traced to "anubis is the one hand-authored theme, and it happens to be the one that passes here" — except this time it inverts: anubis is the one theme that _passes_, and the other three mandated bases fail, on the exact sentence FR-C6.6 exists to make readable. A user on daisyUI's own unmodified `light` theme (a completely plausible host-theme choice, not an edge case) gets a disabled command whose "why" sentence sits at 3.90:1.

**It gets worse in a state that is not hypothetical.** `KeyboardNavigationService.configure` (`libs/frontend/ui/src/lib/native/shared/keyboard-navigation.service.ts:100-111`) sets `activeIndex` to `0` the instant `itemCount > 0`, and `rankPaletteMatches` (`palette-match.ts:154-171`) ranks purely on label text with no awareness of `disabledReason` — so a disabled entry landing at index 0, and therefore becoming the `bg-primary`/`text-primary-content` **active** row (see §4) while also carrying `opacity-60`, is one keystroke away (e.g. typing "set" surfaces the selection-scoped `Set status: …` entries, several of which are disabled with no task selected). I computed that compound state — the active-row fill and text both blended through the same 0.6 opacity — for all four bases:

| Theme           | active + disabled contrast |
| --------------- | -------------------------- |
| anubis          | **2.91:1**                 |
| anubis-light    | **2.40:1**                 |
| daisyUI `dark`  | **3.00:1**                 |
| daisyUI `light` | **3.18:1**                 |

**All four mandated bases fail 4.5:1 in this state, and none of them come close.** This is not a corner of the theme matrix; it's a state a keyboard user reaches by typing a common word.

- **File**: `libs/frontend/tasks-ui/src/lib/components/palette/task-command-palette.component.ts:156`
- **Fix**: stop dimming disabled rows with element-level `opacity`; the reason text already carries the "why" in words (that part is correct design), so the row doesn't need a second, contrast-destroying channel. A `text-base-content` (full opacity) label/reason plus a non-opacity cue — a left border, a muted icon, or simply relying on the reason sentence itself, which the app's own Batch 9 precedent already established as sufficient without any colour or opacity treatment at all — would keep the distinction without failing the text gate on 3 of 4 bases at rest and on all 4 when also active.

**One more, smaller point on the same control**: the disabled `<button>` never gets the HTML `disabled` attribute (correctly, since `mouseenter` still needs to fire so hovering a disabled row can move `activeIndex` onto it) — but that also means the cursor stays the default clickable pointer on hover, on a control whose click `runEntry` (`:335-338`) silently no-ops. Non-blocking; a `cursor-not-allowed` class conditioned on `entry.disabledReason !== null` would close the gap without touching the deliberate hover/mouseenter behaviour.

## 4. The active-option indicator: unambiguous as a _shape_, but its own text fails contrast on the app's default theme

The mechanism itself is sound for the question the brief asks ("must be able to see which row is armed without a focus ring on it"): the active row is the only one with a full-width background fill (`[class.bg-primary]`/`[class.text-primary-content]`, `:154-155`), driven by `aria-activedescendant` and scrolled into view (`scrollActiveIntoView`, `:352-365`) on every move — including on `(mouseenter)`, so keyboard-arrow and mouse-hover share one visual language. A solid, full-row fill is a strong enough shape/area cue that it stays identifiable even for a user who can't distinguish the specific hue, which is the right property for a listbox where nothing else marks the active row.

**Where it breaks is legibility of that row's own text, and it's the identical colour pair Batch 7 already flagged and left unresolved at the root.** `[class.bg-primary]`/`[class.text-primary-content]` paints `primary`-on-`primary-content`, and Batch 7 §5a found this exact pair fails 4.5:1 on anubis (the app's `darkTheme`, the theme most installs actually see). I did not take that number on faith — I called daisyUI's real `generateForegroundColorFrom` (via `culori`, `node_modules/daisyui/src/theming/functions.js`) for the two generated themes to get their literal, non-approximated values, and hand-verified anubis and anubis-light from the literal hexes/OKLCH in `tailwind.config.js`:

| Theme           | primary                       | primary-content                                    | Contrast    | Gate (4.5:1) |
| --------------- | ----------------------------- | -------------------------------------------------- | ----------- | ------------ |
| **anubis**      | `#2563eb`                     | `#e8e6e1`                                          | **4.144:1** | **fails**    |
| anubis-light    | `oklch(85% 0.138 181.071)`    | `oklch(43% 0.078 188.216)`                         | 5.198:1     | passes       |
| daisyUI `dark`  | `oklch(65.69% 0.196 275.75)`  | daisyUI-generated: `oklch(13.138% 0.0392 275.75)`  | 6.005:1     | passes       |
| daisyUI `light` | `oklch(49.12% 0.3096 275.75)` | daisyUI-generated: `oklch(89.824% 0.06192 275.75)` | 5.589:1     | passes       |

`entry.label` is `text-sm` (14px, normal text by any definition) and `[class.text-primary-content]` is bound at the `<button>` level, so it also colours the `text-[11px]` group-label/reason spans beneath it — the whole active row's text fails together on anubis.

The consequence is larger than "one more theme fails a badge": `KeyboardNavigationService.configure` puts the active index at row 0 the instant the palette has any results — **this is the palette's default rendered state on every open**, not a state a user has to navigate into. On the app's own default dark theme, the very first thing a user sees after `Ctrl+K` is a highlighted row whose text is below the WCAG AA text gate.

- **File**: `libs/frontend/tasks-ui/src/lib/components/palette/task-command-palette.component.ts:154-155` (consumer), root cause `apps/ptah-extension-webview/tailwind.config.js:51,53` (unchanged since Batch 7 flagged it)
- **Fix**: same two options Batch 7 already named — lighten anubis's `primary-content`, or stop using the `primary`/`primary-content` fill pair for text on anubis specifically. This batch is the second consumer to inherit a contrast failure that was flagged, not fixed, three batches ago; a root-cause fix in `tailwind.config.js` closes it for every future consumer at once instead of asking each new component to route around it individually (which is what the rollup did in Batch 7's own fast-follow, per its comment at `task-card.component.ts:217-226`).

## 6. Target sizes

Every new interactive element clears WCAG 2.2 SC 2.5.8's 24×24px floor:

- **Backdrop button** (`:86-93`): `absolute inset-0`, i.e. the entire viewport minus the dialog — trivially over the floor, and correctly excluded from the tab order (`tabindex="-1"`).
- **Query input** (`:109-123`): full-width row inside a `px-3 py-2` container — well over 24px tall.
- **Result rows** (`:141-173`): `px-3 py-1.5` button with `text-sm` (14px, ~20px line-height) content ⇒ ≈32px tall single-line rows — clears the floor with margin, including the shortest (group-labelled, enabled) rows.

**The backdrop reads as intended, not as a stray control.** It's a plain `<button>` with no `.btn` class and an explicit `cursor-default` (`:89`) rather than the pointer a real button would get — combined with Tailwind's Preflight resetting native button chrome (border/background), it should render as an inert-looking translucent scrim, not something that visually invites a click the way a styled button would. `tabindex="-1"` keeps it out of the tab sequence, so the "one focusable element" trap the class doc claims (`:61-65`) holds structurally — I traced the template and found exactly one native `<input>`/`<button>` with a non-`-1` tabindex inside the dialog: the query input. Everything else, including the backdrop and every result option, is `tabindex="-1"`. **Confirmed as documented.**

_(Out of scope, noted only for completeness: `task-card.component.ts:100`'s status-menu trigger is `h-5 w-5` — 20px, under the 24px floor — but that control predates this batch; Batch 10 only added `[attr.tabindex]="rovingTabIndex()"` to it, it didn't touch its size, and as a real `<button>` it was already independently tabbable before this batch existed. Not a new defect, not re-scored here.)_

## 7. The roving tabindex's visual consequence: nothing tells a sighted user arrow keys exist

I grepped both `task-board.component.ts` and `tasks-view.component.ts` for any on-screen hint — a `title`, a footer legend, a `kbd` glyph — naming arrow-key navigation, and found none. The board itself carries no `role` at all (`task-board.component.ts:59`, a plain `<div>`), and the column is a `<section>` with only an `aria-label` (`task-column.component.ts:31-33`) — neither is `role="grid"` or any other ARIA widget role that would let a screen reader announce arrow-key semantics either. So the gap isn't purely visual: there is currently no channel, visual or assistive, that tells a first-time keyboard user "you can move between cards with the arrow keys" once they've tabbed in.

**What a sighted user actually sees**: one card carries the gold focus ring (§1); the other 180-ish look exactly as they did before this batch — same border, same hover treatment, nothing marking them as part of a navigable set. That reads as "the board has one focusable thing," not "the board is one grid you can move through," which is the opposite of the intended discoverability. This is the expected, conventional behaviour for the WAI-ARIA roving-tabindex pattern (it is discoverable-by-convention, the same way it works in most kanban/grid UIs), and the palette's own trigger button states the `Ctrl+K` shortcut in its `title` (`tasks-view.component.ts:147`) — so the _palette's_ entry point is discoverable, even if arrow-navigation-once-inside-the-board is not.

- **File**: `libs/frontend/tasks-ui/src/lib/components/board/task-board.component.ts` (whole file — no hint anywhere), `libs/frontend/tasks-ui/src/lib/components/tasks-view.component.ts` (no supplementary legend near the board)
- **Impact**: non-blocking — this is the accepted convention for the pattern, not a defect against any stated requirement — but worth naming because it's genuinely easy to miss on a first visit: the board looks like it lost most of its keyboard reach rather than gained a systematic one.
- **Fix suggestion** (optional, not required by any FR I could find): a one-line `title` on the board container, or a small "↑↓←→ to move, Enter to open" hint the way some command palettes show a footer legend — the palette component itself is a natural place to advertise this too, alongside its own overflow-count footer.

## R10 — the manual gate I also could not close

The brief is explicit that the developer did not perform this check and said so. I want to be equally explicit that I did not close it either, for the same underlying reason: no live VS Code host.

I read the evidence the developer's own claim rests on. `tasks-view.component.spec.ts:862-877` ("is bound to the host element, not to the document (R10)") dispatches `Ctrl+K` on a sibling `<div>` outside the Tasks surface and asserts the palette does not open — that's a real, correctly-targeted test, and it does prove the handler is host-scoped rather than `document`-scoped, which rules out the specific failure mode described in its own comment (stealing the shortcut from the chat composer or any other webview surface). `onKeyDown` (`tasks-view.component.ts:720-728`) also only calls `preventDefault`/`stopPropagation` on the one combination it consumes (`Ctrl/Cmd+K`, no `Alt`), so nothing here suppresses a keystroke it doesn't act on.

**None of that reaches the actual open question.** jsdom has no concept of VS Code's own workbench-level keybinding service, and in particular no concept of `Ctrl+K` as a _chord prefix_ (VS Code owns several two-key chords that start with `Ctrl+K`, e.g. `Ctrl+K Ctrl+S` for keyboard shortcuts). Whether this component's `preventDefault()` on the _first_ keypress of that chord is enough to stop VS Code's own workbench from entering "waiting for the second chord key" mode — or whether VS Code's keybinding service intercepts the combination before it ever reaches the webview's DOM at all, in which case this component's handler wouldn't even fire — is not something a component-level Angular test can observe, and not something I can observe without a live VS Code window either. I looked for a `package.json` `contributes.keybindings` entry that might pre-empt or conflict with `Ctrl+K` inside the Tasks webview and did not find a conflicting one, which matches the developer's own stated evidence, but that's the same static-analysis ceiling the developer already named, not a new confirmation.

**I am stating this as an open item, not converting it to a pass.** This matches how every prior agent on this task has handled the same class of gap.

## Verdict

**NEEDS REVISION** on contrast; the rest is real but lower-stakes.

Two Serious findings, and both are the same shape of problem this task has now hit four times: a component reaches for daisyUI's `primary`/`primary-content` (or an opacity-derived) text pairing, and it fails on at least one of the four mandated bases because the underlying colour value was hand-authored rather than daisyUI-generated (finding 1), or because dimming a whole row's opacity is mathematically indistinguishable from the `text-base-content/NN` pattern this codebase already banned for exactly this reason (finding 2). Finding 1 in particular is not a new discovery in the abstract — it's Batch 7's own unresolved root cause, now surfacing on the palette's default, no-action-required, every-single-open visual state, which is a more exposed surface than the hover-only badge it was originally found on. Finding 2 is new to this batch and fails on more of the mandated matrix (3 of 4 at rest, 4 of 4 compounded) than either of the two prior contrast findings in this task.

Neither finding is a layout break or an overflow — the palette fits at realistic widths, truncation works where it needs to per the CSS spec's own automatic-minimum-size rule, the hit targets are correctly sized, and the focus-ring/selected-ring layering is legible on every mandated theme. The label/reason shrink-priority risk (finding 3) is real but explicitly unconfirmed without a live browser, matching the same discipline Batch 9 applied to its own version of this exact pattern. I'd want findings 1 and 2 addressed — ideally by fixing `tailwind.config.js`'s anubis `primary-content` once at the root, which would also retroactively close whatever the _next_ batch reaches for `bg-primary`/`text-primary-content` on — before calling this batch visually done.

**Does the replacement actually read as "armed" at a glance?** Yes, and for a reason stronger than any single visual cue: it doesn't rely on one. Three things change together on the active row — a `ChevronRight` glyph appears in a slot that is reserved-but-empty on every other row (`:185-192`, `w-3 shrink-0`, so nothing reflows when the highlight moves), the label goes `font-semibold` (`:199`, a shape/weight change, not a colour one — legible under any colour-vision profile and in a forced-colours/high-contrast mode where `bg-base-300` would vanish entirely), and the trailing slot swaps from the group name to the literal words `Enter to run` (`:202-207`, `data-testid="task-palette-enter-hint"`). That last one is the strongest possible channel for "this is what a keypress will do" — it doesn't imply state through tint, it states it. I checked this holds on the disabled branch too: an active _disabled_ row correctly suppresses the hint (`:202`'s condition requires `entry.disabledReason === null`) and shows the group label instead, so the row never claims Enter will do something it won't — confirmed against the template, not just the spec's `shows no Enter affordance on an active DISABLED row` test (which I also ran; it passes).

**Does `bg-base-300` pull any weight at 1.05–1.13:1?** No, and the comment (`:164-165`) says so itself — this is an honest self-assessment, not an overclaim. Practically invisible at that ratio on every mandated theme; a user with unusually good contrast sensitivity or an unusually calibrated panel might perceive the faintest tint as a fourth, bonus reinforcement, but nobody is relying on it, and the three non-colour cues above would carry the state identically if `bg-base-300` were deleted outright. I'd call keeping it harmless-but-genuinely-dead-weight rather than actively wrong — worth a one-line note, not a finding.

**One honest trade-off worth naming, non-blocking**: the trailing slot can only show one thing at a time, so the active row loses its group label (e.g. "Filters", "Board") in exchange for "Enter to run" — the one row a user might most want confirmed as belonging to the right group loses that specific cue. In practice the label text itself is almost always self-describing enough (`Filter by status: Backlog` doesn't need a "Filters" tag next to it to be understood), so I don't think this costs much, but it is a real, deliberate trade, not a non-issue.
