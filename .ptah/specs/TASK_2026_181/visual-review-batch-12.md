## 1. The three bar states — structurally distinct, and legible where tested; one gap the mechanism itself creates

`task-bulk-bar.component.ts:52-181` renders exactly one of three mutually exclusive branches (`@if (progress(); as run)` → `@else if (requested(); as target)` → `@else`), so "which state am I in" is never a colour question — it's a different DOM shape each time: a spinner + a single Cancel button; a sentence + two buttons; a count + a `<select>` + supporting buttons. I traced the template rather than trusting the doc comment's claim, and the three shapes genuinely cannot be confused for one another at a glance. **Confirmed.**

**The confirmation legibly names both facts.** `confirmPrompt()` (`:227-229`) renders `Move {{ count() }} task(s) to {{ statusLabel(target) }}?` as the first, unclipped, unadorned text in the row (`:87-99`, `class="min-w-0 flex-1"` — no `truncate`, no `max-w`, so it wraps rather than clips at any width). `task-bulk-summary.component.spec.ts:299-311` asserts both facts render on the visible text, not just an `aria-label` — I read the test, not just its name; it checks `textContent` on `[data-testid="task-bulk-confirm"]`, which is the sighted-user-facing path. **Confirmed legible, not buried.**

**Where this breaks down**: `_bulkSummary` (the previous run's persistent failure panel) is cleared in exactly one place — the top of `bulkUpdateStatus` (`tasks-store.service.ts:1298`), which only runs once the user has actually clicked Confirm. `requestBulkStatus` (`:1209-1217`), which fires the moment a status is picked above the 10-item threshold, only sets `_bulkRequest` — it does not touch `_bulkSummary`. Between those two calls, `bulkBarVisible()` is already true (`tasks-view.component.ts:642-647`, gated on `bulk() !== null || bulkRequest() !== null`, not on the summary), so the confirming bar (`:279-293`) renders **above** a still-visible summary panel from the run before it (`:297-303`). This is directly reachable through the summary's own Retry button: `retry.emit(summary().status)` (`task-bulk-summary.component.ts:73`) calls straight into `requestBulkStatus` (`tasks-view.component.ts:300`), so clicking Retry on a >10-failure summary puts the confirmation bar on screen **directly above the same failure rows Retry was just clicked from**, which have not yet been touched and will not update until the user confirms again. A user who doesn't track that sequence closely could read the still-visible old failure list as "it failed again already," when nothing has been re-attempted yet. Non-blocking — the panel below is not wrong, it's stale-but-honest — but it's a real, code-confirmed overlap the brief's "which state am I in" question doesn't quite cover, because it's two components stacked, not one bar in an ambiguous state.

- **File**: `libs/frontend/tasks-ui/src/lib/services/tasks-store.service.ts:1209-1217,1292-1298`; consumed at `libs/frontend/tasks-ui/src/lib/components/tasks-view.component.ts:279-303`
- **Fix**: clear `_bulkSummary` in `requestBulkStatus` too (or at minimum when the request originates from Retry), not only inside `bulkUpdateStatus`.

## 2. The persistent failure summary: comprehensible per-row, but has no height bound, and 20 failures is not a hypothetical

`task-bulk-summary.component.ts:102-134`. Each failure renders as a bordered `<li>` (`:105-108`) carrying an icon, the task id (`font-mono`, unbounded — no `truncate`), an optional title (`truncate`, correctly bounded), the backend's message, and — on a conflict — the `currentStatus` sentence (`:124-129`, "It is now in `<Status>` on disk — the change you asked for was not applied over it," ~85 characters, no `truncate`/`nowrap`, so it wraps rather than clips). At 256px-class widths that sentence alone is 2-3 lines. **No individual row overflows — this part is sound**, and it's the right failure mode (wrap, don't clip, on a sentence a user needs in full).

**The list itself has no bound.** `<ul class="flex flex-col gap-1" data-testid="task-bulk-summary-list">` (`:103`) sets no `max-h` and no `overflow-y`. I grepped the whole `bulk/` directory for `max-h`/`overflow-y`/`overflow-x` and found zero matches — this is not a class I missed, it isn't there. Compare this to the sibling defect Batch 9 found and the developer fixed one component over: `task-view-menu.component.ts`'s saved-views list now carries `max-h-80 overflow-y-auto` for exactly this reason. This component reintroduces the identical omission the codebase already has a known fix for.

**I traced where the overflow actually goes, and it is worse here than in the Batch 9 case, not better.** The saved-views popup was an absolutely-positioned dropdown with an uncertain clipping ancestor; this panel is a plain block sibling inside the page's own root flex column: `tasks-view.component.ts:99`, `<div class="flex flex-col h-full w-full bg-base-100">`. Walking every sibling in that column — header (`flex-shrink-0`), the transient alert banners, the saved-views bar, the filter bar, the bulk bar — **none of them carries `min-h-0`, so none of them can shrink below its own content height.** The one exception is the body wrapper, `tasks-view.component.ts:306`, `<div class="flex flex-1 min-h-0">` — the _only_ flexible region in the column, and `min-h-0` on a flex item with `flex-1` means it is explicitly permitted to shrink **all the way to zero** rather than to its content's natural minimum, which is precisely the pattern that lets the board absorb whatever a taller sibling above it demands.

At roughly 90-100px per failure row (border + padding + icon + up to four wrapped text lines, per the elements traced above), 20 failures is 1.8-2.0k px — a routine outcome, not an edge case: `BULK_CHUNK_SIZE` is 20 (`libs/shared/src/lib/types/task-view.types.ts:114`), and the developer's own test fixture at `task-bulk-summary.component.spec.ts:97-105` exercises a 120-task, 40-attempted run, matching the brief's own example numbers. A summary with a comparable count of _failures_ (not just un-attempted, which don't render rows — see §4) would, on my read of the flex mechanics, squeeze the body region — and with it, all six board columns — down toward zero height before the failure list itself gets a scrollbar of its own. The retry/dismiss controls (`:69-87`) sit _above_ the list, so they at least stay reachable — this is not the "controls become permanently unreachable" failure mode Batch 9 found, it's the other one that same finding named: "nothing clips it, and opening [it] ... forces the whole page to grow," except here it's not the page, it's the one region — the board — this whole feature exists to sit above.

- **File**: `libs/frontend/tasks-ui/src/lib/components/bulk/task-bulk-summary.component.ts:102-134` (missing bound); mechanism confirmed at `libs/frontend/tasks-ui/src/lib/components/tasks-view.component.ts:99,306` (root flex column, only the body is `min-h-0`)
- **Impact**: **Visual Breaking.** A run with a realistic number of failures (a full 20-item chunk, or more) can reduce the board — the surface the whole Tasks feature is built around — to a sliver or nothing, directly contradicting the persistent-not-a-toast design intent: a panel that's supposed to stay legible while a user works through failures instead crowds out the thing they're supposed to be working on.
- **Fix**: `max-h-[Nrem] overflow-y-auto` on the `<ul data-testid="task-bulk-summary-list">`, mirroring `task-view-menu.component.ts`'s own fix for the identical mechanism one file over. Not covered by any existing test — I read `task-bulk-summary.component.spec.ts` in full; nothing in it renders more than two failure rows or asserts a height-bound class.

## 3. The cancellation sentence: legible and unclipped, but not visually distinguished from the line above it

`task-bulk-summary.component.ts:90-100`. `Cancelled after {{ summary().attempted }} of {{ summary().requested }}. Writes already issued completed and were not reversed.` renders as a bare `<p>` with no width constraint, no `truncate`, no `nowrap` — it cannot be clipped at any tested width, and I found no mechanism that would cut it short. On the letter of item 3 ("can it be truncated or clipped away") the answer is **no**.

**On prominence, the answer is closer to no than yes.** The paragraph is styled identically to the headline paragraph directly above it — same `text-xs`, same `text-base-content`, no `font-medium`/`font-semibold`, no icon, no border or background differentiation, sitting in the same `flex flex-col gap-1.5` stack (`:52-53`) as every other line in the panel. The component's own doc comment calls this "the entire honesty of the feature" (`:26-30`) — a phrase strong enough that I'd expect the rendering to match it, the way `task-bulk-summary.component.ts:111` gives the error icon `text-error` specifically so a failed row reads differently from a plain one. The cancellation sentence gets no equivalent treatment; visually it reads as one more line of body copy, not as the load-bearing caveat the doc comment says it is. This is a real gap between what the comment claims the sentence _is_ and what the CSS makes it _look like_ — not a defect in the wording (which is exactly the required text, verbatim, per `task-bulk-summary.component.spec.ts:97-105`), but in how hard it is to skim past.

- **File**: `libs/frontend/tasks-ui/src/lib/components/bulk/task-bulk-summary.component.ts:95-99`
- **Impact**: Moderate, non-blocking — the sentence is always present and always readable, just not visually weighted to match its own stated importance.
- **Fix**: a one-line differentiation — `font-medium`, a small warning-toned icon (matching the failure rows' use of an icon as "redundant reinforcement... not the signal," which the component's own doc already treats as acceptable practice), or simply putting it first, before the headline, since it's the fact that reframes everything the headline says beneath it.

## 4. The three-group model: correct in the data, effectively invisible in the UI

This is the item the brief weights heaviest, and I traced it end to end rather than trusting the doc comment's account of it.

`tasks-store.service.ts:1392-1454`, `settleBulk`. The code is exactly as documented: an id with no entry in `outcomes` (never reached before cancellation) goes back into `nextSelection` **without** being pushed onto `failures` (`:1422-1428`). The doc comment (`:1392-1406`) is explicit about why: "reporting them as failures would tell the user that 80 tasks broke when they pressed Cancel." That data-level claim is correct and I verified it against the actual loop, not just the comment.

**What I could not find anywhere is a rendering of that third group as its own, named thing.** I read every line of both bulk components again specifically hunting for it. There is none:

- **On the board**, an un-attempted card and a failed card are rendered identically: both are simply `checked()` (still in the selection, per `settleBulk` putting both back into `nextSelection`), neither is `pending()` (the run has ended), so both get exactly the same `bg-base-200` fill and checked checkbox (`task-card.component.ts:90,117`) and nothing else. There is no third card state — no distinct badge, border, or icon — for "queued but never reached" versus "reached and refused." A user scanning the board sees N checked cards and has no visual way to tell which of them are the ones named in the failure list below and which are not.
- **In the summary panel**, only `failures` gets an explicit row — icon, id, title, message, `currentStatus` (`:102-134`). The un-attempted group gets **zero** explicit representation: no count, no list, no id. The only place their existence is even implied is arithmetic across two different sentences: the headline (`:155-163`) states `succeeded` and `failures.length`, which together equal `attempted`, not `requested`; the cancellation sentence (`:95-99`) separately states `attempted` **of** `requested`. A user has to subtract `attempted` from `requested` themselves, in their head, across two sentences that don't reference each other, to learn that a third group exists at all — and even then they learn only its _size_, never _which_ tasks are in it.

I confirmed this against the developer's own test fixture rather than a hypothetical: `task-bulk-summary.component.spec.ts:97-105` renders exactly the brief's own numbers — `requested: 120, attempted: 40, succeeded: 40, cancelled: true`, zero failures. The rendered text in that exact scenario is `"40 task(s) moved to Done."` plus `"Cancelled after 40 of 120. Writes already issued completed and were not reversed."` **Nowhere does either sentence, or any element in the tree, say "80 were never reached" or "80 are still queued."** The 80 are on the board right now, still checked, indistinguishable in every rendered pixel from a task that was actually attempted and refused — which is exactly the outcome the doc comment says the design goes out of its way to avoid ("nothing is known to have been written... reporting them as failures would tell the user that 80 tasks broke"). The code avoids _mislabeling_ them; it does this by not labeling them at all, which is a different, and visually, a materially worse outcome than the failure list's treatment of an actual failure. **Un-attempted does not read as failed — it reads as nothing, which a user then has to interpret unaided as either "still selected on purpose" or "quietly failed," and the UI gives them no way to tell which.**

- **Files**: `libs/frontend/tasks-ui/src/lib/services/tasks-store.service.ts:1392-1454` (the split — correct); `libs/frontend/tasks-ui/src/lib/components/bulk/task-bulk-summary.component.ts:59-134` (the rendering — incomplete); `libs/frontend/tasks-ui/src/lib/components/board/task-card.component.ts:84-98` (no third card state)
- **Impact**: Serious. This is the batch's own highest-stated-risk item (context.md's Q4 note calls C4 "R2, the highest-risk item... score 10"), and the specific failure mode the plan says it engineered around — un-attempted tasks reported as failures — is avoided at the data layer but effectively reintroduced at the visual layer, because "not a failure" renders as "not mentioned," and a user cannot distinguish "not mentioned because it's fine" from "not mentioned because nobody told me."
- **Fix**: a third, explicit line — "N were never reached and are still selected" — parallel in treatment to the headline's success/failure sentence, ideally computed directly (`requested - attempted - ...` is already knowable inside the component from `summary().attempted`/`summary().requested`, no new store field needed) rather than left as subtraction across two unrelated sentences. On the board, the un-attempted subset doesn't need a fourth visual state on the card — but the summary panel absolutely needs to name them, since they're the one group nothing else in the UI ever will.

## 5. The selection checkbox: does not crowd the card, is shape-distinct from the isolate toggle, but is a new sub-24px hit target

`task-card.component.ts:112-121`. Laid out first in the header row (`class="flex items-start justify-between gap-1"`, `:101`), ahead of the id span (`flex-1 truncate`, `:122-126`), the optional pending spinner, the optional warning icon, and the status-menu trigger. Because the id span is the one flexible, truncating element in that row, the checkbox does not force any horizontal overflow — I traced the row's content budget the same way Batch 7 traced the filter bar's, and there's nothing here that can't shrink. **Not a crowding defect.**

**It is visually distinguishable from the isolate toggle**, which is the other checkbox-shaped control on the card. `.checkbox` (this control) renders as a small square box with a checkmark; `.toggle` (`task-card.component.ts:366-373`, the isolate control) renders as a pill-shaped switch — genuinely different silhouettes, per daisyUI's own compiled rules, not just a colour difference — and they sit in different rows of the card (header vs. footer), so there's no proximity confusion either. **Confirmed distinguishable**, on both shape and position.

**Its hit target is 16×16px, under the 24×24px SC 2.5.8 floor this task has repeatedly enforced.** I read daisyUI's compiled CSS directly: `[type="checkbox"].checkbox-xs { height: 1rem; width: 1rem }` (`node_modules/daisyui/dist/full.css:27843-27845`) — 16px, not the `.btn-xs` 24px this task's own established rule (`task-card.component.ts:278`'s own comment: "`btn-xs` is 24px — SC 2.5.8's floor") deliberately targets. The checkbox is a bare `<input>` with `mt-0.5 shrink-0` (spacing only, no padding) and no wrapping `<label>` — unlike the isolate toggle, which at least sits inside a `<label class="label cursor-pointer gap-1 p-0">` (even that has `p-0`, so it doesn't clear the floor either, but that toggle predates this batch — Batch 10's own precedent is to not re-score a pre-existing sub-floor control). This checkbox is new to Batch 12, and at 16px it is the second sub-24px control this task's own component now carries (alongside the pre-existing 20px status-menu trigger at `:155`, also out of scope per Batch 10), and the first one that is a plain, unwrapped native element with genuinely nothing padding out its box.

- **File**: `libs/frontend/tasks-ui/src/lib/components/board/task-card.component.ts:112-121`
- **Impact**: Serious — matches the severity this task assigned the same defect class in Batch 7 (the 12px rollup badge, the 12px chip-remove button), both of which were fixed by moving to a `.btn`-class or explicit sizing.
- **Fix**: wrap the input in a `<label>` with real padding (e.g. `p-1`, giving an effective ~24px box while the visual glyph stays 16px), the standard daisyUI/Tailwind pattern for exactly this — a checkbox glyph that stays visually compact while its clickable region clears the floor.

## 6. The `pending` state: reads as in-progress, not failure — one adjacent oddity worth naming

`task-card.component.ts:131-138`. `loading loading-spinner loading-xs` with `role="status"` and a per-task `aria-label` (`'Updating ' + task().id`). The spinner uses `currentColor` (no semantic-error/warning tint anywhere in its class list), so it carries no alarm colour — it reads as motion, not danger, which is the right choice for a state that is neither success nor failure. Positioned between the id and the warning/status-menu icons, small enough (`loading-xs`) not to compete visually with the checkbox for attention. **On the letter of item 6 — visible without being alarming, reads as in-progress — this is correct**, and I found no contrast or colour concern on it (it inherits `text-base-content`, already established at 7-14:1 across the mandated bases in prior batches for this exact token).

**One adjacent, minor oddity I traced through the code rather than guessing at**: nothing disables the checkbox while a card is `pending()`. `bulkUpdateStatus` captures the id list once at the start of the run (`tasks-store.service.ts:1294`, `const ids = [...this._selection()]`) — a later click on that same card's checkbox changes `_selection` but has no effect on the in-flight write, which already has its own copy of the id list. So a user can, mid-run, uncheck a card that is still visibly spinning — producing a card that shows **no checkmark and an active spinner at the same time**, which momentarily reads as "why is an unselected card being written to?" It resolves itself the instant the run's `finally` block clears `_pending` (`tasks-store.service.ts:1334`), and functionally nothing is wrong (the write still lands or fails on its own terms), but it's a reachable, code-confirmed visual inconsistency, not a hypothetical one.

- **File**: `libs/frontend/tasks-ui/src/lib/components/board/task-card.component.ts:112-121` (checkbox, unconditional); mechanism at `libs/frontend/tasks-ui/src/lib/services/tasks-store.service.ts:1292-1334`
- **Impact**: Minor, non-blocking.
- **Fix** (optional): `[disabled]="pending()"` on the checkbox, or simply accept the momentary mismatch as harmless — the run's own bookkeeping does not depend on the checkbox staying checked.

## 7. Contrast — recomputed, not asserted

I did not take the two components' own doc comments on faith, even though both are unusually careful (both cite the exact `alert-error`/`alert-info` numbers from Batch 9's audit and correctly avoid those classes — confirmed by grep, zero `alert-*` occurrences in either file). What neither doc comment addresses is `primary`/`primary-content` — the pair Batch 7 found failing and Batch 10 explicitly moved the palette's active-row fill _off of_, root cause still unfixed (`tailwind.config.js` is explicitly off-limits to this batch per the brief).

**`task-bulk-bar.component.ts:109-116`, the confirm-run button, uses `btn btn-primary btn-xs`.** `.btn-primary` paints `background-color: var(--p)`, `color: var(--pc)` — the exact pair already established. I re-read the literal anubis values directly rather than trusting the prior batches' citation: `apps/ptah-extension-webview/tailwind.config.js:51,53` — `primary: '#2563eb'`, `'primary-content': '#e8e6e1'` — unchanged since Batch 7 first computed this pair at **4.144:1**, which fails the 4.5:1 normal-text gate (`btn-xs` text is 12px, unambiguously normal text). This is the app's own default theme. This button is the run's actual commit action — "Move N to Status?" — the single most consequential control in the whole feature, and its own text is the one piece of text in this batch that fails contrast on anubis.

This is not a new root cause — it's a new, unaudited consumer of one. `task-card.component.ts:272-281`'s own comment shows the team already knows how to route around this exact pair (the child-rollup control was deliberately moved off `badge-primary`/`hover:badge-primary` for precisely this reason, and documents the 4.14:1 figure by name), and Batch 10 did the same for the command palette's active row. Nothing in `task-bulk-bar.component.ts` shows equivalent awareness for this button — the doc comment's contrast section is thorough about `alert-*` and silent about `primary`/`primary-content`.

- **File**: `libs/frontend/tasks-ui/src/lib/components/bulk/task-bulk-bar.component.ts:109-116`; root cause (unchanged, out of this batch's scope) `apps/ptah-extension-webview/tailwind.config.js:51,53`
- **Impact**: Serious — matches the severity this task assigned the same pair in Batch 7 and Batch 9, on the app's own default theme, on the button most likely to be pressed in this entire feature.
- **Fix**: the same move already made twice elsewhere in this codebase — stop using `btn-primary` for this button specifically (e.g. `btn-outline btn-primary`, which changes the _border_ to primary rather than filling with the failing text/background pair, or simply `btn` with no colour suffix, matching the neutral treatment the rest of this bar already uses for every other button).

**Everything else in both files is compliant with the established rule.** I grepped both components for `text-\w+/[0-9]` and `alert-`: zero hits outside doc comments. Every text node is `text-base-content` at full opacity on `bg-base-200` — the same pairing Batch 9/10 independently verified at 12.3-14.9:1 across all four mandated bases. `text-error` on the failure icon (`task-bulk-summary.component.ts:111`) is `aria-hidden`, decorative reinforcement rather than the signal (the row's text states the failure in words regardless) — I computed it anyway, since WCAG 1.4.11 can still apply to a meaningful graphic: `#dc2626` (anubis `error`) against `#1a1a20` (anubis `base-200`) computes to **≈3.75:1**, clearing the 3:1 non-text gate even though the icon doesn't strictly need to. The checked-card fill (`task-card.component.ts:90`, `bg-base-200`, unmodified from the existing daisyUI token) is a background, not text — not subject to the text-contrast gate, and it is the same token already in use elsewhere on the card for other structural surfaces, so it introduces no new colour value to audit.

## 8. Accessibility beyond contrast

- **Focus rings on every new control are covered by the app's existing global rule**, unlike Batch 7's `<summary>` gap. The checkbox is a real `<input>`, the `<select>` is a real `<select>`, every button in both components is a real `<button>` — all four are inside the `button, input, select, textarea, a` selector the global focus-visible rule targets (`apps/ptah-extension-webview/src/styles.css:439-448`). I found no new `<summary>`, `<div role="...">`, or other element type that would fall outside that rule the way the facet-menu triggers did. **No new gap.**
- **Accessible names are present and correctly stateful.** The checkbox's `selectAriaLabel()` (`task-card.component.ts:658-662`) states the action and direction ("Select"/"Deselect task `<id>`"), matching the pattern this task already established for the rollup button. Retry (`task-bulk-summary.component.ts:69-76`) and Dismiss (`:78-87`, `aria-label="Dismiss this summary"`) both carry accessible names independent of colour. Cancel's text changes ("Cancel" → "Stopping after this batch") when disabled, so the state change is legible to a screen reader through the accessible name itself, not only through the native `disabled` announcement.
- **Selection state is conveyed by more than colour.** The checkbox's own native checked glyph is a non-colour, unambiguous signal, independent of the `bg-base-200` fill — satisfying the WCAG 1.4.1 concern the card's own doc comment (`:78-83`) states as the reason the two are kept visually distinct. I did note (§5) that the fill and the column's own `bg-base-200/60` background are close in value, which slightly softens the fill's own contribution — but the checkbox glyph alone is sufficient, so this doesn't rise to a finding.
- **The progress indicator is announced.** `task-bulk-bar.component.ts:56-65`, `role="status" aria-live="polite"` wraps the full "Moving to `<Status>` — N / M" sentence, re-announced on each chunk boundary (every 20 items) — a reasonable cadence, not a spam risk.
- **One minor, non-blocking ARIA-structure note**: the confirmation text is `role="alertdialog"` (`task-bulk-bar.component.ts:89`) on a `<p>` that does not structurally contain the Confirm/Cancel buttons — they're siblings, outside the element carrying the dialog role. `alertdialog` conventionally names a container that owns its interactive content; here the role is on a paragraph that doesn't. I could not verify how VS Code's or Electron's accessibility tree actually presents this without a live host, so I'm flagging it as a structural mismatch worth a second look, not asserting a broken AT experience.

## Verdict

### 3. The three-group split reaching the pixels — the coordinator's own framing was right to press on this; here is the honest answer

`task-card.component.ts:163-181`. Read purely as shapes, at rest, without stopping to read either badge's text, **I would not call the two badges glance-distinguishable from icon or colour alone** — this is the honest version of the answer the coordinator asked for, not the reassuring one.

**Where this differs from "reads as one undifferentiated state" is the text itself, which is the actual, intended signal, and it is unambiguous the moment it's read**: "refused" (7 characters) versus "not attempted" (13 characters) are different words with no risk of confusion, rendered at rest — no hover, no click, no tooltip required to see either one, which is a meaningfully better position than my first-pass finding (where the untouched group had _zero_ representation anywhere on the card). I'd frame the honest verdict this way: **this is not "one undifferentiated 'something went wrong' badge"** — the text is unambiguous, present at rest, and satisfies the same words-not-colour standard this task has held every other component to.
