## Failure Mode Analysis

### Failure Mode 1: Cumulative blank-line drift (the defect this batch fixes) — VERIFIED REAL AND CORRECTLY FIXED

- **Trigger**: any metadata write through `updateFrontmatter`, repeated.
- **Root cause, confirmed empirically** (not from the diff's own comment): `matter.stringify('', data)` — tested directly against the installed `gray-matter` — emits `"---\n<yaml>\n---\n" + "\n"`, i.e. one extra trailing newline beyond the block's closing fence, regardless of whether the source was LF or CRLF (js-yaml always dumps LF; verified with a CRLF-seeded round trip). `FRONTMATTER_RE` (`/^---\r?\n[\s\S]*?\r?\n---(\r?\n|$)/`) consumes only **one** `\r?\n` after the closing fence, so the sliced `body` still carries whatever blank line legitimately follows. Pre-fix, concatenating the two-newline block with the body inserted one extra blank line per write, and because the next write re-slices the same way, the extra line becomes part of `body` and a fresh extra line is added again — genuine, unbounded accumulation on a gitignored, undo-less file.
- **Fix**: `.replace(/\n$/, '')` on the stringified block before concatenation, making the rebuilt block end in exactly the one newline `FRONTMATTER_RE` will consume on the _next_ write — idempotent by construction.
- **Verified correct and complete, by direct testing, not by trusting the test file**:
  - CRLF: confirmed `matter.stringify` never emits `\r\n` (js-yaml is LF-only), so `.replace(/\n$/, '')` is the right (and only necessary) strip regardless of the source file's line-ending style. The body itself is untouched byte-for-byte since it's a plain slice — CRLF in the body survives regardless of frontmatter re-serialization.
  - A body that legitimately begins with a blank line: preserved. `FRONTMATTER_RE` still only ever consumes one newline, so any additional blank line the author put between the fence and the body is `body`'s own leading content and was never touched by the fix.
  - An empty body: traced by hand (`raw` ending exactly at the closing fence's single trailing newline) — `body = ''`, rebuilt output ends in exactly one newline, matching pre-batch shape.
  - BOM: independently verified the mock's `TextDecoder` strips a leading BOM on read (`new TextDecoder().decode(...)` with default `ignoreBOM: false`), confirmed by direct execution, not by reading the test's comment — so the BOM assertion is correctly placed against `updateFrontmatter` directly, not through the mock. A mock-routed version would indeed have been green while proving nothing.
  - One genuinely unrealistic edge case, not tested, not blocking: a carrier with **zero bytes** after the closing fence's `---` (no trailing newline at all — regex matches `$`, not `\r?\n`) would, post-fix, gain a trailing newline it didn't have pre-fix, since the fix always leaves exactly one `\n` after the fence. `renderTaskMd` always terminates with a newline, so no current producer creates this shape. Noted as a residual, extremely low-probability, non-blocking gap.
- **Confirmed it is genuinely the single write path, not a second splice in disguise**: grepped every `this.fs.writeFile` call in `task-writer.service.ts` — exactly two: `writeCarrier` (used by `create`/`adoptFolder`, unrelated to metadata update, zero diff to `adoptFolder` itself) and `applyFrontmatterPatch`'s single write (used by both `updateStatus` and `updateMetadata`). `registry-generator.service.ts` and `task-spec.contract.ts` (`renderFrontmatterBlock`) show **zero** diff (confirmed by file-level `git diff --stat`, not by string search).
- **Re-ran the accumulation regression myself**: the new `task-writer.metadata.spec.ts` performs four consecutive `updateMetadata` calls and asserts the body is unchanged afterward; ran it in isolation (27/27 pass) independent of the full suite.

## Adjudication of the three developer decisions

### 1. The blank-line defect and its fix

**Real defect, correctly and completely fixed** within the scope of realistic inputs. See Failure Mode 1 above for the full verification (root cause reproduced against the actual installed `gray-matter`, fix traced against `FRONTMATTER_RE`'s exact consumption, CRLF/BOM/empty-body/leading-blank-line cases all independently checked, not merely inferred from the test file's existence).

### 2. `patchChangesSomething` vs. the plan's `.refine((p) => Object.keys(p).length > 0)`

**Verified true and the substitute is genuinely stronger, not merely different.** Tested directly against the installed `zod@4.3.6`:

```
z.object({a:z.string().optional()}).parse({})              → {} (no key)
z.object({a:z.string().optional()}).parse({a: undefined})  → {a: undefined} (KEY PRESENT)
```

So the plan's literal `Object.keys(p).length > 0` would pass a caller-supplied `{ labels: undefined }` (any code path that spreads a partially-undefined object into the patch — e.g. handler code building a patch from optional local variables — would produce exactly this shape), reach `updateFrontmatter`, refresh `updated`, and rewrite a carrier on behalf of a caller who asked for no change, on a tree with no undo. `Object.values(patch).some((v) => v !== undefined)` correctly returns `false` for both `{}` and `{ labels: undefined }`, and correctly returns `true` for any patch carrying a real value (including `labels: []`, which is a real "remove the key" request, not a no-op). This is a Zod-4-specific behavior change from Zod 3 the plan predates; the deviation is correct and should be adopted as the standard idiom elsewhere in this codebase's Zod-4 boundaries where a similar "did the caller actually ask for anything" check exists.

### 3. Guard hardening beyond the stated three, plus writer-level defense-in-depth

**Both correct, not scope creep.** `TasksGetParamsSchema.taskId` and `TasksUpdateStatusParamsSchema.taskId` were bare `z.string().min(1)` — **weaker** than the three guards G3 explicitly named (which at least checked for `/`, `\`, and exact `..`). Folding all five sites onto one implementation is the only fix that doesn't recreate the exact divergence G3 exists to end, and `tasks:get`'s previously-unguarded `taskId` is arguably the more urgent of the two additions, since an unguarded read-side `taskId` is a file-disclosure vector (read arbitrary files under `.ptah/specs/../..`), not merely a write-side one.

The writer-level `isSingleTaskPathSegment(taskId)` check inside `updateMetadata` is a deliberate, narrow deviation from "trust past the validated boundary" (per `CLAUDE.md`'s stated Zod-boundary standard), scoped only to `taskId` (the one value this exact method joins onto a path) and `parent` (the one field this codebase has treated with elevated caution since Batch 1). Given `TaskWriterService.updateMetadata` is the single funnel every future caller (RPC, MCP, and eventually bulk operations in Batch 11) routes through, and given `.ptah/**` has no undo, this is a defensible, narrowly-scoped exception to the "trust past the boundary" rule rather than redundant validation — it is not blanket re-validation of every field (the relation arrays are correctly left to the Zod boundary alone, since they're never path-joined — see Failure Mode 3's finding above).

Cheap, closes the gap permanently rather than relying on every future call site happening to append a suffix.

## Minor / Informational Issues

### Minor Issue 3 — MCP-path G2 coverage is call-boundary only, not on-disk, contrary to the stated verification methodology

`tasks-namespace.builder.spec.ts`'s "G2 — create carries the five metadata fields to the writer" tests use a mocked `writer.create` (`jest.fn()`), never a real `TaskWriterService` + real mock filesystem. The developer's Batch 4 report frames this as "asserted twice per path — at the call boundary and against a real carrier on disk," which is true for the RPC path (`tasks-rpc.handlers.spec.ts`) but not literally true for the MCP path taken alone. Traced and found the gap is closed **transitively**, not by this file: `tasks-namespace.builder.ts`'s `create()` has zero diff and forwards `parsed.data` wholesale to the same `TaskWriterService.create()` the RPC on-disk test exercises, so a regression in the writer would still be caught. A regression specific to the MCP wrapper (e.g. someone later replaces the `parsed.data` spread with an explicit field list and forgets one) would still be caught by the mocked call-boundary assertion. Net: no real coverage hole, but the stated methodology overclaims what the MCP spec file proves in isolation. Suggest tightening the batch report's wording rather than adding a test.

### Minor Issue 4 — Guard docstring overstates the live threat for drive-relative paths

`isSingleTaskPathSegment`'s docstring claims a drive-relative value "escapes a join without ever containing a separator." Live-tested: `path.join(root, '.ptah', 'specs', 'C:NAME', 'task.md')` does **not** reinterpret the embedded `C:NAME` as an absolute reference — Node's `path.join` treats it as a literal middle segment, and Windows `fs` returns `ENOENT`. The escape scenario is real only if the tainted string were used as a _bare_ path (not embedded via `path.join`) — which none of this codebase's current call sites do. Rejecting it anyway is still correct (belt-and-suspenders, and cheap), so this is not a functional issue — purely a documentation-accuracy note, since a future reader might over-trust the stated mechanism.

### Minor Issue 5 — Trailing-dot/trailing-space concern (carried from Batch 1's review as Moderate Issue 2) does not reproduce on this OS/Node combination

Batch 1's review flagged `" .. "`/trailing-space/trailing-dot values as dangerous because "Windows' `CreateFile`-family APIs silently strip trailing dots and spaces." Live-tested on this Windows 11 + current-Node combination: `TASK_2026_100 ` and `TASK_2026_100.` both resolve to `ENOENT`, i.e. they do **not** alias to `TASK_2026_100`. The padded-traversal case (`" .. "`) is separately and correctly rejected by the guard regardless (it trims to `..`). This downgrades, but does not eliminate, the original concern — different Windows/Node/filesystem-driver combinations could plausibly behave differently, and the guard doesn't reject bare trailing dots/spaces on a name that isn't otherwise `.`/`..`. Not asking for a fix; flagging so a future reviewer doesn't need to re-derive this.

### Minor Issue 6 — Empty-body-with-no-trailing-newline edge case, untested

See Failure Mode 1's last bullet. A carrier with literally zero bytes after the closing fence's single newline would gain a trailing newline it didn't have, post-fix. No current producer creates this shape (`renderTaskMd` always terminates with `\n`).
