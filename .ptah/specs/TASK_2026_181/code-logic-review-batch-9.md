## Failure Mode Analysis

### Failure Mode 1: Rapid apply-then-apply-a-different-view races the active-pointer write

- **Trigger**: user clicks "Show View A" in the saved-views menu, then clicks "Show View B" before the first `tasks:saveViews` round trip resolves (plausible: webview↔host bridge latency is not instant, and nothing visually indicates a request is in flight for this specific control).
- **Symptoms**: `TaskViewsService.applyView()` sets the board filter/sort **synchronously in click order**, so the board content always ends up correctly showing View B's lens. But each call also fires an independent `persist()` whose _success_ branch does `this._activeViewId.set(requested)` using the `activeViewId` value **captured in that call's own closure**. If the RPC for "View A" resolves _after_ the RPC for "View B" (plausible under real network/bridge jitter), the final `_activeViewId` reverts to `'A'` — the menu highlights and badges View A as active while the board is actually showing View B's results. A page reload afterward reflects whichever `tasks:saveViews` call physically landed last server-side, which need not be the user's last click either.
- **Impact**: visibly inconsistent UI (wrong view highlighted/checked in the menu vs. what the board shows); on reload, the active view can silently differ from what the user last selected. Not data loss (both writes carry the same, unmodified `views` array — only the active pointer races) but a real, user-visible correctness bug.
- **Current handling**: none. Every _other_ control in the same row — move up (`task-view-move-up`), move down, update (`task-view-update`), rename (`task-view-rename`), delete (`task-view-delete`) — is `[disabled]="busy()"` (`task-view-menu.component.ts:234, 245, 263, 280, 291`). The apply button (`task-view-menu.component.ts:212-229`, `data-testid="task-view-apply"`) has **no `[disabled]` binding at all**, breaking the pattern the rest of the same component establishes. No test exercises this (`task-view-apply` appears only in click/label/hostile-name tests in `task-view-menu.component.spec.ts`, never in a `busy: true` scenario).
- **Recommendation**: add `[disabled]="busy()"` to the apply button, consistent with every sibling control in the row. This is a one-line fix; flagging because it is the kind of asymmetry that is easy to miss in review of a large template and the rest of the file demonstrates the author was clearly aware of the pattern.

### Failure Mode 2: The stale-facet note for executors can be wrong in the direction that misleads the user

- **Trigger**: a saved view's `filter.executors` array contains a value that is not already whitespace-trimmed exactly the way `TaskGraph.knownExecutors` stores it — reachable via a hand-edited `~/.ptah/settings.json` (a scenario the component's own doc comments explicitly anticipate: "the list is read back out of a settings file a user can hand-edit", `task-view-menu.component.ts:44-49`) or any external caller of `tasks:saveViews` (MCP, a future CLI flag, a prior app version), since `TaskFilterSpecSchema.executors` is `z.array(z.string().min(1).max(...))` with **no trim transform** (`task-filter.ts:259-262`).
- **Symptoms**: the shared predicate `matchesExecutors` trims the **selected** filter value before comparing (`selected.some((value) => value.trim() === executor)`, `task-filter.ts:355`), so a filter value like `' Alice'` still matches a task whose executor is `'Alice'`. But the stale-facet check in `TaskFilterBarComponent.chips` does **not** trim the filter value before testing set membership: `knownExecutors.has(executor)` (`task-filter-bar.component.ts:752`) where `executor` is the raw, untrimmed entry from `filter.executors` and `knownExecutors` (line 684) holds only trimmed values (mirroring how `TaskGraph.knownExecutors` is built, `task-graph.ts:421-422`, `task.executor?.trim()`). Result: the chip is annotated "no longer present in this workspace" for a facet value that **actively matches tasks on the board** — the exact wrong-direction error the note exists to prevent (a user reading "no longer present" and concluding, incorrectly, that the facet is dead and safe to ignore/remove).
- **Impact**: a misleading annotation on live UI. No data loss, no auto-pruning (the underlying spec is still untouched, per the write-side check below), but it directly contradicts the developer's own claim that the check "match[es] how the predicate matches" — it does not, specifically for whitespace.
- **Contrast with labels**: labels are symmetric and correct. Both `matchesLabels` and the chip's stale check fold through the same `labelKey` (trim + lowercase) on both sides (`task-filter.ts:334-337`, `task-filter-bar.component.ts:683`), so there is no equivalent bug there. This asymmetry is specific to the executor path, which was deliberately **not** folded (case-sensitivity is correct and intentional per `task-filter.ts:340-347`) but the trim was dropped along with the case-fold.
- **Current handling**: none; not covered by any test. `task-filter-bar.component.spec.ts`'s stale-facet describe block (`the stale-facet annotation`) tests case difference (`'Alice'` vs `'alice'`) and label trailing-space/case-fold, but never a filter value carrying leading/trailing whitespace itself.
- **Recommendation**: `knownExecutors.has(executor.trim())`, mirroring the predicate exactly (`task-filter-bar.component.ts:752`). Low-risk, one-line fix.
- **Confidence**: HIGH on the mechanism (verified by direct reading of both `matchesExecutors` and the chip-note computation side by side). MEDIUM on real-world severity — the trigger requires a value that never enters `filter.executors` through the shipped picker UI (which only ever offers already-trimmed `knownExecutors()` entries, `task-filter-bar.component.ts:624-631`), so this is a real but narrow-window correctness gap rather than something a normal click-through session can hit today.

## Moderate Issues

### Issue: "no `tasks:saveViews` is issued when a stale view is applied" is true only for the passive (already-active-on-load) path, not for an interactive Apply click

- **File**: `task-views.service.ts:320-328` (`applyView`), contrasted with `tasks-view.component.spec.ts` (`applies a view naming a vanished label, annotates it, and prunes nothing`) and `task-views.service.spec.ts` (`the stale-facet annotation` / "applies, matches nothing, and prunes nothing").
- **Scenario**: `applyView(id)` unconditionally calls `await this.persist(this._views(), view.id)` — this **does** issue a `tasks:saveViews` call, to persist the active-view pointer (contract 3/4 territory), regardless of whether the target view's facets are stale. The component-level test that asserts `expect(rpcCall).not.toHaveBeenCalledWith('tasks:saveViews', ...)` only holds because that specific test seeds the view as **already active from the initial `tasks:getViews` payload** (`activeViewId: 'view-stale'`), which goes through `applyReadResult`'s read-only branch (no `persist()` call) rather than through a user click on `task-view-apply`. The service-level test in the same area (`applies, matches nothing, and prunes nothing`) _does_ show a `tasks:saveViews` call (`harness.saves[0]`) for the equivalent scenario reached via `applyView()`.
- **Assessment**: not a bug — the write only ever carries the view's filter **unchanged** (no auto-pruning occurs; verified: `sent[0].filter.labels` stays `['retired-label']`), so FR-C2.4 (nothing is auto-pruned) is genuinely upheld either way. This is a precision note: the "no save on stale apply" claim should be read as "no save that _edits_ a stale filter," not "applying a stale view is a pure read." Recommend tightening the doc comment or the component test's own framing so a future reader does not over-generalize from the single test that happens not to exercise the click path.

### Finding 1 (round 1) — apply-button busy guard: CONFIRMED FIXED

`task-view-menu.component.ts:279-280` now carries `[disabled]="busy()"` on the apply button, alongside every sibling control. This is a genuine fix, not cosmetic: because it is a native `disabled` attribute on a `<button>`, a programmatic or user `.click()` does not dispatch a `click` event at all (DOM spec behavior, honoured by jsdom), so `viewApplied.emit(...)` cannot fire while `busy()` is true — the race is closed at the point of entry, not papered over by disabling a handler that could still run.

Verified the guard actually closes the described race:

- `TasksViewComponent` wires `[busy]="views.saving() || views.loading()"` (unchanged since round 1), and `TaskViewsService.persist()` sets `_saving` to `true` for the full duration of a `tasks:saveViews` round trip (`task-views.service.ts:508`, `finally` at 560-562). So from the moment a first `applyView()` call fires its RPC to the moment that RPC resolves, `busy()` reads `true` for the whole menu.
- Two tests confirm the closure directly: `locks every mutating control, apply included, while a write is outstanding` (`task-view-menu.component.spec.ts:421-439`) asserts `.disabled === true` on **every** apply button (not just one row) via the native DOM property, and `emits nothing when apply is clicked while busy` (`task-view-menu.component.spec.ts:441-450`) clicks a non-active row's apply button while `busy: true` and asserts `applied` (the subscribed output array) stayed `[]`.
- This closes exactly the scenario I described in round 1: view A clicked, then view B clicked before the first RPC settles — the second click is now a no-op at the DOM level, so only one `applyView()` (and one `tasks:saveViews` call) can be in flight from this control at a time. No remaining race through this path.

### `nextViewId` collision-branch coverage — CONFIRMED, genuinely pinned
