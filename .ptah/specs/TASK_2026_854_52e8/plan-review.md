# Cross-family design review

**Verdict: REJECT.** The design needs a stable evidence precedence and durable handling of first-turn events before implementation. Source code was read only; no build or test was run.

## Findings

1. **Blocker — Reconciliation is order dependent and retains stale auto links.** `decisions.md:58-61,71-102` gives R4 and R5 the same `worktree` rank, applies R5 only when R4 has no ID, and never deletes an auto link. If peer evidence first links task A through R5, then the worktree name later identifies task B through R4, `decideTaskLink` keeps A primary because ranks tie; B becomes related. If the events reverse, B wins. A parent changing its primary likewise leaves the child's old inherited link. The store only demotes on a new primary and upserts; it has no evidence-removal step (`libs/backend/session-organization/src/lib/session-organization.store.ts:784-799`). **Fix:** give R4 explicit priority over R5, persist the evidence/rule that owns each auto link, and reconcile the complete desired auto-link set, removing or demoting links whose evidence vanished while preserving protected and suppressed links. Test both event orders, peer ambiguity appearing later, worktree rename, and parent/fork changes.

2. **Blocker — A first prompt can be lost before SQLite opens.** The host starts capture before `openAndMigrate`, and captures while closed are dropped (`libs/backend/session-organization/src/lib/di/start.ts:10-15`; `libs/backend/session-organization/src/lib/session-organization.service.ts:757-775`). The plan repeats this for auto linking (`implementation-plan.md:309-315,483-485`) and assumes a next event retries, but a one-time `/orchestrate` hook need not recur. Removing the board fallback leaves that session unlinked. **Fix:** queue validated first-turn candidates until the store's `onDidOpen` signal, or gate SDK first-turn processing on migration; replay by real session ID and test prompt-before-open followed by open, reload, and restart.

3. **Blocker — Suppression and rekey are not atomic.** `decisions.md:107-117,283-292` and `implementation-plan.md:253-257,483-486` use two stores and explicitly log a failed second-store rekey/delete without retry. The current rekey removes old link rows and emits the new ID (`libs/backend/session-organization/src/lib/session-organization.service.ts:587-605`; `libs/backend/session-organization/src/lib/session-organization.store.ts:751-758`). If the main-store rekey succeeds but suppression rekey fails, a previously unlinked task is eligible for automatic relinking under the new ID, including after restart. A failed delete leaves suppression/todo rows, contrary to the required cascade. **Fix:** run link, suppression, todo, rekey and delete writes in one SQLite transaction on the shared connection, or make failures retryable before publishing a successful rekey/delete. Test injected failures at every boundary.

4. **Major — An unsent board launch is lost on reload.** The three board prompt branches really do begin with `/orchestrate <taskId>` (`libs/frontend/tasks-ui/src/lib/services/task-start.service.ts:144-164`), and the bridge only prefills it (`libs/frontend/chat/src/lib/services/chat-store/task-prompt-bridge.service.ts:119-126`). The prefill is a one-shot signal (`libs/frontend/core/src/lib/services/app-state.service.ts:460-465,1407-1423`), consumed into an input (`libs/frontend/chat/src/lib/components/templates/chat-view.component.ts:1284-1297`); `ComposerDraftStore` holds drafts only in a signal-backed map (`libs/frontend/chat/src/lib/services/composer-draft.store.ts:19-51`). A reload before send loses both prompt and task intent, despite `decisions.md:133-138` saying reload cannot lose a link. **Fix:** persist the board-created draft or task intent with the tab until first send, restore it after reload, and test reload before send plus subsequent send. The host prompt rule can still own the final link.

5. **Major — The expansion path can attribute a subagent command to the parent.** R3's expansion alternative has no main-thread condition (`decisions.md:57`; `implementation-plan.md:279-286`). The expansion handler forwards `command_name`, `command_args` and resolved session ID without inspecting `agent_id` (`libs/backend/agent-sdk/src/lib/helpers/user-prompt-expansion-hook-handler.ts:35-61`), whereas the submit handler explicitly recognizes subagent prompts (`libs/backend/agent-sdk/src/lib/helpers/user-prompt-submit-hook-handler.ts:75-83`). **Fix:** add optional `agentId` to `UserPromptExpansionPayload`, populate it from hook input, reject subagent expansions in R3, and test the subagent-only expansion case.

6. **Major — Existing sessions and later task folders do not get reconciled.** The plan says there is no startup backfill and only a later organization change retries a missing task folder (`decisions.md:172-178`). New worktree detection runs only on `SessionIdResolved` (`decisions.md:187-192`; `implementation-plan.md:287-294`), while `startSessionOrganization` merely subscribes (`libs/backend/session-organization/src/lib/di/start.ts:36-49`). A persisted session resumed after restart, or a task folder created after the last organization change, may never receive its required worktree link. **Fix:** reconcile persisted sessions at startup/resume and on task registry changes, with bounded batched reads; test restart with preexisting metadata and task-folder creation after the first scan.

7. **Major — Migration 0063 breaks an existing guard spec.** Version 63 is free: `libs/backend/persistence-sqlite/src/lib/migrations/index.ts:442-447` ends at 62 and the migration directory ends at `0062_provider_account_operation_host.ts`. The 0062 spec asserts that the maximum version is exactly 62 (`libs/backend/persistence-sqlite/src/lib/migrations/0062_provider_account_operation_host.spec.ts:51-60`), so registering 0063 makes it fail. Static SQL, `IF NOT EXISTS`, no enum CHECK and the runner-owned transaction match the 0050/0062 conventions (`libs/backend/persistence-sqlite/src/lib/migrations/0050_session_organization.ts:15-24`; `libs/backend/persistence-sqlite/src/lib/migrations/0062_provider_account_operation_host.ts:20-30`). **Fix:** change the 0062 spec to assert its relative registration only, and make the new 0063 spec assert the new maximum, schema and idempotence.

8. **Major — Task ID validation disagrees across entry points.** R3/R4 accept sequence lengths of three or more (`decisions.md:63-69`), matching the allocator, but `ptah_session_start taskId` still uses exactly three digits (`libs/backend/vscode-lm-tools/src/lib/code-execution/mcp-core/session-tool-args.schema.ts:23-24,39-45`). Thus a valid `TASK_2026_1234` works through `/orchestrate` but is rejected by R2, violating the common precedence table. `decisions.md:312-313` explicitly defers the mismatch. **Fix:** share one task-ID schema across MCP and host rules now, and pin four-digit sequence cases at both boundaries.

9. **Minor — Guard and contract coverage needs tightening.** The plan adds DI smoke checks but leaves VS Code's unavailable spec unchanged (`implementation-plan.md:430-445`). Since the new services are registered behind a SQLite token (`libs/backend/session-organization/src/lib/di/register.ts:33-38`) and VS Code intentionally has no organization service (`apps/ptah-extension-vscode/src/di/session-organization-unavailable.spec.ts:89-114`), assert the new tokens are absent there and the new cache makes no RPC read. Keep RPC Zod guards: webview sources are restricted to `user`/`board-start` (`libs/backend/rpc-handlers/src/lib/handlers/session-organization-rpc.schema.ts:69-73,96-102`), while host hook TodoWrite inputs need the planned Zod parse. Also revise `contract-for-git-view.md:17`: a null `worktreePath` means unknown or workspace root; failed worktree detection can leave it null (`decisions.md:187-192`). **Fix:** add the absence/cache specs and clarify the null contract.

## Verified decisions and scope

- **Status policy is sound:** the requirement permits zero automatic status writes (`context.md:26-29`); the board delegates transition to the agent (`libs/frontend/tasks-ui/src/lib/services/task-start.service.ts:43-47`), and `updateStatus` delegates without an expected-status precondition (`libs/backend/task-specs/src/lib/task-writer.service.ts:483-497`). No status-write change is needed.
- **File placement is reasonable:** existing store/service are already 875/949 lines; `implementation-plan.md:273-336` puts rules, auto storage, reconciliation and todo capture in separate files. Keep the proposed main-file additions limited to by-ID access and transaction orchestration.
- **Verification gap:** `implementation-plan.md:513-579` lists many rule and restart cases, but add the failure, stale-evidence, startup, subagent-expansion and pre-send reload cases above. No matching invocable review skill was exposed in this lane; `rg` was inaccessible, so file searches used Ptah and PowerShell.
