## R3 findings

1. **Blocking cap deletion — PARTIAL.** The cap now calls `postUndeliveredNotice`, which removes the pending record and queues a short notice (`subagent-handoff-delivery.ts:264-285,321-343`). A dropped notice restores a notice-only record when the session is live (`:331-340`), so a later parent message can repost it (`:197-210`). However, the queue reaches the parent only when a later main-thread PostToolUse drains it (`post-tool-use-hook-handler.ts:91-109`). If the fifth rejected retry finishes after the last tool result of a turn, the queued notice is cleared at turn end (`session-budget.service.ts:258-269`), and the callback can only mark it due for a *later* main-thread message. If the session ends first, `SubagentBudgetMonitor.release` deletes the restored record (`subagent-budget-monitor.ts:576-591`; `subagent-handoff-delivery.ts:215-222`). Neither handoff nor terminal notice reaches the parent. Keep an owner-visible terminal route or durable unresolved state until delivery is observed; do not treat queue insertion as delivery.

2. **Message during drop-triggered backoff — FIXED for the R3 scenario.** `sendDropped` registers the record before awaiting the first push (`subagent-handoff-delivery.ts:229-248`); `retryPending` records an opportunity while `inFlight` (`:197-210`), and a failed drop-triggered send consumes it immediately (`:248-261,288-294`). The new spec injects the parent message inside that backoff and verifies a subsequent push (`subagent-handoff-delivery.spec.ts:183-214`). The concurrency defect below is a distinct overlap after the guard clears.

## New findings

1. **Serious — one pending handoff can be pushed twice concurrently, and its terminal notice can be queued twice.** `pushRecord` clears `record.inFlight` as soon as `push` settles, before the awaiting `sendDropped` or `retryRecord` continuation consumes `record.missed` (`subagent-handoff-delivery.ts:297-313,248-261,265-294`). A parent message during the first push sets `missed = true` (`:205-206`). After that push rejects, a second parent message can run in the promise-continuation gap, see `inFlight = false`, and start `retryRecord` (`:207-210`); the original continuation then sees the still-true `missed` flag and starts another `retryRecord`. Both call `pushParentMessage` for the same record. The executor invokes monitor observation without awaiting it, so overlapping observations are permitted (`session-query-executor.service.ts:284-295`). If either push succeeds, the parent can receive duplicate handoffs; near the retry cap, both failed calls can independently queue the terminal notice (`subagent-handoff-delivery.ts:266-285,321-343`). **Fix:** hold one record-level ownership guard across the push, missed-opportunity decision, and cap transition. The guard must be checked atomically before incrementing retries or posting a notice; drain a remembered opportunity in that same owner loop.

## Failure-mode checks

1. **Silent success:** cap handling returns normally after queue insertion, even when turn-end clear and release prevent parent delivery (`subagent-handoff-delivery.ts:275-285,321-343`; `session-budget.service.ts:262-269`).
2. **User action:** ending the turn after the cap attempt drops the notice; session end then removes its restored record (`main-thread-notice-queue.ts:116-120`; `subagent-budget-monitor.ts:576-591`).
3. **Wrong answer from input:** two closely spaced main-thread messages can cause duplicate delivery through the cleared `inFlight` window (`subagent-handoff-delivery.ts:205-210,308-313,289-293`).
4. **Dependency failure:** repeated rejected pushes hit the cap and rely on a future hook drain that may never occur (`subagent-handoff-delivery.ts:265-285,328-343`; `post-tool-use-hook-handler.ts:91-109`).
5. **Missing contract:** queue insertion is not an acknowledgment that the parent saw the terminal notice (`main-thread-notice-queue.ts:64-79,85-94`). The unchanged `SEND_TIMEOUT` policy was excluded as requested (`subagent-handoff-delivery.ts:370-379`).
