# Option E design plan review

Verdict: REVISE

Score: 4/10. Removing the pending retry/cap removes R4's two specific defects, but the proposed durable path has several ordinary failure schedules that still lose the only discoverable handoff. This is below 5–6 because the central never-lose guarantee fails at write and lookup boundaries; it is above 1–2 because the normal file write, foreground notice, and background push paths are connected.

Evidence key: all source paths below are relative to the stated worktree; plan and R4 paths are in the task folder. This is a design review of `implementation-plan-e.md` against targeted source reads, not an implementation verdict. No tests or builds were run.

## Blocking

1. **The irreversible stop can complete without a durable record.** The plan explicitly allows no file when the workspace is unknown, a write fails or times out, and even after a session is released during the existing file-preparation wait (`implementation-plan-e.md:96,126-129,175-179,262-264`; `subagent-budget-monitor.ts:847-861`). A later push failure or turn-end queue clear then has neither record nor future pointer; that reproduces R4's silent-loss outcome (`code-logic-review-r4.md:9,19-22`). **Required:** make persistence a prerequisite to the irreversible stop, or define a durable host-owned fallback that is guaranteed discoverable before treating the stop as complete. A timeout must leave an observable unresolved state and a retry/reconciliation path; do not call the no-file path a completed handoff.

2. **A written file can be permanently undiscoverable.** `write` saves the file before its ref, but a failed ref write is only logged; fallback files are ignored by the task-folder convention and the pointer scans only refs (`implementation-plan-e.md:41-46,121-129,203-207,239-243,263-264`; `r4-options.md:51-59`). A session ending after that failure leaves the handoff only in the ignored fallback directory (`.gitignore:135-139`). **Required:** commit an exclusive ref before claiming durable delivery, reconcile orphan files by bounded fallback-directory scan, or use another atomic index. Test a ref failure after each file location is created.

3. **The pointer does not meet “next prompt” or “while pending” discovery.** Pending files younger than 60 seconds are skipped, so the only next prompt can pass without a pointer; pending refs older than seven days are deleted while the only copy remains, so no later prompt can find them (`implementation-plan-e.md:107-109,203-219,274-276`). The hook has no other recurring delivery route (`user-prompt-submit-hook-handler.ts:23-75`). **Required:** point to every unresolved pending file on the next eligible main-thread prompt, including fresh files, and retain discovery of pending files until consumed or explicitly resolved. Use a different mechanism to avoid a concurrent continuer.

4. **The fixed first-20-ref scan can starve a pending file forever.** The plan does not order, rotate, or filter the refs before taking 20; seven days of delivered refs can occupy the first 20 while a later pending ref is never examined (`implementation-plan-e.md:44-46,203-215,216-222`). This is especially likely with two sessions sharing a workspace. **Required:** bound work while guaranteeing fair coverage across prompts, or maintain a bounded pending-only index with atomic updates. Test more than 20 refs with a pending one beyond the first window.

## Serious

5. **Two sessions can overwrite or alias one another's fallback handoffs.** The fallback name and ref key derive from the sanitized tool-use id, and the fallback uses `flag: 'w'` (`implementation-plan-e.md:82-95,121-122`). Sanitization is many-to-one (`subagent-handoff-files.ts:63-73`); reused or colliding ids in the same workspace overwrite the first file and ref, while task-folder `wx` only protects that location. **Required:** use a collision-resistant per-stop key including session identity or a random nonce; create the record and ref exclusively, verify the ref still targets that record, and test concurrent stops in two sessions plus colliding sanitized ids.

6. **The status write can undo an agent's `consumed` edit.** “Read head, replace status, write back” is a read/modify/write; the agent can set `consumed` between the host read and write, and the host can restore `delivered` or overwrite the body (`implementation-plan-e.md:100-112,116-130,239-243`). The shared contract already warns that stale whole-file writes discard another writer's change (`task-spec.contract.ts:553-555`). A 64 KB read cap also leaves large task texts without a status transition (`implementation-plan-e.md:73-78,130`; `subagent-handoff-message.ts:73-75`). **Required:** separate host delivery acknowledgment from the agent-edited record, or specify a genuinely safe compare-and-swap/locking protocol shared by both writers; parse only strict frontmatter and update without a size-dependent whole-body rewrite. Test the interleaving and a large handoff.

7. **Path containment is checked before a later write, and fallback containment is unchecked.** The Task Folder is model-authored; `realpath` plus a one-child `relative` check rejects static traversal, external absolute/drive/UNC paths, and symlinks out of `specs` (`implementation-plan-e.md:85-95`). But a directory or junction can be replaced between validation and `<dirReal>/...` creation; the fallback `.ptah/subagent-handoffs` is recursively created and written with `w` without a realpath check (`implementation-plan-e.md:93-95,121-129`). A symlinked fallback can write outside the workspace, then the pointer rejects it (`implementation-plan-e.md:203-207`). **Required:** validate the destination at creation and at read/delete using canonical workspace containment, reject symlinked path components or use directory-handle-safe operations, and write exclusively. Test traversal, case variants, drive-relative and UNC inputs, symlink swaps, and a symlinked fallback directory.

8. **Cleanup may delete the agent's input while it is in use.** The scan removes delivered or consumed files by mtime and schedules deletion without awaiting it; it has no reader coordination and can race with a continuer opening or editing the same file (`implementation-plan-e.md:105-109,203-215,239-243`). The pending-ref deletion in finding 3 is worse: it keeps a file while removing its only fallback discovery route. **Required:** never delete unresolved pending records; use a lease or a retention rule that excludes files an agent may be reading, and make file/ref cleanup ordered and crash-recoverable. Test agent read/edit overlapping cleanup and process exit between file and ref deletion.

9. **“Delivered” is not an end-to-end acknowledgment.** The plan marks delivery after queue `take` and `SEND_TIMEOUT`, while the queue's `take` only removes a notice before `PostToolUse` returns its `additionalContext`; the timeout path itself says the parent has not read it (`implementation-plan-e.md:101-106,190-197`; `main-thread-notice-queue.ts:81-94`; `post-tool-use-hook-handler.ts:137-160`; `subagent-handoff-delivery.ts:370-379`). A process exit after status flips and before the hook result reaches the model can suppress future pointers. **Required:** define delivery as a verifiable boundary, or keep the file discoverable until `consumed`; test exit/cancellation between `take`, status flip, and hook return. State the accepted semantics of `SEND_TIMEOUT` explicitly.

## Moderate

10. **Ref parsing and index repair are underspecified.** The proposed 1 KB head read and ref-path regex do not state that `status` must be the first key inside a complete YAML frontmatter block with exactly one recognized value; malformed or duplicate keys could be mistaken for pending/delivered (`implementation-plan-e.md:63-78,111-112,203-209`). Cleanup is unawaited, so a stale ref can remain after its target is removed (`implementation-plan-e.md:107-109,208-215`). **Required:** specify strict frontmatter parsing, reject malformed refs/records without deleting their only copy, and reconcile missing targets and partial deletes. Test malformed, duplicate, truncated, and reordered headers, plus file/ref split writes.

11. **The hook's audience assumption needs a gate.** The plan assumes `UserPromptSubmit` is main-thread-only and its `cwd` matches the monitor workspace (`implementation-plan-e.md:224-235`); the current handler checks only the event type and passes the builder's `cwd` (`user-prompt-submit-hook-handler.ts:23-43`; `sdk-query-options-builder.ts:1974-1981`). **Required:** verify this with an SDK fixture or guard the input/session explicitly so a subagent cannot receive another task's pending handoff. Test rekey and a later session in the same workspace.

12. **The test plan omits the schedules that decide correctness.** Planned specs cover static path cases, one timeout, the status table, and basic hook output (`implementation-plan-e.md:131-140,159-162,185-188,220-235,297-303`). They do not cover findings 1–11's split writes, late timeout completion, first prompt before 60 seconds, >20 refs, concurrent sessions, status race, or cleanup/read overlap. **Required:** add fault-injection and controlled-clock tests for those schedules before approval.

## Five logic questions

1. **Silent success:** write/ref failure or hook timeout can return normal delivery with no later pointer (`implementation-plan-e.md:126-129,157-158,263-267`).
2. **User action:** ending the only next turn inside 60 seconds, or continuing an older pending task after seven days, bypasses discovery (`implementation-plan-e.md:107-109,208-219`).
3. **Wrong answer from data:** colliding sanitized ids can replace a different session's handoff, and malformed status can be read as the wrong state (`implementation-plan-e.md:77-78,82-95,121-122,203-209`).
4. **Dependency failure:** slow filesystem, failed ref write, or lost hook output leaves no reliable recovery path (`implementation-plan-e.md:126-129,203-215,262-267`).
5. **Missing contract:** who owns an end-to-end acknowledgment, pending retention, reader safety, and two-session identity remains unspecified (`implementation-plan-e.md:100-112,121-122,190-215`).

The convention scope is reasonable: existing static agent definitions, the generated shared task-spec block, and both orchestration skill copies each serve a separate entry path (`implementation-plan-e.md:237-254`; `task-spec.contract.ts:516-564`; `template-partial-resolver.ts:96-100,150-157`; `.claude/skills/orchestration/SKILL.md:119-128`). The plan also correctly adds the record path to the handoff message before the 2,000-character queue cap (`implementation-plan-e.md:164-170`; `main-thread-notice-queue.ts:29-43`). These parts should remain after the durability and discovery fixes.
