## Flaws

1. **Answer A overstates both duplication and default navigation.** The Activity view does mount pipeline status and diagnostics together (`libs/frontend/skill-synthesis-ui/src/lib/components/skill-synthesis-tab.component.ts:476-490`), but only the diagnostics accordion renders the eligibility histogram and event feed (`libs/frontend/skill-synthesis-ui/src/lib/components/diagnostics/skill-diagnostics-accordion.component.ts:53-64`, `:96-105`); there are not two event lists and two histograms. Also, the default subview is Recommended, not Sessions/Candidates (`libs/frontend/skill-synthesis-ui/src/lib/components/skill-synthesis-tab.component.ts:881-893`). The page has overlapping summaries and poor hierarchy, not the exact duplicated component tree Answer A claims.
2. **Answer A proposes an impossible naming order.** `CandidateNamerService.nameCandidate` requires an existing `CandidateId` and persists through `setDisplayName` (`libs/backend/skill-synthesis/src/lib/naming/candidate-namer.service.ts:117-129`), so it cannot populate `display_name` “before `registerCandidate()`” without changing its contract. More importantly, wiring another LLM pass treats a symptom. Once archaeology-first synthesis owns title and description, delete `CandidateNamerService`; otherwise call it after registration as an explicitly retryable fallback.
3. **Answer A generalizes the first-prompt defect too far.** Name, description, and template body start from the trajectory fallback, and boot deliberately stays template-only, but a successful non-boot synthesizer replaces all three (`libs/backend/skill-synthesis/src/lib/skill-synthesis.service.ts:770-793`). The measured bad names prove that fallback/boot output dominates the live corpus, not that every production path always uses the first prompt.
4. **Answer B is wrong that duplicate track keys crash or reject the view.** The local template can collide (`libs/frontend/skill-synthesis-ui/src/lib/components/diagnostics/event-feed.component.ts:26`), but Angular 21's reconciler records duplicate keys only under `ngDevMode` and reports NG0955 with `console.warn` (`packages/core/src/render3/list_reconciliation.ts:116-129`, `:305-329` in Angular 21). It still reconciles all input items. Collisions can cause unstable DOM identity and extra reconciliation work, but they do not themselves insert duplicate data or throw the duplicate-key diagnostic.
5. **Both answers simplify invocation telemetry too much.** `SkillInvocationTracker` indeed has no production caller and is the only path here that increments candidate success then invokes promotion (`libs/backend/skill-synthesis/src/lib/skill-invocation-tracker.ts:59-84`). However, production hooks do capture real Skill/Task/prompt-expansion use (`libs/backend/skill-synthesis/src/lib/triggers/skill-trigger.service.ts:514-543`, `:611-623`) through a separate recorder (`libs/backend/skill-synthesis/src/lib/triggers/skill-trigger.service.ts:673-683`). The defect is not “no real telemetry”; it is that real slug-based telemetry is disconnected from candidate counters and promotion while fake creation rows occupy `skill_invocations`.
6. **Answer B's “drop or force-process” stale-row rule is unsafe and unverifiable.** A stalled curator intentionally leaves rows unprocessed for retry (`libs/backend/memory-curator/src/lib/triggers/memory-trigger.service.ts:773-787`, `:821-832`); setting `processed_at` without a successful pass would falsely report consumption. Conversely, keeping them forever is impossible because the current purge excludes unprocessed rows (`libs/backend/memory-curator/src/lib/observation-queue.store.ts:151-157`, `:648-654`). Use an explicit terminal stale disposition, not fake success.
7. **Both answers put too much destructive work in a one-shot migration.** The repository already has a carefully bounded migration that deletes unprocessed observations older than 30 days because the JSONL conversation remains canonical (`libs/backend/persistence-sqlite/src/lib/migrations/0039_reap_orphaned_queue_rows.ts:24-35`, `:81-95`). Adding an unconditional full `VACUUM` to startup would make a 1.28 GB upgrade long and space-hungry. Run deletion in bounded maintenance, expose progress, then compact out of band or incrementally; the present cron vacuums only 100 pages (`libs/backend/thoth-runtime/src/lib/start-thoth-cron.ts:333-363`).
8. **My Round 1 attributed the visible repetition too confidently to the key collision and claimed duplicate event cards that are not present.** The proven defects are non-unique identity, oldest-first slicing, `events[0]` treated as newest, and overlapping status summaries. A repeated-looking data stream may also contain genuinely repeated events. The UI must show an event ID, stage, attempt, and aggregation before declaring rows duplicates.

## Disputes 1–5

1. **`CandidateNamerService` is operationally dead.** Production code registers it as a singleton and token (`libs/backend/skill-synthesis/src/lib/di/register.ts:90-99`, `:193-198`) and exports it, but the only non-test `nameCandidate(` occurrence is its own declaration (`libs/backend/skill-synthesis/src/lib/naming/candidate-namer.service.ts:117-129`). Registration is not invocation. Therefore it does not fill live `display_name`; the column is written only if some caller invokes this method.
2. **`timestamp-kind` causes a duplicate-key warning, not duplicate rows or an Angular duplicate-key exception.** The collision is real in the template (`libs/frontend/skill-synthesis-ui/src/lib/components/diagnostics/event-feed.component.ts:26`). Angular 21 emits NG0955 via `console.warn` in development (`packages/core/src/render3/list_reconciliation.ts:305-329`); production does not perform that diagnostic. The reconciliation may associate DOM nodes ambiguously across updates, so replace the key with a durable backend `eventId`, but diagnose repeated content separately. Newest-first ordering must also be fixed (`libs/frontend/skill-synthesis-ui/src/lib/components/diagnostics/event-feed.component.ts:54-64`).
3. **Use a plain unused-for-N-days policy for retention; use an immutable base plus decaying terms only for ranking.** `base * recency` is better than the current positive-only accumulation, but by itself it lets time erase intrinsic importance and does not solve lifetime hit/tier floors. Delete the persisted-composite feedback path (`libs/backend/memory-curator/src/lib/salience-scorer.ts:44-71`) and the `< 0.1` deletion surrogate. Keep immutable `base_importance`; calculate a query-time rank such as `base_importance * recency + decayed_recent_use`, with pinning as a policy flag. Separately demote/delete by `last_used_at`, hit state, tier, pin, and explicit workspace caps. `last_used_at` is updated on a real returned search hit (`libs/backend/memory-curator/src/lib/memory-search.service.ts:341-361`), making the lifecycle rule explainable.
4. **Manual promote is truly blocked by `successCount`; the quality fix is archaeology-first plus cross-session clustering, with a separate manual bypass.** Manual Promote delegates directly to `evaluate` (`libs/backend/skill-synthesis/src/lib/skill-synthesis.service.ts:1208-1213`), and `evaluate` returns `below-threshold` when the count is under the effective threshold (`libs/backend/skill-synthesis/src/lib/skill-promotion.service.ts:209-216`). The creation-time direct store write does not increment that count (`libs/backend/skill-synthesis/src/lib/skill-synthesis.service.ts:916-923`), while the incrementing tracker is uncalled in production (`libs/backend/skill-synthesis/src/lib/skill-invocation-tracker.ts:59-84`). Implement distinct `promoteManually` and `evaluateAutomatic` paths: manual bypasses frequency only, retaining validation/dedup/security checks. For automatic recommendations, cheap stricter prefiltering reduces waste, but cannot establish reusability: run archaeology before drafting, reject degraded/no-routine verdicts instead of obeying “still produce” (`libs/backend/skill-synthesis/src/lib/skill-synthesizer.service.ts:230-243`), cluster evidence across sessions, then synthesize one candidate and test it on real use. Delete synthetic creation invocations and the current synthesize-before-archaeology edge (`libs/backend/skill-synthesis/src/lib/queue/stage-handlers.service.ts:266-286`).
5. **Retain processed observations for 7 days, not 14; reap the 5,106 stale unprocessed rows through the existing 30-day rule, never by marking them successful.** Processed observations are bulky staging telemetry, not the canonical conversation; the JSONL source remains intact (`libs/backend/persistence-sqlite/src/lib/migrations/0039_reap_orphaned_queue_rows.ts:24-30`). Seven days is already the repository's longest cited telemetry precedent (`libs/backend/persistence-sqlite/src/lib/migrations/0039_reap_orphaned_queue_rows.ts:59-69`) and halves steady-state queue storage versus fourteen. Add a daily, batched seven-day processed purge and a byte ceiling, with earlier payload scrubbing for large processed tool responses. The measured unprocessed cohort is over 30 days old, so first apply/verify migration 0039's exact predicate (`libs/backend/persistence-sqlite/src/lib/migrations/0039_reap_orphaned_queue_rows.ts:81-95`) after its validated pre-migration backup; then make the 30-day stale reap recurring and count it as `stale-orphaned`, not `processed`. Recent stalled rows remain retryable; add attempt/last-error visibility and alert at 48 hours.

## Revise?

Yes. I retain the core Round 1 diagnosis, but revise three claims: duplicate track keys warn and destabilize identity rather than crash or create data; the Activity page has overlapping summaries but only one actual event feed/histogram; and real skill invocation telemetry exists, though it is disconnected from candidate promotion. I also replace my proposed 48-hour quarantine of every unprocessed row with the repository's already-reasoned 30-day orphan reap plus a 48-hour alert/retry threshold.

Final prioritized fix plan:

1. **Stop storage growth first:** schedule bounded daily deletion of processed observations after seven days; apply/verify migration 0039 for the stale unprocessed cohort; make its 30-day stale-orphan policy recurring; cap queue bytes; rotate pre-migration snapshots from three to one (`libs/backend/persistence-sqlite/src/lib/backup.service.ts:105-110`); compact outside startup and expose rows/bytes/freed pages.
2. **Make memory lifecycle deterministic:** schedule the lifecycle job, add immutable base importance, remove recursive salience persistence, use unused-age/pin/tier/cap rules for demotion and deletion, and show per-rule countdowns and last-run results.
3. **Repair the skill evidence graph:** prefilter, archaeology, cross-session cluster, synthesize, validate/holdout, trial on real invocation, then automatic promotion. Delete forced one-off synthesis, creation-time fake invocations, and disconnected candidate-success accounting.
4. **Restore the user escape hatch:** add an explicit manual promotion path that bypasses only the frequency threshold; preserve schema, dedup, security, and write checks; show the exact gate evidence and decision.
5. **Rebuild Activity around one ordered source:** add durable event IDs and attempt IDs, sort newest-first, merge poll/live events by ID, aggregate repeated stage attempts, and put raw UUIDs/payloads behind details. Consolidate overlapping pipeline/diagnostics summaries without claiming nonexistent duplicate feeds.
6. **Make value visible:** default to Recommended, present readable synthesized titles and previews, show why each skill is pending/rejected/promoted, and add tests/metrics proving queue size falls, stale rows reach terminal disposition, memory cohorts age out, manual promotion works, automatic promotion requires real cross-session evidence, and same-millisecond events remain distinct.
