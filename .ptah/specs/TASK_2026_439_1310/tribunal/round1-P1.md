### A — Memory lifecycle / unbounded growth
## Position — the core thing that is wrong, 1–2 sentences
Thoth has lifecycle-shaped classes but no running retention lifecycle. Observations are marked processed rather than removed, memories feed their previous composite score back into the next decay calculation, expiry is opt-in but never assigned, and the only scheduled storage work is backup—not retention.

## Root causes — numbered; each with `file:line` evidence and which brief number it explains
1. Processed observations have a delete primitive, but no production caller. `PURGE_SQL` deletes only old processed rows and `purgeOlderThan()` exposes it (`libs/backend/memory-curator/src/lib/observation-queue.store.ts:155`, `libs/backend/memory-curator/src/lib/observation-queue.store.ts:648`); repository search finds its only call in its unit spec. Normal drain merely stamps `processed_at` (`libs/backend/memory-curator/src/lib/observation-queue.store.ts:569`). This directly explains brief #1 and the 200,725 processed rows retaining 756 MB of tool responses.
2. Decay cannot decay the stored population. The scorer uses the already-composite `memory.salience` as the next run's `base` (`libs/backend/memory-curator/src/lib/salience-scorer.ts:55`), then adds only non-negative recency/hit/tier terms (`libs/backend/memory-curator/src/lib/salience-scorer.ts:44`). New rows are already stored with a composite score (`libs/backend/memory-curator/src/lib/memory-curator.service.ts:675`, `libs/backend/memory-curator/src/lib/memory-curator.service.ts:679`), so repeated sweeps ratchet or preserve score instead of decaying a stable intrinsic score. Yet archival requires `< 0.1` (`libs/backend/memory-curator/src/lib/memory-decay.job.ts:91`). This explains brief #1's 0 archival rows and 1.1–1.4 score floor.
3. Nothing schedules the decay job. DI registers `MemoryDecayJob` (`libs/backend/memory-curator/src/lib/di/register.ts:129`), but Thoth cron registers daily backup and the three skill drains (`libs/backend/thoth-runtime/src/lib/start-thoth-cron.ts:373`, `libs/backend/thoth-runtime/src/lib/start-thoth-cron.ts:392`), not `memory:decay`. Expiration would delete rows, but inserts default `expires_at` to null (`libs/backend/memory-curator/src/lib/memory.store.ts:198`) and the decay job only deletes explicitly expired rows (`libs/backend/memory-curator/src/lib/memory-decay.job.ts:72`). This explains brief #1's absent decay/retention job and zero expiry values.
4. Even a running decay sweep never deletes archival or unused memories; it only changes recall to archival (`libs/backend/memory-curator/src/lib/memory-decay.job.ts:91`) and deletes explicit expiry (`libs/backend/memory-curator/src/lib/memory-decay.job.ts:72`). Thus it is tier maintenance, not retention. This explains brief #1's permanent growth and 88% zero-hit corpus.
5. Backup retention multiplies the oversized source. Pre-migration retention deliberately keeps three full copies (`libs/backend/persistence-sqlite/src/lib/backup.service.ts:105`, `libs/backend/persistence-sqlite/src/lib/migration-runner.ts:98`), while reset backups are defined as unbounded (`libs/backend/persistence-sqlite/src/lib/backup.service.ts:105`, `libs/backend/persistence-sqlite/src/lib/backup.service.ts:150`). Rotation is count-only, not age/byte-budget based (`libs/backend/persistence-sqlite/src/lib/backup.service.ts:443`). This explains the backup portion of brief #1.

## Systematic fix — the design you recommend (lifecycle/retention rules, pipeline changes, UI information architecture), concrete enough to plan from; name what to delete, not only what to add
Create one idempotent `MemoryRetentionService`, invoked by a named daily cron handler and manually from Maintenance. In one bounded transaction per batch it should: (1) delete processed observations after 7 days, with a shorter 24-hour retention for large `tool_response_text`; (2) quarantine unprocessed observations older than 48 hours into a small failure ledger, then delete their large payload after preserving session/kind/error metadata; (3) recompute salience from an immutable `base_salience`, age, and real hits—not the last composite score; (4) demote unpinned zero-hit recall after 14 days, delete archival after 30 days, and enforce per-workspace count/byte caps; (5) preserve pinned core indefinitely; and (6) run incremental vacuum proportional to freed pages after deletion.

Add explicit retention settings with safe defaults and dry-run counts. Migrate existing rows by deriving/clamping `base_salience`, then run a resumable, batch-limited cleanup so the first launch does not lock a 1.28 GB DB. Replace count-only backup retention with both count and total-byte/age limits: keep one pre-migration snapshot until the next validated daily backup, retain daily backups by age plus budget, and cap reset/dev artifacts unless explicitly pinned.

Delete `ObservationQueueStore.purgeOlderThan()` as an orphan public operation after moving its SQL behind the retention service. Delete recursive salience feedback in `scoreMemory`. Delete the current “archival is terminal forever” behavior. Delete the `reset: 0 = unlimited` default and automatic preservation of three giant pre-migration copies.

## Verification — how the user will be able to SEE it works (metrics, UI signal, test)
Maintenance must show DB bytes; observation rows/bytes split into pending, processed-retained, and reclaimable; oldest pending age; memory counts by lifecycle state; zero-hit count; last retention result; next run; and estimated/reclaimed bytes. A “Preview cleanup” action must list counts and bytes before a destructive run.

Automated proof: fake-clock lifecycle tests for every boundary and pinned exemptions; an integration fixture with processed payloads, stuck rows, memories/chunks/FTS/vec rows, and backups; two consecutive retention runs proving idempotence; foreign-index coherence checks; and a file-size test proving `VACUUM`/incremental vacuum actually returns pages. Release acceptance should show processed-observation bytes plateauing, oldest pending age below 48 hours, archival/deletion throughput, and 7/30-day DB growth trends.

## Tradeoffs
Short retention reduces forensic depth, and vacuuming/large deletes add I/O. Batch limits, idle/power gates, a compact failure ledger, configurable windows, and a preview make that cost controlled; leaving raw tool outputs forever is not a defensible default.

## Confidence — high/medium/low + biggest risk
High. The dead purge path, unscheduled job, recursive score, and non-deleting archival policy are explicit. Biggest risk: old unprocessed rows may represent recoverable work, so the first cleanup must quarantine metadata and ship as dry-run before payload deletion.

### B — Skill synthesis quality and verifiability
## Position — the core thing that is wrong, 1–2 sentences
The pipeline authors a per-session skill before it performs the evidence analysis intended to establish outcome and reusable routine. Its “invocation” and promotion model then records candidate creation as success while giving an unpublished candidate no credible route to accumulate the real successes promotion requires.

## Root causes — numbered; each with `file:line` evidence and which brief number it explains
1. Stage order is backwards. The `prefilter` handler calls `analyzeSession`, which synthesizes and registers the candidate, and only after success enqueues archaeology and gates (`libs/backend/skill-synthesis/src/lib/queue/stage-handlers.service.ts:266`, `libs/backend/skill-synthesis/src/lib/queue/stage-handlers.service.ts:285`). `analyzeSession` asks the synthesizer for the verdict at candidate-authoring time (`libs/backend/skill-synthesis/src/lib/skill-synthesis.service.ts:781`), but that verdict normally cannot exist yet. The synthesizer therefore falls back to raw trajectory text (`libs/backend/skill-synthesis/src/lib/skill-synthesizer.service.ts:257`). This explains brief #2's session-based output and mostly empty `routine`.
2. Candidate identity is deliberately derived from the first user turn (`libs/backend/skill-synthesis/src/lib/trajectory-extractor.ts:230`), and failed/unavailable synthesis falls back to that same slug and description (`libs/backend/skill-synthesis/src/lib/skill-synthesizer.service.ts:311`). Boot work explicitly skips LLM synthesis and emits the template path (`libs/backend/skill-synthesis/src/lib/skill-synthesis.service.ts:776`), whose body embeds a normalized transcript and asks the user to make it reusable (`libs/backend/skill-synthesis/src/lib/skill-synthesis.service.ts:1400`). This explains brief #2's complaint-name slugs and poor drafts.
3. The prefilter accepts a session when *any* edit, tool-count, test, or conversation-depth signal passes (`libs/backend/skill-synthesis/src/lib/skill-synthesis.service.ts:1188`). It does not require a verified successful outcome or a cited reusable routine. Worse, the synthesis prompt says that even a one-off or incoherent workflow must still produce a generalization (`libs/backend/skill-synthesis/src/lib/skill-synthesizer.service.ts:243`). This explains brief #2's non-code and tribunal/resume candidates.
4. Candidate creation writes a successful invocation immediately (`libs/backend/skill-synthesis/src/lib/skill-synthesis.service.ts:916`) even though the skill did not run. Real telemetry has a separate capture path keyed to actual Skill/Task/prompt-expansion events (`libs/backend/skill-synthesis/src/lib/triggers/skill-trigger.service.ts:514`, `libs/backend/skill-synthesis/src/lib/triggers/skill-trigger.service.ts:611`). This explains brief #2's one-success-per-candidate illusion.
5. Automatic promotion is structurally disconnected. Promotion requires `success_count >= 3` by default (`libs/backend/skill-synthesis/src/lib/skill-promotion.service.ts:4`, `libs/backend/skill-synthesis/src/lib/skill-promotion.service.ts:209`), while the creation-time direct `recordInvocation` does not call the tracker that increments success and triggers evaluation; that logic lives in `SkillInvocationTracker.recordInvocation()` (`libs/backend/skill-synthesis/src/lib/skill-invocation-tracker.ts:59`, `libs/backend/skill-synthesis/src/lib/skill-invocation-tracker.ts:66`). The repository has no production caller of that tracker. This explains brief #2's 0 promoted out of 2,432 candidates.
6. The advertised empirical replay gate is not in the normal pipeline: `enqueueCandidateGates` enqueues judge and trigger evaluation only (`libs/backend/skill-synthesis/src/lib/queue/stage-handlers.service.ts:415`), and the replay handler documents that nothing produces replay rows (`libs/backend/skill-synthesis/src/lib/queue/stage-handlers.service.ts:549`). Promotion also explicitly permits never-measured replay (`libs/backend/skill-synthesis/src/lib/skill-promotion.service.ts:368`). This explains why brief #2's user cannot verify transfer beyond judge opinion and self-generated retrieval prompts.

## Systematic fix — the design you recommend (lifecycle/retention rules, pipeline changes, UI information architecture), concrete enough to plan from; name what to delete, not only what to add
Replace the per-session candidate factory with an evidence-first funnel:

1. Capture cheaply, then scope to coding work and the owning workspace.
2. Run archaeology before authoring. Require a non-degraded verdict, a cited `routine`, and acceptable evidence (`tests-green`, explicit confirmation, or a separately verified artifact). “No routine” is a terminal, visible rejection—not a synthesis prompt.
3. Cluster routines across at least two independent sessions/contexts before authoring by default. Synthesize from the common cited steps, not raw transcript prose. Permit a one-session draft only as an explicitly labeled manual experiment.
4. Validate the draft against held-out transcripts/tasks and execute deterministic checks where possible. Judge and trigger retrieval are supporting signals; replay/behavioral evidence is the promotion gate.
5. Publish accepted drafts as probationary skills so they can be invoked, then record real invocation outcomes with source, session, task, and verification evidence. Promote to resident only after real cross-context wins; expire/reject stale experiments.

Delete the creation-time invocation write at `skill-synthesis.service.ts:916`. Delete automatic template candidates and the instruction to fabricate a skill from one-offs. Delete first-prompt slug/description fallback from the automatic path. Delete judge-only promotion when replay is null. Collapse or retire the legacy `SkillInvocationTracker` unless the real event recorder is made the single authoritative counter and promotion trigger.

## Verification — how the user will be able to SEE it works (metrics, UI signal, test)
Every suggested skill needs an evidence card: generalized title, trigger, source project count, independent session count, cited routine steps linking to sanitized transcript turns, outcome evidence, hold-out/replay result, judge score, retrieval precision/recall, real invocation wins/losses, and the exact reason it is pending/rejected/promoted. Show a funnel with absolute counts and oldest age: captured → eligible → archaeologized → routine found → clustered → drafted → replayed → probationary → promoted.

Tests must prove stage dependency (`archaeology done` before synthesis), reject one-off/non-code/degraded/no-routine sessions, prevent synthetic invocations, enqueue replay with a genuine hold-out, and promote only after real recorded outcomes across contexts. A golden corpus of known reusable and non-reusable sessions should report precision/recall and regression diffs for generated `SKILL.md` files. A canary skill with a known trigger and task should demonstrate an actual invocation and verified result in the UI.

## Tradeoffs
Evidence-first synthesis yields far fewer skills and takes longer; that is desirable because the scarce product is trustworthy reusable procedure, not candidate volume. Held-out replay costs compute and some valuable one-off workflows will need manual override.

## Confidence — high/medium/low + biggest risk
High. The stage ordering and synthetic invocation are direct code paths. Biggest risk: transcript evidence alone may still misclassify success, so executable task-level replay needs a safe sandbox and cannot be faked with another LLM score.

### C — Thoth UI usability and broken/repeating activity log
## Position — the core thing that is wrong, 1–2 sentences
The UI exposes subsystem internals as a nested control console instead of answering “Is Thoth healthy, what did it do for me, and what needs my decision?” The Skills activity feed also violates its own event ordering and row-identity assumptions, while the page repeats the same status information in multiple components.

## Root causes — numbered; each with `file:line` evidence and which brief number it explains
1. The shell describes itself only as “Agentic platform” and presents four implementation pillars with counts (`libs/frontend/thoth-shell/src/lib/components/thoth-shell.component.ts:83`, `libs/frontend/thoth-shell/src/lib/components/thoth-shell.component.ts:131`). Memory then adds five more peer views (`libs/frontend/memory-curator-ui/src/lib/components/memory-curator-tab.component.ts:301`) and Skills adds five (`libs/frontend/skill-synthesis-ui/src/lib/components/skill-synthesis-tab.component.ts:881`). This explains brief #3's unclear value and navigation overload.
2. Critical operational truth is hidden. Memory health counts memories/chunks/vector indexes but not DB bytes, observation-queue bytes, processed backlog, stuck age, retention policy, or next cleanup (`libs/backend/memory-curator/src/lib/diagnostics.service.ts:62`). The visible stats likewise show only tier counts, code index, and last curated (`libs/frontend/memory-curator-ui/src/lib/components/memory-stats-strip.component.ts:25`). This explains why brief #1 is invisible in the UI and contributes to brief #3.
3. Skills “Activity” repeats itself. The top pipeline card already renders last analysis and accepted/ineligible counts (`libs/frontend/skill-synthesis-ui/src/lib/components/skill-pipeline-status.component.ts:125`); the diagnostics component immediately renders last analysis, the eligibility histogram, candidate counts, and events again (`libs/frontend/skill-synthesis-ui/src/lib/components/diagnostics/skill-diagnostics-accordion.component.ts:28`). Both are mounted together (`libs/frontend/skill-synthesis-ui/src/lib/components/skill-synthesis-tab.component.ts:476`). This explains brief #3's repeating-components layout.
4. The skill event list is oldest-first while labeling it “Recent.” Backend `recentEvents()` takes the tail but preserves chronological order (`libs/backend/skill-synthesis/src/lib/skill-synthesis.service.ts:1052`), live state also appends in chronological order (`libs/frontend/skill-synthesis-ui/src/lib/services/skill-diagnostics-state.service.ts:163`), and the component renders `events.slice(0, limit)` without sorting (`libs/frontend/skill-synthesis-ui/src/lib/components/diagnostics/event-feed.component.ts:54`). The pipeline card compounds this by treating `events[0]` as latest (`libs/frontend/skill-synthesis-ui/src/lib/components/skill-pipeline-status.component.ts:316`). This directly explains brief #3's broken activity log.
5. Event row identity is not unique: Angular tracks only `timestamp + kind` (`libs/frontend/skill-synthesis-ui/src/lib/components/diagnostics/event-feed.component.ts:26`). Two events of one kind in the same millisecond collide, allowing DOM reuse/repetition artifacts. The memory feed avoids the collision only by adding the render index (`libs/frontend/memory-curator-ui/src/lib/components/diagnostics/event-feed.component.ts:72`), which is stable neither across reordering nor refresh. This explains brief #3's repeated/badly rendered rows.
6. The UI treats developer knobs as primary work. Memory Maintenance exposes ten trigger toggles plus provider selection before the recent events and health panel (`libs/frontend/memory-curator-ui/src/lib/components/diagnostics/memory-diagnostics-accordion.component.ts:67`, `libs/frontend/memory-curator-ui/src/lib/components/diagnostics/memory-diagnostics-accordion.component.ts:161`); Skills Activity similarly mixes pipeline, digest, diagnostics, trigger toggles, and spec maintenance (`libs/frontend/skill-synthesis-ui/src/lib/components/skill-synthesis-tab.component.ts:476`). This explains brief #3's inability to find a useful next action.

## Systematic fix — the design you recommend (lifecycle/retention rules, pipeline changes, UI information architecture), concrete enough to plan from; name what to delete, not only what to add
Make Thoth open on one outcome-oriented Overview with three sections: Health, Recent outcomes, and Needs your attention. Health shows storage/retention, synthesis backlog/funnel, schedule failures, and gateway connectivity with a plain-language status and one repair action. Recent outcomes is one durable, newest-first, cross-subsystem activity stream with filters and drill-down. Needs attention contains only actionable items: reclaimable storage, stuck observations, candidate reviews, failed jobs, and gateway approvals.

Keep Memory, Skills, Schedules, and Messaging as task pages, but give each a single primary job: search/manage learned knowledge; review verified skill suggestions and their evidence; manage schedules; connect/approve messaging. Move triggers, model lanes, raw queue rows, cost ledgers, DB coherence, and destructive tools under one Advanced/Diagnostics drawer. Add onboarding empty states that say what data will appear, when it appears, and the first safe action.

Define a persisted activity-event contract with a ULID `eventId`, subsystem, event type, severity, occurred-at, workspace, entity link, outcome, and dedup key. Query it newest-first with cursor pagination; merge live events by `eventId`; never synthesize DOM identity from time/kind or array index.

Delete the second Skills diagnostics summary from the Activity page; merge its unique controls under Advanced. Delete duplicate “last analysis,” histogram, candidate-count, and event cards. Delete raw session UUIDs and `key=value` dumps from the default feed; retain them in detail. Delete the separate in-memory-only Memory and Skills event histories once the durable unified ledger is live.

## Verification — how the user will be able to SEE it works (metrics, UI signal, test)
The first screen must answer, without opening a subtab: current storage and reclaimable bytes, whether retention ran, whether skill learning is progressing, the oldest queued work, failed schedules, connected messaging platforms, and the next recommended action. Each activity row links to the affected memory/skill/job/gateway item and displays a human outcome.

Component tests must feed same-kind/same-millisecond events and prove one row per `eventId`, newest-first order, stable rows after poll/live merge, cursor pagination, and no duplicate summaries. Playwright should cover empty, healthy, backlog, degraded, narrow-sidebar, and 200-event states with screenshot/keyboard assertions. A usability acceptance test should ask a new user to reclaim memory, explain why a skill is pending, and find a failed drain without documentation.

## Tradeoffs
A unified overview and durable ledger add schema/RPC work and deliberately hide some power-user detail. Advanced remains available, while defaults become legible; event retention itself must be bounded so the observability fix does not create another unbounded table.

## Confidence — high/medium/low + biggest risk
High for the ordering, identity, duplication, and missing-health findings; medium for the precise final navigation without user testing. Biggest risk: merging four domains into one feed can become noisy unless severity, deduplication, retention, and “needs attention” rules are strict.

## Priority order
1. Stop disk growth immediately: schedule processed-observation cleanup, quarantine stale pending payloads, cap backups, and expose preview/reclaimed-byte metrics.
2. Correct memory semantics: immutable base salience, real decay, archival deletion, expiry/count/byte caps, and bounded vacuum.
3. Stop manufacturing misleading skills and telemetry: remove template auto-candidates and creation-time success rows.
4. Reorder synthesis to archaeology → cited routine/evidence → cross-session cluster → draft → hold-out replay → probationary real use → promotion.
5. Fix Skills activity correctness now: newest-first ordering and real event IDs; remove duplicated panels.
6. Rebuild Thoth around Overview / Needs attention / task pages, with diagnostics moved under Advanced and end-to-end usability tests.
