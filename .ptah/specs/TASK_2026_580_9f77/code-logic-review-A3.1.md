## Five logic questions

1. **Silent failure?** The only deliberate ones are the plan's: unknown enum values read as defaults with one log line, and captures while closed throw out of the `db` getter for the A3.2 service to catch (the store does not swallow). A failed statement inside a transaction rolls back and propagates — nothing here converts an error into a success-looking result.
2. **Unexpected user action?** Re-linking the same task with identical values still bumps `updated_at` (via `ensureOrganization`), which can reorder a `lastActive`-sorted list on a no-op write. Cosmetic; see finding 6.
3. **Wrong-answer input?** The store trusts its typed inputs (documented at :21-24); the service (A3.2) owns vocabulary and URL validation, which is the plan's split. A `pinned` value other than 0/1 would read as `false` (:778), but the store is the only writer and always binds 0/1.
4. **Dependency failure?** A closed connection throws from the `db` getter before any statement runs; a mid-transaction failure rolls back the whole write (`deleteSession`'s rollback is proven by a forced failure); the conflict log line is emitted only after commit (:690), so it never reports a rolled-back rekey.
5. **Missing from the requirements?** Rollback coverage exists only for `deleteSession`; the other multi-statement transactions are untested under failure (finding 1). Nothing else in the plan's Component-4 store contract is absent.

## Findings

1. **Minor — no forced-failure rollback test for `linkTask`, `addPrLink` or `rekeySession`.** Evidence: the only trigger-based rollback test covers `deleteSession` (`session-organization.store.spec.ts:733-746`); the demotion+upsert pair (`session-organization.store.ts:752-759`) and the all-workspaces rekey (:678-689) rest on `db.transaction` with no test proving partial failure leaves the previous state intact — for rekey, a failure in the second workspace must also undo the first. Fix: copy the trigger pattern from the `deleteSession` test onto `rekeySession` (fail on the second workspace, assert the first workspace's rows are back under `oldId`), and onto `linkTask` (fail inside the upsert, assert the old primary kept `role = 'primary'`).
2. **Minor — `listWorkspace` returns the organization rows in storage order.** Evidence: `SQL.selectOrganizations` (`session-organization.store.ts:199-203`) has no `ORDER BY`, so the `Map` insertion order (:445-449) follows SQLite's unspecified scan order. `listTaskLinks` and `selectPrLinks` do order their rows (:208, :219). Fix: add `ORDER BY session_id` — free on the `(workspace_root, session_id)` primary key.
3. **Minor — rekey conflict can silently downgrade a primary to `related` when both ids link the same task.** Evidence: when `oldId` links task T as `primary` and `newId` already links T as `related`, `demoteMovingPrimary` (:297-303) does nothing (no primary under `newId`), `moveTaskLinks` (:304-309) excludes T because it is already under `newId`, and `deleteAllTaskLinks` (:318) deletes the old primary row — the surviving link keeps role `related`. This follows the plan's literal rule (:442-446, "links whose task_id is not already under newId"), and the session ends with no primary. Fix (optional, needs a plan call): when the dropped old link was `primary` and `newId` has no primary, promote `newId`'s row instead of deleting; at minimum add a spec case pinning today's behaviour.
4. **Nit — a known PR field can never be cleared back to null.** Evidence: `upsertPrLink` COALESCE (:256-263) keeps the previous value whenever the new one is null. This matches the plan ("refreshes when known") and is documented (:548-551); a caller that must clear a stale `state` has to delete and re-add the link. No store change needed; A3.2 should document it at the service boundary.
5. **Nit — the conflict path drops the old organization row's worktree/branch/lineage columns.** Evidence: `session-organization.store.ts:710-711` deletes the `oldId` organization row whenever `newId` has one. This is the plan's stated rule (:442-446), and the rebind scenario makes a genuine collision rare, but the loss is only visible in the single aggregated log line (:690-696). Acceptable; noting as residual risk.
6. **Nit — a no-change re-link still bumps `updated_at`.** Evidence: `writeTaskLink` runs `ensureOrganization` (:751) before every upsert, so re-linking the same task with the same role and source moves `updated_at` to `now`, which can reorder a `lastActive` sort without any content change. Sensible as "last organized change"; no fix requested.
