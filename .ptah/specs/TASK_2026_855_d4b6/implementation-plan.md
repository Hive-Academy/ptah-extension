## Architecture decision

- **Chosen approach — Proposed:** replace singular `pluginConfigRoot` with optional internal `pluginConfigAncestorRoots: readonly string[]`, nearest ancestor first. Carry the same shape in runtime session configuration and the existing `SessionMetadata` record. It contains only root identities, never copied/effective policy values. A child B of A receives `[A, ...A.ancestors]`; R → A → B therefore yields B local > A > R > global > defaults, including after all runtime objects are destroyed.
- **Rationale:** the existing source session ID and metadata owner provide the association and durability boundaries. Embedding a short ordered root list avoids session-parent traversals, dependence on ancestor records remaining undeleted, and a new policy registry. It preserves live ancestor settings without treating descriptive organization links as authority.
- **Rejected alternatives:** reconstructing one parent from workspaceId/cwd loses R; a flattened config snapshot becomes stale and loses override provenance; persisting only parent session IDs requires recursive cross-record lookup and ancestor retention on every restore; organization rows are descriptive and user-editable; lexical/git worktree inference does not prove policy authority; redirecting resolve(cwd) widens execution/MCP trust; a new registry duplicates metadata ownership.
- **Effect on existing code:** narrow optional metadata/type/forwarding changes, loader multi-layer reads and fingerprint extension, explicit session-root validation, plus execution-folder correction. Raw plugin homes, local save APIs, permissions, credentials, organization capture and UI remain unchanged. No new agent override API.
- **Assumptions:** intermediate lifecycle/adapter config constructors, fork/handoff copies, storage projections and tests may enumerate fields. Confirm these edges before source edits; forward/preserve the optional field rather than creating another owner. The exact existing adapter/lifecycle test filenames must be confirmed before implementation; test destinations below that are new are explicitly marked CREATE.

## Decisions

1. **Transitive durable ancestry:** chosen nearest-first root list in existing metadata; alternative parent-ID graph rejected for lookup/lifetime cost. Evidence: nested root narrowing and metadata serialization above. Reversible shape addition, but rollback to older code stops transitive inheritance; it is not policy-equivalent rollback.
2. **Plugin/skill-only inheritance:** local explicit plugin/skill value > nearest explicit ancestor > farther explicit ancestors > global > source defaults. Missing ID means inherit; contradictory lists within one layer mean off. `disabledAgentIds` comes only from the local config. No parent agent enable API is invented. Evidence: explicit maps and local save lists above. Reversible without settings conversion.
3. **Live reads, stable lineage:** roots are captured for a session; values are read afresh at each query construction. Existing persistent queries are not hot-patched. Ancestor changes affect descendants at next query recreation; session deletion does not erase a descendant's saved root list. Ancestry itself is not recomputed from current UI or organization state.
4. **Fail closed at trust boundaries:** every governing root is authorized, safety-checked and availability-checked at launch and every restore before reading its policy. A valid worktree does not authorize an invalid ancestor. Existing checks are extended explicitly. No automatic enrollment of independent worktrees.
5. **Distinct saved cwd is mandatory:** missing/unsafe/unauthorized/unreadable distinct saved cwd produces `SESSION_FOLDER_UNAVAILABLE`, never parent fallback. Legacy records without a distinct cwd retain workspace identity as execution candidate. This deliberately corrects previously tested behavior.

## Integration architecture

- Data flow: host-authenticated source ID → source durable/live lineage → child candidate `[parent cwd, ...ancestors]` → full execution/config-root validation → runtime config → capability resolver's plugin-only context → strict local/ancestor/global snapshot → worktree harness sync and SDK options from that same snapshot → SDK init persists lineage via existing metadata create/bind before ID-resolution consumers. Restore loads saved lineage (or explicit legacy recovery), validates every root again, and follows the same policy path.
- State/persistence: raw plugin homes own choices; session metadata owns lineage and cwd; global policy store owns global choices/MCP items; organization owns descriptive annotations. Durable root list is a binding, not proof of current authorization. Validation must run again after restart.
- External boundaries: prompt/frontend/MCP arguments cannot supply an arbitrary ancestor list. Validate durable metadata as untrusted persisted input too. Execution root, MCP trust/import/approval identity and plugin file lookup never become ancestor roots. Parent config read does not install parent hooks or expose credentials.
- Failure/rollback: root validation refuses execution; strict read failures retain restrictive policy-unknown behavior. Child provision rollback remains existing spawner behavior. Optional metadata field requires no bulk migration, but older code ignores it and cannot preserve nested policy semantics; rollback must acknowledge that functional limitation, not claim equivalent policy.
- Observability: existing RPC refusal/log and capability policy-unknown reason paths record root role and rejected identity. Include ordered governing roots/fingerprint in existing bounded diagnostic context, not prompts, credentials or settings dumps. Legacy recovery logs only that further ancestry is unavailable.
- Association audit disposition: preserve earlier review's scope. Existing child organization capture, worktree open/copy and git-stats behavior are not scheduled for replacement. Distinct-cwd fallback is the verified association/execution defect. Historical-tab hydration and generic tool-created worktree enrollment remain unproven audit leads, not UI repairs or policy authority. TASK_2026_386 backlog workflows remain excluded.

## Architecture-level quality requirements

- Functional: R → A → B inheritance survives restart; B local explicit choice wins, then A, then R, then global/default. Root toggles change next reconstructed query's policy and fingerprint. Disabled plugins still gate their skills; child skill ON alone does not bypass a disabled provider plugin. Local-only agent disables remain unchanged.
- Security: validate every governing config root at launch/restore, including local stateRoot mappings; refuse removed/unregistered/unsafe/outside-symlink ancestors before policy read. Parent-only MCP declaration, approval, plugin file, hook, credential or permission cannot become available through the new context.
