# Code logic review — TASK_2026_660

## Verdict

**NEEDS_REVISION — 4/10.** The normal live-parent path now carries the parent's level into the SDK launch (`session-spawner.service.ts:310,408`; `chat-session.service.ts:657-676`), and the tests cover `yolo`, `auto-edit`, `ask`, and `plan` (`chat-session-agent-child.spec.ts:325-391`). Two paths can still change permissions on the wrong security principal. This is a 3–4 review rather than 5–6 because those paths can grant `yolo` without a verified parent choice; it is above 1–2 because the principal happy path is wired and tested.

## Findings

1. **Blocking — Unknown parent level can escalate a child to saved `yolo`.** `libs/backend/rpc-handlers/src/lib/chat/session/chat-session.service.ts:706-725` uses the global saved autopilot level when `params.permissionLevel` is absent. `libs/backend/cli-agent-runtime/src/lib/session-children/session-spawner.service.ts:269-310` verifies that the caller is active but does not require `lifecycle.find(caller)` to return a level; the host adapter can also pass no level (`libs/backend/rpc-handlers/src/lib/chat/session/child-chat-session-host.adapter.ts:57-70`). If a live parent has no readable lifecycle record, or its record disappears between the two lookups, and saved config is `yolo`, the child runs at full bypass even though the parent's level is unknown. The new test explicitly pins this escalation (`chat-session-agent-child.spec.ts:363-370`). **Fix:** default an unknown parent level to `ask` (or refuse creation); never infer a parent's authority from global config. Test the missing-record case with saved `yolo`.

2. **Blocking — A sessionless tab can change another session's permissions.** `libs/frontend/chat/src/lib/components/molecules/chat-input/chat-input.component.ts:578-582` supplies `null` before the tab has an SDK session; the new popover forwards it on enable and disable (`libs/frontend/chat-ui/src/lib/molecules/chat-input/autopilot-popover.component.ts:237-245,260-264`). The backend treats `null` as absent and selects `getActiveSessionIds()[0]` (`libs/backend/rpc-handlers/src/lib/handlers/config-rpc.handlers.ts:369-380`). Thus enabling full autopilot from a fresh tab can set an unrelated parent or gateway session to `bypassPermissions`, while the UI operation appears successful. The new popover test accepts the null forwarding (`libs/frontend/chat-ui/src/lib/molecules/chat-input/autopilot-popover.component.spec.ts:59-66`). **Fix:** distinguish an explicit webview `null` from legacy CLI/TUI omission at the RPC boundary; save the default but do not mutate any live session when the originating tab has none. Add a test with two live sessions and a fresh tab.

3. **Serious — Existing tabs can display full autopilot while their live level remains lower.** The popover reads the root-wide `AutopilotStateService` signals (`libs/frontend/chat-ui/src/lib/molecules/chat-input/autopilot-popover.component.ts:191-219`; `libs/frontend/core/src/lib/services/autopilot-state.service.ts:72-92`), but the newly passed ID makes a toggle update only that tab's session (`autopilot-popover.component.ts:240-245`; `config-rpc.handlers.ts:370-380`). Toggle tab A to `yolo`, then view tab B, whose session was already `auto-edit`: B's popover shows the global `yolo`, while `ptah_session_start` from B reads B's live `auto-edit` (`session-spawner.service.ts:310`) and its child asks for permissions. The UI gives a success-looking account of the exact behavior this task is meant to fix. **Fix:** display each tab's effective live permission level and enabled state, with a separate default for fresh tabs; test toggling one tab and spawning from another.

## Five logic questions

1. **Silent success:** a sessionless tab's toggle reports success after changing another session (`config-rpc.handlers.ts:369-401`); a failed live sync is also logged and swallowed after config is saved (`:377-393`).
2. **Unexpected user action:** enabling full autopilot in a fresh tab can re-gate the most recently active session (`autopilot-popover.component.ts:240-245`; `config-rpc.handlers.ts:369-380`).
3. **Wrong answer from valid data:** a live caller with no readable lifecycle record and saved `yolo` produces a `yolo` child rather than a safe `ask` child (`session-spawner.service.ts:269-310`; `chat-session.service.ts:706-725`).
4. **Dependency failure or race:** if `setPermissionMode` rejects, the lifecycle record was already changed (`session-control.service.ts:503-521`) and the RPC handler suppresses the error (`config-rpc.handlers.ts:377-393`); a child can inherit that unconfirmed record level (`session-spawner.service.ts:310`). Parent changes after the synchronous guard read do not affect an already requested child (`session-spawner.service.ts:310,408`), matching the commit's capture-at-start test (`session-spawner.service.spec.ts:306-325`).
5. **Requirement gap:** the requested behavior specifies inheritance at launch but not whether a later parent-level change should propagate. Current child launch passes one level once (`chat-session.service.ts:657-676`), so it remains independent afterward. The handoff path named in `task.md` is absent from the changed implementation and cannot be verified from this commit.
