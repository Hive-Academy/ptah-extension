# Research Addendum — TASK_2026_575 (open questions Q1–Q4)

## Q1 — Does the main process's cumulative total_cost_usd / modelUsage already include subagent spend?

**Verdict: YES, for SDK-native Task-tool subagents. Defect 2's framing needs correction: the live header already carries subagent cost; only the `AGENTS` badge count is separate.**

Evidence:
- `node_modules/@anthropic-ai/claude-agent-sdk/sdk.d.ts:5373-5376` (`SDKResultSuccess.modelUsage`, v0.3.278): "Per-model totals for every model call made through the query pipeline during this query() call — **main loop, Task subagents, sidechains**, and internal calls such as compaction". `total_cost_usd` (`:5366-5368`) is defined as "covering the same query-pipeline calls as modelUsage" — same coverage.
- Contrast: `usage` (`:5369-5370`, the per-turn field) is explicitly "MAIN AGENT LOOP ONLY — excludes Task subagent, sidechain".
- `libs/backend/agent-sdk/src/lib/helpers/stream-transformer.ts:674-687,703-707` builds `runModels`/`totalCost` from `sdkMessage.modelUsage`/`total_cost_usd`, not `usage` — i.e. the live path already uses the subagent-inclusive fields.
- Confirmed these ARE SDK-native (in-process) Task subagents, not ptah-orchestrated separate `query()` calls: `subagent-hook-handler.ts:1-25` documents the SDK's own `SubagentStart`/`SubagentStop` hooks and `task_*` system-message stream, `parent_tool_use_id` correlation — the SDK subprocess itself runs the subagent and reports it back through the same result stream.
- Real transcript `C:\Users\abdal\.claude\projects\...\0b2799b9-...\` has a `subagents/agent-*.jsonl` with its own model (`gpt-5.6-sol`) distinct from the parent's (`sonnet`, `gpt-6-astra`); the parent transcript never persists `result`/`modelUsage` lines at all (0 matches for both strings) — SDK result messages are stream-only, never written to disk, which is why the DISK path (`aggregateLedgers`) cannot reuse `modelUsage` and instead sums raw per-message `usage` (confirmed per-call, non-cumulative: sample line shows `output_tokens:43`) from the parent transcript **plus** the subagent ledger separately (`session-usage-aggregator.ts:243-250`).

Consequence: the disk aggregator is not double-counting — it independently re-derives the same total from raw per-message records (parent-own usage, which is main-loop-only, plus subagent-own usage) rather than trusting the SDK's self-reported cumulative `modelUsage`. Both paths *should* converge on the same figure; `recordAgent()` (`session-stats-owner.service.ts:526-533`) only needs to keep counting distinct agent IDs for the badge — it correctly adds no cost, because `replaceRun` already received it via `modelUsage`. Defect 2's "header omits subagent spend" claim is not supported for SDK Task subagents; re-verify empirically (log `modelUsage` keys vs subagent model ids on a live run) before treating it as a live-side gap. The genuine gap is CLI lanes (Q2).

## Q2 — CLI lanes (ptah_agent_spawn: codex/opencode/antigravity/ptah-cli)

**Verdict: no cost/token/model is recorded or shown anywhere for CLI lanes today. Recommend: out of scope for this task, label explicitly.**

- `CliSessionReference` (`libs/shared/src/lib/types/agent-process.types.ts:375-395`) fields: `cliSessionId, cli, agentId, task, startedAt, status, stdout?, segments?, streamEvents?, ptahCliId?` — no usage/tokens/cost/model field exists.
- `cliAgentsFor()` (`session-rpc.handlers.ts:1013-1019`) reads `metadata.cliSessions[].cli` and returns only the **distinct CLI names** (e.g. `['codex']`) — a label list for the `cliAgents` badge, never a number.
- `libs/backend/cli-agent-runtime/src/lib/wiring/agent-events.ts` has no `usage`/`tokens`/`model` handling at all.
- Only `ptah-cli` (itself Claude-Agent-SDK-based) could plausibly report structured per-turn usage via its `streamEvents?: FlatStreamEventUnion[]`; codex/opencode/antigravity are external processes captured as raw `stdout`/`segments` with no guaranteed usage schema.
- Recommendation: do not fold CLI-lane spend into the header/analytics total in this task — no reliable, uniform price signal exists across lanes. If wanted later, scope it to `ptah-cli` only (parse `streamEvents` for cost, same pipeline `calculateMessageCost` uses) and show it as a **separate labeled figure**, never merged into `sessionStats.totalCost`, to avoid re-opening defect 3's "silent drop vs. silent merge" trap.

## Q3 — `[1m]` model ids: which rates apply?

**Verdict: real Anthropic tiering exists (input/output roughly doubles above 200K tokens); `pricing.utils.ts` has no tiered rate data and no `[1m]` stripping. Fix: reuse the existing normalizer, and treat rate lookup and tiering as two separate problems.**

- `pricing.utils.ts:266-302` (`lookupPricingEntry`) strips `provider/` prefix and matches a date-snapshot suffix only; it has no handling for a trailing `[..]` tag, so `"claude-opus-5-5[1m]"` matches nothing (`remainder = "[1m]"` fails `DATE_SNAPSHOT_SUFFIX`) → `null` → unpriced, confirming defect 4.
- A correct normalizer already exists, but is local/unexported: `stream-transformer.ts:82-89` (`normalizeModelKey`, added by 20a67d5e1) strips `(\[[^\]]*\])+$`, then provider prefix, then date suffix — exactly the transform `lookupPricingEntry` is missing. 20a67d5e1 only used it for matching `lastTurnContextTokens` tracking keys, not pricing.
- `getModelContextWindow` (`pricing.utils.ts:454-486`) already infers a 1M window for `opus ≥4.6` via a non-anchored regex that happens to match through a trailing `[1m]` tag, but this is a context-window heuristic, not a rate lookup — it does not touch `lookupPricingEntry`.
- Live confirmation (`ptah_web_search`, 2026): Anthropic's long-context tier is real — Opus 4.6 input/output roughly doubles for prompts >200K tokens ($5→$10 input, per anthropic.com/news/claude-opus-4-6, and per a forum report 1M context later went GA "at standard pricing" — i.e. the premium-tier rule has changed over time and is not fixed).
- Recommendation: (1) apply `normalizeModelKey`-equivalent stripping in `lookupPricingEntry` so a `[1m]` id at minimum resolves to the base model's published rate (fixes the "$0/unpriced" bug, defect 4's literal scope). (2) Separately flag as an **unknown**, not solved here: `calculateMessageCost` has no per-call token-count tiering at all (no >200K threshold anywhere in this file), so even a correctly-priced base rate will under-bill a long-context call today. Whether OpenRouter's live catalog publishes the `[1m]`/long-context variant as its own distinct priced SKU (in which case an exact match should be tried BEFORE stripping) was not verified against the live OpenRouter response in this pass — recommend checking `OpenRouterModel.id` values at runtime before deciding whether to strip-first or exact-first.

## Q4 — Per-turn cost delta: where to compute it, and reload/consumer impact

**Verdict: compute the delta inside `SessionStatsOwnerService.replaceRun`, alongside the existing accept/reject logic, and return it to the caller — reload already computes correct per-turn deltas independently, so only the live path needs the change. One frontend consumer (`agent-stats.service.ts`) currently sums the (currently cumulative) `cost` field and will be fixed, not broken, by the change; the header itself does not sum message cost.**

- `replaceRun` (`session-stats-owner.service.ts:459-499`) already tracks exactly what's needed: `run.current` (latest accepted cumulative `RunUsageResult`) and `run.base` (`resolveRunBase`/`subtractRunBase`, `:197-224`) for cross-process restarts. `applyResult(run, result)` decides accept/reject (non-monotonic, stale) BEFORE `run.current` is overwritten. The cleanest fix: capture `previous = run.current ?? run.base` before calling `applyResult`, and on `outcome === 'accepted'` return `delta = newTotalCost - (previous?.totalCost ?? 0)` alongside `outcome`/`snapshot`/`firstRejection`. This makes rejected results (non-monotonic, stale-owner) and the run-base restore case go through the identical accepted-delta path stream-transformer already branches on (`stream-transformer.ts:714-750`), instead of stream-transformer re-deriving `totalCost` itself at `:674-687` and publishing the raw cumulative value as `rawStats.cost` (`:772-774`).
- History reload does **not** need a matching fix: `session-replay.service.ts:233-282` recomputes `cost` per message from that message's own **raw, non-cumulative** `usage` tokens (`calculateMessageCost(priced.modelId, tokenUsage, ...)`), summing only the several raw API-call parts that belong to one logical turn (`:264-280`). Cost is never persisted as a stored field — it is always freshly computed at reload from per-call token counts, so reloaded messages already show correct per-turn (not cumulative) costs. Note: reload prices at the CURRENT rate card, not the rate in effect at turn time — an existing, separate limitation, out of scope here.
- Header total does not sum message cost: `session-stats-aggregator.service.ts:80` ("Session totals are never added up here (TASK_2026_533)") — it only installs the backend's `sessionStats` snapshot.
- Consumers of the per-message `cost` field in `libs/frontend`:
  - `chat-execution-tree/src/lib/agent-stats.service.ts:97-98,120` — **sums** `complete.cost` across a subagent's child `message_complete` events into `totalCost` for the per-agent badge. Today this is subtly wrong (summing cumulative numbers whenever an agent has >1 turn); becomes correct once `cost` is a true per-turn delta.
  - `chat-streaming/src/lib/message-finalization.service.ts:157-236` and `history-message-builder.service.ts:174-218` — pass `cost` straight through onto one message (display only, no aggregation).
  - `chat-execution-tree/src/lib/builders/message-node.fn.ts:52` — passes `completeEvent?.cost` onto a tree node (display only).
  - `chat-ui/.../cost-badge.component.ts`, `message-bubble.component.ts:157`, `compact-session-stats.component.ts` — render a single message's `cost` (display only).
  - None of these except `agent-stats.service.ts` perform arithmetic on `cost`, so switching semantics to a delta only requires auditing that one aggregator (verify it recomputes correctly once inputs are deltas — the `+=` already assumes additive/delta semantics, so no code change is likely needed there, only the input's meaning changes).
