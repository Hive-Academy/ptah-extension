# Requirements — TASK_2026_462_c819

## Summary

Enhance the admin Waitlist Pipeline at `/admin/waitlist` so administrators can distinguish lifecycle stages reliably, narrow the queue with combined filters, act on multiple eligible entries, and inspect a person's waitlist and account context without leaving the page.

Today the page maps New to `notified:false`, although approval deliberately does not update `notifiedAt`; an approved entry can therefore remain in New and still receive an Approve action (`libs/web/admin/src/lib/waitlist/waitlist-pipeline.ts:68-81`, `libs/web/admin/src/lib/waitlist/waitlist-pipeline.ts:155-169`, `libs/web/admin/src/lib/waitlist/waitlist-pipeline.html:144-168`). The header also derives New as total minus notified, which includes approved-but-never-notified entries (`libs/web/admin/src/lib/waitlist/waitlist-pipeline.ts:232-249`). The generic list API supports search and allowlisted sorting, but accepts only one `field:value` filter (`libs/api/admin/src/lib/admin.service.ts:429-518`); the waitlist UI does not expose search, source/date filters, sort controls, or page-size controls.

Classification: FEATURE. Estimated size: L, because the observable outcome spans an Angular admin workflow, validated NestJS query/detail contracts, cross-model detail aggregation, selection semantics across paginated results, export, audit behavior, and regression coverage. Priority is not defined by the request or repository task contract.

## In scope

### 1. Stage separation

- **R1.1 — Disjoint lifecycle stages.** The waitlist shall classify every entry into exactly one displayed stage using this precedence: Converted when `convertedAt` is present; otherwise Approved when `approvedAt` is present; otherwise Invited when `notifiedAt` is present; otherwise New. Stage tabs and their result totals shall use the same predicates.
- **R1.2 — Accurate pipeline summary.** The New, Invited, Approved, and Converted summary counts shall reflect the disjoint stage definitions in R1.1, so approved or converted entries are not counted as pending New entries.
- **R1.3 — Approval eligibility.** Approve controls and approval selection shall be available only for entries whose `approvedAt` and `convertedAt` are both absent. An already approved or converted entry shall never present an approval action, regardless of its historical `notifiedAt` value.
- **R1.4 — Visible differentiation.** Every listed entry shall show a clearly labelled lifecycle badge and the timestamp relevant to its current stage. Approved and converted entries shall remain visually distinguishable from actionable New or Invited entries in the All view and in search results.

### 2. Advanced filters

- **R2.1 — Combined filtering.** Administrators shall be able to combine stage, free-text search, source, signup-date range, and sort criteria with AND semantics, while free-text search continues to match the allowlisted email and source fields.
- **R2.2 — Filter controls.** The page shall expose controls for search, source, created-from date, created-to date, sort field, sort direction, and page size, plus a single action that clears all optional filters.
- **R2.3 — Allowlisted sort and pagination.** Administrators shall be able to sort by the existing waitlist sort fields (`createdAt`, `notifiedAt`, `approvedAt`, `convertedAt`, and `source`), choose an allowed page size, and move through server-paginated results without loading the entire result set into the browser.
- **R2.4 — Shareable filter state.** Active stage, search, source, date range, sort, direction, page, and page size shall be represented in the URL. Reload, deep-link navigation, and browser back/forward shall restore the same valid view; changing a narrowing criterion shall return to the first page.
- **R2.5 — Boundary validation.** Unsupported filter fields, stage values, sort fields, malformed dates, reversed date ranges, and invalid page parameters shall be rejected with a safe validation response and shall never become dynamic Prisma field names or predicates.

### 3. Bulk actions

- **R3.1 — Selection controls.** Eligible rows shall support individual selection, select/deselect current page, and clear selection. The interface shall show the selected count and whether selection covers only the current page or the matching result set.
- **R3.2 — Select matching.** Administrators shall be able to select eligible entries matching the current filters beyond the visible page. The default scope for approval shall be capped at 50 entries, consistent with the approval boundary; the interface shall disclose the cap and shall not silently omit entries.
- **R3.3 — Bulk approval.** A bulk approval shall use the existing confirmation flow, submit no more than 50 explicit waitlist IDs per request, and display the returned totals and per-entry outcomes for approved, already approved, already paid, not found, and failed entries.
- **R3.4 — CSV export.** Administrators shall be able to export all entries matching the active filters and sort, not only the visible page. The export shall include the waitlist identity, source, current stage, and lifecycle timestamps, and its headers and row order shall be deterministic.
- **R3.5 — Post-action state.** After a bulk approval response, the list and stage totals shall refresh. Entries that failed or were not processed shall remain identifiable for retry, while a transport failure shall preserve the selection. Successful entries shall no longer appear as approval-eligible.

### 4. Details drawer

- **R4.1 — In-context details.** Activating any waitlist row shall open the shared admin details drawer without discarding the current filters, page, or selection; closing it shall return focus to the triggering row control.
- **R4.2 — Waitlist identity and timeline.** The drawer shall show the waitlist ID, email, source, current stage, joined time, notified time, approved time, and converted time, using an explicit “not recorded” state for absent timestamps.
- **R4.3 — Linked account context.** The drawer shall show any user matched by normalized email and that user's relevant licenses, subscription state, and cohort/group memberships. Each missing relationship shall be shown as an explicit empty state rather than being treated as an error.
- **R4.4 — Audit history and contextual actions.** The drawer shall show relevant audit events in reverse chronological order, including actor, action, time, and safe metadata, and shall expose only actions valid for the entry's current state, including approval when eligible and navigation to the linked user/license when present.
- **R4.5 — Detail failure states.** While details load, the drawer shall expose a loading state; a missing entry, validation failure, or dependency failure shall show a non-sensitive error and a retry or close path without breaking the underlying list.

## Out of scope

- Reintroducing the retired paid invitation campaign or changing `notifiedAt` during approval — it remains a historical “invite sent” fact with a separate writer (`apps/ptah-license-server/prisma/schema.prisma:462-477`).
- Changing the complimentary Builders grant duration, founding-cohort assignment, welcome-email behavior, paid-entitlement guard, or per-entry transactional approval semantics — the task enhances administration of the existing approval workflow.
- Editing lifecycle timestamps from the details drawer — `approvedAt` is the approval idempotency claim and must not become a generic editable field (`libs/api/admin/src/lib/admin-models.config.ts:374-384`).
- General redesign of other admin record pages or expansion of advanced filtering to every admin model — shared infrastructure may be extended safely, but only waitlist behavior is required.
- Creating a new user, license, subscription, or cohort relationship from the details drawer outside the existing waitlist approval action.
- Bulk removal of waitlist entries unless the first Open Decision is explicitly accepted; the recommended baseline excludes it.

## Acceptance criteria

1. **AC-R1.1:** Given entries representing every combination of the three lifecycle timestamps, when the pipeline and each stage tab are queried, the system shall place each entry in exactly one stage using Converted → Approved → Invited → New precedence.
2. **AC-R1.2:** Given an approved entry with no `notifiedAt`, when summary counts load, the system shall count it as Approved and shall not count it as New or Invited.
3. **AC-R1.3:** Given an entry with `approvedAt` or `convertedAt`, when it is displayed in any tab or filtered result, the system shall expose neither its row checkbox as approval-eligible nor an Approve action.
4. **AC-R1.4:** Given mixed lifecycle entries in the All view, when the list renders, the system shall show an accessible stage label and the relevant lifecycle date for each entry, with approved and converted entries visually distinct from actionable entries.
5. **AC-R2.1:** Given stage, search, source, and date-range criteria together, when the administrator applies them, the system shall return only entries satisfying every criterion while matching search against email or source.
6. **AC-R2.2:** Given one or more active optional filters, when the administrator invokes Clear filters, the system shall remove search, source, and date criteria, restore the default sort/page size, and retain the selected stage unless the product decision explicitly labels stage as part of Clear all.
7. **AC-R2.3:** Given more matching entries than one page, when the administrator changes an allowlisted sort, direction, page size, or page, the system shall return the corresponding server-paginated slice and accurate total/page metadata.
8. **AC-R2.4:** Given a valid filtered URL, when it is opened directly or reached with browser back/forward, the system shall restore the represented view; when a narrowing criterion changes, the system shall request page 1.
9. **AC-R2.5:** Given an unsupported field/value, malformed date, reversed range, or invalid pagination value, when the request reaches the API, the system shall return a sanitized 400 response before issuing a query with user-controlled field names.
10. **AC-R3.1:** Given a page containing eligible and ineligible entries, when the administrator selects all on the page, the system shall select only eligible entries, announce the count, support deselect/clear, and preserve an unambiguous selection-scope label.
11. **AC-R3.2:** Given more than 50 eligible matches, when Select all matching is chosen for approval, the system shall select at most 50, disclose both the selected and total matching counts, and require no hidden truncation.
12. **AC-R3.3:** Given 1–50 selected eligible IDs, when bulk approval is confirmed, the system shall send explicit IDs through the existing approval path and render its aggregate and per-entry outcomes; given 0 or more than 50 IDs, it shall not submit the action.
13. **AC-R3.4:** Given filters whose matches span multiple pages, when CSV export completes, the system shall produce one deterministic row per matching entry with the defined identity, source, stage, and timestamp columns.
14. **AC-R3.5:** Given a mixed approval result, when the response is processed, the system shall refresh rows/counts, remove successful entries from approval eligibility, and keep failed/unprocessed entries identifiable; given a transport failure, it shall retain the prior selection.
15. **AC-R4.1:** Given a focused row-details trigger, when it is activated and then the drawer is closed by button, backdrop, or Escape, the system shall preserve the list state and return keyboard focus to that trigger.
16. **AC-R4.2:** Given an existing waitlist entry, when its details load, the system shall display its ID, email, source, derived stage, and all four lifecycle times, explicitly marking absent values.
17. **AC-R4.3:** Given entries with and without a normalized-email user match, when details load, the system shall show the matching user's relevant licenses, subscription, and cohorts or a separate explicit empty state for each absent relationship.
18. **AC-R4.4:** Given an entry with relevant audit records, when details load, the system shall show newest-first safe audit information and only state-valid actions; an ineligible entry shall not expose approval.
19. **AC-R4.5:** Given slow, missing, invalid, or failed detail retrieval, when the drawer is open, the system shall show the appropriate loading/not-found/error state with retry or close and shall leave the list usable.

## Non-functional constraints

- **Security and validation:** All waitlist list/detail endpoints remain behind `JwtAuthGuard` and `AdminGuard`. Every new `@Query()` or `@Body()` binding shall use the repository's explicit `dtoPipe(Dto)` rule; this is required because runtime DTO metadata is not inferred (`libs/api/admin/src/lib/admin-waitlist.controller.ts:25-48`). Filter and sort names, stage/source values, date operators, page sizes, export columns, and detail identifiers shall be allowlisted at the boundary. Client-provided strings shall not select Prisma fields or raw predicates. Error responses shall not expose raw dependency or database messages.
- **Approval bound and resilience:** A single approval request shall contain 1–50 explicit IDs, preserving `ApproveWaitlistDto`'s `@ArrayMaxSize(50)` limit (`libs/api/admin/src/lib/admin.dto.ts:130-161`) and the existing per-admin throttle. The UI shall interpret per-row outcomes rather than treating HTTP 200 as universal success (`libs/api/admin/src/lib/admin-waitlist.controller.ts:61-86`).
- **Auditability:** Every successful approval shall retain its transactional `waitlist.approve` audit record; an audit failure shall continue to roll back that row's grant (`libs/api/admin/src/lib/waitlist-approval/waitlist-approval.service.ts:347-370`). CSV export shall be attributable through existing request logging or a dedicated audit event if repository policy treats PII exports as auditable. Any future delete action shall require a dedicated audit action containing actor, target, and safe snapshot metadata.
- **Pagination and performance:** List filtering, sorting, counts, select-matching resolution, export, and detail aggregation shall remain server-bounded for the current roughly 400+ row dataset and shall not fetch all rows into the browser merely to filter, count, or select them. Normal list requests shall retain server pagination (current default 25, maximum 100) and the paired rows/count behavior (`libs/api/admin/src/lib/admin.service.ts:159-204`). Detail loading shall occur on demand and avoid per-list-row relationship queries.
- **Accessibility:** Row and page-selection checkboxes shall have unique accessible names, select-all shall expose checked/unchecked/mixed state, and changes to selection/result counts shall be available to assistive technology. The drawer shall preserve the shared dialog behavior (`role="dialog"`, modal labelling, initial focus, Escape close, and inert closed content) established in `libs/web/panel-ui/src/lib/detail-drawer/detail-drawer.ts:13-27` and `detail-drawer.html:24-72`, and shall return focus to its trigger. All controls shall be keyboard operable with visible focus, and stage differences shall not rely on color alone.
- **Framework and boundaries:** Angular changes shall remain standalone, signal-driven, zoneless-safe, and `OnPush`. NestJS controllers shall delegate to services and shall not inject Prisma directly. Web and API code shall share wire contracts only through an allowed contracts boundary when a shared type is needed; neither surface shall import product-incompatible backend/frontend libraries.

## Open Decisions

1. **Should “Remove entries” ship as a bulk action?** Recommended default: **No, exclude it from this task.** It is destructive, has undefined retention/recovery semantics, and can leave linked users, licenses, cohort assignments, and audit history without their originating waitlist row. If required, define soft-versus-hard deletion, eligible stages, confirmation text, audit payload, and recovery policy before implementation.
2. **Should “select all matching” be capped?** Recommended default: **Yes, cap approval selection at 50 eligible matches.** This matches the enforced request limit and keeps one confirmation mapped to one bounded approval wave. Show “50 selected of N matching”; allow page selection for smaller deliberate sets. Export remains independent of approval selection.
3. **Should CSV export be server-side or client-side?** Recommended default: **Server-side.** Export must cover all filtered matches across pages, apply the same authoritative stage/filter predicates, avoid loading 400+ records into browser state, and support formula-injection protection and auditability. Client-side export would otherwise be limited to already fetched rows or require bypassing pagination.
4. **Does Clear filters also reset the lifecycle stage?** Recommended default: **No.** Clear search/source/date/sort/page-size overrides while retaining the active stage, because the stage tabs are primary navigation rather than an incidental filter. “All” remains the explicit way to remove stage restriction.
