# Research: keeping the Electron main process responsive under FS storms + heavy child processes

TASK_2026_437_0778. Supports the software-architect's implementation plan for
the 2026-09-14 freeze (10 worktrees removed in one Bash command → 33 s of
265-615 ms main-loop lag → `git status` timeout → app-wide freeze, no crash
record).

## Question

Decision this supports: which isolation mechanism(s) — out-of-process watcher,
`utilityProcess`, `worker_threads`, watcher-technology swap, child-process
hygiene — to specify in `implementation-plan.md` for each of six concerns
(watcher storms, heavy child processes, process isolation choice, child-process
hygiene, IPC backpressure, self-protection/detection).

Bounds: this is options + trade-offs + local cost, not the plan itself. It does
not choose exact debounce numbers, does not redesign `GitInfoService`'s cache
API, and does not cover macOS/Linux-specific watcher bugs beyond noting where
behaviour is known to differ.

## Answer

VS Code's own answer to (a) is an out-of-process native watcher (`@parcel/watcher`
in a `utilityProcess`) with excludes applied _before_ the OS ever emits an
event, not after; this repo currently does the opposite — `fs.watch({recursive:
true})` and chokidar run **inside the Electron main process itself**, and the
exclude list they filter against (`WATCH_IGNORED_DIRS`) is missing the exact
folder pattern (`.claude-worktrees/`, `.claude/worktrees/`) that broke on
2026-09-14. The fix with the best evidence behind it is two-layered: fix the
exclude list immediately (cheap, closes the specific incident), and move the
workspace-root watcher off the main thread into a `utilityProcess` on the same
pattern this repo already uses for the embedder/integrity/voice workers
(`ElectronUtilityWorkerProcess.fork`), so a _future_ unlisted churn source
degrades a worker, not the app. For (b), this repo has already solved the
general problem once — `OffThreadProcessSpawner` moves the SDK's synchronous
`child_process.spawn` onto a `worker_threads` Worker — and the same worker
already exists for `IProcessSpawner`; the qustion for the architect is whether
`git status`/`GitInfoService`'s exec path should route through it too, since
today it still runs `execGit` inline on main via `cross-spawn`.

## Options

### (a) Watcher technology + process placement

| Option                                                                                                                                        | Fit here                                                                                                                                                                                                                                                                                       | Cost to adopt                                                                                                                                                                                                                                                                                  | Known failure mode                                                                                                                                                                                                                                                                                                                                 |
| --------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Keep `fs.watch({recursive:true})` in-process, only fix `WATCH_IGNORED_DIRS`                                                                   | Cheapest possible fix; closes the exact 2026-09-14 incident (worktree folders now excluded)                                                                                                                                                                                                    | ~1 line + test                                                                                                                                                                                                                                                                                 | Does not generalize — the _next_ unlisted high-churn folder (a build output dir, an npm install under a nested workspace) reproduces the same class of freeze. `fs.watch` recursive on Windows still has the documented `ReadDirectoryChangesW` overflow/crash history (nodejs/node #4792) with no overflow→rescan fallback in this codebase today |
| Swap to `@parcel/watcher` in-process (same main-thread placement, better engine)                                                              | Native ignore-glob is applied _before_ JS ever sees the event — removes the per-event `isIgnoredWorkspaceEvent` cost entirely, and its overflow behavior is a documented "resync" event rather than a crash                                                                                    | New native dependency + prebuild verification across win32/darwin/linux archs (this repo already tracks native-module ABI carefully for `better-sqlite3`, so the process is known but not free); requires wiring an ignore list at watch-start instead of the current watch-then-filter design | Still runs on Electron main — one runaway build under an unlisted folder still costs main-thread JS time proportional to event volume, just less of it                                                                                                                                                                                             |
| Move the workspace watcher(s) to a `utilityProcess`, keep `@parcel/watcher` inside it, only cross the coalesced/debounced result back to main | Matches the pattern this repo already ships three times (`ElectronUtilityWorkerProcess.fork` for integrity/embedder/voice) — same fork helper, same crash-isolation story ("a native ONNX abort kills only the child") applies to "a watcher storm consumes only the worker's CPU, not main's" | Highest effort of the three: new `IWatcherProcessFactory` + protocol (mirroring `IIntegrityWorkerProcessFactory`), a coalescing layer inside the worker so it doesn't just forward 10,000 IPC messages to main, and a supervision/restart path for a wedged watcher                            | A worker that gets stuck instead of main is invisible progress unless it also reports a "still busy" heartbeat main can render — otherwise the git-status UI silently goes stale with no distinguishable failure mode from "no changes happened"                                                                                                   |
| Chokidar v4 in place of chokidar's current version, in-process                                                                                | Chokidar v4 dropped globbing and does per-directory native watches — cheaper CPU per directory than v3's userland glob walk, but still N `fs.watch`/`FSEvents`/`inotify` handles, one per directory, and still in-process                                                                      | Migration cost is real: chokidar v4 changed its ignore/glob API surface, and `workspace-file-index.service.ts` already depends on chokidar's current shape                                                                                                                                     | Does not solve process-placement at all — same main-thread exposure as today, just cheaper per-directory overhead. Not a fix for the freeze class, only a partial mitigation                                                                                                                                                                       |

**Recommendation**: fix `WATCH_IGNORED_DIRS` now (unconditionally correct,
near-zero cost, closes the reported incident) — then treat the `utilityProcess`
watcher move as the durable fix, because it is the one option whose failure
mode ("a storm degrades a worker, not the app") matches the stated goal
("long/heavy work must not affect the app badly") rather than merely reducing
the odds of hitting the ceiling again. `@parcel/watcher` is the natural engine
choice _inside_ that worker, on VS Code's own precedent and its native
pre-filtering.

### (c) Isolation mechanism: `utilityProcess` vs `worker_threads` vs `child_process`

| Option                                            | Fit here                                                                                                                                                                                                                                                                                                                          | Cost to adopt                                                                                                                                                                                                                                                                                                                                                                                                                                                    | Known failure mode                                                                                                                                                                                                                                                     |
| ------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `utilityProcess` (own OS process)                 | Already the pattern for CPU/native-crash-risky work: SQLite integrity check, ONNX embedder, voice. Matches VS Code's own choice for its watcher. Full process isolation — a wedged or crashed worker cannot take main down with it, and Electron's `child-process-gone` event (currently unused in this repo) fires when one dies | Highest per-instance overhead (own process, own V8 heap, own event loop) — not something to spin up per-git-call, but fine for a long-lived watcher or a rare heavy check                                                                                                                                                                                                                                                                                        | Structured-clone/`postMessage` cost for large payloads (the embedder worker already deals with this); needs explicit supervision/restart wiring, which this repo has NOT yet built generically — each factory (`electron-integrity-worker-factory.ts` etc.) is bespoke |
| `worker_threads` (shared process, own thread)     | Already the pattern for the _synchronous spawn_ problem specifically (`OffThreadProcessSpawner`) — cheaper to create per-call than a `utilityProcess`, which matters because a spawn happens far more often than "start the watcher"                                                                                              | Lower overhead than `utilityProcess` but still real — the repo already accepts an `eval`'d worker source string (`OFF_THREAD_SPAWNER_WORKER_SOURCE`) to avoid bundling issues; any CPU-heavy JSON/Zod work moved here still shares the process's memory limits and a crash in `node:worker_threads` can, in some Electron versions, be noisier to recover from than a `utilityProcess` crash (see the worker_threads SIGTERM/assertion issues found in research) | Does not get its own OS-level crash isolation — a worker thread crash is a V8 fatal error in most cases, not a recoverable "child process died" event                                                                                                                  |
| Plain `child_process` (no worker/utility wrapper) | What `execGit` does today; simplest, and fine for short-lived, bounded-timeout commands                                                                                                                                                                                                                                           | None beyond what exists                                                                                                                                                                                                                                                                                                                                                                                                                                          | No off-main-thread win at all — the _spawn call itself_ still blocks main under Windows' `CreateProcessW` cost, same defect class TASK_2026_341 fixed for the SDK                                                                                                      |

**Recommendation, mapped to concerns**: watcher (long-lived, high event
volume, benefits from OS-level crash isolation) → `utilityProcess`, following
VS Code and this repo's own integrity/embedder/voice precedent. Heavy but
short child-process _spawns_ (git, agent Bash launch) → `worker_threads` via
the existing `OffThreadProcessSpawner`, extended rather than duplicated. CPU-
heavy JSON/Zod validation of large payloads (not concretely evidenced as a
freeze cause here, but named in the question) → `worker_threads` is the
better fit than a fresh `utilityProcess` per call, given the same overhead
argument.

## Disagreements

- **How much of the fix belongs in-process vs. out-of-process**: VS Code's own
  architecture (utility-process watcher, excludes applied at watch-start) says
  "isolate the watcher." The GitHub issue threads on VS Code's own git
  extension ("too many active changes", `git.autorefresh: false` as the
  standard workaround) say the _practical_ fallback even inside that
  architecture is still "turn the feature off/back off," not "the isolation
  alone solved it." What decides it here: this repo's git-status channel is
  push-based and debounced already (`git-watcher.service.ts`), which is
  actually a stronger starting position than plain VS Code polling — the
  missing piece is specifically the exclude-list gap and the coalescing bug,
  not an architecture rewrite. Isolation (this report's (a)/(c)) is the
  durable fix for _unknown future_ churn sources; the exclude-list and
  coalescing fixes are what closes _this_ incident.
