# Research Report — TASK_2026_437 — Main-process event-loop inventory

## Question

- Decision this supports: where to cut isolation boundaries (worker_thread / utilityProcess / child_process) so heavy external load (agent Bash, mass file ops, git on a many-worktree monorepo, builds, large transcripts) cannot freeze the Electron main process.
- Question: what work runs on the main event loop today, and which of it is reachable by that load?
- Bounds: renderer-side work (tile replay, tab persistence, streaming re-parse) is out of scope here — flagged in context.md as "unconfirmed candidates" and owned by the renderer-investigator agent. No load testing was run; all costs are read from source, not measured.

## Answer

The freeze had two independent causes that compound: (1) no watcher — `fs.watch`-based or chokidar-based — excludes `.claude-worktrees`/`.claude/worktrees`, so a 10-worktree delete (~74k file events) is fully delivered to main-thread JS callbacks; and (2) `git-watcher.service.ts:667` deletes the in-flight coalescing entry immediately before re-requesting it, so every one of those watcher events can spawn its own `git status`. Neither is a raw CPU stall inside `fs.watch` itself — the OS-level watch and child-process spawn are already reasonably cheap/off-thread — the damage is JS callback volume × unbounded concurrent git spawns × synchronous better-sqlite3 writes from the symbol indexer, all competing for the one event loop with no backpressure. Existing worker/utilityProcess patterns (integrity/backup, embedder, voice, state-storage, TS diagnostics, off-thread process spawner) already prove the isolation approach works here; the fix is applying that same shape to the watcher event path, the git coalescing, and the SQLite write path.

## Top 10 risks (ranked)

1. **Watcher exclude lists omit `.claude-worktrees`/`.claude/worktrees` in both `fs.watch` (git-watcher) and chokidar (file-index) paths** — direct cause of the 2026-09-14 freeze. `git-watcher.service.ts:449-467`, `workspace-scan.constants.ts:57-78`, `workspace-file-index.service.ts:635`, `workspace-default-excludes.ts:1-26`.
2. **`invalidateReadCache` called immediately before `getGitInfo` defeats in-flight coalescing**, letting every watcher event spawn its own `git status` concurrently, unbounded. `git-watcher.service.ts:653-684`, `git-info.service.ts:314-329,363-367`.
3. **Per-file content-change debounce creates one `setTimeout` per distinct filename** under a delete/create storm — with 74k events across 10 worktrees this is tens of thousands of live timers before the workspace debounce even fires. `git-watcher.service.ts:508-560`.
4. **No global spawn concurrency ceiling on git/editor/CLI child processes outside `AgentProcessManager` and `InternalQueryService`** — a coalescing-defeated git watcher plus a busy agent session can pile up an unbounded number of worker-threads-per-spawn. `off-thread-process-spawner.ts:294`, `exec-git.ts:156-289`.
5. **better-sqlite3 traffic for memory-curator, skill-synthesis, cron-scheduler and the symbol indexer runs synchronously on main with no worker boundary**, unlike backup/integrity which already got one. Any concurrent burst of curator/indexer writes competes directly with watcher/IPC work for the same loop. `sqlite-connection.service.ts:1-13`.
6. **No `render-process-gone`, `child-process-gone`, or webContents `unresponsive`/`responsive` handlers**, and renderer console isn't forwarded — during the actual freeze there was no crash record, no Crashpad dump, and no way to distinguish "slow" from "dead" from the log. This is why the incident is reconstructed from lag samples, not a handler firing. Absence confirmed by grep across `apps/ptah-electron/src`.
7. **`editor:detectTargets` is a fully sequential `await`-chained `fs.stat` walk over PATH×PATHEXT×5 descriptors**, no cache/timeout/concurrency — 51s observed at boot; on a slow/network filesystem this is worse. `editor-launcher-detection.ts:163-235`.
8. **`execGit`/`execGitBuffer` buffers entire stdout/stderr in memory with no size cap** — large diffs/blobs during heavy git activity build unbounded buffers on main-adjacent code before the caller ever sees them. `exec-git.ts:254-289`.
9. **Legacy state store does synchronous full-file `readFileSync`+`JSON.parse`/`writeFileSync`+`JSON.stringify`** — only a fallback path, but if the worker-backed v2 store degrades under the same load spike that's already stressing main, this fallback compounds it right when it's least wanted. `electron-state-storage.ts:291-320`.
10. **Symbol indexer's inter-batch yield doesn't protect against a single large file's tree-sitter parse or a batch's SQLite insert** — mitigation is coarse (per-batch, not per-file), so one large source file in the index queue still runs to completion synchronously. `code-symbol-indexer.service.ts:159-228,302,410`.

## Existing isolation patterns worth reusing

- **Shared utilityProcess fork shim**: `apps/ptah-electron/src/services/platform/electron-utility-worker-process.ts:21-61` — one ~40-line factory reused structurally (no `implements` clause) by integrity/backup, embedder, and voice workers. This is the lowest-cost template for any new "move X off main" job that touches a native addon (better-sqlite3, ONNX).
- **Bounded run-loop convention**: `libs/backend/persistence-sqlite/src/lib/integrity/integrity-worker.ts` + its `db-worker-runner.ts` — budget timeout, single-settle-on-reply/exit/kill, id-correlated request/response. Directly reusable shape for offloading better-sqlite3 traffic (risk #5) and/or exec-git buffering (risk #8).
- **Pure-JS worker_threads pattern**: `electron-state-storage-worker-host.ts` (JSON protocol + byte-budget guard + handshake timeout + restart cap) and `libs/backend/workspace-intelligence/src/diagnostics/ts-diagnostics-worker.ts` (keeps `ts.createProgram` off main) — template for anything CPU-bound but not native-addon-bound, e.g. the symbol indexer's tree-sitter parse (risk #10).
- **Generic off-thread process spawner**: `off-thread-process-spawner.ts` already gives every spawned child (git, SDK CLI, rival CLIs) worker-thread isolation with real stream backpressure — the gap is a concurrency ceiling, not the isolation mechanism itself, which is proven.
- **Rate-limited/serialized background job pattern**: skill-synthesis's `CuratorRateLimitService` + shared query lane, and memory-curator's `CuratorJobQueue` (one pass at a time, stall-not-drop on lost slot) — reusable pattern for gating the watcher→git-spawn path (risk #2) behind a similar per-workspace serialization.

## Disagreements

None found between the parallel investigations — the four areas (watchers, spawns, sync/CPU work, background jobs/isolation) were disjoint and the sub-findings were mutually consistent (e.g. both the watcher and spawn investigations independently converged on `git-watcher.service.ts:667` as the coalescing-defeat site, matching context.md's own finding).

## Local consequences

- `apps/ptah-electron/src/services/git-watcher.service.ts`: needs the exclude list fixed (risk #1) and the invalidate-then-fetch sequence reworked to preserve coalescing (risk #2) before any worker-boundary work is worth doing — otherwise the isolation just moves the storm, it doesn't bound it.
- `libs/shared/src/lib/constants/workspace-scan.constants.ts` and `libs/backend/workspace-intelligence/src/file-indexing/workspace-default-excludes.ts`: both need `.claude-worktrees`/`.claude/worktrees` (and ideally any `.git/worktrees`-registered path, read dynamically) added; a hardcoded list will drift again.
- `libs/backend/persistence-sqlite/src/lib/sqlite-connection.service.ts` and its callers: candidate for the same utilityProcess treatment already given to backup/integrity, if measurement (see Unknowns) shows contention during heavy load.
- `apps/ptah-electron/src` app-lifecycle wiring: needs `render-process-gone`/`child-process-gone`/webContents `unresponsive`/`responsive` handlers and `console-message` forwarding added regardless of which isolation fix ships first — this is the observability gap that turned a 33-second lag into an unexplained 8-minute-to-relaunch outage.

## Unknowns

- Actual event volume and JS-callback wall-clock cost per event during a 10-worktree delete was not measured here (only inferred from ~7,400 files/worktree × 10). Smallest experiment: reproduce the delete against a scratch repo with the event-loop monitor armed and `PTAH_PROFILE_ON_LAG_MS` set low, capture the `.cpuprofile`.
- Whether concurrent `git status` spawns from risk #2 actually reach the process/thread limits that caused the 33s uninterrupted lag, versus the watcher event volume alone being sufficient — not separated experimentally. Smallest experiment: patch out either the exclude-list fix or the coalescing fix independently and re-run the same delete to see which one alone resolves the freeze.
- IPC batch payload size per flush (`ipc-bridge.ts:242-266`) was inferred, not measured — during a session with 3 open canvas tiles, whether the serialize step itself is a meaningful cost is unknown. Smallest experiment: log payload byte size and flush duration under the three-tile scenario from the incident.
- Whether `AgentProcessManager`'s concurrency ceiling applies to the interactive chat spawn path or only to internal one-shot queries was not fully confirmed — the sub-investigation flagged this as an open question for `SdkAgentAdapter`.
