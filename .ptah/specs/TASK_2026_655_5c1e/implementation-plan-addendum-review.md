## Defects

1. **Moderate — a byte-cap-truncated seeded context shows its in-flight block twice.** Addendum `:949-960` (rule P's `seedBlockKeys` basis), `:961-971` (rule P2's "tracked from a seed start" condition), `:1008-1015` (rule I tracks only on an anchor), `:1069-1097` (absorption); `implementation-plan.md:337-346` (deferred anchors and the 1 MiB byte cap); `accumulator-core.service.ts:314-321` (replace, no removal). Root cause: the byte cap clears a context's suffix, so the context contributes **no** seed events — its block keys are absent from `seedBlockKeys` (rule P falls through, by design, to avoid loss) and its anchor is deferred, arriving only when the host next publishes content for it (plan 4g). Rule I therefore tracks X only *after* the truncated context's pre-snapshot content has already been drained, and rule P2 requires exactly that tracking, so neither verifies it against `H`. Two orderings, both duplicate-only, no loss:
   - **(a) The truncated block completes before the snapshot.** X streams block B (> 1 MiB of deltas) → the host suffix cap clears X's suffix and marks it truncated → B's complete batch is published pre-snapshot (context: anchor + empty suffix, not closed → deferred anchor; `k0` counts B) → resync snapshot: `liveSeed` omits X, `liveSeedBlocks` carries `k0` → the webview fence already holds X's pre-snapshot stream deltas **and** B's complete batch (all `arrival < prefixMark`) → at drain, rule P falls through (no `seedBlockKeys` entry), rule I does not track (no anchor seen), rule P2 does not apply (X not tracked) → deltas and batch are kept and applied → the live node shows B in full; the deferred anchor arrives later and tracks X at `k0` (correct only for the *next* block) → the history page also shows B (`H(X)[B]`, paged) → **B shows twice, both in full**.
   - **(b) The truncated block completes after the snapshot but persists before the read.** Same cap, B still streaming at the snapshot (`k0` = B's position) → the fence holds B's pre-snapshot deltas → drain keeps them (same fall-through) → the live accumulator holds B's partial text with no anchor → the deferred anchor arrives → X tracked at `k0` → B's post-snapshot deltas are absorbed → B's complete batch arrives (`arrival > prefixMark`) and rule H drops it against `H(X)[k0]`, an exact match → the applied partial is never replaced → **partial live copy plus full history copy of the same block**. At the terminal, `finalizeCurrentMessage` builds a tree from the partial (`message-finalization.service.ts:181-243`) and `placeFinalizedTrees` appends it (`:85-90`), so the duplicate is finalized and lasting.
   **Correction:** verify the pre-snapshot content of an X that `seedStartK` names even though the seed holds none of it — extend rule P2 (or rule P) so that pre-snapshot stream *and* complete events of a `seedStartK` X are checked against `H(X)` without requiring rule-I tracking first: a joined stream prefix or complete signature that matches some `H(X)[p]` is dropped (the history node shows it); no verified match is kept, as everywhere fail-open. Add a truncated-context R-B1s variant (both orderings) asserting no duplicate and no loss.

## Proportionality

Residual B now costs: shared — two optional reply fields, one `z.literal(true)` param, one optional snapshot field with a schema refine; host — an optional collector on replay, an opt-in on the reader, a passthrough on `readForResume`, one new pure helper file (`history-block-owners.ts`, two exports), `resumeSession` wiring, plus one integer counter per projection context and one snapshot field in the plan's projection and coordinator; webview — two new small files (`persisted-content-filter.ts`, `history-tool-result-patch.ts`), the fence entry type with `arrival`, per-claim filter inputs, a `persistedFilters` registry, seed-through-filter, `deliver(excludeTabIds)`, and loader validation. Against that, the 5 s timer and the 2000-event release are **removed**, so the hold machinery is smaller than Revision 1's. The rejected smaller designs are code-verified, not taste: release-then-remove needs an accumulator removal op and a history text-node mapping that do not exist (`accumulator-core.service.ts:297-322`; only tool and agent nodes carry `toolCallId`, `tool-node.fn.ts:213-226`, `agent-node.fn.ts:116-129`); keep-without-patch would never show the real output (`tool-node.fn.ts:163-165`); a fresh resync can re-synthesize (`session-replay.service.ts:375-415`). The per-context counter is the cheapest possible position basis. Proportionate — defect 1 is the one place the design stopped short of its own verification principle, and its correction is a rule extension, not new machinery.

## Decisions

- **REVISE.** Round-2 defects 1-3 are resolved for a current host with verified evidence; one Moderate defect (the byte-cap-truncated context) leaves a real ordering in which a block shows twice, so the user goal is not yet met in every ordering. 0 blocking, 0 serious, 1 moderate.
- **Older-host fallback, stated plainly (round-2 defect 2's remaining half):** with a host that sends no `liveSeedBlocks`, a seeded message whose block persisted between snapshot and read **does** show twice (Revision 1 behaviour, addendum `:1709-1712`). It is acceptable as a mixed-version case, not a goal violation of this system: the webview is bundled inside the VS Code extension and the Electron host ships with its webview (addendum `:1329-1331`), so "new webview + old host" is not a runtime ordering of any shipped build; it arises only under rollback or a manually mismatched install, degrades to the approved base plan's documented duplicate, and never loses content. Round 2's rejection targeted a *current-host* cap fallback, which Revision 2 removed (`:842-845`).
- **Accepted no-loss duplicate edges, unchanged from rounds 1-2 and not reopened:** the page-edge pass-through (round-1 defect 3's resolution; dropping would lose content not in the page), the rule R turn boundary (B.10 point 3), and A-B2 premise failure (B.10 point 2). All document which ordering duplicates and all lose nothing.
- **RB2-A3 is confirmed** (`message-finalization.service.ts:176` read and `:249-251` write in one synchronous pass; `placeFinalizedTrees:56-96` preserves existing message objects), so the patch design stands as written; no plan change needed beyond B.10 point 5's stale-plan amendments, which remain for the orchestrator.
- **Batches and test commands:** unchanged from round 2's assessment (S before B/F; file-disjoint; scoped, serial, worker-limited commands). Not re-run: document review.
- **Tests to add with defect 1's correction:** the truncated-context R-B1s variants (orderings (a) and (b) above).

## Notes

Not a behaviour difference — `isReplay` only gates the live user `message_start` uuid reconcile (`streaming-handler.service.ts:441-450`) and `deliverToTab` carries assistant-scoped events only. Suggest the addendum say "the call replay already uses, minus `isReplay`".
2. Rule S's parenthetical "when X still has a queue (only after a full drop, see H)" vs `:1067-1068` ("stays as X's pending queue for rule S") is ambiguous: read together, a passed-through X whose anchor is still queued has its queue flushed by the next content event (rule S's first sentence) and its non-content events appended. The implementer should treat the `:1067` queue as flushable; the parenthetical should name it.
3. P2's keep-path premise — that every `arrival < prefixMark` event was published before the snapshot — rests on a single ordered delivery channel (the 16 ms host batch buffer preserves order, and the snapshot and chunks share the channel). It holds here, but the addendum never states it; one sentence would pin it.
4. Malformed `liveSeedBlocks` is treated as absent (`:1200-1204`), which restores the Revision-1 seeded duplicate for that snapshot — fail-open with a `console.warn`, reachable only from a host bug. Acceptable; worth the same "safe direction" sentence the synthetic list gets.
5. B.10 point 4's remaining older-host and no-match cases (`:1720-1728`) are consistent with the rules as written.
6. `reconcileHistoryToolResult` returning `false` leaves the synthetic output on screen with only a `console.warn` (`:1156-1157`). The walk mirrors the working `markAgentsAsInterruptedByToolCallIds` precedent (`message-finalization.service.ts:431-461`), so the risk is low; a UI-visible signal would be better than a console line if it ever fires.
7. The compact-view row per live `tool_result` (B.10 point 6) is a cosmetic double-count candidate for a kept history-tool result; recorded by the addendum, unchanged.
