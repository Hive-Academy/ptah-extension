## Check 1 — Does the fix remove the failure; is the diagnosis plausible

**Yes, by construction.** `batched-update.service.ts:176-177` now checks `activeId === tabId` and returns `true` *before* any visible-set logic, so no registration state — stale or not, empty or not — can defer the active main-agent tab while the surface is observable. This holds for both A→B and A→B→A: after `switchWorkspace` synchronously installs the new `_activeTabId` (`tab-manager.service.ts:784-785`), the very next content event for that tab passes `scheduleUpdate` (:127-136) straight into `pendingTabUpdates`. Previously-deferred state for the newly-active tab is drained by the `activeTabId` effect (:93-99) via `drainDeferredForTab` (:246-257).

**Diagnosis is plausible and the wiring checks out:**

- `switchWorkspace` swaps `_tabs` and `_activeTabId` (`tab-manager.service.ts:773-786`) but never touches `_visibleTabIds` (registration methods :2844-2859 are lifecycle-internal only).
- Canvas tiles register/unregister from the `visible` *input* (`canvas-tile.component.ts:556-563`), which is `[visible]="active()"` in the grid (`canvas-workspace-grid.component.ts:129`), driven by `[visible]="path === canvasStore.activeWorkspacePath()"` (`orchestra-canvas.component.ts:189`). Both workspaces' grids stay mounted (`[style.display]` hide, `canvas-workspace-grid.component.ts:97`), so between the synchronous signal swap and Angular processing the grids' input change, old-workspace tiles remain registered — a real transient stale window that reproduces the failing gate inputs.
- The conductor registers once in `ngOnInit` (`conductor-tile.component.ts:227-230`) with no visibility or workspace gating and unregisters only in `ngOnDestroy` (:233-238) — a *persistent* stale window while the tribunal view survives a workspace switch.

Under the old predicate (visible set non-empty ⇒ only its members flush), both sources reject the new active tab while it is streaming. The regression spec reproduces exactly these gate inputs (`batched-update.service.spec.ts:276-288`).

**Other persistent causes not covered:** none that can still block the *active* tab — the short-circuit at :177 precedes all registration logic, closing the failure class regardless of registration source. Future `ngOnInit`-style registrants remain contained for *flushing* by the new membership clause (:180), but they still narrow the non-active flush set and are the fuel for Defect 1 below. I verified there are no other `registerVisibleTab` call sites in `libs/frontend`.

## Check 2 — Cross-workspace isolation and draining

**Isolation holds and is strengthened.** A registered tab of a *background* workspace cannot flush: `visible.has(tabId) && this.tabManager.tabs().some(...)` (:180) — `tabs()` is `_tabs.asReadonly()` (`tab-manager.service.ts:393`), which `switchWorkspace` replaces with the current workspace's partition (:784), so a stale background-workspace registration fails membership. A non-registered background tab fails at `visible.has` and falls through to `!activeId` (:182), false whenever an active tab exists. The regression spec pins both directions: stale `'a'` does not flush while B is current (`batched-update.service.spec.ts:288`), and `'b'` (visible-but-not-member) stays deferred after the return (:298).

**Drain coverage has a real hole (Defect 1).** Drain triggers exist only for: surface activation (:52-82), document visibility (:83-91), `activeTabId` change (:93-99 — but `drainDeferredForTab` drains *only the new active tab*), and a *changing* `visibleTabIds` set (:101-107). Nothing tracks `tabs()`. Canvas tiles always drain because their registration flips with the grid's `visible` input, so the set changes on every switch and :101-107 fires. The conductor does not: its registration is identical before and after a switch, so the set does not change, and if the restored active tab is a *different* tab, :93-99 drains only that one. Result: the conductor tab's deferred snapshot is stranded on return until its next event, a `visibilitychange`, a turn-end `flushSync()` full drain, or another `activeTabId` change. Bounded mid-run (next event publishes the whole snapshot — no data loss), but stale indefinitely if the stream ended without a finalization drain.

## Defects

1. **[Moderate] No drain trigger on a `tabs()`-only change — deferred state stranded for a registered non-active tab after returning to its workspace.**
   - Location: `libs/frontend/chat-streaming/src/lib/batched-update.service.ts:101-107` (effects; no `tabs()` effect) and `:174-183` (`canFlush`, whose new membership clause makes `tabs()` the eligibility pivot for registered tiles); contributing: `conductor-tile.component.ts:210-239` (lifetime-only registration), `tab-manager.service.ts:784-785` (synchronous `_tabs`/`_activeTabId` swap, `_visibleTabIds` untouched).
   - Failure scenario: tribunal view open in workspace A, conductor tab `c` registered once in `ngOnInit` and never re-registered on workspace switches. User switches to B mid-run; `c`'s events correctly accumulate in `deferredTabUpdates` (membership fails). Stream for `c` pauses or ends (abnormally, without a turn-end `flushSync()`), user switches back to A where the restored active tab is the main chat, not `c`. The `activeTabId` effect drains only the main tab (:246-247); the `visibleTabIds` set never changed, so :101-107 does not fire; `tabs()` changed but nothing listens. The conductor tile now shows pre-switch content while the full snapshot sits in `deferredTabUpdates` — until the next `c` event, a window minimize/restore, or any tab switch. Mid-stream the delay is one event (the whole snapshot republishes, so no loss); at end-of-stream it is unbounded.
   - Suggested fix: add a constructor effect tracking `this.tabManager.tabs()` that calls `drainDeferred()` inside `untracked`, mirroring :101-107. Cost: one effect evaluation per `tabs()` change (tab open/close/switch) — negligible against the per-event RAF path.

2. **[Minor] Drain dead zone when the visible set empties or `activeTabId` becomes null.**
   - Location: `batched-update.service.ts:103` (early return on empty set) and `:95` (early return on null active id), interacting with the `!activeId` fallback at `:182`; trigger path: `tab-manager.service.ts:795-803` (`removeWorkspaceState` sets `tabs=[]`, `activeTabId=null`).
   - Failure scenario: deferred entries held for background-workspace tabs become flushable through `!activeId` when the active workspace folder is removed, but neither effect fires (both early-return on the new values), so nothing drains until each tab's next event or an external trigger. State is intact and republished whole on the next event — a one-event display delay in a rare path. Pre-existing structure (both early returns are outside this diff), unchanged by the fix and not worsened by it; recorded because the fix's stated contract ("deferred state must drain when the workspace becomes active again") has drain triggers attached to the wrong signals.
   - Suggested fix: fold into Defect 1's `tabs()` effect (a `tabs()` change fires on `removeWorkspaceState` too), and drop the `:103` early return so an emptying set also re-runs `drainDeferred()`.

3. **[Minor, test precision] The regression spec's return phase mutates three signals at once and does not pin the drained snapshot.**
   - Location: `batched-update.service.spec.ts:290-298`.
   - Issue: phase 3 changes `activeTabId`, `tabs` and `visibleTabIds` together before `TestBed.tick()`, so the observed drain of `'a'` could arrive from either the `activeTabId` effect (:93-99) or the `visibleTabIds` effect (:101-107) — the test proves "drains on return" but not through which trigger, and Defect 1 lives precisely in the gap between those two triggers. Additionally `expect.any(Object)` (:297) cannot distinguish *which* snapshot flushed, since all `makeEmptyStreamingState()` states are identical.
   - Suggested fix: leave `visibleTabSignal` untouched in the final phase (the stale registration premise already justifies it) so only the `activeTabId` effect can drain, and tag the deferred snapshot (`backgroundA.currentMessageId = 'a-final'`) and assert `toHaveBeenCalledWith('a', expect.objectContaining({ currentMessageId: 'a-final' }))`. Not a weakening of assertions — a tightening opportunity.

## Five logic questions

1. **Silent failure:** the old code produced exactly one — events consumed, no error, UI frozen for chunks while status/tool writes (direct `TabManager` paths) kept moving. The fix removes it for the active tab by construction. Remaining silent gap: Defects 1-2 (accumulated snapshot not republished when eligibility changes without an event).
2. **Unexpected user action:** switching workspaces and back while a background stream runs on a *non-active* registered tab (conductor) — stale tile content on return until the next event; removing the active workspace folder while other workspaces hold deferred state (Defect 2).
3. **Wrong answer rather than error:** none found. `tabs()` membership cannot misfire in the direction of flushing a hidden-workspace tab (both conjuncts must hold); a deferred entry for a *closed* tab cannot leak — close/cleanup paths call `clearPendingUpdates` (`streaming-handler.service.ts:472, :558`, `chat-lifecycle.service.ts:235`, `session-history-replayer.service.ts:145, :389`).
4. **Dependency failure/shape:** `canFlush` now dereferences `tabs()` with `.some`; the real `TabManager` exposes a `signal<TabState[]>` (:225/:393) so an array is guaranteed, and the SSR guards around `document` (:83, :164) are pre-existing and untouched. A future mock omitting `tabs` would throw at :180 — the two changed specs both supply it; other suites with visible-tab mocks were audited per `diagnosis.md:40` and none regress (624 passed recorded).
5. **Missing from requirements:** the drain half of "deferred state must drain when the workspace becomes active again" is implemented only for the tab that *becomes active*; registered tiles of the newly-current workspace have no matching trigger (Defect 1).
