# Workspace switch stream loss proof — TASK_2026_655

## Verdict

**PARTLY CONFIRMED.** The backend definitely discards all hidden events after the 256-event cap, including an in-flight `message_start`, and reveals a `resyncRequired` snapshot without events. The resync path definitely resets and then finalizes the tab from JSONL history; live deltas without their start cannot form a rendered message. The stronger claim that `chat:resume` *never* contains any part of the current assistant turn is not established: it returns whichever assistant records are already in JSONL at read time, and no live buffer is merged into that reply. Thus this failure occurs when the current live message has no matching persisted history record, or when the record does not preserve the live message identity.

## Answers

- **Q1 — `chat:resume` and the live turn.** The RPC dispatch invokes `ChatSessionService.resumeSession` (`libs/backend/rpc-handlers/src/lib/handlers/chat-rpc.handlers.ts:264-285`). It calls `historyRead.readForResume` before testing whether the stream is live (`libs/backend/rpc-handlers/src/lib/chat/session/chat-session.service.ts:945-950,1038-1072`), and returns only `fullEvents` or a selected history page (`:1074-1092`). `readForResume` calls `SessionHistoryReaderService.readSessionHistory` (`chat-history-read.service.ts:67-74`), which reads the session JSONL (`libs/backend/agent-sdk/src/lib/session-history-reader.service.ts:472-489`) and projects those records into events (`:415-454`). The projector creates `message_start` and `text_delta` from an assistant JSONL record with content (`libs/backend/agent-sdk/src/lib/helpers/history/session-replay.service.ts:215-232,283-299`). It does not read the live delivery tail or synthesize the partial message from live deltas. The Electron `ptahUiFence: true` flag is passed by the frontend (`libs/frontend/chat/src/lib/services/chat-store/session-loader.service.ts:855-867`), but in this live-stream case `activate` is absent for a targeted resync, and the flag only appears in the activation branch of `resumeSession` (`chat-session.service.ts:1038-1049`). **Answer:** a persisted assistant record can appear as reconstructed start/content, but the in-flight stream's exact `message_start` and deltas so far are **not guaranteed and are not sourced from the live stream**. Whether the SDK has already written the current record is an external timing fact not established by these files.
- **Q2 — fence and status.** The resync snapshot invokes `resyncStream` (`libs/frontend/chat/src/lib/services/chat-message-handler.service.ts:530-536`; `libs/frontend/chat/src/lib/services/chat.store.ts:227-235`). Targeted resync claims a fence, resets the tab to empty messages/state and `resuming`, then replays history (`libs/frontend/chat/src/lib/services/chat-store/session-loader.service.ts:820-854,937-961`; `libs/frontend/chat-state/src/lib/tab-manager.service.ts:2533-2561`). Replay closes the fence after history finalization (`libs/frontend/chat/src/lib/services/chat-store/session-history-replayer.service.ts:209-228`); its last holder delivers deferred callbacks in arrival order (`:520-549`). The `finally` release covers failures and empty replies (`session-loader.service.ts:980-983`; `session-history-replayer.service.ts:173-179`). History finalization drops `streamingState` and sets tab status `loaded` (`libs/frontend/chat-streaming/src/lib/message-finalization.service.ts:281-301`; `libs/frontend/chat-state/src/lib/tab-manager.service.ts:2005-2015`). Only an accepted live `turn_state` with phase `generating` re-marks it `streaming` (`tab-manager.service.ts:1433-1455,1471-1509`); ordinary text chunks do not (`chat-message-handler.service.ts:505-509`). A hidden `generating` event lost in the overflowing tail is not recovered by this resync.
- **Q3 — delta-only bucket.** `text_delta` is indexed and accumulated, but does not append its `messageId` to `messageEventIds` (`libs/frontend/chat-streaming/src/lib/accumulator-core.service.ts:297-312`); that insertion happens in the `message_start` case (`:248-284`). Even if a builder visits the bucket, `buildMessageNode` returns `null` without `findMessageStartEvent`, which scans for an actual start event (`libs/frontend/chat-execution-tree/src/lib/builders/message-node.fn.ts:27-36,67-76`). Hence the later text has no rendered message node.
- **Q4 — other dropping paths.** `applyResumingSession` resets `lastTurnStateRevision` to `undefined`, which makes the next relevant revision acceptable rather than filtering it (`libs/frontend/chat-state/src/lib/tab-manager.service.ts:2555-2560,1450-1455`). `cleanupSessionDeduplication` deletes processed message/tool ID sets; it does not discard subsequent chunks (`libs/frontend/chat/src/lib/services/chat-store/session-loader.service.ts:853-855`; `libs/frontend/chat-streaming/src/lib/streaming-handler.service.ts:98-105`; `libs/frontend/chat-streaming/src/lib/event-deduplication.service.ts:315-319`). The fence releases buffered callbacks as above, with a bounded overflow that delivers early rather than dropping (`session-history-replayer.service.ts:457-481,528-549`). **Additional loss:** the resync initializer and history finalizer erase the old streaming state (`tab-manager.service.ts:2533-2547,2005-2015`), and the lost `generating` state leaves the tab `loaded` until another `turn_state` arrives. A snapshot without `sessionId` would also depend on the active tab lookup (`chat-message-handler.service.ts:533-535,545-548`), but this coordinator includes a session ID when `publish` received one (`chat-stream-delivery-coordinator.service.ts:118-120,226-230`).

## Other causes found

- The resync path changes the tab from `resuming` to `loaded` even while the backend turn can still run. Without a fresh `generating` event, it does not restore the streaming status (`libs/frontend/chat-state/src/lib/tab-manager.service.ts:2005-2015,1433-1455`). This is an additional state symptom, independent of the missing root node.
- A history record can be projected under the JSONL line UUID, while the live message ID comes from the stream; the replay chooses `msg.uuid` for its assistant message ID (`libs/backend/agent-sdk/src/lib/helpers/history/session-replay.service.ts:215-229`). Whether these IDs match for the affected SDK turn needs a captured transcript/live event pair. Do not assume persisted content always repairs the live bucket.

## Fix constraints

- The delivery tail is capped at 256 events and 512 KiB; overflow clears the **entire** tail and ignores later hidden events until reveal (`libs/backend/rpc-handlers/src/lib/chat/streaming/chat-stream-delivery-coordinator.service.ts:22-24,203-218`). Reveal emits either events or `resyncRequired`, never both (`:220-248`).
- Targeted resync sends `chat:resume` with `historyPage`, Electron `ptahUiFence: true`, and no `activate` (`libs/frontend/chat/src/lib/services/chat-store/session-loader.service.ts:855-867`). The response is a page from the JSONL-derived event list; it does not include a live-tail snapshot (`libs/backend/rpc-handlers/src/lib/chat/session/chat-session.service.ts:945-950,1074-1092`).
- Replay fences live chunks only while loading and releases them in order; a fix must preserve this ordering and handle the case where history lacks the current message start (`libs/frontend/chat/src/lib/services/chat-store/session-history-replayer.service.ts:143-179,209-228,457-481,528-549`).
- Rendering needs a `message_start` keyed to the same message ID as subsequent deltas (`libs/frontend/chat-streaming/src/lib/accumulator-core.service.ts:248-284,297-312`; `libs/frontend/chat-execution-tree/src/lib/builders/message-node.fn.ts:27-36,67-76`).

## Decisions

| Decision | Options | Evidence | Reversible |
| --- | --- | --- | --- |
| How to preserve a live message across hidden-tail overflow | Preserve a minimal live message anchor; reconstruct a live snapshot on reveal; or merge live state with the JSONL resync | Tail overflow removes the start and JSONL history is a separate source (`chat-stream-delivery-coordinator.service.ts:203-248`; `chat-session.service.ts:945-950,1074-1092`) | Yes; no implementation chosen here |
| How to restore liveness after targeted resync | Carry forward live turn state; request a current turn-state snapshot; or emit a fresh generating revision | Replay sets `loaded`; only generating `turn_state` sets `streaming` (`tab-manager.service.ts:2005-2015,1433-1455`) | Yes; no implementation chosen here |
