# Research Report - TASK_2026_707

## Question

- Decision this supports: How should Ptah diagnose and handle an Antigravity CLI headless turn that wrote files but ends with `result.status: ERROR` and process exit 1: treat it as a CLI failure, change a flag/version, or override the status from apparent work?
- Question: What public evidence explains this outcome, especially when the log contains one retried `503 UNAVAILABLE`?
- Bounds: Read-only web and adapter review. No `agy` run beyond `agy --version`; no private log inspection or reproduction. Gemini CLI reports are comparisons, not proof of shared code or identical behavior.

## Summary

**Best answer (medium confidence):** A completed file write is compatible with a later failed model/agent step; the final `result` is the documented terminal outcome, so an `ERROR` and nonzero exit should remain a failure. The one logged 503 is a plausible trigger, but a `retrying` log line alone does **not** establish that a recovered request poisoned the final status: Antigravity's changelog says transient 503s are retried in process while preserving completed tool outputs, and an unrecovered 503 should surface an error. The decisive missing evidence is the final `result.error`, any `AGY_ERROR` stderr line, and the model-attempt sequence after the observed retry. [Headless protocol](https://antigravity.google/docs/cli/headless/); [Antigravity CLI v1.2.1 notes](https://antigravity.google/docs/changelog?tab=cli&version=1.2.1); [Antigravity CLI v1.2.6 notes](https://antigravity.google/docs/changelog?tab=cli&version=1.2.6).

## Installed version vs source versions

`agy --version` returned **1.4.3** on this machine (run once, 2026-10-20). The official changelog currently labels **v1.4.0 (2026-10-16)** latest and lists no v1.4.3 entry, so there is no public evidence here that upgrading the installed binary would fix this symptom. The retry, structured error, and headless exit behavior cited above were announced in **v1.2.1, v1.2.6, v1.2.10, v1.2.13**—all older than 1.4.3. The direct Antigravity capacity report used **1.3.5**; Gemini CLI issues used a separate `gemini` CLI and cannot be version-compared with `agy`. [Official changelog](https://antigravity.google/docs/changelog?tab=cli); [Antigravity issue #1246](https://github.com/google-antigravity/antigravity-cli/issues/1246); [Gemini issue #27230](https://github.com/google-gemini/gemini-cli/issues/27230).

## Disagreements

- **Headless timeout default:** the undated [guide](https://antigravity.google/docs/cli/headless/#flag-reference) says 5 minutes; dated [v1.2.6 notes](https://antigravity.google/docs/changelog?tab=cli&version=1.2.6) say unlimited unless explicitly set. Use the later release note for 1.4.3, while Ptah's explicit `3600s` controls its own runs. The local `PRINT_TIMEOUT` comment still states the old default (`antigravity-cli.adapter.ts:93`).
- **Retry log versus terminal failure:** [v1.2.1 notes](https://antigravity.google/docs/changelog?tab=cli&version=1.2.1) and [issue #1246](https://github.com/google-antigravity/antigravity-cli/issues/1246) show that logged 503 attempts can be retried without discarding earlier file/tool output. The user's failed-run correlation remains meaningful but does not prove the one retry caused the final `ERROR` or that it recovered. Need the final error and later log entries to decide.
- **Exit code:** [v1.2.6](https://antigravity.google/docs/changelog?tab=cli&version=1.2.6) documents exit 3 for terminal agent/model errors, whereas the observed failure exits 1. This may be a different path, a difference in stream-input operation, or a regression; none is established. Ptah also converts a non-success result to its own turn code 1 (`antigravity-cli.adapter.ts:1009`).

## Local consequences and recommended next step

1. In `libs/backend/cli-agent-runtime/src/lib/cli-agents/cli-adapters/antigravity-cli.adapter.ts`, add optional `error` to `AgyResultSchema` and use it in `handleResult`; preserve `status`, raw child process exit, and any `AGY_ERROR` stderr line separately. The public protocol explicitly supplies `error`, while the current code uses only `response` or a generic message. [Official envelope](https://antigravity.google/docs/cli/headless/#handle-exit-codes-and-errors); local `:159-169`, `:843-860`, `:1000-1014`, `:1116-1127`.
2. For one existing failed long run, compare timestamps of the 503 retry, any subsequent successful model response or failed attempt, the final `result.error`, `AGY_ERROR`, and the process exit. Redact credentials, prompts, file contents and trace identifiers before sharing. This is the smallest experiment that separates exhausted retry, a later independent failure, a timeout, and a false terminal-status bug. [Retry behavior](https://antigravity.google/docs/changelog?tab=cli&version=1.2.1); [error contract](https://antigravity.google/docs/cli/headless/#handle-exit-codes-and-errors).
3. Keep `ERROR` as failure even if files exist. If a later policy retries coding turns, resume using the returned `conversation_id` and an explicit request to assess remaining work, rather than blindly replaying the original prompt; the protocol supports `--conversation`. This is a proposed safety policy, not a documented fix for the observed failure. [Continuation docs](https://antigravity.google/docs/cli/headless/#continue-a-conversation).

## Decisions

- **Recommendation, not architecture decision:** prioritize preserving `result.error` and differentiating adapter turn code from child exit. Options were flag/version changes and overriding terminal failure. Evidence is the documented result envelope, the already explicit local timeout, and the absence of a public 1.4.3 fix. Reversible: yes, this is an additive diagnostic change.
- **Evidence handling:** treat the one-503 correlation as a hypothesis, not a proven cause. The public changelog and direct Antigravity issue both show retries can precede successful work. Reversible: yes, update the conclusion when a full failed capture is available.

## Open questions

- What are the exact final `result.error` and stderr `AGY_ERROR` payload for the failed run? The current adapter discards the former; those fields should name the failure path. [Official headless guide](https://antigravity.google/docs/cli/headless/#handle-exit-codes-and-errors).
- Did the request following the logged `retrying` line succeed, exhaust retries, or fail later at a different step? The log sample described in the task lacks that sequence. [Official retry notes](https://antigravity.google/docs/changelog?tab=cli&version=1.2.1).
- Does `agy` 1.4.3 intentionally use exit 1 in `--input-format stream-json` for agent/model failure, despite the v1.2.6 headless exit-3 note? The cited public documents do not settle this combination. [v1.2.6 notes](https://antigravity.google/docs/changelog?tab=cli&version=1.2.6); [stream-input docs](https://antigravity.google/docs/cli/headless/#stream-prompts-from-stdin).
- No verified public report found of a **successfully recovered** 503 alone causing Antigravity or Gemini CLI to mark an otherwise successful turn `ERROR`; public Gemini retry issues describe noisy retry output or stale partial text, not this terminal-status transition. [Gemini CLI #27230](https://github.com/google-gemini/gemini-cli/issues/27230); [Gemini CLI #7428](https://github.com/google-gemini/gemini-cli/issues/7428).
