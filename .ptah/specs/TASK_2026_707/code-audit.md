## C. Session and usage data

- Current dashboard presets are 1/2/3/7/14 days, with a 200-session cap (`libs/frontend/dashboard/src/lib/services/session-analytics-state.service.ts:83-114`). It calls `session:list` with workspace and `since`, then `session:stats-batch` in 20-ID pages with `[since,until)` range (`:394-419`, `:435-465`; `libs/shared/src/lib/types/rpc/rpc-session.types.ts:481-501`). `session:list` supplies session metadata; the stats RPC returns one `SessionStatsEntry` per ID, not dated usage points.
- The stats DTO contains session ID, primary model, four disjoint token classes (uncached input, output, cache read, cache creation), total/known cost, per-model token/cost rows, CLI agent names and pricing coverage (`rpc-session.types.ts:359-428`). It has no provider field, per-day series, cost-source category, or per-event rows. The frontend projection further drops per-model cache read/write fields (`session-analytics-state.service.ts:540-567`). Aggregate totals sum priced session estimates and token classes (`:223-295`); partially priced sums are lower bounds (`libs/frontend/dashboard/src/lib/models/session-analytics.models.ts:76-103`).
- Source transcripts are JSONL parent and subagent files, located by workspace (`libs/backend/agent-sdk/src/lib/session-stats/session-stats-reader.service.ts:123-166`, `:213-273`). Its ledger projects each usage record's timestamp, model, input, output, cache-read and cache-creation counters (`libs/backend/agent-sdk/src/lib/session-stats/session-usage-ledger.ts:20-32`, `:188-225`). The range aggregator filters these timestamps and excludes untimestamped usage as partial coverage (`session-usage-aggregator.ts:161-171`, `:215-234`). No reasoning-token counter is in that ledger projection (`session-usage-ledger.ts:80-91`, `:188-225`). The metadata store may be SQLite-backed, but the measured token data used here comes from JSONL, not a ready-made daily SQLite fact table (`session-stats-reader.service.ts:123-166`, `:262-273`).
- Model prices exist in the shared rate card (`libs/shared/src/lib/utils/pricing.utils.ts:18-64`, `:122-158`, `:221`, `libs/shared/src/lib/providers/provider-registry.ts:22`, `:121-126`). The reader looks up `findModelPricing` (`session-stats-reader.service.ts:27-40`) and the aggregator computes model cost from all four token classes; missing prices yield `null` and `pricingCoverage` full/partial/none (`session-usage-aggregator.ts:252-299`). Costs use the *current* rate card, so historical estimates may change when rates change (`libs/frontend/dashboard/src/lib/models/session-analytics.models.ts:27-39`).
- The dashboard counts CLI agent names but explicitly excludes their spend (`session-analytics-state.service.ts:65-74`, `:267-273`; `analytics-card.component.html:128-133`). Its transcript stats pipeline is Claude SDK session accounting; Codex, OpenCode, Grok, Antigravity and Ptah CLI lane usage are not fed into this cost aggregate. `scripts/agent-usage/lane-metrics.ts:4-23`, `:42-43` is an offline measurement vocabulary for Codex/OpenCode/Claude and has lane-detection limits, not a dashboard RPC or all-provider collector.
- **Feasibility:** day × model for Claude transcript usage is derivable without new capture by grouping dated ledger records and applying the rate card, but the current RPC aggregates the date away. Day × provider × model across all requested providers cannot be made complete from this RPC or existing ledger alone. Extending 7/30/90-day reporting also needs revised range/UI constraints and pagination beyond the 200 most recent sessions; otherwise totals are knowingly partial (`analytics-card.component.html:92-96`). This is an inference from the cited data path.

## Decisions

- **Audit interpretation:** Treat plan quota and token-cost analytics as separate measurements. Evidence: independent stores/components (`dashboard-grid.component.html:81-87`; `plan-limits.store.ts:1-15`; `session-analytics-state.service.ts:394-465`). Reversible: yes. This is a reporting boundary, not an architecture decision.
- **Cost wording:** Call current totals estimates/lower bounds. Evidence: current-rate-card calculation and partial pricing semantics (`session-usage-aggregator.ts:252-299`; `session-analytics.models.ts:27-39`, `:76-103`). Reversible: yes.

## Open questions

- Should the requested dashboard cover *all* CLI lane sessions and subscription accounts, or only usage with reliable token-priced cost? Existing stats exclude CLI spend (`session-analytics-state.service.ts:65-74`).
- Which source can expose Ollama website session/weekly percentages and reset timestamps to this host? The current authenticated `/api/usage` reader validates only request count (`ollama-cloud-plan-usage.reader.ts:35-43`, `:127-154`).
- Should a Grok row represent default grok.com subscription quota, standalone xAI API usage, or both? Current reader intentionally selects only default CLI login (`grok-account-plan-usage.reader.ts:63-117`).
- What does “raw token cost” mean for subscription-covered or provider-free usage: model-rate equivalent, account billed charge, or both? Existing rate-card accounting and plan quota do not establish a single billable-cost meaning (`session-usage-aggregator.ts:252-299`; `plan-usage.service.ts:155-168`).
