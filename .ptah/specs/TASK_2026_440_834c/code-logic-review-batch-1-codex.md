## Findings

1. **Serious — A same-second failed backup can delete an already validated backup at the colliding destination.** `compactIso()` removes milliseconds, so every pre-migration or reset backup started within the same second receives the same filename (`libs/backend/persistence-sqlite/src/lib/backup.service.ts:97-103,228-237`). The worker marks the destination as its artifact before calling `source.backup()`, then unconditionally removes that destination if copying, permission restriction, or validation throws (`libs/backend/persistence-sqlite/src/lib/integrity/integrity-worker-protocol.ts:609-620,654-656`). It does not distinguish a file that existed before this attempt. Concrete failure scenario: a small database produces a valid pre-migration backup, then another runner/service instance starts a second pre-migration backup during the same second; the second attempt reuses the validated file's path and fails after entering the copy path. Cleanup deletes the validated backup, the host returns `null`, and migration proceeds without rotation—so the failed attempt has shrunk the archive even though the non-null rotation gate is correct. Cross-process callers are not protected by the service instance's promise queue. The new rotation specs use distinct timestamps and therefore do not catch this (`libs/backend/persistence-sqlite/src/lib/backup.service.spec.ts:638-678,698-718`). Use a collision-proof destination (for example, timestamp plus random/monotonic suffix), or preserve/atomically replace a pre-existing destination and only delete artifacts owned by the failed attempt; add a regression spec with a pre-existing valid file at the computed destination.

## Disagreements with the prior review

The prior review's approval relies on the statement that `compactIso()` produces a "strictly increasing string across calls" under normal clock behaviour. That is false: milliseconds are explicitly stripped (`backup.service.ts:97-103`), so calls within one second produce identical paths (`backup.service.ts:228-237`). Rotation still cannot select the just-written successful artifact for deletion—the colliding names are one filesystem entry, and newest-first selection keeps it—but failure cleanup can delete the earlier validated artifact as described in Finding 1. Therefore I disagree with the prior review's conclusion that same-second ordering presents no material backup-safety defect.

I agree with the prior review that the new `CLAUDE.md` wording overstates current call-site adoption of `KEEP_BY_KIND`; I did not duplicate that documentation-only issue as a behavioural finding.
