# Batch 4c cross-side review — round 1

**Verdict: REVISE.** Static review only; checks were running elsewhere.

## Defects

1. **A restored tab URL can be discarded before its workspace tabs load** — `libs/frontend/chat/src/lib/services/chat-tab-route-sync.service.ts:85-92`. `TabManagerService` synchronously loads the panel's legacy key in its constructor (`tab-manager.service.ts:637-658,2759-2775`), but workspace tabs load only on the later `switchWorkspace` call (`tab-workspace-partition.service.ts:193-226`). `App.handleInitialView` can settle a restored `/chat/B` before the initial `workspace:switch` RPC. If B exists in the workspace's stored tabs but is absent from the currently loaded `tabs()`, this listener treats B as unknown and replaces the URL with `/chat/A` or bare `/chat`; `SurfaceRoutePersistence` also writes that correction. If the workspace's stored active tab is A while the saved URL addresses B, the later workspace switch leaves A active and B's deep link is permanently lost. This violates the intended restore of a valid, existing `:tabId`. Reconcile after workspace state is ready, or defer unknown-ID correction during boot and prove the ordering with a boot integration case.

2. **An in-flight correction can undo a newer tab switch** — `libs/frontend/chat/src/lib/services/chat-tab-route-sync.service.ts:92,99-103,136-141`. Start with active A and a settled bare `/chat`, which starts a replace to `/chat/A`. Before that replace settles, the user switches to existing tab B. The effect sees `pendingSurface() === 'chat'` and skips writing B. When `/chat/A` settles, `followUrl` sees a valid A and calls `switchTab(A)`, reversing the user's B selection. The same sequence follows an invalid URL correction. The tests settle each navigation before changing tabs (`chat-tab-route-sync.service.spec.ts:186-203`) and do not exercise this interleaving. A corrective navigation must not let its stale URL become a new selection after active tab state changes.

## Notes

- The first-segment chat guard is sound for pre-boot `/`: `currentSurface()` falls back to chat there. `navigateToSurface(..., { replaceUrl: true })` preserves the intended replacement semantics and handles failures; the services barrel export reaches the public API. The root subscription uses `DestroyRef`, and the root effect tracks only `activeTabId()`.
- In the ordinary settled case, URL-to-tab and tab-to-URL converge without a loop; unknown/invalid IDs correct without an error. The interleaving in defect 2 breaks the claimed at-most-one-correction behaviour across a user tab change.
- Each bare `/chat` completion causes a second `NavigationEnd` and therefore a second `ptahRoute` write. The last write wins when both land; defect 1 explains why the early write matters during boot.
- The report's duplicate-history example is not the normal reselect path: `AppStateManager.setCurrentView` returns early when chat is current, navigation is idle, and the current workspace owns the settled surface (`app-state.service.ts:995-1005`). An unowned/pending edge may still issue bare `/chat`; that should be covered where this path is handled. The ordinary case does not justify a separate 4c defect.
- The service specs use the real Router and memory location, so they genuinely exercise route settlement and replacement. `webview-routing.spec.ts` checks the route shape and round trip; neither suite covers the boot ordering or the in-flight correction race. No tests, lint, typecheck, Nx, or build were run for this review.
