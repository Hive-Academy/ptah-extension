# Host restore plan — TASK_2026_524_1125

## Findings

- **Verified** — AC3 and AC4 remain open: the task calls for a persisted logical URL and a VS Code panel serializer (`.ptah/specs/TASK_2026_524_1125/context.md:78-84`; `completion-validation.md:17-18,32-34`). The current Angular boot reads only `window.initialView` or `ptahConfig.initialView` and navigates to a surface (`apps/ptah-extension-webview/src/app/app.ts:131-149`).
- **Verified** — The editor panel is created only in `AngularWebviewProvider.createPanel`, with view type `ptah-angular-spa`, a unique `ptah.panel.<uuid>` runtime ID, `enableScripts`, `retainContextWhenHidden`, and three local resource roots (`apps/ptah-extension-vscode/src/providers/angular-webview.provider.ts:106-133`). Creation registers it with `WebviewManager`, a per-panel event queue, a message listener, HTML, and disposal cleanup (`angular-webview.provider.ts:134-178`). Commands for ordinary, analytics, and orchestra-canvas panels all call this method (`apps/ptah-extension-vscode/src/core/ptah-extension.ts:131-177`). The development reload replaces each panel's HTML without carrying `initialView` (`angular-webview.provider.ts:308-326`), so AC3 must rely on webview state.
- **Verified** — The sidebar is a `WebviewView`, registered as `ptah.main` with `retainContextWhenHidden` (`ptah-extension.ts:121-130`) and initialized in `resolveWebviewView` with options, HTML, and a message listener (`angular-webview.provider.ts:61-99`). `WebviewPanelSerializer` applies to **panels**, not `WebviewView` (`node_modules/@types/vscode/index.d.ts:10179-10224,10227-10230`). The sidebar's `setState`/`getState` handles recreated content; retention handles ordinary hide/show. No sidebar serializer is required.
- **Verified** — A second panel path exists: `SetupWizardService` uses view type `ptah.setupWizard` and supplies a completion/reload custom message handler (`libs/backend/agent-generation/src/lib/services/setup-wizard.service.ts:30-43,72-96`). `WizardWebviewLifecycleService` creates it through `WebviewManager.createWebviewPanel`, supplies options and custom handlers, and hardcodes `initialView: 'setup-wizard'` (`libs/backend/agent-generation/src/lib/services/wizard/webview-lifecycle.service.ts:109-155`). The manager's creation path also owns its panel map and lifecycle listeners (`libs/backend/vscode-core/src/api-wrappers/webview-manager.ts:94-146`). Merely registering a serializer for this view type would leave that runtime ownership and custom handler unbound.
- **Verified** — `WebviewHtmlGenerator` validates `initialView` against the shared accepted surface list (`apps/ptah-extension-vscode/src/services/webview-html-generator.ts:125-135`), then injects `window.ptahConfig.initialView`, panel/session metadata, and `window.ptahPreviousState = vscode.getState()` before Angular starts (`webview-html-generator.ts:446-482`). `initialView` is a surface ID, not a URL. `VSCodeService.setState(key,value)` merges one key into the existing state object, and `getState(key)` reads that key (`libs/frontend/core/src/lib/services/vscode.service.ts:215-248`).
- **Verified** — VS Code gives `deserializeWebviewPanel(panel,state)` the JSON state last written with webview `setState`; the serializer must take ownership, restore HTML, and reattach events (`node_modules/@types/vscode/index.d.ts:10189-10224`). Registration requires the matching `onWebviewPanel:<viewType>` activation event and must occur during activation (`index.d.ts:11734-11746`). The extension manifest currently has `onView:ptah.main` and command activations but no panel activation (`apps/ptah-extension-vscode/package.json:37-44`), and the provider is resolved and registered during extension initialization (`apps/ptah-extension-vscode/src/core/ptah-extension.ts:58-64,111-130`).
- **Verified** — Electron loads a fresh renderer document from `renderer/index.html` (`apps/ptah-electron/src/activation/post-window.ts:90-100`). Its preload exposes `window.vscode.getState/setState` through IPC and sets `ptahConfig.initialView` from startup config (`apps/ptah-electron/src/preload.ts:24-47`). IPC reads/writes `webview-state` through `WORKSPACE_STATE_STORAGE` (`apps/ptah-electron/src/ipc/ipc-bridge.ts:125-132,510-543`), whose workspace adapter uses `ElectronStateStorage` (`apps/ptah-electron/src/di/phase-1-infra.ts:143-162`). The store persists to disk (`libs/backend/platform-electron/src/implementations/electron-state-storage.ts:303-319`). Thus a reload/restart does **not** preserve the renderer instance, but persisted state is available to a new instance. Once the webview-side boot reads and validates the route state, Electron needs no host change for route restoration. An immediate reload after asynchronous `set-state` could precede the disk update; verify that boundary in the webview work.
- **Verified** — The app-level DI composition root registers `AngularWebviewProvider` as a singleton in phase 4 (`apps/ptah-extension-vscode/src/di/phase-4-app.ts:23-47`). The extension already resolves that instance and owns registration disposables (`ptah-extension.ts:58-64,121-130,214-222`). This is the existing seam for serializer registration; a second host service and DI token would add no distinct responsibility.

## Host contract

- **Agreed webview state.** The webview batch 4a defines and tests `WEBVIEW_ROUTE_STATE_KEY = 'ptahRoute'`, `WebviewRouteState { v: 1, route: string, seed: string | null, panelId: string }`, and `parseWebviewRouteState(record: unknown)` in `@ptah-extension/shared` (`implementation-plan.md:419-439,885-911`). The whole `vscode.setState` value remains a mergeable record; the webview writes `ptahRoute` after each settled navigation and leaves other keys intact (`vscode.service.ts:238-249`; `implementation-plan.md:912-914`). The parser bounds and validates the route, seed and panel ID; the host uses that parser, then `isSurfaceRouteId` for any title derived from the first route segment. **Dependency:** host H1 follows webview 4a, which produces the shared contract.
- **Restore precedence.** `deserializeWebviewPanel(panel, state)` omits the generator's optional `initialView` option, so generated `window.ptahConfig.initialView` is `null` (`webview-html-generator.ts:39-55,464-466`), even when the saved route is valid. The host never injects a restored full URL or a route-derived surface as `initialView`; it may derive a title only. The webview reads its own `getState()` and applies the seed rule: DevTools override, then a new host deep link whose value differs from saved `seed`, then saved route, then host surface/chat fallback (`implementation-plan.md:197-225,915-923`). Passing a route-derived `initialView` would cause the saved `/chat/:tabId` or `/thoth/:tab` path to be discarded.
- **Panel ownership and ID.** VS Code supplies the panel; the provider adopts it and reapplies the same options, HTML, queue, message listener, ready flush, broadcast and disposal wiring as `createPanel` (`angular-webview.provider.ts:106-178`). Reuse `state.ptahRoute.panelId` only after `parseWebviewRouteState(state)` succeeds, the ID matches `^ptah\.panel\.[0-9a-f-]{36}$`, and no live panel holds it. Otherwise allocate `ptah.panel.${crypto.randomUUID()}`. This ID is a validated hint, not a trusted workspace or session input. `TabManagerService` keys editor-panel tabs by `panelId` (`tab-manager.service.ts:637-658`); always allocating a new ID would lose the chat tab after restart. Keep the supplied state record untouched so the restored webview can read its route and seed. Invalid state still restores a usable default panel.
- **Wizard boundary.** `ptah.setupWizard` is a distinct panel type and workflow. This AC4 host slice restores `ptah-angular-spa` panels. A wizard serializer requires a separate, real adoption path in `WebviewManager` and recreation of the wizard's custom completion handler and session semantics (`setup-wizard.service.ts:72-96`; `webview-lifecycle.service.ts:109-155`); the generic provider must not impersonate it. The wizard route key can be persisted for content reload, but that alone does not make the wizard workflow restart-safe.

## Risks

- VS Code revival timing: registration must complete during activation before VS Code first reveals a serialized panel (`node_modules/@types/vscode/index.d.ts:10205-10224,11734-11746`). If initialization fails before `registerWebviews`, revival cannot proceed; the existing initialization catch rethrows (`apps/ptah-extension-vscode/src/core/ptah-extension.ts:58-73`).
- A panel's `setState` is independent of Angular's in-memory URL. If the companion webview work does not persist after navigation and seed before first navigation, the host can restore an empty/default surface (`apps/ptah-extension-webview/src/app/app.ts:131-149`; `webview-html-generator.ts:479-482`).
- The wizard has its own manager, custom handler, and setup session. Restoring only its HTML would show a panel with broken behavior; keep the separate view type out of the generic serializer until wizard adoption and session reconstruction are specified (`libs/backend/agent-generation/src/lib/services/setup-wizard.service.ts:72-96`; `libs/backend/vscode-core/src/api-wrappers/webview-manager.ts:94-146`).
- Electron `setState` uses asynchronous IPC while `getState` is synchronous (`apps/ptah-electron/src/preload.ts:28-33`; `ipc/ipc-bridge.ts:520-543`). Normal restart should read persisted workspace state; a crash or immediate reload after a write may expose the previous route. The companion webview test should cover expected ordering/fallback.
