# Code Logic Review — `TASK_2026_452_097c`

## Verdict

**FAIL** — F1's own fallback is correct for the two frontend-driven chat paths, but the change also touches an unnamed-session path the task never enumerated (`gateway-chat-bridge`), and there it silently trades a date-stamped metadata name plus SDK auto-title generation for a fixed literal `'New Chat'` on every session, undocumented in `implementation-notes.md` and unverified by any spec.

## Defects

### 1. Gateway sessions lose date-based identity and permanent SDK auto-title, unacknowledged by the task

- File: `libs/backend/agent-sdk/src/lib/sdk-agent-adapter.ts:678-687` combined with `libs/backend/gateway-chat-bridge/src/lib/gateway-chat-bridge.ts:754-764`
- Scenario: `GatewayChatBridge.startNew` calls `startChatSession({ tabId, prompt, projectPath, workspaceId, model, includePartialMessages, permissionLevel, mcpServerRunning, enhancedPromptsContent })` — no `name` and no `sessionName` field, for every first inbound message on every Telegram/Discord/Slack binding (confirmed: no `name`-setting call site exists anywhere in `gateway-chat-bridge.ts`). Before this change, `config?.name || 'Session ${new Date().toLocaleDateString()}'` gave each gateway session a date-stamped metadata name, and `sessionConfig.sessionName` was left `undefined` (old conditional spread), so `Options.title` was never set and the SDK was free to auto-generate a real summary title (`sdk.d.ts:2830-2833`: "provided… skips automatic title generation"). After this change, `resolvedSessionName` unconditionally resolves to the literal `'New Chat'` (`sdk-agent-adapter.ts:678-682`), which now feeds all three surfaces: `SessionMetadataStore.create` receives the literal `'New Chat'` instead of a date, `--name`'s role becomes `new-chat` instead of the previous `chat`, and `Options.title` is now **always** set (`sdk-query-options-builder.ts:1010-1012`, `!resumeSessionId && sessionConfig.sessionName` is now always truthy for this caller), which per the SDK contract permanently skips auto-title generation for every gateway conversation.
- Impact: every gateway-originated session — potentially many per day across bindings — now shows identically as `New Chat` in `SessionMetadataStore`-backed surfaces (including the peer picker's `ptahTitle`, per the prior commit `e428db275`), where before at least the creation date gave weak distinguishing signal. This is a real instance of the exact class of blast-radius regression the review brief anticipated ("a gateway/cron session that used to be distinguishable by date") and is not discussed anywhere in `implementation-notes.md`, which only reasons about the two frontend-driven `chat:start` paths.
- Severity: **Serious**. Not data loss, but a directly user-visible regression on a caller class the implementer never enumerated or tested — `agent-rpc.handlers.resume-parent-session.spec.ts` and `sdk-agent-adapter.spec.ts` cover only the CLI-resume and frontend-name paths.
- Fix: `resolvedSessionName` should fall back to something distinguishable (e.g. keep `Session ${date}` for metadata, or synthesize a name from the conversation/binding id) when there is genuinely no caller-supplied name at all, or `gateway-chat-bridge.ts` should pass an explicit per-conversation name (e.g. platform + conversation id) instead of relying on the adapter's generic default.

### 2. New `sdk-query-options-builder.spec.ts` test is redundant, not a regression net for the claimed behavior

- File: `libs/backend/agent-sdk/src/lib/helpers/sdk-query-options-builder.spec.ts:381-387`
- Scenario: the added test passes the literal `sessionName: 'New Chat'` straight into `buildWith(...)` and asserts `opts.title === 'New Chat'` and `opts.extraArgs?.['name'] === 'ptah-ws-new-chat-tab-fi'`. This exercises nothing the adjacent test at line 376-379 (`sessionName: 'Fix the Billing Bug!'` → `opts.title` equals it) does not already cover — the builder treats `'New Chat'` as an ordinary string, identically to any other name. `implementation-notes.md` describes this test as proving "the resolved fallback reaches both the raw SDK title and the slugged registry name," but the actual fallback **resolution** happens in `sdk-agent-adapter.ts:678-682`, a different file this spec never touches; the builder never sees an unresolved/blank name in this test.
- Severity: **Minor** (test-coverage clarity, not a logic defect — the resolution logic itself is genuinely covered by `sdk-agent-adapter.spec.ts:964-1030`).

### Prior defects

**Defect 1 (gateway date-identity + permanent auto-title suppression) — RESOLVED.**
The fix splits the two name surfaces the doc comment always said were distinct. `sdk-agent-adapter.ts:678-689` now computes `callerSuppliedName` (nonblank `sessionName`/`name` only, else `undefined`) and `resolvedSessionName` (`callerSuppliedName ?? \`Session ${date}\``, restoring the pre-diff date fallback). `resolvedSessionName` feeds `sessionConfig.sessionName` (metadata + `--name` role, `sdk-query-options-builder.ts:861` for `buildExtraArgs`) unconditionally, but the new `sessionTitle` field is spread in **only** when `callerSuppliedName` exists (`sdk-agent-adapter.ts:689`). `SdkQueryOptionsBuilder` was updated to read `sessionConfig.sessionTitle` instead of `sessionConfig.sessionName` for `Options.title` (`sdk-query-options-builder.ts:1010-1012`). For the gateway caller (no name at all): metadata/`--name` get the date-stamped fallback exactly as before this task, `sessionTitle` is never set, `Options.title` is never set, and the SDK auto-title path runs exactly as it did before this task — confirmed by the new builder spec at `sdk-query-options-builder.spec.ts:384-390`, which asserts `opts.title` is `undefined` and `extraArgs['name']` is the date-derived slug for a `sessionName`-only input. Confirmed by grep across `libs/` that no other call site reads `sessionConfig.sessionName` expecting it to be absent for an unnamed session, or sets `Options.title` from anything but `sessionTitle` (only two producers: `sdk-agent-adapter.ts:689`; only one consumer: `sdk-query-options-builder.ts:1010-1012`). Resume (`sdk-agent-adapter.ts:822-827`, untouched) still reads only `config?.sessionName ?? resumedName` and is unaffected — no caller sets `config.sessionName` ahead of a resume, and `Options.title` is a documented no-op on resume regardless (`sdk.d.ts:2831`: "Has no effect on the persisted title when resuming an existing session").

**Defect 2 (redundant/tautological builder test) — RESOLVED.**
The test at `sdk-query-options-builder.spec.ts:381-386` was extended to a genuine equivalence case (supplies both `sessionName` and `sessionTitle`, proving they compose independently), and the new test at `sdk-query-options-builder.spec.ts:388-393` (`'builds --name from a fallback without suppressing SDK auto-title generation'`) is the actual regression net this defect asked for: it supplies `sessionName` alone and asserts `opts.title` is `undefined` while `extraArgs['name']` is still slugified — the exact contract Defect 1's fix depends on, at the builder layer.

**Defect 3 / open mismatch (interactive Ptah-CLI child metadata title) — RESOLVED.**
`ChatPtahCliService` now records the caller's nonblank conversation `name` on the session entry (`chat-ptah-cli.service.ts:172-174`) and exposes it via `getSessionName(tabId)` (`chat-ptah-cli.service.ts:314-315`). `ChatStreamBroadcaster` reads it with the SAME key the entry is stored under — `tabId` (`chat-stream-broadcaster.service.ts:208-210`; `ptahCliSessions` is never re-keyed to the SDK session id, confirmed — only a separate map, `ptahCliSdkSessionIds`, tracks that), so the entry is guaranteed available at the point `createChild` is called on the first distinguishing stream event. The registry `--name` role for this interactive path is built from the same `name` (`chat-ptah-cli.service.ts:158`, threaded into `startChatSession`), so metadata and `--name` now share one source of truth, closing the mismatch the peer picker's "renamed" hint depended on. Verified the slug match holds for the fallback shape too: `slugifyLikeSessionName('Session 9/15/2026')` → `session-9-15-2026`, identical to what `buildSessionName({ role: 'Session 9/15/2026', ... })` would slugify for `--name`'s role component, so a freshly spawned fallback-named session does not spuriously trip the "renamed" hint. New specs at `chat-ptah-cli.service.spec.ts:203-223` and `chat-stream-broadcaster.service.spec.ts:174-192` exercise this with concrete assertions, not tautologies.

Write-order check against `session-metadata-store.ts` (both `create()` and `createChild()` can now race for the SAME session id on this path — `SdkAgentAdapter`'s own `sessionIdCallback` calls `create()` at `sdk-agent-adapter.ts:722-725` for every session including Ptah-CLI-backed ones, while the broadcaster independently calls `createChild()` for the same id when `isPtahCliSession`):

Name consistent, `isChildSession` preserved — confirmed correct.
- **`create` wins first, `createChild` runs second**: `createChild()` (`session-metadata-store.ts:1166-1184`) unconditionally builds and saves a **fresh** record with `isChildSession: true` and the same `name` (now consistent thanks to this fix), so name and `isChildSession` are both correct in the final record — the specific claim under review holds. However, `_saveInternal`'s merge (`session-metadata-store.ts:456-471`) only carries over `isChildSession`/`cliSessions`/`workingDirectory`/`resumableSdkSubagents` from the prior record, not `createdAt`/`totalCost`/`totalTokens`, so this order silently resets those three fields to zero/`now`. **This is pre-existing behavior in `createChild()` itself, which this diff does not touch** (only the `sessionName` value passed to it changed) — recorded for visibility, not counted as a defect introduced by this task, and not blocking.
