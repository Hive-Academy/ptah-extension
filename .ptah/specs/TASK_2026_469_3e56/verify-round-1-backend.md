## New defects

### 1. A terminal candidate that starts and exits at once reports success

- Severity: **moderate**
- Files: `libs/backend/platform-core/src/utils/terminal-launch.ts:239-242`; `libs/backend/platform-core/src/interfaces/process-spawner.interface.ts:58-66`
- Failure scenario: the `whenSpawned` port resolves a pid as soon as the spawning thread reports one, and it carries no exit signal (`process-spawner.interface.ts:58-66`). A broken `WindowsApps\wt.exe` app-alias stub — the exact machine state defect 6 named — starts the stub process, prints its error, and exits. `spawnTerminalProcess` sees `pid !== null` and returns (terminal-launch.ts:239-242). The RPC answers `{ success: true }`, the `cmd.exe` fallback one candidate lower is never tried, and the user sees no terminal and no error.
- Fix: after a successful spawn, wait a short bounded window (for example 500 ms) for the first `exit` event on the handle. A candidate that exits inside the window counts as failed and the loop continues; one that stays alive passes. Detached GUI launchers survive this window; the stub does not.

### 2. No fallback on non-Windows hosts

- Severity: **minor**
- File: `libs/backend/platform-core/src/utils/terminal-launch.ts:181`
- Failure scenario: the follow-on candidate list is built only under `platform === 'win32'` (terminal-launch.ts:181). On Linux, detection picks `/usr/bin/x-terminal-emulator` — a Debian alternatives link that can exist while the real emulator is broken. The spawn fails, `candidatePaths` holds only the detected path, and `gnome-terminal`, `konsole`, `xfce4-terminal` and `xterm` (all listed at terminal-launch.ts:34-40) are never tried. The user gets "Could not launch the requested editor." on a machine with four working terminals.
- Fix: build the follow-on list from `terminalExecutableCandidates` for every platform, not only `win32`.

### 3. The handler-level fallback cannot run in production

- Severity: **minor**
- Files: `libs/backend/rpc-handlers/src/lib/handlers/editor-rpc.handlers.ts:185-194`; `libs/backend/platform-core/src/utils/editor-launcher-detection.ts:261-262, 358-360`; `libs/backend/rpc-handlers/src/lib/handlers/editor-rpc.handlers.spec.ts:173-199`
- Failure scenario: `openDetected` retries by looping over detected candidates with the same id (editor-rpc.handlers.ts:186-194). But detection returns at most ONE target per id — the pass picks the first available candidate per definition (editor-launcher-detection.ts:261-262) and the installed pass excludes ids already found on PATH (editor-launcher-detection.ts:360). So the loop always runs a single iteration. The spec feeds two `terminal` targets into a mocked `detect` (editor-rpc.handlers.spec.ts:184) — an input production cannot produce. The loop is harmless, but the fix report lists it as defect-6 coverage, and it covers nothing. The operative fallback is inside `spawnTerminalProcess`, and it is Windows-only (new defect 2).
- Fix: either delete the loop and its unreachable-input spec, or make detection return every available terminal candidate so the loop has real work. Prefer the former; keep the retry in `spawnTerminalProcess` where the candidate order lives.

### 4. The fallback spec exercises a call shape no production adapter uses

- Severity: **minor**
- Files: `libs/backend/platform-core/src/utils/terminal-launch.spec.ts:190-201`; `libs/backend/platform-electron/src/implementations/electron-editor-launcher.ts:55-60`; `libs/backend/platform-cli/src/implementations/cli-editor-launcher.ts:58-63`
- Failure scenario: `spawnTerminalProcess` takes a `candidates` argument, and the new test passes one explicitly. Both production adapters call it without `candidates`, so the tested path (an explicit ordered list) is never exercised in the product; production always enters the internal list-building branch (terminal-launch.ts:176-202), whose Windows edge cases — the `targetIndex === -1` case when the detected path does not appear in the rebuilt list (terminal-launch.ts:193-200) — have no test.
- Fix: add a test that calls `spawnTerminalProcess` without `candidates` on `win32` with a detected `wt.exe` path, and assert the spawn attempts include the `cmd.exe` fallback.
