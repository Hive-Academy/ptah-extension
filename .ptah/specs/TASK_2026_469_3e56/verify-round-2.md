# Verify Round 2 — `TASK_2026_469_3e56`

## Verdict: REVISE

Ten of the eleven round-2 defects are fixed for their originally reported scenarios. Backend defect 2 remains incomplete when PATH resolves a terminal outside the built-in candidate list. The final review found three merge-blocking regressions in the replacement logic: a successful Windows Terminal handoff can be mistaken for a broken app alias and launch a second terminal, concurrent same-workspace `git:info` calls can publish an older response over a newer one, and a superseded stash-list reload can report success and overwrite the newer reload's failure. Follow-ups cover an over-eager confirmation reset, the unconditional 1.5-second terminal-launch delay, and loss of the actual asynchronous spawn error.

Tests, lint, and typecheck were not rerun, as requested. “Would fail without fix” below evaluates the assertion itself, not the reported green run.

## New findings

### 1. MERGE-BLOCKING — a successful Windows Terminal handoff is classified as a broken alias and falls through to `cmd.exe`

- **File:** `libs/backend/platform-core/src/utils/terminal-launch.ts:253-262,284-293,325-334`
- **Failure scenario:** every path under `Microsoft\WindowsApps` is marked `knownStub`, and _any_ exit from that path—including exit code 0—returns `failed = true`. A healthy `wt.exe` app execution alias is allowed to hand the request to Windows Terminal and return successfully; when it does so inside 1.5 seconds, Ptah treats the successful handoff as failure and launches the next candidate, normally `cmd.exe`. The user can receive both the requested Windows Terminal window/tab and an unexpected Command Prompt. The test at `terminal-launch.spec.ts:405-428` encodes the unsafe assumption by representing both a broken alias and a healthy handoff as the same `{ exitCode: 0 }` outcome.
- **Fix:** do not infer package health from the `WindowsApps` pathname plus a zero exit. Preserve non-zero exits and `error` events as failures, but distinguish a broken zero-exit alias using observable failure evidence (for example its diagnostic stderr or a separate alias/package health probe) before falling back. Add a test for a successful zero-exit `wt.exe` handoff that asserts no `cmd.exe` launch.

### 2. MERGE-BLOCKING — an older same-workspace `git:info` response can overwrite newer data

- **File:** `libs/frontend/git-ui/src/lib/services/git-status.service.ts:327-359`
- **Failure scenario:** two refreshes for workspace A get generations 1 and 2. Generation 2 resolves first and publishes the newest branch/files. Generation 1 then resolves; because the active workspace is still A, it passes the only response guard at line 340 and calls `applyGitInfo` at line 353, overwriting the newer snapshot. The generation is checked only in `finally`, where it controls the loading flag, not data publication. The round-2 test at `git-status.service.spec.ts:306-335` covers A→B loading ownership but never resolves two same-workspace responses out of order or inspects their data.
- **Fix:** before applying a response, require both `generation === this.fetchGeneration` and the captured workspace to remain active. Add an out-of-order same-workspace test whose two responses contain different branch/file data and assert the newer invocation wins.

### 3. MERGE-BLOCKING — a superseded stash-list reload reports success and can overwrite a newer failure

- **File:** `libs/frontend/git-ui/src/lib/services/git-stash.service.ts:117-178,314-334`
- **Failure scenario:** `loadListFor()` returns success when its generation has been superseded. A mutation recovery path can therefore treat an obsolete reload as applied and restore its fallback or mutation error over the real error published by the newer reload.
- **Fix:** return a distinct superseded result and restore fallback errors only when the reload response was actually applied. Add an out-of-order test where the newer failed reload completes before the superseded reload settles.

### 4. FOLLOW-UP — an equivalent stash-list refresh cancels an in-progress drop confirmation

- **File:** `libs/frontend/git-ui/src/lib/stash/stash-popover.component.ts:193-203`
- **Failure scenario:** the linked-signal source creates a new array whenever its dependencies recompute. If an in-flight list refresh returns a new entries array containing the same hashes in the same order, the joined hash string is unchanged but the outer source array has new identity, so `computation: () => null` resets the confirmation. A user who clicked Drop while the opening refresh was still completing sees the confirmation disappear even though workspace and stash identity did not change. The named test changes the hash (`stash-popover.component.spec.ts:147-163`) and does not cover a semantically identical list emission.
- **Fix:** return a stable primitive source key (for example open state + workspace + joined hashes), or supply structural equality for the source. Add a test that replaces `entries` with new objects carrying the same hashes and asserts the confirmation remains.

### 5. FOLLOW-UP — every healthy long-lived terminal launch is delayed by the full 1.5-second probe

- **File:** `libs/backend/platform-core/src/utils/terminal-launch.ts:162-170,252-260,311-335`
- **Failure scenario:** a healthy terminal that stays alive has no success event after `whenSpawned`; the only success path is the timer at line 329. Consequently `openWorkspace` and the RPC remain pending for 1.5 seconds on every such launch, on every platform. The test at `terminal-launch.spec.ts:328-341` confirms that a healthy live process cannot resolve until the full window advances.
- **Fix:** scope the expensive probe to candidates that need it (not every built-in terminal), or use a shorter measured early-failure window and an explicit Windows alias health signal. Pin the expected latency so a future probe cannot silently add seconds to every good launch.

### 6. FOLLOW-UP — asynchronous spawn errors are discarded before the host log can record them

- **File:** `libs/backend/platform-core/src/utils/terminal-launch.ts:252-267,311-334`; `libs/backend/rpc-handlers/src/lib/handlers/editor-rpc.handlers.ts:192-207`
- **Failure scenario:** `onError` ignores its `Error` argument and reduces it to `true`. The candidate loop then stores a generic `Failed to launch Terminal` error. If all candidates fail, the RPC handler logs only that generic replacement, despite its stated contract that the real error stays in the host log. An actionable `EACCES`, missing DLL, or worker failure is lost, while the renderer still gets the same fixed safe copy.
- **Fix:** have the probe return a discriminated result carrying the original error, retain the last concrete failure across candidates, and throw that for the handler to log. Keep the fixed renderer message unchanged. Extend the asynchronous-error test to assert the final logged/thrown error retains its original message, not merely that the next mock was called.
