## Description

### Origin

Discovered while filing the TASK_2026_174 security follow-ups. Two carriers filed
in one turn — `TASK_2026_188` (gateway `yolo`) and `TASK_2026_189` (sandbox
`process` reachability) — were silently overwritten by a concurrent orchestrator
session that allocated the same IDs for its own tasks (an `@IsOptional()` sweep
and a `prisma.config.ts` `.env` fix). The lost carriers had to be re-filed as
`TASK_2026_192` / `193`. This task fixes the allocator so that cannot recur.

### The defect

ID allocation (per `.claude/skills/orchestration/references/task-tracking.md`
§"Generating a New Task ID") is: scan all `TASK_YYYY_*` folders → take the
highest `NNN` → +1 → create the folder. That is a **read-then-write with no
mutual exclusion**. When two orchestrator sessions run against the same
`.ptah/specs` concurrently:

1. Both scan and see the same highest (e.g. 187).
2. Both pick 188.
3. Both `mkdir` + write `task.md` — the second write clobbers the first.

Three things make the clobber silent rather than caught:

- **`registry.md` is not a guard.** It is a generated, derived, read-only view
  (`GENERATED by Ptah tasks:generateRegistry — DO NOT HAND-EDIT`), and the spec
  explicitly allocates from a folder scan, _not_ from it. It is also badly stale
  (last regenerated `2026-07-14`; lists only `157`/`159` while the tree holds
  folders up to `194`), so deriving IDs from it would collide with everything
  created since — worse, not better. Even a _fresh_ registry read-then-write has
  the identical race.
- **`.ptah/specs` is gitignored** (`.gitignore:128 .ptah/**`), so git provides no
  conflict/merge safety net — both sessions write the same untracked local dir.
- **The write path does not detect collision.** Folder creation via `mkdir -p`
  ignores an existing dir, and `task.md` is written with an overwriting write —
  zero collision detection at the moment of writing.

### Why it matters

Silent data loss of task carriers. A user asks to file N follow-ups; some are
overwritten by a concurrent session with no error, and the board simply shows
someone else's task under that ID. The problem is structural: sequential
highest-plus-one allocation assumes a single writer, and the project now runs
parallel agent sessions.

### The chosen approach

**Atomic reservation + no-overwrite guard**, keeping the tidy sequential IDs.

1. **Reserve atomically via `mkdir`.** `mkdir` (fail-if-exists, NOT `mkdir -p`)
   is atomic on POSIX and Windows and fails `EEXIST` if the folder already
   exists. Allocation becomes: pick candidate `NNN`; attempt the exclusive
   `mkdir`; on failure, increment and retry. The folder creation itself is the
   lock — a concurrent grab of the same id becomes a retry, not a clobber. (This
   task's own carrier was allocated this way as a proof of concept — see the
   reservation loop used to reserve `TASK_2026_194`.)
2. **Refuse to overwrite an existing `task.md`.** The carrier write must fail
   loudly if `task.md` already exists in the target folder, so any residual race
   surfaces as an error instead of silent loss.
3. **Regenerate the stale `registry.md`.** Separate from the race fix, but the
   current registry is 4 weeks stale and misleading; regenerate it and confirm
   the generator is wired to run (or is invoked) after carrier creation.

### Scope / investigation

- The allocation rule lives as **prose instructions** in the orchestration skill
  (`.claude/skills/orchestration/references/task-tracking.md` and `SKILL.md`).
  Update the instruction to the atomic-reserve algorithm so every orchestrator
  session follows it.
- Determine whether allocation ALSO happens in **code** — check `libs/backend/
task-specs` and any `tasks:*` RPC / CLI (`tasks:generateRegistry`, a
  create-task path). If a programmatic allocator exists, centralize the atomic
  reservation there so the agent flow and any code flow share one implementation
  rather than duplicating the algorithm in prose.
- Decide whether to keep sequential IDs (favoured; requires the atomic reserve)
  or move to collision-free IDs (timestamp/short-uuid suffix — no global counter,
  but loses the readable numbering the board relies on). Default: keep sequential.

### Acceptance criteria

1. Concurrent allocation cannot clobber: two allocations racing for the same
   `NNN` resolve to two distinct IDs, proven by a test that simulates the race
   (e.g. parallel reserve calls, or a reserve that sees the folder pre-created).
2. Writing a carrier into a folder that already has a `task.md` fails loudly
   rather than overwriting.
3. The allocation instruction in the orchestration skill reflects the atomic
   reserve; if a code allocator exists, it implements it and the skill points at
   it.
4. `registry.md` is regenerated and current (or the generator is confirmed to run
   post-creation), and no longer used as an allocation input.
