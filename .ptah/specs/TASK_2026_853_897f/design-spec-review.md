Verdict: REVISE

## Findings

1. **Blocking — §2, no-workspace install state; prototype lines 133–136.** The spec automatically selects **All workspaces** when no folder is open. Clicking the primary install button then writes globally without the user choosing global, contrary to Phase D AC4 and decision #3. Keep the workspace choice visible but unavailable, disable install, and require an explicit selection of **All workspaces** before enabling it. Show the no-workspace error only for an attempted workspace install, not beside an available global choice.

2. **Blocking — §3, migration notice; prototype lines 185–192.** “Switched them off everywhere,” “each workspace only shows what you install in it,” and “They are switched off” are false for retained workspace `.claude/skills` content. Phase D migration AC2 and the scope exclusions preserve git-tracked or edited workspace files, which can remain available in their own workspace. The prototype even names the repo-committed `impeccable`, `typesafe-ai`, and `frontend-design` skills as skipped items. Distinguish retired global sources from retained local files in the notice and counts; say retained files may still be available in their workspace. Use hypothetical Ptah-managed examples instead of repo-authored skills in installed rows.

3. **Serious — §1 tool dependency table; prototype line 84.** The default-off RemoteTrigger row says it hides `schedule (cloud routines)`, while decisions.md #11 and Phase A's scheduling decision require `/schedule` to stay listed by default. Remove that dependency claim and keep the scheduling skill listed, or leave RemoteTrigger enabled pending architect evidence that the supported schedule flow does not need it. The final dependency map must govern the row.

4. **Serious — §1 dependency rule, lines 65–66.** Omitting a skill from group 2 whenever a tool owns it removes the individual re-enable control required for *every* terminal-only default-off skill by Phase B AC7. `workflow-authoring` is both a Phase B candidate and a prototype tool dependency. Specify independent tool and skill states: keep each architect-listed terminal-only skill row with its own checkbox, show when a disabled dependency prevents effective availability, and explain that both controls must be on. Do not make turning on a tool silently enable an independently default-off skill.

5. **Serious — §2 shared scope control; prototype lines 123–128 and 149–154.** Each `role="radiogroup"` has `aria-describedby` but no accessible name; the adjacent `fieldset` legend does not name that nested ARIA group. Remove the redundant `role="radiogroup"` and use the native fieldset/legend, or add `aria-labelledby` pointing to the legend. Then verify arrow-key behavior, focus visibility, and announced names in the actual DaisyUI implementation. The static prototype cannot establish the claimed focus behavior of `join`/`btn` classes.

6. **Moderate — §1 success state, line 59.** The promised “Turned on/off … It will …” Undo toast is not produced by the cited `SettingsSaveFeedbackService.saveGeneric`: its current success copy is always `Saved {label}.` (service lines 151–183). Either use that existing copy and describe what Undo restores, or explicitly scope a shared feedback-service change and verify it does not alter other settings toasts. The fixed failure copy is consistent with the matrix.

7. **Moderate — §2 MCP targets, lines 97–102.** The global-scope state checks only four targets although the current directory checks all seven (`mcp-directory-browser.component.ts:37–45,356–358`) and Phase D AC6 says global targets are written as today. The spec also resets user target choices on every scope change. Preserve the current seven-target default for an explicitly selected global scope unless the product decision changes, and preserve compatible user choices when switching scopes; clear only home targets when returning to workspace scope.

8. **Moderate — §1 and prototype state presentation.** The static page displays the normal table, an empty account-skill state, load and save errors, and a success toast simultaneously; loading and saving are prose only (prototype lines 71–115). These are understandable as examples but do not visually establish the disabled/loading layout or focus return after an error. Add distinct prototype states or a compact state gallery with actual disabled controls and skeleton rows. The skill toggle's accessible name should be stable (for example “docx skill”), because “Turn on the docx skill” remains its announced name when checked; the checked state already conveys on/off.

9. **Minor — §1 savings copy, line 36; prototype line 75.** “Hidden by default” describes the initial policy, but `{N}` is defined as the sum of items *currently* off. After a toggle, that heading becomes inaccurate. Use “Currently hidden: about {N} tokens…” and make clear the figure is an estimate for a new session. Keep the real values dependent on the architect's measured list.

## Lane-introduced constraints

- Global-only tool and skill toggles (§ Decisions 1) are a designer product choice, not a requirement: Phase A AC3 and B AC7 require persistence, not global scope. The choice is reasonable for app-level prefix policy if made explicit; retain the note and record it for product approval.
- One inline migration card at the top of chat (§ Decisions 4) is a placement choice. P-4 requires one notice after migration completion, but not this location or dismissal behavior. Ensure it appears even when completion occurs before a chat view exists, persists across app restarts until seen, and does not dismiss merely by opening Marketplace unless that is intended.
- Unchecking home-config targets after the user explicitly chooses global (§ Decisions 5) changes the current seven-target default without a requirement authorizing that global behavior. Phase D P-2 only changes workspace-scope preselection.
- Reverse conversion (“Make workspace-only”) and automatic target reset on scope changes (§2) go beyond Phase D AC2's required conversion to global. The reverse action needs defined behavior for existing copies and home-config entries before it is promised.
- “At most two significant digits” for token estimates and a zero/zero suppression rule (§ Decisions 6; §3) are presentation choices. The requirements ask for approximate cost and one notice after migration completion; suppressing a zero/zero notice can hide completion when all items were safely retired without deletion. State how retired-only items are counted before adopting the rule.

## Decisions

1. **Global built-in toggles — qualified agreement.** Their note is clear and the settings matrix pattern fits; persistence does not itself prove global scope. Carry this as an explicit product decision.
2. **Checkbox means available — agree.** This matches the existing MCP namespace matrix (`mcp-port-config.component.ts:124–159`), subject to the independent skill/dependency fix in Finding 4.
3. **Install-scope radio choice — agree after Finding 5.** A mutually exclusive choice is clear; no-workspace handling must require an explicit global choice (Finding 1).
4. **Inline migration card — qualified agreement.** A persistent card can carry counts and reinstall steps better than the existing eight-second settings toast. Its copy must distinguish local retained files (Finding 2), and its placement must still guarantee the notice is seen.
5. **Disabled home-config targets in workspace scope — agree.** It makes Phase D AC5–6 visible. Global preselection and scope-switch reset need correction (Finding 7).
6. **Approximate token costs — agree as placeholders only.** The prototype's values cannot validate savings; final rows and costs must follow the architect's measured list. The rendered dark and light prototype looked readable, and the stated border-contrast failures are plausible because text carries the meaning. Actual DaisyUI and axe were not checked.
7. **Scheduling tools stay enabled — agree.** This follows decisions.md #11 and Phase A; remove the conflicting RemoteTrigger/schedule example (Finding 3).

Review evidence: requirements and decisions, the three named existing components, settings feedback service, and the in-workspace prototype rendered in both themes through Ptah browser navigation and screenshots. No build, tests, axe run, or state-changing git action was performed. Skill inventory found `frontend-design`, but this CLI exposed no skill invocation mechanism, so its instructions could not be loaded.
