## Findings

1. **Blocking — Phase D migration, lines 203–217.** AC1 requires removal of every `ptah-skillssh-*` root and the MCP intent records, while AC2 and the stated safety rule allow deletion only for Ptah-written, manifest-tracked content. A matching root name or intent record is insufficient proof: `SkillsShSourceRootService.listRoots` accepts roots without metadata (`skills-sh-source-root.service.ts:243-253,381-399`), its metadata has no content hash, and `McpIntentStore` records intent rather than ownership of current config entries (`mcp-intent-store.ts:1-20,47-68`). The managed manifest covers workspace-relative target entries (`managed-manifest.ts:40-69`), not these home roots. **Fix:** make AC1 conditional on a specified ownership record and current-content match for every file or config entry removed; skip and log unverifiable, edited or foreign content. Define how legacy global roots can be retired without deleting untracked files. AC3 must require the same proof before removing a home-config entry.

2. **Serious — Phase B, lines 105–130.** The requirement promises that each default-hidden Claude Code built-in skill can be re-enabled in settings, but the acceptance criteria specify controls only for account-synced skills (AC2). AC1 tests hiding, not restoration, persistence or the control list for terminal-only built-ins. **Fix:** add an acceptance criterion that lists every selected built-in skill in the settings section and verifies toggling one on makes it appear in a fresh session, persists across restart, and leaves unrelated skills hidden.

3. **Serious — Phase A, lines 65–75 and 82–98; Risks line 255.** ScheduleWakeup and Cron tools are candidates for default-off even though the document says they drive `sleeping`. Source confirms `sessionCrons.length > 0` selects `sleeping` (`session-turn-state.registry.ts:359-368,411-412`); the UI has a ScheduleWakeup renderer. The risk mitigation says QA runs `/loop` with defaults, while Phase B may hide `/loop` by default. **Fix:** require the architect to decide explicitly whether scheduling is a supported default flow, keep its tools enabled if it is, and test the live state transition and `/loop` only in a configuration where the needed skill and tools are enabled. Retain the replay criterion separately.

4. **Serious — Non-functional compatibility, lines 237–239.** “Each project the change touches” is narrower than `CLAUDE.md:36-43`, which requires typecheck and tests for every host project dependent on a changed shared library. **Fix:** require scoped `npm run verify -- -p A,B` for changed projects and dependent host projects, including Electron, VS Code and TUI where applicable; record the selected project set. Keep build and workspace-wide targets out of verification.

5. **Moderate — Measurement, lines 227–236.** The 5k/3k/2k/0.5k phase targets can be restated later by the architect without a fixed decision rule, so they are not stable acceptance thresholds. “Before and after” also does not specify the before sample count, whether phases are measured against their immediately preceding state, or whether all token figures use the same api-request-shape field. **Fix:** define one measurement procedure with at least three fresh main and three subagent sessions on each side of each phase, the exact token field, a controlled workspace/settings baseline and the immediately preceding phase as comparator. Treat any lower target as a documented requirements revision before implementation, not an automatic pass.

6. **Moderate — Phase D scope and open questions, lines 163–199 and 262–266.** The user asked to understand plugin and subagent-template delivery (`context.md:17-18`), but no criterion requires an evidence-backed map of the bundled plugin, external plugin, generated-agent and per-workspace mirror paths, or confirmation of which need scope changes. The agent-leak question is already answerable from `context.md:102-114`: generated agents go into the workspace and are mirrored under a workspace-labelled user path. Home-config MCP targets are also identified as global by nature (`context.md:148-151`). **Fix:** require the architecture plan to record these paths and its scope decision for each surface, resolve both open questions there, and test only the surfaces that need behavior changes.

7. **Minor — Phase D migration, lines 218–221.** AC4 says a partial failure leaves “remaining items untouched” yet also retries on next start; it does not specify whether already removed items are counted again or how the one notice in AC5 behaves across retries. **Fix:** specify per-item idempotence, completion marker only after all eligible items finish or are safely skipped, and one completion notice with a deduplicated count.
