# PR #879 Code Logic Review — `d990147cc`

## Verdict

**REVISE — 4/10.** The commit handles the ordinary corrupt-file, per-target failure, and no-folder cases, but it still permits a malformed intent to disappear, can delete a root taken global during a migration run, and can retire skills before a failed migration records any ledger. Those data-loss and capability-loss paths put it below the 5–6 band; the implemented guards and passing-path coverage keep it above the foundational 1–2 band.

Source review only. No tests, builds, or `npm run verify` were run, as requested. Scoped `ptah_get_diagnostics` was attempted for the five production files; its TypeScript check timed out after 45 seconds and reported all five unchecked.

## New defects introduced by this commit

1. **Blocking — a corrupt MCP intent can retire skills even though migration fails.** `libs/backend/rpc-handlers/src/lib/install-scope/install-scope-migration.service.ts:528-544` writes the skills.sh retired registry *before* `mcpIntents.listRetired()`. With a corrupt existing intent file, the new throw stops the run at `:473-481` before `discoveredAt` or a ledger is written, but the newly retired registry remains. A user starts Electron with a legacy global skills.sh root and corrupt MCP intent: the skill disappears from installed/loadable lists (`skills-sh-source-root.service.ts:979-1006`) with no completed migration notice. Read/validate the MCP intent before changing the registry, or persist an explicit recoverable step before retirement.

2. **Serious — one unreadable metadata file blocks all unrelated migration work indefinitely.** The new per-root metadata read at `libs/backend/rpc-handlers/src/lib/install-scope/install-scope-migration.service.ts:585-596` propagates EACCES/EIO from `readRootMetadata` (`skills-sh-source-root.ts:345-360`). `runOnce` then returns `failed` at `:473-481` before recording discovery, processing other roots, or visiting workspaces. A permanently permission-denied metadata file leaves every other legacy install unmigrated on every launch, whereas the existing ownership proof can classify an unreadable root as unproven and keep it (`skills-sh-source-root.ts:386-395`). Record that root as kept/failed and continue independent items while preserving the no-delete rule.

3. **Serious — a malformed live registry can erase pending ledger work and still complete migration.** `libs/backend/rpc-handlers/src/lib/install-scope/install-scope-migration.service.ts:607-617` maps malformed JSON to `null`; `:677-690,701-716` interprets that as every undecided root being intentionally unretired and drops its ledger item. If the registry is truncated between discovery and the next run, undecided roots and clones are skipped, and `finish` can set `completedAt` (`:1096-1118`). Restoring the registry later cannot resume cleanup because completed runs return early (`:457-461`). Treat malformed registry as an incomplete/read-failed run, distinct from a valid empty registry or an intentional cleared mark.

4. **Serious — a failed clone row can make migration permanently incomplete after its root is unretired.** The new `releaseUnretiredRoot` clears only the root path failure at `libs/backend/rpc-handlers/src/lib/install-scope/install-scope-migration.service.ts:701-715`; an existing failed clone path remains. The reaper filters out that now-global root at `:799-807`, so it can never clear the clone failure, while `itemOutcome` stays undefined (`:209-215`) and `finish` stays `incomplete` (`:1096-1107`). This occurs when clone removal failed on the first run and the user then selects Make global or reinstalls globally. Close or reclassify outstanding clone failures when releasing a root, without deleting its current clones.

5. **Moderate — the ledger continues to report a root as retired after it is taken back.** `libs/backend/rpc-handlers/src/lib/install-scope/install-scope-migration.service.ts:679-685` skips the new release path for any root already marked `onDisk` or removed. A first run can mark a legacy v1 root `onDisk`; the user then makes it global, clearing its live retired mark, while another workspace keeps migration incomplete. On retry the item remains `retired: true`, so notice counts at `:218-233` claim the re-enabled root is retired. Apply the live-state correction to every ledger item, while retaining paths already removed or kept.

6. **Minor — the proven-delete specs now rely on a contradictory fixture.** `libs/backend/rpc-handlers/src/lib/install-scope/install-scope-migration.service.spec.ts:136-161` changed the default metadata from `scope: 'global'` to `scope: 'workspace'` while writing the fixture under the global plugins directory. The proof/deletion assertions at `:390-404` therefore exercise a workspace-scoped record in a global location, not a realistic pre-migration global install. This hides whether the migration safely handles actual v1 global roots (kept on disk) and v2 global roots (skipped) in the same delete-path suite. Use explicit fixture scopes in those cases and name the synthetic proof case as such.

## Five logic questions

1. **Silent failure:** The invalid v2 bucket is dropped without error (`mcp-intent-store.ts:623-635`); malformed live registry can drop ledger items and still mark completion (`install-scope-migration.service.ts:607-617,701-716,1117-1118`).
2. **Unexpected user action:** Make global or a global reinstall during deletion can still lose the root after the registry snapshot (`install-scope-migration.service.ts:678-688,728-734`); doing so after an `onDisk` decision leaves misleading notice counts (`:679-685,218-233`).
3. **Wrong input answer:** A v2 server bucket without any config passes the permissive schema and becomes no server (`mcp-intent-store.ts:99-107,623-635`).
4. **Dependency failure:** EACCES on one metadata file aborts every other migration item (`install-scope-migration.service.ts:585-596,473-481`); a corrupt MCP intent fails after the skills registry has already changed (`:528-544`).
5. **Missing requirement:** The migration needs a recoverable transaction boundary across intent validation, registry retirement, ledger writes, and concurrent global reinstall (`install-scope-migration.service.ts:528-557,677-734`). The current rules specify per-item proof but do not settle this cross-step ownership race.

## Decisions

- **Intent semantics:** Interpret “schema-invalid” in ruling #84 as including a v2 bucket without either bucket config or the legacy top-level fallback. Options were to drop it or reject it; rejecting preserves the file and prevents reconcile from planning removals. Evidence: `mcp-intent-store.ts:99-107,613-638`. Reversible: yes, by tightening validation before normalization.
- **Live registry semantics:** A valid registry with a cleared mark is evidence of user opt-in; malformed JSON is not. Options were to release all pending items or pause the migration; pausing preserves ledger and ownership evidence. Evidence: `install-scope-migration.service.ts:607-617,701-716`. Reversible: yes.
- **Scope and verification:** Reviewed only commit `d990147cc` and its relevant callers; no source files were edited. The requested diagnostics tool was unavailable after its timeout, and CI remains the verification authority for this PR.
