1. **Serious — Environment digest accepts an added auth selector.** `libs/backend/agent-sdk/src/lib/helpers/claude-certified-launch.ts:178` (consumed at `:265`). Concrete input: build a certified environment from `{ ALL_PROXY: 'proxy\nANTHROPIC_API_KEY=fixture-key' }`. Change the actual environment to `ALL_PROXY='proxy'` and add a separate `ANTHROPIC_API_KEY='fixture-key'`, preserving every other entry. Both serialize to the same sorted newline-separated `key=value` text. The digests match, and `assertCertifiedLaunch` accepts the newly introduced credential selector. This is an encoding ambiguity, not a SHA-256 collision. I reproduced acceptance using the committed helper. The existing digest tests cover ordinary added keys but not embedded separators. **Fix:** compare actual non-policy key/value entries directly with `launch.env` at the boundary, in addition to the existing digest, so the approved digest representation need not change. Alternatively use an unambiguous canonical encoding consistently. Add regression cases for both boundaries proving that this environment transformation refuses and that neither extra credential selectors nor parent-managed keys can survive it.

2. **Serious — Settings can bypass certification through two accepted launch inputs.** `libs/backend/agent-sdk/src/lib/helpers/claude-certified-launch.ts:280`, with the incomplete `extraArgs` check at `:254`. Concrete inputs: (a) an otherwise valid bootstrap launch with `flagSettings='{"apiKeyHelper":"fixture-helper"}'` passes because the settings check runs only in final mode; (b) an otherwise valid final launch with no `flagSettings` and `extraArgs: { settings: '{"apiKeyHelper":"fixture-helper"}' }` passes because only `managed-settings` is rejected. I reproduced both acceptances. The installed SDK's argument builder copies `extraArgs`, overrides its `settings` entry only when the ordinary settings option is supplied, and emits those entries as CLI flags. Thus case (b) supplies an unchecked `--settings` tier. Empty `settingSources` does not remove this separately supplied flag tier. These guards therefore cannot establish the advertised absence of alternate credential settings. **Fix:** validate the effective settings tier in both modes; reject settings supplied through `extraArgs`, or normalize and validate them before comparison. Restrict other extra arguments that can replace certified launch inputs (such as setting sources) to prevent the same bypass pattern. Add bootstrap override/malformed-settings and `extraArgs.settings` regression cases, alongside the existing both-mode managed-settings cases.
