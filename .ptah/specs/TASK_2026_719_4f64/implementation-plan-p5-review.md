## Findings

1. **Blocking — The badge can display a success-looking partial count while the ambient read is loading or has failed.** Plan: Component specifications §7, `implementation-plan-p5.md:299`, and §14 at `:432`. The helper suppresses the badge for an unavailable/stale account snapshot, but otherwise counts signed-in named accounts even when the ambient view is checking, idle, locally failed, or ready with `unknown`. With two signed-in named accounts and a failed ambient read, the specified result is “2 connected”; D41 explicitly requires hiding the badge during loading or read failure (`decisions.md:251`). This is silent misleading output under the reviewer severity definition, not a cosmetic preference. The two reads are independent in §14 (`implementation-plan-p5.md:429`), and the actual account view only describes its own request (`libs/frontend/core/src/lib/services/provider-accounts-state.service.ts:44`, `:464`, `:489`). Require a ready, nonfailed ambient result as well as a ready, nonstale account snapshot before calculating the total. A successful `signed-out` result contributes zero; `unknown` must hide the badge. Add presentation/page tests with a positive named count for ambient idle, checking, transport failure, host unknown, signed-out and connected; assert recovery and pushed account-state changes. The display-only text, zero suppression, page read and drawer-close hooks otherwise match D41 (§14, `:427`–`:436`).

2. **Moderate — The batch verification lists omit hosts that depend on changed shared libraries.** Plan: B1–B3 at `implementation-plan-p5.md:575`, `:581`, `:590`, and F1–F7 at `:595`–`:623`. None includes `ptah-tui`; B1/B3 change shared types but omit `ptah-extension-webview`; the frontend batches omit `ptah-extension-vscode`. These are actual consumers: `apps/ptah-tui/src/hooks/use-chat.ts:4` imports shared, `apps/ptah-tui/src/transport/tui-webview-manager-adapter.ts:1` imports cli-engine, and `libs/backend/cli-engine/src/lib/container.ts:107` imports auth-providers. VS Code packages the webview (`apps/ptah-extension-vscode/project.json:101`); Electron also declares it (`apps/ptah-electron/project.json:7`). Root guidance requires dependent-host tests/typechecks even during Electron-first work (`CLAUDE.md:35`). Correct each scoped `npm run verify -- -t lint,test,typecheck -p ...` list and its claimed N using the dependency graph; include TUI for the backend/shared batches, the webview for shared-type batches, and VS Code for webview/core/chat changes. This is a required validation-plan gap, not evidence that those hosts already fail. No host feature work is requested.

3. **Moderate — Same-key single flight does not implement the promised one-child limit across environment changes.** Plan: Component specifications §4 steps 3–5, `implementation-plan-p5.md:192`, versus its quality promise at `:216` and Architecture-level quality requirements at `:468`. Start probe A, change the effective environment, then request B before A completes. The only join rule is for the same key; the receipt guard covers already-returned unclosed children, not the still-running A. The specified algorithm can therefore start B concurrently. A generation counter prevents old cache writes but does not bound children. The underlying command is a per-call owner with independent limits, not a global queue (`libs/backend/auth-providers/src/lib/accounts/claude-account-command.ts:286`, `:325`; limits at `:45`). Specify serialization or abort-and-await-close before starting a different-key probe, retaining receipt ownership on timeout. Add a deferred-command test for environment change during an active probe that asserts maximum active children, correct-key results, and ignored obsolete completion. Also remove the unsupported assertion that an existing flight started “at most milliseconds before” a refresh (`implementation-plan-p5.md:193`): it can have been running for seconds. State the intended refresh-while-running policy explicitly and test it.

4. **Moderate — Synthetic timestamps violate the completed-probe meaning of checkedAt.** Plan: Component specifications §4 step 4 (`implementation-plan-p5.md:194`) creates a new checkedAt while refusing to spawn because a previous child is unclosed; §6 (`:267`) fabricates the host-shaped timestamp on a frontend transport failure. Neither establishes when a host probe completed. The controlling contract requires that provenance (`design-spec-p5-review-r1.md:44`; `design-spec-p5.md:199`), and the command returns an unclosed-child receipt specifically when termination is unproved (`libs/backend/auth-providers/src/lib/accounts/claude-account-command.ts:290`). Keep local request failure/time separate from the host result. For a blocked read, preserve the completed failed attempt's timestamp rather than minting a new probe time; if no host result was received, render unknown without a purported host checkedAt. Add tests for repeated blocked reads and transport failure after an earlier connected result, asserting no fresh probe timestamp or stale positive result is manufactured. The plan already has `localFailure`, so this can be resolved without exposing additional host data.

## Five logic questions

1. **Silent failure:** a partial count remains visible after the ambient read fails (finding 1); synthetic checkedAt obscures whether a host check occurred (finding 4).
2. **Unexpected user action:** opening Accounts while a page probe is already running can join an older flight; changing the effective environment during it exposes the missing cross-key serialization (finding 3). Removal and moving focus during writes are explicitly protected by B-1/B-2.
3. **Wrong-answer input:** a positive named count plus ambient checking/unknown produces a badge contrary to D41 (finding 1). Omitted and missing named selections are correctly distinguished in the planned presentation tests (`implementation-plan-p5.md:303`).
4. **Dependency failure/timeout/shape:** the command/parser maps malformed output, timeout and failed certification to unknown (§§3–4, `implementation-plan-p5.md:171`, `:197`). Transport failure has a safe unknown state but incorrect timestamp provenance (finding 4). Runtime behavior and hostile payload tests have not been executed.
5. **Unspecified cases:** the cross-key in-flight policy and no-new-probe timestamp semantics need explicit contracts (findings 3–4). Verification must account for dependent hosts rather than treating Electron-first as a host exclusion (finding 2).
