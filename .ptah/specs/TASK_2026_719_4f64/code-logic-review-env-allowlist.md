# Settings env allowlist security review

Verdict: **REVISE**

Score: **6/10**. The separate settings classifier preserves the process-env boundary, but the list includes an executable selector and one key whose semantics remain unverified. These prevent a 7–8 (sound) rating. The shared, fail-closed classifier and unchanged launch-env checks distinguish this from a 3–4 implementation requiring structural rework.

## Part B — findings

1. **Serious — an executable selector is admitted as a safe tuning key.** `libs/backend/agent-sdk/src/lib/helpers/claude-certified-launch.ts:90`, `:171`, `:469`. `USE_BUILTIN_RIPGREP=0` changes execution from bundled ripgrep to system `rg`, according to the [official environment-variable reference](https://code.claude.com/docs/en/env-vars) and [official troubleshooting instructions](https://code.claude.com/docs/en/troubleshooting). A settings block containing this key is now classified `none`; the classifier checks names, not values. A project can also supply `PATH`, already permitted at `:15`, so the combined block can select a different executable through executable lookup. Exploitation depends on an attacker-controlled executable being reachable; no exploit was executed in this read-only review. Even without that condition, selecting a system helper directly violates the requested exclusion of keys that load executable helpers. The new key enables this behavior on a path that previously refused it. Remove it from the settings-safe list and pin rejection of both the key alone and its combination with `PATH`. The name-pattern test at `claude-certified-launch.spec.ts:231` cannot establish executable safety.

2. **Moderate — one admitted key lacks confirmed semantics.** `libs/backend/agent-sdk/src/lib/helpers/claude-certified-launch.ts:87` adds `DISABLE_NON_ESSENTIAL_MODEL_CALLS`, while `claude-certified-launch.spec.ts:257` positively accepts every list member. I could not confirm this key in the current [official environment reference](https://code.claude.com/docs/en/env-vars.md); the other 17 names have entries. The implementer describes it as suppressing flavor-text calls, but provides no version-pinned implementation evidence for the supported CLI build. This is an evidence gap, not a claim that the key redirects credentials. The explicit review contract says to flag keys that cannot be confirmed. Remove it pending confirmation, or provide a bounded inspection of its readers in the certified build showing that all values affect only non-auth behavior. A regex over the name is insufficient evidence.

## Five logic questions

1. **Silent failure:** a successful classification conceals the executable-selection change in finding 1 (`claude-certified-launch.ts:90`, `:469`).
2. **Unexpected user action:** opening a project with `USE_BUILTIN_RIPGREP=0` changes which search executable runs instead of refusing that configuration (`:90`).
3. **Wrong input accepted:** a block combining that key with `PATH` passes the same classifier; the name-only tests cannot detect the semantic violation (`:15`, `:171`; spec `:231`).
4. **Dependency failure:** unreadable, oversized or malformed settings refuse in `claude-auth-settings-scan.ts:256`; boundary scan failures refuse at `claude-route-certifier.ts:257`. No dependency-error swallowing or new catch was added here. CLI behavior for the unconfirmed key remains unknown.
5. **Unspecified requirement:** safe environment names need a version-specific semantic evidence policy, not only name-pattern exclusions. The certifier is version-bound (`claude-route-certifier.ts:256`), but the new list and tests do not record inspected CLI readers (`claude-certified-launch.ts:73`; spec `:231`).

## Decisions

- Accept D64's existing logger contract for this scoped review; options were demanding local guards or retaining the repository convention. Evidence is the existing unguarded refusal/cleanup calls above. Reversible; no source changed.
- Treat case-insensitive finite membership as satisfying the no-bypass intent, consistent with Windows environment semantics and the existing certified matcher. Exact-case-only matching was the alternative. Reversible; credential names still refuse.
- Require revision for executable selection and withhold confirmation for the undocumented key, rather than infer safety from their names. Removing the entries is reversible and preserves the requested `ENABLE_TOOL_SEARCH` use case. No decision to broaden executable authority is made by this review.
