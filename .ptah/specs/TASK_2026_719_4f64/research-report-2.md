## Summary

- The right repo is `github.com/pingdotgg/t3code` (confirmed with `gh repo view`, default branch `main`). It supports several Claude accounts as several **provider instances**, each with its own `CLAUDE_CONFIG_DIR`. It does NOT use separate HOME, `CLAUDE_CODE_OAUTH_TOKEN`, or `setup-token`. The user runs `CLAUDE_CONFIG_DIR=<dir> claude auth login` in a terminal themselves (`docs/user/providers-claude.md`).
- t3code does **no** policy/settings certification. It never checks `apiKeyHelper`, never strips ambient auth env, and does not set `CLAUDE_SECURESTORAGE_CONFIG_DIR`. Its only policy-adjacent code reads `<configDir>/remote-settings.json` and `<configDir>/settings.json` to decide whether "bypass permissions" may be offered. So t3code is evidence for the mechanism, not for R3.5 compliance.
- Anthropic documents the same mechanism officially: "Log in with multiple accounts ... give each account its own configuration directory ... `CLAUDE_CONFIG_DIR` ... Each directory has its own settings, session history, and claude.ai login" (docs `authentication`). This closes A-S1 for the CLI. Status: **proved** (docs + binary + t3code), with one residual caveat (see table).
- A-S12 is **proved**: the "parent" channel is the SDK `Options.managedSettings`, which the CLI receives as the `--managed-settings` flag. By default (`parentSettingsBehavior: "first-wins"`) it is dropped whenever any admin tier exists, and when merged it is filtered restrictive-only. Ptah can make A-S12 a hard invariant by never passing `--managed-settings` and never setting `CLAUDE_CODE_PROVIDER_MANAGED_BY_HOST`.
- A-S9 is **not provable as written, and the evidence says the plan's worry is real**: docs state the remote fetch is NOT blocking. Only a first interactive sign-in waits up to 5 seconds; "in any other startup ... Claude Code opens the session while the fetch continues, so a brief window passes before the settings load". Only an admin-set `forceRemoteSettingsRefresh: true` makes the CLI block. So no file-based check inside the child can prove the fetch has not taken effect first.
- Server-managed settings are documented for **Claude for Teams and Enterprise only**; eligible credentials are a Team/Enterprise OAuth login, `CLAUDE_CODE_OAUTH_TOKEN`, or a directly configured API key. `apiKeyHelper` output and Workload Identity Federation do not trigger the fetch. Whether a personal Pro/Max login performs a (empty) fetch is not stated by the docs (unknown). A Pro/Max account has no admin console to push settings from, so the practical risk is Team/Enterprise accounts.
- Dangerous interaction found: in non-interactive runs (`-p`, Agent SDK, VS Code chat panel), delivered settings that need approval (including `apiKeyHelper`, hooks, proxy/base-URL env) are **applied for that run without the dialog** (docs `server-managed-settings`, "A non-interactive run"). And `apiKeyHelper` outranks subscription OAuth in the credential order (docs `authentication`, "Authentication precedence", items 4 vs 7). So an org-pushed `apiKeyHelper` could run in Ptah's SDK child. This is the concrete R3.5 hazard; it only exists for accounts that belong to a Team/Enterprise org.
- Recommendation: close Gate 2 with a classification rule instead of a file-based proof (Option 1 below), and offer the user an explicit scope decision for org accounts (Option 3 as the default for them).

### Answers to the specific A-S9 questions

- **Which account types receive server-managed settings?** Documented: Claude for Teams and Claude for Enterprise (docs `server-managed-settings`, Note and Requirements). Personal Pro/Max: not documented as eligible; there is no admin console for them. A Console API key belongs to a separate Console org and does not receive claude.ai admin-console settings (same page, "Platform availability").
- **When fetched?** At startup, then hourly during active sessions (same page, "Fetch and caching behavior").
- **Blocking?** No, except (i) the up-to-5-second wait on a fresh interactive sign-in, (ii) when an admin sets `forceRemoteSettingsRefresh: true` (blocks, exits on failure; `claude auth` subcommands exempt), (iii) `managedMcpServers` waits up to 30 s before connecting MCP servers (v2.1.259+), (iv) Claude apps gateway sign-ins wait. Cached payloads apply immediately at startup (except the withheld env categories).
- **Can an env var or flag disable it without "suppressing managed policy"?** There is no documented opt-out. The documented skips are side effects of changing provider or base URL (`CLAUDE_CODE_USE_*`, non-default `ANTHROPIC_BASE_URL`), which also changes the account's billing path and is a policy bypass, so using them would violate R3.5's "never suppress managed policy". `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC` is documented for telemetry, updates and similar, and its row does not mention remote settings (not a supported control for this). `CLAUDE_CODE_REMOTE_SETTINGS_PATH` (binary only, undocumented in the pages I could read) replaces the fetch with a local file and so would also be a suppression; Ptah should strip it, never set it.

## Recommendation

Adopt Option 1 as the Gate 2 closure, with Option 3 as the default behaviour for class O (org) accounts in this release, and run the Option 2 experiment (a read-only `claude doctor` under a throwaway empty config dir, then, if the user permits, under their real second account) to decide whether org accounts can be enabled later without a waiver. Rationale: it is the only combination that meets R3.5 as written for every account, it uses evidence that is proved (A-S1, A-S12) or fails closed (A-S9), and it does not require Ptah to read credentials. Drop the plan's reliance on "cache or consent file absent means no remote policy"; the documentation contradicts it. This is a recommendation; the architect and the user decide scope (whether org accounts are in or out for the user's second account is a user question, since it changes the goal).

Decision for the user (not mine to make): is the second account a personal Pro/Max login or a Team/Enterprise seat? If personal, Option 1 delivers the goal now.
