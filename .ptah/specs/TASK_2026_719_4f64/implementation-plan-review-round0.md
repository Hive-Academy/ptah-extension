## Findings

1. **Blocking — Components 1–3, 5, 8; lines 101–114, 154–170, 282–287, 404–412: certification does not describe the environment/settings context actually executed.** Auth commands use a baseline allowlist, while SDK children retain everything outside selected prefixes. Bootstrap explicitly keeps `cwd: tmpdir()` and `settingSources: []` (evidence table line 45), whereas admission scans the workspace and final execution loads project/local settings. The certification record contains only executable path, version and identity, so consumers cannot verify the promised context equality. The proposed pattern also narrows the existing `CLOUD_` family to `CLOUD_ML`; the research's explicitly named selectors are covered, but arbitrary cloud keys are not. Managed registry policy is checked only by the user in E4, with no implementation that refuses a present or unreadable policy source. Settings certification is specified only for run admission, not before login/status/logout, which can themselves consume settings. These gaps violate R3.1, R3.3, R3.5 and the unknown-precedence refusal.

   **Exact fix:** define a backend-only certified launch context containing the effective environment, cwd, settings sources/policy evidence and executable descriptor; use and validate it at every named child boundary. Enumerate the final safe-key allowlist and all research selectors rather than delegating the security policy to an implementer grep. Keep all unknown cloud-family selectors removed/refused. Resolve managed-source discovery now, with an executable runtime refusal for unsupported or unreadable sources; a live-test checklist is not a production gate. Specify a pre-command scan that never invokes helpers. If bootstrap intentionally differs from the final context, certify both explicitly and explain how R3.3 remains satisfied. Add tests for context drift, registry-policy presence/unreadability, settings auth injection, and every selector.

2. **Serious — Component 8 and B8, lines 399–437, 613: existing main-chat holds remain outside the work list.** `libs/backend/agent-sdk/src/lib/sdk-agent-adapter.ts:1183–1185` refuses named selection on an active query, and `:1653` unconditionally refuses named selection in another continuation path. The approved task explicitly identifies both. Neither file nor its bound-turn checks appears in the component or batches. Implementing the executor alone does not satisfy R1.1/R1.4 and R4.3.

   **Exact fix:** add this adapter and its relevant specs to an owned batch. Define active-query continuation and relaunch behavior: resolve the authoritative binding, reject conflicting explicit selections, revalidate route/epoch/identity before dispatch, preserve the current owner's lease, and use the certified lifecycle when launching a replacement query. Test omitted, same named and conflicting selections on both existing branches; remove their unconditional holds without changing ambient behavior.

3. **Serious — Component 5/6, lines 279–300, 329–350: lease-only admission is incompatible with the current store settlement contract.** The store's `commitRunBinding` exists, but at `provider-account.store.ts:124–125` it simply calls `admit`, which inserts a binding and another lease. More importantly, `held()` at `:425–432` validates reservation authEpoch through a LEFT JOIN to the binding and substitutes zero when no binding exists. After the proposed lease-only admission, a nonzero authEpoch cannot be released or retained before binding commit. Resume also needs a new lease without reinserting the existing immutable binding. “Split admit” does not define these required changes.

   **Exact fix:** specify separate acquire-lease and commit-binding-under-existing-reservation APIs, including exact inputs, ownership/CAS checks and resume semantics. Store the reservation epoch independently of the binding (or define an equally sound independent validation), migrate it as necessary, and adapt `held`, release and retain. Commit must not acquire a second lease. Test fresh failure before commit at a nonzero epoch, exact-once settlement, resume with an existing binding, cancellation during commit and late admission completion. Replace the incorrect migration lookup `0056_provider_accounts.ts` at line 306 with the actual `0058_provider_accounts.ts`.

4. **Blocking — Component 5 and integration rollback, lines 285–286, 313–314, 546–547: unconditional release on certification failure contradicts uncertain-child retention.** The command outcome explicitly carries `terminated: false`. Nevertheless the admission algorithm says to release on *any* failure, and its test instruction expects release on each refusal. A status/version child whose kill is unproved could still access the directory after its lease is freed. Similarly, sign-in success says kill then completeAuth, but only disposal explicitly requires retention when termination is unproved.

   **Exact fix:** propagate termination evidence for every certification/auth child into reservation settlement. Release only after every owned child is proved closed; retain on uncertainty, including successful polling followed by an unproved console kill, timeout and cancellation. Serialize polling so status children cannot overlap and aggregate all their close evidence. Add explicit tests for unproved version/status/console termination, not only SDK query termination. Preserve the existing action-service rule that `completeAuth` is not called when termination is unproved.

5. **Serious — Component 3, lines 200–215 and B4/B4b: the required spawner work is left conditional and assigned to the wrong implementation locations.** `ProcessSpawnRequest:64–81` has neither `stdio` nor `windowsHide`; it has `needsConsole`. The actual `OffThreadProcessSpawner` in agent-sdk converts that to `windowsHide` at `:731`, and both its inline path (`:811`) and worker source (`:254`) hard-code stdin/stdout pipes. Ignoring stream listeners in the launcher does not prove that Ptah's spawner never reads login bytes. The plan instead sends implementers to assumed platform-electron/vscode/cli implementations.

   **Exact fix:** make the required process-port and agent-sdk worker/shim/inline changes concrete, with explicit null-stream/ignored-stdio behavior and visibility semantics. Assign those real files and their tests to batches. Test both worker and inline paths, no output forwarding/buffering/logging, and that agent/MCP terminal tools cannot enumerate or operate on this console (R2.2). Preserve the launch guard and test console-child tree ownership. D5 authorizes the separate console; it does not remove the need to implement this transport contract.

6. **Serious — Components 3/4/7 and U3, lines 206–207, 239–241, 365–368, 505: fallback cannot reliably log in to the named profile.** The fallback contains only an executable argument array and directory.
