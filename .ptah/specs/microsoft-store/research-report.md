# Research Report - microsoft-store

## Question

- Decision this supports: whether and how to ship Ptah (Electron 44.4.3, electron-builder 26.16.1 installed, NSIS today) to the Microsoft Store as MSIX from GitHub Actions `windows-latest`, with Microsoft re-signing (no own certificate).
- Question: what does the appx/MSIX build, Partner Center setup, CI submission, runtime behaviour, update handling and packaging gotchas look like for Ptah, and what could block it?
- Bounds: not investigated - paid/IAP, Xbox, ARM64 builds, the EXE/MSI Store path beyond a one-line comparison, `msix` target of electron-builder master (not installed here), AppInstaller/sideload distribution, Store listing copy/screenshots. Firecrawl returned 401, so WebFetch/WebSearch and the installed `node_modules` source were used. Dates below are page "updated_at"/"ms.date" values from the fetched Microsoft Learn pages (all within 2026) unless marked undated.

## Answer

Build an unsigned `appx` target (MSIX-compatible `.appx`) with electron-builder on CI and upload it with `msstore publish` after a one-time manual first submission in Partner Center; Microsoft re-signs it. It is feasible, but four things need work first: (1) the app version is `0.1.70`, and the Store forbids a first version segment of 0, so the Store build needs a mapped version; (2) the in-app GitHub update check must be disabled when `process.windowsStore` is true; (3) the `runFullTrust` justification, the runtime download of executables (policy 10.2.2/10.2.3/10.2.4) and live generative AI (policy 11.16) must be handled in the listing and certification notes; (4) the first submission, Entra app registration and Partner Center association cannot be automated.

## Disagreements

- Unsigned appx and Store upload: Microsoft says no CA cert is needed and the Store re-signs (app-package-requirements). Nothing in the fetched Microsoft pages states in so many words that a completely unsigned package passes upload validation; the only direct evidence is one third-party project (openscreen PR 285) and the installed electron-builder behaviour. Decided by the first real upload; use the local self-signed sideload test first (see Unknowns).
- Whether `publisher` must come from the cert: electron-builder docs say it must equal the signing cert subject; the installed source ignores that for an unsigned Store build and uses the configured `publisher`. For the Store build, set `publisher` to Partner Center's `CN=...` value.
- Certification duration: Microsoft says "up to three business days"; a third-party ebook (via search summary) says automated-only passes can take hours and manual testing up to five days; the dev.to account saw resubmission approved within 24 h. Plan for 1-3 business days, longer for the first `runFullTrust` review.
- Where the Entra app is created: the Learn GitHub-Actions page says register it in Entra and add it in Partner Center; the older REST page says create one from Partner Center. Both end in the same Manager-role association.

## Local consequences

- `D:/projects/ptah-extension/apps/ptah-electron/electron-builder.yml`: add an `appx:` block, for example `identityName` (Partner Center Name, e.g. `12345Publisher.Ptah`), `publisher` (the `CN=...` GUID string), `publisherDisplayName`, `applicationId: Ptah`, `displayName: Ptah`, `backgroundColor: transparent` or a brand hex, `languages: [en-US]`, `capabilities: [runFullTrust]` (already forced), plus `protocols` only if the app registers a custom scheme (none found in `src`). Do not add `electron-winstore-auto-launch` unless a startup task is wanted. Keep `win.target: [nsis]` and select appx per job with `--win appx`, so the NSIS release is unchanged. `asarUnpack` already covers better-sqlite3, sqlite-vec(-*), onnxruntime-node, ffmpeg-static, codex binaries.
- `apps/ptah-electron/assets` (buildResources is `assets`, not `build`): the asset folder is `assets/appx/` containing StoreLogo.png (50x50), Square44x44Logo.png (44x44), Square150x150Logo.png (150x150), Wide310x150Logo.png (310x150); add `.scale-100/200/400` variants only if wanted (they trigger makepri). Optional SplashScreen/LargeTile skip if absent. Store listing separately needs a Store logo and 1+ screenshot.
- Version: `0.1.70` yields `0.1.70.0`, invalid for the Store (first segment 0). Needs a Store-only mapped version (inference: pass `-c.extraMetadata.version=1.<minor>.<patch>`, or set a floor such as `1.0.<n>`); it must also increase on every submission, and the 4th segment stays `0`. Pre-release suffixes: `getVersionInWeirdWindowsForm` splits on `.` and `parseInt`s, so `0.1.70-beta.1` would still parse as 0.1.70, but avoid them.
- `apps/ptah-electron/src/services/update/update-manager.ts` (and its start call site): skip `start()`/periodic check when `process.windowsStore` is true. Electron's own `autoUpdater` is not used here, so no other change; Store delivers updates itself. Consider hiding the "Download update" UI path too.
- `.github/workflows/publish-electron.yml`: add a separate `windows-latest` job (or step after the existing prepackaged win-unpacked build) that runs `npx electron-builder --config electron-builder.yml --project dist/apps/ptah-electron --publish never --win appx --prepackaged <win-unpacked>` WITHOUT passing the signing env, then `microsoft/microsoft-store-apppublisher@v1.1`, `msstore reconfigure ...`, `msstore publish <appx> -id <productId>`. Whether `--prepackaged` works with the appx target is untested (the existing code comments cite an `elevate.exe` issue only for NSIS). Do not sign the appx; the existing signing pass (which signs .node/.dll) is harmless for contents but the appx container must not be signed with the Authenticode cert whose subject differs from `publisher`, or the Store may reject the identity mismatch (inference).
- GitHub secrets to add: `AZURE_AD_TENANT_ID`, `AZURE_AD_APPLICATION_CLIENT_ID`, `AZURE_AD_APPLICATION_SECRET`, `SELLER_ID`, plus a variable for the Store product ID.
- Runtime code spawning `node`: the dev.to failure (`spawn node` on machines without Node) applies if any Ptah code path spawns `node` from PATH; the Claude/Codex CLIs are separate and are the user's concern. Audit for `spawn('node'...)` and use `process.execPath` + `ELECTRON_RUN_AS_NODE=1`.
- Listing text: per policy 10.2.4 put a dependency disclosure (needs Claude Code / Codex / git CLIs installed by the user) at the very beginning of the description; per 11.16 disclose live generative AI in metadata and in Partner Center, and ship a visible way to report inappropriate AI output (confirm whether one exists; not checked in this pass); per 10.2.3 avoid any flow where Ptah offers to install third-party secondary software that does not enhance the product (the helper-binary download needs review against this and 10.2.2).
- Privacy policy URL: required if the app collects/transmits personal info; Ptah sends prompts to AI providers and checks GitHub, so provide one.

## Answers to the six numbered questions (condensed)

1. appx config: see Local consequences. Unsigned Store-bound build is supported by the installed electron-builder (log line "Windows Store only build"). Native modules: no appx-specific bug found in the sources checked; the requirement is that `.node`, `.dll`, `.exe` live in `app.asar.unpacked` (already done). A Claude desktop MSIX issue (https://claudeissues.com/issue/54020-bug-windows-msix-node-pty-fails-to-spawn-shell-error-file-not-found-in-windowspt, undated, closed "not planned") reported node-pty failing with "File not found: " in `windowsPtyAgent.js` from `app.asar`; the reporter's hypothesis is an asar `__dirname` path used with explicit `fs` calls. Not confirmed as an MSIX limitation. Test Ptah's node-pty path resolution (use `app.asar.unpacked` paths) in the sideloaded MSIX.
2. Partner Center: reserve name (steps above), then Product management > Product identity for Name/Publisher/PublisherDisplayName. Product type: "MSIX or PWA app". Age rating: IARC questionnaire required, all questions. Privacy policy: required if personal info collected. Certification: up to 3 business days. Flighting: package flights (needs a published non-flighted submission first; group = Microsoft account emails; same certification; supported in `msstore flights`).
3. CI: use `msstore` + `microsoft/microsoft-store-apppublisher@v1.1`. Commands: `msstore reconfigure --tenantId --sellerId --clientId --clientSecret`; `msstore publish <file>.appx -id <productId> [--noCommit]`; if staged, `msstore submission publish <productId>`; poll with `msstore submission poll <productId>` or `msstore submission status <productId>`. Manual once: register developer account (ID verification), reserve name, associate/create Entra tenant (Partner Center > Account settings > Tenants), register Entra app + client secret, add it under User management > Microsoft Entra applications with Manager role, complete the FIRST submission (pricing, properties, age rating, packages, listing, privacy URL, restricted-capability justification) in the portal and wait until it is live. Note the Entra client secret has an expiry; calendar a rotation.
4. Runtime: see Evidence (virtualization) and below.
5. Updates: the Store updates automatically per customer settings once a higher version is published; the app must not self-update. Skip the GitHub check when `process.windowsStore` is true.
6. Gotchas: version `X.Y.Z.0` with X >= 1 and monotonic; 25 GB cap (practical limit is your own size - dev.to saw 526 MB shrink to 191 MB by pruning `files`; Ptah's `**/*` pattern should be audited); test locally before submitting.

### Runtime behaviour notes (item 4)

- userData (`%APPDATA%`, i.e. AppData\Roaming\Ptah) and `%LOCALAPPDATA%` writes work; new files are redirected to a per-package private store but appear at the normal path to the app (Microsoft doc). Consequence: files the app creates are not visible to external tools through the real filesystem in the same way (inference: the merge is only presented to the packaged process tree; an external CLI like `claude` launched from the app is a child process and inherits the same view, but a separate terminal may not see AppData files the app created). Files under `~/.ptah` and the user profile outside AppData are not virtualized (writes outside the package and AppData are allowed with user permission), so keeping `~/.ptah/models`, workspace files and CLI session data outside AppData avoids this, and the existing design already uses `~/.ptah`.
- HKCU writes are per-app copy-on-write; removed on uninstall.
- Spawning external executables, ConPTY: full-trust (Medium IL) apps run as the user with no AppContainer, so `child_process`/node-pty launching `git`, `claude`, `codex` is the same OS mechanism as unpackaged. No official statement was found that PATH differs; PATH comes from the user's environment (inference, not verified). Verify in a sideloaded build.
- Downloading and running binaries at runtime: not blocked by the OS for full-trust apps. Policy risk is 10.2.2/10.2.3, not technical.
- Package files are read-only: nothing may write under the install dir (`process.resourcesPath`). Check Ptah for any write next to the exe (for example the ONNX model cache already redirected to `~/.ptah/models`).
- Single instance (`app.requestSingleInstanceLock` at `src/main.ts:56`): works as-is; the packaged app is also activated by Start menu / protocol launches. Protocol handlers: `setAsDefaultProtocolClient` writes the registry and does not take effect inside MSIX; declare protocols in the manifest through electron-builder `protocols` (none found in current source; confirm). Startup tasks: use the manifest `windows.startupTask` (electron-winstore-auto-launch) instead of `app.setLoginItemSettings`; none found in the source.
- `process.windowsStore` is `true` in MSIX-packaged Electron.

### Local test recipe (item 6, inference from the cited WACK/MSIX pages plus standard Windows tooling; not run)

1. Build the appx (unsigned) with the Store `identityName`/`publisher`.
2. For local install you need a signed package: create a self-signed cert whose subject equals the manifest `Publisher` exactly (`New-SelfSignedCertificate -Type Custom -Subject "<Publisher>" -KeyUsage DigitalSignature -FriendlyName test -CertStoreLocation Cert:\CurrentUser\My -TextExtension @("2.5.29.37={text}1.3.6.1.5.5.7.3.3","2.5.29.19={text}")`), sign a COPY with `signtool sign /fd SHA256 /a /f test.pfx /p <pw> Ptah.appx`, import the cert into Local Machine > Trusted People (admin), then `Add-AppxPackage .\Ptah.appx`. Electron-builder doc (via search summary) also mentions Developer Mode for unsigned packages.
3. Run WACK: `appcert.exe reset` then `appcert.exe test -appxpackagepath Ptah.appx -reportoutputpath report.xml` (elevated, interactive session; default path `C:\Program Files (x86)\Windows Kits\10\App Certification Kit\`). Upload the original unsigned file, not the self-signed copy.
4. Optionally use a package flight after the first public release for beta testing without exposing it to everyone.
