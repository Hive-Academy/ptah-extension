# Part B and Batch C code logic and security review

Review family: codex (implementer: grok)  
Score: **5/10**  
Verdict: **REVISE**

The implementation covers ordinary in-root navigation, rejects lexical traversal and nonempty conventional authorities, and installs `Fetch` before direct navigation. The score is below the sound 7–8 band because two routes can bypass the claimed file boundary. It is above the 3–4 band because direct requests and ordinary follow-on requests are checked against real paths. No live browser security probe or scoped Jest run was performed under this review's command restriction. `ptah_get_diagnostics` returned **unavailable** after its 45-second TypeScript timeout; it did not report a pass.

## Findings

1. **Major — file validation has a check/open race.** `browser-file-url.ts:118-140` validates a pathname with `realpath`, then `chrome-launcher-browser-capabilities.ts:727-733` or `electron-browser-capabilities.ts:728-732` tells Chromium to continue opening the original URL. A caller or local process can replace an in-root symlink/junction with one to an outside file between these steps. The current per-request recheck does not close the interval on that request. Serve the file from a descriptor opened and verified by the host, or use an isolated copy/snapshot that Chromium opens; add a deterministic swap-at-continue test. This is the main reason the stated "only inside workspace" guarantee is not established.

2. **Major — popup targets are not guarded.** `electron-browser-capabilities.ts:475-525` creates one window, attaches one debugger, and enables `Fetch` there; it installs no window-open denial or guard for a child. `chrome-launcher-browser-capabilities.ts:493-515,684-715` similarly attaches to one CDP client without target auto-attach. An in-root HTML page can call `window.open` on an outside `file:` URL; the new target is outside the file-request handler. Deny popups, or attach and install the same guard before permitting a new target to navigate. Test an outside-root `window.open` in both hosts.

3. **Minor — follow-on navigation can enter a scheme that direct navigation forbids.** `browser-namespace.builder.ts:180-190` rejects direct `data:`, `javascript:` and other schemes, but `chrome-launcher-browser-capabilities.ts:713-715` and `electron-browser-capabilities.ts:523-525` intercept only `file:*`; their current-page checks return success for every non-file URL (`chrome-launcher-browser-capabilities.ts:643-645`; `electron-browser-capabilities.ts:700-702`). A loaded page can navigate itself to a non-file scheme and subsequent screenshot/evaluate/content calls operate there. Apply the direct scheme policy to follow-on main-frame navigation, and define treatment for `blob:`, `filesystem:`, `view-source:`, `chrome:` and `devtools:` explicitly.

4. **Minor — root reconfiguration can lose an update during session creation.** Both hosts copy `_pendingOptions`, await asynchronous cleanup, then reset `_pendingOptions` and `rootsDirty` (`chrome-launcher-browser-capabilities.ts:448-463,502-505`; `electron-browser-capabilities.ts:458-469`). If `configureSession` runs during that await, its new roots can be overwritten. `ensureSession` also returns after an existing `sessionPromise` without checking whether roots changed while it waited (`chrome-launcher-browser-capabilities.ts:431-445`; `electron-browser-capabilities.ts:435-455`). A subsequent call may use stale root scope. Serialize configuration with creation, then recheck the generation before exposing the session.

5. **Minor — legitimate paths beginning with `..` are rejected.** `browser-file-url.ts:53-60` uses `relative.startsWith('..')`. For a real file such as `<root>/..preview.html`, `path.relative` returns `..preview.html`, even though it is a child path. This gives the wrong answer without an error. Reject only `relative === '..'` or `relative.startsWith('..' + pathApi.sep)`; retain the absolute-path guard. Add both POSIX and Windows cases.

6. **Minor — authority parsing accepts `?`/`#` forms as an empty host.** `browser-file-url.ts:161-167` strips query and fragment characters *inside the authority string* before testing it. An input such as `file://?/C:/page.html` can pass the lexical nonempty-authority check and be validated as `/C:/page.html`, while the URL parser sees a different path. Validate the raw authority before any query/fragment stripping and reject either marker before the first path slash. Keep the `Fetch` defense in place.

7. **Minor — the sync spec does not enforce its stated full alignment.** `lane-policy-sync.spec.ts:17-22,62-70` checks four shared tool names, while the child policy lists eleven tool substitutions at `cli-adapter.utils.ts:422-433`; its messaging regex at `lane-policy-sync.spec.ts:25-26,85-91` misses simple unconditional claims such as "steer always works." The current docs' UI and messaging text agrees with the inspected policy, but this test can pass after meaningful drift. Assert the complete required tool set and positive capability-dependent wording rather than a narrow forbidden phrase.

## Five logic questions

1. **Silent failure:** the popup route lacks the target's `Fetch` guard yet the original browser session remains connected (`electron-browser-capabilities.ts:508-525,540`; `chrome-launcher-browser-capabilities.ts:506-515,568-570`). A roots change during session startup can also be silently overwritten (`chrome-launcher-browser-capabilities.ts:448-463`).
2. **Unexpected user action:** an in-root page opening an outside file in a new window escapes the monitored target (`electron-browser-capabilities.ts:475-525`).
3. **Wrong answer from input:** `<root>/..preview.html` is a valid child but fails the containment function (`browser-file-url.ts:53-60`).
4. **Dependency failure/shape:** failure to install `Fetch` tears down creation, and a paused-request handler tries to fail closed (`chrome-launcher-browser-capabilities.ts:506-515,739-749`; `electron-browser-capabilities.ts:523-537,738-749`). Unexpected missing `requestId` on Electron is ignored, leaving no explicit error (`electron-browser-capabilities.ts:565-579`); protocol behavior needs a focused test.
5. **Missing requirement:** the requirements discuss links, redirects, frames and subresources but do not specify popup/new-target handling or an atomic file-open contract. The current single-target installation exposes both gaps (`implementation-plan.md:70-74`; `electron-browser-capabilities.ts:475-525`).

### Findings requiring action

1. **Major — the descriptor is not bound to the contained path.** `browser-file-url.ts:173-199`. After an in-root path resolves, an attacker with workspace write access can replace that path with a symlink to an outside file for the `open`, then restore the original before both later `realpath` checks. `handle.read` returns bytes from the outside descriptor, which the hosts fulfill to Chromium (`chrome-launcher-browser-capabilities.ts:822-829`; `electron-browser-capabilities.ts:773-781`). Verify the identity of the opened file against a safely opened path under the root, or use a platform-specific containment-preserving open; test a controlled swap at the open boundary. A recheck of the same pathname does not prove the descriptor's origin.

2. **Major — attached non-popup targets can remain paused forever.** `chrome-launcher-browser-capabilities.ts:770-791` enables auto-attach with `waitForDebuggerOnStart: true`, but `Target.runIfWaitingForDebugger` is absent from the installed CDP protocol (`node_modules/devtools-protocol/types/protocol-mapping.d.ts:1235,4436`). The optional `resume` is therefore undefined, so a worker or out-of-process iframe is neither closed nor resumed at `:782-785`. Resume via `Runtime.runIfWaitingForDebugger` on the attached session, or avoid pausing targets that are allowed; test worker and cross-process iframe creation against the actual CDP API. If allowed child targets are resumed, their file requests also need the same guard.

3. **Minor — status and network reads bypass the follow-on page policy.** `chrome-launcher-browser-capabilities.ts:349-430` and `electron-browser-capabilities.ts:374-439`. A page that navigates itself to `data:` or another refused scheme is withheld by `content` or `screenshot`, but `status()` still returns that page's URL/title, and `getNetworkRequests()` still returns non-file entries from it. Apply the same current-page check before these reads, or explicitly narrow the requirement and return only session metadata when the page is refused.

4. **Minor — an in-root FIFO can hang a file request.** `browser-file-url.ts:173-175`. `open(canonical, 'r')` occurs before the regular-file check; opening a FIFO for reading can wait indefinitely for a writer. Use nonblocking/no-follow open flags where supported, reject special files before blocking open, and bound the request with a timeout/cancellation path. The existing size cap does not address this case.
