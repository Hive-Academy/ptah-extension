# P1 review lifecycle — logic hunt

Read-only. No source edits. No lifecycle-review skill applies in this session; the hunt used the task contract and Ptah file tools (`ptah_search_files`, `ptah_ast_analyze`). Symbol index was empty, so bodies were read directly.

## Findings

1. **High.** Crash and lease expiry never become a claimable attempt (AC-2.4, AC-2.2). `libs/backend/review-core/src/lib/persistence/sqlite-review.repository.ts:104-112`, `:77-80`, `:52-54`. `libs/backend/review-core/src/lib/review-orchestrator.service.ts:128-130`. `apps/ptah-electron/src/activation/review-worker.activation.ts:59`.
   - Scenario: the worker dies or the 60s lease lapses. Startup calls `reconcileExpiredLeases`, which marks the attempt `interrupted` and clears the lease. `claimNext` only selects `state = 'queued'`. The next poll hits the automatic-attempt dedupe and returns that same interrupted row, so `claimNext` stays null. A head that was mid-review is still unreviewed after the 48-hour startup poll. `stage()` also refuses a `running` or `interrupted` checkpoint and returns null, so reclaiming the same attempt would partial-out instead of resuming. The repository spec locks this in (`sqlite-review.repository.spec.ts:65-75`).
   - Fix: when the active head's latest automatic attempt is `interrupted` or `failed` and no unexpired `running` row exists, insert a new queued attempt (keep the old row for history). Run stages only on that new attempt. Do not treat dedupe of a non-queued row as a successful enqueue.
   - Quote: `UPDATE review_attempts SET state = 'interrupted' ... WHERE state = 'running' AND lease_expires_at <= ?`

2. **High.** A lost heartbeat makes `release` a no-op, and the orchestrator ignores that. `sqlite-review.repository.ts:89-101`. `review-orchestrator.service.ts:75-79` and `:111`. `review-orchestrator.service.ts:63-67` never reconciles before claim.
   - Scenario: the event loop stalls past 60s, or heartbeat updates 0 rows (owner lost, attempt already cancelled). The `catch` logs a generic error and the stage keeps going, including publication. `release` requires `state = 'running' AND lease_owner = ? AND lease_expires_at > now`. It returns false. The row stays `running` with an expired lease, so `claimNext`'s `NOT EXISTS (... state = 'running')` blocks that PR until the next process start, which then hits finding 1.
   - Fix: `release` for the current owner must clear the lease even when `lease_expires_at` is already past, as long as the row is still `running`. If it returns false, abort before any further write. A heartbeat that returns false must stop the attempt. `drain` must call `reconcileExpiredLeases` before `claimNext`.
   - Quote: `WHERE attempt_id = ? AND state = 'running' AND lease_owner = ? AND lease_expires_at > ?`

3. **High.** Quit can close SQLite while the review lease is still held. `apps/ptah-electron/src/activation/review-worker.activation.ts:79-88`. `apps/ptah-electron/src/activation/shutdown.ts:241`, `:330-333`, `:442-444`. `libs/backend/review-core/src/lib/lanes/review-lane.runner.ts:66-75`. `review-orchestrator.service.ts:75-80`.
   - Scenario: `handleWillQuit` aborts the boot signal, then `dispose()` only clears the 30s poll timer and unregisters the cron handler. It does not abort the in-flight `drain` or the lane `AbortController` (that timer is the lane deadline, not the boot signal). `awaitStopped` is raced against 5s and is not cancelled on expiry. The heartbeat callback returns immediately once the signal is aborted, so the lease is not renewed. `process()` is still inside a lens or `publication.run` when `SQLite close` runs. `release` in `finally` then hits a closed database. The expiry comment says the next start will reconcile; finding 1 shows that does not requeue the head.
   - Fix: give the worker its own `AbortController`, abort it from `dispose()`, and pass that signal into lane `spawn`. Before closing SQLite, await in-flight `release` (bounded). On budget expiry, run one synchronous `release` for the active attempt id while the connection is still open, then close.
   - Quote: `await withBudget('Review worker lease release', () => reviewWorker.awaitStopped(), 5_000, 'the lease will expire and reconcile on next start.')`

4. **High.** Rediscovering a known SHA does not move the active head (AC-1.2, AC-2.3). `sqlite-review.repository.ts:52-54` returns before `:55-64`.
   - Scenario: head A is reviewed, head B becomes active, then the PR returns to A (force-push or revert). The automatic row for A already exists, so `enqueue` returns it and never supersedes B or inserts a queued attempt. `claimNext` still requires `review_heads.state = 'active'` for the attempt SHA, so A is not claimed. B remains the stored active head while GitHub's head is A. Open findings for B stay `status = 'open'`.
   - Fix: inside the same transaction, if the active head SHA differs, supersede it and insert a new queued attempt for the discovered SHA. Return the old attempt only when that SHA is already the active head and a queued or running automatic attempt exists.
   - Quote: `if (existing) return this.queueAttempt(existing);`

5. **High.** Dry-run publication writes current findings with no live head check (AC-11.4, AC-2.3). `libs/backend/review-core/src/lib/stages/publication-stage.runner.ts:33-43`. `libs/backend/review-core/src/lib/stages/publication-finding.persistence.ts:46-70`. `review-orchestrator.service.ts:98-104`.
   - Scenario: the orchestrator guard compares `github.getPull().headSha` only between stages. `publication.run` never calls GitHub or `policy.publication`. `persistVerifiedFindings` loads the attempt row and inserts `review_findings.status = 'open'` for every accepted verdict, including `same-family-weaker`. It does not require `review_attempts.state = 'running'` or `review_heads.state = 'active'` for that SHA. A push that lands after the pre-publication guard, or an enqueue that already cancelled the attempt, still commits those rows as open. Unavailable verdicts are not inserted, but the publication stage still runs and is stored as completed.
   - Fix: in the finding transaction, update only when the attempt is still `running`, the lease owner matches, and the active head SHA equals the attempt SHA. Re-read the PR head and skip the write when it differs. Do not call `publication.run` for a superseded claim.
   - Quote: `INSERT INTO review_findings (... status ... ) VALUES (..., 'open', ...)`

6. **High.** Supersession cancels the attempt without `result_status`, and history then throws. `sqlite-review.repository.ts:60-61`. `libs/backend/review-core/src/lib/persistence/review-query.repository.ts:51-52`.
   - Scenario: a new head cancels queued and running attempts and clears the lease, leaving `result_status` null. The in-flight worker's later `release(..., 'superseded')` matches zero rows because the state is already `cancelled`. `listRuns` / `getRun` set `status` from `result_status ?? state` and throw `Review result status unavailable` on `cancelled`. One superseded PR fails the whole runs page.
   - Fix: set `result_status = 'superseded'` in the cancel update. Map a cancelled row with a null result to `superseded` instead of throwing.
   - Quote: `if (status === 'completed' || status === 'cancelled') throw new Error('Review result status unavailable');`

7. **High.** The verifier is one launch per finding, so the per-PR cap of 6 drops every candidate after the first (D12, FR-7). `libs/backend/review-core/src/lib/stages/verification-stage.runner.ts:20-28`. `libs/backend/review-core/src/lib/lanes/review-lane-admission.service.ts:34-43`. `review-lane.runner.ts:64`.
   - Scenario: admission counts launches per `prKey:attemptId` and does not return that count on `release` (the cap is total, not concurrent). Triage plus four lenses use 5 of 6. Each finding then calls `lanes.run({ kind: 'verifier' })`. The second finding gets `{ status: 'partial', reason: 'budget' }`, which the verifier labels `unavailable`. Publication still runs and can persist the single accepted finding. D12 is one verifier batch inside the six-lane cap (triage, four lenses, one verifier).
   - Fix: spawn one verifier for the whole candidate list and count it as one launch. If admission returns partial, mark the batch partial once. Do not start a seventh lane.
   - Quote: `if ((this.launchedByPr.get(prKey) ?? 0) >= 6) return { status: 'partial', reason: 'budget' };`

8. **High.** Partial stages are stored as completed, and a partial triage still publishes. `libs/backend/review-core/src/lib/stages/lens-stage.runner.ts:50`. `review-orchestrator.service.ts:91-104` and `:141`. `review-query.repository.ts:43`.
   - Scenario: a lens with `result.status === 'partial'` is saved as `review_stages.state = 'completed'`. `stage()` does the same for any runner that returns instead of throwing, including triage `{ status: 'partial' }`. The orchestrator sets the attempt to partial and then still runs lenses, verification, and publication. Run history maps every `completed` stage to `succeeded`, so a coverage-limited lens looks successful (AC-6.2).
   - Fix: persist `partial` as the stage state. Return from `process` before publication when triage or verification did not finish, except to write an explicitly partial artifact that contains no accepted findings. Map `outcome = 'partial'` to a partial run-stage status.
   - Quote: `await this.repository.saveStage({ ...row, state: 'completed', ... outcome: result.status });`

9. **Medium.** Context reports success with no repository checks. `libs/backend/review-core/src/lib/stages/context-stage.runner.ts:56`.
   - Scenario: `checks.run` is always called with `[]`. No degradation audit or ESLint is scheduled. The context stage completes, coverage has no check row, and the attempt can still finish `succeeded`. AC-5.1 and AC-5.4 need an explicit unavailable or failed check, not an empty list.
   - Fix: pass the configured check definitions into `checks.run`. Record each unavailable or failed check on the context stage. Do not treat an empty definition list as a completed check pass.
   - Quote: `const checks = await this.checks.run(claim.repo, paths.src, [], dependency.status === 'available');`

10. **Medium.** Any failed guard is stored as `superseded`, which dedupe then freezes. `review-orchestrator.service.ts:84` and `:115-122`. Same early return as finding 4 (`sqlite-review.repository.ts:52-54`).
    - Scenario: the head SHA still matches, but the PR is draft, closed, or the author is no longer allowed. `guard` returns false and the attempt is released as `superseded` (or left `cancelled` if finding 6 already happened). The next poll, after the PR is ready again on the same SHA, returns the old automatic row and does not queue it. AC-1.3's "current head is then queued" does not happen once any automatic row exists.
    - Fix: record the eligibility reason on the attempt (`cancelled` plus a distinct result, not `superseded`, unless the SHA changed). On a later eligible discovery of that SHA, insert a new queued attempt when the previous one is terminal and the head is active.
    - Quote: `if (!await this.guard(claim)) { status = 'superseded'; return; }`

## Checked, no defect filed

- Migration `0065_ptah_review.ts`: `review_operator_settings` (`id = 1`, `settings_json` with `json_valid`), `review_findings.payload_json` with `json_valid`, and lease columns plus `idx_review_attempts_lease` are present. Settings writes go through that table (`review-settings.store.ts:29-30`).
- Admission math matches the P1 spec: per-attempt launch cap 6, review concurrency `min(3, max(0, maxConcurrentAgents - 1))`, immediate `partial` for deadline, budget, `operator-reserve`, and `review-capacity` (`review-lane-admission.service.ts:33-37`, spec lines 6-22). `release` frees only the global slot; the per-PR counter is the launch budget.
- Cross-family verifier preference and the weaker label are implemented for a single verifier call (`review-lane-selector.ts:29-31`, `review-lane.runner.ts:85-86`). The preview prints `weaker evidence (same-family verifier)` (`review-artifact.writer.ts:63-65`). Unavailable verdicts are not inserted (`publication-finding.persistence.ts:36-37`), so AC-7.5 holds for those rows; finding 5 is the stale-head hole around the rows that are inserted.
- `claimNext` compares lease owner on heartbeat and release, orders by newest `queued_at`, and will not claim a second `running` row for the same PR (`sqlite-review.repository.ts:77-93`).
- Worker poll timer is `clearInterval`'d on dispose (`review-worker.activation.ts:82`). Lane `setTimeout` is cleared in the runner `finally` (`review-lane.runner.ts:92`). The gap is the in-flight attempt outliving that dispose, finding 3.
- `startupPoll` runs discovery when `last_poll_at` is null or at least 48 hours old (`review-orchestrator.service.ts:50-54`, `review-worker.activation.ts:56-62`). That does not repair an interrupted head, finding 1.
