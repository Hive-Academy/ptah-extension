## Five logic questions

### 1. How does this fail silently?

- On an incremental head (`scope.publishNewVerifiedRootsOnly === true`), an already-published finding from a previous head matches with `identity.outcome === 'still_open'`, bypasses line 98 of `review-publication.service.ts` (which checks `identity.outcome !== 'new' && identity.outcome !== 'still_open'`), and is either re-published in the new head's `overview` under `Additional verified findings` (`review-publication.service.ts:125-127`) or consumes one of the 10 inline slots (`review-publication.service.ts:120`) before `GithubReviewPublicationAdapter` drops it (`github-review-publication.adapter.ts:173`).
- When a publish attempt times out after `repository.identity()` has already updated `review_findings.status` to `'addressed'` or `'reopened'` (`publication-outbox.repository.ts:146-149`), the retry sees the mutated `prior.status` in SQLite and silently omits the addressed/reopened follow-up (`review-publication.service.ts:67,71,93`), leaving the `follow_up` row in `review_publications` in `state = 'unknown'`.
- In production DI (`libs/backend/review-core/src/di/registration.ts:74-75`), `ReviewPublicationService` is always injected into `PublicationStageRunner`, so `publication-stage.runner.ts:58` (`if (this.sqlite && !this.publication && !signal?.aborted) persistVerifiedFindings(...)`) is skipped, and when dry-run or pause is active `ReviewPublicationService.publish` returns immediately at line 49 — leaving `review_findings` empty for dry-run and paused attempts.

### 2. What user action produces unexpected behaviour?

- On a fresh install (`review_operator_settings` has no row yet), an operator who opens the Review Settings drawer, saves a valid bot token (seeing `"Connected as <login> | Verified ..."`), attests permissions, and clicks "Save review settings" to enable live mode gets rejected with `Bot identity and maintainer permission attestation required` because `review:getBotIdentity` skipped `setLiveGate` when `getSettings()` returned `null` (`review-rpc.handlers.ts:89-93,161-165`), and `review:updateSettings` clears `liveGate` whenever `old` is `null` (`review-rpc.handlers.ts:158,170-171`).
- Replacing a bot token while a repository is already in live mode (`dryRun: false`) clears `liveGate` (`review-rpc.handlers.ts:103`), but because the "Keep this repository in dry-run" checkbox is already unchecked (`review-settings-drawer.component.ts:22,82-86`), clicking "Save review settings" sends `attestation: undefined` (`review-runs.store.ts:174`) and fails unless the operator first toggles dry-run on and back off.

### 3. What input data produces a wrong answer?

- A previously addressed finding that was reopened (`status = 'reopened'` in `review_findings`) and then fixed in a subsequent commit is omitted by `SqliteReviewRepository.getOpenFailures` (`sqlite-review.repository.ts:43-44`, which filters `status = 'open'`) and rejected by `review-publication.service.ts:67` (which hardcodes `status: 'open'`), so the second fix is never recognized as `addressed`.

### 4. What happens when a dependency fails?

- If GitHub fails or times out during `publisher.publish` on a head that addresses or reopens a prior finding, `PublicationOutboxService` marks the `follow_up` row `'unknown'` (`publication-outbox.service.ts:57`), but because `review_findings.status` was already committed as `'addressed'` or `'reopened'` (`publication-outbox.repository.ts:147`), a retry of `ReviewPublicationService.publish` does not regenerate the follow-up entry (`review-publication.service.ts:67,71,93`).

### 5. What is missing that the requirements never mentioned?

- Nothing material beyond the existing specification. All remaining defects are state-transition and gating bugs in the P2 implementation.

## New Findings

### 1. Blocker — `publishNewVerifiedRootsOnly` check is dead code; `still_open` findings from prior heads leak into incremental review summaries and consume the 10-inline cap

- File: `libs/backend/review-core/src/lib/publication/review-publication.service.ts:98-128` (and `libs/backend/review-core/src/lib/publication/publication-outbox.repository.ts:141-145`)
- Scenario: At `review-publication.service.ts:91`, `repository.identity()` is called without `recheckInput`. After line 92 (`findingId === null`) and line 93 (`outcome === 'reopened'`), the only possible values of `identity.outcome` returned by `publication-outbox.repository.ts:141-145` are `'new'` and `'still_open'`. Consequently, `if (scope?.publishNewVerifiedRootsOnly && identity.outcome !== 'new' && identity.outcome !== 'still_open')` at `review-publication.service.ts:98` is always false (`previously-identified-root` is dead code). On any incremental head (`scope.publishNewVerifiedRootsOnly === true`), every already-published open finding from an earlier head that is re-detected (`still_open`) is pushed into `selected` (`line 114`).
  1. If its line is not in the incremental diff's RIGHT anchors (or ranks outside the top 10), it enters `overflow` (`line 125`) and is baked directly into `overview` under `Additional verified findings (${overflow.length})` (`line 127`). Because `GithubReviewPublicationAdapter.publish` (`github-review-publication.adapter.ts:168-176`) only filters `candidates` by `alreadyPosted` and never filters `overview`, old findings from Head 1 are re-published in Head 2's review summary body.
  2. If its line is in the diff's RIGHT anchors and ranks in the top 10, it consumes one of the `Math.min(settings.maxNewInline, 10)` slots in `inline` (`line 120`), displacing a genuinely new finding into `overflow` (`rank-cap-or-outside-diff`) before `GithubReviewPublicationAdapter` (`line 173`) filters out the already-posted `still_open` finding.
- Fix: Track or query whether a `still_open` finding already has a confirmed publication (or pass unconfirmed `still_open` retry candidates separately from `new` findings). When `scope?.publishNewVerifiedRootsOnly` is true, suppress already-confirmed `still_open` findings as `previously-identified-root` (calling `repository.suppress`), and do not allow `still_open` retry candidates to consume `maxNewInline` slots or enter `overflow` ahead of marker reconciliation.

### 2. Blocker — Addressed and reopened follow-ups are lost on retry after a publication timeout

- File: `libs/backend/review-core/src/lib/publication/publication-outbox.repository.ts:141-149` and `libs/backend/review-core/src/lib/publication/review-publication.service.ts:65-75,93-97`
- Scenario: `repository.identity()` updates `review_findings.status` in SQLite to `'addressed'` or `'reopened'` (`publication-outbox.repository.ts:146-149`) before `this.outbox.publish()` calls GitHub (`review-publication.service.ts:129`). If the GitHub request times out or fails, `PublicationOutboxService` marks the `follow_up` and `review` rows `'unknown'` (`publication-outbox.service.ts:55-57`). On the retry for that head:
  1. For an `addressed` finding, `review-publication.service.ts:67` passes `status: 'open'`, which no longer matches `prior.status` (`'addressed'`) at `publication-outbox.repository.ts:141` (`recheckInput.status === prior.status`), returning `outcome: 'uncertain'` and omitting the follow-up from `followUps`. (If a new retry attempt runs `ContextStageRunner`, `getOpenFailures` at `sqlite-review.repository.ts:43-44` also excludes the finding from `scope.recheckFailureIds` because its status is already `'addressed'`.)
  2. For a `reopened` finding, `prior.status` in SQLite is now `'reopened'` rather than `'addressed'`, so `publication-outbox.repository.ts:143-145` returns `outcome: 'still_open'` instead of `'reopened'`; `review-publication.service.ts:93` skips the reopened follow-up and pushes the finding into `selected` as a regular candidate, while the `'unknown'` follow-up row in `review_publications` is never reconciled or confirmed. Also note that `publication-outbox.service.ts:39` hardcodes `marker: <!-- ptah-review:addressed:${item.findingId} -->` even for reopened follow-ups whose body uses `<!-- ptah-review:reopened:${identity.findingId} -->`.
- Fix: Either defer mutating `review_findings.status` until `PublicationOutboxService` confirms the publication, or allow `repository.identity()` / `ReviewPublicationService.publish` on retry of the same head (`last_head_sha === attempt.head_sha` or an unconfirmed `follow_up` row in `review_publications` / event in `review_finding_events`) to reproduce the `'addressed'` / `'reopened'` outcome and follow-up payload until the `follow_up` row is `'confirmed'`. Set the outbox `marker` in `publication-outbox.service.ts:39` to match the follow-up kind (`addressed` vs `reopened`).

### 3. Major — A reopened finding can never be rechecked or marked addressed on a subsequent head

- File: `libs/backend/review-core/src/lib/persistence/sqlite-review.repository.ts:43-44` and `libs/backend/review-core/src/lib/publication/review-publication.service.ts:66-70`
- Scenario: When an addressed finding regresses on Head 3, `review_findings.status` is set to `'reopened'` (`publication-outbox.repository.ts:147`). When Head 4 fixes that regression:
  1. `SqliteReviewRepository.getOpenFailures` (`sqlite-review.repository.ts:43-44`) executes `SELECT finding_id, path FROM review_findings WHERE repo_id = ? AND pr_number = ? AND status = 'open'`, omitting `'reopened'` findings from `openFailures` and therefore from `scope.recheckFailureIds` (`incremental-scope.service.ts:32`).
  2. Even if `scope.recheckFailureIds` contained the finding ID, `review-publication.service.ts:67` passes hardcoded `status: 'open'` into `repository.identity()`, which checks `recheckInput.status === prior.status` (`publication-outbox.repository.ts:141`) and returns `'uncertain'` instead of passing `prior.status` (`'reopened'`) to `FindingRecheckService.decide` (`finding-recheck.service.ts:24`, which explicitly supports `input.status === 'open' || input.status === 'reopened'`).
- Fix: Change `SqliteReviewRepository.getOpenFailures` (`sqlite-review.repository.ts:44`) to `WHERE repo_id = ? AND pr_number = ? AND status IN ('open', 'reopened')`, and pass `prior.status` (or accept `'open' | 'reopened'`) in `review-publication.service.ts:67` / `publication-outbox.repository.ts:141`.

### 4. Major — First-time settings save and post-token-replacement live attestation fail in `review:getBotIdentity`, `review:updateSettings`, and the settings drawer

- File: `libs/backend/rpc-handlers/src/lib/handlers/review-rpc.handlers.ts:88-93,157-172` and `libs/frontend/review-runs-ui/src/lib/components/review-settings-drawer.component.ts:82-91`
- Scenario:
  1. On a fresh database where `review_operator_settings` has no row (`this.settings.getSettings()` returns `null`), connecting a bot token calls `review:getBotIdentity` (`review-rpc.handlers.ts:89-93`). Because `settings` is `null`, `const repo = settings?.repositories[0]` is `undefined` and `this.settings.setLiveGate(...)` is skipped, yet `review:getBotIdentity` returns a verified identity DTO to the UI. When the operator then attests permissions and clicks "Save review settings", `review:updateSettings` (`line 161-165`) reads `gate = await this.settings.getLiveGate()` (`null`) and throws `Bot identity and maintainer permission attestation required`.
  2. In `review:updateSettings` (`review-rpc.handlers.ts:158,166-171`), on the first save (`old === null`), `if (old?.repositories[0]?.owner !== settings.repositories[0]?.owner || ...)` evaluates `undefined !== 'Hive-Academy'` (`true`) and calls `await this.settings.setLiveGate(null)` at line 171, erasing `liveGate` right after saving. In addition, line 166 calls `this.settings.setLiveGate(...)` before `this.settings.updateSettings(settings)` at line 169, which throws `'Review settings are unavailable'` (`review-settings.store.ts:100`) whenever no settings row exists yet.
  3. When a repository is already in live mode (`dryRun: false`) and the operator replaces the bot token, `review:setBotToken` clears `liveGate` (`review-rpc.handlers.ts:103`) and `store.setBotToken` resets `this.liveAttested.set(false)` (`review-runs.store.ts:137`). Because the "Keep this repository in dry-run" checkbox is already unchecked, `setRepositoryDryRun` (`review-settings-drawer.component.ts:82-86`) never opens the `live-enable` confirmation dialog unless the operator manually checks dry-run and unchecks it again; clicking "Save review settings" sends `attestation: undefined` (`review-runs.store.ts:174`) and fails at `review-rpc.handlers.ts:164-167`.
- Fix: In `review:getBotIdentity` (`review-rpc.handlers.ts:90`), fall back to the default repository `{ owner: 'Hive-Academy', name: 'PtahCode' }` and allow `ReviewSettingsStore.setLiveGate` to persist when no settings row exists yet (or seed defaults). In `review:updateSettings` (`review-rpc.handlers.ts:158-171`), persist `updateSettings(settings)` before `setLiveGate(...)`, and guard the repo-change clear on `old !== null`. In the UI (`review-settings-drawer.component.ts` / `review-runs.store.ts`), require/record `liveAttested` when replacing a token while `dryRun === false` (or when saving with `dryRun === false` and no active attestation), and initialize `attestorLogin` from `maintainerLogins[0]` when empty so a single-maintainer setup does not fail Zod validation on `attestation.who`.

### 5. Major — Verified findings are not persisted to SQLite in dry-run or paused mode when `ReviewPublicationService` is injected

- File: `libs/backend/review-core/src/lib/stages/publication-stage.runner.ts:58,74-75` and `libs/backend/review-core/src/lib/publication/review-publication.service.ts:48-49`
- Scenario: In production DI (`libs/backend/review-core/src/di/registration.ts:74-75`), `ReviewPublicationService` is registered and injected into `PublicationStageRunner`, so `this.publication` is always non-null. At `publication-stage.runner.ts:58`, `if (this.sqlite && !this.publication && !signal?.aborted) persistVerifiedFindings(this.sqlite.db, claim.attemptId, verified)` is therefore skipped. At line 74, `this.publication.publish(...)` is called, which checks `const decision = this.policy.publication(settingsInput, baseConfig); if (!decision.allowed) return;` (`review-publication.service.ts:48-49`). Whenever the repository is in dry-run mode (`dryRun: true`) or publication is paused, `decision.allowed` is `false` and `publish()` returns immediately before recording identities or findings in SQLite. As a result, dry-run and paused review runs in Electron write zero rows to `review_findings` and `review_finding_events`, and `review:listFindings` returns `[]`.
- Fix: Persist verified findings and identity decisions in SQLite before returning on `!decision.allowed` in `ReviewPublicationService.publish` (or call `persistVerifiedFindings` in `PublicationStageRunner.run` whenever `!this.policy.publication(operatorSettings, baseConfig).allowed`).

## Verdict

- Recommendation: REVISE
- Confidence: HIGH
- Top risk: On incremental PR heads, `still_open` findings bypass `publishNewVerifiedRootsOnly` and are re-published in the review summary or consume inline slots, while a timed-out publish on an addressed or reopened finding drops its follow-up on retry.
- What a robust implementation would add:
  1. Suppress already-confirmed `still_open` roots when `publishNewVerifiedRootsOnly` is true, and keep unconfirmed retry roots out of `overflow` and the new-inline cap.
  2. Preserve or reconstruct unconfirmed `addressed` / `reopened` follow-ups across retries until `review_publications` confirms them, and include `'reopened'` findings in `getOpenFailures` and fixed-recheck status checks.
  3. Fix `liveGate` persistence on initial settings save (`old === null`) and allow re-attesting permissions when replacing a token while live mode is already enabled.
  4. Persist verified findings to SQLite even when `this.policy.publication(...).allowed` is `false` (dry-run / paused).
