### 1. MAJOR — Batch 8/9 tools define their own bench-data guard instead of the landed `resolveBenchDataDir`

- Where: `tools/mcp-bench/src/memory-skills/data/verify-candidate-manifest.ts:77-102` (`assertSafeBenchDataDir`), `:54`, `:74-76`; consumed by `candidate-row-diff.ts:205`, `sample-sessions.ts:205`, `select-rubric-sample.ts:680`, `build-labelling-packet.ts:118`.
- Scenario: 619 4c landed on this branch at `d716e0e8f` (2026-10-07 00:14, `tools/mcp-bench/src/bench-data.ts`) — 41 minutes **before** the batch 8 commit `60ac44a36` (00:55). The comments ("explicit until 619's resolveBenchDataDir() lands", "Replaced … in Batch 16") describe a state that no longer holds: the shared helper exists and is the single guard per context.md:102 and :130 (`resolveBenchDataDir()`, `BENCH_DATA_DIR_ENV`). The local duplicate is also **weaker**: `findRepoRoot` (verify-candidate-manifest.ts:278-286) stops at the *nearest* `.git`, so when these tools run from the task worktree the accepted "repo root" is the worktree, and a bench data dir placed inside the main checkout but outside the worktree passes the refusal. `resolveBenchDataDir` uses the *outermost* `nx.json` (bench-data.ts:93-106), which covers the main checkout. Two guards for one data-safety rule will drift.
- Required change: consume `resolveBenchDataDir` (validate the explicit argument through its rules, or accept the resolved dir) and delete `assertSafeBenchDataDir`; do not wait for Batch 16.

### 2. MAJOR — session sampler copies a partially-written transcript without any visible marker

- Where: `tools/mcp-bench/src/memory-skills/data/sample-sessions.ts:117-121` (`unparseable` counted), `:147-172` (`classifySession` ignores it), `:59-79` (`SessionSampleManifest` has no field for it), `:269-277` (recorded `bytes` comes from the scan-time `stat` at `:103`).
- Scenario: a transcript file that is still open (idle since before the eval-window end) can be captured mid-write; its last JSONL line is truncated. `scanSession` counts it in `unparseableLines`, but the count is dropped: the session stays eligible, is copied, and the manifest records only `bytes/sha256/first/lastTimestamp`. The `sha256` is of the copy so it is self-consistent, but `bytes` was taken at scan time and can disagree with the copied content if the file grew between scan and copy — the manifest then holds a stale size next to a true hash. Nothing downstream can tell that this frozen session contains an unparsable line; ground truth drafted from it can be silently wrong. The batch-8 report itself flagged that the last sessions may have been copied while still being written, so the risk was observed, not hypothetical.
- Required change: carry `unparseableLines` into `ClassifiedSession`, and either exclude such sessions (an `ExclusionReason`) or record the count per session in the manifest; take the recorded `bytes` from the copy, not from the scan-time stat.

### 3. MINOR — freeze check is blind to empty directories and aborts on non-regular entries

- Where: `tools/mcp-bench/src/memory-skills/data/verify-candidate-manifest.ts:163` (top-level dirs counted from file paths), `:231-244` (`listFiles` walks files only), `:239` (throws on a non-regular entry).
- Scenario: an empty top-level directory in the copy (or a dir whose whole subtree holds no files) is invisible to the missing/extra/changed detection and is not counted in `dirsOnDisk`, so `dirs` can be under-reported vs the manifest. A junction or symlink aborts the whole verification with a raw error instead of being reported as a problem row. Unlikely on a scripted frozen copy; the file-level guarantees (missing `:170-172`, extra `:173-175`, changed `:176-184`, pinned manifest hash `:150-154`) are correct.
- Required change: none blocking; report non-regular entries as `problems` and count empty dirs, or record the limitation.

### 4. MINOR — `worktree-619-cwd` exclusion regex over-matches
