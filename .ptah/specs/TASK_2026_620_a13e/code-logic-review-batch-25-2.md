Consequently a normal bench invocation completes and presents model-panel labels as generic labelled/human-style ground truth rather than honestly reporting `model-panel`; this is a success-looking provenance failure in the benchmark evidence. Wire the private manifest into the production invocation (without committing it), validate it against the frozen population/raters, and add an integration-level assertion for that invocation.

## Five logic questions

1. **Silent failure:** Missing panel input falls through to `method: 'labelled'` rather than failing or warning (`rubric-agreement.suite.ts:304-309`; `rubric-ground-truth.ts:504-508`).
2. **Unexpected user action:** Running the normal production benchmark entry point after accepting these fixtures yields the incorrect provenance, because that entry point omits `panel` (`run-memory-skills.entry.ts:77-82`).
3. **Wrong-answer input:** A fully valid committed 105-row model-panel data set produces an incorrect `labelled` method when the private manifest is absent from options; no malformed input is necessary (`rubric-ground-truth.ts:444-508`).
4. **Dependency failure/shape:** The private manifest is not read on the production route at all, so it cannot be validated for provider/family/model, timeout/failure counts, or population before a scorecard is emitted (`run-memory-skills.entry.ts:77-82`; `rubric-agreement.suite.ts:66-83`).
5. **Unspecified/missing requirement:** The design says private manifests capture provider/model, packet count, responses/failures, unresolved share, and timestamp (`design-addendum-codex-recording-and-model-panel.md:87`), but Batch 25 lacks a production-only manifest-discovery/configuration contract. That gap is what allowed test-only provenance injection to stand in for the real run.
