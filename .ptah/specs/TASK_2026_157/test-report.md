### F-D2 forced structural-failure check — CONFIRMED FAIL (expected, per orchestrator steer + code-logic-review.md Serious Issue 1)

Per the orchestrator's steer and `code-logic-review.md` ("Serious Issue 1" / Failure Mode 2), the current code is expected to leak a phantom `in_progress` transition on a **structural** `chat:start` failure (as opposed to a thrown exception) — e.g. `AUTH_REQUIRED` or model-unavailable, where the backend RPC call itself succeeds but returns `data.success===false`. Root cause (traced, not modified):

- `MessageSenderService.startNewConversation` (`libs/frontend/chat/src/lib/services/message-sender.service.ts:389-398`): on a structural failure (`!result.success || authFailed || result.data?.success === false`) it logs to `console.error` and calls `sessionManager.failSession()`, but the `try` block does **not** `throw` — the function returns normally.
- `TaskPromptBridgeService.consume()` (`libs/frontend/chat/src/lib/services/chat-store/task-prompt-bridge.service.ts:54-71`): `outcome` defaults to `{success:true}` and is only overwritten in the `catch` block. Since `send()` never throws on a structural failure, `outcome` stays `{success:true}` and `request.resolve(outcome)` fires with success.
- `TaskStartService.start()` (`libs/frontend/tasks-ui/src/lib/services/task-start.service.ts:84-97`): sees `launch.success === true` → calls `store.updateStatus(taskId, 'in_progress')`.

**Empirically forced and confirmed** via a temporary integration spec (`__qa157-fd2-forced-failure.spec.ts`, deleted after the run) wiring the **real** `AppStateManager` + `TaskPromptBridgeService` together, with `MessageSenderService.send` mocked to mimic the real structural-failure behavior (resolves normally, does not throw/reject — exactly what `startNewConversation` does per the trace above):

```
[QA.2/F-D2] resolve() called with: {"success":true}
```

`expect(resolve).toHaveBeenCalledWith({ success: true })` — **passed**, i.e. the bridge genuinely resolves success on a structural failure. Chained through `TaskStartService`, this means `tasks:updateStatus(taskId, 'in_progress')` **would** fire, producing the phantom `in_progress` board state described in `code-logic-review.md`.

**This is recorded as a CONFIRMED FAIL against the acceptance criterion "structural-failure branches leave no phantom transition," tied to follow-up F-D2 (tracked in `tasks.md`'s Follow-ups table, MED priority, ACCEPTED as a phase-1 deviation by the Batch D team-leader verdict).** Per instructions, this is reported, not patched. The timeout and thrown-exception branches (the other two R6.4 failure modes) both correctly leave no transition, as shown above.
