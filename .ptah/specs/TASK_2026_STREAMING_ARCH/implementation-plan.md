## Decisions

### D1 — One common stream-delivery coordinator, not three independently tuned host queues

- **Requirement:** no per-chunk traffic for hidden sessions while retaining VS Code, Electron, and CLI behaviour. **Rule source:** `user-requested`.
- **Decision:** add a backend `ChatStreamDeliveryCoordinator` at the existing `ChatStreamBroadcaster` boundary. It owns only per-tab visibility, ordered batch selection, hidden-tail retention, sequence assignment, and reveal snapshots. It accepts the existing `StreamBatchBuffer` sink contract rather than parsing agent events or knowing UI trees. **Rule source:** `lane-proposed`.
- **Why:** the broadcaster already knows the stable `tabId` on every `chat:chunk` payload and owns lifecycle ordering; it currently broadcasts through a minimal `WebviewManager` port. [Verified: `chat-stream-broadcaster.service.ts:75-78,135-181,233-247`]
- **Rejected alternative:** make `MessageRouterService` drop hidden chunks. It avoids template work but still pays host-to-webview serialization, postMessage/IPC traffic, router queueing, and batch expansion, violating the stated hidden-session traffic requirement. **Rule source:** `lane-proposed`.
- **Existing-code effect:** replace only the broadcaster's direct `batch.push(...broadcastMessage...)` sink with coordinator publication. Keep `StreamBatchBuffer` ordering, in-flight cap, `dispose`, and `settle` contracts unchanged. **Rule source:** `lane-proposed`.

### D2 — Visibility is a negotiated delivery preference keyed by `tabId`

- **Requirement:** focused / visible / hidden sessions with snapshot-on-reveal. **Rule source:** `user-requested`.
- **Decision:** use the stable frontend `tabId` as the delivery key, not the SDK `sessionId`; send one typed `chat:setStreamViewport` RPC whenever the focused tab, rendered-tab set, or route/surface activity changes. The request declares `protocolVersion: 2`, one optional `focusedTabId`, and a deduplicated `visibleTabIds`; omission of a streaming tab makes it hidden. **Rule source:** `lane-proposed`.
- **Why:** a fresh stream begins with a `tabId` before the real SDK id is known, and the broadcaster specifically retains that tab identity through the loop. [Verified: `chat-stream-broadcaster.service.ts:150-165,233-240`]
- **Rejected alternative:** key delivery by `sessionId`. The initial `sessionId` can be absent/rekeyed, creating a race exactly at stream start. **Rule source:** `lane-proposed`.
- **Existing-code effect:** evolve the existing `active` / `SURFACE_ACTIVE` composition, which currently computes only active versus frozen. [Verified: `chat-transcript.component.ts:218-229`; `app.config.ts:136-143`]

### D3 — A reveal snapshot is an ordered, bounded delta tail with an explicit resync path

- **Requirement:** hidden sessions receive no per-chunk host traffic and catch up on reveal. **Rule source:** `user-requested`.
- **Decision:** while hidden, retain each tab's ordered `FlatStreamEventUnion` tail in the coordinator and send exactly one `chat:streamSnapshot` envelope on hidden-to-visible/focused transition. The envelope carries the tab/session identifiers, monotonically increasing `fromSequence`/`toSequence`, and ordered events. The frontend applies those events through the existing stream-processing path inside a single presentation flush. **Rule source:** `lane-proposed`.
- **Failure and memory contract:** cap a retained tail by both event count and serialized byte budget. On overflow, discard the tail, mark `resyncRequired: true`, and make the reveal path use the existing `chat:resume` history response rather than retain unbounded duplicate state. `chat:resume` already returns replayable `FlatStreamEventUnion[]` and stale-snapshot metadata. [Verified: `rpc-chat.types.ts:280-329`]
- **Assumption to verify before implementation:** an active session's resume/history path includes every event needed to reconstruct the currently streaming turn after an overflow. The implementer must trace `chat:resume` through its active-session handler and add a regression fixture for an overflow during an open turn. If it does not, the coordinator must obtain the canonical active-turn event source from the session owner; it must not create a second unbounded event log.
- **Rejected alternative:** cache a frontend `StreamingState` model in the host. That crosses the frontend/backend library boundary and duplicates `ExecutionTreeBuilderService` semantics. **Rule source:** `project-rule`.

### D4 — Per-message presentation records, not a rebuilt transcript signal

- **Requirement:** avoid rebuilding the transcript on each chunk and update only the streaming message incrementally. **Rule source:** `user-requested`.
- **Decision:** introduce a webview-scoped `StreamPresentationStore` with a stable `WritableSignal` record for each live message id and a separate structural transcript signal. Stream application mutates the affected record's revision/content/tree reference; finalization transfers that same record to the finalized structural collection by id. The transcript reads stable message slots and observes only the record for the bubble it renders. **Rule source:** `lane-proposed`.
- **Why:** current id tracking and finalization identity are intentional and must survive: the final tree/message id is preserved so Angular reuses the bubble. [Verified: `chat-transcript.component.ts:431-443`; template track: `chat-transcript.component.html:34-62`]
- **Rejected alternative:** cache more copies of `allMessages`. The component already memoizes the merged list by finalized/streaming array identity, but upstream `streamingMessages()` still creates new filtered/mapped arrays. [Verified: `chat-transcript.component.ts:403-469`]
- **Existing-code effect:** `ChatStore`/streaming handler continues to own event semantics; it publishes a narrow message change-set to the presentation store after each event or snapshot application. `ChatTranscriptComponent` stops deriving trees/sets/maps for content-only revisions. **Rule source:** `lane-proposed`.

### D5 — Incremental Markdown must preserve the final sanitizer contract

- **Requirement:** address performance batch 3 without weakening Markdown safety. **Rule source:** `user-requested`.
- **Decision:** add `StreamingMarkdownRenderer` for the one mutable assistant message. It renders only completed block boundaries with the existing marked/extensions/DOMPurify final pipeline; the unfinished suffix is escaped text until its block closes. On finalization, replace the incremental result with the existing full renderer output and assert DOM-equivalence for the supported fixture corpus. **Rule source:** `lane-proposed`.
- **Why:** the current renderer explicitly documents whole-content marked, five extensions, DOMPurify, and DOM reparse per growing update. [Verified: `execution-node.component.ts:441-451`]
- **Rejected alternative:** merely raise the rAF throttle. It trades latency for fewer O(n) reparses and leaves the cumulative O(n²) behaviour. **Rule source:** `lane-proposed`.

### D6 — Zoneless is a migration phase, not a prerequisite or a blanket timer rewrite

- **Requirement:** use `provideZonelessChangeDetection`, exhaustive no-changes audit, migration order, and rollback. **Rule source:** `user-requested`.
- **Decision:** after the delivery and presentation phases are stable, replace `provideZoneChangeDetection` in the webview with `provideZonelessChangeDetection`; enable `provideCheckNoChangesConfig({ exhaustive: true })` only in the development/test migration configuration, not the normal shipped provider list. **Rule source:** `lane-proposed`.
- **Why:** Angular documents the zoneless scheduling notifications that are relevant here—signals read in templates, listeners, `markForCheck`, inputs, and view attachment—and documents exhaustive checking as a way to expose OnPush-hidden changes. [Verified: `core.d.ts:3103-3121,3448-3471`]
- **Rejected alternative:** remove `zone.js` and its provider with the first stream change. Batch 1 deliberately left non-stream messages zone-required because timers, dialogs, async side effects, and RPC ordering had not been audited. [Verified: `perf-batch1-report.md:21-55,74-84`]

## Data flow and scheduling

1. **Focused:** an SDK event reaches the coordinator; it appends to the existing batch buffer. One `StreamFlushScheduler` rAF applies all received records for the focused tab, then publishes their signal revisions once. Markdown gets at most that same frame. **Rule source:** `user-requested`.
2. **Visible:** events are batch-delivered but the webview scheduler coalesces them to a configurable-in-code, fixed 50 ms maximum publication cadence (one timer per visible surface, never per message). Input and focused work win. **Rule source:** `lane-proposed`.
3. **Hidden:** the coordinator records ordered tail state but does not call the host transport; the transcript stays at its existing frozen VM. On reveal it emits one snapshot or an explicit resync request. **Rule source:** `user-requested`.
4. **Terminal ordering:** coordinator flushes the focused/visible batch or reveal tail before `chat:complete`/`chat:error`; on a hidden terminal it retains the terminal state in the snapshot/resume result, then releases state only after snapshot acknowledgement or after the normal session retention boundary. **Rule source:** `lane-proposed`.
5. **Scroll/layout:** presentation publication produces one transcript-level dirty signal. The existing rAF scroll path must batch reads before writes, and the inline agent `MutationObserver` / 50 ms timeout must be replaced or gated by that shared dirty signal. **Rule source:** `user-requested`; verified current competing observer/timer: `inline-agent-bubble.component.ts:771-825`; existing transcript rAF: `chat-transcript.component.ts:827-936`.

## Acceptance metrics and observability

- **INP:** proposed approval gate is p75 keyboard interaction INP ≤200 ms during a representative active stream and no sampled interaction >500 ms; baseline is 2,048 ms. **Rule source:** `lane-proposed`; baseline verified in `perf-inp-report.md:7-19`.
- **Frames:** focused stream has no more than one presentation flush/rAF per display frame and no long task >50 ms attributable to transcript/markdown flush in the representative trace. Visible stream publishes no faster than every 50 ms; hidden publishes zero chunk envelopes. **Rule source:** `lane-proposed`.
- **Message counts:** instrument `receivedEvents`, `transportEnvelopes`, `suppressedHiddenEvents`, `snapshotEvents`, `snapshotBytes`, `snapshotOverflowResyncs`, `focusedFlushes`, `visibleFlushes`, and `lateFrames`, keyed only by ephemeral tab hash/counter—not content, prompts, or secrets. **Rule source:** `lane-proposed`.
- **Correctness:** sequence gaps, duplicate snapshots, unknown protocol versions, and snapshot apply failures report a bounded diagnostic and trigger resync; they never tear down the SDK stream. **Rule source:** `project-rule`; existing buffer failure posture continues stream delivery: `stream-batch-buffer.ts:35-40,184-201`.

## Questions for the user

1. Which release gate should approve the architecture's performance phases?

   - **p75 ≤200 ms and no interaction >500 ms (Recommended)** — a strong, measurable reduction from the 2,048 ms baseline.
   - **p75 ≤300 ms and no interaction >750 ms** — lower rollout risk but leaves less headroom for long transcripts.
   - **Relative-only: ≥75% improvement** — accommodates host variance but is harder to use as a release gate.

2. Is a one-release bootstrap fallback acceptable for the zoneless phase?

   - **Yes, remove it after one stable release (Recommended)** — permits a low-risk provider rollback while avoiding a permanent dual runtime.
   - **No fallback** — simpler final state but requires all hosts to migrate atomically.
