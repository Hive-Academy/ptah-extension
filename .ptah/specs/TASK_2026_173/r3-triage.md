## Prerequisite: the `rev-parse --verify --quiet` substitution

2A's docstring (`git-info.service.ts:483-494`) claims the plan's originally
specified `git cat-file -e <rev>:<path>` exits 128 (not 1) for a missing
path, and substitutes `git rev-parse --verify --quiet <rev>:<path>` to get a
clean 0/1/128 partition. **Independently verified against real git 2.54.0
(Windows)**:

```
git cat-file -e HEAD:missing.txt        -> exit 128  (fatal: path 'missing.txt' does not exist in 'HEAD')
git rev-parse --verify --quiet HEAD:missing.txt -> exit 1
```

Confirmed exactly as claimed. The substitution is correct: `cat-file -e`
would have misclassified every `absent` row as `error` had it shipped as
originally planned. `rev-parse --verify --quiet` gives the exact 0 (resolves)
/ 1 (absent) / other (error, further probed) partition `readBlob` depends on.

## Follow-up findings (non-blocking, out of Batch 2 scope)

1. **Directory rows produce a generic `unknown` error rather than a
   directory-specific message.** Clicking an untracked directory row in
   Source Control (row 14 above) is technically clickable today and resolves
   to a correct, non-crashing, persistent error overlay — but the copy says
   "Git could not read this file" rather than something like "Cannot diff a
   directory." Low severity: no data-integrity risk, no crash, no
   misrendering as content. Candidate fix: either disable/hide the diff
   affordance on `isDirectory` rows in `SourceControlFileComponent`, or add a
   dedicated `is-a-directory` outcome/code. Filed as a UX polish follow-up,
   not a Batch 2 blocker — A3's actual requirement (never render an unreadable
   path as fabricated content) is already satisfied.
2. **Submodule paths surface as the generic `unknown` error code**, not a
   `submodule` or `gitlink` -specific code. Same non-blocking shape as #1 —
   correct, safe behaviour with a slightly less specific message than ideal.
