## Findings

1. **Serious.** D9 capture reads the latest turn, so a late write from an older turn does not keep T1. Plan lines 14, 33, 47, and 132.

   The SDK callback payload is `prompt`, `sessionId`, `workspaceRoot`, and `timestamp` (`libs/backend/agent-sdk/src/lib/helpers/user-prompt-submit-callback-registry.ts:8-13`). There is no turn id. `proposeConfig` knows only `getCallerSdkSessionId()` (`libs/backend/vscode-lm-tools/src/lib/code-execution/namespace-builders/harness-namespace.builder.ts:1098-1108`). The plan stores one "active turn start" per SDK session and workspace and reads it at write time, then clears that slot on terminal or abort (plan lines 14 and 47).

   Sequence the acceptance test requires: T1 start, user choice at T2, new `UserPromptSubmit` at T3 on the same session, proposal write at T4 from the T1 turn. The T3 callback overwrites the single slot before T4 reads it, so the stored `turnStartedAt` is T3. T3 is later than `chosenAt`, so the stale proposal replaces the user's field. Clearing the slot when T1 ends makes T4 store no time instead. Missing time loses to the user on chosen fields, which is safe for that one comparison, and it is a different result from "retains older start" (plan line 47).

   Hydration applies "oldest first" in append order (plan line 33). A late T1 revision is appended after a T3 revision, so it is applied last. Unchosen fields "accept latest proposal" (plan line 34). Latest-by-append lets the stale T1 body replace T3's unchosen fields even when `turnStartedAt` was stored correctly.

   Required change: freeze the proposing turn's start inside that tool invocation and pass it into `save` as an argument. A later `UserPromptSubmit` on the same session must not replace a start already frozen for an in-flight write, and terminal/abort must not drop a start a late write still has to persist. Order revisions by `turnStartedAt` (absent stays unattributed and loses to the user; it does not sort after a newer attributed revision). Add the T1/T2/T3/T4 test where T3's callback runs before `save` reads the clock, and a second test where T1's write is persisted after T3's revision and unchosen fields stay on T3.

## Decisions for the user

1. **Abort-failure warning (plan lines 151-153).** The recommendation to use an existing host warning outside Setup Hub is the right question, and the APIs that exist do not satisfy it. `NotificationLedgerService` (`notification-ledger.service.ts:121-163`) stores completion cards and pending questions. `ActionBannerService.showWarning` (`libs/frontend/chat/src/lib/services/action-banner.service.ts:27-28,90-96`) is dismissible via `clear()` and auto-clears after 8 seconds, and ChatView is what renders it (`chat-view.component.ts:374-409`). On Setup Hub the chat column is the hidden standalone surface, so that banner is not on screen after a leave that lands on the Hub. `vscode.window.showWarningMessage` is used by the extension host for file prompts (`apps/ptah-extension-vscode/src/services/rpc/handlers/file-rpc.handlers.ts:205`) and is not a webview-or-Electron persistent banner. There is no current host API that is persistent, user-dismissed, and visible on the Hub without a Hub element. Prefer amending D10 for the one withdrawn status line (design line 304), or explicitly accept a warning that disappears on its own and is easy to miss after navigation. Do not add the banner inside the implementation batch before that choice.

2. **Hub confirm copy (finding 2).** The existing dialog says "Discard and start" and "stops it and clears its transcript and configuration" (`setup-hub.component.ts:1111-1131`). The leave-dialog flow must not abort on that click. D10 forbids changing the words. Either accept that this button now only opens the builder leave dialog, or allow a copy change on this one existing dialog. The reverse direction (AI Team Builder card while New Project is open) has no dialog today (`1298-1300`); that path can go straight to the builder leave dialog with no new Hub element.

3. **Relay failure while the user is still on the Hub (finding 5).** If no current Hub element can show that error, it is the same class of decision as the abort warning: name an existing element, amend D10, or accept that a malformed relay is logged until the builder page is open.
