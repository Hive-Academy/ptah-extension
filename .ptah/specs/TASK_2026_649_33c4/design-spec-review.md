## Findings

1. **Blocking — `design-spec.md §11.1` (`:370`), `decisions.md D1`.** The required host-controlled suppression of 677's session header/inspector is a real shared chat change, while D1 says “No chat changes beyond 648.” Current `SessionEmbedComponent` has no such input. Revise the spec to use an existing host-level composition path if one exists, or reserve this specific exception for the user; do not call it an architect-only decision or state “Clarifications Needed: None.” Also specify what happens before and after 677 lands so the builder never shows two headers/right panels.
2. **Serious — `design-spec.md §4:88`, `§11.3:372`; `chat-input.component.ts:234–240,1574–1581`.** `requestComposerPrefill` fills the message value; it cannot supply the claimed Configure *placeholder*. Revise the first screen to use the shared chat's existing generic placeholder with builder guidance in the sidebar, or explicitly request approval for a scoped chat placeholder API. Keep actual prefill for preset notes and “propose it again,” where sendable text is intended.
3. **Serious — `design-spec.md §11:361–366`, `workflow-tab-launcher.service.ts:26–59`.** Splitting `WorkflowTabLauncherService` changes shared chat infrastructure beyond 648 and the current `open()` navigates to chat before the builder could host the tab. Specify the builder entry sequence and make grid-cap refusal handling conditional on a caller that actually adopts into the grid. If the split is necessary, include it in the D1 user decision; otherwise put create/tag/preamble in the builder adapter and keep normal-chat adoption owned by the grid as D2 requires.
4. **Serious — `design-spec.md §5.3:137–148`, `§11.4–6:373–375`; `setup-hub.component.ts:1444–1453`.** The backend's stack result is currently dropped before navigation, and neither the tab type nor the page route identifies a stored profile. Specify an atomic tab-ID-keyed handoff, durable schema/validation and reload lookup, plus when the “details unavailable” fallback is shown. Bind the page to the intended workflow tab rather than inferring from whichever tab is active.
5. **Serious — `design-spec.md §5.4:152–166`, `§11.5:374`; `harness-builder-state.service.ts:85–103,312`.** “Persist a per-tab preview snapshot and merge it over hydrated proposals” lacks the conflict rule for later agent updates, tab replacement/deletion and workspace isolation. Define snapshot ownership and precedence per field, including clearing stale edits after Start over/Discard, so live agent proposals cannot overwrite the user's chosen helper result or resurrect an old preview.
6. **Moderate — `design-spec.md §5.5:182`, `§12:422`; `parity-inventory.md:72`.** Row 54 is labeled `wire`, yet search-skills/create-skill have no new caller. Correct the parity decision with evidence that existing agent tools satisfy the intended scope, or add a real path for those wrappers; this is a scope choice if it intentionally drops the requested wiring.
7. **Moderate — `design-spec.md §7.1:260–264`, `§8:299–304`.** The dialog correctly specifies trap/Escape/return, but the non-modal full-cover sheet leaves the header operable and relies on `inert` for the covered chat. Specify focus behavior if the sheet closes while focus is in a helper/result control, and when a dialog opens over that sheet. Return focus to the peek bar or the invoking control and restore the previous inert state. The 400 px screenshots support visual layout, not these focus transitions.
8. **Minor — `design-spec.md §13:439`.** Relabel the sidebar recipe as inherited 648/677 guidance or lane-proposed; it is not a project rule in the supplied brief.

## Decisions for the user

1. **D1 exception:** May 649 add a minimal host-controlled chat chrome switch to suppress the 677 header/inspector on the builder embed? This is the only clearly necessary shared ChatView change proposed; D1 currently forbids it. The existing tab-targeted composer prefill needs no exception.
2. **Shared launcher scope:** If the builder cannot implement create/tag/navigation locally, may 649 split the shared `WorkflowTabLauncherService` as section 11 recommends? This is also a chat-side change beyond 648.
3. **Row 54 scope:** Should `harness:search-skills` and `harness:create-skill` be wired to new frontend call paths, or is preserving the existing agent-tool capability sufficient? The inventory currently says `wire` while the design does not add callers.

No user decision is needed for the remaining storage, focus, responsive or visual details; those can be specified by the architect and designer.
