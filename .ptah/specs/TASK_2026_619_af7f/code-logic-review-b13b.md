## Verdict: REVISE — 4/10

Two blocking races leave the index silently wrong after a create or delete during a census. This is below 5/10 because the stated edit/add/delete behavior is not reliable; it is above 3/10 because storm handling, root-scoped full-run ownership, and same-file write ordering are implemented. The supplied scoped Jest/typecheck/lint/prettier evidence is clean, but does not exercise either race with the real purge/delete sink.

## Requirements

1. **13b.1 — NOT MET.** The lifecycle correctly keeps create/update events debounced and calls `reindexFile` during a full run, without setting `followUp` (`libs/backend/thoth-runtime/src/lib/workspace-index-lifecycle.ts:323-358`), and preserves the storm/overflow/directory-delete branches (`:264-321`, `:360-395`). However, a created path absent from discovery is later removed by the census purge; a supported-file delete can be resurrected by the census. Both make the required per-file result non-durable.
2. **13b.2 — MET.** `indexWorkspace` records a root run synchronously before discovery and clears it in `finally` (`libs/backend/workspace-intelligence/src/services/code-symbol-indexer.service.ts:487-510`, `:622-649`, `:670-682`). `ensureIndexFresh` and full `reindex()` gate on `runIsActive` (`libs/backend/vscode-lm-tools/src/lib/code-execution/namespace-builders/code-namespace.builder.ts:236-244`, `:316-339`, `:510-524`). The active signal is scoped by `graphPathIdentity`, which normalizes slashes, trailing slashes and Windows case (`libs/backend/workspace-intelligence/src/ast/dependency-graph.service.ts:199-215`), so a run for root A does not suppress root B.
3. **Same-path per-file writes — MET.** Both census and `reindexFile` route through `indexFileRecorded` (`libs/backend/workspace-intelligence/src/services/code-symbol-indexer.service.ts:888-892`, `:1002-1027`), and its `withFileLock` encloses the read, analysis, replacement, and outcome recording (`:715-763`, `:1096-1287`). A census cannot write content read before a later per-file write; the second lock holder reads after the first write settles.

## Findings

1. **BLOCKING — a successful add-then-query can regress to no results when the census purges.** Discovery snapshots `presentPaths` before the batch writes (`libs/backend/workspace-intelligence/src/services/code-symbol-indexer.service.ts:791-832`). A file created after that snapshot is indexed by the newly enabled lifecycle path (`libs/backend/thoth-runtime/src/lib/workspace-index-lifecycle.ts:323-358`), but the complete census subsequently calls `purgeMissing(workspaceRoot, presentPaths)` unchanged (`libs/backend/workspace-intelligence/src/services/code-symbol-indexer.service.ts:928-934`, `:1067-1087`). Since that new path is absent from `presentPaths`, purge deletes the rows written by `reindexFile`. The query can therefore pass in the interval after the per-file write and before purge, then silently regress once the census finishes. A rename has the same new-path failure; an ordinary update of a discovered path is not a purge candidate. Fix: have `purgeAbsentPaths` exclude paths successfully written by non-census `reindexFile` while a run is active (or merge them into that run's purge-present set). This is safer than checking candidates on disk: it preserves the exact per-file write that won the lock, avoids a second filesystem race, and does not retain rows for a file whose reindex read failed.

2. **BLOCKING — a supported-file delete races the census and can be permanently resurrected.** The lifecycle delete calls the sink directly (`libs/backend/thoth-runtime/src/lib/workspace-index-lifecycle.ts:343-351`; adapter `:147-153`) rather than the indexer's locked path. Census writes are serialized only through the indexer's private file lock (`libs/backend/workspace-intelligence/src/services/code-symbol-indexer.service.ts:715-763`) and later replace all rows (`:1051-1061`, `:1265-1287`). If census analysis read the file, then the watcher delete runs, the census replacement may execute afterward and restore symbols. Because the deleted path was already captured in `presentPaths`, the final purge retains it (`:791-803`, `:928-934`). Fix: expose a locked `deleteFileRecorded`/`deleteSymbolsForFile` operation on `CodeSymbolIndexer` that uses the same `withFileLock` identity as `reindexFile`, and route the lifecycle adapter through it; it must record a deletion/tombstone for the active run so purge cannot restore it.

## Five logic questions

1. **Silent failure:** both findings produce normal watcher completion and a success-looking full-run result while search later returns stale or missing symbols (`workspace-index-lifecycle.ts:343-358`; `code-symbol-indexer.service.ts:928-934`).
2. **Unexpected user action:** save/create a supported file, query it while the census is still running, then query after completion; or delete such a file while its census parse/write is in progress (`workspace-index-lifecycle.ts:323-358`; `code-symbol-indexer.service.ts:888-892`).
3. **Wrong-answer input:** a newly created or rename-destination path absent from the discovery snapshot is purged; a deleted source whose census replacement was already underway is restored (`code-symbol-indexer.service.ts:791-832`, `:928-934`).
4. **Dependency failure/timeout/malformed shape:** per-file read, parse, and write failures are converted to counted failed outcomes (`code-symbol-indexer.service.ts:1114-1153`, `:1265-1278`); purge failure is logged and rethrown (`:1067-1081`), and background callers report it (`code-namespace.builder.ts:279-292`). No timeout boundary is introduced by this batch. The unhandled issue is ordering, not an observed dependency-error swallow.
5. **Missing requirement:** the batch specifies applying per-file events during a census but does not specify the required purge/tombstone coordination. Its tests prove calls occur during a held full-run mock, not that their effects survive the real census purge or a concurrent sink replacement (`workspace-index-lifecycle.spec.ts:190-238`; `batches.md:1690-1700`).

## Round 2

### Verdict: REVISE — 6/10

The two Round 1 per-file races are fixed, but a second full census can still overlap the lifecycle census for the same root and reintroduce the stale-snapshot purge race. This is 6/10 rather than 7/10 because an explicit user reindex can take that path during boot; it is above 5/10 because the ordinary watcher create/update/delete path now retains its result. Supplied scoped Jest/typecheck/lint/prettier evidence is accepted and was not rerun per instruction.

1. **Round 1 finding 1 — FIXED.** A non-census `reindexFile` that actually replaces rows records its path on every active root run (`libs/backend/workspace-intelligence/src/services/code-symbol-indexer.service.ts:803-824`), and purge merges those paths with the discovery snapshot (`:1148-1186`). Thus a create or rename destination written after discovery is retained without a second disk check.
2. **Round 1 finding 2 — FIXED.** Watcher deletes now call the indexer's locked delete surface (`libs/backend/thoth-runtime/src/lib/workspace-index-lifecycle.ts:345-359`); that method serializes the sink delete with the same identity and tombstones every active run (`libs/backend/workspace-intelligence/src/services/code-symbol-indexer.service.ts:1075-1085`). A census which acquired the lock first checks that tombstone before replacement (`:1379-1396`), and purge also drops the discovered path (`:1148-1173`).

### New findings

1. **SERIOUS — same-root full censuses are still concurrent, so the older census can purge rows the newer one indexed.** `indexWorkspace` unconditionally starts a run (`libs/backend/workspace-intelligence/src/services/code-symbol-indexer.service.ts:512-535`), while `beginRun` explicitly supersedes rather than serializes an older run and retains both in `runsInProgress` (`:641-675`). The runtime exposes an ungated user-initiated `symbolIndexer.indexWorkspace` through `runSymbols` (`libs/backend/thoth-runtime/src/lib/boot-thoth-runtime.ts:506-542`) at the same time the lifecycle starts its background census (`:561-588`). If the older discovery snapshot lacks a newly created path, the newer census writes it as a census write (so it is not put in the older run's `keptPaths`, `code-symbol-indexer.service.ts:803-824`); when the older run later calls purge, it deletes that newer row (`:1148-1186`). Proposed fix: serialize/coalesce `indexWorkspace` per root in `CodeSymbolIndexer` (or make all callers join the active root promise), rather than representing overlapping full censuses as superseded runs; add an integration test with an old held snapshot, a newer run that indexes a new path, then release the old purge.
2. **MINOR — `workspaceSymbolIndexFrom` retains a dead `sink` API and both hosts still resolve it although the adapter discards it.** The adapter accepts then voids `sink` (`libs/backend/thoth-runtime/src/lib/workspace-index-lifecycle.ts:137-156`), while runtime boot resolves/passes it (`libs/backend/thoth-runtime/src/lib/boot-thoth-runtime.ts:573-577`) and CLI bootstrap does the same (`libs/backend/cli-engine/src/lib/bootstrap/cli-workspace-index.ts:131-135`). This obscures that deletes must go through the indexer and leaves needless DI coupling. Proposed fix: remove the argument and its `ISymbolSink` imports/resolutions from both hosts, and update the adapter specs (`libs/backend/thoth-runtime/src/lib/workspace-index-lifecycle.spec.ts:489-504`).

### Five logic questions

1. **Silent failure:** overlapping full runs both complete successfully, but the older run can silently erase symbols written by the newer run's census at purge (`code-symbol-indexer.service.ts:1148-1186`).
2. **Unexpected user action:** press a user-initiated reindex while the boot lifecycle census is still running; the two calls use the same `CodeSymbolIndexer` without a root-level join (`boot-thoth-runtime.ts:506-542`, `:561-588`).
3. **Wrong-answer input:** a supported file created after the older census discovery but before the newer user census is indexed becomes absent again when the older snapshot purges it (`code-symbol-indexer.service.ts:803-824`, `:1148-1186`).
4. **Dependency failure/timeout/malformed shape:** delete errors remain observed and reported by the lifecycle (`workspace-index-lifecycle.ts:345-358`); purge errors remain logged and rethrown (`code-symbol-indexer.service.ts:1176-1194`). `AsyncLocalStorage` only bypasses the lock for work causally running inside `fileLockContext.run` (`:747-767`); no current watcher or runtime caller is such a re-entry, so it neither avoids a real external wait nor currently creates a demonstrated deadlock.
5. **Missing requirement:** the revision assumes one full run per root, but the indexer deliberately permits supersession (`code-symbol-indexer.service.ts:641-675`) and the user-reindex route supplies a concurrent entry point (`boot-thoth-runtime.ts:506-542`). The contract needs one root-level full-census owner or explicit merge semantics.
