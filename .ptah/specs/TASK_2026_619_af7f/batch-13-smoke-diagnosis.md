## Job B — root causes

### 1. Watcher binding and delivery

`IWorkspaceWatcher` is bound in the bench host's normal CLI bootstrap. `bootCodeExecutionHost` calls `withEngine` without a bootstrap override and explicitly enables `workspaceIndex` ([bench-host-boot.ts:417-428](D:/projects/ptah-extension/.claude-worktrees/task-619-tool-benchmark/tools/mcp-bench/src/transport/bench-host-boot.ts:417)). The default `CliDIContainer.setup` unconditionally supplies `workspaceWatchHost: createCliWorkspaceWatcherOptions(container, __dirname)` ([container.ts:395-407](D:/projects/ptah-extension/.claude-worktrees/task-619-tool-benchmark/libs/backend/cli-engine/src/lib/container.ts:395)); platform-cli registers `WORKSPACE_WATCHER` when that option is supplied ([registration.ts:111-116](D:/projects/ptah-extension/.claude-worktrees/task-619-tool-benchmark/libs/backend/platform-cli/src/registration.ts:111)). Therefore the premise that this bench process has no binding because no host was supplied is false.

Delivery cannot be proven from the scorecard alone: it contains no watcher-host diagnostic. The failures are consistent with delivery, because the lifecycle deliberately turns an edit received during a full run into a trailing full run instead of calling `reindexFile` ([workspace-index-lifecycle.ts:320-325](D:/projects/ptah-extension/.claude-worktrees/task-619-tool-benchmark/libs/backend/thoth-runtime/src/lib/workspace-index-lifecycle.ts:320), [342-346](D:/projects/ptah-extension/.claude-worktrees/task-619-tool-benchmark/libs/backend/thoth-runtime/src/lib/workspace-index-lifecycle.ts:342)). A missing watch-host bundle would make `watch()` fail only when the lifecycle starts it; that error is reported through `onError` ([workspace-index-lifecycle.ts:226-237](D:/projects/ptah-extension/.claude-worktrees/task-619-tool-benchmark/libs/backend/thoth-runtime/src/lib/workspace-index-lifecycle.ts:226)), but no such evidence was supplied. Real `ptah mcp-serve` uses the same normal CLI container, so it supplies the same watcher host; the bench is not intentionally a watcher-less configuration.

### 2. Per-file work during a full run

At the lifecycle layer it is deferred, not run: both `schedule` and `apply` check `fullRun`, set `followUp`, and return ([workspace-index-lifecycle.ts:320-325](D:/projects/ptah-extension/.claude-worktrees/task-619-tool-benchmark/libs/backend/thoth-runtime/src/lib/workspace-index-lifecycle.ts:320), [342-346](D:/projects/ptah-extension/.claude-worktrees/task-619-tool-benchmark/libs/backend/thoth-runtime/src/lib/workspace-index-lifecycle.ts:342)). The full run finishes before the one queued follow-up is started ([workspace-index-lifecycle.ts:384-398](D:/projects/ptah-extension/.claude-worktrees/task-619-tool-benchmark/libs/backend/thoth-runtime/src/lib/workspace-index-lifecycle.ts:384)). Thus an edit or addition is invisible until the full corpus has completed, then another full run completes.

The indexer itself would support the priority behavior. Its lock is per file, not per workspace ([code-symbol-indexer.service.ts:702-749](D:/projects/ptah-extension/.claude-worktrees/task-619-tool-benchmark/libs/backend/workspace-intelligence/src/services/code-symbol-indexer.service.ts:702)); a per-file reindex only waits when the full run is writing that same file. The current bottleneck is consequently the lifecycle policy, not an unavoidable indexer-wide serialization.

### 3. Competing full runs

Yes. The boot lifecycle starts a full run (`start()` calls `requestFullRun`) ([workspace-index-lifecycle.ts:220-238](D:/projects/ptah-extension/.claude-worktrees/task-619-tool-benchmark/libs/backend/thoth-runtime/src/lib/workspace-index-lifecycle.ts:220)). The first symbol search independently calls `ensureIndexFresh` before reading ([code-namespace.builder.ts:357-370](D:/projects/ptah-extension/.claude-worktrees/task-619-tool-benchmark/libs/backend/vscode-lm-tools/src/lib/code-execution/namespace-builders/code-namespace.builder.ts:357)); when freshness is stale it starts another `indexWorkspace` based only on that namespace's private `inFlight` set ([code-namespace.builder.ts:303-325](D:/projects/ptah-extension/.claude-worktrees/task-619-tool-benchmark/libs/backend/vscode-lm-tools/src/lib/code-execution/namespace-builders/code-namespace.builder.ts:303)). It has no knowledge of the boot lifecycle's run. `CodeSymbolIndexer` permits multiple root runs in progress and only serializes writes for the same file ([code-symbol-indexer.service.ts:429-446](D:/projects/ptah-extension/.claude-worktrees/task-619-tool-benchmark/libs/backend/workspace-intelligence/src/services/code-symbol-indexer.service.ts:429), [702-725](D:/projects/ptah-extension/.claude-worktrees/task-619-tool-benchmark/libs/backend/workspace-intelligence/src/services/code-symbol-indexer.service.ts:702)).

This explains the regression shape, though the scorecard cannot allocate CPU time between the two runs. Batch 12 removed the default cap, so every eligible source file is now discovered and indexed ([batch-12-executor-report.md:32-36](D:/projects/ptah-extension/.claude-worktrees/task-619-tool-benchmark/.ptah/specs/TASK_2026_619_af7f/batch-12-executor-report.md:32)); duplicate uncapped discovery plus duplicated parse/write work is a credible cause of B13's lower progress rate.

### 4. Duration and 120-second feasibility

No full-run completion time was recorded, so this is an estimate, not a measured duration. In B13, the active index reached only 3,566 symbols by the 60-second edit check and 6,286 even after the later 120-second index-age wait, while still `reindexInFlight: true` ([b13 scorecard.md:44-46](D:/projects/ptah-extension/.claude-worktrees/task-619-tool-benchmark/tools/mcp-bench/out/b13-cli-smoke/scorecard.md:44), [50](D:/projects/ptah-extension/.claude-worktrees/task-619-tool-benchmark/tools/mcp-bench/out/b13-cli-smoke/scorecard.md:50)). B11's single lazy-start shape had already reached 5,796 at the first edit check, 8,497 at 60 seconds, and 11,430 at the large-file scenario, yet it too had not settled after its final 120-second wait ([b11 scorecard.md:515-521](D:/projects/ptah-extension/.claude-worktrees/task-619-tool-benchmark/tools/mcp-bench/out/b11-cli-smoke/scorecard.md:515)).

Accordingly, a complete uncapped corpus run is demonstrably longer than 120 seconds on this host; B13's observed rate makes a cold-start answer based on waiting for the full run infeasible. The scenario can meet 120 seconds only by indexing the requested/probe file first (or otherwise prioritizing query-relevant files), then allowing the governed census to continue. The indexer is deliberately governed at each 20-file batch for background runs ([code-symbol-indexer.service.ts:855-898](D:/projects/ptah-extension/.claude-worktrees/task-619-tool-benchmark/libs/backend/workspace-intelligence/src/services/code-symbol-indexer.service.ts:855)), so merely making the full scan eager is neither a reliable latency fix nor an appropriate replacement for priority indexing.

## Recommended fixes

1. **Batch 13 — let watcher changes use `reindexFile` while a census is active.** In [workspace-index-lifecycle.ts](D:/projects/ptah-extension/.claude-worktrees/task-619-tool-benchmark/libs/backend/thoth-runtime/src/lib/workspace-index-lifecycle.ts), remove the `fullRun` deferral branches in `schedule`/`apply` for create/update events. Retain storm coalescing and full-run handling for overflow/truncation/directory deletes. The indexer's per-file lock already prevents an interleaved write to the same file. Add cases showing edit and create are searchable before an intentionally held full run finishes. This is the smallest direct fix for edit-then-query and add-then-query.

2. **Batch 13 — share full-run ownership with lazy freshness.** In [code-namespace.builder.ts](D:/projects/ptah-extension/.claude-worktrees/task-619-tool-benchmark/libs/backend/vscode-lm-tools/src/lib/code-execution/namespace-builders/code-namespace.builder.ts) and [code-symbol-indexer.service.ts](D:/projects/ptah-extension/.claude-worktrees/task-619-tool-benchmark/libs/backend/workspace-intelligence/src/services/code-symbol-indexer.service.ts), expose/consume a root-level active-run signal (or inject one coordinator) so `ensureIndexFresh` does not start a second run when the lifecycle run is active. Keep a single coordinator as the owner of queued follow-ups. This removes the likely B13 throughput regression and preserves the background governor.

3. **Batch 13, if cold-start remains an acceptance gate — query-file priority.** In [code-namespace.builder.ts](D:/projects/ptah-extension/.claude-worktrees/task-619-tool-benchmark/libs/backend/vscode-lm-tools/src/lib/code-execution/namespace-builders/code-namespace.builder.ts), when `searchSymbols` has a valid `filePath` and the index is empty/stale, await `reindexFile` for that file before the search, while the full census remains background work. This can make cold-start and the two edit/add cases independent of an uncapped scan length. It needs an explicit bounded-latency/error test; do not claim it is met merely because a background run started.

4. **Later Batch 15 — persist run timing/progress, not as a substitute for the fixes above.** Batch 15 is explicitly the persisted index-run summary work; record full-run start/end, selected-file count and final symbols there. Its planned summary is the appropriate source of a real duration rather than extrapolation. Do not duplicate Batch 14 (VS Code lifecycle wiring) or Batch 16 (one-line clean coverage); their titles and scope are [batches.md:1683-1765](D:/projects/ptah-extension/.claude-worktrees/task-619-tool-benchmark/.ptah/specs/TASK_2026_619_af7f/batches.md:1683).

## Decisions

- Treated the user-authorized mixed-batch change as a narrow review item; it is fixed and is not the cause of the smoke failures.
- Did not infer absent watcher delivery from a missing result. Static wiring proves the binding; the current lifecycle deferral independently explains the behavior. Host diagnostic evidence is required to prove or disprove event delivery.
- Treated the B13 slow-down as likely duplicate uncapped full runs, not a proven throughput measurement, because the scorecard does not identify each run or record run duration.
- Assigned behavior that makes Batch 13's explicit lifecycle smoke pass to Batch 13; assigned only persisted observability to its already-planned Batch 15.
