## Five style questions

1. **What breaks when requirements change in six months?** Adding another pack outcome or target behavior requires coordinating the selection component's separate kept/failure collections and legacy status mapping (`agent-selection.component.ts:1010`, under `libs/frontend/setup-wizard/src/lib/components/`). That is a maintenance risk, not a claim of a current runtime failure. S1 gives those transitions one owner.
2. **What would a new team member misread here?** `GenerationPreviewService` appears to require a logger, container, checkpoints, and origin reader, but its behavior also depends on multiple runtime registrations (`libs/backend/rpc-handlers/src/lib/handlers/wizard-generation/generation-preview.service.ts:241`, `:671`, `:740`). S2 makes that dependency list explicit.
3. **What does this cost to maintain that a simpler shape would not?** Pack result helpers live with rendering and async install orchestration (`libs/frontend/setup-wizard/src/lib/components/pack-install-prompt.component.ts:81`, `:441`). A pure result module permits focused tests and reuse without importing the component implementation; a component-scoped store reduces the state transitions embedded in the large selection view.
4. **Where is it inconsistent with sibling code?** The decision controls already share a pure state module (`libs/frontend/setup-wizard/src/lib/components/preview-decisions/preview-decisions.state.ts:180`, `:204`, `:227`). `GenerationWorkflowStore` owns its signals and RPC workflow (`libs/frontend/setup-wizard/src/lib/services/generation-workflow.store.ts:27`, `:104`), while the new pack/preview state remains in `agent-selection.component.ts:698`. Existing RPC handlers do use service location, but copying that into new services conflicts with the supplied dependency-injection rule.
5. **What would I do differently, and why is it better rather than merely other?** Use a focused workflow store, explicit injected collaborators, and a pure pack-result module as described in S1–M1. These changes make ownership and dependencies inspectable and reduce changes to large coordinator files. Retain the surface-specific modal layouts: `generation-preview-modal.component.ts:171` intentionally separates definite/conditional rows, while `agent-preview-dialog.component.ts:314` constructs its sidebar presentation. Their differing presentation does not justify a new configurable modal abstraction.
