## Numbered findings

### 1. Serious — interrupted plugin-agent creation permanently excludes the clone from the Library

**Evidence:** `libs/backend/agent-generation/src/lib/services/user-layer/user-layer-plugin-agents.ts:265`, `:268`, `:241`, `:258`, `:191`; `libs/backend/agent-generation/src/lib/services/user-layer/user-layer-mirror.service.ts:547`, `:551`.

**Scenario:** Install a plugin with a new agent. Copying its body succeeds, but hashing the source or writing the origin sidecar fails (for example, the source disappears or the disk fills), or the process exits between the two writes. The body remains. On the next pass, `mirrorOne` sees the body without a sidecar and treats it as user-authored, records a conflict without creating any metadata, and returns. The plugin-agent reconcile wrapper explicitly returns for this same body-without-sidecar case, so the facade's missing-sidecar recovery never runs. `listClones` only includes entries with readable sidecars. A transient failure therefore leaves a persistent agent that ordinary refresh cannot bring into the Library.

**Fix:** Make creation recoverable across the body/sidecar boundary, with durable pending provenance and a digest of the exact bytes being published, or an equivalent staged transaction. On retry, repair only files proven to belong to that interrupted creation; continue preserving genuinely user-authored files without sidecars. Add fault-injection coverage after body publication and before sidecar publication, including a new service instance to simulate restart. Check that retry restores Library visibility without overwriting a user edit.

### 2. Serious — legacy basename-only ownership can adopt another external plugin's content

**Evidence:** `libs/backend/agent-generation/src/lib/services/user-layer/user-layer-plugin-agents.ts:153`, `:154`, `:114`; `libs/backend/agent-generation/src/lib/services/user-layer/user-layer-mirror.service.ts:1732`, `:1735`, `:1747`, `:1750`. The same ownership predicate guards file clones at `user-layer-mirror.service.ts:1799`.

**Scenario:** An existing skill clone came from external plugin A, whose directory basename is `toolkit`. Its older sidecar has `pluginId: 'toolkit'` but no `sourceRef`. Another enabled external plugin B has the same basename and supplies the same skill slug. If B is encountered first on the first reconcile after upgrade, `ownsSourcedClone` accepts B solely because the basename matches. `withSourceIdentity` assigns B's identity. For an unedited clone whose content still matches the old source hash, reconciliation clears/copies the content from B and persists B's identity. For an edited clone, it instead offers divergence against the wrong upstream. A later pass over A cannot correct the now-persisted identity. Distinct descriptors protect already-migrated sidecars, but do not resolve this legacy ambiguity.

**Fix:** Only backfill a missing source identity when ownership is unambiguous across the installed sources, or when trustworthy prior provenance establishes the owner. When two candidate sources share the basename/slug, preserve the clone and report ambiguous ownership rather than fast-forwarding or assigning whichever descriptor is encountered first. Add a legacy-sidecar case with two external coordinates sharing a basename, test both orders, and assert that neither source can silently acquire the other's clone. The helper test currently accepts missing-ref ownership at `libs/backend/agent-generation/src/lib/services/user-layer/user-layer-plugin-agents.spec.ts:73`; extend that coverage to the ambiguous migration case.

### 3. Moderate — per-file failures are reported as a successful refresh

**Evidence:** `apps/ptah-electron/src/activation/plugin-activation.ts:407`, `:412`, `:418`, `:502`, `:507`, `:533`, `:589`, `:642`; the producer increments errors at `libs/backend/agent-generation/src/lib/services/user-layer/user-layer-plugin-agents.ts:289` and `:328`.

**Scenario:** A plugin agent cannot be copied, or a plugin's agents directory returns a real I/O error. The mirror counts/logs the failure and resolves. Electron ignores that count, may persist the first-backfill completion marker, and returns `ok`. Reconciliation similarly logs its error count and returns `ok`. If catalog sync does not throw, the pass broadcasts `updated` and the refresher returns `refreshed`, despite missing or stale Library items. This is observable success-looking failure, not merely an incomplete log. CLI has the analogous unconditional `refreshed` after resolving calls at `libs/backend/cli-engine/src/lib/bootstrap/harness-boot.ts:146`.

**Fix:** Keep processing healthy files, but translate nonzero mirror/reconcile error counts into the aggregate failed/degraded outcome. With the current two-state public contract, return `failed` and still broadcast so the Library can show partial results and the failure notice. Account for nested retirement errors as well. Do not label the initial backfill complete when it failed. Add a host-level case where the service resolves with an error count instead of throwing; verify both the requester's outcome and push payload.

## Five logic questions

1. **How does this fail silently?** Resolved per-file failures become `ok`/`updated`/`refreshed` (finding 3, `plugin-activation.ts:418`, `:533`, `:589`). A stranded sidecar-less agent subsequently looks like a normal user-owned collision (finding 1, `user-layer-plugin-agents.ts:258`).
2. **What user action produces unexpected behavior?** Installing a same-basename external plugin before an old clone has received a source identity can switch its upstream on reconcile (finding 2, `user-layer-plugin-agents.ts:154`, `user-layer-mirror.service.ts:1735`). Refreshing after an interrupted agent installation does not recover it (finding 1).
3. **What input produces a wrong answer rather than an error?** A valid legacy sidecar lacking `sourceRef`, together with two distinct external coordinates sharing basename and slug, passes the ownership predicate for either coordinate (`user-layer-plugin-agents.ts:153`).
4. **What happens when a dependency fails, times out, or returns an unexpected shape?** Plugin file I/O failures increment counters (`user-layer-plugin-agents.ts:288`) but lose failure status at the host. The broadcaster catches both synchronous resolution/call failures and asynchronous rejection (`library-change-broadcaster.ts:46`, `:56`). Wizard-origin reads return `{}` silently for ENOENT and warn for other I/O/parse failures (`wizard-agent-origin.store.ts:93`, `:96`, `:112`); persistence delegates to `atomicWriteWithRetry` and returns false on failure (`:208`, `:214`). Coalescer outcomes are settled after `await run` (`coalesced-job.ts:264`, `:269`); there is no timeout around a run that never settles. No timeout requirement was supplied, so that last limitation is not scored as a defect.
5. **What is missing from the requirements?** A recovery contract for publishing an agent body and provenance separately, and a safe migration rule for ambiguous legacy source identity. Findings 1 and 2 supply concrete cases. The host also needs an explicit partial-success policy (finding 3), beyond the plan's instruction that per-file errors are counted without throwing.

## Decisions

- **Count per-file I/O failures in the pass outcome.** Options: continue reporting success whenever the method resolves, or preserve partial progress while reporting failed/degraded. Recommend the latter because the caller and Library consume a refresh result, and successful execution of the loop does not mean successful refresh (`plugin-activation.ts:589`, `:642`). This is a reversible status-policy change; no source was changed.
- **Preserve ambiguous legacy ownership.** Options: assign the first matching basename, infer only from reliable provenance, or leave ambiguity visible for resolution. Recommend reliable provenance with a conservative unresolved state otherwise. A basename alone cannot distinguish the two coordinates (`user-layer-plugin-agents.ts:154`). Reversible migration policy; destructive reassignment is not justified.
- **Do not merge conflicting configs or broaden candidate discovery.** The supplied plan explicitly defines candidates as registered folders (`implementation-plan.md:998`), and current enumeration follows it (`plugin-config-home.ts:558`). Closed-folder discovery is therefore an unreviewed product limitation rather than an invented implementation finding. Home records remain the stable authority once present (`plugin-config-home.ts:519`).
- **Honor read-only review and verification constraints.** Use current-worktree source evidence and disclose the missing diff/runtime evidence rather than claim exact-range verification or execute prohibited git/build/test commands.
