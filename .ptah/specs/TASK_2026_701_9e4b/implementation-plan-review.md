## Findings

1. **Blocking — forbidden fixture dependency.** Plan:1105–1107,1142,1231; `libs/frontend/webview-e2e-harness/project.json:6`; `eslint.config.mjs:410–417`. F7e proposes importing fixtures from `webview-e2e-harness` into both marketplace and skill-synthesis-ui specs. Both consumers are `scope:webview,type:feature`; the destination is `scope:webview,type:test-harness`, which feature dependencies do not allow. Tests are included by the rule (`eslint.config.mjs:247`). The cited fixture file also imports Playwright (`marketplace.fixtures.ts`, AST verified), so importing its existing module would bring browser-test helpers into Jest. **Exact change:** select a concrete shared, pure-data fixture location in an allowed project, export only DTO fixtures, and name both imports and its verification project. Remove the forbidden alternative and the claim that there are no new library edges. This requires no new project. [project-rule]

2. **Serious — the Marketplace consent snapshot cannot detect successive edits.** Plan:240,597–600,759–775. The scanner returns `recordedHash`, which is the managed manifest's last-write hash, not necessarily the current local content hash. `ExternalLocalItem` has `recordedVersion?`, but no specified current-content baseline; clone edit state provides only `exists/edited/pluginId`. After edit A at plan time and edit B before confirm, state remains `owned-edited` (or an edited clone), and the recorded hash remains identical. The proposed re-scan can therefore authorize replacement of B without its approval, violating 8.5e. **Exact change:** define an internal, server-held baseline for each exact target/relative path or scoped clone, including the current content/tree digest and ownership/source identity. Carry that baseline to the repair/rebase boundary and validate it immediately before mutation. Never use the manifest ownership hash as the approval hash. Add file and clone tests for edited-A → edited-B, disappearance/recreation, unreadable-after-plan, and changes while install is in flight. [user-requested U1; lane-proposed safety elaboration]

3. **Serious — retained pack cache and in-flight deduplication bypass the new contract.** Plan:526–534; `libs/backend/platform-core/src/agent-pack-download.service.ts:149–158,246–264,475–481`. A matching manifest cache plus existing paths returns `success:true, agentsDownloaded:N` without examining content or decisions. An explicitly approved replacement of a hand-edited cached file would do nothing. Separately, `inFlightPromises` is keyed only by URL and filenames: concurrent requests for different roots or decisions receive the first operation's result and mutation behavior. **Exact change:** retain caching for fetched content, but evaluate every destination guard and per-file outcome on every install. Do not share a mutation promise across targets/approval contexts; serialize overlapping destination writes or define a key and guard protocol that preserves each caller's decisions. Add cached-local-edit Replace/Keep tests and concurrent same-pack requests with different roots and decisions. Keep unchanged outcomes honest. [user-requested; project-rule concurrency safety]

4. **Serious — plugin agents disappear unless unrelated agent-sync consent exists.** Plan:664–666. The plan gates plugin-agent mirroring on `MirrorSources.workspaceRoot` from `resolveAgentMirrorSource`. Current `libs/backend/harness-sync/src/lib/state/agent-sync-gate.ts:182–191` returns `{}` when consent is disabled; `resolve` at :70–75 can disable it in a fresh workspace. Installing/enabling a plugin without a wizard run then produces no Library agents, violating 8.3/8.8. A14/Q2 concerns pack consent and does not cover this path. **Exact change:** specify how plugin-agent Library ingestion receives a harness-root scope independently of permission to fan agents out to rival CLIs. Preserve the existing consent boundary; do not silently grant it. If that separation requires a reserved decision, escalate it to the orchestrator before implementation. Add fresh-workspace and explicitly-disabled-sync plugin install/enable tests. This finding does not answer Q2. [user-requested Library parity; project-rule consent boundary]

5. **Serious — refresh results are not correlated to requests.** Plan:710–714,1192; `apps/ptah-electron/src/activation/coalesced-job.ts:216–265`. The proposed last-result-per-root map cannot distinguish a newly skipped batch from an older successful batch. The current coalescer settles skipped requests without invoking `run` (:233–235), returns `Promise<void>`, and allows another batch while a pass is running. “No outcome was recorded for this batch” is not observable from the proposed map. A stale success can suppress the required Library failure/skipped notice. **Exact change:** define a batch/request identity and correlate completion to that identity, or return a typed batch outcome through the coalescer. Specify success, step failure, thrown pass, admission skip and merged request behavior. Add success→skip and overlapping-pass tests; update the currently “unchanged” coalescer spec if its contract changes. Preserve/filter the message workspace root in `LibraryChangeFeed`, and test workspace switches and out-of-order refresh replies. [user-requested 3.7/8.2b/8.10a; lane-proposed mechanism]

6. **Serious — successful no-write pack installs skip the required Library pass.** Plan:544–546 requires at least one successful write before propagation. Requirement 3.2 requires the pass when a harness-root pack install completes; existing identical or kept files must become visible too. A cached or all-kept install after a prior catalog failure would never heal through this action. **Exact change:** run the Library synchronization path for successful harness-root completion with kept/current outcomes as well as written outcomes; define all-failed behavior separately. Keep any consent-dependent fan-out decision conditional on Q2. Add all-current, all-kept and cached-completion tests proving an open Library refreshes and failures produce the nonfatal notice. [user-requested]

7. **Serious — changed content can inherit Replace during automatic re-preview.** Plan:919–926 and :978; B1 preview DTO at :220–222. F1 carries choices forward when row *state* is unchanged. Under D7 both old and newly edited readable content have state `exists`. A confirmation-time re-preview can mint a fresh token for edited content and retain Replace without asking the user again; B2 then sees a matching new baseline and overwrites it. **Exact change:** reset Replace and require reconfirmation when baseline identity changes, not only when existence state changes. Expose an opaque comparison revision or perform the comparison server-side; do not require generated-content prediction. Add both-surface tests for exists(A)→exists(B), and a pack differs(A)→differs(B) test. [user-requested U1; lane-proposed 1.12 safety elaboration]

8. **Serious — required config root alignment is explicitly deferred.** Plan:752–758 leaves workspace plugin config on active-workspace storage and tells implementers to record a follow-up if it is not keyed to the harness root. Requirement 8.1 explicitly includes plugin config in the steps that must use the harness root. **Exact change:** resolve A-cfg from the workspace-provider/storage implementation now and document the actual key and adapter call. If the keys differ, include the required alignment or escalate a migration decision; a follow-up cannot satisfy this task's acceptance criterion. Add a subfolder enable/disable/install test that checks config, mirror, catalog and reconciliation all use the same intended workspace. [user-requested]

9. **Serious — surviving pluginId is insufficient to retain an orphan's former display name.** Plan:831–843. B13 derives display names from the active external state store/loader, then falls back to pluginId. After uninstall those records may be gone; retaining the identifier alone cannot preserve a different display name, as required by 8.8b. The plan also acknowledges basename ambiguity but allows fallback instead of resolving identity. **Exact change:** define a durable source identity and retained display-label source for orphaned clones, populated before the source record disappears. Cover two external plugins with the same basename, and uninstall of a plugin whose display name differs from its id. Verify both card/drawer and installed/orphaned UI agreement. [user-requested; lane-proposed storage mechanism to be selected]

10. **Moderate — registration and host guards are named, but not fully assigned.** Plan:449–455,570–575,1226–1230,1511–1514. Thus P1 cannot deliver a compiling implementation of its contracts. The selected-skills unit test also does not prove requirement 6.7's generated-output case. **Exact change:** use a separately reviewed expected instruction mapping/snapshot plus rubric digests so one-sided changes fail, and add a representative prompt/output fixture for a relevant but forbidden skill. Avoid claiming a stub with compliant output proves the generator's general compliance; describe that test's limits. [user-requested 6.3/6.7; lane-proposed test mechanism]
