## Findings

1. **Serious — Component 4 / AC 2.1, 2.3, 2.5:** `implementation-plan.md:288-297`, `:310-325`; `chat-session.service.ts:1462-1469`. `evaluate` checks the active provider before a potentially ten-second history read, but `startSession` resolves the provider again at launch. A switch back can call the old provider. Pin the new-provider identity through launch, or revalidate at the launch boundary and fail before any provider call on change. Add a deferred-read/provider-switch spec asserting zero old-provider calls and old-session writes.
2. **Serious — Component 7 / AC 7.5:** `implementation-plan.md:470-480`. The `HISTORY_UNREADABLE` and `START_FAILED` completions call `flagAuthRequired` without checking their generation. An older failure can overwrite a newer refusal. Guard every failure-side banner and offer mutation by original generation and tab identity; test a newer refusal followed by both failure results.
3. **Serious — Components 7-8 / AC 5.4, 7.5-7.7:** `implementation-plan.md:458-489`, `:550-564`; `chat-lifecycle.service.ts:139-180`. A successful RPC clears `inFlightSessionIds` in `finally` while `pending` and the offer remain until `SESSION_ID_RESOLVED`; a second click can create another session. `claimSessionResolution` also accepts any resolution for that tab. Keep the offer disabled until binding or definitive failure and correlate the resolution with this launch, or serialize all launches for the tab. Test success-before-resolution, a second click and an unrelated resolution.
4. **Serious — Components 4-5 / AC 8.3, 8.5:** `implementation-plan.md:293-301`, `:376-391`; `chat-session.service.ts:1119-1132`. Reused `startSession` logs the raw exception and sends it to Sentry. A provider error can echo transcript text. Specify a safe internal failure path that logs only fixed text and an error name for carry-over launches; test a thrown error containing a transcript sentinel across logger, Sentry and RPC outputs.
5. **Serious — Component 2 / AC 3.5:** `implementation-plan.md:176-184`, `:203-205`; `task-description.md:181-183`. The extractor drops every `tool_result`, whereas AC 3.5 requires a line naming each tool call or result. Map results to tool names via their associated tool-use id where possible, emit a placeholder without result content, and test paired and result-only cases.
6. **Moderate — Components 2-3 / AC 3.8:** `implementation-plan.md:168-170`, `:249-258`. Starting after the last `system` or `compact_boundary` can erase valid turns after an ordinary system event. Define the boundary from the latest in-window compaction summary; otherwise retain eligible turns in the window. Test a system event after prose and a boundary without an in-window summary.
7. **Moderate — Handoff / verification:** `implementation-plan.md:760-767`; `scripts/verify.mjs:1-8`. The seven-project command includes two unmodified app projects, contrary to its changed-project claim. Use scoped `nx test/typecheck/lint <changed-project> --parallel=1` checks, with targeted Electron contract specs only where registration needs them, one heavy check at a time.
8. **Moderate — Component 9 / AC 7.3:** `implementation-plan.md:607-619`. The view-only offer test is conditional on a chat-view harness and otherwise delegated to specs that cannot prove the view's tab filter. Require a concrete view-level matching/nonmatching tab test and inspect Electron dark/light screenshots.
