# Research Report — Electron 40.10.1 → 44.4.3 upgrade (TASK_2026_498)

## Question

- **Report date**: 2026-09-21 (Pre-migration baseline snapshot)
- **Baseline commit / lockfile state**: measured against `d5d1a6bd73bd40742a209c677f0e348176acda83` / `9ced6498e` (pre-migration branch state prior to dependency upgrades landing). Electron inventory and vulnerability data recorded herein represent this pre-migration baseline.
- Decision this supports: whether/how to bump `electron` (and the native-module stack riding on it) in `apps/ptah-electron`, and what the migration steps and compile risk are.
- Question: what does the Electron 40 → 44 jump require across breaking changes, ABI, native modules (better-sqlite3, node-pty, @parcel/watcher, sqlite-vec), `@huggingface/transformers`, and electron-builder — and what in this repo has to change?
- Bounds: did not investigate macOS/Linux code-signing pipelines in depth (repo runs this research on Windows 11; Windows path only verified end-to-end). Did not investigate CI runner images. Did not evaluate `sharp`/`onnxruntime-node` prebuilt matrices beyond what feeds the transformers question. Did not attempt an actual build.

## Answer

The Electron bump itself is low-risk for this codebase: `contextIsolation`/`sandbox` are already hardened, no removed API (`remote`, deprecated `protocol.register*Protocol`, renderer `clipboard`) is used anywhere in `apps/ptah-electron/src`, and the app is 64-bit-only already (Electron 44 drops 32-bit, which does not affect this repo). The real work is native-module ABI: Electron 40 = ABI 143, Electron 44 = ABI 149 (verified against the `node-abi` registry and corroborated by an independent project's changelog), and only `better-sqlite3` needs an Electron-specific rebuild — `sqlite-vec` is a loadable SQLite extension (not a Node addon) and `@parcel/watcher` ships N-API prebuilds that are already ABI-stable, both already documented as such in this repo's own scripts. The one upgrade that is **not safe to do in the same pass** is `@huggingface/transformers` 3.8.1 → 4.3.0: transformers 4.x pins `onnxruntime-node` to an exact `1.30.0` (not a range), which is a large jump from the repo's current `1.24.3` override, and — more seriously — `kokoro-js@1.2.1` declares `"@huggingface/transformers": "^3.5.1"` as a hard dependency, so bumping the hoisted copy to 4.x breaks kokoro-js unless a 4.x-compatible kokoro-js release exists (not found). Recommend decoupling: do the Electron/electron-builder/native-module bump now, leave `@huggingface/transformers` on 3.8.1 until kokoro-js has a 4.x-compatible release.

## Disagreements

- Whether Electron 44's stable NODE_MODULE_VERSION is exactly 149 for every 44.x patch: the node-abi registry entry checked was `44.0.0-alpha.1`, not `44.4.3`. Electron's ABI number is fixed at the alpha stage of a major and does not change across that major's patch releases (this has held for every prior major in the repo's own fallback table, e.g. 40.0.0-alpha.2=143 matches the repo's already-verified Electron 40.10.1=143), so 149 is treated as verified-by-convention here, not independently re-checked against 44.4.3 specifically.
- better-sqlite3's own release notes say N-API prebuilds "should theoretically work across different versions of Node.js and Electron," but the same project's changelog keeps shipping Electron-major-specific prebuild artifacts (e.g., "support for electron v43 prebuilds" as a distinct line item). This repo's `npmRebuild: false` + explicit from-source `rebuild-native.js` step sidesteps the disagreement entirely — it never relies on better-sqlite3's prebuilt binary, so whichever is true does not change what this repo has to do.

## Numbered upgrade procedure (Windows 11, this repo)

1. Bump `package.json`: `"electron": "^40.9.3"` → a `44.x` range (recommend pinning close to `44.4.3`, matching electron-builder's `electronVersion`), and `"electron-builder": "^26.8.1"` → `^26.15.3`. Do not touch `@huggingface/transformers`, `onnxruntime-node`, `kokoro-js`, `sqlite-vec`, `node-pty`, or `@parcel/watcher` in the same change.
2. Update `apps/ptah-electron/electron-builder.yml:4` `electronVersion: 40.8.5` → `44.4.3` (or the exact patch pinned in step 1).
3. Add a `44: 149` entry to `ELECTRON_ABI_FALLBACK` in both `apps/ptah-electron/scripts/rebuild-native.js` and `apps/ptah-electron/scripts/verify-packed-native.js`, even though the primary lookup goes through the live `node-abi` package — this keeps the fallback from silently no-op'ing the ABI check if the dynamic import ever fails in CI.
4. Delete `node_modules`, run `npm install` (this fires `postinstall` → `rebuild-native.js` non-fatally, then `patch-transformers-onnx-dep.js`). Confirm in the log that `node-abi`'s resolved version reports ABI 149 for the installed Electron version rather than falling back.
5. Run the explicit rebuild: `npx nx rebuild-native ptah-electron` (wraps `node apps/ptah-electron/scripts/rebuild-native.js`). This must run on a machine with the MSVC C++ build toolchain (Visual Studio Build Tools with the "Desktop development with C++" workload) since `better-sqlite3` compiles from source — same requirement as today, just against Electron 44's headers instead of Electron 40's.
6. Verify the ABI landed correctly:
   ```
   node -e "console.log(require('fs').readFileSync('node_modules/better-sqlite3/build/Release/better_sqlite3.node').toString('binary').match(/node_register_module_v(\d+)/)[1])"
   ```
   Expect `149`.
7. Dev-serve smoke test: `npx nx serve ptah-electron` — exercises `rebuild-native.js` again (should now hit the `[skip]` branch), the full `build-dev` chain, and `scripts/launch.js`. Manually verify: app boots, SQLite-backed features work (Memory/Skills/Cron/Gateway — the same features `rebuild-native.js`'s own comment names as what breaks on an ABI mismatch), the workspace watcher (`@parcel/watcher` via `workspace-watch-host.mjs`) picks up file changes, voice transcription/synthesis still functions (still on transformers 3.8.1/onnxruntime 1.24.3, unchanged), and any Copilot/Codex rival-CLI session that would exercise `node-pty` runs without a `NODE_MODULE_VERSION` error in the console.
8. Package smoke test: `npx nx package ptah-electron` (or `package-local-production` for a faster local loop). This chains `build` → `copy-renderer` → `rebuild-native` → `patch-transformers-onnx-dep.js` → `prune-dist-deps.js` → `electron-builder --config electron-builder.yml` → `verify-packed-native.js` → `verify-packed-wasm.js` → `verify-packed-onnx.js`. Confirm `verify-packed-native.js` prints ABI 149 for the packed `better-sqlite3` binary and exits 0.
9. Install and run the packaged NSIS build on a clean Windows 11 machine/VM (no dev toolchain) to confirm the shipped binary does not attempt a runtime compile and that code signing (SSL.com IV/eSigner env vars, read at `electron-builder` invocation time per `apps/ptah-electron/CLAUDE.md:80`) still succeeds under electron-builder 26.15.3.
10. Update `apps/ptah-electron/CLAUDE.md`'s "Deployment Notes" line ("Electron 40 = ABI 143") to reflect Electron 44 = ABI 149, and update the header line ("Standalone Electron 40 desktop build") if the project's naming convention tracks the major version.
11. Only after the above is stable, open a **separate** task to evaluate `@huggingface/transformers` 4.x, gated on first confirming whether a `kokoro-js` release compatible with transformers 4.x exists; until then, `apps/ptah-electron/scripts/patch-transformers-onnx-dep.js` and the `overrides.onnxruntime-node = "1.24.3"` pin stay exactly as they are.

## Modules that carry real compile risk

1. **`better-sqlite3` (^13.0.3)** — the only Node addon this app forces to compile from source for the target Electron ABI. Real risk: node-gyp/MSVC toolchain compiling against Electron 44's V8/Node headers for the first time; this is the same risk profile the repo already accepts today for Electron 40, just against newer headers.
2. **`onnxruntime-node` (pinned 1.24.3) / `@huggingface/transformers` (3.8.1)** — not touched by this Electron bump, but flagged because it is the next adjacent upgrade this repo will face, and it is **not** a simple compile risk — it is a cross-package version-compatibility risk (`kokoro-js` pins `^3.5.1`, transformers 4.3.0 requires `onnxruntime-node@1.30.0` exactly). Do not bundle it with the Electron bump.
3. **`node-pty` (1.1.0)** — not directly used by this repo's own code, but present as a hoisted dependency and referenced in Copilot-adapter log matching; unverified whether it ever loads in-process inside Electron's main process via `@github/copilot-sdk`. Flagged as an unknown to smoke-test, not a known compile blocker.
4. **`@parcel/watcher` (2.5.6) and `sqlite-vec` (0.1.6)** — low/no compile risk: both are already documented in this repo's own scripts as not needing an Electron-specific rebuild (N-API-stable prebuilds, and a loadable SQLite extension respectively).
