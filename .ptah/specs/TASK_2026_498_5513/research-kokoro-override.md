# Research Report - TASK_2026_498 - kokoro-js / transformers 4.3.0 override

## Question

- Decision this supports: whether to add an npm `overrides` entry forcing
  `kokoro-js@1.2.1` to resolve `@huggingface/transformers@4.3.0` instead of its
  declared `^3.5.1` range (which resolves to the repo's pinned 3.8.1), or
  whether to leave the whole repo pinned to transformers 3.8.1.
- Question: does `kokoro-js@1.2.1`'s actual (not declared) use of the
  transformers API still work unmodified against 4.3.0, and is the resulting
  dependency tree/native-binding shape safe?
- Bounds: did not investigate transformers 4.0.0/4.1.0/4.2.0 as intermediate
  targets, did not investigate patching kokoro-js itself, did not investigate
  the `@huggingface/transformers-structured-output` package mentioned for
  4.3.x, did not run the packaging pipeline end-to-end (assessed via code
  reading only, per instructions not to change source files).

## Answer

**OVERRIDE-UNSAFE.** `kokoro-js@1.2.1` returns a `RawAudio` instance from
`KokoroTTS.generate()`/`.stream()`, and this repository's only caller,
`libs/backend/voice-providers/src/lib/worker/kokoro-pipeline.ts:230`, calls
`audio.toWav()` on that instance. `RawAudio.toWav()` no longer exists on
`@huggingface/transformers@4.3.0` — verified by reading the installed 4.3.0
`transformers.node.cjs` `RawAudio` class body, which defines only `data`,
`toBlob()` and `save()`. Forcing kokoro-js onto 4.3.0 would make every TTS
`synthesize()` call throw `TypeError: audio.toWav is not a function` the
first time it runs, with no code change anywhere else needed to trigger it.
Independent of that, the onnxruntime-node pin conflict (repo pins 1.24.3
globally; transformers 4.3.0 declares 1.30.0 exact) is a second, separate
blocker that the existing packaging patch script cannot currently absorb.

## Disagreements

- None found between sources on the core fact (`toWav()` removal): the official
  blog post is simply silent on it, while direct inspection of the shipped
  4.3.0 source is unambiguous. Silence in marketing/release-note prose versus
  a hard absence in the actual class body is not a disagreement between two
  claims — it is an under-documented breaking change. The GitHub release note
  mentioning a `toBlob()` fix in 4.3.0 corroborates that `toBlob()` (not
  `toWav()`) is the currently maintained method, consistent with the direct
  source read.

## Local consequences

- `libs/backend/voice-providers/src/lib/worker/kokoro-pipeline.ts:32` (the
  `KokoroAudio.toWav(): ArrayBuffer` interface) and `:230`
  (`audio.toWav()` call) both encode a hard dependency on the transformers 3.x
  `RawAudio` shape. Any move to transformers 4.x for kokoro's code path
  requires changing this file to call `.toBlob()` (returns WAV bytes directly
  per the 4.3.0 source, despite its JSDoc saying "Blob" — it literally
  `return encodeWAV(audio, this.sampling_rate)`) or `.save(path)`, plus
  updating `kokoro-pipeline.spec.ts`'s `toWav` stubs (5 occurrences) to match.
- `apps/ptah-electron/scripts/patch-transformers-onnx-dep.js` — its
  `TARGET_MANIFESTS` array and single `PIN_VERSION` model assume exactly one
  onnxruntime-node version applies to every transformers copy in the tree.
  A kokoro-scoped transformers 4.3.0 override breaks that assumption and the
  script would need a second, version-aware branch before packaging could
  trust its "production dependency not found" guard again.
- `libs/backend/voice-providers/CLAUDE.md` documents `@huggingface/transformers`,
  `kokoro-js`, `ffmpeg-static` as dynamically imported, never bundled — this
  is unaffected by the override question either way, since both the shared
  and the kokoro-scoped copy would still be resolved at runtime via
  `import()`.

## Unknowns

- Whether `RawAudio.toBlob()` in 4.3.0 returns an `ArrayBuffer` (as
  `kokoro-pipeline.ts` needs to wrap in `new Uint8Array(...)`) or something
  else — its JSDoc says `@returns {Blob}` but its body calls `encodeWAV(...)`
  directly and returns that value un-wrapped; `encodeWAV`'s return type was
  not traced in this pass. Smallest experiment: read
  `encodeWAV`'s definition in the same 4.3.0 bundle, or run
  `Object.prototype.toString.call(rawAudio.toBlob())` once against a real
  4.3.0 install.
- Whether loading two onnxruntime-node native addon builds (1.24.3 and
  1.30.0) in one Node/Electron `utilityProcess` actually conflicts, or
  merely wastes memory/thread pools. Both would load as separate `.node`
  files from different `node_modules` paths, which Node treats as distinct
  native modules — no OS-level symbol collision is guaranteed, but
  onnxruntime's execution-provider registration and threading are known to
  have had process-wide state bugs in this exact codebase's history (the
  HandleScope note). Not resolved by code reading alone. Smallest experiment:
  actually construct the scoped override, install, and load both a
  Whisper (3.8.1-backed) and a Kokoro (4.3.0-backed) session in the same
  worker process in a throwaway branch, then watch for crashes/hangs under
  repeated load/unload.
- Whether `@huggingface/jinja` and the new `@huggingface/tokenizers`
  dependency chain introduce any other transitive native or ESM-only
  requirement incompatible with this repo's CJS/ESM dual-build worker
  bundling (`voice-worker.mjs`) — not traced beyond confirming
  `@huggingface/tokenizers` itself ships pure JS.
