## NEEDS-CHANGE detail

### 1. `@types/node` — do not take `latest`

- Runtime is Node 24.15.0; `package.json:5-7` pins `"engines": {"node": "24.x"}`.
- Current `@types/node@^22.15.0` is BEHIND the runtime (types for Node 22, running on Node 24 — some Node-24-only globals/APIs are untyped).
- `latest` dist-tag is `26.6.2`, which is AHEAD of the runtime and would type Node-26-only APIs that do not exist on Node 24 — a real footgun if anyone starts using something the types offer but the runtime lacks.
- **Recommended exact version: `24.13.6`** — the newest published version on the `24.x` line as of 2026-09-21 (`npm view @types/node versions` newest 24.x entries: `24.12.2` … `24.13.6`). Edit: `"@types/node": "24.13.6"` (or `^24.13.6` if the repo's convention is caret ranges for this family — check sibling `@types/*` entries, which mostly use `^`).

### 2. `@vscode/vsce` 4.0.0

- **Node baseline raised to `>=22`** (`npm view @vscode/vsce@4.0.0 engines`) — the repo's `engines.node: "24.x"` and every CI workflow's `NODE_VERSION: 24` satisfy this; not a blocker, but note it explicitly since the root `package.json` itself has no `vsce`-specific engine check.
- **No `.vscodeignore` semantic change was found documented in the v4.0.0 release** (GitHub releases page fetched directly; the historical `.vscodeignore`-semantics issues referenced in search results — #576, #587, #588 — are all against pre-3.x versions, years old, already absorbed). This directly answers the CLAUDE.md-flagged risk (marketplace scanner rejecting trademarked names in non-JS files via `.vscodeignore` exclusion): **no evidence of regression**, but the release swaps the glob engine from `glob` to `tinyglobby` — glob-engine swaps have a history of subtly changing edge-case pattern matching (e.g., brace-expansion, dot-file handling) even when not called out as "breaking." **Action**: after bumping, run `npx nx run ptah-extension-vscode:package` and manually diff the resulting `.vsix` file list against a pre-bump package (`vsce ls`) to confirm the same files are excluded/included, particularly any file under `apps/ptah-extension-vscode/assets/plugins/**` or template markdown that names trademarked terms. This is a verification step, not a code edit.
- `--no-dependencies` flag: no removal or behavior change found in the v4.0.0 release notes or in secondary sources; the repo's current `package` script pattern (pre-install prod deps into `dist/`, then `vsce package --no-dependencies`) is not contradicted by anything found.
- The v4.0.0 release also swaps `keytar`→`@napi-rs/keyring` for credential storage (`vsce login`) — irrelevant to this repo's CI publish path, which passes `--pat ${{ secrets.VSCE_PAT }}` directly (`.github/workflows/publish-extension.yml:216`) and never calls `vsce login`.
- **Edit required**: none beyond the version bump itself; the item is "NEEDS-CHANGE" only in the sense of "needs a verification run," not a code change.

### 3. `@workos-inc/node` 8.13.0 → 10.13.0

- Confirmed call sites, all in `libs/api/identity/src/lib/services/workos/workos-user.service.ts`:
  - `:78` `authenticateWithPassword` — present in v10 API, unaffected per v8 guide.
  - `:101` `authenticateWithCode` — present, unaffected.
  - `:129` `createUser` — present, unaffected.
  - `:149` `verifyEmail` — present, unaffected.
  - `:166` `sendVerificationEmail` — present, unaffected (this is NOT the removed `sendMagicAuthCode`).
  - `:183` `listUsers` — present, unaffected (this is NOT the removed `listOrganizationMemberships` — that method requires `userId`/`organizationId` in v8+; not called here).
  - `:203`, `:229` `getAuthorizationUrl` — the v8 migration guide states `SSOAuthorizationURLOptions` became a discriminated union and `context` was removed in favor of `state`; **read both call sites' option objects before bumping** to confirm neither passes `context` or `domain`.
- None of the methods actually called here are in the v8-removed list (`sendMagicAuthCode`, `sendPasswordResetEmail`, `refreshAndSealSessionData`, `verifyFactor`). That part is a clean pass.
- **UNKNOWN, unresolved in this pass**: whether the 9.x and 10.x majors specifically (on top of the already-absorbed 8.0.0 jump) introduce further breaking changes to `userManagement` or `getAuthorizationUrl`. No primary 9-or-10-specific changelog was found; do not assume "safe" — read `getAuthorizationUrl`'s exact options object at both call sites and the WorkOS CHANGELOG.md for the 9.0.0 and 10.0.0 entries specifically before merging this one.

### 4. `@astrojs/starlight` 0.38.3 → 0.42.2 (coupled to `astro` 6→7)

- **Hard peer requirement, directly measured**: `@astrojs/starlight@0.42.2` requires `astro: '^7.2.10'`. It **cannot** install cleanly against the repo's current `astro ^6.1.9` — these two packages must be bumped together in the same commit, never independently.
- `astro.config.mjs:1-244` uses only stable, documented Starlight config (`title`, `description`, `favicon`, `customCss`, `social`, `editLink`, `sidebar` with `autogenerate`/explicit `items`) — none of it touches the one Starlight-0.42-specific breaking surface found (custom `MobileMenuToggle`/`PageFrame` component overrides), so once the peer requirement is satisfied by bumping `astro` too, no config edit is needed.
- Astro 7 itself: Vite 8 bump under the hood; `apps/ptah-docs` has "zero `.astro` components" and no `vite.config`/plugin overrides per its own `CLAUDE.md`, so the Vite 8 migration surface (Vite-specific plugin/config breakage) does not apply here.
- **Edit required**: bump `astro` to `^7.3.3` (or exact `7.3.3`) in the SAME change as `@astrojs/starlight` to `^0.42.2` — bumping only one leaves either an unsatisfiable peer (Starlight alone) or an untested Astro major with the old Starlight (Astro alone, not recommended since Starlight explicitly pins `^7.2.10` as its floor for a reason).

### 5. `@openai/codex-sdk` 0.147.0 → 0.155.1 (flagged, not confirmed safe)

- This is a pre-1.0 package; by semver convention a "minor" bump in the `0.x` line carries no compatibility guarantee at all, unlike the other targets in this table.
- `libs/backend/cli-agent-runtime/src/lib/cli-agents/cli-adapters/codex-cli.adapter.ts:87` explicitly documents that its local `ThreadEvent` type mirrors "the actual @openai/codex-sdk ThreadEvent type structure" — i.e., this file hand-maintains a shape contract against the package's internals rather than importing its types directly in that spot, which is exactly the kind of coupling a minor bump in a sub-1.0 package can silently break.
- `:483` further notes "The installed `@openai/codex-sdk` Thread API exposes no mid-turn steer" — a capability-absence assumption that should be re-checked against 0.155.1's actual Thread API surface.
- No breaking-change list for this specific version range was located from a primary OpenAI source in this pass (the public Codex changelog pages returned no version-keyed entries reachable via search/fetch here). **Recommendation: treat this as a standalone bump requiring a manual smoke test of `codex-cli.adapter.ts`'s thread-create/stream path against a real Codex CLI session before merging — do not fold it into a batch with unrelated packages.**
