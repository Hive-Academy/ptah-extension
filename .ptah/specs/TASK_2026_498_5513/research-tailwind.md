# Research Report — TASK_2026_498 — Tailwind 4 / daisyUI 5 migration

## Question

- Decision this supports: whether/how to sequence the tailwindcss 3.4.19→4.3.3
  and daisyui 4.12.24→5.7.42 bump inside the broader TASK_2026_498 dependency
  migration, and how much hand-editing to budget after the official codemod.
- Question: what does this migration require in this repo, and what is the
  real blast radius (files touched, config rewrites, browser-support risk)?
- Bounds: did not investigate `postcss-import`/`postcss-nesting` usage (none
  found), did not run the codemod (instructed not to change source files or
  `package.json`), did not benchmark build-speed gains.

## Answer

Config surface is small (2 `tailwind.config.js`, 1 `postcss.config.js`, 2
`styles.css` entry points, zero `.claude-worktrees` copies counted) but the
**daisyUI theme rewrite is the real cost**: this repo hand-authors 6 custom
themes with dozens of daisyUI-v4-only CSS custom properties
(`--rounded-box`, `--btn-focus-scale`, `--animation-btn`, `--tab-radius`,
etc.) that daisyUI 5 replaces with a different variable set
(`--radius-box`, `--radius-field`, `--depth`, `--noise`, …) declared via
`@plugin "daisyui/theme"` in CSS, not JS objects — none of that is mechanical
text substitution, it is a redesign of 6 theme blocks against undocumented
value semantics. Utility-class renames are real but codemod-coverable
(`npx @tailwindcss/upgrade` claims ~90% automation industry-wide; the daisyUI
migration has no equivalent official codemod for component-class renames).
Browser floor (Chrome 111+/Safari 16.4+/Firefox 128+) clears both Electron 40
(Chromium 144) and current VS Code Electron generations with wide margin, so
that is not a blocker.

## Disagreements

- None found between primary sources (tailwindcss.com and daisyui.com upgrade
  guides agree on directionality: JS config → CSS, `@tailwind` → `@import`,
  autoprefixer folded in). The only gap is that daisyui.com's own docs did not
  state whether a v4-named CSS variable left in a v5 theme block silently
  no-ops or throws/warns — that is an unknown, not a disagreement between
  sources.
- Practitioner blog posts (Medium/dev.to hits from the Tailwind search) echo
  the official guide numbers verbatim in places, so they were not counted as
  independent corroboration — treated as restating the primary source, not as
  a second source.

## Local consequences

- `apps/ptah-extension-webview/postcss.config.js:1-6`: `tailwindcss: {...}` plugin key must become `'@tailwindcss/postcss': {...}`; `autoprefixer: {}` should be dropped per the upgrade guide (v4 handles vendor prefixing internally).
- `apps/ptah-extension-webview/tailwind.config.js` and `apps/ptah-landing-page/tailwind.config.js`: the `daisyui: {...}` block (themes array, `darkTheme`, `base`, `styled`, `utils`, `prefix`, `logs`, `themeRoot`) has no v5 JS-config equivalent — it must move into `apps/*/src/styles.css` as `@plugin "daisyui"` + one `@plugin "daisyui/theme" {...}` block per theme (6 total across the two apps), re-deriving every non-color custom property (`--rounded-*`, `--btn-focus-scale`, `--animation-*`, `--tab-*`) into the v5 vocabulary (`--radius-*`, `--size-*`, `--border`, `--depth`, `--noise`).
- `apps/ptah-extension-webview/src/styles.css:1-18`, `apps/ptah-landing-page/src/styles.css:1-4`: `@tailwind base/components/utilities` → `@import "tailwindcss";`; the `@import '@angular/cdk/overlay-prebuilt.css'` and `@import 'gridstack/dist/gridstack.min.css'` ordering comment ("MUST come before Tailwind directives") needs re-validation once those become plain `@import` statements ahead of `@import "tailwindcss"`.
- `apps/ptah-extension-webview/src/app/base-content-muted.spec.ts` (referenced in both tailwind configs' comments) recomputes `--bcm` contrast ratios from the literal theme colors; it is the regression gate that will catch a broken OKLCH value if the theme-block port drops precision, but it will NOT catch a removed/renamed non-color variable (`--btn-focus-scale` etc.) silently doing nothing — that needs a manual visual pass per TASK_2026_183/186's own logic.
- All 95 files carrying `input-bordered`/`select-bordered`/`textarea-bordered`/`file-input-bordered` (272 occurrences) render borderless-by-default form fields under daisyUI 5 unless the class is dropped (border is now default) — worst-hit: `libs/frontend/skill-synthesis-ui/.../skill-settings-panel.component.ts` (26), `libs/frontend/chat/.../agent-orchestration-config.component.ts` (10), `libs/frontend/chat/.../custom-provider-form.component.html` (10).
- All 24 files carrying `form-control`/`label-text`/`label-text-alt` (231 occurrences) lose those layout/typography classes outright in v5 with no direct renamed equivalent — worst-hit: `libs/frontend/chat/.../auth-config.component.html` (34), `libs/web/admin/.../pack-form-modal.html` (25), `libs/frontend/chat/.../custom-provider-form.component.html` (21).
- 11 files carrying `tabs-bordered`/`tabs-lifted`/`tabs-boxed` (17 occurrences) need the `-border`/`-lift`/`-box` suffix rename.
- 2 files carrying `card-bordered`/`card-compact` need `card-border`/`card-sm`.
- 58 files carrying `flex-shrink-*`/`flex-grow-*` (152 occurrences) are covered by the official codemod's rename table (`shrink-*`/`grow-*`) — low manual risk, high volume.
- The 1 `phone-`/`artboard`-pattern hit needs a manual look (likely a false positive against the regex, not an actual daisyUI mockup class) before being counted as a real removal.
- `apps/ptah-electron` (`electron ^40.9.3`, Chromium 144) and current VS Code webview Chromium generations both clear the v4 floor (Chrome 111+) by 30+ major versions — not a blocker for either shipping surface.

## Unknowns

- Whether a daisyUI-v4-named custom property (`--rounded-box`, `--btn-focus-scale`, etc.) left inside a v5 `@plugin "daisyui/theme"` block is silently ignored, warns, or breaks the theme — the official docs fetched did not say. Smallest experiment: port one theme (e.g. `anubis`) in isolation on a branch, build, and diff computed styles against the current v4 output.
- Whether `libs/frontend/ui` (the Native\* Floating-UI primitives lib, called out in CLAUDE.md as depended-on by both apps) contains any daisyUI class usage that behaves differently once compiled under each app's own v5 theme — not separately audited beyond the aggregate greps above, which do include `libs/frontend/ui` in their file counts.
- Exact Electron version bundled in the _currently installed_ stable VS Code build the team targets was not directly queried (search results only confirm the trend: VS Code is on Electron 40+ class as of Sept 2026, moving to 43.6.0 in the next release train) — low risk either way given the 111+ floor, but not pinned to a single verified version number the way the repo's own `electron ^40.9.3` pin was.
- No official daisyUI codemod exists (only `@tailwindcss/upgrade` for the Tailwind side) — confirmed by the absence of any codemod reference in daisyui.com's own upgrade guide fetch. This means the daisyUI file counts above (503 combined `*-bordered` + `form-control`/`label-text*` occurrences, plus 17 tab and 2 card occurrences) are the actual hand-edit floor, not a codemod-reducible number.

## Migration procedure

1. Branch, then bump `tailwindcss`, `daisyui`, `postcss`, `autoprefixer` in `package.json`, and add `@tailwindcss/postcss` as a new devDependency; run `npm install`.
2. Run `npx @tailwindcss/upgrade` at repo root (Node 20+ required) to auto-migrate both `tailwind.config.js` files' non-daisyUI settings into `@theme` blocks in the corresponding `styles.css`, convert `@tailwind base/components/utilities` to `@import "tailwindcss";` in both `apps/ptah-extension-webview/src/styles.css` and `apps/ptah-landing-page/src/styles.css`, and rename the ~152+38 mechanical utility occurrences (`flex-shrink/grow-*`, `outline-none`, `shadow-sm`, `rounded-sm`, opacity-suffix classes, bare `ring`) across the codebase.
3. Update `apps/ptah-extension-webview/postcss.config.js` by hand: replace the `tailwindcss` plugin key with `@tailwindcss/postcss`, and drop the `autoprefixer` entry (confirm `apps/ptah-landing-page` picks up the same builder-level Tailwind detection change, since it currently has no explicit `postcss.config.js`).
4. Remove daisyUI from both `tailwind.config.js` files by hand — the codemod does not do this — and add `@plugin "daisyui";` plus one `@plugin "daisyui/theme" { ... }` block per theme (6 total: `anubis`, `anubis-light` in the webview; `operator`, `operator-admin`, `operator-member`, `operator-member-light` in the landing page) into each app's `styles.css`, re-deriving every non-color custom property into the v5 vocabulary (`--radius-selector/-field/-box`, `--size-selector/-field`, `--border`, `--depth`, `--noise`) since there is no automated mapping.
5. Re-run `apps/ptah-extension-webview/src/app/base-content-muted.spec.ts` (and its landing-page equivalent, if one exists) to catch any OKLCH/contrast regression the theme-block port introduces.
6. Hand-edit the daisyUI-4-only component classes across the ~95+24+11+2 affected files: drop `input-/select-/textarea-/file-input-bordered` (border is default in v5; use `-ghost` only where the original intent was borderless), replace `form-control`/`label-text`/`label-text-alt` usages with their Tailwind/daisyUI-5 layout equivalent, rename `tabs-bordered/-lifted/-boxed` → `tabs-border/-lift/-box`, rename `card-bordered/-compact` → `card-border/-sm`. Prioritize by occurrence count: `libs/frontend/skill-synthesis-ui`, `libs/frontend/chat/.../auth-config.component.html`, `libs/frontend/chat/.../custom-provider-form.component.html`, and the `libs/web/admin` form-modal components carry the bulk of the volume.
7. Manually verify the single `phone-`/`artboard` grep hit — confirm whether it is a real daisyUI mockup class or a regex false positive before deciding it needs a rename.
8. Full visual pass (all 6 themes × both apps) focused on: form-field borders (post `-bordered` removal), tab styling, card density, and button/tab focus rings (`--btn-focus-scale` has no direct v5 equivalent).
9. Confirm Electron (`^40.9.3`, Chromium 144) and the VS Code webview both continue to satisfy the Tailwind v4 floor (Chrome 111+) — no action expected, but worth a one-line changelog note since it is a hard floor, not a soft warning.
10. Re-run `npx nx run-many -t build -p ptah-extension-webview ptah-landing-page ptah-electron` and `npx nx run-many -t test -p ...` per this repo's CLAUDE.md rule (never `nx test projA projB` directly).

**Honest hand-edit estimate after the codemod runs**: the Tailwind-utility-rename slice (152 `flex-shrink/grow`, 20 `outline-none`, 18 `bg-gradient`, 18 `shadow-sm`, 4 opacity-family, ~3 `rounded-sm`/`ring`) — call it ~215 occurrences across roughly 90-100 distinct files — is expected to be handled by `npx @tailwindcss/upgrade`'s codemod with only spot-checks needed. The daisyUI slice has **no automated coverage at all**: 272 `*-bordered` occurrences (~95 files) + 231 `form-control`/`label-text*` occurrences (24 files) + 17 tab occurrences (11 files) + 2 card occurrences (2 files) + 6 theme blocks rewritten from scratch = **realistically 120-140 distinct files need a human hand-edit**, plus a full visual regression pass across 6 themes × 2 apps before this is safe to ship.
