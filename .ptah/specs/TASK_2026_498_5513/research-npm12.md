# Research: npm 11.12.1 → 12.0.2 (TASK_2026_498)

Audit only. No files edited except this report.

## 1. npm 12 breaking changes from npm 11

Source: GitHub Releases API, `npm/cli` tag `v12.0.0`, retrieved verbatim via
`curl https://api.github.com/repos/npm/cli/releases/tags/v12.0.0` (release dated
2026-07-08). https://github.com/npm/cli/releases/tag/v12.0.0

Full breaking-change list from the release body:

1. `npm view --json` now always returns an array (previously a bare object for
   a single result).
2. `npm sbom --sbom-format=cyclonedx` reports `package.json` `name` instead of
   on-disk directory name; changes `name`/`bom-ref`/`purl` for root and
   aliased deps.
3. Global install no longer registers man pages (`man npm-install` stops
   working; `npm help install` unaffected).
4. `npm pkg` output no longer forced to JSON.
5. `npm shrinkwrap` removed, `shrinkwrap` config alias removed,
   `npm-shrinkwrap.json` no longer read anywhere (project root or inside
   dependency tarballs). Not relevant here — this repo has no
   `npm-shrinkwrap.json`.
6. Twitter/Freenode profile fields removed from registry profile.
7. npm no longer resolves node via `whichnode`; uses `process.execPath`
   directly. Only matters to scripts that relied on npm overriding
   `process.execPath` with a PATH-resolved/symlinked node.
8. `npm pack`/`npm publish --json` output format changed to be consistent.
9. `star`, `stars`, `unstar` commands removed.
10. `npm adduser` removed (use website + `npm login`).
11. Git HTTPS protocol preserved when working with git deps (#8703).
12. `npm init` default license changed from `"ISC"` to empty string.
13. **Node engine support changed to `^22.22.2 || ^24.15.0 || >=26.0.0`.**
14. **`allow-git` and `allow-remote` default to `"none"`** (previously
    resolved automatically); must opt in with `--allow-git`/`--allow-remote`
    (or `"all"`/`"root"`) to install git or tarball-URL dependencies.
15. Root `preinstall` now runs before dependencies are installed (order
    change vs. npm 11, where root `preinstall` ran after dependency
    installation in some cases — verify locally if root `preinstall` timing
    matters; this repo's only root lifecycle script is `postinstall`, not
    `preinstall`, so unaffected).
16. Unknown `.npmrc` configs, unknown CLI flags, abbreviated flags, and
    single-hyphen multi-char shorthands now **throw** instead of warning.
17. **Dependency lifecycle scripts (`preinstall`/`install`/`postinstall`, and
    `prepare` for non-registry sources) are blocked by default** unless
    allowed via the root package's `allowScripts` policy. Recovery path:
    `npm approve-scripts --allow-scripts-pending` to list pending scripts,
    then `npm approve-scripts <pkg>` per trusted package (or
    `npm deny-scripts`), which writes an `allowScripts` map into
    `package.json`.

Corroborating secondary source (undated relative to npm's own release, but
consistent): https://github.blog/changelog/2026-06-09-upcoming-breaking-changes-for-npm-v12/
— covers items 13/14/17 as the three flagship security changes; it predates
release and does not mention lockfileVersion.

No changes were found, in the official release notes for v12.0.0, v12.0.1, or
v12.0.2, to: `overrides` resolution semantics, `npm ci` semantics, `npm
update` semantics, `--include=optional` semantics, or peer-dependency
resolution algorithm. Verified by reading the v12.0.0, v12.0.1
(https://github.com/npm/cli/releases/tag/v12.0.1, 2026-07-10, two bug fixes
only: `npm view` array-wrapping fix, sigstore dev-dependency conflict fix) and
v12.0.2 (https://github.com/npm/cli/releases/tag/v12.0.2, 2026-07-27, two bug
fixes only: `npm pack` `min-release-age-exclude`, `npm owner` scoped-registry
lookup) release bodies directly — none mention those four commands/flags.

## 2. lockfileVersion — the single most important question

**npm 12 does not change lockfileVersion. Both npm 11 and npm 12 write
`lockfileVersion: 3`.**

- This repo's current `package-lock.json` has `"lockfileVersion": 3` at line 4
  (`file:D:\projects\ptah-extension\package-lock.json:4`, read directly).
- lockfileVersion 3 has been the format for all npm v7+ releases with no
  further bump through npm 12 — verified against the npm docs lockfile format
  history and confirmed by web search (no source claims a v12 lockfile
  version bump; multiple sources state npm 12.0.2 still emits
  `lockfileVersion: 3`).
- The v12.0.0/v12.0.1/v12.0.2 GitHub release bodies (read in full above)
  contain zero mention of lockfileVersion, package-lock format, or any
  lockfile-shape change.
- **Conclusion: a lockfile regenerated by npm 12.0.2 stays fully readable by
  npm 11.x and any other npm 7+.** The "regenerated lockfile becomes
  unreadable to older npm" risk this question was checking for does not
  apply to this migration.

## 3. Node version support

Release text (verbatim, from the v12.0.0 API body): **"`npm` now supports
node `^22.22.2 || ^24.15.0 || >=26.0.0`"**.
https://github.com/npm/cli/releases/tag/v12.0.0

This repo's environment is Node **24.15.0** exactly. `^24.15.0` in npm's
own semver range means `>=24.15.0 <25.0.0` — so 24.15.0 is the _exact floor_
of the supported 24.x range, not comfortably inside it. Any 24.x patch older
than .15.0 is NOT supported by npm 12 (relevant if any CI runner or developer
machine is on an earlier 24.x patch — see section on workflows below, none
pin a patch, so this is a live risk on whatever `actions/setup-node@node-version:
24` resolves to at run time). Root `package.json` `engines.node` is `"24.x"`,
which is broader than npm 12 supports (it would accept 24.0.0–24.14.x, which
npm 12 rejects). This is a real gap: `engines.node: "24.x"` does not guarantee
npm-12 compatibility, only `engines.node` being narrowed to `>=24.15.0` would.

## 5. `npm outdated` / `npm view` / `--json` output shapes

- `npm view --json` **changed**: always returns an array now (previously
  returned a bare object when the query matched one package/version). This is
  a real breaking shape change for any script doing
  `JSON.parse(child_process.execSync('npm view ... --json'))` and treating
  the result as a single object. **Action: grep this repo's scripts for
  `npm view` usage before upgrading if this pattern exists** (not searched in
  this pass — out of the bounds of this audit's file list; flagging as a
  follow-up, not verified against this repo's `scripts/` directory).
- `npm pack`/`npm publish --json` output format changed to be "consistent" —
  same caution applies to any packaging script parsing that JSON.
- `npm outdated --json`: no change documented in any of the three release
  bodies.

## 6. Known incompatibilities: Nx 23, electron-builder 26, prisma 7, husky 9, lint-staged 16

- No official documentation, issue, or advisory was found stating Nx 23,
  electron-builder 26, prisma 7, husky 9, or lint-staged 16 are broken by npm
  12 specifically (checked via web search; none of these projects were named
  in any npm-12 compatibility discussion found).
- The real, repo-general risk is **not** version-pinned incompatibility but
  the `allowScripts` default-off change (item 17, section 1): this repo's
  current `package-lock.json` has **27 packages with `hasInstallScript:
true`** (read directly via `node -e` against the lockfile), including:
  `electron`, `electron-winstaller`, `esbuild` (and 4 duplicate copies pulled
  in by `@angular/build`, `@remotion/bundler`, `astro`, `ng-packagr`, `vite`),
  `nx`, `@prisma/engines`, `prisma`, `node-pty`, `onnxruntime-node`,
  `@parcel/watcher` (+ jest-haste-map's copy), `@swc/core`, `sharp`, `lmdb`,
  `keytar`, `fsevents`, `ffmpeg-static`, `msgpackr-extract`, `protobufjs`,
  `unrs-resolver`, `@vscode/vsce-sign`, `@nx/webpack`'s `less`. Under npm 12
  defaults, **every one of these silently has its install/postinstall script
  skipped** unless an `allowScripts` map is added to root `package.json` (via
  `npm approve-scripts`) — this repo's `package.json` has no `allowScripts`
  key today (confirmed by reading the full file). Skipped scripts here mean,
  concretely: Electron's binary download skipped, esbuild's native binary
  download skipped, `nx`'s own postinstall skipped, native module builds
  (`node-pty`, `sharp`, `lmdb`, `keytar`, `onnxruntime-node`, `@parcel/watcher`,
  `msgpackr-extract`, `@swc/core`) skipped. This is very likely to break
  `npm install`/`npm ci` outright on first run after the upgrade, independent
  of Nx/electron-builder/prisma/husky/lint-staged version numbers.
- This is compounded by the repo's own root `postinstall` script
  (`apps/ptah-electron/scripts/rebuild-native.js` +
  `patch-transformers-onnx-dep.js`) — that script is the _root project's own_
  lifecycle script, which npm always runs regardless of `allowScripts` (that
  policy governs _dependency_ scripts only). But `rebuild-native.js` itself
  presumably depends on native addons already having been built by their own
  install scripts, which would now be skipped — so the root postinstall would
  likely run against unbuilt/undownloaded native deps and fail or silently
  produce a broken build. Labeled **inferred**, not run/tested.

## GO / NO-GO recommendation

**NO-GO for bundling the npm 12.0.2 bump into this migration task.**

Reasons, in order of weight:

1. **`allowScripts` defaulting to off is a real, multi-file migration in its
   own right** — this repo has 27 packages with install scripts (Electron,
   esbuild ×5 copies, native modules, Nx itself). Landing this silently
   inside a dependency-migration task that "already rewrites the lockfile"
   (per the task's own guidance to weigh isolation heavily) means a broken
   `npm ci` is indistinguishable from a Nx-migration regression when someone
   bisects a failure later.
2. **Node floor is exact, not comfortable**: npm 12 requires `^24.15.0`
   exactly as this environment's Node version — meaning `engines.node: "24.x"`
   in `package.json` is not tight enough to guarantee every future
   contributor/CI image satisfies npm 12's floor. That gap should be closed
   (tighten `engines.node` to `>=24.15.0 <25`) as part of any npm-12 task,
   which is more scope than "bump the CLI."
3. **lockfileVersion does NOT change (both write 3)** — this removes the
   single biggest cross-compat risk the question was worried about, so if
   the `allowScripts` and Node-floor work is done properly, the npm bump
   itself is otherwise low-risk and backward-lockfile-compatible.
4. CI is not currently pinned to any npm version at all, so **CI will adopt
   npm 12 on its own timetable regardless of this task's decision** — the
   only thing this task controls is whether local developer machines and the
   `allowScripts` allowlist are prepared for that day, which argues for
   doing it deliberately and separately rather than reactively when a CI run
   breaks.

**If GO is chosen anyway**, exact command and blast radius:

```
npm install -g npm@12.0.2
```

(local/global CLI swap only — this does not touch `package.json` unless a
`packageManager` field or CI-side npm pin is added, and none exists today).
Blast radius if done with no other changes: every `npm install`/`npm ci`
invocation on any machine/CI runner using that npm 12 install will skip
lifecycle scripts for the 27 packages listed in section 6 above, most
severely `electron`, `esbuild` (all 5 copies), and `nx` itself — very likely
breaking the Electron app build, the esbuild-based extension/webview build,
and Nx's own postinstall step until an `allowScripts` allowlist is generated
via `npm approve-scripts --allow-scripts-pending` and committed. The two
Docker build paths (`apps/ptah-license-server/Dockerfile{,.dev}`) are
insulated because they already pass `--ignore-scripts` and compensate
manually.
