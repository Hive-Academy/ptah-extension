New findings

1. **major** — `libs/backend/memory-curator/src/lib/triggers/boot-scan-failure-ledger.ts:28-43` (also `boot-scan-runner.ts:250-286`): a session that has reached `given_up`, is later modified, and then fails again is silently dropped from automatic retries. The normal scan sees the newer mtime and calls `recordFailure`, but the upsert's `WHERE status = 'pending'` leaves the terminal row unchanged; `recordFailure` then reads that non-null `given_up` row, so the runner treats the failure as recorded and advances the watermark. Pending-only retry selection excludes it forever (`boot-scan-failure-ledger.ts:48-52`). A later modified session that succeeds is curated, but also leaves a stale given-up diagnostic because normal-scan success does not remove the terminal row. Required change: store a file generation marker (at least mtime, preferably content/version identity) and reopen/reset a terminal row when a newer generation fails, or do not advance the watermark when recording against a terminal row; remove obsolete terminal rows on normal-scan success. Add positive and negative tests for changed given-up sessions.

2. **major** — `libs/backend/memory-curator/src/lib/triggers/boot-scan-runner.ts:198-205,348-405`; `libs/backend/memory-curator/src/lib/triggers/memory-trigger.service.ts:1008-1025`: ledger retries run first and consume the same hourly limiter, with no slot reserved for the normal scan. With a low `maxCuratesPerHour` and a large pending ledger, the first retry spends the available slot, the next retry returns `stalled`, and the normal scan is not started. Each entry is finite (three attempts), so a fixed finite ledger is eventually drained, but the delay is unbounded in boot count as backlog grows (for a limit of one, roughly three boots per pending entry) and defeats the goal of promptly reaching healthy new sessions. Required change: reserve at least one curate-budget slot for normal scan work when eligible normal sessions exist, or otherwise impose and surface a bounded retry budget that cannot consume the whole hourly allowance; add a low-budget/backlog test.

3. **minor** — `libs/backend/persistence-sqlite/src/lib/migrations/0052_memory_boot_scan_failures.ts:31-32`: the added index is only on `status`, whereas the hot retry query filters by `workspace_fingerprint` and `status` and orders by `last_failed_at, session_id` (`libs/backend/memory-curator/src/lib/triggers/boot-scan-failure-ledger.ts:48-52`). Larger multi-workspace ledgers require filtering/sorting beyond this index. Required change: replace or add a composite index such as `(workspace_fingerprint, status, last_failed_at, session_id)` and assert its query plan in the migration/store test.
