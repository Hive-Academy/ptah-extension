## New findings

1. **Serious — A returned draft can be consumed while no composer exists.** The plan specifies `takeDraft(sessionId)` as a once-per-`operationId` consuming read and directs an effect to call it before putting the text into `chatInput.restoreDraftToInput` (`implementation-plan-v2-user-authorized.md:350-352,362-366`). In compact view, the full-view input is not rendered (`libs/frontend/chat/src/lib/components/templates/chat-view.component.html:4-18,254-258`), and the existing input reference is optional (`libs/frontend/chat/src/lib/components/templates/chat-view.component.ts:638,1313-1317`). If Cancel or a failure is published while the tab is compact, `takeDraft` can mark the operation handled while `chatInputRef()` is absent; returning to full view cannot recover the text. Require the effect to wait for a mounted input before consuming, or make `takeDraft` a peek plus explicit acknowledgement after `restoreDraftToInput` succeeds. Add a compact-view-to-full-view recovery case to S20. This is a likely user path and loses text without an error.

**Five failure questions for this scoped change:** the silent-success path is the consumed but unapplied draft above; switching to compact view before Cancel exposes it; an existing non-empty input must append rather than overwrite (`implementation-plan-v2-user-authorized.md:365-366`); a lane-provider exception must remain unknown and await a click (`:170-175`); and the missing requirement is that draft consumption must depend on the composer actually being mounted (`:350-366`). No other unauthorized start or source send path was found in the revised entry-point contract (`:58-73,214-225,313-332`).
