# Implementation plan — restored Command Center provider mark

## Findings

1. **Running provider.** `ChatSessionService` resolves a workspace-specific `ProviderProfile` for a new run and passes it to the SDK adapter (`libs/backend/rpc-handlers/src/lib/chat/session/chat-session.service.ts:867-901`); it repeats that resolution for a resumed turn (`:1569-1603`). The profile has a canonical `providerId` (`libs/shared/src/lib/types/provider-profile.types.ts:17-25`). `SdkAgentAdapter` receives it at start, resume, and slash-command relaunch (`libs/backend/agent-sdk/src/lib/sdk-agent-adapter.ts:918-966`, `:1209-1269`, `:1614-1650`). The profile can be `undefined` when the shared auth environment serves the same active provider (`libs/backend/auth-providers/src/lib/auth/workspace-provider-profile-resolver.ts:99-125`); the executed query also returns `capacityRoute`, resolved from its effective auth environment (`libs/backend/agent-sdk/src/lib/helpers/session-lifecycle/session-query-executor.service.ts:95-142`). Use `providerProfile?.providerId ?? capacityRoute.providerId`, and leave null routes unknown. These IDs use the same provider registry values as the UI's brand keys, for example `anthropic`, `openai-codex`, `openrouter`, `moonshot`, and `z-ai` (`libs/frontend/ui/src/lib/native/brand-mark/brand-slugs.ts:74-95`). The UI deliberately recognizes only its known keys and otherwise uses the monogram (`libs/frontend/command-center/src/lib/components/command-center-projection.source.ts:19-24`; `libs/frontend/ui/src/lib/native/provider-mark/provider-marks.data.ts:78-87`). No translation to logo slugs belongs in storage.

2. **Persistence.** `SessionMetadata` is keyed by the real SDK session UUID and has no provider field (`libs/backend/agent-sdk/src/lib/session-metadata-store.ts:69-127`). `SessionMetadataStore` writes both detail and lean summary, including record-repository rows (`:288-308`, `:642-701`); `get` and `getForWorkspace` recover them (`:776-800`, `:852-872`). Its Electron legacy-array migration has an explicit `summaryFields` list (`:193-211`) that must include the new field. New-session metadata is created after SDK `init` resolves the real ID (`libs/backend/agent-sdk/src/lib/sdk-agent-adapter.ts:1395-1457`). Resume currently only touches metadata (`:1290-1317`). An optional `providerId` fits `SessionMetadata`; absent remains unknown for old/imported sessions. Add an atomic, serialized update for an existing record so a resumed turn or slash-command relaunch records the latest known provider without overwriting concurrent metadata changes. Do not derive it from the provider selected when old history is merely viewed.

3. **RPC.** `chat:resume` already reads `metadata` (`libs/backend/rpc-handlers/src/lib/chat/session/chat-session.service.ts:1092-1097`) and returns the reply (`:1224-1255`); the smallest resume change is optional `ChatResumeResult.providerId` (`libs/shared/src/lib/types/rpc/rpc-chat.types.ts:281-321`). `session:list` reads stored metadata, maps each row to `ChatSessionSummary`, and returns a page (`libs/backend/rpc-handlers/src/lib/handlers/session-rpc.handlers.ts:417-434`, `:452-515`; type at `libs/shared/src/lib/types/execution/node.ts:229-264`). Add optional `ChatSessionSummary.providerId` to that mapping. The summary Zod schema exists at `libs/shared/src/lib/types/execution/schemas.ts:111-119`; extend it with an optional nonempty string if this boundary is parsed. No reply Zod schema was found for `ChatResumeResult`; the list request and stats-batch request have separate Zod checks (`libs/backend/rpc-handlers/src/lib/handlers/session-rpc.handlers.ts:388-399`; `libs/backend/rpc-handlers/src/lib/handlers/session-rpc.schema.ts:26-33`). `session:stats` is a broadcast, and `SessionStatsEntry` is shared by that push, `chat:resume.stats`, and `session:stats-batch` (`libs/shared/src/lib/types/rpc/rpc-session.types.ts:349-359`); provider identity is session metadata, so do not add it to accounting stats or invent an RPC method.

4. **Frontend.** `SessionLoaderService.switchSession` opens or reuses a tab, calls `chat:resume`, then applies the reply after its current replay/stale-snapshot guards (`libs/frontend/chat/src/lib/services/chat-store/session-loader.service.ts:943-959`, `:990-1059`). Add the reply's provider to that accepted tab through `TabManagerService` (`libs/frontend/chat-state/src/lib/tab-manager.service.ts:1610-1675`), independently of whether stats exist; use the listed summary for the initial tab value when available, then let the reply refresh it. Add optional `TabState.providerId` (`libs/frontend/chat-types/src/lib/chat-types.ts:605-612`). Clear it on fresh reset and rebind to another session (`libs/frontend/chat-state/src/lib/tab-manager.service.ts:1518-1552`, `:2735-2761`); sanitize any persisted value on restore because tabs are spread from storage (`libs/frontend/chat-state/src/lib/tab-persistence.ts:111-130`, `:255-300`). `tabProvider()` currently tries live capacity and a model-matched usage row (`libs/frontend/command-center/src/lib/components/command-center-projection.source.ts:42-51`); change its last expression to `provider(usage?.contextCapacity?.providerId) ?? provider(tab?.providerId)`, and remove the early `!model` return so metadata works without a model. Keep the current priority for live evidence.

## Design

- Persist only the canonical ID of the **root session's latest successfully launched provider**. At new-session SDK `init`, create metadata with the run's known ID. At a resumed turn, update the real session's metadata after query creation and ID validation; at a slash-command relaunch, update after query creation as well. Do not update from `chat:resume`'s read-only history path. Skip null/empty IDs. Keep existing IDs when a run's route is unknown. Preserve metadata on repeated `create` and unrelated `save` calls.
- Pass the optional ID through the existing `chat:resume` reply and `session:list` row. The list allows early display; the resume reply is authoritative for the hydrated tab. Do not add a method or alter `session:stats`, `session:stats-batch`, or transcript reconstruction (`libs/backend/agent-sdk/src/lib/session-history-reader.service.ts:1151-1160`).
- Apply reply state only after the loader's current ownership and stale-snapshot checks. On a missing reply field, do not use today's selected provider; preserve a matching list value if it came from the same session, otherwise leave unknown. When a tab binds to a different session, clear the old ID first. A restored local tab may show its last recorded ID while the backend read completes, but the reply refreshes it.

1. **`agent-sdk`:** `session-metadata-store.ts` — optional field, migration summary field, serialized existing-record update, preservation in saves/creates; `sdk-agent-adapter.ts` — capture the launched query's provider on new, resumed, and slash-command runs. No change to `session-history-reader.service.ts`.
2. **`shared`:** `types/rpc/rpc-chat.types.ts` — optional resume field; `types/execution/node.ts` and `types/execution/schemas.ts` — optional list-row field and matching Zod schema. `rpc-session.types.ts` stays unchanged.
3. **`rpc-handlers`:** `chat/session/chat-session.service.ts` — copy metadata ID into successful resume reply; `handlers/session-rpc.handlers.ts` — copy it into list rows. Existing workspace authorization and filtering remain the boundary.
4. **`chat-types`:** `chat-types.ts` — optional tab field.
5. **`chat-state`:** `tab-manager.service.ts` — set/clear the ID at session binding and reset; `tab-persistence.ts` — accept only a bounded nonempty string on restore.
6. **`chat`:** `services/chat-store/session-loader.service.ts` — seed from the matching list row and apply accepted `chat:resume.providerId` after stale/ownership checks.
7. **`command-center`:** `components/command-center-projection.source.ts` — final provider fallback. `frontend/ui` brand tables need no change.

## Risks

- A session may span providers. One mark cannot encode its history. Choose the **latest provider that launched the root's turn**, matching the current-session display and the requested provider-switch behavior; overwrite the persisted ID only after a later query launches. Child/CLI agent providers do not replace the root mark.
- `ProviderProfile` can be absent on the shared-auth path; use the executed query's `capacityRoute.providerId` then. Its resolver deliberately returns null for ambiguous/custom routes (`session-query-executor.service.ts:124-142`); keep unknown rather than guessing from a current selection. Unknown/custom IDs may still have no UI artwork and retain the monogram.
- Metadata `save` currently merges only selected fields (`session-metadata-store.ts:642-659`); explicitly preserve `providerId` on unrelated writes and serialize updates. Imported old sessions have no field, and transcript history cannot reconstruct it (`session-history-reader.service.ts:1155-1159`).
- Frontend tabs can be reused, rebound, restored from local storage, or receive an older reply after a newer load. Reset mismatched IDs and use the loader's existing replay claim/stale checks (`session-loader.service.ts:1022-1045`).

## Decisions

| Decision | Options | Evidence | Reversible |
| --- | --- | --- | --- |
| Store one optional canonical provider ID in session metadata | Metadata field; infer from model/history; separate store | Metadata already persists and lists by real session ID (`session-metadata-store.ts:69-127`, `:288-308`); history has no route evidence (`session-history-reader.service.ts:1155-1159`) | Yes |
| Use latest root run's provider | First run; latest run; multi-value history | Resume resolves a fresh profile per turn (`chat-session.service.ts:1573-1603`); one Command Center mark per root tab (`command-center-projection.source.ts:42-51`) | Yes |
| Extend existing resume and list payloads | Resume only; list only; new RPC; both existing payloads | Resume already reads metadata (`chat-session.service.ts:1092-1097`); list already maps metadata (`session-rpc.handlers.ts:417-515`) | Yes |
| Prefer live evidence, then stored identity | Stored first; current provider; live first | Current live/stat priority (`command-center-projection.source.ts:42-51`); absent old metadata must stay unknown (`context.md:18-28`) | Yes |

## Clarifications Needed

None. The task context settles the scope and latest-root-provider policy is the smallest defensible single-mark representation.
