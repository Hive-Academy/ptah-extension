# Setup Hub builders vs. the normal chat session — analysis

Paths are relative to `libs/` unless noted. `FE` = `frontend/harness-builder/src/lib`, `BE` = `backend/rpc-handlers/src/lib`.
Line counts are the editor's totals (`view_file`) or approximations; "not read" marks code I did not open.

**Headline:** both builders already run a REAL `chat:start` / `chat:continue` session. What is bespoke is the _rendering shell_ around it: a private composer (`<textarea>`), a private transcript (user bubbles in localStorage merged by timestamp with an execution tree), a private claim/surface/rehydrate lifecycle, and a one-shot broadcast (`HARNESS_CONFIG_PROPOSED`) that feeds the config preview and is lost on reload.

## A. End-to-end flow today

**Shared turn runtime (both modes).** `HarnessWorkflowService.startWorkflow` mints a `TabId` correlation id + `SurfaceId`, claims them (`FE/services/harness-workflow.service.ts:278-297`), then calls the ordinary RPC `chat:start` with `surfaceMode: true` and the correlation id as `tabId` (`:305-315`). Follow-ups use `chat:continue` (`:373-378`), stop uses `chat:abort` (`:427`). So turns DO go through the real chat session runtime (`BE/chat/session/chat-session.service.ts:512,580,770`, `surfaceMode` is threaded to `chat-stream-broadcaster.service.ts:136-184`). Events are then diverted from the tab list to the harness surface: `WorkflowSessionClaimService` maps correlationId→SurfaceId (`chat-routing/src/lib/workflow-session-claim.service.ts:6-29`); `ChatMessageHandler.renderedSurfaceFor` checks the claim + a registered adapter (`chat/src/lib/services/chat-message-handler.service.ts:344-349`); `StreamRouter.routeStreamEventForSurface` writes into the adapter registered by `HarnessBuilderStateService.registerWorkflowSurface` (`FE/services/harness-builder-state.service.ts:567-575`) via `StreamingSurfaceRegistry` (`chat-routing/src/lib/streaming-surface-registry.service.ts:66-89`, `interactive` flag).

**AI Team Builder (`configure-harness`).**

1. Hub card → `openHarnessBuilder()` (`FE/components/setup-hub.component.ts:1299`) → `ptah-harness-builder-view`. `ngOnInit` calls `harness:initialize` (`harness-builder-view.component.ts:693-714`).
2. User types in the view's own textarea (`:355-363`). `sendMessage()` (`:773-804`): adds a local bubble, and if no workflow is active calls RPC `harness:workflow-prompt` (`:783`, handler `BE/handlers/harness-rpc.handlers.ts:922-931` → `HarnessWorkflowPromptService.composePrompt`, `BE/harness/ai/harness-workflow-prompt.service.ts:17-96`) to wrap the user's intent in a ~128-line system-style prompt, then `startWorkflow('configure-harness', composed.prompt)`.
3. The agent calls MCP tool `ptah_harness_propose_config` (`vscode-lm-tools/.../tool-description.builder.ts:1694`) → `proposeConfig` validates with Zod and `broadcast(HARNESS_CONFIG_PROPOSED, …)` (`vscode-lm-tools/.../harness-namespace.builder.ts:1066-1081`).
4. `HarnessWorkflowMessageHandler.handleConfigProposed` (`FE/services/harness-workflow-message.handler.ts:143-151`) calls `state.applyConfigUpdates` (`harness-builder-state.service.ts:325`) → `HarnessConfigPreviewComponent` (`FE/components/harness-config-preview.component.ts:190-264`).
5. "Apply to Workspace" (`harness-builder-view.component.ts:329-352, 806-860`) builds a full `HarnessConfig` in the component and calls `harness:apply` (`BE/handlers/harness-rpc.handlers.ts:481-604`) which writes CLAUDE.md, agents, skills, MCP and reconciles.

**New Project.**

1. Hub card → intake form (state in `setup-hub.component.ts:1179-1250`, `buildIntake` `:1374`, `submitIntake` `:1397`) → `startNewProject(intake)` (`:1440-1444`) → RPC `harness:start-new-project`.
2. Backend (`BE/handlers/harness-rpc.handlers.ts:813-920`): Zod-parses intake (`:822`), enables bundled plugins + reconcile (`:827-847`), composes the seed prompt via `buildNewProjectSeedPrompt` (`:850-854`), `focusChat` (`:857`), **broadcasts `HARNESS_OPEN_WORKFLOW`** `{mode, seedPrompt, intake}` (`:871-879`), disposes the wizard webview (`:889-895`).
3. `HarnessWorkflowMessageHandler.handleOpenWorkflow` (`FE/services/harness-workflow-message.handler.ts:40-69`) → `AppStateManager.requestHarnessWorkflow` + `navigateToSurface('harness-builder')` (`:100-141`) → view `ngOnInit` consumes the request (`harness-builder-view.component.ts:661-683`), sets intake summary as first bubble, `startWorkflow('new-project', seedPrompt)`.

**Where the paths mix.**

- Two prompt composers: `buildNewProjectSeedPrompt` (new-project) vs `HarnessWorkflowPromptService.composePrompt`; the latter has its own "workspace is empty → plan the project first" branch (`harness-workflow-prompt.service.ts:76-96`) that overlaps New Project's purpose.
- Two ways to reach the same view: pull (`workflowPrompt` RPC from the view) vs push (broadcast → AppState request → router → `ngOnInit`).
- The config preview only listens in `configure-harness` mode (`harness-workflow-message.handler.ts:144`), yet the New Project prompt also tells the agent to call proposeConfig; those proposals are dropped.
- **Bespoke SDK path still exists but is not used by the builders:** `HarnessLlmRunner` (`BE/harness/ai/harness-llm-runner.service.ts:12-13`) + `HarnessStreamBroadcaster` (`BE/harness/streaming/harness-stream-broadcaster.service.ts:96,128`) serve `harness:suggest-config / design-agents / generate-skills / generate-document / analyze-intent`. The wired `HarnessRpcService` methods (`FE/services/harness-rpc.service.ts:86-272`) have **no frontend callers** besides `initialize` (`harness-builder-view.component.ts:703`, `harness-builder-state.service.ts:251`), `apply` (`:849`), `workflowPrompt` (`:783`), `startNewProject` (`setup-hub.component.ts:1444`); `harness:load-presets` is called directly from the hub (`:1265`). No frontend code consumes `harness:flat-stream` (grep: only `apps/ptah-cli/src/cli/output/event-pipe.ts:41-42`). The remaining consumer of those RPCs is the CLI (`apps/ptah-cli/src/cli/commands/harness.ts:452,531,585,648`).

## E. Proposed target design

**Builder = a normal chat tab + add-on.** Both precedents already exist:

- `TaskPromptBridgeService.consume` creates a tab, navigates to chat, adopts it as a canvas tile in grid layout, and prefills the composer (`chat/.../task-prompt-bridge.service.ts:53-92`).
- Tribunal creates a conductor tab and injects hidden instructions with `TabManagerService.setFirstMessagePreamble` (`tribunal-panel/.../tribunal-run.service.ts:170-191`; defined `chat-state/.../tab-manager.service.ts:1767-1779`; consumed in `chat/.../message-sender.service.ts:414-417`).

Target flow (both builders):

1. Hub action → one RPC returns the seed prompt (merge `harness:workflow-prompt` and `harness:start-new-project`: plugin enable/toolchain/seed composition stay; **drop** the `HARNESS_OPEN_WORKFLOW` broadcast, `focusChat`, and navigation relay).
2. Frontend: `tabManager.createTab('AI Team Builder' | 'New Project')`, tag it (new tab field, e.g. `workflow: 'harness-config' | 'new-project'`; next to `firstMessagePreamble`, `chat-types.ts:636`), `setFirstMessagePreamble(tabId, seed)`, prefill composer with the intake summary / intent, `setCurrentView('chat')`. No claim, no surface, no `surfaceMode`. The user then uses `ptah-chat-input` and the normal message list, permissions, autopilot, model/effort, stop, tile layout and tab restore.
3. **Add-on panel** for tabs tagged as harness workflows: `HarnessConfigPreview` + "Apply" (+ workspace-pin badge). Needs a host slot in chat view / tile (Assumption, verify; otherwise a docked panel in the app shell keyed on the active tab).
4. **Structured output:** keep `ptah_harness_propose_config` (it already exists and validates input with Zod, `harness-namespace.builder.ts:1070-1076`). To make it reload-safe and session-scoped, rebuild the preview by **folding the session's own tool-call events** for that tool, instead of a one-shot broadcast. _Assumption:_ flat `tool_use` events carry the tool input and are present in the `chat:resume` history; verify before committing. Fallback: persist proposals per session in `HarnessConfigStore`.
5. Apply stays a user-confirmed `harness:apply` (unchanged backend).

**Becomes deletable (approximate):**

- `harness-workflow.service.ts` (672) — all.
- `harness-workflow-message.handler.ts` (153) — all; at most ~20 lines survive in the add-on state for config proposals.
- `harness-builder-view.component.ts` (871) — ~550 lines (composer, transcript, bubbles, permissions, stats, start-over, seed consumption); ~300 remain as the add-on (preview + apply + pin).
- `harness-builder-state.service.ts` (671) — ~250-350: streaming state, operation surfaces, `HarnessSurfaceFacade`, `registerWorkflowSurface` (`:40-70,547-690`), conversation/intent setters (`:303,481-516`, **callers not checked**).

- `new-project-intake.ts` (88) stays; hub shrinks by ~150-300.
- Specs for the above: `harness-builder-view.component.spec.ts` 747, `…prompt-isolation.spec.ts` 483, `harness-workflow.service.spec.ts` 747, `harness-workflow-message.handler.spec.ts` 291, and ~400 of `harness-builder-state.service.spec.ts` 853 are rewritten or removed.

LLM-runner family (~1,640 lines: suggestion 570 + prompts 229, doc-gen 239, subagent-design 167, skill-gen 142, runner 167, broadcaster 126) is **not** removable until the CLI decision (Open questions).

## F. Known fragility (bespoke path)

1. **Config preview is lost on reload.** Transcript is replayed from history (`harness-workflow.service.ts:640-670`) but `proposeConfig` is a live broadcast (`harness-namespace.builder.ts:1078`) consumed only by `applyConfigUpdates` (`harness-workflow-message.handler.ts:147`). The workflow record stores only `mode/sessionId/workspaceRoot/bubbles` (`:61-67`). After reload the agent's conversation exists but the preview and "Apply" are empty. (No `localStorage` hit in the state service; **verify** it has no other persistence.)
2. **Proposals are not session-scoped.** The broadcast carries no session/tab id (`:1078-1081`) and the handler accepts it whenever the workflow mode is `configure-harness` (`harness-workflow-message.handler.ts:144`). A normal chat agent calling the tool, or a second window, mutates the builder preview; New Project proposals are dropped.
3. **Two parallel identities and in-memory claims.** Correlation id/`SurfaceId` die with the page; rehydrate mints new ones and rebinds (`harness-workflow.service.ts:556-583`). The claim map is an in-memory signal (`workflow-session-claim.service.ts:6`). Events that arrive between claim and adapter registration fall through to the tab path (`chat-message-handler.service.ts:344-349`); `rehydrate` is async (`:545`) and invoked from an `effect` guarded by a boolean (`:226-233`).
4. **Launch relay has 5 hops** (RPC → broadcast → AppState request → router → `ngOnInit`): failure handling at `harness-workflow-message.handler.ts:127-141`, a view-level `ngOnInit` consume that depends on mounting (`harness-builder-view.component.ts:661`); broadcast failure is only a warn (`harness-rpc.handlers.ts:881-888`) while the RPC returns `success: true` (`:904`).
5. **Spinner/processing state is hand-managed.** `isProcessing` mixes `_started` and liveness (`harness-workflow.service.ts:196-203`); abort must call `liveness.markIdle` by hand because no turn-end fires (`:409-436`); `failTurn` resets `_started` (`:399-403`). Each new path is another chance for a stuck composer.
6. **User messages dropped silently.** `sendMessage` with no resolved `sessionId` logs and returns (`:363-368`) but the bubble was already added (`view:778`); `workflowPrompt` failure only `console.error`s (`view:791-796`) after the bubble was added; `rollBackFailedStart` clears storage but not bubbles (`:341-357`).
7. **Timeline hack.** User bubbles and nodes are merged by wall-clock `at`/`startTime` (`:36-48`, `view:566-600`); pre-timeline records use `at: 0` (`:564-571`). User turns are not part of the SDK history replay, so ordering depends on two clocks and localStorage.
8. **Non-interactive auto-deny.** A prompt for a surface-only conversation is auto-denied (`stream-router.service.ts:460-470`); correctness depends on `registerWorkflowSurface` having set `interactive` (`harness-builder-state.service.ts:567-575`; flag `streaming-surface-registry.service.ts:46-94`). Pending questions need a separate restore pass (`workflow.service.ts:605-631`) or the 5-minute auto-pick answers for the user (comment `:594-598`).
9. **Double workspace pinning.** `HarnessWorkflowService._workspaceRoot` (`:146`) and `HarnessBuilderStateService` pinned root + `_buildInProgress` (`:128-147,230-236`) pin the same fact separately; apply reads the state one (`view:848`).
10. **Session invisible to normal tooling.** Claimed tab ids are filtered from the tab bar (`tab-bar.component.ts:198`) so the builder session cannot be viewed/resumed/forked as a session tile. (Assumption: it still appears in session history; not checked.)
11. **Dead streaming plumbing.** `registerOperationSurface/routeOperationEvent/unregisterAllOperationSurfaces` (`harness-builder-state.service.ts:64-69,578-672`) have no external callers; `harness:flat-stream` has no webview consumer.
12. **Large test surface for a thin shell:** ~3,550 spec lines across 6 files (747+483+431+853+291+747) guard code that duplicates chat behaviour.

## Decisions

1. **Reuse the real tab, not the surface.** Evidence: `TaskPromptBridgeService` and Tribunal already create tabs and inject prompts; the surface path forces a copy of every chat feature (B).
2. **Seed via `setFirstMessagePreamble` + composer prefill** rather than a hidden first turn: the user sees only their own message, and the existing consume point is `message-sender.service.ts:414-417`.
3. **Keep `ptah_harness_propose_config` as the structured channel;** change _how the preview derives state_ (fold the session's tool events) so it survives reload and is session-scoped.
4. **Keep the prompt composers and apply pipeline;** only the transport and shell change.
5. **Do not touch `WorkflowSessionClaimService`/surface registry** in this change; other consumers depend on them.
6. **Hub:** extract the intake into its own component; keep the card grid as navigation.
