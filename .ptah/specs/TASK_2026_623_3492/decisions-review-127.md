# Decision review #127 — Batch 28 preview metadata

## Verdict

**AGREE-WITH-CHANGE — REVISE.** The ruling is correct that the present per-tool data cannot support the prototype's file-relative Edit range or the Write `New file` assertion. It must not, however, leave the visible `1..n` gutter unqualified: in a file preview it reasonably reads as file line numbers while it is actually the ordinal within each replacement string. Require the minimal Batch 28 change: label the gutter (visually and accessibly) as **“replacement snippet line”** (or remove the numbers). Do not present a file range. `N lines` is acceptable.

Severity: **1 Moderate**. This is a user-visible wrong implication on every multi-line Edit, but it neither changes files nor corrupts transcript data.

Score: **6/10** (works with a real correctness gap). It exceeds 5 because it does not fabricate unavailable metadata and accurately renders the supplied strings; it cannot reach 7 until the displayed line-number semantics are made unambiguous and covered by a spec.

## Evidence and conclusions

### 1. Is “no data available” correct?

Yes for the data supplied to this component and for the declared Edit/Write tool results.

- `EditToolInput` contains only `file_path`, `old_string`, `new_string`, and optional `replace_all`; it has no offset, match location, or file-line range ([fs.ts:18](D:/projects/ptah-extension/.claude-worktrees/task-623-display-panel/libs/shared/src/lib/type-guards/guards/fs.ts:18)). `WriteToolInput` contains only `file_path` and `content`, with no create/overwrite discriminator ([fs.ts:11](D:/projects/ptah-extension/.claude-worktrees/task-623-display-panel/libs/shared/src/lib/type-guards/guards/fs.ts:11)).
- The declared `EditToolOutput` adds only `message`, `replacements`, and `file_path`; the declared `WriteToolOutput` adds only `message`, `bytes_written`, and `file_path` ([fs.ts:73](D:/projects/ptah-extension/.claude-worktrees/task-623-display-panel/libs/shared/src/lib/type-guards/guards/fs.ts:73), [fs.ts:132](D:/projects/ptah-extension/.claude-worktrees/task-623-display-panel/libs/shared/src/lib/type-guards/guards/fs.ts:132)). Neither supplies a range or creation signal.
- `DiffDisplayComponent` receives only `EditToolInput` plus a replacement count ([diff-display.component.ts:129](D:/projects/ptah-extension/.claude-worktrees/task-623-display-panel/libs/frontend/chat-ui/src/lib/molecules/tool-execution/diff-display.component.ts:129)); the transcript tree preserves input as an untyped record and output as `unknown` ([node.ts:151](D:/projects/ptah-extension/.claude-worktrees/task-623-display-panel/libs/shared/src/lib/types/execution/node.ts:151)). The builder passes the raw tool-result output but does not parse or attach a location ([agent-monitor-tree-builder.service.ts:687](D:/projects/ptah-extension/.claude-worktrees/task-623-display-panel/libs/frontend/chat/src/lib/services/agent-monitor-tree-builder.service.ts:687)). Parsing an incidental text result would therefore be heuristic, not a real contract.

There is a distinct source that could superficially look relevant, but it is not a usable exception. A `TurnChangeSetFile.status === 'A'` records a file as added relative to HEAD ([rpc-change-set.types.ts:12](D:/projects/ptah-extension/.claude-worktrees/task-623-display-panel/libs/shared/src/lib/types/rpc/rpc-change-set.types.ts:12), [rpc-change-set.types.ts:18](D:/projects/ptah-extension/.claude-worktrees/task-623-display-panel/libs/shared/src/lib/types/rpc/rpc-change-set.types.ts:18)). It is a post-turn, turn-wide file list, not an Edit/Write result or a call-correlated event; the transcript resolves it by the whole turn window ([transcript-turn-snapshots.ts:55](D:/projects/ptah-extension/.claude-worktrees/task-623-display-panel/libs/frontend/chat/src/lib/components/organisms/transcript/transcript-turn-snapshots.ts:55)). It cannot prove that a particular Write created rather than overwrote a file, especially where several operations affect the same path or the file was already dirty. Wiring it into a live per-call preview would be out of scope and still semantically wrong.

### 2. Edit gutter semantics

The ruling correctly identifies that the component derives the values from the two strings: each old and new string starts at `i + 1` ([diff-display.component.ts:141](D:/projects/ptah-extension/.claude-worktrees/task-623-display-panel/libs/frontend/chat-ui/src/lib/molecules/tool-execution/diff-display.component.ts:141), [diff-display.component.ts:151](D:/projects/ptah-extension/.claude-worktrees/task-623-display-panel/libs/frontend/chat-ui/src/lib/molecules/tool-execution/diff-display.component.ts:151)). That is not a file-relative range.

The displayed gutter gives only a bare number and is hidden from assistive technology ([diff-display.component.ts:97](D:/projects/ptah-extension/.claude-worktrees/task-623-display-panel/libs/frontend/chat-ui/src/lib/molecules/tool-execution/diff-display.component.ts:97)). Nothing visible says “snippet” or “replacement,” while the approved visual specification pairs a file preview's line-number gutter with `Lines 41-46` ([design-spec.md:194](D:/projects/ptah-extension/.claude-worktrees/task-623-display-panel/.ptah/specs/TASK_2026_623_3492/design-spec.md:194)). A user can consequently read a shown `1` as the first line of the file, a success-looking but wrong result. The source comment’s internal clarification does not reach the user ([diff-display.component.ts:18](D:/projects/ptah-extension/.claude-worktrees/task-623-display-panel/libs/frontend/chat-ui/src/lib/molecules/tool-execution/diff-display.component.ts:18)).

Required change: retain the useful ordinals only if the diff block/gutter visibly identifies them as **replacement snippet lines**, and expose the same meaning in its accessible name. Add a spec for a file edit whose strings yield `1..n`, asserting that the qualifier is rendered and no file-relative range is claimed. Removing the gutter also resolves the defect, but is a larger loss of the design/plan’s line-number-gutter capability ([implementation-plan.md:1103](D:/projects/ptah-extension/.claude-worktrees/task-623-display-panel/.ptah/specs/TASK_2026_623_3492/implementation-plan.md:1103)).

Calling it “New file” would claim the unavailable state described above, despite the prototype wording ([design-spec.md:193](D:/projects/ptah-extension/.claude-worktrees/task-623-display-panel/.ptah/specs/TASK_2026_623_3492/design-spec.md:193)). No change is required for this portion of ruling #127.

## Five logic questions

1. **Silent failure:** bare snippet ordinals present as file-looking line numbers; no error indicates their different semantics ([diff-display.component.ts:97](D:/projects/ptah-extension/.claude-worktrees/task-623-display-panel/libs/frontend/chat-ui/src/lib/molecules/tool-execution/diff-display.component.ts:97)).
2. **Unexpected user action:** opening any multi-line Edit and using its gutter to navigate or reason about the target file produces a wrong location; the numbers restart for added text ([diff-display.component.ts:151](D:/projects/ptah-extension/.claude-worktrees/task-623-display-panel/libs/frontend/chat-ui/src/lib/molecules/tool-execution/diff-display.component.ts:151)).
3. **Wrong-answer input:** an Edit replacing lines 41–46 with a two-line string displays `1`, `2` rather than its real file range, although the prototype explicitly depicts the latter ([design-spec.md:194](D:/projects/ptah-extension/.claude-worktrees/task-623-display-panel/.ptah/specs/TASK_2026_623_3492/design-spec.md:194)).
4. **Dependency failure/shape:** there is no validated location/create field to fail over from; raw `toolOutput?: unknown` cannot safely be parsed as a location contract ([node.ts:153](D:/projects/ptah-extension/.claude-worktrees/task-623-display-panel/libs/shared/src/lib/types/execution/node.ts:153)). The safe behavior is the no-range / `N lines` fallback.
5. **Requirement gap:** R7 requires readable sign-gutter diffs and counts, but does not define what non-file-relative line numbers mean ([task-description.md:809](D:/projects/ptah-extension/.claude-worktrees/task-623-display-panel/.ptah/specs/TASK_2026_623_3492/task-description.md:809)). The label is necessary to close that omission without inventing metadata.
