## Architecture decision

- Chosen approach: extend existing shared contracts; place named-account registry, route admission and official authentication actions in auth-providers; expose a narrow token-only resolver port to SDK. Add a thin first-class Claude adapter using a shared extraction of the existing native lane executor, with `SdkQueryRunner.runInteractive` as launch funnel. Bind every named run durably before its first prompt. Scope all directory-sensitive resources to that immutable binding. Codex subsequently implements the same domain contract through per-home existing services.
- Rationale: this preserves the repository's proven query, policy, permission, MCP, stream, session and owner paths while correcting their currently ambient-only readers. It avoids an SDK → concrete auth-providers dependency cycle and distinguishes account identity from local routing.
- Rejected alternatives: a second Claude stream protocol duplicates working behavior; aliasing `ptah-cli` fails first-class identity; process-global env switching races; copying credentials/shadow homes violates scope; putting registry in ordinary settings loses concurrent updates; directory-derived known quota keys invent separate allowances; “latest native query” usage reads cross accounts; replacing actions with directory selection removes approved scope.
- Assumptions: A1–A4 above are explicit live-enable compatibility holds. No assumed Claude model ID, unsupported SDK effort level, credential-store namespace, auth-status identity field, or auth command flag is a contract.
- Effect on existing code: bounded extraction replaces the native registry's duplicated launch mechanics in place. Its ambient env/policy behavior remains tested unchanged. Existing provider definitions, API-key routes, other lanes and default resolution remain. No V2/legacy shims or alternate account scheduler.

### 2. Transactional registry, canonical routes and run leases

- Purpose: authoritative non-secret local profile/routing state with race-safe admission.
- Duplicate-directory safe result and UI copy remain exactly design §3.1: “This local account directory is already represented by another profile. Rename that profile instead.” No path is included.
- Responsibilities: Add, list, rename, metadata removal, independent selections, physical route reservation, CAS revisions, and authentication/run exclusion across processes using the same DB.
- Verified contracts: public SQLite transaction and prepared-statement surface (`sqlite-connection.service.ts:46-77`); common DB profile/path (`db-path.ts:11-64`); relational transaction precedent (`sqlite-lane-outcome.store.ts:178-229`); migration registry (`migrations/index.ts:82-105`).
- Proposed storage: profiles (opaque ID, provider, label, physical route/fingerprint, revision, auth epoch/state), workspace/provider/scope selections, run bindings/leases, and exclusive account-operation reservations. Keep tombstones/reservations for removed IDs/routes so a directory cannot masquerade as a newly isolated account while old bindings exist. No auth file bodies, OAuth tokens, browser URLs or raw identities in DB. Identity hash follows existing owner derivation; it is not an authorization credential.
- Canonicalization: create directory before reservation; resolve its physical realpath including Windows junctions/symlinks, record stable filesystem identity where available, compare actual filesystem equivalence rather than unconditional lowercasing (case-sensitive APFS/Windows directories exist). Revalidate realpath/identity immediately before launch/action. Canonical duplicate is one route, not two accounts. Include ambient routes observed by active runs in collision/reservation checks; reject aliasing a named route to them. Permission/unresolvable/unsupported physical identity checks fail closed. A malicious same-user process replacing files is outside an OS sandbox guarantee, but detected route changes never silently pass.
- Add transaction reserves unique canonical route and inserts profile; failed commit removes only the newly created **empty** directory owned by this attempt. Never recursively delete external/user/credential content. Empty orphan directories after crash may be cleaned only when ownership and emptiness are proven. No automatic import/adoption of another credential directory.
- Run admission transaction reads selected profile/revision, checks operation exclusion, reserves immutable run context; auth action uses exclusive route reservation. No SQL transaction is held over process/network await. CAS completes operation only if operation ID/epoch still matches. Cross-process SQLITE_BUSY/storage failure is safe retryable refusal, not in-memory fallback.
- Lease lifetime: acquired before preflight and released after child close, including startup failure/cancel/abort/timeout/disposal. Metadata removal does not revoke an already executing lease but blocks every new user continuation/resume. Never expire/break an auth exclusion solely by age. After a crash, unresolved operation/run reservations are unavailable until the owner is proved terminated and recovered; absence of proof blocks mutation. Assumption: implementer must verify a host-neutral process-liveness/recovery contract before adding automatic reclamation; this plan does not authorize PID-only, timeout-only lock stealing. No per-profile polling timers. Reservations are keyed per canonical physical route: a stuck route refuses only that route, not unrelated canonical routes. This task adds no automatic reclaim, PID or timeout lock stealing.
- Dependencies: auth-providers → persistence-sqlite public API, platform/process ports and shared contracts. Persistence owns only static schema. Registrations may be lazy: Electron currently registers auth before persistence (`phase-2-libraries.ts:207,397`), so no eager DB access during service registration.
- Failure behaviour: no partial selection/profile writes; corrupt registry fails named operations without changing ambient routes. ## Integration architecture

### Data flow

1. Electron typed intent → strict account RPC schema/capability → registry transaction → sanitized revision snapshot → shared host messages → state owner → Accounts view.
2. Fresh native main/lane request → existing provider/policy selection → account selection resolution → physical route/store/source certification and lease → account-aware model/output-style/MCP/resources → existing SDK runner with immutable child env → own-query identity → awaited binding persistence → first prompt.
3. Stream output → existing transformer/events → owner fixed to observed run identity → ledger and output persistence. Completion closes SDK child and releases resources/lease; no account mutation or rotation.
4. Resume/continuation/child → stored binding (or truly legacy absence) → identity/physical-route admission → existing resume/cost/permission path. No current-default lookup for bound resume.
5. Usage discovery → observed route/query handles → identity-derived owner dedup → owner-correct reader → owner cache → existing dashboard. Unknown stays distinct.

### State or persistence

- Registry is authoritative for profile revision, scoped future selections, route reservation, auth epoch, operation ID and run binding. Session detail/reference duplicates only required immutable linkage and remains validated.
- Child env, SDK query, mailbox, operation process and account-service handles belong to one admitted run/operation. No process-global account state.
- Credentials belong to official provider CLI stores, not Ptah storage. Remove metadata never deletes directory/keychain/login/transcript. No automatic cross-account migration or registry import from credential files.
- Existing ambient behavior is retained per runner. Profile-less legacy records are not backfilled with current selected/default profile.

### External boundaries

- Untrusted inputs: RPC IDs/labels/revisions, persisted records, CLI stdout/exit status, SDK account/model/usage payloads, filesystem identity and external settings. Validate each at entry; parameterized SQL and process argument arrays; bounded output/control calls.
- Auth-source precedence and store compatibility are certified explicitly. Unknown cannot be silently treated as isolated. No credential content in logs/UI/events. Managed policy is not bypassed.
- Technical implementation and mocked tests do not establish Anthropic/OpenAI authorization or permit live sign-in/inference.

### Failure and rollback

- Failure before first prompt aborts/disposes child, records safe failure, releases lease, leaves original conversation/binding intact.
- Atomic metadata transactions roll back together; external auth side effects cannot be rolled back by pretending DB rollback restored credentials. Recheck status and surface uncertain/disconnected state.
- Resume failure never retries with ambient/another profile. User must explicitly start a different conversation; this task does not design migration.
- Failed route verification, stale operation completion, invalid persistence, wrong App Server home and unverified store all fail closed. Auth action timeout is not success; cancellation is not proof provider-side authorization was revoked.

### Observability

- Use existing repository logger/event paths with safe codes, provider, opaque profile/run/operation IDs, revision/epoch, capability and boolean presence flags. No raw auth output, paths, email/org, tokens, browser URLs or credential bodies.
- Record admission stage and refusal reason so an otherwise silent persistence/source/route failure is diagnosable. UI distinguishes unsupported, unavailable, busy, held, cancelled and signed-out; quota unknown is not signed-out.
