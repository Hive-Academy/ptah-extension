## Numbered issues

### 1. Blocking — Diagnostics coverage never reaches the formatter

**Plan section:** Diagnostics / Batch 25 (`Plan:221`, `Plan:345`).

**Verified evidence:** `MCP/namespace-builders/core-namespace.builders.ts:225` explicitly reconstructs unavailable results; `:254` explicitly reconstructs available results with only status, source, diagnostics and requestedFiles. `MCP/types.ts:200` has no coverage field. Neither file is in Batch 25. Adding coverage to the provider and reading it in the formatter does not pass it through this boundary. The proposed unavailable-language counts also have no typed home if coverage is added only to the available arm (`Plan:327`).

**Fix:** Include the payload type and namespace forwarding in the design/file ownership, with an explicit available/unavailable representation. Require a real provider → namespace → dispatcher/formatter regression for a mixed TS/Python workspace, including the nonempty-diagnostics branch, severity filtering, and a long result under the budget. A formatter-only fake payload test cannot catch this defect.

### 2. Blocking — Symbol search and reindex still return silent empty answers

**Plan section:** Inventory row for code tools / Batches 22 and 24 (`Plan:98`, `Plan:327`, `Plan:339`).

**Verified evidence:** `WI/services/code-symbol-indexer.service.ts:381` returns zero symbols and zero errors for an unsupported extension. `MCP/namespace-builders/code-namespace.builder.ts:388` then reports `filesScanned: 1`. Search returns `{ hits, bm25Only, index }` at `:317`, with hits ahead of metadata and no language coverage. The full index discovers only configured extensions and stops at 2,000 files (`WI/services/code-symbol-indexer.service.ts:203`, `:218`); its skip filter runs afterward (`:234`).

**Fix:** Design response-level coverage for both code tools, including an unsupported single-file reindex, a file-filtered search, and mixed-workspace search. Give the namespace and index result contracts owners. Persist or retain coverage with the index generation that actually answers; a fresh filesystem census alone cannot prove an older index covers it. Preserve freshness/error fields and put bounded coverage before hits. Include cap/skipped/failed accounting and vendor exclusions for this indexer, not only the dependency graph. Descriptions do not satisfy Decision 18(a).

### 3. Serious — The proposed coverage shape cannot represent its own promised outcomes

**Plan section:** Coverage contract (`Plan:116`), lazy loading (`:160`), graph coverage (`:210`), diagnostics (`:224`).

**Verified evidence:** The shape defines uncovered as files skipped _for their language_. It has no representation for grammar-load/read failures, a truncated census, the 50-file diagnostics limit, resolver-context partiality, vendor exclusions, or per-language discovered/graphed counts promised later. `WI/ast/dependency-graph.service.ts:238` currently publishes the input count, not successful node count; parsing failures are skipped at `:339`. `MCP/mcp-core/protocol-dispatcher.ts:2773` only compares counts. `PC/interfaces/diagnostics-provider.interface.ts:39` says a scoped available answer may not silently check less than the owning projects, whereas the new provider deliberately offers a single-file syntax check.

**Fix:** Define disjoint accounting and a bounded reason/status representation before implementation. Separate supported capability, actual completed checks, unsupported language, excluded files, cap omissions, and analysis failures; explicitly disclose unknown/truncated census totals. Resolve the syntax-only scope contract in the interface and its contract tests. Do not infer TypeScript/JavaScript checked-file counts from filename extensions: the TS provider returns diagnostics, not a list of all checked files (`WI/diagnostics/type-script-diagnostics-provider.ts:504`). Describe how its real scope is obtained or report that scope as unknown. Define multi-root aggregation for the merged symbol index (`MCP/mcp-core/protocol-dispatcher.ts:2185`) and publish graph plus coverage atomically under the existing generation guard (`WI/ast/dependency-graph.service.ts:231`). Keep Batch 9/9b meanings and field order intact. Add tests for partial grammar failure, unreadable files, 51 requested files, census saturation, superseded builds and mixed roots. Measure the serialized budget bound; collection-length bounds alone do not prove 500 characters.

### 4. Serious — Resolver inputs and declaration maps have not been designed

Merely adding query node names and resolver classes cannot supply the proposed C#/Java declaration maps or Rust lexical module context.

**Fix:** Specify the normalized extraction contract and its producer/consumer changes, including necessary changes to `ast-analysis.interfaces.ts` and extraction logic. Define import kind, relative level, aliases/multiple imported names, namespace/package declarations and Rust inline module context where needed. Document capture conventions if reusing existing fields instead; demonstrate they preserve the required distinctions. Define resolver dispatch/wiring, including where each later batch enables the capability and registers its resolver. Test nested C# namespaces, using-static/aliases/global using, Java nested-type/static imports, Python multi-name and relative imports, Go grouped/backtick imports, Rust grouped uses and inline modules. Clarify that Java FQN imports are not universally file-exact merely by joining public type/file names.

### 5. Serious — LSP honesty wiring is incomplete, and the new graph gate still loses references

**Plan section:** Electron fallback / Batch 26 (`Plan:258`, `Plan:351`).

**Verified evidence:** The host capability is defined in `MCP/namespace-builders/ide-namespace.builder.ts:42`, not just `types.ts`. That builder reconstructs the LSP namespace at `:214`; adding an optional method to the host does not forward it. Neither interface nor forwarding is in Batch 26's file list. C# fallback also needs actual declaration queries: `Electron:459` returns uncertain without an entry, and the partial query map at `:153` has no C#. Updating extension mapping alone is insufficient.

The proposed references gate checks graph capability, but graph capability does not establish complete reference scope. `Electron:646` restricts search to graph dependents. The design expressly omits same-namespace C# references, same-package Java references, and several dynamic/module cases (`Plan:200`–`:204`). Once those languages gain graph capability, the restriction again drops real references. Capped or partially failed graphs create the same problem. `Electron:72` also excludes Kotlin, `.csx` and `.cxx` from brute scans, and `:684` caps scans without result metadata. The no-host implementation returns empty lists at `MCP/namespace-builders/ide-namespace.builder.ts:347`; the inventory covers Electron only.

**Fix:** Specify and forward the capability method through both interfaces and the builder. Add real declaration queries or keep definitionFallback false. Use complete-enough scope evidence, not language support alone, to justify graph narrowing; otherwise scan conservatively and disclose text-search approximations and caps. Derive scan extensions from the relevant capability. Cover no-host CLI answers, unsupported references, Kotlin after activation, C# same-namespace references, Java same-package references, capped graphs and cross-language importers. Keep array-returning namespace APIs compatible unless an explicit migration is designed; response notes can be introduced at the MCP boundary.

### 7. Serious — File caps do not bound discovery, resolver expansion or manifest work

**Plan section:** Dependency graphs / Risks (`Plan:191`, `Plan:212`, `Plan:428`).

**Verified evidence:** Graph discovery currently asks for `Number.MAX_SAFE_INTEGER` results and slices afterward (`MCP/mcp-core/protocol-dispatcher.ts:2679`). The plan bounds each manifest at 256 KiB but does not bound manifest count/total bytes, namespace/package expansion, or aggregate edge count. Existing linking yields between imports (`WI/ast/dependency-graph.service.ts:386`); a new single import returning thousands of targets needs yielding/cancellation inside that expansion. The same 5,000 files can produce quadratic file-to-file namespace/package edges.

**Fix:** Define bounded discovery/census behavior, manifest count and total-byte budgets, and aggregate edge/expansion limits with honest truncation. Filter vendor paths before cap allocation; retain existing `node_modules` and `target` excludes (`WI/file-indexing/workspace-default-excludes.ts:17`, `:24`). Distinguish eligible graph files from unsupported census-only files so unsupported languages do not consume all parse slots. Extend generation checks/yields through context creation and multi-target linking. Add a large single-package/namespace fixture, many-manifest fixture, vendor decoys, saturation, and cancellation checks. Realpath containment must apply to manifest reads too; membership in a lexical discovered-file set is not proof of physical containment.

### 8. Serious — Q2's recommended automatic checker mode is not safely specified

**Plan section:** Tier 1 / Security / Q2 (`Plan:235`, `Plan:309`, `Plan:448`).

**Verified evidence:** The proposed four Go environment overrides do not constrain inherited `GOCACHEPROG` or `GOENV`. Go documents an external cache command and configurable environment-file loading. It also documents private-module proxy bypass. Thus the stated “no project code / no network” guarantee does not follow from these overrides. The cited repository precedent spreads the inherited environment (`WI/project-analysis/toolchain-probe.ts:115`), and it is a toolchain probe, not a sandbox. The process port accepts the _complete_ child environment (`PC/interfaces/process-spawner.interface.ts:28`). [Go command environment documentation](https://pkg.go.dev/cmd/go#hdr-Environment_variables), [private module handling](https://pkg.go.dev/cmd/go#hdr-Configuration_for_downloading_non_public_code).

**Fix:** Before asking the user to choose Q2, specify an allowlisted environment, disable environment-file/external-cache hooks and private-module network escape paths, constrain toolchain roots, and strip Node preload hooks for a Node-based checker. Resolve canonical executable paths outside the workspace, rejecting relative/empty PATH entries and repository-local or symlinked wrappers; “not node_modules/.bin” alone is insufficient. Explain that executing a PATH program is an execution trust choice even if the intended checker is static. Require a consent/opt-in policy or revise the automatic option's guarantees. Add fake-spawner tests for hostile PATH/environment, delayed spawn followed by timeout, output overflow, process failure and cancellation. Preserve partial successful diagnostics when another checker fails. No checker was executed in this review.

## Additional risks and unresolved verification

- A registry capability is an implementation claim, not evidence that a particular file/index/build was successfully analyzed. Preserve per-run failure evidence and independently fixed acceptance criteria.
