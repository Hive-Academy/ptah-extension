## Part 1 — C# resolver findings

No Blocking finding was found: I traced `resolve()` end to end (name parsing → scope walk → `lookup` → `linkTo`/`LINKS_NOTHING` → `outsideTheWorkspace`) against several adversarial fixtures reasoned through by hand (typo'd namespace segments, ancestor-only namespaces, cross-project namespace collisions, partial types, MSBuild `<Using>` sharing) and none produces a wrong answer under a clean/complete report; the risky-looking mechanisms are each backed by a real semantic reason.

### R34C-01 — Moderate — `linksNothing` self-tally short-circuits coverage counting for manifest-declared global usings, one arbitrary file decides the whole project's disclosure

- File: `libs/backend/workspace-intelligence/src/ast/dependency-graph.service.ts:930-949` (implicit-import branch), `csharp-context.ts` `manifestUsings` (one shared `imp` object per `<Using>` item).
- Scenario: an MSBuild `<Using Include="Contoso.Missing">` (no workspace namespace, no package proof, not the framework root) is shared by a 50-file C# project. `Map` iteration order (insertion order of `nodes`) picks whichever file was added to the graph first as the one whose resolution is tallied (`talliedImplicit`); every other file's resolution of the same `imp` object is computed but only used for edges, never re-tallied.
- Impact: this is not a wrong-answer risk here (the miss is external/unresolved either way, independent of `fromFile`, since no workspace namespace matches it under any exclusion), but it does mean the _choice_ of which file's resolution stands for the coverage gap is arbitrary and undocumented beyond "the first time it is resolved" (build order, not source order). If a future change makes resolution `fromFile`-sensitive for the external/unresolved path (e.g. per-file `LangVersion`/nullable-context proof), this tally-once-by-identity design would silently keep using whichever file iterates first. Today it is safe because `outsideTheWorkspace` never reads `fromFile`.
- Recommendation: no fix required now; leave a code comment at the `talliedImplicit` check noting the invariant it relies on (that `outsideTheWorkspace`'s classification is `fromFile`-independent), so a future resolver change that breaks the invariant is caught by inspection rather than by a flaky first-file-wins result.

### R34C-02 — Minor — `record`/`struct`/`class` all report `kind: 'class'`

- File: `csharp-public-symbols.ts:77-84` (`TYPE_KINDS`).
- A public `record` or `struct` is indexed with `kind: 'class'`, same as an actual class. `ptah_get_symbol_index` callers cannot distinguish a record from a class from the kind field. This is a labelling coarseness, not a wrong answer (the symbol is real, public, and correctly named) — Minor, not Serious.

### R34C-03 — Minor — `Microsoft`/`System` root proof and `outsideTheWorkspace`'s ordering are disclosed but not tested against a workspace namespace that shares the root

- File: `csharp-import-resolver.ts:224` (`FRAMEWORK_ROOTS` checked before the internal-namespace fallback).
- If a workspace declared its own `namespace System.Something { … }` with direct content, `lookup()` would find it first (namespace lookup runs before `outsideTheWorkspace`), so this is not reachable as a false-external in practice — confirmed by tracing the call order in `resolve()`. No fixture exercises this exact adjacency, but the code path that would matter never reaches `outsideTheWorkspace` for a namespace with real content. Documented in the executor's D5; no test gap that changes the verdict.

No finding reaches Serious or Blocking. The `linksNothing` mechanism itself — the specific thing the brief asked me to try to break — is sound: `ctx.csharp.namespaces` (the set that makes `linksNothing` reachable) is built exclusively from genuinely declared namespace blocks and their real dotted ancestors (`csharp-context.ts:253-261`); it never contains a typo'd or coincidental name. I constructed the adversarial case by hand (a `using` naming a namespace that is a real ancestor of an unrelated, distant declaration, with no direct content of its own) and confirmed by reading the C# language rule that `using N;` on an ancestor-only namespace genuinely binds nothing usable — so `linksNothing` there is not hiding a miss, it is modelling actual C# scoping correctly. Genuine misses (typos, moved namespaces) fall through to `UNRESOLVED_INTERNAL` because their exact dotted path is absent from both `namespaceFiles` and `namespaces`.

The 200-file truncation bound (`MAX_TARGETS_PER_IMPORT = 200`, `import-resolver.ts:107`) is applied identically for `namespace`- and `file`-kind resolutions in `linkTo`, and the executor's 300-file namespace fixture is present and passing. `ProjectReference` is confirmed never parsed as a package (`readMsbuildItems`'s regex only matches `(Global)?PackageReference`), matching the documented rule that it is never proof of externality.

Public symbols: partial types with no access modifier and declarations with an `ERROR` child are both routed to `'unknown'` and end up in `unextracted` (not dropped), except when their owner is already `'unknown'` (to avoid double disclosure) — traced through `csharpPublicSymbols`/`visibilityOf`/`ownerUnknown` and confirmed by the passing spec's partial/unreadable-modifier tests.
