### R34G-01 — Blocking — MSBuild `<Using>` items are silently dropped for every C# file with no enclosing `.csproj` (the root group)

**Anchors:** `import-resolution/csharp-context.ts:334-347` (`manifestUsings` builds its result only `for (const project of projects.dirs)`), `:152-176` (`dirs` only collects directories where a `.csproj` was found), `:243-275` (`projectsGuessed` fires only on `!projects.complete` or a _file_-declared `global using` with `project === ''`).

**Failing input (executed, real `buildResolverContext` over a temp root):**

- `Directory.Build.props`: `<Project><ItemGroup><Using Include="Acme.Billing" /></ItemGroup></Project>`
- `Billing/Invoice.cs`: `namespace Acme.Billing; public class Invoice {}`
- `App/Program.cs`: `public class Program {}`
- No `.csproj` anywhere.

**Observed (probe output):** `ctx.gaps = []` (no `csharp-project-unknown`, no other gap), `ctx.csharp.globalUsings` keys = `[]`, and `CSHARP_IMPORT_RESOLVER.implicitImports('App/Program.cs')` = `[]` — although the props manifest **was** found, listed and read. In a graph build nothing is tallied: no edge `App/Program.cs → Billing/Invoice.cs`, `external: 0`, `unresolvedInternal: 0`, `truncatedImports: 0`, `context: 'complete'` — a **clean answer with the real implicit import missing**. The very same props file reaches every file once any `.csproj` exists (probe contrast: `implicitImports` returns the using with `declaredOutsideGraph: true`), which proves the drop is the root-group special case, not the normal path. The same silent drop hits the realistic variant where one subtree has a `.csproj` and other C# files (scripts, tools, top-level files) sit outside every project directory while the nearest `Directory.Build.props`/`.targets` above them declares usings.

The module comment's own model says a project's global usings include the nearest `Directory.Build.props`/`.targets` at or above _its directory_; for the root group the code applies neither the usings nor the `csharp-project-unknown` gap that exists precisely for "a project and the global usings it declares may be missed". Fix either way: apply the nearest manifest usings to the root group, or raise the gap.

### R34G-02 — Serious — a `$(…)`-built `<Using Include="…">` is dropped with no disclosure at all

**Anchors:** `import-resolution/csharp-context.ts:384-390` (`includes()` filters every value containing `$(`), consumed at `:209-220` (`readMsbuildItems` usings) — no unextracted marker, no gap anywhere for a skipped using.

**Failing input (executed):** `readMsbuildItems('<Project><ItemGroup><Using Include="$(RootNamespace).Models" /></ItemGroup></Project>')`.

**Observed (probe output):** `usings: []`. `<Using Include="$(RootNamespace).Models" />` is ordinary MSBuild (SDK projects do this with `$(RootNamespace)`); when the expanded value is a workspace namespace, every file of the project silently loses those dependency edges and the answer stays clean (`external: 0`, `unresolvedInternal: 0`, `context: 'complete'`). The module comment's rationale — "a value built from a property proves nothing and is skipped" — is right for _package proof_ (dropping proof is conservative) but wrong for _usings in scope_: an unresolvable using is an import the graph could not analyse, and must be disclosed (a gap, or tallied unresolved/partial), not skipped.

### R34G-03 — Serious — `linksNothing` for an enclosing-only namespace hides reachable workspace content as clean

**Anchors:** `import-resolution/csharp-import-resolver.ts:95-100` (the `namespaces.has(...)` second loop returns `LINKS_NOTHING`), `:62-66` (`linksNothing`), `import-resolution/dependency-graph.service.ts` `tally` (`linksNothing` returns `[]` before any unresolved count; no approximation is added). Pinned as intended by `import-resolution/csharp-import-resolver.spec.ts:177-187` ("a namespace holding only nested namespaces links nothing and is not unresolved", asserting `unresolvedInternal: 0`, `external: 0`).

**Failing input:** the spec's own `BILLING` fixture (`Billing/Invoice.cs`, `Billing/Order.cs` declare `namespace Acme.Billing`) plus `App/Use.cs` = `using Acme;\npublic class Use { Acme.Billing.Invoice i; }`.

**Observed:** `deps('App/Use.cs') = []` and the coverage stays `unresolvedInternal: 0`, `external: 0`, context complete — clean. But `using Acme;` genuinely brings `Acme` into scope, so `Billing.Invoice` is reachable through the directive and the file does depend on the `Acme.Billing` files. The `using Acme.Billing;` form of the same dependency gets an approximation-marked edge; the parent form gets nothing at all. `namespaces` (csharp-context.ts:253-262) already knows `Acme` is an enclosing-only namespace with content below it, so the cheap honest options are: fan out to the files of every namespace below it under the existing `csharp:namespace-edges` approximation, or disclose the under-approximation instead of returning a bare `linksNothing`. This is exactly the reviewed rule ("a resolved import linking to nothing is not unresolved") hiding a real miss as clean. The "declared only by the importing file" sub-case of `linksNothing` is correct; this one is not.

### R34G-04 — Minor — a file whose declarations could not be extracted files its public types under the _global_ namespace, which can mint a wrong **precise** edge

**Anchors:** `import-resolution/csharp-context.ts:263-269` (`typeNamespaces = declared.length > 0 ? declared : ['']`), `import-resolution/csharp-import-resolver.ts:182-187` (`lookup` length-0 fallback reads `typeFiles.get('\u0000T')`).

`FileNode.declarations` is absent whenever the declaration query yields nothing (e.g. the `namespace` node is lost under an `ERROR` parse region) while the export query still captures the type. `typeFiles` then holds `''\u0000MathX`, and another file's `using static Acme.Util.MathX;` binds through the length-0 global fallback to a `kind: 'file'` edge with **no approximation** — a wrong (namespace-misfiled) target presented as precise. Plain `using Acme.Util;` degrades honestly (`unresolved-internal`, because some workspace namespace starts with `Acme`), which contains the damage. I could not produce a grammar input that triggers the declaration-loss half, so this is flagged theoretical, not executed: if the Batch 34 author cannot name a real trigger either, a `declarations`-absent-with-`exports`-present disclosure (or filing such types nowhere) closes it.

Notes (documented in the executor report's "Known limits", disclosed at capability level, no finding): `<Using Remove>` can leave phantom edges (`referenceScopeComplete: false`); a type is filed under every namespace its file declares, which only affects invalid directives (`using static A.T` when `T` is in `A.B`); `Microsoft.*` root as unconditional external proof is the executor's disclosed D5.
