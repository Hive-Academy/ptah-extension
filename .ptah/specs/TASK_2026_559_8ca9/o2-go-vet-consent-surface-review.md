# O2 consent-surface amendment review

Verdict: **REVISE**

Reviewed against the source on disk and context.md Decisions 18, 19 and 24. This is the single design review round; it does not authorize a new review loop or change batch state. Paths below are repository-relative.

## Findings

1. **Serious — the proposed generic revoke route silently does nothing.** Document §§1–2 says adding `supportedTargets: ['workspace']` lets `config:getScopes` inspect and `config:clearScopeOverride` revoke consent. `libs/backend/rpc-handlers/src/lib/handlers/config-scope-rpc.handlers.ts:112` treats _any_ one-element target list as global-only and immediately returns success without clearing; its inspection logic repeats that assumption at `:178`. Thus the proposed row reports no override and the advertised generic revoke leaves consent enabled. **Required change:** explicitly include this handler and its spec in the amendment; determine global-only from the actual target value rather than list length, and test inspection and both clear modes for a workspace-only key. Alternatively remove this generic route and its allowlist registration from the design and use only the dedicated consent RPC. Do not advertise both while implementing only the dedicated route.

2. **Serious — consent is not bound to the workspace displayed to the user.** Document §3 GET returns a workspace root, but SET accepts only `{ enabled }` and writes to whichever workspace is active when SET arrives. `apps/ptah-electron/src/activation/bootstrap.ts:226` supplies a mutable active-folder source; `libs/backend/settings-core/src/scope/workspace-scope-resolver.ts:105`, `:197` and `:215` resolve the active path afresh. Display A, switch to B, then deliver the old toggle: B can become authorized although the user saw A; the equivalent stale revoke can leave A authorized. **Required change:** return a workspace identity with GET and require that expected identity on SET; validate it against host-owned roots and reject stale requests before writing or clearing. Specify UI refresh on workspace changes and tests for A→B and A→no-workspace between GET and SET. Caller identity is a comparison token, never authority to open an arbitrary root. Include a grant→run→revoke→next-run-no-spawn test and state when the checker rechecks consent before launching queued work.

3. **Moderate — `which` does not search only the supplied sanitized PATH on Windows.** Document §5 and test §7.5 assume that behavior. The installed dependency is declared at `package.json:196`; `node_modules/which/lib/index.js:25` prepends `process.cwd()` on Windows, and `:20` inherits PATHEXT unless overridden. Rejecting a final result inside the checked workspace protects that particular root, but does not enforce the stated search restriction when the host process cwd differs from the checked root. It can also let a rejected cwd candidate hide a valid installed Go binary. **Required change:** resolve candidates strictly from the sanitized absolute directories, constrain Windows lookup to `go.exe`, canonicalize directories and candidates, and reject workspace-owned destinations. Do not rely on bare `which('go', { path })` for this property. Add a test with host cwd different from the checked root and containing `go.exe`, plus a sanitized PATH containing the valid toolchain. Preserve the final canonical-path and wrapper checks. The process port alone is not a no-shell guarantee: `libs/backend/agent-sdk/src/lib/helpers/off-thread-process-spawner.ts:705` reparses via cross-spawn; test the accepted executable path through that adapter too.

4. **Serious — the replacement consent storage contract and reader ownership remain inconsistent.** Document §2 replaces the approved plan's host-state key with a home-settings override, but §7.3 still says `getStorage`/resolver and the governing checker requirement at `batches.md:4273` still mandates `getStorageForWorkspace(root)` denial. The replaced contract is `implementation-plan-languages.md:380`. These are different stores and failure conditions, not alternate names for one operation. In addition, importing settings-core directly into the checker would violate the current settings-core consumer guard (`libs/backend/settings-core/src/settings-core.spec.ts:784`–`:821`, which does not admit workspace-intelligence). Electron's resolver is registered only after `ElectronDIContainer.setup` (`apps/ptah-electron/src/activation/bootstrap.ts:218`, `:231`, `:234`), so early checker construction cannot assume it exists. **Required change:** explicitly enumerate the superseded consent key/read/write/failure contract and align the checker acceptance tests with the chosen store. Name the host-owned adapter or injected consent reader and its registration timing; keep the checker free of an unapproved settings-core import. Resolve the two §3 assumptions now: CLI active-root sourcing exists at `libs/backend/cli-engine/src/lib/container.ts:737`, resolver registration at `libs/backend/platform-cli/src/settings/cli-settings-registration.ts:88`; Electron registration is at `libs/backend/platform-electron/src/settings/electron-settings-registration.ts:85`. Required Electron/CLI enablement cannot be satisfied merely by returning `supported:false` when wiring is missing.

5. **Moderate — the surface file/test handoff is incomplete.** Document §8 names only the settings HTML parent; the standalone parent's explicit imports are in `libs/frontend/chat/src/lib/settings/settings.component.ts:63`–`:78`, which must also change. The CLI router is not identified by path, although the comparable registration is `apps/ptah-cli/src/cli/router.ts:331`. Section 7 specifies checker tests but no assertions for the new UI, CLI or consent RPC specs. **Required change:** name the parent TypeScript file, `apps/ptah-cli/src/cli/router.ts`, `apps/ptah-cli/src/cli/commands/config.spec.ts`, the consent handler spec, and any host wiring specs; give surface acceptance cases: persisted workspace-only grant; no global fallback; restart/readback; workspace isolation; revoke; no open root; unsupported VS Code; invalid params; failed persistence without success UI/CLI output; and stale-root rejection from finding 2. Specify the SET success/error result and CLI failure exit behavior. Record a host test proving repository settings cannot enable consent. The existing file store is host-configurable (`libs/backend/platform-cli/src/implementations/cli-workspace-provider.ts:49`), so describe the actual host-selected settings directory rather than claiming every invocation necessarily uses the default home path.

6. **Moderate — the hostile toolchain test expects the wrong result.** Document §5 says a newer `go` **or** `toolchain` line fails under `GOTOOLCHAIN=local`; §7 expects `toolchain go9.99.0` alone to produce `toolchain-mismatch`. A `toolchain` directive is a suggestion, whereas the `go` directive establishes the minimum version. With local switching disabled, a newer suggestion need not fail. This is also stricter than the existing acceptance at `implementation-plan-languages.md:401`, which asks for no switch and the local version. The environment reaches the process as supplied (`libs/backend/platform-core/src/interfaces/process-spawner.interface.ts:28`; `libs/backend/agent-sdk/src/lib/helpers/off-thread-process-spawner.ts:706`). **Required change:** separate tests: a newer suggested toolchain proves no switch/download; a newer minimum `go` version proves reported incompatibility. Correct the §5 prose accordingly. Evidence: [official Go toolchain selection](https://go.dev/doc/toolchain#select).

7. **Minor — one evidence citation does not support its claim.** Document §4 cites `batches.md:1940`–`:1945` for the quoted-`from` validate-deps rule. Those lines record a commit and successful checks, not that rule. **Required change:** replace the citation with the actual validator implementation or the current explanatory batch passage. Also refresh the resolver citations: `readForPath` starts at `workspace-scope-resolver.ts:149`, `hasOverrideForPath` at `:168`, and the global fallback write is at `:200`.

## Verification and limits

- Checked the cited settings registry/defaults, prefix routing, schema definition/registry, scope allowlist, generic settings setter, RPC manifest/type-map examples, CLI config example, browser settings card, VS Code diagnostic read, and host-owned-root batch decision. Their underlying mechanisms exist; the concrete discrepancies are above. A VS Code `getDiagnostics()` call does not itself prove that a Go extension is installed or configured to run vet; phrase that host note conditionally.
- The proposed strict boolean read plus an explicit workspace override prevents global-only consent from authorizing every workspace. Its storage is not a repository configuration file by default. No production `setConfiguration` caller was found in vscode-lm-tools; matching test mocks are not production writes.
- The fixed argument array, no caller flags, module/package bounds, explicit environment, 30-second run timeout within the 45-second budget, combined 2 MiB output limit and cancellation/tree-kill requirements are appropriate design requirements. They are not implemented or proven by this document. Retain the real-binary hostile fixtures and delayed-spawn cleanup tests. No project code or Go checker was executed or changed in this review.
- Only review deliverables were written. No tests/builds were run: this reviews proposed contracts, with no implementation edits to verify.
