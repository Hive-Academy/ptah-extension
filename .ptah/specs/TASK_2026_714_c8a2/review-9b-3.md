## Checked

- **Packaged builds cannot enable native routing through the override.** `readCodexDevRouteOverride` (`codex-dev-route.ts:18`) returns null unless `isPackaged === false` and `PTAH_CODEX_RUNTIME_DEV` is exactly `'1'`. `true`, missing, and `undefined` packaging all return null (`codex-dev-route.spec.ts:22` and `:46`). `createElectronCodexRouting` (`codex-runtime-composition.ts:76`) is the only production caller, and the packaged case expects both capability flags false and `devRoute: null` (`codex-runtime-composition.spec.ts:173`). `registerCodexRuntime` will honor a hand-built `devRoute`, but Electron passes only `routing.devRoute` from that reader (`codex-runtime-composition.ts:252`). VS Code `surface-composition.spec.ts` and CLI `codex-runtime-composition.spec.ts` forbid `readCodexDevRouteOverride`, `registerCodexRuntime`, and `devRoute` in host production sources. No other production registration of `DevRouteOverride` exists. Bootstrap reads `app.isPackaged` (`apps/ptah-electron/src/activation/bootstrap.ts:587`).
- **Lane never passes the override.** `codexDevRouteCovers` rejects `'lane'` before it reads `consumers` (`codex-dev-route.ts:10`). The frozen list is only `'chat'` and `'gateway'` (`codex-dev-route.ts:25`). `resolveGatedCodexRuntime` throws `Codex production routing disabled by parity gate` for lane even when the override is present, and it does not warn (`registration.ts:121`, `registration.spec.ts:94` and `:124`). The Electron scope spec asserts the same throw (`codex-runtime-composition.spec.ts:212`).
- **Old `consumer` field readers in production are updated.** Ripgrep over `*.ts` / `*.tsx` for `devRoute`, `DevRouteOverride`, `readCodexDevRouteOverride`, `codexDevRouteCovers`, and `.consumer ===` found no production read of the old override field. The two production readers now call `codexDevRouteCovers`: `registration.ts:121` and `codex-runtime-composition.ts:83` and `:86`. `index.ts:48` exports the helper. VS Code and CLI do not read the override. The remaining `{ consumer: 'chat' }` `DevRouteOverride` values are the three fixtures in finding 2. Other `.consumer ===` hits are execution-profile consumers, not the override.
- **Warn-once WeakMap is correct.** `devRouteWarnedConsumers` (`registration.ts:106`) keys a `Set` by container. The set is created on first bypass, the warning is emitted only when that consumer is absent, and the consumer is added after the warn (`registration.ts:124`). The message names the consumer. A disabled gate with no coverage throws before any warn. A second resolve of the same consumer on the same container does not warn again. A second container warns again. The registration spec pins both containers, gateway then chat, lane silent, and the parity gate still `enabled: false` (`registration.spec.ts:77`). Re-entrant `logger.warn` could warn twice because `add` happens after `warn`; the Electron logger does not re-enter this function. Not counted as a defect.
- **Specs cover the required cases.** Gateway without DS1 stays gated for all three consumers and does not resolve `Runtime` (`registration.spec.ts:53`). Gateway and chat with DS1 are admitted, lane is refused, and each container warns once per admitted consumer (`registration.spec.ts:77`). Chat without an override still throws the parity error (`registration.spec.ts:62`). Electron: default flags off (`codex-runtime-composition.spec.ts:164`), packaged DS1 ignored (`:173`), both flags follow `CodexParityGate.isEnabled` without DS1 (`:186`), and unpackaged DS1 sets both flags and admits chat and gateway while lane throws (`:196`). `CodexParityGate.isEnabled` is typed and implemented as constant `false` (`codex-parity-gate.ts:222`), so today the flags are true only through the override.

Not a 9b-3 defect.** `createElectronCodexRouting` sets the flag (`codex-runtime-composition.ts:84`). `bindElectronCodexChat` publishes that same object as `hostCapabilities` (`codex-runtime-composition.ts:363`) and as `SDK_TOKENS.RUNTIME_HOST_CAPABILITIES` (`:600`). `createCodexRuntimeAdmission` builds `ChatRuntimeProfileService` with that object (`codex-chat-host-ports.ts:185`). `prepare` forwards `hostCapabilities` but hardcodes `consumer: 'chat'` (`chat-runtime-profile.service.ts:129`).
