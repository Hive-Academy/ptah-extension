## Registrations and lifecycle

`registerCodexRuntime(container, ports)` receives resolved `CodexRuntimeOptions` plus `usage: { auth, profileForHome } | null`. No registration factory calls `resolve`.

| Token                           | Provider                                                                                 |
| ------------------------------- | ---------------------------------------------------------------------------------------- |
| `CODEX_RUNTIME_TOKENS.Runtime`  | One concrete `CodexRuntime(ports)` per registration.                                     |
| `ExecutableSource`              | Supplied executable port.                                                                |
| `ApprovalSink`                  | Supplied sink.                                                                           |
| `ThreadIdentityStore`           | Supplied store.                                                                          |
| `Clock`                         | Supplied clock.                                                                          |
| `Logger`                        | Supplied logger.                                                                         |
| `HomeAuthReader`                | Supplied usage auth reader, or `{ useFactory: () => null }`.                             |
| `CodexParityGate` class         | One gate instance.                                                                       |
| `CodexAccountUsageClient` class | One client using the shared internal process and clock, or `{ useFactory: () => null }`. |

The seven Symbol.for tokens are reused unchanged. The two additional services use class tokens because 2a provides no symbols for them. The usage process factory validates consumer `usage` and the exact requested normalized home before constructing the internal process. Composition provides a full profile, so the registration invents no default model, workspace, permission level or home. Registration creates no process, auth watcher or timer. Register once per host; its owner explicitly calls runtime/client `close()` at shutdown. The real runtime port lacks `close()`, so host cleanup uses the concrete class contract.

Only a type import from tsyringe is needed in production registration. No decorators or runtime tsyringe import are introduced there; consequently no new reflect-metadata dependency is needed. Existing Jest setup already loads reflect-metadata before the test's real container import.

## P2 review-note reconciliation

1. **Manifest duplication:** public canonical name is `CodexExecutableManifestRow` from the 2a ports. `CodexProtocolManifest` stays internal and is not exported by the barrel. The portable row structurally satisfies the internal verifier input; it also preserves version/schema digest fields and omits developer binary paths. Removing the internal duplicate declaration would require editing committed 2b source, outside this batch.
2. **experimentalApi:** not behaviorally fixed because neither the profile builder nor the process/validator belongs to 2k. The public barrel documents the exact discrepancy and cites `codex-protocol-validator.ts:539`, `experimentalApi: z.literal(true)`. The process (`:162`) always sends true; the builder (`:246`) sets the profile field only for ask. A barrel wrapper would conceal two builders and alter fingerprint/resume semantics. Follow-up in the owning files must align the profile contract/fingerprint with the negotiated literal before rollout. This batch neither widens the validator nor changes the handshake.
