## New gaps

1. **Settings save of gpt-6-sol did not reach the composer; T1 ran on gpt-6.1-sol.** The main-agent save logged `config:model-switch {"model":"gpt-6-sol"}` (app-run1.log 1362-1363), and the first `config:models-list` sent `savedModel: gpt-6-sol` (1495). A concurrent second `models-list` then sent `savedModel: "gpt-6-astra"` (1497-1498; the global `selectedModel` at settings.json:142). The composer ended up on "Default (recommended)", which is the opus tier = gpt-6.1-sol. T1's usage and rollout show `gpt-6.1-sol` (1582). The available list has no gpt-6-sol (`sdkValues: default, gpt-6.1-sol, gpt-5.6-terra, gpt-5.6-luna`). gpt-6-sol could only be chosen through the extra "GPT 6 Sol" entry, per tile (`model-selector.component.ts:279-288` keeps a per-tab override). No model notice is shown because 'default' is exempt (`chat-runtime-profile.service.ts:160`). Evidence: `modelpick.png`, `t1.png`.
2. **Every in-place Codex follow-up fails (new regression).** The second message on any live Codex session gives "Message delivery failed. Codex chat could not start." (T2 on A, T4 on B; app-run1.log 1617, 1736). `chat-session.service.ts:1282-1286` always passes `{ files, images, clientMessageId }`. `codex-chat-adapter.ts:536-542` rejects any option key other than `files`, `images` or `admission`, so it throws `unsupported('messageOptions')`. This throw skips `failure()`, so **nothing is logged**; it only reaches the generic `CODEX_RUNTIME_FAILED`. `clientMessageId` arrived with `7fb4ad120` ("carry prompt identity on chat continue"), which is not in the p8j head. Multi-turn Codex chat now works only via restart + resume. Evidence: `t2.png`, `t4-inplace.png`.
3. **A killed Codex process leaves the tab stuck and shows no error (S3).** `chat-stream-broadcaster.service.ts:371-381` skips `CHAT_ERROR` because the adapter error is `webviewReported: true`. The renderer's `handleChatError` (`chat-lifecycle.service.ts:209-251`) settles a tab only through `settleFailedSessionStart` (announced tabs). It logged `Chat error: [object Object]` and left the tab `running` with a skeleton loader; Stop does not clear it. Evidence: `t8-stuck.png`, `t8-after-stop.png`; app-run1.log 2124-2148.
4. **Read auto-accept never applies (p8j gap A still open).** The sink declines with `reason: details-gate` because Codex sends a non-null `environmentId` on every command approval (`codex-chat-approval-sink.ts:135-137`). Plain `Get-Content -LiteralPath README.md -TotalCount 3` still shows a card in Manual. The diagnostic line added after p8j works (gap 3 of p8j is fixed). Evidence: app-run1.log 1839, 1930; `t6-approval1.png`.
5. **The mode chip does not match the effective Codex policy (p8j gap 2 still open).** E changed to Auto-edit on a live thread (toggle succeeded), then resumed after the restart without refusal, but T10's `turn_context` still says `untrusted` / `workspace-write`. Suspect the live `updateNextTurn({ permissionLevel })` (`codex-chat-adapter.ts:701-715`) is recorded, so the resume identity check passes, but the resumed turn's native policy stays the thread's original one. Not verified. Evidence: E rollout `turn_context`, app-run1.log 2393, app-run2.log 1317.
6. **A mode change on a tab whose Codex process died fails silently (p8j gap 1, partly fixed).** Live threads now work, but a dead or not-ready context fails with `runtime-failed: permission. Error: Codex context is not ready` and no visible error. Evidence: app-run1.log 2173, 2214, 2262, 2303; `s6-autoedit-prerestart-popover.png`.
