## Goal

A live Codex `chat:continue` no longer waits for the whole turn. `sendMessageToSession` resolves when `turn/start` returns a receipt (`codex-chat-turn-stream.ts:156-160`). `publishUntilAdmitted` keeps the broadcaster loop running and logs a later publisher rejection (`codex-chat-admission.ts:36-53`). The host adds the streaming id before the first pull (`chat-stream-broadcaster.service.ts:153`, `:207`), so the post-send check still sees an attached loop and returns `{ success: true, sessionId, enqueued: true }` (`chat-session.service.ts:1302-1309`). That is inside the 120s admission budget. Claude is unchanged: `nativeFollowUp` requires `acceptsFollowUpWithoutStream`, and `promptDelivered` is still Codex-only (`chat-session.service.ts:1290-1293`, `:1973-1975`).

## Defects

1. `chat-session.service.ts:1257-1258` (severity: moderate). A resumed Codex turn that is still streaming now returns `enqueued: true`. The approved 8r-5 correction returned `{ success: true, sessionId }` for that case. Both replies arm streaming (`message-sender.service.ts:877-882`). The flag is the only difference: `enqueued !== true` retires the pending prompt. Resume never forwards `clientMessageId`. The resume config omits it (`chat-session.service.ts:1903-1922`), and the open-thread `turn()` call has no third argument (`codex-chat-adapter.ts:237-243`), so the stream never echoes that id and the terminal `turn_state` has no `consumedClientMessageId`. The prompt stays in `QueuedPromptRecord` for the whole turn. A lane report that arrives while it is still the transcript tail is inserted before the user's message (`inbound-peer-message.ts:57-68`). Restore `{ success: true, sessionId }` for the running resume branch, and point `chat-continue-codex-resume-once.spec.ts:449` back at that payload. The live follow-up at `:1309` already returns `enqueued: true`.

2. `codex-chat-turn-stream.ts:357-394` (severity: moderate). A `turn/start` refusal is rejected only after the catch yields the failure notice and the failed turn state, and after `deps.close(session)`. The broadcaster therefore paints the notice before `sendMessageToSession` rejects. `codexFailure` then returns `CODEX_RUNTIME_FAILED` (`chat-session.service.ts:657-665`). The renderer rolls the optimistic user bubble back and appends a delivery-failure bubble (`message-sender.service.ts:849-865`) on top of the notice. Before this batch the broadcaster swallowed that throw (`chat-stream-broadcaster.service.ts:315-383`) and the ended stream took the `settled: true` path, which keeps the user bubble and does not add a second card. Signal the admission rejection before those yields, or skip the notice when the RPC will carry the error. A kill after admission is unaffected: the send has already resolved, the notice stays the one card, and `webviewReported` still suppresses the second `chat:error`.

- Post-admission. The publisher promise has both handlers (`codex-chat-admission.ts:38-51`). Production `streamEventsToWebview` swallows the stream error, so the new "after admission" log line does not run for a normal host failure; `failure()` already logged it (`codex-chat-adapter.ts:690-693`).

A resumed turn can still finish inside the microtasks queued by the fire-and-forget `streamEventsToWebview` (`chat-session.service.ts:1965-1970`) before `continueSession` checks `isStreaming`, so the ended-resume `settled: true` branch remains reachable. G3 is unchanged for a kill after admission: no `forceIdle` was added, the RPC has already succeeded, and the terminal `failed` state settles the tab.
- Specs. The open-stream, swallowed-refusal, late-publisher, and real-adapter continue tests fail on the old awaited send (`codex-chat-adapter.spec.ts:290-394`, `chat-continue-codex-resume-once.spec.ts:180-315`). New deferred resolvers are `let finishPublish: () => void = () => undefined`. The new tests have no `any`, `as unknown as`, `ts-ignore`, readonly mock assignment, or private bracket access.
