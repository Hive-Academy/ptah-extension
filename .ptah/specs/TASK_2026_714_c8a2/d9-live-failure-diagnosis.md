## 2. Fatal frame handling and logging

`codex-app-server-process.ts:328-338` labels a response with its pending method, calls `receive`, and catches **every** exception as `Codex invalid protocol frame`. `receive` validates the whole reply before settling the pending request (`:342-349,376-417,439-468`). Only `model/list` `invalidResult` receives request-local rejection (`:402-415`); any `thread/list` result failure escapes to `onData`, which invokes `fail`. `fail` stores a process-wide failure and calls `close` (`:538-579`), rejecting all pending work. A result-schema mismatch is therefore treated like malformed JSON/framing even when the response ID and envelope are valid. `request()` validates the result again after `sendRequest` (`:271-278`), but that point is never reached after `receive` throws.

`codex-protocol-validator.ts:57-65` discards `safeParse` issues and `CodexProtocolError` retains only code and method (`:46-55`). `fail` logs reason, method, optional RPC code and stderr tail (`codex-app-server-process.ts:559-577`); it does not inspect its cause for schema paths. This explains why `electron.log:1887,2093,2245` names `thread/list` but has no failing path. `codex-session-history.ts:31-49` would classify a directly surfaced `invalidResult` as `malformedPage`, but the current process-wide wrapper makes this a `processFailure` and the user sees `HISTORY_FAILED` (live report and log `:1888,2098,2246`).

## 3. Minimal correct fix and spec cases

1. Preserve a bounded list of **issue paths and issue codes only** in `CodexProtocolError` from `safeParse`; never retain or log the received value, Zod message, input, preview, prompt, or full reply. Record method plus paths/codes at WARN when a response result is rejected. `unrecognized_keys` messages can contain field names, so log the structured `issue.path` and `issue.code`, not `issue.message` or issue metadata. Bound both path depth and issue count.
2. Once an envelope has a known pending response ID, handle `invalidResult` for **any** request by clearing that request's timer, deleting only its pending entry, rejecting it with `CodexProtocolError`, and returning from `receive`. Keep malformed JSON, invalid envelope, unknown response ID, and malformed server requests on the existing fatal path. This extends the narrow `model/list` path at `codex-app-server-process.ts:402-415` and lets history map the direct error to `malformedPage` (`codex-session-history.ts:39-40`). A bad `thread/list` page must not close a healthy App Server or reject unrelated requests.
3. Change a field schema only **after a captured failing 0.165.0 reply identifies its path**. Follow the existing server-data policy: preserve known discriminants, allow additive object keys (`z.object`) and safely tolerate unknown future enum strings where consumers can handle them. Do not replace the whole thread/page with `z.any()` or globally weaken envelope/parameter validation. A generated JSON schema diff alone is insufficient if the actual runtime payload is where the drift appears.
4. Capture a redacted, recorded 0.165.0 `thread/list` page containing both root and child, with `source.subAgent.thread_spawn`, parent link, pagination fields, and the **actual offending field/value shape**; retain only synthetic IDs/text/paths in the committed fixture. The current real child is proof of the shape to include, but the existing live folder has no raw rejected reply, so this fixture cannot yet reproduce the historical failure. Test root and child `thread/read`, including `includeTurns:true`, separately.

Spec cases: valid recorded root+child page; additive top-level/thread fields; unknown safely-tolerated enum; truly malformed required field rejected with exact sanitized path; two concurrent requests where one invalid result rejects only that promise and a following request succeeds; invalid envelope still closes process; history error is `malformedPage` rather than process failure; pagination reaches child and applies parent link. ## 4. Native sub-agent history projection

This is a **backend translation-layer gap**. The native item is `collabAgentToolCall` (`codex-protocol-schemas.ts:351-386`). `codex-event-translator.ts:474-491` translates every such call into plain `toolStarted` / `toolCompleted` with native names (`spawnAgent`, `sendInput`, `wait`) and only `receiverThreadIds` as input/output. `CodexChatEvents.map` then emits `tool_start` with `isTaskTool:false` (`codex-chat-events.ts:236-253`) and `tool_result` (`:254-270`). `codex-chat-turn-stream.ts:330,351-369` forwards those events unchanged. The existing frontend builds an agent card only when a tool start has `isTaskTool` or a recognized agent-dispatch tool name (`libs/frontend/chat/src/lib/services/agent-monitor-tree-builder.service.ts:710-725`); otherwise it builds a plain tool node (`:727-744`). No frontend Codex branch is needed.

The history projector already discovers child links from `receiverThreadIds` (`codex-history-projector.ts:64-85`), adds `parentToolUseId` to child events (`:87-98,143-179`), and synthesizes an `agent_start` on a linked child (`:180-184`). But it passes `{}` as the agent input, so `HistoryEventFactory.createAgentStart` yields `agentType:'unknown'` unless a Claude-style task input exists (`history-event-factory.ts:261-294`). More importantly, its parent `tool_start` still has `isTaskTool:false`, so the existing frontend does not build the agent node. The correct emitted contract for a native **spawn** is Claude-compatible `tool_start` marked as an agent-dispatch/Task tool, with `toolCallId`, `toolInput` containing a meaningful `subagent_type`, `description` and prompt when available, and a matching `agent_start` with `toolCallId`, `agentId` = native child thread ID, `agentType`, description, timestamp and `parentToolUseId` as appropriate. Child `message_start`, deltas, nested tool events and completion must carry the spawn tool ID as `parentToolUseId`; the spawn's `tool_result` closes the card. Translate follow-up `sendInput`/`wait` as child activity/results without creating duplicate agent cards. This is implementable in `codex-event-translator.ts`, `codex-chat-events.ts`, and `codex-history-projector.ts`, with the typed event contract in `codex-runtime.types.ts` if new metadata is needed. Keep frontend contracts unchanged.

The finished `wait` labelled **Running** is real in both `before-reload.json` and `after-reload.json` (the former already says `Running\nwait`), so reload did not introduce it. Since native history failed, the after-reload view came from renderer cache; **this run does not exercise the history projector for that row**. A row remains streaming whenever its `tool_start` lacks matching `tool_result` (`agent-monitor-tree-builder.service.ts:715,727-744`). The translator emits a result for a completed `collabAgentToolCall` (`codex-event-translator.ts:474-483`); the projector emits started and completed notifications for each persisted item (`codex-history-projector.ts:221-225`). A fresh read-only `thread/turns/list` of the affected root returned a completed first turn and three persisted collab items: `spawnAgent completed`, `sendInput completed`, and `wait completed`; the first visible `wait` in cached UI has no clear corresponding persisted item. That makes a missing live result or stale cached row plausible, but its exact event loss cannot be proven without raw event IDs. Add a regression that checks every finished wait's `tool_start` has a matching `tool_result`, including resync/replay; repair this in backend translation/replay if the missing completion is confirmed. Do not synthesize a success from turn completion alone when Codex reports an unresolved call.
