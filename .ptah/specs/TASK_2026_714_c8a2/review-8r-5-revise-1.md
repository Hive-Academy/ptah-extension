## Root cause assessment

The previous re-arm is fixed for a Codex turn that has already left the broadcaster. `publish` awaits `streamEventsToWebview` (`codex-chat-host-ports.ts:447-448`). That function swallows the stream rejection, including a `webviewReported` failure (`chat-stream-broadcaster.service.ts:315-383`), and deletes the streaming id in `finally` before the promise resolves (`chat-stream-broadcaster.service.ts:395`). A failed Codex follow-up and a completed one therefore both return `{ success: true, sessionId, settled: true }` from the live path (`chat-session.service.ts:1290-1310`). The resumed Codex path now awaits the same loop before `promptDelivered` (`chat-session.service.ts:1965-1981`) and returns `settled: true` once `isStreaming(sessionId)` is false (`chat-session.service.ts:1254-1259`).

The renderer `settled` branch (`message-sender.service.ts:867-875`) does not strip the user bubble, the assistant reply, or the failure notice.

- `removeUserPromptBoundary` drops the queued-prompt entry and, only when `streamingState.events.get(clientMessageId)` is a user `message_start` whose `messageId` is that same id, that one event (`accumulator-core.service.ts:679-694`, `streaming-handler.service.ts:191-198`). It does not call `setMessages`. The optimistic user bubble stays in `tab.messages`.
- The Codex user echo is a different event id, `codex-user:${session.id}:${turnId}`, with `messageId` set to the client id (`codex-chat-turn-stream.ts:250-260`). After dedup replaces the provisional boundary, `events.get(clientMessageId)` no longer holds the echo, so the settled removal does not delete it. Assistant deltas and the failure notice use their own message ids.
- `markLoaded` writes `status: 'loaded'` only (`tab-manager.service.ts:1798-1799`). `markTabIdle` drops the spinner set and the `AbortController` without aborting (`tab-manager.service.ts:3275-3281`, `3363-3364`). `setStatus('loaded')` does not clear `messages` or `streamingState`. Streaming bubbles still render from `streamingState` when status is `loaded` (`chat-transcript.component.ts:496-544`). The empty skeleton requires `isStreaming`, which is `streaming` or `resuming` (`chat-transcript.component.ts:456-458`, template `164`).
- A failed turn does not take the `CODEX_RUNTIME_FAILED` branch (`message-sender.service.ts:837-846`). The broadcaster resolves, so the RPC is success plus `settled`, with no `errorCode`. `CHAT_ERROR` stays suppressed for `webviewReported` (`chat-stream-broadcaster.service.ts:372`). The notice yielded before the `failed` turn state remains. This is the same settled branch a completed slash command already uses.

Claude is unchanged. The resume await is gated on `deliversFollowUp && execution.runtime === 'codex-app-server'` (`chat-session.service.ts:1974-1976`). `promptDelivered` uses the same gate (`chat-session.service.ts:1979-1980`). A Claude loop is attached when `sendMessageToSession` resolves, so `nativeFollowUp` is false and the reply stays `{ success: true, sessionId, enqueued: true }`.

Stop during the await does not abort the `chat:continue` promise. `handleStop` calls `chat:abort` (`chat-input.component.ts:1811-1815`, `conversation.service.ts:463-465`). The signal on `chat:continue` is the tab-close controller (`message-sender.service.ts:285-311`). After abort, the broadcaster resolves and the success `settled` path runs. Closing the tab does abort that signal and would surface `RPC aborted: chat:continue`.

## Defects

1. `chat-session.service.ts:1974-1976` and `chat-session.service.ts:1294-1310` (severity: high). Both Codex `chat:continue` paths now hold the RPC open until the broadcaster loop finishes. The renderer starts no override timeout (`message-sender.service.ts:807-828`). `chat:continue` is an admission method, so `ClaudeRpcService` uses `CHAT_ADMISSION_RPC_TIMEOUT_MS` (`claude-rpc.service.ts:32-33`, `150-154`), which is `90_000 + 30_000` (`rpc-chat.types.ts:33-48`). At 120s the timer deletes the pending call and resolves `{ success: false, error: 'RPC timeout: chat:continue' }` (`claude-rpc.service.ts:173-184`). The late host reply is dropped. `runContinueConversation` then rolls back the prompt boundary, `markLoaded`, `markTabIdle`, and `setStatus('loaded')` (`message-sender.service.ts:849-865`) while the turn is still running, and `showSendFailure` appends an assistant bubble `Message delivery failed. RPC timeout: chat:continue` (`message-dispatch.service.ts:250-251`, `418-429`). The host `RpcHandler` only slow-warns; it does not cancel the handler. Electron `ipc-bridge.ts:388-407` has no second timer, so this renderer timer is the one that fires. The resume await is new in this batch. The live follow-up already awaited `publish` before this batch and has the same false error for any Codex turn longer than 120s. The admission budget is documented as the named-account deadline, not a turn budget (`rpc-chat.types.ts:23-46`).

## Notes

- Live-turn vs ended-turn reply. `nativeFollowUp` is captured only when neither session id nor tab id is streaming and `acceptsFollowUpWithoutStream` is true (`chat-session.service.ts:1290-1293`). That router answer is native `canSendFollowUp`: a registered thread that is not busy, blocked, or closing (`session-runtime-router.ts:90-94`, `codex-chat-session-controls.ts:57-59`). Codex `sendMessageToSession` awaits `publish` (`codex-chat-adapter.ts:483-497`, `567`). The streaming id is added synchronously at loop start and removed in `finally` before resolve, so a resolved send is not streaming and the post-check returns `settled`. A loop that is already attached makes `nativeFollowUp` false; `turn()` throws `busy` if `session.busy` (`codex-chat-adapter.ts:529`), so a second send during the turn is an error result rather than `enqueued`. An ended idle thread with the flag still true returns `settled`, which is what skips `markStreaming` (`message-sender.service.ts:877-882`).
- A follow-up that starts while the previous loop is still inside `await settle()` (`chat-stream-broadcaster.service.ts:393-395`) would see `isStreaming` true, skip `nativeFollowUp`, await its own full publish, and still return `enqueued` after that turn has ended. `settle()` resolves when the transport send finishes, and the id delete is synchronous on that continuation, so the renderer’s next `chat:continue` normally arrives after the delete. I did not find a same-tick window that reproduces the old skeleton on the single in-flight send.
- Specs assert the `chat:continue` payload and fail on the old replies. Failed and completed follow-ups require `settled: true` (`chat-continue-codex-resume-once.spec.ts:229-256`); the old service returns `enqueued: true`. Resume-with-prompt, attachment-only resume, and the deferred ended-resume require `settled: true` (`:166-188`, `:274-309`); the old service returns `{ success: true, sessionId }`. The ended-resume case holds the reply until `finishBroadcast`. `chat-session.native.spec.ts:611-615` requires `settled: true` for the mocked live follow-up whose send resolves with no attached loop. The broadcaster spec (`chat-stream-broadcaster.service.spec.ts:1054-1096`) keeps one `failed` terminal, four chunks, no `chat:error`, and no `chat:complete`; it passes on the restored broadcaster and does not claim to prove the RPC result.

They lock the ended-send reply. They stay green if the post-check is deleted and every `nativeFollowUp` returns `settled` while a loop is still attached.
